## 1. Role of the data source layer and architectural patterns (PEAA p.40-44)
- The data source layer communicates with the infrastructure; most of it is talking to a relational database, and SQL is the common base, with vendor extensions `[from source] (PEAA p.40)`.
- First set: **architectural** patterns, which determine how the domain logic talks to the database; the choice is far-reaching and hard to refactor; it is affected by the design of the domain logic `[from source] (PEAA p.40)`.
- Recommendation: separate SQL access from the domain logic into their own classes, generally one class per table; these classes form a **Gateway (466)**; the rest of the application does not need to know about SQL and the DBAs have a clear place to work `[from source] (PEAA p.41)`.
- Two uses of Gateway: **Row Data Gateway (152)** (one instance per returned row) and **Table Data Gateway (144)** (one instance per table, with methods that return a **Record Set (508)**) `[from source] (PEAA p.41)`. The author uses a Gateway even in simple applications `[from source] (PEAA p.42)`.
- Table Data Gateway combines well with Record Set and is the obvious choice with **Table Module (125)**; it is also worth it for organizing *stored procedures* `[from source] (PEAA p.42)`.
- With **Domain Model (116)**: if the model is simple and matches one class per table, each domain object can load and save itself, the **Active Record (160)**; it can be seen as a Row Data Gateway plus domain logic, especially when seeing repetition across several **Transaction Scripts (110)** `[from source] (PEAA p.42)`.
- With more complex logic, Active Record breaks: the 1:1 class-table mapping fails, the relational database does not handle inheritance (making GoF *strategies* hard to use), and testing the logic without the database becomes difficult `[from source] (PEAA p.42-43)`. The better route is to isolate the Domain Model from the database with **Data Mapper (165)**, which handles all loading/saving and lets both vary independently; it is the most complicated, but provides complete isolation `[from source] (PEAA p.43)`.
- The author's guide: do not use Gateway as the primary persistence mechanism of a Domain Model; simple logic and close correspondence: Active Record; something more complicated: Data Mapper; **do not mix** primary persistence mechanisms `[from source] (PEAA p.43)`.
- "Table" in the text also stands for views, encapsulated queries and procedures; updating views is more complicated `[from source] (PEAA p.44)`.
- **Object-oriented databases**: they would eliminate the mapping; the anecdotal observation is that mapping to relational consumes around **one third** of the programming effort, a cost that continues in maintenance; most projects do not use them because of the **risk** `[from source] (PEAA p.44)`. Even so, the author advises considering **O/R mapping tools** when there is a Domain Model, and knowing the patterns to understand the options `[from source] (PEAA p.45)` `[DATED]` (mention of JDO, p.45).

## 2. The behavioral problem (PEAA p.45-47)
- The hardest part of O/R mapping is the architectural and behavioral part: how objects load and save themselves `[from source] (PEAA p.45)`.
- **Unit of Work (184)**: keeps track of everything read and modified and coordinates the write; the programmer says "commit" instead of saving each object; it works as the controller of the mapping `[from source] (PEAA p.45-46)`.
- **Identity Map (195)**: records each row read so there are not two objects for the same row; helps coordinate updates; can serve as a cache, but the main purpose is to keep **correct identities, not performance** `[from source] (PEAA p.46)`.
- **Lazy Load (200)**: a placeholder in place of the reference to avoid pulling a huge graph from the database `[from source] (PEAA p.46)`.
- Reading data: *finder* methods that wrap SELECTs; with row-based classes, use separate **finder objects** to be able to swap the database in tests with a **Service Stub (504)**; finders work on the state of the database, not of the in-memory objects `[from source] (PEAA p.47)`. Practical performance rules: bring several rows at once, never make repeated queries on the same table for several rows, and prefer bringing too much to bringing too little (careful with pessimistic locks); databases are optimized for up to three or four *joins* per query; profile with your database and data `[from source] (PEAA p.47-48)`.

## 3. Structural mapping patterns (PEAA p.48-54)
- Relationships: objects use references, databases use keys; collections in objects become foreign keys on the "many" table `[from source] (PEAA p.48-49)`. Use **Identity Field (216)** to hold the relational identity, **Identity Map (195)** as a lookup table and **Foreign Key Mapping (236)** to link references; without the key in the map, go to the database or use Lazy Load `[from source] (PEAA p.49)`.
- If the collection's objects are only used within the owner's scope: **Dependent Mapping (262)**; many-to-many: **Association Table Mapping (248)** `[from source] (PEAA p.50)`.
- Pitfall: relying on the **order** of collections; consider unordered sets or define the order in the query; update order and referential integrity (defer the check to the end of the transaction, topological sort or a fixed table order) `[from source] (PEAA p.51)`.
- Small value objects (dates, money) do not become a table: **Embedded Value (268)**; no Identity Map for them. To group objects into a column: **Serialized LOB (272)** (BLOB/CLOB, for example XML), good for hierarchies and for reducing round trips to the database, but SQL cannot see inside, so only when you do not want to query the parts `[from source] (PEAA p.51-52)`.
- **Inheritance**: three options, **Single Table Inheritance (278)**, **Concrete Table Inheritance (293)** and **Class Table Inheritance (285)**; the trade-offs are structure duplication vs access speed: Class Table is the simplest class-table relationship, but requires several joins; Concrete avoids joins, but is fragile to changes; Single Table may waste space and become a bottleneck, but gathers everything in one place and avoids joins; they can be combined `[from source] (PEAA p.52-54)`. The author's first choice tends to be Single Table Inheritance because it is easy and resilient to refactoring; talk to the DBAs `[from source] (PEAA p.54)`.

## 4. Building the mapping (PEAA p.54-57)
- Three situations: a schema you choose; an existing immutable schema; an existing negotiable schema `[from source] (PEAA p.54)`.
- Own schema with simple logic (Transaction Script or Table Module): design the tables around the data, with Row/Table Data Gateway; with Domain Model, do not let the model look like the database; Data Mapper gives more flexibility, Active Record works if an isomorphic design makes sense `[from source] (PEAA p.55)`.
- Iterate: six months of Domain Model without a database is very risky; use iterations of at most six weeks, integrating each part with the database `[from source] (PEAA p.55)`. Existing schema: Gateways mirroring the database for simple logic; Domain Model with Data Mappers for complex logic `[from source] (PEAA p.55)`.
- **Double mapping**: data from several sources; an intermediate logical schema only pays off with many similarities `[from source] (PEAA p.55-56)`.
- **Metadata Mapping (306)**: a metadata file describes columns and fields; avoids repetitive code through code generation or reflection; that is why commercial tools use metadata; on top of it, **Query Object (316)** and **Repository (322)**, which hides the database and works well with a rich Domain Model `[from source] (PEAA p.56-57)`.

## 5. Connections and miscellany (PEAA p.57-60)
- Connections: expensive in many environments; use a *pool* only if you measure a gain; they must be closed as soon as possible; every command in a transaction uses the same connection; passing the connection as a parameter pollutes signatures; a thread-scoped **Registry (480)** is an option; relying only on the garbage collector to close is a bad main strategy, acceptable as a safety net `[from source] (PEAA p.57-58)`. Tie the connection to the transaction; a **Unit of Work** can manage both; a disconnected Record Set requires attention to concurrent changes `[from source] (PEAA p.59)`.
- `select *` can break with positional indexes; prefer indexes by name (perhaps slower: measure); keep simple CRUD tests per mapping structure; prefer precompiled static SQL and avoid string concatenation to build queries; batch queries in production `[from source] (PEAA p.59-60)`.
- Further reading: Brown and Whitenack, Ambler, Yoder, Keller and Coldewey `[from source] (PEAA p.60)`.
