# ASVS V14 Configuration (p.61-64) and Appendix C IoT (p.69-71)

Source: ASVS 4.0.3. `L1/L2/L3` = required at that level.

## V14 — Configuration
### Objective (ASVS p.61)
- [from source] Requirements: a secure, repeatable and automatable build environment; hardened management of libraries, dependencies and configuration so that **outdated or insecure components are not included**. The "out of the box" configuration must be secure enough to be on the Internet (ASVS p.61).
- [from source] Build pipelines are the basis of repeatable security: every flaw discovered can be fixed in the code, the build or the deploy scripts and tested automatically; the book encourages pipelines with automatic security and dependency checks that **warn or break the build**; irregular manual steps create avoidable errors (ASVS p.61). With software-defined infrastructure and containerized builds it is possible to automatically build and deploy a "known good" replacement for any compromised system; in the traditional model, harden and back up manually to allow quick replacement (ASVS p.61).
- [from source] Compliance with V14.1 requires an automated build system and access to the build and deploy scripts (ASVS p.61).

- [from source] L1 note: V14.2.1 at L1 involves observing/detecting client-side libraries and other components, not the build-time static analysis/dependency check, which is more precise and discoverable by interview (ASVS p.62).
- [from source] V14.3: production configurations must be hardened against common attacks (debug consoles, XSS, RFI) and eliminate trivial information-discovery "vulnerabilities", rarely high risk on their own but chained with others; V14.2 says that failure to keep dependencies up to date is the root cause of the largest and most expensive attacks (ASVS p.62).
- References (ASVS p.64): WSTG 4.1 HTTP Verb Tampering and Configuration/Deployment Management; Content-Disposition in APIs (helps against Reflected File Download); CSP Cheat Sheet; CORS misconfiguration; sandboxing of third-party components.
- Contrast with the OCRG: the OCRG (A5, A9) is heavily centered on 2017 Java/.NET framework configuration (struts-config, web.xml, IIS/web.config; see `references/ocrg-a5-misconfiguracao-e-a9-componentes.md`) and has a header table (Table 11, OCRG p.54) including `X-XSS-Protection` `[DATED]`; it does not mention Referrer-Policy, SBOM or SRI (terms absent from the text).

## Appendix C — IoT requirements (preview) (ASVS p.69-71)
- [from source] The IoT chapter left the main branch; it is a preview of a future IoT ASVS and anyone who needs it should prefer the OWASP IoT project. Objective: controls equivalent to those of the server, in a trusted environment; sensitive data in hardware (secure element); TLS for transmitted data (ASVS p.69).
- The table uses the "Since" column (4.0) in place of CWE; IDs C.1 to C.34 (**34 items**) (ASVS p.69-71). Examples: C.1 debug interfaces (USB/UART/serial) disabled or protected; C.2 unique keys/certificates per device; C.3 ASLR/DEP; C.4 JTAG/SWD disabled; C.7-C.10 TLS and authenticated/encrypted wireless communication; C.12 **SBOM** per firmware; C.13 review third-party code/binaries for hard-coded credentials; C.19 boot image signature validation; C.21 signed firmware; C.22 anti-rollback (ASVS p.69-70). Levels: L1 (14 items), L2 (24), L3 (34) in the extracted data.
- Boundary: IoT/firmware is outside this agent's core specialty; use it as a requirements list and state the limitation.
