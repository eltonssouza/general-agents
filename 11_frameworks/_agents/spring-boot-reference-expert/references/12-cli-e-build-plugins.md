## CLI
- **[from source]** Command-line tool for prototyping with Groovy scripts; installation (SDKMAN!, Homebrew, MacPorts, Scoop, manual) in SBR p.29-31, 541. `spring run app.groovy` (options `--autoconfigure`, `--classpath`, `-cp`, `--no-guess-dependencies`, `--no-guess-imports`, `-q`, `-v`, `--watch`); app args after `--` (e.g. `spring run hello.groovy -- --server.port=9000`); `JAVA_OPTS` for the JVM (SBR p.542-543). On Windows, when setting `JAVA_OPTS` quote the whole statement, e.g. `set "JAVA_OPTS=-Xms256m -Xmx2048m"`, so the values reach the process correctly (SBR p.543).
- **[from source]** Deduced dependencies (the CLI tries to deduce what to `@Grab` from the code; e.g. `@RestController` → Spring MVC + Tomcat). Table of "grab hints" (SBR p.543): `JdbcTemplate`/`NamedParameterJdbcTemplate`/`DataSource` → JDBC application; `@EnableJms` → JMS; `@EnableCaching` → cache abstraction (caching abstraction); `@Test` → JUnit; `@EnableRabbit` → RabbitMQ; `extends Specification` → Spock test; `@EnableBatchProcessing` → Spring Batch; `@MessageEndpoint`/`@EnableIntegration` → Spring Integration; `@Controller`/`@RestController`/`@EnableWebMvc` → Spring MVC + embedded Tomcat; `@EnableWebSecurity` → Spring Security; `@EnableTransactionManagement` → transaction management. For the exact detail, the book says to see the `CompilerAutoConfiguration` subclasses in the CLI source code. JPA annotations such as the entity one are **not** in the table (SBR p.543). Other points: `@Grab` without a version consults metadata of the CLI version, `@DependencyManagementBom` (at most once), automatic main (SBR p.543-545). **CLI context:** "Custom Dependency Management" (SBR p.544-545) refers only to the CLI: it uses the `spring-boot-dependencies` management when resolving `@Grab`, and extra BOMs declared with `@DependencyManagementBom` (coordinates groupId:artifactId:version) override the default, with the given order applying when there are several (SBR p.544-545); it is **not** the version override in Maven/Gradle projects (SBR p.42, 876-881; references/14).
- **[from source]** `spring jar my-app.jar *.groovy` packages (default includes/excludes in SBR p.545); `spring init --dependencies=web,data-jpa my-project` and `--list` use start.spring.io; `--build`, `--java-version`, `--packaging` (SBR p.545-546); `spring shell` (SBR p.546-547); `spring install/uninstall` extensions (SBR p.547); `beans{}` DSL (SBR p.547-548); Maven `settings.xml` honored (offline, mirrors, servers, proxies, profiles) (SBR p.548). Completion commands: `grab help jar run test version` (SBR p.31).
- **[inference]** The CLI is a prototyping tool; the text suggests migrating to a Maven/Gradle project when you reach its limits (SBR p.549).

## Plugins
- **[from source]** Maven plugin (packages executable jar/war, `run`); Gradle plugin (requires Gradle 6.8, 6.9, 7.x or 8.x; packages, runs, uses the `spring-boot-dependencies` management) (SBR p.550). AntLib: tasks `exejar` and `findmainclass`; **`exejar`**, attributes and whether required (table with a Required column): `destfile` (jar to create) **required**, `classes` (root of the `.class` files) **required**, `start-class` (main class) **optional** (if omitted, uses the first class found that declares `main`); nested elements: `resources` (one or more Resource Collections added to the jar contents) and `lib` (Resource Collections added to the runtime classpath libraries); the book shows two examples, one with `start-class` and another with automatic detection (SBR p.551-552); use `ant -lib <dir with spring-boot-antlib-2.7.18.jar>` (SBR p.550-552). Other systems: `spring-boot-loader-tools` (`Repackager`, `Libraries`) (SBR p.552-554).
- **[from source, how-to]** `build-info` (Maven goal; Gradle `springBoot { buildInfo() }`) generates the build info file read by the Actuator (`META-INF/build-info.properties`) (SBR p.468); `git.properties` via `git-commit-id-plugin`/`gradle-git-properties` (date format `yyyy-MM-dd'T'HH:mm:ssZ`) (SBR p.652-654).
- **[from source, how-to]** Build info in detail: both the Maven and the Gradle plugin generate a file with the project's coordinates, name and version and accept additional properties; when the file exists, Boot auto-configures a `BuildProperties` bean (SBR p.652-653). Maven: add to `spring-boot-maven-plugin` (version 2.7.18 in the example) an `<execution>` with the `build-info` goal; Gradle: `springBoot { buildInfo() }` (SBR p.653). The file is `META-INF/build-info.properties` and the `info` endpoint publishes its data (SBR p.468).
- **[from source, how-to]** Git info in detail: Maven and Gradle generate a `git.properties` with the repository state at build time (SBR p.653). In Maven, `spring-boot-starter-parent` **already ships the plugin pre-configured**: just declare the `git-commit-id-plugin` (group `pl.project13.maven`) in the POM, with no configuration (SBR p.653-654). In Gradle use the `com.gorylenko.gradle-git-properties` plugin (version 2.4.1 in the example) (SBR p.654). Both let you configure which properties go into `git.properties`. By default the `info` endpoint exposes `git.branch`, `git.commit.id` and `git.commit.time` and the value of `git.commit.time` must be in the format `yyyy-MM-dd'T'HH:mm:ssZ` (the default of both plugins), which allows parsing to `Date` and controlling the JSON format through Jackson's date settings (SBR p.467, 654).
- **[from source, how-to]** Overriding managed versions: the `spring-boot-dependencies` POM manages the versions; the Maven and Gradle plugins let you customize them through **build properties** documented in each plugin (the text points to the Maven plugin and Gradle documentation, which are not part of this collection). Warning from the book: each Boot release is designed and tested against a specific set of third-party dependencies and overriding versions may cause compatibility problems (SBR p.654).
- **[from source, how-to]** Executable jar with Maven: with `spring-boot-starter-parent` it is enough to declare `spring-boot-maven-plugin` (`repackage` is already on); without the parent you must add `<executions>` with the `repackage` goal (SBR p.654-655). Boot application as a dependency: not the intended use; prefer moving shared code to a separate module; if you cannot, configure the plugins to produce an extra artifact with a `classifier`, because the executable jar keeps classes in `BOOT-INF/classes` and they are not found when the jar is used as a dependency (SBR p.655).
- **[from source, how-to]** Overriding managed versions can cause incompatibilities (each release is tested with the set of dependencies) (SBR p.654). Maven executable jar: `repackage` (already on with `starter-parent`) (SBR p.38, 654-655). A Boot app **does not work as a dependency** (classes in `BOOT-INF/classes`); use `classifier` `exec` or a separate module (SBR p.655-656); the classifier goes on the executable archive name and leaves the default archive for use as a dependency (SBR p.655); XML from the book (p.656): inside `<configuration>` of `spring-boot-maven-plugin`, `<classifier>exec</classifier>`. **`requiresUnpack` (SBR p.656):** most nested libraries do not need to be unpacked; some cause problems (example from the book: JRuby has its own nested jar support and assumes `jruby-complete.jar` is a direct file); you mark the nested jar to be **unpacked automatically on the first run of the executable jar**; the unpacked jars go under the temporary directory of the system property **`java.io.tmpdir`**; the book **warns** that the operating system must be configured **not to delete** those jars while the application runs; the book says nothing more about cleanup/retention (gap: any cleanup policy is an **[extrapolation]**). Example XML (Maven): in `<configuration>` of `spring-boot-maven-plugin`, `<requiresUnpack><dependency><groupId>org.jruby</groupId><artifactId>jruby-complete</artifactId></dependency></requiresUnpack>` (SBR p.656). Remote debugging with `jvmArguments` (SBR p.657).

## Executable jar format (Appendix E)
- **[from source]** Structure: `BOOT-INF/classes`, `BOOT-INF/lib`, loader classes at the root; war: `WEB-INF/lib` and `WEB-INF/lib-provided` (SBR p.838-839). Optional indexes live under `BOOT-INF/` (SBR p.839).
- **[from source]** Indexes, common rules (SBR p.839): `classpath.idx` can exist in jar and in war; `layers.idx` "jar only" (to slice the jar into Docker/OCI layers). The syntax is YAML-compatible to ease third-party tooling, but the files are **not read as YAML**: they must follow exactly the described format, otherwise they are not used.
- **[from source]** `BOOT-INF/classpath.idx` (SBR p.839): normally generated by the Maven/Gradle plugins; lists the jar names (with the directory) in the order they enter the classpath, which in the plugins matches the order the build uses to run/test. Each line starts with dash + space and the name goes in double quotes; example from the book: items like `- "BOOT-INF/lib/dependency2.jar"`, one per line, the line order is the classpath order. The `JarLauncher` uses this file to get a predictable order (SBR p.436).
- **[from source]** `BOOT-INF/layers.idx` (SBR p.839-840): lists the layers and the jar parts of each; layers appear in the order they will be added to the image. The layer name is a quoted string, with prefix dash + space and suffix colon (`- "dependencies":`); the content (file or directory, in quotes) comes with prefix of two spaces + dash + space; a directory name ends in `/` (all its files go into the layer), a file name does not. Default layers: `dependencies`, `spring-boot-loader`, `snapshot-dependencies`, `application` (SBR p.436-437).
- **[from source, internal CONFLICT]** `layers.idx` and war: Appendix E says `layers.idx` can only be used in a jar (SBR p.839), but the images section (SBR p.437) states that Boot also supports layers for war "with the help of a layers.idx" and points to the plugins' "packaging layered jar or war". The package does not resolve the conflict: cite both pages; **[inference]** the Maven/Gradle plugin (outside the collection) decides what it generates; confirm in the plugin before promising layers for war.
- **[from source]** Launchers: `JarLauncher` (`BOOT-INF/lib`), `WarLauncher` (`WEB-INF/lib` and `lib-provided`), `PropertiesLauncher` (`loader.path`, `loader.home`, `loader.args`, `loader.main`, `loader.config.name|location`, `loader.system`; variables `LOADER_PATH` etc.); manifest: `Main-Class` + `Start-Class` (SBR p.840-843).
- **[from source]** `PropertiesLauncher`, defaults and rules: `loader.home` (resolves relative paths of `loader.path` and locates `loader.properties`) defaults to `${user.dir}`; `loader.system` (copy properties to System properties) defaults to `false`; `loader.config.name` defaults to `loader`; `loader.config.location` defaults to `loader.properties`. `loader.properties` is searched in `loader.home`, then at the classpath root, then in `classpath:/BOOT-INF/classes` (the first one that exists wins); `loader.home` only points to the file when `loader.config.location` is not given. Empty `loader.path` = `BOOT-INF/lib` (behaves like the `JarLauncher`); `loader.path` does **not** configure the location of `loader.properties` (the search uses the JVM classpath). Property search order: environment variables, system properties, `loader.properties`, exploded manifest, manifest. Placeholders are resolved against System, the environment and the file itself. Manifest/environment forms: `Loader-Path`/`LOADER_PATH`, `Loader-Home`/`LOADER_HOME`, `Loader-Args`/`LOADER_ARGS`, `Start-Class`/`LOADER_MAIN`, `Loader-Config-Location`/`LOADER_CONFIG_LOCATION`, `Loader-System`/`LOADER_SYSTEM` (SBR p.842-843).
- **[from source]** Restrictions: nested jar entries must be **STORED** (no compression); use the context classloader; `java.util.logging` uses the system classloader, so consider another logging implementation (SBR p.843). Alternatives: Maven Shade, JarClassLoader, OneJar, Gradle Shadow (SBR p.843).

## Round 4 additions: Ant and loader tools (page details)
- **[from source]** Ant task `findmainclass` (used internally by `exejar`, but usable directly): attributes `classesroot` (root directory of the `.class` files; required unless `mainclass` is given), `mainclass` (short-circuits the search) and `property` (Ant property that receives the result; optional, if omitted the result goes to the log); examples from the book: find and log, find and set (`property="main-class"`) and override and set (SBR p.552). `exejar` without `start-class` detects the start class (SBR p.551-552).
- **[from source]** Other build systems: for a tool that is not Maven, Gradle or Ant, you probably need your own plugin; executable jars follow a specific format and certain entries must be uncompressed; the Maven and Gradle plugins use `spring-boot-loader-tools`, which you can use directly (SBR p.552). `org.springframework.boot.loader.tools.Repackager` takes an existing jar or war in its constructor and has two `repackage()` methods (replace the original or write to a new destination); the nested libraries come from the `Libraries` interface (no concrete implementations, since they depend on the build; `Libraries.NONE` if the archive already includes the libraries); without `Repackager.setMainClass()`, it uses ASM to find a class with `public static void main(String[] args)` and throws an exception if there is more than one candidate (SBR p.553). The book's example uses `setBackupSource(false)` and a `library` callback with `LibraryScope.COMPILE` per dependency (SBR p.554).
