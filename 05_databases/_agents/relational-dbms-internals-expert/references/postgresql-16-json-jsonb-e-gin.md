# PostgreSQL 16: json x jsonb, containment/existence operators and GIN indexes

> Pages = PDF; PG16 printed = N − 38. Source: section 8.14 "JSON Types" (PG16 p.219-225). For the mechanics of GIN itself (posting lists, `fastupdate`), see `postgresql-16-tipos-de-indices-e-estrategias.md`. Literal quotations avoided; paraphrased text.

## 1. json or jsonb? [from source]
- PostgreSQL offers two types for JSON, `json` and `jsonb`, and the `jsonpath` type for efficient queries; both accept almost the same input values. It would also be possible to store JSON as `text`, but the JSON types enforce that each value is valid JSON and come with their own functions and operators (PG16 p.219).
- **Main practical difference: efficiency.** `json` stores an **exact copy of the input text**, which the processing functions must reparse (parse) on every execution. `jsonb` stores in a **decomposed binary** format: input is a little slower (conversion), but processing is much faster (no reparse), and `jsonb` supports **indexing** (PG16 p.219).
- Semantic consequence: `json` preserves irrelevant whitespace, the **key order** and duplicate keys (the functions consider the last one as the operative one); `jsonb` **does not preserve** whitespace, does not preserve key order and does not keep duplicate keys (only the last value remains) (PG16 p.219). The output examples are in PG16 p.220-221: numbers with E notation are printed without it in `jsonb`, which also preserves trailing fractional zeros (PG16 p.221).
- **Manual recommendation**: most applications should prefer `jsonb`, except for specialized needs, such as legacy assumptions about key order (PG16 p.219).
- Input details: `jsonb` is stricter with Unicode escapes (rejects `\u0000` and escapes of characters that do not exist in the database encoding) and rejects numbers outside the `numeric` range (NaN and infinity are not allowed); `json` does not make these checks (PG16 p.219-220). When exchanging data with systems that represent JSON numbers as IEEE 754 `double`, beware of loss of precision (PG16 p.220).
- `[inference]` for a field that the code only writes and returns whole, without searching inside, and whose original formatting matters, `json` is sufficient; for any search by key/value or by index, the manual points to `jsonb`. The question "which one to use" has a source-based answer: `jsonb` by default (PG16 p.219).

## 2. Designing JSON documents; concurrency [from source]
- JSON is flexible for fluid requirements and can coexist with the relational model, but even so a **reasonably fixed structure** in the documents is recommended, to make queries that summarize a set of documents easier (PG16 p.221).
- Concurrency: JSON follows the same rules as any type; **any update acquires a row lock on the entire row**. Therefore limit the size of documents to reduce contention among transactions that update; ideally each document is an atomic datum that business rules do not allow to be subdivided into independently modifiable parts (PG16 p.221).
- `[inference]` a large document that is heavily updated in independent fields (for example, counters and preferences in the same `jsonb`) causes unnecessary contention through the whole-row lock; splitting into columns or tables reduces this. The manual gives the principle (document = atomic datum), not this example.

## 3. Containment and existence in `jsonb` [from source]
- **Containment** (`@>`): tests whether one `jsonb` document contains another; there is no equivalent for `json`. The structure of the contained must match that of the container (after discarding array elements or object pairs that do not match); the order of array elements **does not matter** and duplicates count once. Exception: an array can contain a primitive value, but not the reverse (PG16 p.221-222). Containment is nested: `'[1, 2, [1, 3]]' @> '[1, 3]'` is false, but `@> '[[1, 3]]'` is true; `'{"foo": {"bar": "baz"}}' @> '{"bar": "baz"}'` is false (PG16 p.222).
- **Existence** (`?`): checks whether a string appears as an object key or array element **at the top level** of the value (does not look at object values or nested levels); `?|` and `?&` vary the theme (PG16 p.222-223). Objects are better than arrays for containment/existence tests with many keys, since they are internally optimized for search (PG16 p.223). Containment, on the contrary, is nested, which allows writing `doc @> '{"tags":[{"term":"paris"}, {"term":"food"}]}'` without selecting sub-objects first (PG16 p.223).

## 4. Indexing `jsonb` with GIN [from source]
- Two GIN operator classes, with performance and flexibility trade-offs (PG16 p.223):
  - **`jsonb_ops` (default)**: supports the existence operators `?`, `?|`, `?&`, containment `@>` and the jsonpath operators `@?` and `@@`.
  - **`jsonb_path_ops`** (non-default): does **not** support the key existence operators, but supports `@>`, `@?` and `@@`.
  - Manual examples: `CREATE INDEX idxgin ON api USING GIN (jdoc);` and `CREATE INDEX idxginp ON api USING GIN (jdoc jsonb_path_ops);` (PG16 p.223).
- **Trap of the operator not applied directly to the indexed column**: the default GIN index on `jdoc` serves `jdoc @> '{"company": "Magnafone"}'`, but does **not** serve `jdoc -> 'tags' ? 'qui'`, because although `?` is indexable, it is not applied directly to the indexed column. Solutions: an **expression index** `CREATE INDEX idxgintags ON api USING GIN ((jdoc -> 'tags'))`, which recognizes `jdoc -> 'tags' ? 'qui'`, or rewriting with containment `jdoc @> '{"tags": ["qui"]}'`, which the simple index on the column supports (PG16 p.224).
- Trade-off of the simple index versus the expression index: the simple index stores copies of **all** keys and values (flexible, serves queries on any key); the expression one stores only the data under the indexed key and tends to be **smaller and faster** (PG16 p.224).
- GIN supports `@?` and `@@` by extracting clauses `accessor_chain = constant` from the jsonpath pattern; the accessors can be `.key`, `[*]` and `[index]`; `jsonb_ops` also supports `.*` and `.**`, `jsonb_path_ops` does not (PG16 p.224-225).
- **`jsonb_path_ops` x `jsonb_ops`** (PG16 p.225): the former is usually **much smaller** and more specific (better when queries have keys that appear a lot in the data). The technical difference: `jsonb_ops` creates independent index items for each key and value; `jsonb_path_ops` creates items only for values, each as a **hash of the value and the keys on the path to it**. Thus, a containment search becomes very specific, but **there is no way to know whether a key appears** (hence it does not support `?`). Disadvantage: JSON structures without values (such as `{"a": {}}`) generate no entries, and searching for them requires a full index scan, which is slow; `jsonb_path_ops` is unsuitable for applications that do this frequently.
- `jsonb` also accepts `btree` and `hash` indexes, normally useful only to compare **equality of whole documents**; the btree ordering is rarely interesting (PG16 p.225).
- To choose between the two operator classes: need `?`/`?|`/`?&` (key existence) → `jsonb_ops`; only `@>`/jsonpath and want a smaller index → `jsonb_path_ops`. This follows from the text above (PG16 p.223, p.225); the size threshold in bytes or the proportion of the difference are **not** in the sources.

## 5. Interaction with SQL injection [from source]
JSON values coming from the user are data: the fact that the type is jsonb validates nothing nor prevents injection if the JSON is concatenated into SQL (see `prevencao-a-sql-injection-e-parametrizacao.md`, ANTI-INJ p.9-12). `[inference]` a JSON field filled in by the user that is later interpolated into another query is "indirect injection" (ANTI-INJ p.14).

## 6. What the manual does NOT say
- Exact maximum size of `jsonb` in bytes on these pages; millisecond gains of `jsonb` over `json`: the manual says only "slightly slower on input, much faster on processing" (PG16 p.219).
- That the flexibility of JSON "replaces" relational modeling: the manual says that both coexist and recommends a predictable structure (PG16 p.221).
