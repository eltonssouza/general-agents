# Buffer pool, storage engine and disk access

> Pages = PDF. ARCH: printed = N + 140. PG16: printed = N − 38.

## 1. Spatial and temporal control [from source]
- The paper states that sequential disk bandwidth is 10 to 100 times that of random access and that this ratio was growing (2007 figure), so the storage manager should place blocks so that large queries read sequentially (ARCH p.70). [DATED] as a number.
- Two ways to store data: direct access to a "raw" device (*raw device*) or file-system files. Raw requires dedicated partitions, is OS-specific, and lost its appeal with RAID, SAN and logical volumes (ARCH p.70-71). A common alternative: one very large file treated as an array of pages (ARCH p.71). Measurement cited by the authors: a 6% loss on TPC-C comparing raw with a large file, and DB2 reports 1% with Direct I/O (ARCH p.72). Today raw would be supported mainly for benchmarks (ARCH p.72, p.76). DBMS vendors **no longer recommend** raw storage and few customers use it (ARCH p.72). If the system uses files instead of raw and needs to write pages of a size different from the file-system page, special interfaces may be needed; the POSIX `mmap`/`msync` calls are the example given (ARCH p.72). `[DATED]` (2007).
- **Temporal control**: the DBMS must control *when* to write. OS buffering gets in the way for correctness (the WAL protocol requires the log to be written before the data pages and the commit to return only after the commit record is in the log) and for performance (OS read-ahead and write-behind ignore the plan's logic; double buffering and memory copies) (ARCH p.72-74).
- Page size: DB2 and Oracle allow configurable pages; SQL Server does not; if configurable, it should be a multiple of the file-system page (ARCH p.72).

## 2. The buffer pool [from source]
- Every DBMS keeps a **shared buffer pool** in its own memory: an **array of frames** the size of a disk block; blocks are copied without format changes, which avoids marshalling cost and external fragmentation (ARCH p.74-75).
- Associated with the array is a **hash table** that maps (1) in-memory page numbers to the frame, (2) the page's location on disk and (3) metadata: **dirty bit** and information for the replacement policy; many systems have a **pin count**: with a non-zero value the page is "pinned" and does not take part in replacement, "will not be forced to disk nor stolen" (ARCH p.75). Only a tiny fraction of the pool should be pinned at any instant; pinning too much hurts (ARCH p.75).
- The pool can be sized dynamically in commercial systems (ARCH p.74). Very large pools complicate recovery speed and checkpointing (ARCH p.76).
- The executor pins pages when an iterator references a tuple in the pool ("BP-tuple") and copies it to the heap ("M-tuple") when it needs to hold it for a long time; forgetting to unpin is a "buffer leak" (ARCH p.50-51).

## 3. Replacement policy [from source]
- Full scans of tables larger than the pool tend to flush all commonly referenced data from the pool. For this pattern recency is a poor predictor of reuse, and the paper states that **OS schemes such as LRU and CLOCK were known to do poorly** on database access patterns (ARCH p.75).
- Today (2007) most systems use "simple improvements over LRU" for full scans; example cited: **LRU-2** (ARCH p.75). Another practice: a policy that depends on the page type (a B+-tree root treated differently from a heap page), in the spirit of "domain separation" (ARCH p.75-76).

## 4. PostgreSQL [from source]
- Default page/block of **8 kB** (PG16 p.2573); `shared_buffers` default typically 128 MB (PG16 p.653).
- The `pg_buffercache` view exposes, per buffer, `isdirty`, `usagecount` ("clock-sweep access count") and `pinning_backends` (PG16 p.2885), consistent with a usage-count and pin mechanism; the view does not take buffer manager locks and therefore does not give a consistent result across buffers, and the summary functions do not take them either (PG16 p.2886-2887; details in `postgresql-16-monitoramento-views-pg-stat-e-extensoes-contrib.md`).
- **Buffer Access Strategy** (ring of buffers) appears in the sources for VACUUM and ANALYZE: `vacuum_buffer_usage_limit`, default 256 kB, range 128 kB to 16 GB, capped at 1/8 of `shared_buffers` (PG16 p.655); the `BUFFER_USAGE_LIMIT` option of VACUUM/ANALYZE (PG16 p.1677, p.2066); `pg_stat_io` mentions rings of limited size in the bulkread, bulkwrite and vacuum contexts (PG16 p.863-864).
- **Background writer**: each round it writes some dirty buffers and sleeps `bgwriter_delay` (default 200 ms), at most `bgwriter_lru_maxpages` (default 100) buffers per round (PG16 p.659).
- **Checkpoint**: flushes all dirty pages and writes a checkpoint record to the WAL; it occurs every `checkpoint_timeout` (default 5 min) or near `max_wal_size` (default 1 GB) (PG16 p.900); the write is spread out by `checkpoint_completion_target` (default 0.9) (PG16 p.901). See `wal-recuperacao-e-algoritmo-aries.md`.

## 4b. Production storage: "not being I/O-bound", RAID and write cache [from source]
- **A well-tuned transactional DBMS is normally not I/O-bound**: the paper says the throughput of a well-tuned OLTP system is usually **not** limited by I/O. In high-end installations this is achieved by buying enough disks and RAM so that repeated page requests are absorbed by the buffer pool and the I/Os are spread across the disk arms at the rate that feeds all the processors; once this "system balance" is reached, I/O latency stops being the main bottleneck and main-memory bottlenecks become the limit. Memory copies become the dominant bottleneck because RAM speed evolves much more slowly than CPU cycles per dollar (ARCH p.74). [DATED] as a 2007 trend. Therefore the statement "OLTP is always I/O-bound" is **false according to the book** and depends on how the system is tuned; `[inference]` in an unbalanced system (little RAM or few disks) the claim may hold, but the book does not make it.
- **OS hooks**: modern operating systems offer ways to get around the *double buffering* of the file cache (calls of the POSIX `mmap` family and the specific DIO and CIO interfaces), so that writes reach the disk when requested and the DBMS controls the page replacement policy (ARCH p.74).
- **Standard usage**: the administrator creates a file system on each disk or logical volume; the DBMS allocates a single large file on each and controls placement through low-level interfaces such as `mmap`; raw access remains available as a high-performance option, but its use is quickly restricted to benchmarks (ARCH p.76).
- **Disk, RAID and SAN** (ARCH p.104-106): the DBMS has a disk management subsystem that maps tables to raw devices, logical volumes or files. Mapping a table to an OS file brought historical problems (file no larger than one disk, few open descriptors, 2 GB limit); so DBMSs treat OS files as abstract storage units, and a table may span several files or several tables a single file (ARCH p.104-105). RAID and SAN devices "pretend" to be disks and complicate the DBMS: RAID performs differently after a failure (complicating the I/O cost model), disks with **write cache enabled** can corrupt data on hardware failure, and SANs with near-terabyte battery-backed caches come with more than a million lines of microcode and new failure modes that are hard to diagnose (ARCH p.105).
- **RAID underperforms in databases** (ARCH p.106): it was designed for byte-oriented storage (UNIX files), not pages; database-specific solutions for partitioning and replicating data (such as Gamma's chained declustering) do better; and RAID hides several devices behind a single interface, subverting the DBA's commands to control partitioning. Many users configure RAID to minimize space overhead ("RAID level 5"), when the database would go "much, much better" with simple mirroring ("RAID level 1"); writes on RAID 5 are poor, which causes surprising bottlenecks (ARCH p.106). In practice: most deployments use files instead of logical volumes or raw, and enterprise storage is mostly hosted on SAN (ARCH p.106).
- **Compression, flash and sparse storage** (ARCH p.76-77): flash memories are an intermediate persistent medium between disk and RAM; with RAM slower than the CPU, keeping data compressed even during processing increases residency in the processor caches, but requires compressed representations that query processing can manipulate; databases are reorderable sets of tuples, which most compression research ignores; for sparse data (thousands of columns, almost all null) attribute-value pairs and column-oriented storage are used (ARCH p.77).
- **Page size**: if configurable, it should be a multiple of the file system's (or raw device's) page size; the paper points to the discussion of the "5-minute rule", updated to "30 minutes" (ARCH p.72).

## 5. [inference]
Since the paper says LRU and CLOCK do poorly on scans (p.75) and PG16 uses a ring of buffers for VACUUM/ANALYZE (p.655), it is reasonable to infer that large scans are handled separately so as not to "pollute" the pool; **PG16 does not describe this mechanism for a plain Seq Scan**.

## 6. [extrapolation] and what the sources do NOT say
- The CLOCK algorithm with a decremented usage counter, "256 KB to 16 MB ring for Seq Scan" and the pin count "golden rule" are descriptions from the v1 package **without backing**; the sources only provide the facts in the sections above. If you need to explain clock-sweep, label it `[extrapolation]`.
- RAM/SSD/HDD latencies in ns/µs/ms that v1 cited do not appear in the sources.
- v1 claimed that the pin count prevents eviction "under no circumstances"; the text says that a pinned page is not eligible for replacement (ARCH p.75).
