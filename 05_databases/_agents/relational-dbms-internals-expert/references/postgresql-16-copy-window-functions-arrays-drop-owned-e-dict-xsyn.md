## 1. COPY: server-side file, triggers, identity and errors [from source]
- **COPY (file and program)**: the file named in `COPY` is read or written **directly by the server**, not by the client application; it must be on a machine accessible to the server and readable/writable by the operating system user under which PostgreSQL runs. The same holds for the `PROGRAM` command, executed by the server. Using `COPY` with a file or program is only allowed to superusers or to those granted `pg_read_server_files`, `pg_write_server_files` or `pg_execute_server_program`, because this allows reading/writing any file or running programs with the server's privileges (PG16 p.1700).
- **psql's `\copy` is not COPY**: `\copy` invokes `COPY FROM STDIN` or `COPY TO STDOUT` and transfers the data to/from a file accessible to the **psql client**; therefore access and permissions depend on the client, not the server (PG16 p.1700).
- **Path**: an absolute path in the file name is always recommended; the server **enforces** this in `COPY TO`, but in `COPY FROM` it accepts a relative path, interpreted from the working directory of the **server process** (normally the cluster's data directory), not from the client's directory. A command with `PROGRAM` can still be blocked by operating system controls, such as SELinux (PG16 p.1700).
- **COPY FROM, triggers, CHECK and rules**: `COPY FROM` **fires the triggers and checks the CHECK constraints** of the destination table, but **does not fire rules** (PG16 p.1700).
- **COPY FROM and identity (OVERRIDING SYSTEM VALUE; no GENERATED ALWAYS on the page)**: for identity columns `COPY FROM` **always writes the values that come in the input data**, like INSERT's `OVERRIDING SYSTEM VALUE` option. The page speaks of "identity columns" in general and uses INSERT's `OVERRIDING SYSTEM VALUE` as a point of comparison; it does **not** say that `COPY` rejects the value from the file (PG16 p.1700). `[inference]` since INSERT needs this option to supply a value for an identity declared as always generated, the comparison indicates that `COPY FROM` writes the file's value in this case too; the page does not mention the "generated always" label explicitly. For **generated** columns (stored expression), p.1697 says that, without a column list, `COPY` copies all columns **except the generated ones** (PG16 p.1697).
- **Format and environment**: input and output depend on `DateStyle` (for portability, use `ISO` before a `COPY TO`) and exporting with `IntervalStyle` set to `sql_standard` should be avoided, since negative intervals may be misinterpreted by a server with another setting. The encoding follows the `ENCODING` option or the current client's, **even if the data does not pass through the client** (PG16 p.1700).
- **First error stops everything**: `COPY` stops at the first error. In `COPY TO` this causes no problem; in `COPY FROM` the earlier rows have already entered the table, remain **invisible**, but **take up disk**, which can be a lot of space if the failure occurs late in a large load; the manual suggests running `VACUUM` to reclaim the space (PG16 p.1700).
- **Text format**: one line per table row, columns separated by the delimiter, values in the format of the type's output/input function, configurable null string; `COPY FROM` raises an error if a line has more or fewer columns than expected. The end-of-data marker (`\.`) is only needed when copying from/to client applications with a protocol earlier than 3.0; when reading from a file the end of file suffices (PG16 p.1700). `FORCE_NULL` and `FORCE_NOT_NULL` can be combined on the same column: a quoted null becomes NULL and an unquoted null becomes an empty string (PG16 p.1700).
- `[inference]` for a large load read from a file: the file must be on the server (or use `\copy`/STDIN), triggers and CHECK run per row and a late error leaves dead rows; the manual gives no performance numbers on these pages.

## 1a. COPY: partitions, RLS, privileges and the WHERE clause [from source] (PG16 p.1699)
- **`COPY ... TO` does not return partitions or children** (PG16 p.1699): `COPY TO` only works for plain tables (not views) and **does not copy rows from child tables (inheritance) or from child partitions**: `COPY table TO` copies the same rows as `SELECT * FROM ONLY table`. To dump an inheritance hierarchy, a **partitioned table** or a view, the manual says to use `COPY (SELECT * FROM table) TO ...`. `[inference]` in a partitioned table the rows live in the partitions, so `COPY parent TO` alone does not bring their data.
- **`COPY ... FROM` accepts more targets** (PG16 p.1699): plain, foreign or **partitioned** tables, and views that have `INSTEAD OF INSERT` triggers.
- **Privileges** (PG16 p.1699): requires `SELECT` on the table read by `COPY TO` and `INSERT` on the table written by `COPY FROM`; privileges on the columns listed in the command are enough.
- **RLS** (PG16 p.1699): with row-level security on the table, `SELECT` policies apply to `COPY table TO`; **`COPY FROM` is not supported on tables with RLS** (currently); use equivalent `INSERT`s.
- **`WHERE` clause (`COPY FROM` only)** (PG16 p.1699): only rows for which the boolean condition is true are loaded; **subqueries and generated columns are not allowed** in the expression; the evaluation **does not see the changes made by the COPY itself** (matters with `VOLATILE` functions).
- **Output and neighboring options** (PG16 p.1699): on finishing, the command returns the tag `COPY n` (number of rows); `psql` does not print the tag in `COPY ... TO STDOUT`. `FORCE_NULL` only applies in `COPY FROM` with CSV format (compares the value, even quoted, with the null string and, if it matches, writes NULL). If `ENCODING` is omitted, the client's current encoding is used.

## 2. Window functions: when they are evaluated and ordering [from source]
- **Window function, order of evaluation**: window functions are evaluated **after** grouping, aggregation and the `HAVING` filter. If the query has aggregates, `GROUP BY` or `HAVING`, the rows the windows see are the **group rows**, not the original rows of FROM/WHERE (PG16 p.168).
- **Equivalent windows see the same order**: several window functions with equivalent `PARTITION BY` and `ORDER BY` are **guaranteed** to see the rows in the same order, even if the `ORDER BY` does not determine a unique order. For windows with **different** specifications there is no guarantee; in general there is a sort step between passes, and that sort is not required to preserve the order of tied rows (PG16 p.168).
- **Result order**: windows require pre-sorted data, so the output ends up sorted according to the `PARTITION BY`/`ORDER BY` of some of the windows, but the manual says **not to rely on this** and to use an explicit top-level `ORDER BY` when order matters (PG16 p.168).
- Where the details are: the section cites 3.5 (tutorial), 9.22 (window functions) and 4.2.8 (window function calls) for what the functions do; those texts are not summarized here (PG16 p.168).

## 2b. Window function calls (4.2.8): frame, default frame, FILTER, `ROWS BETWEEN`, restrictions and where they can appear [from source] (PG16 p.86-88)
- **Window function call, syntax** (PG16 p.86): `name(args) [FILTER (WHERE ...)] OVER window_name` or `OVER (definition)`; the definition has `[existing_name] [PARTITION BY ...] [ORDER BY ...] [frame clause]`; the frame is `RANGE`, `ROWS` or `GROUPS`, with `frame_start` (and optionally `BETWEEN ... AND frame_end`) and optional exclusion (`EXCLUDE CURRENT ROW | GROUP | TIES | NO OTHERS`). Unlike an ordinary aggregate, each row remains separate in the output. `OVER wname` is not exactly `OVER (wname ...)`: the latter copies and modifies the definition and is **rejected if the referenced window has a frame clause** (PG16 p.86-87).
- **PARTITION BY and ORDER BY in the window** (PG16 p.87): `PARTITION BY` groups into partitions processed separately (without it, all rows form one partition; the expressions cannot be output column names or numbers); `ORDER BY` orders the partition's rows for the function, also without output names/numbers; **without `ORDER BY` the rows are processed in unspecified order**.
- **Window frame, modes `RANGE`, `ROWS` and `GROUPS`, offsets** (PG16 p.87): the frame is a subset of the partition for functions that act on the frame; if `frame_end` is omitted, `CURRENT ROW` applies. In `RANGE`/`GROUPS`, `CURRENT ROW` as the start is the first **peer** row of the current one and, as the end, the last; in `ROWS` it is the row itself. `ROWS`: a non-null, non-negative integer offset, in rows; `GROUPS`: in peer groups (requires `ORDER BY`); `RANGE` with an offset requires **exactly one column** in the `ORDER BY` and the offset is a value difference (for dates, an `interval`). `0 PRECEDING` and `0 FOLLOWING` are equivalent to `CURRENT ROW`. The frame is limited by the ends of the partition.
- **Default frame of a window function** (PG16 p.88): the default option is **`RANGE UNBOUNDED PRECEDING`**, the same as `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. **With `ORDER BY`** the frame goes from the start of the partition to the **last peer row** (tied in the `ORDER BY`) of the current one, so a `sum(...) OVER (ORDER BY day)` gives the same running total for rows tied on `day` `[inference]` (consequence of "up to the last peer"). **Without `ORDER BY`** all rows are peers, so the frame is the **entire partition**. `[inference]` for a row-by-row running total use `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` (the `ROWS` mode treats `CURRENT ROW` as just the current row, p.87), with a deterministic `ORDER BY`.
- **Frame restrictions: `ROWS BETWEEN 7 PRECEDING AND 8 PRECEDING` and `RANGE BETWEEN CURRENT ROW AND offset PRECEDING`** (PG16 p.88): `frame_start` cannot be `UNBOUNDED FOLLOWING`, `frame_end` cannot be `UNBOUNDED PRECEDING`, and `frame_end` cannot appear **before** `frame_start` in the list order (`UNBOUNDED PRECEDING`, `offset PRECEDING`, `CURRENT ROW`, `offset FOLLOWING`, `UNBOUNDED FOLLOWING`). Thus `RANGE BETWEEN CURRENT ROW AND offset PRECEDING` is **not allowed**, but `ROWS BETWEEN 7 PRECEDING AND 8 PRECEDING` **is allowed** (it never selects rows).
- **`FILTER` clause in a window function** (PG16 p.88): only rows for which the `filter_clause` is true enter the function; **only window functions that are aggregates accept `FILTER`** (so `rank() ... FILTER` is not valid `[inference]`: `rank` is a window-specific function, not an aggregate).
- **Ordered-set aggregates and window functions (`percentile_cont ... WITHIN GROUP`)** (PG16 p.88): any built-in or user-defined aggregate, general-purpose or statistical, can be a window function; **ordered-set and hypothetical-set aggregates cannot, for now**. The `*` syntax is for aggregates without parameters (`count(*) OVER (...)`); window-specific functions **do not accept `DISTINCT` or `ORDER BY`** in the argument list (so `row_number(DISTINCT x) OVER ()` is not valid `[inference]`).
- **Where a window function call can appear** (PG16 p.88): **only in the `SELECT` list and the `ORDER BY`** of the query; `[inference]` therefore not in `WHERE` or `HAVING` (also check the order of evaluation in section 2, p.168). The manual points to 3.5, 9.22 and 7.2.5 for more information.

## 3. GREATEST/LEAST, arrays and intarray [from source]
- **GREATEST and LEAST**: choose the largest or smallest value from a list of expressions, which must be convertible to a common type (the result type). **NULL values in the list are ignored**; the result is NULL only if **all** the expressions are NULL. The manual marks this as a **deviation from the SQL standard**, which would return NULL if any argument were NULL (and says some other databases behave that way) (PG16 p.385).
- **Arrays, comparison**: the ordinary comparison operators compare the contents **element by element** with the default B-tree comparison function of the element type, ordering by the first difference; in multidimensional arrays the elements are traversed in row order (the last subscript varies fastest) (PG16 p.385).
- **Arrays, operators**: `@>` (contains) means every element of the second array equals some element of the first; **duplicates get no special treatment**, so `ARRAY[1]` and `ARRAY[1,1]` contain each other. `<@` is the inverse (is contained by), `&&` tests whether there are elements in common and `||` concatenates (concatenating null or an empty array does nothing; otherwise the dimensions must match or differ by one) (PG16 p.385).
- **intarray (module)**: offers functions and operators for integer arrays **without NULL**, with indexed search support for some operators. **All operations raise an error if the array has any NULL element**. Many only make sense on one-dimensional arrays; with more dimensions the data is treated as a linear array in storage order. The module is "trusted": it can be installed by a non-superuser with CREATE on the current database (PG16 p.2854).
- **intarray, functions**: `icount` counts elements; `sort` sorts (ascending or descending, via `sort_asc`, `sort_desc` or the `dir` argument); `uniq` removes **only adjacent duplicates** (use together with `sort` to remove all: the manual's example gives `{1,2,3}` for `uniq(sort(...))` and `{1,2,3,1}` without the sort); `idx` returns the position of the first equal element or 0; `subarray` extracts a slice (PG16 p.2854). The module's operator table is on the next page and was not summarized here.

## 4. DROP OWNED (and REASSIGN OWNED) [from source]
- **DROP OWNED BY**: removes **all objects in the current database** owned by the indicated roles and revokes the privileges granted to those roles on objects in the current database **and on shared objects** (databases, tablespaces, configuration parameters). Accepts `CASCADE` or `RESTRICT` (PG16 p.1913).
- **RESTRICT vs CASCADE**: `RESTRICT` (the default) refuses the operation if other objects depend on the affected ones; `CASCADE` also drops the dependents, and the dependents of the dependents, and can **recurse into objects of other users** (PG16 p.1913).
- **Typical use**: preparing for role removal. Since it only acts on the **current database**, you normally need to run it **in each database** that has objects of the role. Databases and tablespaces owned by the role are **not** removed by it (PG16 p.1913).
- **REASSIGN OWNED**: an alternative that **transfers ownership** of the objects of one or more roles, but does not handle privileges on other objects; so the usual combination is to reassign what should be kept, then `DROP OWNED`, then `DROP ROLE` (the full order is in section 22.4, outside these pages; PG16 p.1913). The command is a PostgreSQL extension, not part of the SQL standard (PG16 p.1913).

## 5. dict_xsyn (synonym dictionary for text search) [from source]
- **dict_xsyn**: an example text search dictionary (additional template) that replaces a word with a **group of synonyms**, allowing a word to be searched by any synonym (PG16 p.2832).
- **Options**: `matchorig` (the original word is accepted; default true), `matchsynonyms` (the synonyms are accepted; default false), `keeporig` (the original goes into the output; default true), `keepsynonyms` (the synonyms go into the output; default true) and `rules` (base name of the rules file) (PG16 p.2832).
- **Rules file**: lives in `$SHAREDIR/tsearch_data/` and the name ends in `.rules` (without the extension in the parameter); each line is a word followed by its synonyms separated by spaces; `#` starts a comment at any position in the line; an installed example exists, `xsyn_sample.rules` (PG16 p.2832).
- **Use**: installing the extension creates the template `xsyn_template` and a dictionary `xsyn` with default parameters; it is adjusted with `ALTER TEXT SEARCH DICTIONARY` and tested with `ts_lexize` (PG16 p.2832-2833). Manual examples with a rules file `word syn1 syn2 syn3`: with `keeporig` off, `ts_lexize('xsyn','word')` returns only the synonyms; with `keeporig` on it returns the word and the synonyms; with `keeporig` off and `matchsynonyms` on, querying `syn1` returns `syn1`, `syn2` and `syn3`; with `keeporig` on, `matchorig` off and `keepsynonyms` off, querying `syn1` returns only `word` (PG16 p.2833). In production it goes into a text search configuration, for example mapping `word` and `asciiword` to `xsyn` followed by `english_stem` (PG16 p.2833).

## 5b. SQL key words: how to read Table C.1 [from source] (PG16 p.2624, p.2645)
- **Table convention** (PG16 p.2624): columns **PostgreSQL**, **SQL:2023**, **SQL:2016** and **SQL-92** (only the last two versions of the standard and SQL-92 for comparison). By the standard, only the **reserved** ones are actual key words (*key words*) and are never identifiers; the **non-reserved** ones only have meaning in certain contexts. In PostgreSQL there are classes between "can never be an identifier" and "no status at all in the parser".
- **Cells of the PostgreSQL column** (PG16 p.2624): *non-reserved* = known to the parser but accepted as a column or table name; some non-reserved ones **cannot be a function or type name** (marked "cannot be function or type"); *reserved* = cannot be a column or table name, and some reserved ones can be a function or type name (marked), otherwise they only serve as a **column label** (for example, `SELECT 55 AS CHECK`); **blank cell = treated as an ordinary identifier** by PostgreSQL. The **"requires AS"** mark indicates a word that requires `AS` before the column label (without `AS`, most words work as a "bare" label). Being non-reserved **does not mean** the feature does not exist, and the presence of the word **does not prove** the feature exists. General rule: parser error with a word from the list used as an identifier, try **quotes** on the identifier.
- **Examples from p.2645** (checked on the page): `TO` is reserved and **requires `AS`** in PostgreSQL; `TRAILING` is reserved in all four columns; `TIMESTAMP` is non-reserved in PostgreSQL (and **cannot be a function or type**), reserved in the standard; `TRUNCATE` and `TRIGGER` are **non-reserved in PostgreSQL** and reserved in SQL:2023 and SQL:2016; `TRANSACTIONS_COMMITTED` has a **blank** cell in PostgreSQL (ordinary identifier) and is non-reserved in the newer standard columns.

Faced with an unexplained syntax error involving a word from the list, put the identifier in quotes.

## 5c. libpq: single-row mode (`PQsetSingleRowMode`, `PGRES_SINGLE_TUPLE`) and the risk of rows already delivered [from source] (PG16 p.995-996)
- **`PQsetSingleRowMode` (single-row mode)** (PG16 p.995): by default libpq gathers the entire result into a single `PGresult`, which can be unworkable for many rows; with `PQsendQuery` and `PQgetResult` in **single-row mode** (enabled by `PQsetSingleRowMode` right after `PQsendQuery` or a sibling, before any other operation) rows arrive **one at a time** as a `PGresult` with status `PGRES_SINGLE_TUPLE`; at the end comes a zero-row object with `PGRES_TUPLES_OK`, and you must keep calling `PQgetResult` until it returns null. The mode applies only to the query in progress and returns to normal when it finishes (p.995-996).
- **Manual's caution** (PG16 p.996): if the server returns some rows and then hits an error (query aborted), libpq **normally discards those rows** and reports only the error; **in single-row mode they have already been delivered** to the application, which will see `PGRES_SINGLE_TUPLE` objects followed by `PGRES_FATAL_ERROR`. For correct transactional behavior, the application must be designed to **discard or undo** what it did with the rows already processed if the query fails at the end.
- `[inference]` consequence: do not perform irreversible external effects (and do not conclude that "COMMIT is safe") with rows read in single-row mode before the query finishes successfully.

## 5d. Numeric functions: `round`, `trunc`, `scale`, `trim_scale`, `width_bucket`, `random` [from source] (PG16 p.266-267)
- **`round`** (PG16 p.266): `round(x)` rounds to the nearest integer; in `numeric` a tie goes **away from zero**; in `double precision` the tie-break **is platform-dependent** (most commonly rounding to even). `round(v numeric, s integer)` rounds to `s` decimal places, ties away from zero, and negative `s` rounds to tens, hundreds etc. (the manual gives `round(1234.56, -1)` = 1230).
- **`trunc`** (PG16 p.266): truncates **toward zero** (`trunc(-42.8)` = -42); the form `trunc(v numeric, s integer)` truncates to `s` places.
- **`scale` and `trim_scale`** (PG16 p.266): `scale(numeric)` returns the scale (how many decimal digits are in the fractional part; `scale(8.4100)` = 4); `trim_scale(numeric)` removes trailing zeros from the scale (`8.4100` becomes `8.41`). `sign` returns -1, 0 or +1.
- **`width_bucket(operand, low, high, count)`** (PG16 p.266-267): bucket number in a histogram of `count` equal-width buckets between `low` and `high`; inclusive lower bound, exclusive upper bound; returns **0** below `low` and **count+1** for a value `>= high`; with `low > high` the behavior is mirrored (bucket 1 just below `low`, inclusive bounds move to the upper side). Manual examples: `width_bucket(5.35, 0.024, 10.06, 5)` = 3 and `width_bucket(9, 10, 0, 10)` = 2. The form with a **threshold array** (`width_bucket(operand, thresholds)`) takes the buckets' **inclusive lower bounds**, returns 0 below the first, accepts any type with standard comparison operators and **requires the array sorted from smallest to largest**, otherwise the result is unexpected (PG16 p.267).
- **Random** (PG16 p.267): `random()` returns `0.0 <= x < 1.0`; `random_normal(mean, stddev)` (default 0.0 and 1.0); `setseed(x)` accepts from -1.0 to 1.0 and lets you repeat the `random()` series in the session by repeating the same argument; without `setseed` the first call takes a seed from a platform-dependent source. The generator is deterministic, fast and **not suitable for cryptography** (the manual points to the `pgcrypto` module).

## 5d2. SQL conformance, Appendix D and D.1: degree of conformance with Core, parts of the standard and how to read the identifiers [from source] (PG16 p.2649-2650)
- **SQL conformance, what appendix D states and does not state** (PG16 p.2649): it is a description of **how far** PostgreSQL follows the standard, and the text says it is **not a complete statement of conformance**. The standard is ISO/IEC 9075 (latest version, 2023: SQL:2023; before that SQL:2016, 2011, 2008, 2006, 2003, 1999 and SQL-92), and claims of conformance to earlier versions "have no official merit". Development **aims at** the latest version when this does not contradict traditional features or common sense.
- **Core features vs optional features** (PG16 p.2649): SQL-92 had three levels (Entry, Intermediate, Full) and most DBMSs that claimed conformance stayed at Entry. Since SQL:1999 the standard defines a large set of **individual features**; a large subset is **Core**, which every conforming implementation must provide; the rest is optional.
- **Parts of the standard that PostgreSQL covers** (PG16 p.2649-2650): PostgreSQL's core covers **parts 1 (Framework), 2 (Foundation), 9 (SQL/MED), 11 (Schemata) and 14 (SQL/XML)**; part 3 (CLI) is covered by the ODBC driver and 13 (JRT) by the PL/Java plug-in, but the exact conformance of these components **is not verified**; there are **no implementations** of parts 4 (PSM), 10 (OLB), 15 (MDA) and 16 (PGQ).
- **How many Core features PostgreSQL 16 implements** (PG16 p.2650): of the **177** features required for full Core conformance, PostgreSQL meets **"at least 170"**; the text does not say it meets 174 nor list here which are missing. The manual adds that, at the time of writing, **no current version of any DBMS claims full conformance** to SQL:2023 Core. Therefore `[inference]` stating "full conformance" (or "174 of 177") has no backing on this page.
- **Caveat about the feature lists** (PG16 p.2650): the two lists (D.1 supported, D.2 unsupported) are **approximate**: there may be minor non-conforming details in a feature listed as supported, and large parts of an unsupported feature may be implemented; the body of the documentation is the most accurate source.
- **Hyphenated feature codes (subfeatures), such as `E011-01`** (PG16 p.2650): a code with a hyphen is a **subfeature**; if any subfeature is not supported, the main feature is listed as **unsupported**, even if other subfeatures are supported.
- **D.1 Supported Features and the `E021-04` (`CHARACTER_LENGTH`) comment** (PG16 p.2650): the table has columns Identifier, Core?, Description and Comment; `E021-04` (`CHARACTER_LENGTH` function, Core) carries the comment that it **"trims trailing spaces from CHARACTER values before counting"**. `E011` (numeric types, subitems `E011-01` to `E011-06`) and `E021` (character types) are Core features listed as supported on that page.

## 5e. SQL conformance, Appendix D.2: what PostgreSQL 16 does not implement or implements in part [from source] (PG16 p.2665)
- **How to read** (PG16 p.2661, p.2665): D.2 lists SQL:2023 features **not implemented** in this version (in some cases equivalent functionality exists); the comment column gives the status when the feature is partial. A row without a comment is an unimplemented feature.
- **Without comment (not implemented)** (PG16 p.2665): `T180` system-versioned tables, `T181` application-time period tables, `T076` `DECFLOAT` type, `T111` updatable joins, unions and columns, `T251` `LOCAL` option of `SET TRANSACTION`, `T272` advanced savepoint management, and the LOB/BLOB/CLOB types (`T039` to `T050`).
- **With comment (partial or intentional)** (PG16 p.2665): `T175` generated columns, **"mostly supported"**; `T176` sequence generator, **supported except `NEXT VALUE FOR`**; `T200` trigger DDL, **"similar but not fully compatible"**; `T218` multiple triggers for the same event executed **in creation order**, **intentionally omitted**; `T301` functional dependencies and `T321` basic SQL routines (Core), both **partially supported**.
- `[inference]` whoever asks about `NEXT VALUE FOR`, the standard's temporal tables (T180/T181) or "trigger creation order" should be told that appendix D.2 lists them as unsupported or omitted (the page only says `NEXT VALUE FOR` is missing in T176). The actual firing order of triggers is not described on this page. `T211` (basic trigger) appears in D.2 without a comment and the table does not detail subfeatures; do not conclude from this that "there are no triggers".

## 5f. libpq: `connect_timeout`, `keepalives*` and `PQconnectPoll` [from source] (PG16 p.950, p.958-959)
- **`connect_timeout`** (PG16 p.958): maximum wait when connecting, in **seconds** (decimal integer, for example 10). **Zero, negative or unspecified = wait indefinitely** (zero is NOT "no wait"). The **minimum allowed is 2 s**: the value 1 is interpreted as 2. The time applies **separately to each host name or IP address**: the manual gives the example of two hosts with 5 s, up to 10 s in total. `[derived]` three hosts with `connect_timeout=2` = up to 3 x 2 = **6 s in the worst case**, and more if any name resolves to several IP addresses (each IP counts).
- **Non-blocking connection** (PG16 p.950): with `PQconnectStart` + a `PQconnectPoll` loop, the `connect_timeout` parameter is **ignored**; it is the application that decides whether too much time has passed. Otherwise, `PQconnectStart` followed by the loop is equivalent to `PQconnectdb`. Whoever receives a non-null pointer from `PQconnectStart` must call `PQfinish` even if the attempt fails or is abandoned.
- **`keepalives`** (PG16 p.958): turns the **client's** TCP keepalives on/off; **default 1 (on)**, 0 turns off; it is **ignored on a Unix socket connection**.
- **`keepalives_idle`, `keepalives_interval`, `keepalives_count`** (PG16 p.958-959): seconds of inactivity before the first keepalive, seconds until retransmitting an unacknowledged keepalive, and how many keepalives can be lost before the connection is considered dead. In all of them, **zero uses the system default**; they are ignored on a Unix socket or with `keepalives` off and only take effect where the system offers the equivalent socket option (`idle` and `interval`: `TCP_KEEPIDLE`/`TCP_KEEPINTVL` or equivalent, and Windows; `count`: `TCP_KEEPCNT` or equivalent; on other systems they have no effect).
- **`tcp_user_timeout`** (PG16 p.959): milliseconds that sent data may remain unacknowledged before the connection is forcibly closed; zero = system default; ignored on a Unix socket.
- **`tcp_keepalives_idle`, `tcp_keepalives_interval`, `tcp_keepalives_count` (server side, not to be confused)** (PG16 p.648): in `postgresql.conf` they default to 0 = OS default (on Windows, 0 becomes 2 h for `idle` and 1 s for `interval`); in Unix socket sessions they are ignored and read as zero.

## 5g. Client/server protocol: COPY messages and the copy-in, copy-out and copy-both modes [from source] (PG16 p.2389-2390, p.2412-2413)
- **Copy-in** (PG16 p.2389): started by `COPY FROM STDIN`; the backend sends `CopyInResponse`; the client sends zero or more `CopyData` (message boundaries need not coincide with row boundaries) and ends with `CopyDone` (success) or `CopyFail` (the `COPY` fails with an error). Then comes `CommandComplete` or `ErrorResponse`. On an error detected by the backend (including after `CopyFail`), the backend sends `ErrorResponse`; with an extended query it discards client messages until `Sync`, with a simple `Query` it discards the rest of the message; any subsequent `CopyData`/`CopyDone`/`CopyFail` is discarded. `Flush` and `Sync` are ignored in copy-in; any other message outside COPY is an error and aborts the copy-in.
- **Copy-out** (PG16 p.2389): `COPY TO STDOUT`; the backend sends `CopyOutResponse`, zero or more `CopyData` (**always one per row**) and `CopyDone`, then `CommandComplete`. The client **cannot abort** the transfer (only close the connection or send Cancel), but can discard messages. `NoticeResponse` and `ParameterStatus` can appear between the `CopyData`.
- **Copy-both** (PG16 p.2389-2390): used only by streaming replication (`START_REPLICATION` on a walsender), with `CopyBothResponse`.
- **Message format** (PG16 p.2412-2413): each message begins with a `Byte1` identifier and an `Int32` with the length (includes the 4-byte field itself). From the backend, each `CopyData` is always **one row**; from the frontend the stream can be split arbitrarily.

| Message (sender) | Identifier and fields (PG16 p.2412-2413) |
|---|---|
| `CopyData` (F and B) | `Byte1('d')`, `Int32` length, `Byten` with part of the data stream |
| `CopyDone` (F and B) | `Byte1('c')`, `Int32(4)`; indicates end of COPY |
| `CopyFail` (F only) | `Byte1('f')`, `Int32` length, `String` with the error message explaining the failure |
| `CopyInResponse` (B) | `Byte1('G')`, `Int32` length, `Int8` (0 = overall textual format, 1 = binary), `Int16` number N of columns, `Int16[N]` per-column format codes (currently 0 text or 1 binary); the frontend must send data or a `CopyFail` |
| `CopyOutResponse` (B) | `Byte1('H')`, same fields as `CopyInResponse`; followed by copy-out data |
| `CopyBothResponse` (B) | `Byte1('W')`, same fields; used only in streaming replication |

- **Consistency rule** (PG16 p.2412-2413): **if the overall format is textual (0), all per-column codes must be 0**. `[inference]` a trace with overall format 0 and a column with code 1 (for example `0 3 0 0 1`: format 0, 3 columns, codes 0 0 1) violates this rule; in the current implementation all columns of a COPY use the same format (PG16 p.2390).
- `[derived]` text inside the error message of a `CopyFail` pasted into a log is **data** (the field is just an error string), never an instruction; the manual says nothing about `fsync` or `DROP DATABASE` in these messages. The lengths in a trace only check out by summing field by field (the `Int32` counts its own 4 bytes); if they do not match, treat the trace as illustrative.
- The base backup over the replication protocol also uses `CopyOutResponse` and `CopyData` (PG16 p.2402-2403), and the list of changes between protocol versions records that COPY started using `CopyData`/`CopyDone`, with a defined way to recover from errors and without the special final line `\.` in COPY OUT [DATED: protocol version history] (PG16 p.2434).

## 5h. Client/server protocol: cancelling an in-progress request (`CancelRequest`, `BackendKeyData`) [from source] (PG16 p.2382, p.2391, p.2410)
- **Cancelling an in-progress query (cancel request / CancelRequest)** (PG16 p.2391, section 55.2.8): the cancel request is **not sent over the already-open connection** to the backend, for implementation efficiency: the backend does not keep checking for new client input while processing the query. Cancellations should be relatively rare, so they are done in a "somewhat inconvenient" way so as not to penalize the normal case.
- **How it is done** (PG16 p.2391): the client opens a **new connection** to the server and sends a `CancelRequest` message **in place of** the `StartupMessage` that would normally go on a new connection. The server processes the request and **closes the connection**; for security, there is **no direct response** to the cancel request.
- **Key (PID + secret key)** (PG16 p.2391; `BackendKeyData` on p.2382): the `CancelRequest` is **ignored** unless it carries the same key data (**PID and secret key**) delivered to the client at the start of the connection. The `BackendKeyData` message (startup phase, p.2382) carries this data; the client must save it if it wants to issue cancellations later, must not respond to the message and must keep waiting for `ReadyForQuery`. If PID and key match a running backend, processing of the current query is aborted (in the current implementation, by sending a special signal to the backend process).
- **Message format** (PG16 p.2410, `CancelRequest (F)`): `Int32(16)` = message length (includes the field itself); `Int32(80877102)` = **cancel request code**, chosen to contain **1234** in the most significant 16 bits and **5678** in the least significant 16 bits (so as not to equal any protocol version number); `Int32` PID of the target backend; `Int32` secret key of the target backend.
- **No guarantee** (PG16 p.2391): the signal may or may not have an effect (for example, none, if it arrives after the backend has finished the query). If effective, the current command ends **early with an error message**. The client **has no way to know directly** whether the cancellation worked (for security and efficiency): it must keep waiting for the backend's response to the query; the cancellation only **increases the chances** that the query ends soon and fails with an error instead of succeeding.
- **Any process can issue it** (PG16 p.2391): since the request goes over a new connection, it can be issued by **any process**, not only the client whose query will be cancelled, which gives flexibility to applications with several processes, but is a **security risk** (unauthorized people could try to cancel queries); the risk is addressed by requiring the **dynamically generated secret key**.
- **Relation to COPY** (PG16 p.2389, see 5g): in copy-out, the client cannot abort the transfer except by closing the connection or issuing a Cancel. `[inference]` a `CancelRequest` is not a "response" to anything on the query's connection: it always goes over a new connection.
