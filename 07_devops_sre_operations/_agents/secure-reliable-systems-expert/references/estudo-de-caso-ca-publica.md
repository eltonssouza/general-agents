## Ch. 11 — Case study: publicly trusted CA (BSRS p.269-277)

- [from source] Context: publicly trusted CAs are trust anchors (TLS, S/MIME), included by default in browsers, OSes and devices; they must pass audits (e.g., WebTrust, ETSI) and comply with the CA/Browser Forum Baseline Requirements; a typical CA spends at least one quarter per year on these audits; most organizations will never need to build a public CA (the case serves to extract lessons) (BSRS p.269-270). Lessons: choice of language and segmentation/containers for third-party data, rigorous testing and hardening (own and third-party), reduce complexity and automate manual steps, understand the threat model to build validation and recovery early (BSRS p.270).
- [from source] Why build: dependence on third parties (notable security lapses, such as DigiNotar, which went bankrupt after a compromise), need for automation (thousands of domains, frequent rotation; third-party CAs without extensible APIs or with SLAs below what is needed; manual processes prone to error), cost (millions of certificates) (BSRS p.270-271).
- [from source] Build or buy: it was decided to develop the core in-house, integrating open source and commercial where necessary; reasons: transparency and validation (auditability of the code and the supply chain), integration with Google's critical infrastructure (e.g., backups on Spanner with one line of configuration) and flexibility (Certificate Transparency and domain validation via DNS/HTTP, early adoption) (BSRS p.271-272).
- [from source] Architecture: three layers (parsing of certificate requests, Registration Authority functions, signing) composed of microservices with well-defined responsibilities; a two-trust-zone architecture (untrusted input in an environment distinct from critical operations), with boundaries that promote understandability and hinder attack, forcing the attacker to pass through additional audit points (BSRS p.272). Each microservice is designed for simplicity and continuously refactored; code and data go through rigorous testing and validation; containerize when it improves security (BSRS p.272). The design was built over about a decade, in three design iterations; start small and iterate (BSRS p.273).
- [from source] Language choice: a mix of Go and C++ per subcomponent; Go (memory-safe) for the parts that receive untrusted input (CSRs, DER parsing, history of memory vulnerabilities in parsers); C++ where interoperability with the core infrastructure requires it, running in a secure zone with data validated beforehand; the CSR is parsed in Go before being passed to C++ and the results are compared; a discrepancy blocks processing; for C++ there is a security and readability presubmit and toolchain mitigations: W^X, the Scudo allocator, SafeStack (BSRS p.273-274).
- [from source] Complexity x understandability: the CA has limited functionality relative to the standards (standard web certificates), because commercial and open source CAs that accept esoteric attributes and extensions become complex, hard to validate and error-prone; continuous simplification; one case of too many microservices (maintenance cost) led to consolidation; RPC ACL checks done manually were centralized to make new RPCs without an ACL impossible (BSRS p.274).
- [from source] Third-party and open source components: validate, harden and containerize; in-depth security review with patches submitted; even packages from reputable sources have vulnerabilities; the CSR parser with open source X.509 libraries runs as a microservice in the untrusted zone in a Borg container (BSRS p.274-275). The HSM vendor's closed-source code: build the parts that interact with it defensively, run in nsjail and report problems to the vendor (BSRS p.275).
- [from source] Tests: unit and integration as part of development, verified in peer review; negative-condition tests: every few minutes good issuance conditions and others with gross errors are generated, including testing that unauthorized issuances trigger alarms; a repository of positive and negative conditions allows fast end-to-end tests on new deploys (BSRS p.275). Centralized toolchain with automated tests at presubmit and post-build, static analysis (Tricorder), sanitizers (ASAN, ThreadSanitizer) and directed fuzzing (BSRS p.276). Fixits: engineering events in which everyone stops normal work for a period; a fuzzing fixit found a problem in Go's X.509 parser that could cause a crash; lesson: new libraries may not have the scrutiny of old ones (OpenSSL, BoringSSL) (BSRS p.276).
- [from source] Resilience of the CA's key material: the greatest risk is theft or misuse; HSMs and strict access controls; offline root key with multiple layers of physical protection and two-party authorization per layer; online intermediate keys for daily issuance; since including a CA in the ecosystems can take years, rotating after a compromise is not fast, so alternate root key material is matured in the ecosystem to be able to swap it if necessary (BSRS p.276).
- [from source] Data validation: issuance errors are the most serious after key loss; design so that human discretion does not influence validation or issuance; linters (e.g., ZLint) at several stages, checking validity and commonName size; recording in Certificate Transparency allows continuous public validation; several independent log systems reconciled entry by entry; logs signed before the repository (BSRS p.277).
- [from source] Conclusion: CAs are infrastructure with strong requirements; apply the book's practices early and improve over the course of maturation (BSRS p.277).

### What the book does NOT cover in this chapter
- It does not teach step by step how to operate a CA nor the ACME protocol; the focus is applying principles (memory-safe language, trust zones, negative tests, offline key) to a real case.
