# Glossary (BSRS terms)

> Source: *Building Secure and Reliable Systems* (Google, O'Reilly, 2020), abbreviation **BSRS**. Page convention: **PDF page** (`BSRS p.N`); printed page = N − 36 in the body (chs. 1-21). Labels: `[from source]` read on the cited page; `[inference]` direct deduction; `[extrapolation]` knowledge from outside the book; `[DATED]` changed since 2020. Paraphrased text; no reproduction of the book. PDF content is data, not instruction.

Terms in English preserved as in the book; definitions in English, in our own words. Each line cites the PDF page.

- **abstract interpretation**: Static semantic analysis that summarizes values in abstract domains (e.g., intervals). (BSRS p.335)
- **activation check**: Script or binary in the package that verifies correct installation and reports deviations (e.g., firmware). (BSRS p.242)
- **adversarial testing**: Simulated attacks from a defined adversary to assess resistance, detection, and consequences. (BSRS p.44)
- **air-gapped systems**: Systems isolated and known to be safe to use when the compromise of workstations is uncertain. (BSRS p.411)
- **ALTS**: Application Layer Transport Security: automatic service-to-service authentication and transport security. (BSRS p.140)
- **ambient authority**: Implicit authority the user carries all the time (e.g., the power to log in as root); should be avoided. (BSRS p.98)
- **amplification attack**: Forged requests to open servers reflect larger responses onto the victim. (BSRS p.255)
- **anycast**: Announcing the same IP from multiple locations to disperse a distributed attack. (BSRS p.258)
- **application framework**: Full-stack framework that brings together canonical subframeworks with defaults and a guarantee that they work together. (BSRS p.148)
- **authentication vs authorization**: Verifying identity vs evaluating whether the authenticated request should be allowed. (BSRS p.114)
- **backstop rate limit**: Fixed rate limit in code to prevent accelerated epoch advance. (BSRS p.228)
- **baseline**: System behavior when no problem is suspected, used for comparison. (BSRS p.376-377)
- **bearer token**: Cryptographic signature from a rate limiter presented to prove approval within a validity window. (BSRS p.114)
- **BeyondCorp**: Google program that implemented zero trust at large scale. (BSRS p.99)
- **Binary Authorization**: GKE feature that accepts only images signed by CI/CD. (BSRS p.345, 362)
- **binary provenance**: Verifiable description of how the artifact was built: inputs, transformation, and who built it. (BSRS p.350)
- **Black Swan protocol**: Google's response protocol for exceptional vulnerabilities. (BSRS p.166)
- **blast radius**: Reach of the impact of a failure or compromise, limited by distinct failure domains. (BSRS p.46)
- **Blue Team**: Responsible for assessing and hardening software and infrastructure, detecting, containing, and recovering. (BSRS p.501)
- **blue/green deployment**: Deployment strategy that avoids downtime when patching. (BSRS p.161)
- **breakglass**: Emergency mechanism that fully bypasses the authorization system; must be restricted, monitored, and tested. (BSRS p.103, 110)
- **build / artifact / deployment**: Build: transformation of artifacts; artifact: any data (file, package, commit, image); deployment: assignment of an artifact to an environment. (BSRS p.340-341)
- **CASB**: Cloud access security broker: intermediary that applies controls and logs access to cloud services. (BSRS p.392)
- **Certificate Transparency**: Mechanism for public monitoring and auditing of issued certificates. (BSRS p.272, 277)
- **change budget**: Budget of automatic policy changes; once exhausted, it requires a human decision. (BSRS p.195)
- **checksum scope**: Coverage of the checksum; including the key in the value and in the checksum detects an error of reading the wrong value. (BSRS p.375)
- **CIA triad**: Confidentiality, integrity, and availability, the traditional attributes of secure systems. (BSRS p.42)
- **clean/safe version of an asset**: Clean version of the asset, isolated from compromised versions, used to recover without recompromise. (BSRS p.460-461)
- **code signing**: Signing binaries; its value depends on what the signature represents and on key protection. (BSRS p.352)
- **collaborative debugging**: Group exercise with a driver and a note taker; actions decided by the audience. (BSRS p.384-385)
- **communications lead (CL)**: Prepares and coordinates communications for stakeholders and press. (BSRS p.446)
- **compartmentalization**: Creating small operational units and limiting access to and from each one. (BSRS p.196)
- **ComponentState**: Component-local state, outside the release, that holds the deny list, MASVN, and keys. (BSRS p.230-234)
- **concolic testing**: Concrete execution combined with symbolic analysis to generate inputs that cover other paths. (BSRS p.335)
- **configuration as code**: Configuration versioned, reviewed, and tested like code. (BSRS p.346)
- **conformance check**: Static or dynamic check that ensures code adheres to the framework's rules and practices. (BSRS p.90)
- **content addressability**: Property of immutable containers: knowing exactly which images are running and finding the susceptible ones via the registry. (BSRS p.161)
- **contextual autoescaping template**: Template that determines the context of each substitution point and escapes or requires the correct type. (BSRS p.291)
- **continuous validation**: Observing the system under realistic and controlled conditions to confirm specific properties. (BSRS p.210)
- **controlled degradation**: Choosing in advance what to disable or adjust under stress, preserving security. (BSRS p.186-188)
- **culture of awareness**: Everyone knows their security responsibilities and how to fulfill them. (BSRS p.512)
- **culture of inevitably**: Assuming failures will happen and preparing for and studying them. (BSRS p.516)
- **culture of review**: Everyone thinks about their role when approving changes (MPA, code, configuration). (BSRS p.510)
- **culture of security and reliability by default**: Security and reliability integrated throughout the lifecycle, invisible to the consumer. (BSRS p.509)
- **culture of sustainability**: Continuous effort and sufficient resources, without heroics. (BSRS p.517)
- **culture of yes**: Taking risks deliberately, measuring them, instead of a culture of "no". (BSRS p.515)
- **CVD (coordinated vulnerability disclosure)**: Process that balances the vendor's time, the reporter, and users. (BSRS p.427)
- **Cyber Kill Chain**: Model of attack stages (the book uses five: reconnaissance, entry, lateral movement, persistence, objectives) to match with defenses. (BSRS p.67-68)
- **data plane / control plane**: Separation between request processing and the policy/configuration that governs it. (BSRS p.163)
- **deep dive**: Specialized topic marked with an alligator icon in the book. (BSRS p.29)
- **defense in depth**: Application of multiple defense mechanisms, sometimes redundant. (BSRS p.46)
- **deployment choke point**: Point through which all deploy requests pass and where the policy decision is made. (BSRS p.361)
- **deviation**: Difference between intended and actual state, reported and repaired. (BSRS p.241)
- **DiRT**: Disaster Recovery Testing, Google's program that simulates internal failures. (BSRS p.48)
- **disaster / crisis**: Any situation that could justify declaring an incident and assembling a response. (BSRS p.400)
- **disaster risk assessment matrix**: Qualitative matrix in which ranking = probability (0.0 to 1.0) x impact (0.0 to 1.0). (BSRS p.535-536)
- **dogfooding**: Adopting the change on your own team before imposing it. (BSRS p.521)
- **DoS / DDoS**: Denial of service; DDoS is the kind that is only effective because it is distributed (botnet or amplification). (BSRS p.256)
- **dry run (audit mode)**: Running the change in alert or audit mode before enforcing it. (BSRS p.169)
- **dynamic program analysis**: Analysis by running the program, with instrumentation. (BSRS p.313)
- **embargo**: Restriction on disclosing a vulnerability before an agreed date. (BSRS p.164)
- **emergency access**: Minimum set of technologies for responders to reach administrative interfaces and communicate during the worst outages. (BSRS p.246)
- **emergent property**: Property that results from the interaction of components; security and reliability are like this. (BSRS p.43)
- **end-user context ticket (EUC)**: Short-lived internal ticket that authenticates a request in the context of a specific external user. (BSRS p.146)
- **epoch / ratchet**: Progress integer that only moves forward, used in place of the wall clock. (BSRS p.227)
- **exit criteria**: Criteria for declaring the incident response concluded (defined in short-term recovery). (BSRS p.401)
- **exponential backoff with jitter**: Doubling the wait after each failure and adding random duration to avoid synchronized retries. (BSRS p.264)
- **fail open / fail closed**: Failing by allowing (reliability) or by blocking (security). (BSRS p.194)
- **fail safe (fail open)**: Behavior in which, without an adversary, the system fails to a state that is safe for people (e.g., a lock that opens without power); may be vulnerable to an adversary. (BSRS p.41)
- **fail secure**: Failing while keeping the resource protected (e.g., a lock that stays closed without power). (BSRS p.41)
- **fail static**: If the controller fails, the policy remains as it is (neither fail open nor fail closed). (BSRS p.261)
- **failure domain**: Isolation boundary that limits the impact of a failure (also of a compromise). (BSRS p.46)
- **fault injection**: Injecting failures or latency into a component to test the response without affecting the whole system. (BSRS p.416)
- **feature (functional) requirement**: Requirement that describes how the user accomplishes a task; a critical subset defines viability. (BSRS p.80)
- **feature flag**: Mechanism that isolates a change; with the flag off the binary must not change behavior. (BSRS p.159)
- **first-party / third-party / related insiders**: Categories of insiders: from the organization; from third parties (open source, partners, vendors); and from the personal circle (family, housemates). (BSRS p.61)
- **fixit**: Google engineering tradition: a period in which everyone is dedicated to a common goal. (BSRS p.276)
- **flaky test**: Test that depends on unguaranteed behavior (external dependency, ordering); must be fixed. (BSRS p.311)
- **follow-the-sun**: Rotation between regions to keep responders rested. (BSRS p.439)
- **ForceCommand**: OpenSSH option that restricts an identity to a single command. (BSRS p.112)
- **forensic imaging / memory imaging / file carving**: Read-only disk copy; memory copy; recovery of deleted files. (BSRS p.434)
- **forensic timeline**: Chronological list of events to determine correlation and causality. (BSRS p.435)
- **formal methods**: Rigorous specification and verification of safety and liveness properties. (BSRS p.337)
- **fuzz engine / driver / target**: The engine generates inputs, the driver passes them to the target (the code that processes the inputs). (BSRS p.316)
- **golden image**: Complete system snapshot; may reintroduce vulnerabilities if reused without updating. (BSRS p.462)
- **Google Front End (GFE)**: Frontend layer as a microservice that terminates TLS, mitigates DDoS, and balances traffic. (BSRS p.162)
- **hacktivism**: Use of technology to call for social change; in the book, focus on the disruptive form (defacement, DDoS). (BSRS p.57)
- **hands off keyboards briefing**: IC briefing with everyone's full attention before starting remediation. (BSRS p.464-465)
- **hedging**: Qualifiers that obscure certainty in responses during the incident. (BSRS p.443)
- **hermetic build**: All inputs fully specified beforehand and outside the build, with unambiguous references. (BSRS p.357)
- **hermetic test**: Test that reproduces the same results in an isolated environment. (BSRS p.309)
- **hero mode**: Small team working overtime; unsustainable and should be rare. (BSRS p.439)
- **high-availability component**: Copy with fewer dependencies and a limited rate of change, with a proven lower probability of outage. (BSRS p.206)
- **high-capacity component**: Main fleet that serves users day to day. (BSRS p.206)
- **horses vs zebras**: Common events (horses) vs rare ones visible only at scale (zebras) when diagnosing. (BSRS p.373-374)
- **HSM**: Dedicated cryptographic processor that acts as a vault for the CA's keys. (BSRS p.275)
- **hunting / reversing / forensics groups**: Three investigation tracks: searching for fingerprints, studying binaries, and analyzing systems. (BSRS p.436)
- **hybrid engineering team**: Team of security specialists who also write code and fix bugs. (BSRS p.482)
- **ICS**: Incident Command System, US government approach to emergency command and coordination. (BSRS p.48)
- **idempotent operation**: Operation that gives the same result if applied several times; facilitates retry. (BSRS p.135)
- **identity / credential**: Identity: attributes of an entity; credentials assert the identity (password, X.509, OAuth2). (BSRS p.136)
- **IMAG**: Incident Management at Google, standard incident management program, modeled on the ICS. (BSRS p.48)
- **immutable logging**: Logs that are hard to alter, with an immutable audit trail and written remotely. (BSRS p.388)
- **in-toto**: Framework that implements provenance policies. (BSRS p.354)
- **incident commander**: Person who leads the response to an incident. (BSRS p.403)
- **incident commander (IC)**: Whoever takes command by explicit declaration, directs the response, and maintains control. (BSRS p.429)
- **initial vs sustained velocity**: Velocity at the start of the project vs over the lifecycle; ignoring security/reliability early harms the sustained one. (BSRS p.92)
- **injection sink**: API prone to vulnerability if it receives poorly validated or encoded input. (BSRS p.151)
- **insider risk**: Threat from trusted people (current or former) with access; includes malicious, negligent, or accidental scenarios. (BSRS p.60)
- **intended state**: Encoded intended state, compared with the deployed state to detect deviations. (BSRS p.240-241)
- **interceptor**: Framework component with before and after stages that perform logging, authentication, authorization, throttling, etc. (BSRS p.283)
- **IOC (indicator of compromise)**: Finite attribute of an attack (IP, hash) used to configure detection programmatically. (BSRS p.66)
- **job shadowing / swapping**: Following along with or switching teams to build empathy. (BSRS p.525-526)
- **key rotation latency**: Time to complete a key rotation cycle. (BSRS p.214)
- **KRL (Key Revocation List)**: Compact binary representation of revoked keys issued by a CA. (BSRS p.238)
- **ksplice**: Runtime kernel patching via function redirection tables, without rebooting. (BSRS p.420)
- **lame-duck mode**: Server keeps serving but signals callers to reduce or stop sending requests. (BSRS p.189)
- **last known good configuration**: Last valid configuration saved to disk to withstand loss of the configuration API. (BSRS p.204)
- **least privilege**: User with the minimum privileges needed for the work at a given moment. (BSRS p.46)
- **legacy conversion**: Single, obvious function that converts strings to a safe type, to exempt legacy code in a controlled way. (BSRS p.295)
- **load shedding**: Returning errors instead of serving excess requests to stabilize the component at peak load. (BSRS p.191-192)
- **long tail**: Long tail of use cases that take a long time to migrate in large-scale changes. (BSRS p.171)
- **low-dependency component**: Alternative implementation with minimal dependencies for the most critical cases. (BSRS p.206-207)
- **low-hanging fruit**: Short-term, easy, small-scope action items. (BSRS p.473)
- **management liaison**: Person who makes hard decisions on the spot (shut down a service, revoke credentials). (BSRS p.430)
- **MASVN**: Minimum Acceptable Security Version Number: low-water mark below which the system must never operate. (BSRS p.231-232)
- **mental model**: Simplified model the engineer uses to reason; fails under extreme conditions. (BSRS p.129)
- **mitigation doc**: Document in which action items for the formal postmortem are kept, short and long term. (BSRS p.458)
- **MITRE ATT&CK**: Framework that details each stage of the kill chain in formal techniques. (BSRS p.68)
- **multi-party authorization (MPA)**: Sensitive operations reviewed and approved by specific sets of people. (BSRS p.46)
- **mutation testing**: Altering the code (e.g., condition to false) to see whether any test fails; reveals weak tests. (BSRS p.309)
- **nonfunctional requirement**: Requirement about general system attributes, such as security and reliability. (BSRS p.81)
- **normalization of deviance**: Bugs that become "normal behavior" and stop being noticed. (BSRS p.377)
- **observability**: Property of determining what the system is doing by examining its outputs. (BSRS p.379)
- **OODA loop**: Observe, orient, decide, act. (BSRS p.438)
- **operations lead (OL)**: Tactical counterpart of the IC; the technical team reports to them. (BSRS p.430)
- **OpSec (operational security)**: Keeping the response activity secret. (BSRS p.430)
- **panic room**: Specific location with additional physical controls from which the zero trust breakglass is accessible. (BSRS p.110)
- **pass-the-hash**: Technique that reuses stolen NTLM/LanMan hashes to log in to other systems. (BSRS p.469)
- **pivot point**: Investigation question whose answer generates new questions or new systems to investigate. (BSRS p.436)
- **playbook**: Specific, procedural, end-to-end instructions for a response task. (BSRS p.409)
- **prestaging**: Preparing systems and people before the incident: logging, automatic responses, access, and procedures. (BSRS p.409-410)
- **priority model**: Scale that defines the speed and time of response; may change over the course of the incident. (BSRS p.406)
- **privilege separation (build)**: Trusted orchestrator signs the provenance; user commands run in an environment without access to the key. (BSRS p.360)
- **production readiness review (PRR)**: Production readiness review integrated into the development flow. (BSRS p.82)
- **progressive stringency**: Increasing the strictness of a control in stages (optional, then with feedback, then mandatory). (BSRS p.521-522)
- **provenance-based deployment policy**: Policy that describes properties of each environment, matched against the provenance of artifacts. (BSRS p.353)
- **pseudonymization / anonymization**: Privacy techniques for logs that preserve a session's timeline without identifying the user. (BSRS p.389)
- **publicly trusted CA**: CA included by default in browsers, OSs, and devices; subject to audits and CA/Browser Forum requirements. (BSRS p.269-270)
- **Purple Team**: Hybrid team that bridges the Red and Blue Teams. (BSRS p.502)
- **Pwn2Own / Pwnium**: Hacking contests used as forcing functions to release fixes in under 24 hours. (BSRS p.486-487)
- **quarantine / isolation**: Isolating a compromised asset (switch port, segmented network) to limit the attacker. (BSRS p.465)
- **ransomware**: Software that hijacks a system or data (usually by encrypting) until payment. (BSRS p.59)
- **recovery checklist**: List of tasks by team and skill, with commands, rollback, and a status color code. (BSRS p.464-465)
- **Red / Blue / Purple Team**: Offensive, defensive, and hybrid that ensures the Red's lessons are fixed by the Blue. (BSRS p.417-418)
- **Red Team**: Runs end-to-end offensive exercises with specific objectives, lasting weeks. (BSRS p.502-503)
- **red zone**: Region poisoned before and after allocations in ASan to detect overflow. (BSRS p.315)
- **release TPM**: Technical program manager who measures the quality and reliability of each release. (BSRS p.486)
- **remediation lead (RL)**: Prepares the cleanup plan during the investigation. (BSRS p.438)
- **reproducible build**: Same commands and inputs generate bit-for-bit identical output. (BSRS p.358)
- **resilience**: Ability to withstand major defects or interruptions, ideally continuing to operate in degraded mode. (BSRS p.179-180)
- **safe proxy**: Proxy that mediates administrative access to systems, applying auditing, access policy, MPA, and rate limiting without altering the target system. (BSRS p.73-74)
- **SafeHtml / SafeUrl / TrustedResourceUrl**: Immutable types whose security contract is guaranteed by constructors for HTML and URL contexts. (BSRS p.290-291)
- **SafeSql / SafeHtml**: Types whose values are provably safe for use in the corresponding sink. (BSRS p.151)
- **safety net / breakglass**: Emergency mechanism that reduces the fear of adopting strict controls. (BSRS p.522)
- **sanitizer (ASan/TSan/UBSan...)**: Tools that detect memory errors, leaks, data races, and undefined behavior. (BSRS p.304)
- **secure by construction**: Framework/workflow that makes classes of vulnerability infeasible (or eliminates them) during development. (BSRS p.94)
- **security boundary**: Interface between the TCB and the rest; everything that crosses it is treated with suspicion. (BSRS p.142)
- **security champion**: Member of each product engineering group who facilitates collaboration with the central security team. (BSRS p.499-500)
- **security design review**: Security review at the start of a project. (BSRS p.493)
- **seed corpus**: Set of sample files that the fuzz engine mutates. (BSRS p.318)
- **self-updating component**: Privileged component that processes its own updates (package daemon, BIOS). (BSRS p.229)
- **severity model**: Scale that categorizes the incident's impact on the organization (e.g., 0-4). (BSRS p.405)
- **short-term vs long-term initiatives**: Immediate mitigations vs fundamental changes in the security posture strategy. (BSRS p.473)
- **sinkhole (DNS)**: False resolution of known malicious domains to prevent their use and trigger alerts. (BSRS p.393)
- **Site Isolation**: Sandboxing project that isolates individual sites to contain cross-site data theft. (BSRS p.487)
- **small functional API**: Endpoint that does one thing well; basis for granting the minimum and auditing with granularity. (BSRS p.101)
- **Smart System for Intake**: Google's ticket queue front end with a dynamic questionnaire that educates and routes requests. (BSRS p.500-501)
- **social engineering**: Deceiving the victim so they help with the attack; low difficulty and high effectiveness. (BSRS p.58)
- **software supply chain**: Process of writing, building, testing, and deploying (VCS, CI, CD). (BSRS p.340)
- **stalkerware**: Cheap spyware usually used by people close to the victim. (BSRS p.59)
- **state exhaustion attack**: Idle connections fill the firewall's memory with connection tracking. (BSRS p.257)
- **strategic response**: Response that avoids informing the adversary's analysis. (BSRS p.261-262)
- **strong type (wrapper)**: Type that wraps a primitive with context or unit, avoiding confusion of parameters and units. (BSRS p.301-303)
- **structured justification**: Structured reference (bug, ticket, case) associated with an audit event for programmatic checking. (BSRS p.106)
- **success disaster**: Excessive user interest that takes the system down; abstract adversary of reliability. (BSRS p.51-52)
- **SVN (Security Version Number)**: Comparable number, independent of other versions, that marks security milestones. (BSRS p.231)
- **syncookies**: Stateless mechanism to validate new TCP connections against synflood. (BSRS p.259)
- **system (in the book)**: Group of components that cooperate toward a function, including software, hardware, and the processes of designing, implementing, and maintaining. (BSRS p.27)
- **system invariant**: Property that is always true, no matter how the environment behaves or misbehaves. (BSRS p.127)
- **tabletop exercise**: Nonintrusive simulation of an incident scenario with decision points. (BSRS p.414)
- **TCB (trusted computing base)**: Components whose correct functioning suffices to guarantee the security policy. (BSRS p.141-142)
- **technical debt**: Shortcuts (TODO/FIXME) that need process and time to be paid down. (BSRS p.297)
- **temporary access**: Time-limited access, scheduled or on demand; reduces ambient authority. (BSRS p.121)
- **Testing on the Toilet**: Weekly flyer of engineering tips, also used for security. (BSRS p.513-514)
- **threat intelligence**: Descriptions of attacks seen in the wild: reports, IOCs, malware reports. (BSRS p.66-67)
- **three-factor authorization (3FA)**: Additional approval from a second platform (e.g., hardened mobile) for sensitive requests; strengthens authorization, not authentication. (BSRS p.118-120)
- **throttling**: Delaying responses to indirectly modify the client's behavior. (BSRS p.192-193)
- **Tink**: Google cryptographic library with APIs that are hard to misuse. (BSRS p.153-154)
- **Tool Proxy**: Google binary with generic RPC that runs command lines under policy, logging, and MPA. (BSRS p.76)
- **Tricorder**: Google static analysis platform displayed in code review. (BSRS p.333)
- **trust on first use (TOFU)**: Key trusted on first use, validated with an existing OTP on the first authentication. (BSRS p.170)
- **trust zone**: Separate environment: untrusted input is handled in a zone distinct from critical operations. (BSRS p.272)
- **trusted build service / rebuilding service**: Trusted service that signs the provenance; or a quorum of rebuilders that reproduce and attest. (BSRS p.356)
- **TrustedSqlString**: Type whose SQL content is built only from source-code literals, preventing injection by construction. (BSRS p.288-289)
- **TTP (tactics, techniques, and procedures)**: Systematic description of how an attacker operates; recommended focus before trying to learn who the attacker is. (BSRS p.51, 69)
- **understandability**: Degree to which someone with relevant background reasons confidently about the system's operational behavior and invariants. (BSRS p.125-126)
- **unzipping attack**: Incremental rollback through versions until reaching a vulnerable one. (BSRS p.230)
- **Upvote**: Self-service portal for approving software outside the allow list. (BSRS p.523-524)
- **usable security**: Focus on helping users make secure decisions. (BSRS p.483-486)
- **use-after-free**: Reading memory that has already been freed, a building block of exploits. (BSRS p.315)
- **verifiable build**: Build whose binary provenance is trustworthy. (BSRS p.355)
- **verified loss of access**: Certainty that the old key became useless after rotation. (BSRS p.215)
- **Vulnerability Reward Program (bug bounty)**: Program that rewards researchers who report flaws within disclosure norms. (BSRS p.54)
- **Vulnerability Reward Program (VRP)**: Rewards program for the research community; in Chrome since 2010. (BSRS p.482)
- **vulnerability scanning vs pentest vs Red Team**: Scan: known, automatable weaknesses; pentest: set of vulnerabilities in a narrow scope, days; Red Team: goal-oriented, weeks. (BSRS p.503)
- **warm / cold storage**: Recent logs in fast storage; old ones in cheap offline storage. (BSRS p.394)
- **well-lit path**: The easy and fast path is also the secure one. (BSRS p.485)
- **Wheel of Misfortune**: Problem simulation with a test giver and a test taker. (BSRS p.385)
- **YAGNI smell**: "Just in case" functionality that creates unnecessary complexity. (BSRS p.296)
- **Zero Touch (ZTP/ZTN)**: Interfaces that remove direct human access to production roles, using automation and secure APIs. (BSRS p.99)
- **Zero Touch Prod**: Project in which every production change comes from automation, is prevalidated by software, or uses audited breakglass. (BSRS p.74)
- **zero trust networking**: Network location does not grant privilege; access decided by user and device credentials. (BSRS p.98-99)
- **zero-day vulnerability**: Vulnerability known to some attackers, not yet disclosed or discovered by the provider; patch absent or not applied. (BSRS p.165)
