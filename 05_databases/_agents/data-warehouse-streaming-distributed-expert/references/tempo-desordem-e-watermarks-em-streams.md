# Time, Disorder and Watermarks in Streams

> Convention: `(STREAM p.N)` = PDF page = printed page. Labels: `[from source]`, `[inference]`, `[extrapolation]`, `[DATED]`.

## 1. Three notions of time
[from source] In the dataflow model, applications can operate in three modes: (i) **event time** (or application time): when the event is generated at the source; (ii) **processing time**: when it is processed in the system; (iii) **ingestion time**: when it arrives at the system (STREAM p.4). Systems such as Flink and Dataflow expect a time domain to be declared; Naiad requires a logical timestamp (STREAM p.4).
- [from source] On fault tolerance, the survey notes that processing-time windows and operators that read several sources are examples of **nondeterminism** that can make the state diverge after recovery (STREAM p.17).
- [inference] It follows that using event time tends to give reproducible results on reprocessing; but the survey does **not** claim that event time is "the only deterministic dimension" (v1 had this sentence).

## 2. Disorder
- [from source] Out-of-order tuples arrive after tuples with a later event timestamp. External causes: network (different latencies) and several uncoordinated sources; internal ones: parallel join (repartitioning), windows on an attribute different from the ordering one, prioritization by another attribute and union of unsynchronized streams (STREAM p.5).
- [from source] Progress = how far the processing has advanced, quantified by an attribute A that orders the stream: it advances when the smallest value of A among the unprocessed tuples grows (STREAM p.5).
- [from source] Two architectures: *in-order* (reorders in buffers up to a lateness bound) and *out-of-order* (processes in arrival order as long as the lateness bound is not exceeded; keeps state up to that bound to include late tuples) (STREAM p.5-6). Order-insensitive operators (select, project, union, etc.) tolerate disorder (STREAM p.6).
- [from source] Ignoring out-of-order data can produce incorrect results; waiting indefinitely blocks output and accumulates state (STREAM p.6).

## 3. Progress mechanisms (Fig. 2 uses a count over 4 s tumbling windows)
- **Slack** [from source]: waits for out-of-order data for a fixed amount of a metric; originally the number of tuples between the occurrence and the expected position; it can also be time; it is a fixed grace period and is part of the user's query specification (STREAM p.6-7). A tuple that arrives beyond the slack is not accepted (STREAM p.6).
- **Heartbeat** [from source]: an external signal with a timestamp indicating that all following tuples will have a larger timestamp; generated by the source or deduced by the system (network latency, clock skew, disorder bound); an *input manager* orders in a buffer and releases tuples ≤ heartbeat; it is an internal mechanism, hidden from the user (STREAM p.6-7).
- **Low-watermark** [from source]: for an attribute A, the lowest value of A in a certain subset of the stream; future tuples will **probabilistically** have a value larger than the low-watermark; A is often the event timestamp; it allows admitting out-of-order data with A ≥ watermark and discarding associated state (e.g. join hash entries). In Fig. 2c, punctuations carrying the low-watermark decide when to close and compute windows; a tuple with t=4 after watermark t=4 is not admitted (STREAM p.7). It differs from the heartbeat because the low-watermark reflects the progress of processing inside the system (oldest pending work), and generalizes to any attribute (STREAM p.7).
- **Punctuation** [from source]: a metadata tuple embedded in the stream, with patterns over attributes; a generic vehicle for reporting progress (watermark, skew, slack), also useful for state, monitoring and flow control (STREAM p.7-8).
- **Pointstamp/frontier** [from source]: (timestamp, location) attached to each tuple; Naiad's progress frontier; allows nested iterations (STREAM p.8). Cyclic queries require special handling to avoid deadlock (STREAM p.8).
- **Triggers and revision processing** [from source]: when data arrives after the bound, triggers (Dataflow) can redo/update results; three refinement policies (accumulating by overwriting, discarding by complementing, accumulating and retracting) (STREAM p.9). Approaches: store and revise, re-execute and revise, partition and consolidate (STREAM p.9-10).

[inference] Package v1 defined the watermark as a guarantee that "no event with timestamp ≤ t will arrive". The survey's text is weaker: the watermark is a **progress indicator** (probabilistic); the one that predicts "all following tuples will have a larger timestamp" is the heartbeat. Events late after the watermark require a policy (discard or revise).

## 4. Windows
- [from source] The survey uses a 4 s *tumbling* window only as an example (Fig. 2) and mentions *sliding window* aggregation in passing (STREAM p.1, p.6, p.22). It does **not** define tumbling/sliding/session as a taxonomy nor cover *session windows*.
- [extrapolation] The tumbling/sliding/session typology (and terms such as allowed lateness and side output) comes from engine documentation and the Dataflow model, not from the survey; when citing, label it as such.

## 5. 1st vs 2nd generation on disorder
[from source] First solutions: reorder in a buffer with lateness measures (slack, heartbeats); then out-of-order processing (tracking progress without ordering) and revision; modern systems refine these concepts, popularizing low-watermarks, punctuations and triggers (Millwheel, Dataflow, Flink, Spark) (STREAM p.10). Open problems: the in-order vs. out-of-order debate, multiple notions of time, misaligned watermarks across sources (STREAM p.10-11).
