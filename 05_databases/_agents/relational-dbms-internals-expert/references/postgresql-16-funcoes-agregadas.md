# PostgreSQL 16: aggregate functions (Tables 9.59 to 9.63), `count(*)`, NULL, ordering and Partial Mode

> Pages = PDF of the PG16 manual (16.15); printed = N − 38. Section 9.21 "Aggregate Functions" = PG16 p.395-402 (Table 9.59 general-purpose p.395-397; notes p.397-398; Table 9.60 statistics p.398-400; Table 9.61 ordered-set p.400; Table 9.62 hypothetical-set p.401; Table 9.63 GROUPING p.401-402). The "Partial Mode" column of the tables says whether the function accepts partial aggregation (used in parallel aggregation, see `postgresql-16-estatisticas-planner-paralelismo-e-snapshots-antigos.md`, PG16 p.564-568); the table pages **do not explain** the concept, they only mark Yes/No. Window functions: see `postgresql-16-copy-window-functions-arrays-drop-owned-e-dict-xsyn.md` (PG16 p.168).

## 1. Table 9.59: general-purpose aggregates [from source] (PG16 p.395-397)
- **`count`** (PG16 p.395): `count(*)` counts the **input rows**; `count(expression)` counts the rows in which the value is **not null**. The result is `bigint`. Both accept partial aggregation (Partial Mode: Yes).
- **`sum`, `avg`, `min`, `max`** (PG16 p.395-397): ignore null input values. Result types of `sum`: `smallint` and `integer` produce `bigint`; `bigint` produces `numeric`; `numeric`, `real`, `double precision`, `interval` and `money` keep the type (PG16 p.397). `avg` of integers (`smallint`, `integer`, `bigint`) returns `numeric`; of `real` and `double precision` returns `double precision`; of `interval` returns `interval` (PG16 p.395). `min` and `max` work for any numeric, text, date/time or enumerated type, plus `inet`, `interval`, `money`, `oid`, `pg_lsn`, `tid`, `xid8` and arrays of those types (PG16 p.397).
- **`bool_and`, `bool_or`, `every`** (PG16 p.395-396; note p.398): `bool_and` is true if all non-null values are true; `bool_or`, if any is; **`every` is the SQL standard equivalent of `bool_and`**. The manual explains that the `bool_and`/`bool_or` aggregates correspond to the standard's `every` and `any`/`some`, but PostgreSQL only offers `every`: `any` and `some` cannot be aggregate names because of an **ambiguity in the standard syntax** (`= ANY((SELECT ...))` can be a subquery or an aggregate) (PG16 p.398).
- **`array_agg`** (PG16 p.395): gathers all input values, **including nulls**, into an array; the form that takes arrays concatenates them into an array with one more dimension (all with the same dimensionality, neither empty nor null). `any_value` returns an arbitrary value among the non-null ones. `bit_and`, `bit_or` and `bit_xor` operate bitwise on the non-null values (`bit_xor` can serve as a checksum of an unordered set).
- **`json_agg`/`jsonb_agg`** (PG16 p.396): gather all the values, **including nulls**, into a JSON array; the `_strict` versions **skip nulls**. `json_object_agg` and variants build a JSON object: keys cannot be null, values can; `_strict` skips entries with a null value; `_unique` raises an error on a duplicate key. `json_arrayagg` and `json_objectagg` are the SQL/JSON syntax forms (with `ABSENT ON NULL`, `ORDER BY`, `RETURNING`). All marked Partial Mode: **No**.
- **`string_agg`** (PG16 p.397): concatenates the non-null text (or `bytea`) values, placing the delimiter before each value after the first. **Partial Mode: Yes.** `xmlagg` concatenates the non-null XML values (Partial Mode: **No**). `range_agg` (union) and `range_intersect_agg` (intersection) work with `anyrange`/`anymultirange` and are also **No**.

## 2. Nulls, zero rows and `coalesce` [from source] (PG16 p.397)
- **With zero rows selected, every aggregate returns NULL, except `count`.** The manual stresses that `sum` of no rows returns **NULL, not zero**, and that `array_agg` returns NULL instead of an empty array; to substitute zero or an empty array, use `coalesce`.
- `[derived]` overflow arithmetic: `sum(integer)` accumulates in `bigint` (maximum about 9.22 x 10^18), and an `integer` is worth at most about 2.147 x 10^9; to overflow it would take summing more than 4.29 x 10^9 rows with the maximum value. `sum(bigint)` accumulates in `numeric` and does not overflow. `[inference]` since the aggregates ignore null inputs, `sum` of a column with only nulls also gives NULL (and `count(column)` gives 0). The type limits are in `postgresql-16-tipos-de-dados-limites-e-constraints.md`.

## 3. Order of input values [from source] (PG16 p.397-398)
- **The order is undefined by default** (PG16 p.397): `array_agg`, `json_agg`, `jsonb_agg` (and `_strict` variants), `json_object_agg`/`jsonb_object_agg` (and `_strict`, `_unique` variants), `string_agg` and `xmlagg`, as well as similar user-defined aggregates, give **different results depending on the input order**. It can be controlled with `ORDER BY` **inside the aggregate call** (section 4.2.7).
- **Alternative with an ordered subquery** (PG16 p.397-398): supplying the values from an already ordered subquery "usually works", but the manual warns that it can **fail** if the outer level has additional processing, such as a join, which may reorder the subquery output before the aggregate. That is why `ORDER BY` inside the aggregate is the safe form.

## 4. `count(*)` and performance [from source] (PG16 p.398)
- **`count(*)` on a whole table is proportional to the table size** (PG16 p.398): the manual warns those coming from other DBMSs that `SELECT count(*) FROM table` requires work proportional to the size: PostgreSQL scans **the whole table or an entire index that includes all rows**. There is no ready-made row counter. `[inference]` this follows from MVCC: each transaction may see a different set of rows, so there is no single total valid for all; the page does not give this explanation.

## 5. Table 9.60: statistics [from source] (PG16 p.398-400)
- **Functions**: `corr`, `covar_pop`, `covar_samp`, `regr_avgx`, `regr_avgy`, `regr_count`, `regr_intercept`, `regr_r2`, `regr_slope`, `regr_sxx`, `regr_sxy`, `regr_syy`, `stddev`, `stddev_pop`, `stddev_samp`, `variance`, `var_pop`, `var_samp` (PG16 p.398-400). `numeric_type` inputs accept `smallint`, `integer`, `bigint`, `numeric`, `real` and `double precision` (PG16 p.398). **`stddev` is a historical alias of `stddev_samp` and `variance`, of `var_samp`** (PG16 p.399-400). In the functions with X and Y, **N** is the number of rows in which **all** input expressions are non-null; **they return NULL when the calculation makes no sense, for example with N equal to zero** (PG16 p.398). All with Partial Mode: Yes.

## 6. Tables 9.61 to 9.63: ordered-set, hypothetical-set and `GROUPING` [from source] (PG16 p.400-402)
- **Ordered-set ("inverse distribution")** (PG16 p.400): `mode()`, `percentile_cont` and `percentile_disc` use `WITHIN GROUP (ORDER BY ...)`; the direct argument (the fraction) is computed only once and **must be between 0 and 1** (error otherwise; a null fraction returns null); they ignore nulls in the aggregated input. `mode()` returns the most frequent value (in a tie, picks the first arbitrarily); `percentile_cont` **interpolates** between adjacent items; `percentile_disc` returns the **first value** whose position equals or exceeds the fraction. All with Partial Mode: **No**.
- **Hypothetical-set** (PG16 p.400-401): `rank`, `dense_rank`, `percent_rank` and `cume_dist` with `WITHIN GROUP` return the value the window function of the same name would have for a "hypothetical" row added to the ordered group; the direct arguments must match the aggregated arguments in number and type; they are **not strict** (they do not discard rows with nulls) and the null ordering follows the `ORDER BY`.
- **`GROUPING`** (PG16 p.401-402): returns a bit mask indicating which `GROUP BY` expressions are **not** in the grouping set of the result row (bit 0 = included, 1 = not included; the rightmost argument is the least significant bit); used with groups (`ROLLUP`, `CUBE`, `GROUPING SETS`) to tell rows apart. In the example with `ROLLUP(make, model)`, values 0, 1 and 3 mark rows grouped by both columns, by `make` only and the grand total.

## 7. Window functions, page pointer [from source] (PG16 p.402-403)
- **Window**: the built-in window functions (Table 9.64: `row_number`, `rank`, `dense_rank`, `ntile` and others) require the `OVER` clause (PG16 p.402). **Any ordinary aggregate** (not ordered-set or hypothetical-set) can become a window function when followed by `OVER`; without `OVER` it acts as a simple aggregate and returns one row for the whole set (PG16 p.402). `first_value`, `last_value` and `nth_value` operate on the **window frame**; the SQL standard defines `RESPECT NULLS`/`IGNORE NULLS` for them, but PostgreSQL only implements the default `RESPECT NULLS` behavior (PG16 p.403).

## 8. [extrapolation] and what the sources do NOT say
- The Partial Mode text on these pages does not explain the concept; for partial and parallel aggregation, see PG16 p.564-568.
- Performance of `count(*)` with a partial index, visibility map or *index-only scan*: the note on PG16 p.398 only says it scans the table or an index with all rows; any concrete gain is `[extrapolation]`.
