## Ch. 12 — Writing code (BSRS p.279-305)

### Premise (BSRS p.279-280)
- [from source] Code will have bugs; avoid common classes of vulnerabilities and reliability problems with hardened frameworks and libraries; security and reliability cannot be added later without pain (BSRS p.279). Educating developers is the first step, but even experts make mistakes; manual review by SREs and security is also imperfect and biased (reviewers gravitate toward new attacks and design flaws, not hundreds of HTML templates for XSS); even so, a review culture encourages structuring code so that the properties are easy to review (BSRS p.279-280).

### Frameworks to enforce security and reliability (BSRS p.280-286)
- [from source] Security and reliability depend on domain invariants (e.g., SQL injection is avoided if queries contain only developer-controlled code, with inputs via parameter binding; XSS is avoided if all input inserted into HTML is escaped or sanitized; backoff on failing RPCs; C++ accessing only valid memory); maintaining this through code discipline alone is nearly impossible in large codebases; manual reviewers cannot keep up with the global context (they would need to know all transitive callers) (BSRS p.280-281). Better: handle it in common frameworks, languages, and libraries that expose only interfaces that prevent common classes of vulnerabilities; when experts fix a problem, it is removed from all applications; SQLI leads the OWASP and SANS lists and with a hardened library such as TrustedSqlString it tends to stop being a problem; types make assumptions explicit, enforced by the compiler (BSRS p.281).
- [from source] Benefits: reuse (authentication, authorization, logging, cryptography; rate limiting, load balancing, retry) avoids a patchwork of distinct bugs per service; the developer only customizes one block (e.g., which credential information matters for authorization, what to log); updates propagate in one place; productivity; tools that export operational metrics (total requests, failures by type, latency per stage), integration with load balancing (redirecting traffic from overloaded instances) and greater reliability; clear separation between business logic and common functions; reduces complexity (BSRS p.281-282). It does not always make sense to build your own framework: do not build your own cryptography, use Tink; evaluate the security posture of any framework, prefer actively maintained ones, and update dependencies (BSRS p.282).
- [from source] Example, a framework for RPC backends (logging, authentication, authorization, throttling): interceptors with before and after stages; an error interrupts the next interceptors but the afters of those already called run in reverse order; the framework can export metrics between interceptors; on an unauthorized request the RPC does not execute, but "permission denied" is logged, and only then is the error sent to the client (BSRS p.283-284). Interceptors share state through a context object (the authentication interceptor handles certificate cryptography by reusing a specialized library and puts the caller object in the context); the framework tracks execution time and cancels the request if it will exceed the deadline; dependencies are registered as soft or hard, with availability monitoring (if a hard one goes down, the service stops, reports itself unavailable, and redirects traffic); retries with exponential backoff are provided by the framework, not by each developer (BSRS p.285). Examples 12-1 to 12-3 in Go (types, an authorization interceptor that allows only listed users, a logging interceptor with WithAttemptCount) (BSRS p.285-287).

### Common security vulnerabilities (BSRS p.287-291)
- [from source] In large codebases, a few classes account for most vulnerabilities; OWASP and SANS publish lists; Table 12-1 (OWASP top 10) with hardening measures in the framework: SQL injection: TrustedSqlString; broken authentication: require authentication with a well-tested mechanism such as OAuth before routing; sensitive data exposure: distinct types instead of strings, restricting serialization and enforcing encryption, transparent HTTPS (LetsEncrypt cited), APIs such as Tink and keys in a KMS instead of a config file; XXE: XML parser without XXE; broken access control: require access restrictions defined per handler/RPC and pass the end user's credentials to the backend; misconfiguration: secure defaults, a single debug flag (example: Rails environment variable) and verification that it is not turned on for the public; XSS: hardened template system; insecure deserialization: libraries designed for untrusted inputs such as Protocol Buffers; components with known vulnerabilities: popular, maintained libraries; insufficient logging and monitoring: logging in a low-level library (BSRS p.287-288).
- [from source] TrustedSqlString: the password reset example with concatenation allows injection (a malicious reset_token resets the admin's hash) (BSRS p.288-289); bound parameters and prepared statements help, but just establishing the guideline does not scale (every developer trained, reviewers reviewing everything); design the database API so that mixing user input and SQL is impossible by design: a type whose SQL is built only from source-code literals (Go: a type alias private to the stringLiteral package; Java: Error Prone's @CompileTimeConstant; C++: template constructor) (BSRS p.289). For uses that do not fit (analytics that runs arbitrary SQL), there is a bypass with security engineer approval: an unsafequery package with a distinct type; only a small fraction of queries; review done by a rotating part-time engineer for hundreds or thousands of developers (BSRS p.290).
- [from source] SafeHtml: XSS occurs when untrusted input is rendered without sanitization; HTML has no equivalent of bound parameters; values must be sanitized or escaped according to context (a URL can execute code with the javascript: scheme); types for contexts (SafeHtml, SafeUrl), immutable wrappers whose contract is guaranteed by constructors (trusted code) (BSRS p.290). Builder libraries for elements (correct type per attribute); a template system with strict contextual escaping: parses the partial HTML, determines the context of each substitution point, and requires the correct type or escapes/sanitizes; example of a Closure Template in which $url requires TrustedResourceUrl; untrusted HTML must go through a sanitizer that removes elements outside the contract; the builders are generated by code from a shared declarative configuration; mature open source implementation: Closure Templates; there is an effort to standardize type-based security on the web (BSRS p.291).

### Lessons for evaluating and building frameworks (BSRS p.292-294)
- [from source] Not every property can be expressed through API design (e.g., the standard browser DOM); use compile-time checks (Error Prone for Java, Tsetse for TypeScript) that forbid risky patterns; compiler errors give immediate, actionable feedback, unlike opt-in linters or checks at review time, when the developer already has finished code; IDE plug-ins and suggested automatic fixes (inserting TrustedSqlBuilder.fromConstant) help; with a fast feedback loop and easy correction, developers adopt safe APIs even without proof that the code was insecure; contrast with the literature that seeks to reduce false positives and negatives, which results in complex, slow verifiers that are hard to explain (BSRS p.292-293).
- [from source] Simple, secure, and reliable libraries: a library that covers all cases (e.g., a template that nests a string in quotes, JavaScript, and an HTML attribute) is difficult; start with a small library for common cases, easier to explain, document, and adopt; offer libraries for different cases; extra cases get access to a risky library reviewed by experts; if similar requests repeat, add support in the safe library; the small volume of reviews allows deep analysis and keeps reviewers motivated; exceptions serve as feedback (BSRS p.293-294).
- [from source] Rollout strategy: types for security properties are very useful in new code; applications on an internal web framework with safe types for HTML from the start had roughly two orders of magnitude fewer XSS reports, and the few came from components that did not use safe types; migrating existing code is harder; Google uses a monorepo and readability standards; in other environments seek broad agreement from code owners (BSRS p.294). Incremental rollout: initially exempt legacy code and handle unsafe callers one by one (e.g., add an overload doQuery(TrustedSqlString) and restrict the String version to existing callers via Error Prone's @RestrictedApi with a whitelist, Git hooks that prevent new use, or Bazel visibility with security approval); code under development migrates organically, and the rest is cleaned up manually (BSRS p.294-295). Legacy conversions: consolidate exemption mechanisms into a single obvious function that converts a string into the safe type; there are fewer types than consuming functions (BSRS p.295).

### Simplicity leads to secure and reliable code (BSRS p.295-298)
- [from source] Avoid multi-level nesting: errors in handling paths are rarely covered by unit tests; the example in Figure 12-2 has the errors "wrong encoding" and "unauthorized" swapped, easier to see in the refactored version with checks right after each error (BSRS p.296). Eliminate YAGNI smells: "just in case" functionality adds complexity to document, test, and maintain (Mammal/Human example with Sleep(bool hibernate)); implement what is needed and generalize when there are multiple cases (BSRS p.296-297).
- [from source] Pay down technical debt: TODO/FIXME markers speed up delivery but incur debt; you need a process and time to pay it down; debt includes wrong handling of exceptional situations and needlessly complex logic, which generate vulnerabilities that tests rarely detect; ways: code health dashboards (coverage, number and age of TODOs, cyclomatic complexity, maintainability index), linters (dead code, unnecessary dependencies, automatic fixing), threshold alerts, a code health culture (regular fixit weeks, bonuses or recognition) (BSRS p.297-298).
- [from source] Refactoring: the most effective way to keep code simple; first measure and increase coverage (100% coverage is no guarantee, the tests may not be meaningful; complement with fuzzing); golden rule: never mix refactoring and functional changes in the same commit (BSRS p.298).

### Security and reliability by default (BSRS p.299-304)
- [from source] Choice of tools: integration with existing code, library availability, team skills; the choice of language has an enormous impact (BSRS p.299). Memory-safe languages: ~70% of security vulnerabilities come from memory problems (Matt Miller, Microsoft, 2019) and 85% of Android bugs (Kralevich, 2016); using Java or Go instead of C/C++ avoids this class; or use sanitizers (BSRS p.299-300). Strong typing and static type checking: invariants verified at compile time; in dynamic languages you can infer something only with 100% coverage; JavaScript is weakly typed (example [9, 8, 10].sort() -> [10, 8, 9]); extensions: Pytype for Python, TypeScript for JavaScript (BSRS p.300).
- [from source] Strong types instead of primitives: they prevent conceptually invalid parameters (AddUserToGroup(string, string); order in Rectangle(3.14, 5.67); Circle(double) radius or diameter), implicit conversions (truncation, loss of precision, unexpected object creation; C++ example with Bar(bool) and Foo(5)/Foo(NULL); make single-value constructors explicit) and unit confusion (harmless: timer 30 s or 30 min; dangerous: Gimli Glider, fuel calculated in pounds instead of kilos; expensive: Mars Climate Orbiter, US$125 million, imperial vs. metric units); unit types with sensible operations and conversions (Go time, C++20 chrono) (BSRS p.301-303).
- [from source] Sanitize your code: pre-submit or continuous build; C++: Valgrind (a VM that interprets the binary without recompiling; Helgrind for synchronization errors and deadlocks) or Google Sanitizers (ASan, LSan, MSan, TSan, UBSan), up to 10 times faster than Valgrind; Go: Race Detector for data races (BSRS p.303-304).
- [from source] Conclusion: frameworks are a powerful strategy (reuse of proven blocks for authentication, authorization, logging, rate limiting, and distributed communication); so are simplicity, the right tools, strong types, and continuous sanitization (BSRS p.305).
