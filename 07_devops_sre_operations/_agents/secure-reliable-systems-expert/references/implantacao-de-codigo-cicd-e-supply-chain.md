## Ch. 14 — Deploying code (BSRS p.339-367)

### Premise (BSRS p.339-340)
- [from source] Central question: is the code running in production what you think it is? Deployment introduces changes that can become a reliability or security problem; controls need to enter early in the lifecycle; it is hard to determine whether an artifact is safe just by inspecting the artifact; controls at several stages of the software supply chain increase confidence (code review reduces errors and deters malicious changes; automated tests give confidence that the code works) (BSRS p.339). Controls in source, build, and test have limited effect if the adversary bypasses them by deploying directly to production; systems must reject deployments that do not come from the correct supply chain, and each step must prove it ran correctly (BSRS p.339-340).

### Concepts and terminology (BSRS p.340-341)
- [from source] Software supply chain = the process of writing, building, testing, and deploying (VCS, CI pipeline, CD pipeline); four steps: code in VCS, build from a recorded version, test the binary, configured deploy (Figures 14-1 and 14-2) (BSRS p.340). The chapter's focus is mitigating threats from insiders (or attackers impersonating them), with or without malice (BSRS p.340). Broad definitions: build = any transformation of input artifacts into output artifacts (artifact = file, package, Git commit, VM image); test = a special case of build with logical output (pass/fail); builds can be chained (BSRS p.340-341). Deployment = any assignment of an artifact to an environment: pushing code (command to download a new binary, update a Kubernetes Deployment object, boot a VM or machine with firmware), updating configuration (SQL schema command; change a flag via Deployment), and publishing a package (deb in apt, image in a registry, APK on the Play Store) (BSRS p.341). Post-deployment changes are out of scope (BSRS p.341).

### Supply chain threat model (BSRS p.342-343)
- [from source] Three adversaries: benign insiders who make mistakes; malicious insiders who try to gain more access than their role allows; external attackers who compromise insiders' machines or accounts (BSRS p.342).
- [from source] Example threats (adapt to your organization): an engineer submits a change that introduces a vulnerability; an adversary submits a change with a backdoor; an engineer builds from a modified local version with unreviewed changes; an engineer deploys a binary with harmful configuration (e.g., debug in production); an adversary deploys a modified binary that exfiltrates credentials; an adversary modifies cloud bucket ACLs; an adversary steals the integrity key used for signing; an engineer deploys an old version with a known vulnerability; CI configured to accept builds from arbitrary repositories; an adversary sends a build script that exfiltrates the signing key; an adversary tricks CD into using a compiler or build tool with a backdoor (BSRS p.342-343). Map threats to existing mitigations and document limitations; threats without mitigation or with significant limitations are areas for improvement (BSRS p.343).

### Best practices (BSRS p.343-347)
- [from source] Require code review: a second reviewer before check-in or deploy (includes configuration); promotes knowledge sharing, norms, readability, and fewer errors; from a security standpoint it is multi-party authorization (no one submits alone); it must be mandatory (the adversary will not be deterred if they can skip the review) and comprehensive (the reviewer understands the change and its implications, otherwise it becomes rubber-stamping); tools: GitHub, GitLab, BitBucket with a number of approvals, or Gerrit and Phabricator with a repository that accepts only pushes from the review system; code review has limitations and should be one of several layers (defense in depth) along with automated tests and Ch.12 (BSRS p.343-344).
- [from source] Trust automation: consistent and repeatable; removing humans from the loop prevents errors and reduces toil; running on a locked-down system hardens against subversion; the scenario of engineers building production binaries on their workstations opens room for error (wrong version, unreviewed changes) and malicious overwriting (BSRS p.344). Automating safely requires, at a minimum: moving all build, test, and deploy steps to automated systems (at least script everything; CI/CD such as Jenkins; an automation policy for new projects, since retrofit is hard); requiring peer review for all supply chain configuration changes (configuration as code); locking the automated system against tampering by administrators or users (consider all paths by which an admin could change something without review, such as configuring the pipeline directly or SSH) (BSRS p.344-345).
- [from source] Verify artifacts, not just people: verifying who initiated the deploy is not enough, since the actor can make a mistake or deploy something malicious; the deployment environment must verify what is being deployed and require proof that each automated step took place; humans cannot bypass the automation unless another control mitigates it (GKE example: Binary Authorization by default accepts only images signed by CI/CD and the cluster audit log notifies when someone uses breakglass to deploy a non-conforming image); limitation: it assumes all components are secure (CI/CD accepts builds only from allowed sources, signing keys accessible only to CI/CD); the advanced strategies section verifies properties directly (BSRS p.345-346).
- [from source] Treat configuration as code: configuration is as critical as code; version, review, and test before deploying; examples: frontend pointed at a test backend; Kubernetes with YAML in version control and deploy restricted to peer-reviewed approved YAML; reuses controls instead of a separate multi-party authorization system for post-deployment configuration; versioning and reviewing configuration is less widespread (engineers know they do not build a production binary from a modified local copy, but deploy a config change without versioning or reviewing it); requires a cultural change, tools for comparing changes (diff, grep), and manual override in an emergency (which must be logged and audited) (BSRS p.346-347).
- [from source] Do not check in secrets: never in version control nor embedded in code (encrypted secrets in code or environment variables, to be decrypted and injected by the build, are possible but hinder central management); use a secrets management system or KMS (e.g., Cloud KMS); strictly limit access: only services, when necessary; never humans directly (if a human needs it, it is probably a password, not an application secret; use separate credentials) (BSRS p.347).

### Mapping mitigations to threats (BSRS p.347-350)
- [from source] Table 14-1: accidental vulnerability: code review plus automated tests; malicious backdoor: code review (raises cost and chance of detection; limitation: does not protect against collusion or attackers who compromise multiple accounts); build from a modified local version: automated CI/CD that always pulls from the correct repository; harmful configuration: treat as code with the same review (limitation: not all configuration can be treated as code); modified binary that exfiltrates credentials: production requires proof that CI/CD built it, with CI/CD pulling only from the correct repository (limitation: bypass via emergency breakglass; mitigated with logging and auditing); bucket ACLs: treat resource ACLs as configuration, changeable only by the deploy process (limitation: collusion); theft of the integrity key: keep it in a KMS accessible only to CI/CD, with rotation (Ch.9) (BSRS p.348). Threats still without mitigation: vulnerable old version, CI accepting arbitrary repositories, build script exfiltrating the key, compiler with a backdoor (BSRS p.349). Each organization decides whether it is worth addressing them (BSRS p.349).
- [from source] Trusting third-party code: if you fully trust the maintainers, the code review, the VCS, and the tamper-proof import, import it as your own code; otherwise, do some level of review before the build, possibly with an internal copy and review of upstream patches; same rigor as your own code, depending on trust; always monitor dependencies for vulnerability reports and apply patches quickly (BSRS p.349-350).

### Advanced mitigation strategies (BSRS p.350-363)
- [from source] Scope: recommendations not yet standard in the industry, may require custom infrastructure, suited to large or very sensitive organizations, and may not make sense for small ones with low insider risk (BSRS p.350).
- [from source] Binary provenance: each build should produce provenance describing exactly how the artifact was built (inputs, transformation, entity that built it); useful in incident investigation (see what code the binary came from) and for provenance-based deploy policies (BSRS p.350). Recommended fields: Authenticity (required; usually a cryptographic signature over the other fields), Outputs (required; usually a cryptographic hash of the artifact), Inputs (sources: main artifacts such as a Git commit from a repository or a file with SHA-256; dependencies: libraries, build tools, compilers not fully specified in the sources; command: preferably structured; environment: architecture and environment variables; input metadata: e.g., commit timestamp), Debug info (not needed for security), Versioning (build timestamp and format version, to invalidate old builds or change the format without suffering rollback attacks) (BSRS p.350-352). Implicit fields can be omitted (Debian's provenance omits the command because it is always dpkg-buildpackage); inputs must have an identifier (URI) and a version (hash); watch the attack surface: if the user who started the build can specify arbitrary compiler flags (GCC's -D) or a custom compiler, the verifier must validate; examples: Debian's deb-buildinfo, Reproducible Builds, JWT for signing and encoding (BSRS p.352).
- [from source] Code signing: the value of the signature lies in what it represents and in protecting the key; trusting any Windows binary with a valid Authenticode can be bypassed by buying or stealing a certificate (cost of a few hundred to a few thousand dollars); for effectiveness: explicitly list the accepted signers, restrict access to the keys, harden the environment where signing occurs, and treat obtaining a signature as a "deployment" (BSRS p.352-353).
- [from source] Provenance-based deploy policies: explicit policies describe the intended properties of each environment and are matched against the artifacts' provenance; advantages over signature alone: fewer implicit assumptions, a clear contract per stage, one signing key per build stage instead of per environment (microservices example: with signing it would be one key per repository; with provenance, CI/CD signs with one key the provenance that declares the source repository, and each microservice's policy lists the allowed repository) (BSRS p.353). Example rules: code submitted to VCS and peer reviewed; came from a specific location (target and repository); built by the official pipeline; tests passed; binary explicitly allowed for the environment (no test binaries in production); version recent enough (see MASVN, Ch.9); no known vulnerabilities according to a recent scan; the in-toto framework is a standard for provenance policies (BSRS p.354).
- [from source] Implementing policy decisions: three steps: verify that the provenance is authentic (cryptographic signature by a specific key); verify that the provenance applies to the artifact (compare the artifact's hash to the value in the payload); verify that it satisfies the policy rules; the simplest rule (signed by a specific key) covers all three; example JWT with sub as an RFC 6920 URI (ni:///sha-256;...) and input.source_uri exactly "https://github.com/mysql/mysql-server" (BSRS p.354-355).
- [from source] Verifiable builds: a build is verifiable if the provenance is trustworthy; depends on the threat model; example non-functional requirements: compromising a dev's workstation does not compromise the integrity of the provenance or artifacts; no undetected tampering; one build does not affect the integrity of another; provenance contains no false information; non-administrators do not configure user-defined build steps (Makefile, Jenkins Groovy script) in ways that violate requirements; snapshot of all sources for at least N months; reproducible build (BSRS p.355-356). Three architectures: trusted build service (single build, does not require reproducibility; Google uses it for internal builds; the service signs the provenance with a key accessible only to it), the verifier's own rebuild (reproduces and compares bit by bit; does not scale, since builds take minutes or hours and the deploy decision takes milliseconds; requires reproducibility) and rebuilding service (quorum of "rebuilders" attests; each rebuilder monitors a package repository and proactively rebuilds; the verifier queries N databases by the artifact's hash; used in projects such as Debian) (BSRS p.356-357).
- [from source] Hermetic, reproducible, verifiable: hermetic = all inputs fully specified up front, outside the build process (sources, compilers, tools, libraries), unambiguous references (resolved versions or hashes); benefits: input analysis and policy enforcement (detect vulnerable software via CVE, open source license compliance, block insecure libraries), integrity of third-party imports (hash or HTTPS from trusted repositories) and cherry-picking fixes without extra changes (reduces the risk of emergency releases); examples: Bazel in sandbox mode, npm with package-lock.json (BSRS p.357). Reproducible = the same commands on the same inputs generate bit-for-bit identical output (almost always requires hermeticity); benefits: verifiability, detection of non-hermeticity, build caching; eliminate sources of nondeterminism (timestamps) and provide the buildinfo; specify the complete toolchain and OS (BSRS p.358). Verifiable = provenance can be reliably determined; generally desirable (not strictly necessary) to be reproducible and hermetic; industry terminology is not standard (BSRS p.357-358).
- [from source] Implementing verifiable builds: basic CI/CD (request, fetching inputs, build, output to storage); adding signed provenance may suffice for a small organization with a central service; as it grows, handle untrusted inputs (user-defined commands in Jenkinsfile, travis.yml, Makefile, BUILD amount to "RCE by design" and allow stealing the signing key, inserting false information into the provenance, modifying system state, or manipulating another build in parallel; mitigate with privilege separation: a trusted orchestrator prepares the clean state, starts the build, and creates the signed provenance, and the user's commands run in an environment without access to the signing key, via sandbox or another machine) and unauthenticated inputs (a dependency fetched over HTTP without TLS allows MITM; hermetic builds in which only the orchestrator fetches the declared inputs are recommended) (BSRS p.358-360).
- [from source] Deployment choke points: a point through which all deploy requests pass; decisions made outside it can be bypassed; Kubernetes example: the master node as the choke point, with the workers accepting requests only from the master (note: deploying the node itself requires another mechanism); the choke point makes the decision directly or via RPC (Admission Controller webhook; Binary Authorization on GKE) or via a proxy in front (requires configuring the admission point to accept only via the proxy) (BSRS p.361-362).
- [from source] Post-deployment verification: even with enforcement at deploy time, it is desirable to log and verify afterward: policies change (re-evaluate existing deployments), the decision may have been allowed because the decision service was unavailable (fail open, useful when launching enforcement), emergency breakglass, testing policy changes before applying, dry run mode, and post-incident forensics; the decision point must record enough (including extra state: in Borg three log sources had to be joined: jobs, allocs, and packages); logs ideally trustworthy and tamper-proof (BSRS p.363).

### Practical advice (BSRS p.364-366)
- [from source] One step at a time: bugs or missing features in the controls can hurt productivity or cause an outage; focus on one aspect of the supply chain at a time (BSRS p.364). Actionable error messages: explain what failed and how to fix it (update the policy or rebuild from the correct URI); "does not meet policy" leaves the user lost; a prototype of an overly flexible policy language was abandoned because it prevented actionable messages (BSRS p.364). Unambiguous provenance: asynchronous upload of provenance to a database generated millions of records for the hash of the empty file, making useful messages impossible ("none of the 497,129 records met the policy"), linear verification blowing the 100 ms SLO, and silently failing uploads that rejected deploys; it is recommended to propagate provenance inline with the artifact (in Kubernetes, an annotation passed to the Admission Controller webhook) (BSRS p.364-365). Unambiguous policies: only one applicable policy per deploy; a global policy as a meta-policy that checks criteria of the individual policies (BSRS p.365). Include a deploy breakglass: emergencies (e.g., reconfiguring the frontend to divert traffic from a failing backend) may not wait for the pipeline; the breakglass must raise alarms and be audited quickly, and be rare enough to distinguish malicious from legitimate use (BSRS p.365-366).
- [from source] Table 14-2: vulnerable old version: policy requires a vulnerability scan within the last N days; CI accepting arbitrary repositories: provenance with the source repository and a policy that requires an approved repository; build script exfiltrating the key: privilege separation (whoever runs custom scripts does not access the key); compiler with a backdoor: hermetic builds require choosing the compiler and tools in the source code, peer reviewed (BSRS p.366).
- [from source] Conclusion: code reviews and automation prevent errors and raise the cost for attackers; configuration as code extends the benefits to configuration; artifact-based deploy controls (provenance and verifiable builds) protect against sophisticated adversaries and scale; they ensure that the code written and tested is the code deployed (BSRS p.366-367).

### DATED
- [DATED] The book (2020) describes binary provenance, in-toto, Binary Authorization, and verifiable builds as "not yet standard". Since then SLSA (supply chain integrity levels), Sigstore (cosign, Fulcio, Rekor), SBOM (SPDX, CycloneDX), attestations, and provenance verification in registries and Kubernetes (for example admission policies) have emerged; [extrapolation] check the current versions. Later incidents (SolarWinds 2020, Codecov 2021, Log4Shell 2021) reinforced these practices and are not in the book.
- [DATED] Jenkins, travis.yml, Gerrit, Phabricator, GKE Binary Authorization, and Authenticode as 2020 tools; Travis CI is now less used.
- [DATED] npm package-lock.json and Bazel sandbox as examples of hermetic builds; today there are lockfiles and images with digests ([extrapolation]).
