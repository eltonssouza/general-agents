## Monitoring overview (console)
- [from source] (LAMBDA p.795) Lambda monitors functions automatically and reports metrics to CloudWatch; tracks the number of requests, duration per request and requests with errors
- [from source] (LAMBDA p.796) The function's Monitor tab in the console shows metric graphs (CloudWatch has a perpetual free tier; beyond it, it charges for metrics, dashboards, alarms, logs, insights)
- [from source] (LAMBDA p.796) Console graphs: Invocations (times invoked); Duration (average/min/max of the time processing an event); Error count and success rate (%); Throttles (invocations that failed due to concurrency limit); IteratorAge (for stream sources: age of the last item of the batch); Async delivery failures (errors writing to a destination or DLQ); Concurrent executions (instances processing events)
- [p.796-797] Procedure: Functions > choose function > Monitor tab > Metrics/Logs/Traces, choose range; "View in metrics" (three dots, Widget actions) opens CloudWatch Metrics; "View logs in CloudWatch" > "View in Logs Insights" > Run query > (optional) Save


## Lambda Insights
- [from source] (LAMBDA p.798) CloudWatch Lambda Insights collects and aggregates runtime performance metrics (CPU time, memory, disk, network) and diagnostics (cold starts, worker shutdowns)
- [from source] (LAMBDA p.798) Implemented as an extension delivered as a Lambda layer; emits a single performance log event per invocation; CloudWatch extracts metrics via embedded metric format; the layer extends CreateLogStream/PutLogEvents on the log group /aws/lambda-insights/
- [from source] (LAMBDA p.798) [DATED] Price: 8 metrics per function and ~1 KB of log per invocation; you pay only for the metrics and logs reported; no minimum fee; you do not pay if the function is not invoked
- [from source] (LAMBDA p.798) Supported runtimes: any runtime that supports Lambda extensions
- [p.798-799] Enable in the console: Configuration > Monitoring tools > Edit > Lambda Insights "Enhanced monitoring" > Save; the console adds the layer and checks/tries to attach the managed policy CloudWatchLambdaInsightsExecutionRolePolicy to the execution role
- [from source] (LAMBDA p.799) Programmatically: AWS CLI, SAM CLI, CloudFormation or CDK; also attaches the same policy to the execution role
- [p.799-800] The Insights dashboard has two views: multi-function overview (aggregates metrics of the account/current region; useful to find over/underutilized functions) and single-function view (for troubleshooting individual requests); there is "Add to dashboard"
- [p.801-802] Anomaly workflow: multi-function > function name > Memory Usage panel > "View in metrics" > Graphed metrics tab > first icon in the Actions column enables anomaly detection
- [p.802-803] Query workflow: Duration panel to find the function; single-function view; Application logs tab (last 1000 logs) and Invocations tab (last 1000 invocations); select an invocation > View logs > "View performance logs" opens an autogenerated query in Logs Insights > Run query


## Function metrics (CloudWatch, namespace AWS/Lambda)
- [from source] (LAMBDA p.804) Lambda sends metrics after finishing the event processing; no charge for them; [DATED] sent at 1-minute intervals; for a more immediate view create high-resolution custom metrics (charged, as are alarms)
- [from source] (LAMBDA p.804) Dimensions: FunctionName (aggregates all versions/aliases); Resource (version or alias); ExecutedVersion (alias+version combination; use to compare the error rate of two target versions of a weighted alias); no dimension = all functions in the region
- [from source] (LAMBDA p.804) Graphs use the Sum statistic by default
- [from source] (LAMBDA p.804) Note: the metric timestamp reflects when the function was invoked, which can be several minutes before emission; with a 10 min timeout look more than 10 min into the past
- [from source] (LAMBDA p.805) Invocation metrics (use Sum): they are binary indicators of the outcome. Invocations (includes success and function error; does not count throttles or invocation request errors; equals the number of billed requests)
- [from source] (LAMBDA p.805) Errors = invocations with function error (exceptions from the code and runtime: timeouts, configuration errors); error rate = Errors / Invocations; the timestamp reflects the invocation, not when the error occurred
- [from source] (LAMBDA p.805) DeadLetterErrors: failed attempts to send an event to the DLQ (async), due to permission, misconfigured resource or size; DestinationDeliveryFailures: same for destination
- [from source] (LAMBDA p.805) Throttles: when all instances are busy and there is no concurrency to scale, Lambda rejects with TooManyRequestsException; throttles count neither as Invocations nor as Errors
- [from source] (LAMBDA p.805) ProvisionedConcurrencyInvocations (invocations on provisioned concurrency); ProvisionedConcurrencySpilloverInvocations (invocations on standard concurrency when all the provisioned is in use)
- [from source] (LAMBDA p.805) Performance metrics (use Average or Max): Duration (billed = Duration rounded up to the nearest ms); PostRuntimeExtensionsDuration (cumulative time the runtime spends running extensions after the function code); IteratorAge (stream event source mappings: time between the stream receiving the record and the mapping sending the event); OffsetLag (self-managed Kafka and MSK: offset difference between the last record written and the last one processed by the consumer group, measured at topic level)
- [from source] (LAMBDA p.806) Duration supports percentiles (e.g. p95 excludes the slowest 5%), useful to ignore outliers
- [from source] (LAMBDA p.806) Concurrency metrics (use Max): ConcurrentExecutions (if it reaches the regional quota or the function's reserved concurrency, Lambda throttles); ProvisionedConcurrentExecutions; ProvisionedConcurrencyUtilization (= ProvisionedConcurrentExecutions / allocated provisioned; .5 = 50%); UnreservedConcurrentExecutions (per region, events from functions without reserved concurrency)


## Logs (CloudWatch Logs)
- [from source] (LAMBDA p.807) Lambda records all requests and sends the code's logs to the log group /aws/lambda/<function name>; queryable via console, CloudWatch console, CLI or API
- [from source] (LAMBDA p.807) [DATED] It can take 5 to 10 minutes for logs to appear after the invocation
- [from source] (LAMBDA p.807) Prerequisite: execution role with log upload permission; use the managed policy AWSLambdaBasicExecutionRole (CLI: aws iam attach-role-policy --role-name your-role --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole)
- [from source] (LAMBDA p.807) No extra cost for Lambda logs; standard CloudWatch Logs prices apply
- [from source] (LAMBDA p.808) CLI: aws lambda invoke --function-name my-function out --log-type Tail; the response has a LogResult field with [DATED] up to 4 KB of logs in base64; decode with base64 -d (macOS may need base64 -D)
- [from source] (LAMBDA p.808) The REPORT line shows Duration, Billed Duration, Memory Size and Max Memory Used (example 79.67 ms / 80 ms / 128 MB / 73 MB)
- [p.808-809] With AWS CLI v2 you need --cli-binary-format raw-in-base64-out (or aws configure set cli-binary-format raw-in-base64-out) when passing --payload; example get-logs.sh invokes, sleeps 15 s and runs aws logs get-log-events --limit 5
- [from source] (LAMBDA p.810) Runtime logging: use the language's standard facility; the runtime sends it to CloudWatch Logs (see the per-language chapters Node.js/Python/Ruby/Java/Go/C#/PowerShell)


## CodeGuru Profiler
- [from source] (LAMBDA p.810) [DATED] Can be enabled via the console for Python3.8, Python3.9, Java 8 (Amazon Linux 2) and Java 11; other versions: enable manually
- [from source] (LAMBDA p.811) Enable: Configuration > Monitoring and operations tools > Edit > Amazon CodeGuru Profiler "Code profiling" > Save; creates the profiler group aws-lambda-<function-name> (renameable in the CodeGuru console)
- [from source] (LAMBDA p.811) When enabled, Lambda adds: the CodeGuru Profiler layer; environment variables (java8.al2/java11: JAVA_TOOL_OPTIONS=-javaagent:/opt/codeguru-profiler-java-agent-standalone.jar; python3.8/3.9: AWS_LAMBDA_EXEC_WRAPPER=/opt/codeguru_profiler_lambda_exec); and the AmazonCodeGuruProfilerAgentAccess policy to the execution role
- [from source] (LAMBDA p.811) When disabled, Lambda removes the layer and env vars, but does NOT remove the AmazonCodeGuruProfilerAgentAccess policy from the execution role


## X-Ray, ServiceLens and Trusted Advisor
- [from source] (LAMBDA p.812) X-Ray prerequisite: Configuration > Monitoring tools > Edit > AWS X-Ray "Active tracing" > Save; if the execution role lacks permissions, the console tries to add them
- [from source] (LAMBDA p.812) Trusted Advisor inspects the environment and recommends savings, availability/performance and closing security gaps; checks evaluate Lambda functions
- [from source] (LAMBDA p.813) Price: X-Ray charges for traces recorded, retrieved and scanned; Trusted Advisor's cost optimization checks are included in Business and Enterprise support
- [from source] (LAMBDA p.813) The ServiceLens service map (CloudWatch) shows endpoints/resources as nodes and highlights traffic, latency and errors; on the node you see correlated metrics, logs and traces. Path: Monitoring > View traces in X-Ray > Service map
- [p.813-814] Trace detail: Insights single-function view > Application logs/Invocations tab > Trace column > View opens the ServiceLens traces view (distributed trace data)
- [from source] (LAMBDA p.814) Trusted Advisor checks Lambda functions in all regions (execution time, billed duration, memory used vs configured, timeout, errors); the "Lambda Functions with High Error Rate" check recommends using X-Ray or CloudWatch; it sits under Cost Optimization
