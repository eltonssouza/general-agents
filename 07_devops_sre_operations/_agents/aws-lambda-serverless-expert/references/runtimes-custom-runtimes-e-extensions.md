## Runtimes: overview (p.102)
- [from source] (LAMBDA p.102) Lambda offers several languages via runtimes; in a container image function, the runtime and Linux distribution are chosen when building the image, and to change the runtime you must create a new image
- [from source] (LAMBDA p.102) In a function with a .zip package the runtime is chosen at creation and can be changed by updating the function configuration
- [from source] (LAMBDA p.102) [DATED] A runtime is paired with an Amazon Linux distribution: Amazon Linux 2 (kernel 4.14) and Amazon Linux (image amzn-ami-hvm-2018.03.0.20220802.0-x86_64-gp2, kernel 4.14)
- [from source] (LAMBDA p.102) Lambda reuses a previous execution environment if available, or creates a new one
- [from source] (LAMBDA p.102) A runtime can support one version, several versions or several languages; runtimes specific to a language/framework version are deprecated when the version reaches end of life
- [from source] (LAMBDA p.102) For other languages a custom runtime is used, which can ship with the code or in a layer; the environment exposes a runtime interface to get events and send responses
- [from source] (LAMBDA p.102) [DATED] In new regions, Lambda does not support runtimes that will be deprecated within the next six months
- [from source] (LAMBDA p.102) [DATED] Table of supported runtimes (identifier / SDK / OS / architectures): nodejs18.x (SDK 3.188.0, AL2, x86_64+arm64); nodejs16.x (2.1083.0, AL2, both); nodejs14.x (2.1055.0, AL2, both); nodejs12.x (2.1055.0, AL2, both; deprecation phase 1 on Mar 31, 2023)
- [from source] (LAMBDA p.103) [DATED] Continued: python3.9 and python3.8 (boto3-1.20.32/botocore-1.23.32, AL2, x86_64+arm64); python3.7 (AL, x86_64 only); java11 (AL2, both); java8.al2 (AL2, both); java8 (AL, x86_64); dotnetcore3.1 (AL2, both; phase 1 on Mar 31, 2023); dotnet6 (AL2, both); dotnet5.0 (AL2, x86_64); go1.x (AL, x86_64); ruby2.7 (SDK 3.1.0, AL2, both); provided.al2 (AL2, both); provided (AL, x86_64)
- [from source] (LAMBDA p.103) Note: in the table, Go exists only as go1.x on Amazon Linux/x86_64 (no arm64); Python 3.7, Java 8 (java8), .NET 5, Go and `provided` run only on x86_64


## Deprecation policy (p.103-104)
- [from source] (LAMBDA p.103) .zip runtimes are a combination of OS, language and libraries; when a component loses security updates, the runtime is deprecated
- [from source] (LAMBDA p.103) Phase 1 (deprecation): Lambda stops applying security patches; you can no longer CREATE functions with the runtime, but you can still UPDATE existing functions (including changing the runtime version and rolling back); functions stop being eligible for technical support
- [from source] (LAMBDA p.103) [DATED] Phase 2: you can no longer create or update functions with the runtime; you must migrate to a supported runtime and afterwards there is no rollback to the previous runtime; Phase 2 starts at least 30 days after the start of Phase 1
- [from source] (LAMBDA p.104) Invocations are NOT blocked on a deprecated runtime; they continue indefinitely, but AWS strongly recommends migrating (patches and support)
- [from source] (LAMBDA p.104) [DATED] Each phase starts at midnight, Pacific time, on the stated date
- [from source] (LAMBDA p.104) [DATED] Runtimes already at end of support (phase 1 / phase 2): python3.6 (Jul 18, 2022; Aug 29, 2022); python2.7 (Jul 15, 2021; May 30, 2022); dotnetcore2.1 (Jan 5, 2022; Apr 13, 2022); ruby2.5 (Jul 30, 2021; Mar 31, 2022); nodejs10.x (Jul 30, 2021; Feb 14, 2022); nodejs8.10 (Mar 6, 2020); nodejs4.3 (Mar 5, 2020); nodejs6.10 (Aug 12, 2019); dotnetcore1.0 (Jul 30, 2019); dotnetcore2.0 (May 30, 2019); nodejs4.3-edge (Apr 30, 2019); nodejs (0.10) (Oct 31, 2016)
- [from source] (LAMBDA p.104) [DATED] Lambda warns by email if there are functions with a runtime that will be discontinued within the next 60 days; in rare cases (e.g. security issue with an incompatible update, component without LTS) there is no advance notice
- [from source] (LAMBDA p.104) Per-language support policies (Node.js, Python, Ruby, Java/Corretto, Go, .NET Core) are listed only as external references


## Modifying the runtime environment (p.106-108)
- [from source] (LAMBDA p.106) Internal extensions run inside the runtime process (they are not separate processes) and can modify the runtime process
- [from source] (LAMBDA p.106) Two ways: language-specific environment variables and wrapper scripts (they delegate the runtime startup to your script)
- [from source] (LAMBDA p.106) [DATED] Per-language environment variables (no-code configuration, preload code at init): JAVA_TOOL_OPTIONS (Java; agents via agentlib/javaagent); NODE_OPTIONS (Node.js 10x and above); DOTNET_STARTUP_HOOKS (.NET Core 3.1+; path of a dll assembly)
- [from source] (LAMBDA p.106) Explicit recommendation: language-specific environment variables are the preferred way to set startup properties
- [p.106-107] javaagent example with Byte Buddy: the JVM invokes the agent's premain method before the entry point; the agent intercepts handleRequest of RequestStreamHandler and the TimerAdvice class (@OnMethodEnter/@OnMethodExit) measures and logs milliseconds; the JAR goes in a layer and is referenced with JAVA_TOOL_OPTIONS=-javaagent:"/opt/ExampleAgent-0.0.jar"
- [from source] (LAMBDA p.107) [DATED] Example dependencies: aws-lambda-java-core 1.2.1; byte-buddy-dep and byte-buddy-agent 1.10.14
- [p.107-108] Shutdown hook in the JVM: when an extension is registered for the Shutdown event, the runtime process has up to 500 ms to shut down gracefully; the hook is useful to dispatch remaining telemetry and close database connections; it must register as an extension, but does not need to explicitly register the Shutdown event (sent automatically to the runtime) [DATED 500 ms]
- [from source] (LAMBDA p.108) Example: obtain InvokedFunctionArn via Context.getInvokedFunctionArn() in the advice


## Wrapper scripts (p.108-110)
- [from source] (LAMBDA p.108) A wrapper script customizes the runtime startup and allows parameters that cannot be set by language environment variables
- [from source] (LAMBDA p.108) Risk: invocations may fail if the wrapper does not successfully start the runtime process
- [from source] (LAMBDA p.108) Wrapper scripts are supported on all runtimes that use Amazon Linux 2
- [p.108-109] Lambda starts the runtime using your script, passing the interpreter path and all the original arguments; the script can inject/alter arguments, set environment variables, capture metrics and errors
- [from source] (LAMBDA p.109) Activation: variable AWS_LAMBDA_EXEC_WRAPPER = filesystem path of an executable binary/script
- [p.109-110] Example procedure (Python 3.8, -X importtime): 1) create the file importtime_wrapper (bash that inserts "-X importtime" before the last argument and does exec); 2) chmod +x; 3) publish as a layer; 4) create a function in the console (wrapper-test-function, Python 3.8); 5) add the layer (Add a layer); 6) paste code and set AWS_LAMBDA_EXEC_WRAPPER=/opt/importtime_wrapper; 7) Test: logs show import time per module
- [from source] (LAMBDA p.110) Pattern: a wrapper in a layer lives in /opt (hence /opt/<name>)


## Custom runtimes (p.111-112)
- [from source] (LAMBDA p.111) A runtime can be written in any language; it is a program that runs the handler; included in the package as an executable called bootstrap
- [from source] (LAMBDA p.111) Responsibilities: run setup, read the handler name from an environment variable, read events from the runtime API, pass the event to the handler and post the response
- [from source] (LAMBDA p.111) Runs in the standard execution environment; can be a shell script, a script in a language present on Amazon Linux or a binary compiled on Amazon Linux; C++ example (awslabs/aws-lambda-cpp)
- [from source] (LAMBDA p.111) [DATED] To use: set the function's runtime to `provided` (in the text; `provided.al2` appears in the p.103 table); the runtime can be in the package or in a layer; if a bootstrap exists in the package Lambda runs it, otherwise it looks in the layers; if bootstrap does not exist or is not executable the invocation returns an error
- [from source] (LAMBDA p.111) The entry point is bootstrap, which can be the runtime or call another file; the example uses a bundled Node.js (node-v11.1.0-linux-x64) running runtime.js with cd $LAMBDA_TASK_ROOT
- [p.111-112] Initialization tasks (once per function instance): read the variables _HANDLER (standard format file.method), LAMBDA_TASK_ROOT, AWS_LAMBDA_RUNTIME_API (host:port of the runtime API); load the handler and run global/static code (create SDK clients and connections once and reuse); on error, call the initialization error API and exit immediately
- [from source] (LAMBDA p.112) Initialization counts toward billed time and the timeout; the init time appears in the logs (Init Duration) and in the X-Ray trace
- [from source] (LAMBDA p.112) Processing loop, in order: (1) get event (next invocation); (2) propagate the tracing header: copy Lambda-Runtime-Trace-Id to the variable _X_AMZN_TRACE_ID; (3) create the context object; (4) invoke the handler; (5) post the response (invocation response); (6) on error call invocation error; (7) cleanup before the next event


## Runtime API (p.113-117)
- [from source] (LAMBDA p.113) HTTP API for custom runtimes inside the execution environment; version [DATED] 2018-06-01 with OpenAPI specification (runtime-api.zip); URL = AWS_LAMBDA_RUNTIME_API + version + path, e.g. curl http://${AWS_LAMBDA_RUNTIME_API}/2018-06-01/runtime/invocation/next
- [from source] (LAMBDA p.113) Next invocation: GET /runtime/invocation/next; body = JSON payload of the event; response headers carry metadata
- [p.113-114] Response headers: Lambda-Runtime-Aws-Request-Id (request id); Lambda-Runtime-Deadline-Ms (timeout moment in Unix time ms); Lambda-Runtime-Invoked-Function-Arn (ARN of the invoked function/version/alias); Lambda-Runtime-Trace-Id (X-Ray header); Lambda-Runtime-Client-Context and Lambda-Runtime-Cognito-Identity (only invocations via the AWS Mobile SDK)
- [from source] (LAMBDA p.114) Rule: do NOT set a timeout on the next invocation GET; the runtime process can stay frozen for several seconds between bootstrap and the event arriving
- [from source] (LAMBDA p.114) The runtime must set _X_AMZN_TRACE_ID with the trace header value; the X-Ray SDK reads this to decide whether to trace
- [from source] (LAMBDA p.114) Invocation response: POST /runtime/invocation/AwsRequestId/response; in synchronous invocation Lambda sends the response to the client
- [from source] (LAMBDA p.114) Initialization error: POST /runtime/init/error; optional header Lambda-Runtime-Function-Error-Type (free string, recommended format <category.reason>, e.g. Runtime.NoSuchHandler, Runtime.APIKeyNotFound, Runtime.ConfigInvalid, Runtime.UnknownReason); optional ErrorRequest JSON body {errorMessage, errorType, stackTrace[]}; Lambda accepts any errorType
- [from source] (LAMBDA p.115) [DATED] Init error response codes: 202 Accepted; 403 Forbidden; 500 Container error (unrecoverable state, the runtime must exit promptly)
- [p.115-116] Invocation error: POST /runtime/invocation/AwsRequestId/error; same headers/body; [DATED] codes 202, 400 Bad Request, 403, 500 (400 exists only here, not in init error)
- [p.115,117] The curl examples use --header "Lambda-Runtime-Function-Error-Type: Unhandled"
- [p.114,115] Note on the text: the description of "Initialization error" says "if the function returns an error" (imprecise wording; it is a runtime init error)


## Tutorial: publishing a custom runtime (p.118-123)
- [from source] (LAMBDA p.118) Path: runtime in the package -> migrate to an independent layer -> share the layer via a resource-based policy
- [from source] (LAMBDA p.118) Prerequisite: execution role (Trusted entity Lambda; permission AWSLambdaBasicExecutionRole = write to CloudWatch Logs; name lambda-role)
- [from source] (LAMBDA p.118) On Windows some Bash commands (e.g. zip) do not work in native terminals; suggests WSL
- [from source] (LAMBDA p.119) Bootstrap in Bash: `set -euo pipefail`; loads function.sh via source using _HANDLER; loop: GET next (curl -LD saves headers), extracts Request-Id from headers, runs the handler function, POST response. Handler (function.sh) logs the event to stderr and returns "Echoing request"
- [from source] (LAMBDA p.119) The text admits the example omits responsibilities (error handling, context for the handler)
- [from source] (LAMBDA p.120) [DATED] CLI steps: chmod 755; zip function.zip; `aws lambda create-function --function-name bash-runtime --zip-file fileb://function.zip --handler function.handler --runtime provided --role ...`; invoke with `aws lambda invoke ... --payload '{"text":"Hello"}' --cli-binary-format raw-in-base64-out`
- [from source] (LAMBDA p.120) The layer isolates the runtime from the code, lets dependencies evolve independently and reduces storage when shared by several functions; created with `aws lambda publish-layer-version --layer-name bash-runtime --zip-file fileb://runtime.zip`
- [from source] (LAMBDA p.121) The function uses the layer via `update-function-configuration --layers <arn:version>`; the layer lives in /opt; Lambda only uses the layer's runtime if it is REMOVED from the function's package (update code with only function.sh via update-function-code)
- [from source] (LAMBDA p.121) Inconsistency in the text: the example output shows layer version :7 after using version :1
- [from source] (LAMBDA p.122) New layer version = new publish-layer-version; the function must explicitly point to the new version (`--layers ...:2`)
- [from source] (LAMBDA p.122) Share: `add-layer-version-permission --layer-name bash-runtime --version-number 2 --principal "*" --statement-id publish --action lambda:GetLayerVersion`; several statements can grant to one account, accounts of an organization or all accounts
- [p.122-123] Cleanup: delete-layer-version per version; a deleted version continues to exist for functions that reference it and they continue to work, but you cannot configure functions to use the deleted version; when changing the layer list you must provide the new version or omit the deleted one


## AVX2 (p.124-125)
- [from source] (LAMBDA p.124) AVX2 = vectorization extension of the Intel x86 instruction set, SIMD over 256-bit vectors; useful in intensive workloads (ML inference, multimedia, scientific simulation, financial modeling) with highly parallelizable algorithms
- [from source] (LAMBDA p.124) arm64 uses NEON SIMD and does NOT support AVX2
- [from source] (LAMBDA p.124) No additional cost; you must ensure the code accesses AVX2-optimized code (libraries with support, recompile with flags, third-party libraries such as Intel MKL, OpenBLAS, AMD BLIS); auto-vectorized languages (e.g. Java) use AVX2 automatically
- [from source] (LAMBDA p.124) [DATED] gcc/clang compilation flags: -march=haswell or -mavx2; TensorFlow: compile with -march=haswell
- [from source] (LAMBDA p.124) Intel MKL uses AVX2 implicitly when the platform supports it; PyTorch is already built with MKL by default; TensorFlow has the option --config=mkl
- [from source] (LAMBDA p.125) Other languages: Python (SciPy/NumPy compiled with AVX2 or MKL versions); Node (AVX2/MKL libraries); Java (JIT auto-vectorizes); Go (the standard compiler does not auto-vectorize; use gccgo with -mavx2); real gain depends on the compiler/interpreter
- [from source] (LAMBDA p.125) Antipattern/recommendation: intrinsics to vectorize manually are possible but NOT recommended (high effort, harder debugging and maintenance)
- [from source] (LAMBDA p.125) Note on the text: the Go example shows `gcc -o avx2 -mavx2 -Wall main.c` (a gcc command with a .c file, not gccgo/.go)


## Lambda extensions: overview (p.126-129)
- [from source] (LAMBDA p.126) Extensions integrate functions with monitoring, observability, security and governance tools; there are partner extensions or your own
- [from source] (LAMBDA p.126) External = independent process in the execution environment, keeps running after the invocation is fully processed, may be in a different language from the function; Internal = runs as part of the runtime process, accessed by wrapper scripts or in-process mechanisms such as JAVA_TOOL_OPTIONS; all runtimes support extensions
- [from source] (LAMBDA p.126) Extensions can be added via console, AWS CLI or IaC (CloudFormation, SAM, Terraform)
- [from source] (LAMBDA p.126) Cost: you are charged for the execution time consumed by the extension in 1 ms increments [DATED]; installing your own extensions has no cost; partners have their own prices
- [from source] (LAMBDA p.126) Execution environment phases: Init (creates/thaws the environment, downloads code and all layers, initializes extensions, initializes the runtime, runs the function's init code outside the handler; happens on the first invocation or ahead of time with provisioned concurrency); Init subdivided into Extension init, Runtime init and Function init, ensuring extensions and runtime finish setup before the function code
- [from source] (LAMBDA p.127) SnapStart: the Init phase occurs when PUBLISHING the version; Lambda takes a snapshot of memory and disk of the initialized environment, persists it encrypted and caches it for low-latency access; the runtime hook beforeCheckpoint runs at the end of Init
- [from source] (LAMBDA p.127) Restore (SnapStart only): on the first invocation and when scaling, Lambda resumes environments from the snapshot; the afterRestore hook runs at the end of Restore, is BILLED, and expires in [DATED] 2 seconds
- [from source] (LAMBDA p.127) Invoke: invokes the handler and then prepares for another invocation. Shutdown: triggered when the function receives no invocations for a period; shuts down the runtime, notifies the extensions (Shutdown event) and removes the environment
- [from source] (LAMBDA p.127) Layers with extensions are extracted to /opt; Lambda looks in /opt/extensions/, treats each file as an executable bootstrap and starts all extensions in parallel
- [from source] (LAMBDA p.127) [DATED] The size of extensions counts toward the package limit: for .zip, total unzipped size of function + extensions cannot exceed 250 MB
- [from source] (LAMBDA p.127) Extensions share CPU, memory and storage with the function (can increase duration); each extension must complete init before the invocation, so slow init increases latency; measure the extra post-execution time with the PostRuntimeExtensionsDuration metric and memory with MaxMemoryUsed; compare versions side by side
- [from source] (LAMBDA p.127) Permissions: extensions have access to the same resources as the function and share permissions (same environment); CloudFormation can attach the same extension configuration (including IAM) to several functions
- [from source] (LAMBDA p.128) Configuration (.zip): the extension comes as a layer (shareable in the organization or community); a layer can have several extensions; [DATED] up to 10 registered extensions per function
- [from source] (LAMBDA p.128) Console: Functions > function > Code tab > Layers > Edit > Specify an ARN > enter the extension layer ARN > Add
- [from source] (LAMBDA p.128) Container image: the extension goes in the image; ENTRYPOINT defines the main process (in the Dockerfile or override in the configuration); you can run several processes in the container; Lambda manages the lifecycle of the main and additional processes, using the Extensions API for extensions
- [from source] (LAMBDA p.128) Example: Dockerfile with FROM public.ecr.aws/lambda/python:3.8, COPY/pip install, `ADD my-extension.zip /opt`; Lambda starts one process per file in /opt/extensions/ and sends Shutdown to each external extension after the function finishes
- [from source] (LAMBDA p.129) Next steps: only references to the AWS Compute Blog and AWS Samples repo (no technical content)

## Extensions API (p.131-144)
- [from source] (LAMBDA p.131) For authors: register for function and environment lifecycle events, start processes, run logic and take part in init, invocation and shutdown; can also use the Runtime Logs API to stream logs
- [from source] (LAMBDA p.131) Explicit recommendation: implement extensions in a compiled language (self-contained binary compatible with the runtimes); in a non-compiled language, include a compatible runtime in the extension
- [from source] (LAMBDA p.131) An internal extension runs as a separate thread in the runtime process, started and stopped by the runtime; alternative: language environment variables and wrapper scripts. In .zip the extension goes as a layer; in a container image, inside the image
- [from source] (LAMBDA p.132) Each phase begins with an event from Lambda to the runtime and all registered extensions; the runtime and extensions signal completion by sending a Next request; Lambda freezes the environment when all processes have completed and there are no pending events
- [from source] (LAMBDA p.134) Init: each extension must register (Register); Lambda validates by the full file name, so every Register must carry the Lambda-Extension-Name header with the full file name
- [from source] (LAMBDA p.134) [DATED] The limit of 10 extensions per function is enforced at the Register call; after registration Lambda starts Runtime init; the runtime calls functionInit for the Function init; Init ends when the runtime and all extensions send Next; extensions can complete init at any moment of the phase
- [p.135-136] Invoke: Lambda sends the Invoke event to the runtime and to each extension registered for Invoke; external extensions run in parallel with the function and continue after it ends (capture diagnostics, send logs/metrics/traces); Lambda returns the response to the client even if extensions are still running; the phase ends when the runtime and all extensions send Next
- [p.136-137] The event for an extension contains only metadata: eventType, deadlineMs, requestId, invokedFunctionArn, tracing (type X-Amzn-Trace-Id, value); to access the event body the extension needs an in-runtime SDK that the function dev uses to send the payload
- [from source] (LAMBDA p.137) Duration limit: the function timeout bounds the entire Invoke phase; there is no independent post-invoke phase; duration = runtime + extensions sum, computed only when all finish (e.g. timeout 360 s applies to function+extensions) [DATED 360 s example]
- [from source] (LAMBDA p.137) CPU is proportional to memory; at low memory, extension and function compete for CPU and execution/init duration increase; recommendation: increase memory. PostRuntimeExtensionsDuration measures the cumulative time between the runtime's Next and the last extension Next; authors should publish expected resource consumption
- [from source] (LAMBDA p.137) Shutdown: Lambda sends Shutdown to each registered external extension in response to a Next; [DATED] maximum duration: 0 ms with no extensions; 500 ms with an internal extension; 2,000 ms with one or more external extensions; in that case Lambda reserves up to 300 ms (500 ms if runtime with internal extension) for the graceful shutdown of the runtime and the rest of the 2,000 ms for the external ones; if it does not respond within the limit, the process receives SIGKILL
- [from source] (LAMBDA p.139) The Shutdown event contains the reason and remaining time; [DATED] shutdownReason: SPINDOWN (normal), TIMEOUT (duration limit), FAILURE (error condition, e.g. out of memory)
- [from source] (LAMBDA p.139) Permissions/config: extensions share CPU, memory and /tmp with the function and use the same IAM role and security context; same filesystem and network namespace (must be compatible with the OS); extra network egress rules must be applied in the function configuration; the code directory is read-only, so extensions do not modify the code
- [from source] (LAMBDA p.139) Extensions access the function's environment variables, except those specific to the runtime process: AWS_EXECUTION_ENV, AWS_LAMBDA_LOG_GROUP_NAME, AWS_LAMBDA_LOG_STREAM_NAME, AWS_XRAY_CONTEXT_MISSING, AWS_XRAY_DAEMON_ADDRESS, LAMBDA_RUNTIME_DIR, LAMBDA_TASK_ROOT, _AWS_XRAY_DAEMON_ADDRESS, _AWS_XRAY_DAEMON_PORT, _HANDLER
- [from source] (LAMBDA p.139) Extension init failure: Lambda restarts the execution environment (fail fast; extensions can be critical: logging, security, governance, telemetry)
- [p.139-140] Invocation failure (OOM, timeout): memory exhaustion affects extensions; if the runtime fails, all take part in Shutdown and the runtime is restarted (automatically on the current invocation or by deferred re-init); on failure (timeout/runtime error) Lambda performs a reset that behaves like Shutdown: shuts down the runtime, sends Shutdown with the reason to the external ones; on a new use of the environment, extension and runtime are reinitialized on the next invocation
- [from source] (LAMBDA p.140) Extension logs go to CloudWatch Logs; Lambda generates an extra log per extension at Init with name and registration preference (event, config) or the failure reason
- [from source] (LAMBDA p.140) Troubleshooting: if Register fails, check Lambda-Extension-Name with the full file name; if it fails for an internal extension, check that it does not register the Shutdown event
- [from source] (LAMBDA p.140) [DATED] Extensions API version 2020-01-01 (OpenAPI in extensions-api.zip); endpoint via AWS_LAMBDA_RUNTIME_API; prefix 2020-01-01/ in every path, e.g. http://${AWS_LAMBDA_RUNTIME_API}/2020-01-01/extension/register
- [from source] (LAMBDA p.141) Register: POST /extension/register; internal ones cannot register for Shutdown (started/stopped by the runtime); required header Lambda-Extension-Name; optional header Lambda-Extension-Accept-Feature (comma-separated list; feature accountId makes the response include the account ID); body events (optional): INVOKE, SHUTDOWN
- [from source] (LAMBDA p.141) Register response: header Lambda-Extension-Identifier (UUID, required in all subsequent requests); [DATED] codes 200 (body with functionName, functionVersion, handler), 400, 403, 500 (unrecoverable; the extension must exit promptly)
- [from source] (LAMBDA p.142) Next: GET /extension/event/next, header Lambda-Extension-Identifier required; it is a blocking call that signals readiness for a new event (Invoke or Shutdown); do NOT set a timeout on the GET since the extension may be suspended; [DATED] codes 200, 403, 500
- [p.142-143] Init error: POST /extension/init/error; use it if the extension fails to initialize after registering; after the error no other API call works and the extension must exit after the response; required header Lambda-Extension-Function-Error-Type (recommended format <category.reason>: Extension.NoSuchHandler, Extension.APIKeyNotFound, Extension.ConfigInvalid, Extension.UnknownReason); [DATED] codes 202, 400, 403, 500
- [p.143-144] Exit error: POST /extension/exit/error; reports an unexpected failure before exiting; same headers/body/codes (202, 400, 403, 500) and same "no subsequent call" rule
- [p.142-144] Slight contradiction between APIs: in the Runtime API the Function-Error-Type header is "Required: no", but in extensions (init/exit error) it is "Required: yes"


## Telemetry API (overview and limits; p.145-174)
- [from source] (LAMBDA p.145) The Telemetry API lets extensions receive telemetry directly (logs, platform metrics, platform traces) in near real time; the extension subscribes to streams from the execution environment and Lambda sends everything automatically; the extension can process, filter and deliver (e.g. S3 or a third-party tool)
- [from source] (LAMBDA p.145) The Telemetry API REPLACES the Logs API (which remains functional); recommended to use only the Telemetry API; after subscribing through one of the APIs, trying to subscribe through the other returns an error
- [from source] (LAMBDA p.145) Three streams: Platform telemetry (logs, metrics, traces about the lifecycle of the runtime/extension and invocations); Function logs (custom logs from the function code); Extension logs (custom logs from the extension)
- [from source] (LAMBDA p.145) Lambda continues sending logs and metrics to CloudWatch and traces to X-Ray (if tracing is active) even if the extension subscribes
- [from source] (LAMBDA p.146) Recommendation: implement in a compiled language (Golang or Rust) for a self-contained binary
