Only the **introduction** is in the PDF, not the papers (Schmidt's Pascal/R 1977, CQL by Arasu, Babu and Widom 2006, Bloom by Alvaro et al. 2011). Paraphrased summaries, no literal quotation. ## 1. Premise of the chapter: two abstractions and the "crisis" [from source]
- **Users and abstractions**: the author observes that most database users are software engineers building applications, and rarely people writing SQL directly. Two values of DBMSs for them: the **transactional model** (the illusion of a sequential machine that does not fail midway through the task) and **declarative query languages** (manipulating datasets without saying how to access them, which gives data independence) (REDBK p.41).
- **Transactions**: they are influential as a programming construct (BEGIN and COMMIT/ROLLBACK), but expensive and often compromised; relaxed semantics expose application logic to races and unpredictable exceptions. The common answer, "eventual consistency", merely shifts the responsibility for correctness to the developer. In the author's opinion, this is a **crisis** of modern software development (REDBK p.41).
- **Query languages**: a success and an improvement over the earlier navigational languages, but they operate on unordered collections (sets, relations, streams), whereas programming languages execute statements in order over complex structures: the **impedance mismatch** that has accompanied relational databases from the start (REDBK p.41).

## 2. Pascal/R, ODBC/JDBC, LINQ and ORMs [from source]
- **Pascal/R**: the first paper attacks the impedance mismatch by defining collection types (today recognizable as Python's dictionary or Java/Ruby's map) and proposing a declarative SQL-like sublanguage embedded in Pascal; it highlights the difference between **enumeration** (generating output) and **quantification** (checking properties), the latter being optimizable when explicit (REDBK p.42).
- **ODBC and JDBC** emerged as a "crutch" for C/C++ and Java: they push queries to the DBMS and iterate over results, but the type systems remain separate. The author sees **LINQ** (Microsoft) as the best modern evolution of the ideas of Pascal/R (REDBK p.42).
- **ORMs**: in the web applications of the 2000s, the repeated patterns were codified in ORMs (Ruby on Rails is cited as one of the most influential). They provide language-native collection primitives, transparently reflect changes to in-memory objects in the database, offer syntax for entities, relationships and keys, and, in some cases (Rails), schema migration tools (REDBK p.42).
- **Problems with ORMs**: the text cites the author of Rails (DHH) arguing for distrusting the database and keeping business logic in the domain layer, without stored procedures or constraints; the chapter says that this distrust creates problems. Applications built on ORMs tend to be **slow** (the ORM does little to optimize the generated queries) and the programmer has to learn to program "differently" (avoid loops and table-by-table iteration) for the ORM to generate efficient SQL; the typical cycle is to write naively, observe slowness, read the SQL logs and rewrite (REDBK p.42).
- **Integrity in the application**: Bailis showed that several open-source Rails applications suffer **integrity violations** from enforcing rules in the application instead of the database; Cheung and colleagues explore **program synthesis** to generate these optimizations automatically. Despite the blind spots, the author considers ORMs a practical advance in programmability and a validation of the ideas of Pascal/R (REDBK p.42).

## 3. CQL and stream languages [from source]
- **CQL (Continuous Query Language)**: a language design paper; it shows that streaming data, seen through the right lens, changes SQL **little**. CQL extends SQL just enough to isolate the semantic difference between querying tables "at rest" and streams "in motion", unlike several more ad hoc streaming languages (REDBK p.43).
- **Adoption**: the first generation of streaming research systems (early 2000s) **had no significant adoption**, neither in open source nor in the spin-off startups. Interest returned in industry, with Spark Streaming, Storm and Heron gaining use and with Google advocating continuous dataflow; the author thinks the area may still occupy more than its current niche, today concentrated in financial services (REDBK p.43).
- **Streams between databases and events**: databases store and retrieve collections, event systems transmit discrete events; when events are viewed as data, event programming and stream programming become similar, with little impedance mismatch between, for example, JavaScript and a stream system. Example cited: the Rx language (reactive extensions), a streaming addition to LINQ (REDBK p.43).

## 4. Bloom, the CALM theorem and monotonicity [from source]
- **Bloom**: seeks to answer whether there is a correct distributed implementation of a program **without transactions** or other expensive order-control schemes. It offers a "disorderly" language: standard structures are relations and the basic constructs are logical rules that can run in any order; simple Bloom programs have a well-defined result independent of execution order, for the same reason that SQL queries can be optimized and parallelized without changing the output (REDBK p.43).
- **Non-monotonic lines**: the exception is constructs that test a property that can oscillate between true and false over time (examples from the text: `NOT EXISTS x` and `HAVING COUNT() = x`). They are sensitive to the order of execution and of messages and need to be "protected" by coordination mechanisms (REDBK p.43).
- **CALM theorem**: a program has a consistent and **coordination-free** distributed implementation if, and only if, its specification is **monotonic**. The Bloom paper shows how a compiler can use CALM to point out where coordination is necessary; CALM analysis can also be applied to stream languages, such as Storm, with programmer annotations (REDBK p.43).
- **Related work and definitions**: there are other lines of avoiding coordination (associative, commutative and idempotent operations, which are monotonic; invariants specific to the database state; program analysis for serializable results without classical concurrency control). The area is new, the works use different models and do not always agree on "consistency" or "coordination". In CALM, **consistency** means globally deterministic results and **coordination** means messages that are necessary regardless of partitioning or replication of the data; if programmers cannot have transactions, they need help at the development layer (REDBK p.43-44).

## 5. Datalog and general-purpose declarative languages [from source]
- **Datalog**: classic example of a general-purpose declarative language ("logic programming"), with a long and controversial history in database research: a favorite topic of theorists in the 1980s and the target of strong reaction from systems researchers of the time, who considered it irrelevant in practice (REDBK p.44).
- **Nicira and the Datalog revival**: it has again received attention from younger database researchers and from other applied areas. Example from the text: the software-defined networking stack of **Nicira** (acquired by VMware for about "a billion" dollars, an informal expression of the author) uses a Datalog language for the network's forwarding state (REDBK p.44).
- **Spectrum**: the author describes a spectrum between using declarative sublanguages only to access database state and aggressive uses of declarative programming, such as Bloom, for the entire application logic; and says that time will show where the declarative-imperative boundary will settle (infrastructure, applications, web and mobile clients) (REDBK p.44).
