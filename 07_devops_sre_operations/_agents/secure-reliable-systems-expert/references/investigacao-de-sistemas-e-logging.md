## Ch. 15 — Investigating systems (BSRS p.369-396; Part IV p.397-398)

### Premise (BSRS p.369-370)
- [from source] The ability to investigate depends on adequate logs and information sources and on expertise; logging systems must be designed with protection and access control; even read-only debug access can be abused, so a balance is needed between debugging needs and data security requirements (BSRS p.369). In this chapter "debugger" is the person who debugs (BSRS p.370).

### From debugging to investigation: the temporary files example (BSRS p.370-372)
- [from source] Alert for Spanner out of storage quota: accumulation of many small files in Colossus; cause: servers with little memory that, when running out of memory, flush many tiny files; the memory was in the kernel's dentry cache (slabtop command in production); hypothesis: creation and removal of vast numbers of temporary files; confirmed by reproducing the bug with a looping program in Borg; the kernel caches the nonexistence of files and only evicts when the container fills up, which never happened; fix: mark temporary files as non-cacheable (BSRS p.370-371). Characteristics of the investigation: no part was broken, kernel tools used without prior experience, an initial error diagnosed as user error only reversed after the data, hypothesis tested before changing the system (BSRS p.372).

### Debugging techniques (BSRS p.372-380)
- [from source] Two requirements (SRE book, ch.12): know how the system is supposed to work and be systematic (collect data, formulate causes, test theories); there is no substitute for understanding the system beforehand (Ch.6); example of a system whose only author left the company (BSRS p.372).
- [from source] Distinguish horses from zebras: at large scale rare events become certainties (example: 25,000 machines and 400,000 RAM chips, 0.1% risk per year per chip, about 400 occurrences per year, one memory failure per day); faulty DIMMs traced to a single vendor and to an environmental failure in a factory clean room; in 2000 memory corruption was a surprise at Google, today routine with end-to-end integrity checking (BSRS p.373). Other zebras: two searches with the same 64-bit cache key; int64 to 32-bit int conversion in C++ causing failure after 2^32 requests; a rebalancing algorithm bug only at hundreds of simultaneous servers; a load test forgotten for a week; a dynamic linker with superlinear time in the number of libraries (10,000 libraries take minutes) (BSRS p.374). In new, small systems expect horses; in old, large, stable systems, zebras; problems appear more in new parts (BSRS p.374).
- [from source] Data corruption and checksums: hardware or software (one thread writing while another reads); it is dangerous to assume every strange bug is hardware; ECC RAM corrects most, uncorrectable errors trigger a machine check exception, the OS may panic or kill the process; checksums: CPU cost vs. protection; CRC protects against simple bit flips, cryptographic hashes against human attackers (CRC is much cheaper); scope of the checksum (a client that includes the key in the value and in the checksum detects a server that returns the wrong value) (BSRS p.374-375).
- [from source] Set aside time: investigations take many uninterrupted hours (the temporary files case took 5 to 10 hours); in a large incident isolate debuggers from the minute-by-minute response; the first responder attributed the outage to users in a context of operational overload and pager fatigue; the SRE book suggests keeping fewer than two tickets/pages per shift (BSRS p.375).
- [from source] Record observations and expectations: structure and memory of the investigation, lets someone else take over, avoids duplicated work, and in possible security incidents the log of each access and step can serve to prove which actions were the attacker's and which the investigators' (including in court); also write down what you expected to observe and why, since bugs live between the mental model and the implementation (BSRS p.375-376).
- [from source] Know what is normal: examples of false alarms (abort at the end of shutdown; Chrome resolves three random .local domains to detect DNS tampering and was mistaken for malware even by Google's investigation team); in security investigations there is background noise (SSH brute force, password errors, port scans) and adversaries who hide; establish a baseline (or infer it from historical logs); example: after the YouTube outage, comparing Borg task OOMs with a two-week baseline showed that Google has many OOMs per day; beware normalization of deviance (a server with ~10% of memory in heap fragmentation accepted for years); counter it by listening to newcomers, rotating on-call, documenting, and using Red Teams (BSRS p.376-377).
- [from source] Reproduce the bug outside production when possible: it does not affect users, exposes no sensitive data, and allows more people and extra logging; sometimes infeasible (bug only at scale) (BSRS p.377). Isolate the problem (turn off components, the smallest subset of code; example of thread stacks with different sizes: libs chose an arbitrary size) (BSRS p.378). Correlation is not causation: trivial correlations; ask "X, Y, and Z are broken: what element do they have in common?"; a tool that correlates machine problems with Borg tasks; deploys can trigger latent bugs (example in which the older, slower code worked as an accidental throttle) (BSRS p.378-379). Test hypotheses with real data: a slow server whose problem was logging everything to disk and calling sync, not the backends; observability = determining what the system does by examining its outputs; Dapper and Zipkin; Brendan Gregg's Systems Performance (BSRS p.379). Reread the documentation (a dashboard with an optimization that never worked: the warning was in the Python documentation) (BSRS p.380). Practice: DiRT and pentests; smaller one-hour exercises with one or two people are worthwhile; keep the code you write when debugging (BSRS p.380).

### When you are stuck (BSRS p.380-384)
- [from source] Improve the debugging process; postmortem methods (Ch.18) can suggest paths (BSRS p.380-381). Improve observability: structured logging (a server with many 404s without a log: it was malware trying to fetch wrong files); serious instrumentation (mutex wrapper in the Bigtable master with queue and hold time); distributed tracing (Dapper joins traces by RPC tree ID); web server embedded in Google binaries with debug endpoints (counters, thread dump, in-flight RPCs); observability does not replace understanding the system or thinking critically; small organizations can use open source or third-party solutions (BSRS p.381-382). Take a break (communicate to the team and document where you stopped) (BSRS p.382). Clean up the code (-Wconversion; more unit tests on suspicious functions; sanitizers and annotated mutexes in concurrent code; better error handling with context) (BSRS p.382-383). Delete: legacy systems may have bugs or be compromised; a researcher reported a flaw via the Vulnerability Reward Program in an isolated and forgotten legacy system, which was removed and replaced with something simpler; beware of rewrites for fun (BSRS p.383). Stop when things start going wrong: example of network equipment corrupting internal DNS responses (exa1 vs. exa2); the archiving service that verified machine identity failed closed (preferable), while the metrics system collected from the wrong machine and triggered repair on exa1 (a technician noticed disk 5 on a machine without five disks); failing closed avoids downstream effects (Ch.8) (BSRS p.383-384). Improve access and authorization even in non-sensitive systems: "too many cooks" make it hard to isolate the cause; reducing roles with access and requiring justification helped investigate database row corruption (BSRS p.384).
- [from source] Collaborative debugging to teach: build psychological safety; rules: only two people with laptops (driver and note taker), every action decided by the audience, no one knows the solution in advance; Wheel of Misfortune (test giver and test taker) as an alternative with more setup; inclusive environment (BSRS p.384-385).

### Security investigations vs. debugging (BSRS p.386-387)
- [from source] Engineers debug; compromise investigations should be done by security and forensics specialists; in the gray zone, collaboration; debugging is focused on code and data; a security investigation quickly asks about the user who submitted the job, their other activities, an active attacker, and next steps (BSRS p.386). Debugging steps can be counterproductive: adding code or disabling systems can have side effects; cases in which a debugger deleted "strange" files that were the attacker's, alerting them (in one case the attacker responded by wiping the entire system); urgency and scope grow (legal, police, regulators); when you suspect compromise, call security professionals (BSRS p.386).
- [from source] Signs of possible compromise: missing, truncated, or corrupted logs and data; hypothesis shifting from system behavior to the actions of an account or user; inexplicable behavior treated as accidental (a web server that spawns interactive shells when it "crashes"); files with abnormal characteristics (a 1 GB rick_roll.gif with ZIP or TAR headers); hidden or misleadingly named files (explore.exe) (BSRS p.386-387). Deciding when to declare an incident is hard; engineers tend not to "make a scene", but continuing until there is proof can be wrong; remember horses vs. zebras, but stay alert to the stripes (BSRS p.387).

### Collecting appropriate and useful logs (BSRS p.387-389)
- [from source] Logs and crash dumps are information for understanding what happened; before launching a service, consider what data it stores and the access paths; assume that any action that leads to access to data or the system may be investigated and audited; "logs" here = structured, timestamped records; core dumps, memory dumps, and stack traces should be treated as logs (BSRS p.387).
- [from source] Design logging to be immutable: hard to alter (but not impossible, see privacy) with an immutable audit trail; attackers erase traces when they establish themselves; practice: write logs remotely to a central, distributed, hardened server (double effort for the attacker); in the old days critical servers printed logs on a line printer (BSRS p.388).
- [from source] Privacy: consult privacy and legal; depth of logging (organizational policy on what can be logged); retention (2018 study: ~200 days on average to discover a compromise; insider investigations at Google used multi-year OS security logs); access controls and auditing as for other data (Ch.5); anonymization or pseudonymization (allows assembling the timeline of a session without knowing who the user is; it is hard to get right; consult specialists); asymmetric encryption of logs (public key writes, private key decrypts; daily key pairs allow obtaining small recent subsets without large aggregates; protect the keys well) (BSRS p.388-389).

### Which security logs to retain (BSRS p.390-393)
- [from source] Be selective: excess logs cost money and slow investigators down (BSRS p.390). OS logs (Windows Event logs; syslog and auditd; appliances with embedded OS; auditd is not enabled by default for performance but the tradeoff is worth it); host agents (HIDS; antivirus is less useful today and can bring risk if poorly written; "next-gen" agents with behavioral modeling, machine learning, and threat intelligence; OSQuery and GRR for real-time visibility; kernel agents have more functionality and more reliability problems, userspace agents are easier; evaluate carefully) (BSRS p.390-391). Application logs (SAP, SharePoint, open source or custom; example of using Google Drive logs to find out whether a compromised computer downloaded sensitive data; combine security and developers to log data writes, owner or state changes, and account activity) (BSRS p.391). Cloud logs (an attacker with credentials of a project launches containers in Kubernetes to steal buckets; new instances daily; BigQuery to collect and detect; Cloud Audit Logs, Stackdriver Logging; difficulty identifying, enabling, and centralizing all logs; providers predefine available logs) (BSRS p.391-392). Asset inventory (cross-reference payments to cloud providers with systems; BeyondCorp's Device Inventory Service); cloud threat detection (Event Threat Detection); CASBs as intermediaries that enforce controls and log (BSRS p.392). Network logs: NIDS and IPS recommended for almost every organization (beware who will triage the alerts), DNS logs (queries to malicious hosts; DNS sinkholes; high-priority alert when someone accesses a sinkholed domain), web proxy logs (consider employee privacy and legal; tune detection to malicious content to minimize employee data) (BSRS p.392-393).
- [from source] Logging budget: investigating uses resources (a system with 100 TB of almost never used logs); budget in advance; query systems (Elasticsearch, BigQuery) cost more as events, machines, and storage grow; prioritize sources for long retention; if you keep only a week of access logs it may not be possible to investigate an intrusion (BSRS p.393). Degrade gracefully instead of stopping collection: summarization (90% for full retention and 10% for lower-fidelity summaries; write two files at collection; e.g., full packet capture deleted after N days and netflow kept for a year); focus on logs with a good signal-to-noise ratio (packets blocked by the firewall); compress; separate warm and cold storage; rotate intelligently (delete the oldest first, preserving more important types for longer) (BSRS p.394).

### Robust and secure debug access (BSRS p.395-396)
- [from source] Reliability: logging also fails (disk full); failing open makes the system more resilient but the attacker can bring down logging; plan to debug the security systems themselves: offline emergency credentials in a secure location that trigger high-confidence alarms (case of a Google network outage in which the authentication system failed closed and the emergency credentials allowed fixing it) (BSRS p.395).
- [from source] Security: phone support systems with user impersonation are great for debugging and for abuse; debugging endpoints (from impersonation to raw database access) must be protected; many incidents do not require user data (encrypting data in transit lets more engineers access packet dumps); metadata is not non-sensitive (correlated access patterns reveal a lot); some analyses require real data (e.g., an account receiving thousands of emails per hour); see access control in "Zero Trust Networking" (Ch.5) (BSRS p.395-396).
- [from source] Conclusion: debugging is systematic, not guesswork; security investigations differ and require security professionals; centralized logging is useful, critical, and useful to the business; iterate by looking at recent investigations and asking what information would have helped; design for security (logs and debug endpoints become targets); "luck favors the prepared" (BSRS p.396).
