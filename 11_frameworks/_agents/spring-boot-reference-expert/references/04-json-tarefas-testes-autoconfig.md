# 04 — JSON, tasks, Boot tests, custom auto-configuration/starter and Kotlin (ch. 7.7 to 7.12)

Pages = PDF (SBR p.N; printed = N−20). Version 2.7.18 [DATED]. **General** testing (JUnit, Mockito etc.) is out of scope; here only what the text says about **Spring Boot** tests.

## JSON
- **[from source]** Three integrated libraries: Gson, Jackson (preferred and default) and JSON-B (SBR p.147). Jackson is part of `spring-boot-starter-json`; there is an `ObjectMapper` bean configurable through properties (SBR p.148).
- **[from source]** `@JsonComponent` registers serializers/deserializers as beans; `JsonObjectSerializer`/`JsonObjectDeserializer` are alternatives; mixins are registered by the `JsonMixinModule` (SBR p.148-152).
- **[from source]** Gson: `spring.gson.*` properties and `GsonBuilderCustomizer`; JSON-B: preferred implementation Apache Johnzon (SBR p.153).
- **[from source, how-to]** Boot's `ObjectMapper` turns off `DEFAULT_VIEW_INCLUSION`, `FAIL_ON_UNKNOWN_PROPERTIES`, `WRITE_DATES_AS_TIMESTAMPS` and `WRITE_DURATIONS_AS_TIMESTAMPS`; features via `spring.jackson.{deserialization|generator|mapper|parser|serialization}.<FEATURE>` and `spring.jackson.default-property-inclusion` (SBR p.589-590). Defining your own `@Primary` `ObjectMapper` turns off auto-configuration (SBR p.590-591).

## Tasks and scheduling
- **[from source]** Without an `Executor` bean, Boot configures a `ThreadPoolTaskExecutor` (8 core threads, which grow and shrink with load) wired to `@EnableAsync` and to async MVC; properties `spring.task.execution.pool.{max-size, queue-capacity, keep-alive}` (SBR p.153-154). The auto-configured `TaskExecutorBuilder` reproduces what auto-configuration does (SBR p.153).
- **[from source]** **Custom `Executor` (TIP, SBR p.153):** `@EnableAsync` uses that `Executor` normally, but Spring MVC's support for asynchronous processing is NOT configured, because MVC requires an implementation of `AsyncTaskExecutor` (named `applicationTaskExecutor`). The book gives TWO ways out, depending on your setup: (1) change your `Executor` into a `ThreadPoolTaskExecutor`; or (2) define both, a `ThreadPoolTaskExecutor` and an `AsyncConfigurer` that wraps your `Executor`. The book gives NO other recipe (for example, "declare any `AsyncTaskExecutor` bean"): do not present that as from the book.
- **[from source]** The book's example for the executor (SBR p.153-154): `spring.task.execution.pool.max-size=16`, `queue-capacity=100`, `keep-alive=10s`; with a bounded queue, when it fills the pool grows up to the maximum, and idle threads are recycled in 10 s (the default is 60 s). In Appendix A, `max-size` exists only under `spring.task.execution.pool.*` (SBR p.675-676); the scheduler has `spring.task.scheduling.pool.size` (default 1) and does NOT have `max-size` (SBR p.676).
- **[from source]** `ThreadPoolTaskScheduler` with 1 thread by default: `spring.task.scheduling.pool.size`, `thread-name-prefix`; there are `TaskExecutorBuilder`/`TaskSchedulerBuilder` (SBR p.153-154).

## Spring Boot tests
- **[from source]** Modules `spring-boot-test` and `spring-boot-test-autoconfigure`; the test starter brings JUnit 5, Spring Test, AssertJ, Hamcrest, Mockito, JSONassert, JsonPath; JUnit 4 via the vintage engine (SBR p.154-155).
- **[from source]** `@SpringBootTest` (creates the context via `SpringApplication`); by default it does not start a server; `webEnvironment` attribute: `MOCK` (default) = web context with a mock web environment, no embedded server, and falls back to a non-web context if there is no web on the classpath, combinable with `@AutoConfigureMockMvc`/`@AutoConfigureWebTestClient`; `RANDOM_PORT` = `WebServerApplicationContext` with a real web environment, embedded server on a random port; `DEFINED_PORT` = same, on the defined port (application.properties) or the default 8080; `NONE` = `ApplicationContext` via `SpringApplication` with no web environment at all (not even mock) (SBR p.156). `RANDOM_PORT` also starts the management server on another random port if the application uses a different management port; with MVC and WebFlux together, MVC prevails and, to test reactive, use `spring.main.web-application-type=reactive` (SBR p.157). A `@Transactional` test does not roll back transactions of the real server (RANDOM_PORT/DEFINED_PORT) (SBR p.156).
- **[from source]** The configuration search goes up through the packages until it finds `@SpringBootApplication`/`@SpringBootConfiguration` (SBR p.157); a nested `@TestConfiguration` is used **in addition to** the primary configuration, unlike a nested `@Configuration`, which would be used **in place of** the application's primary configuration (SBR p.158); `@TestConfiguration` on a top-level class indicates that it should not be picked up by scanning and must be imported where needed (`@Import(MyTestsConfiguration.class)`), which prevents configuration classes created only for certain tests from being picked up everywhere (SBR p.158); the context is cached between tests (SBR p.157-159).
- **[from source]** `MockMvc` (`@AutoConfigureMockMvc`), `WebTestClient` and `TestRestTemplate`; MockMvc does not test container behavior (e.g. the error page) (SBR p.160-166). `@MockBean`/`@SpyBean` (reset after each method; not suitable for beans exercised during the refresh; they affect the context cache) (SBR p.168-171). JMX is off in tests by default because the context is cached and identical components would register in the same domain; if the test needs an `MBeanServer`, the book's example uses `@SpringBootTest(properties = "spring.jmx.enabled=true")` together with `@DirtiesContext` (the book says to mark it dirty as well) (SBR p.167). Metrics registries (except in-memory ones) are not auto-configured in `@SpringBootTest`, whatever the classpath; to export metrics to another backend in an integration test, annotate the test with `@AutoConfigureMetrics` (SBR p.168).
- **[from source]** Slices (`@JsonTest`, `@WebMvcTest`, `@WebFluxTest`, `@GraphQlTest`, `@DataJpaTest`, `@JdbcTest`, `@DataJdbcTest`, `@DataR2dbcTest`, `@JooqTest`, `@DataMongoTest`, `@DataNeo4jTest`, `@DataRedisTest`, `@DataLdapTest`, `@RestClientTest`, `@WebServiceClientTest`...) load part of the context; two `@…Test` are not combined (SBR p.172-217). List of auto-configurations per slice: Appendix D (SBR p.828-837; diff `@DataJdbcTest` x `@DataJpaTest` summarized below, SBR p.830). **Details per annotation (what they scan, transaction, embedded database, how to change): section "Test slices: details per annotation" further below.**
- **[from source]** A custom `@ComponentScan` on the application class disables the slice filters (SBR p.158, 222-223). `@Bean` beans in `@Configuration` do not enter a slice by scanning; split the configuration and use `@Import` (SBR p.650-652).
- **[from source]** Utilities: `ConfigDataApplicationContextInitializer` (does not support `@Value` by itself), `TestPropertyValues`, `OutputCaptureExtension`, `TestRestTemplate` (does not throw on 4xx/5xx; details in the next line) (SBR p.223-228). `ApplicationContextRunner` tests auto-configurations (SBR p.236-240). Testcontainers with `@DynamicPropertySource`: `registry.add("spring.neo4j.uri", neo4j::getBoltUrl)` (SBR p.649); the container starts before the tests if Docker is running locally (SBR p.648); in Kotlin it uses a `companion object` and `neo4j.boltUrl` (SBR p.650).
- **[from source]** `TestRestTemplate` in detail (SBR p.226-229): a convenience alternative to `RestTemplate` for integration tests; it can be the plain version or the one that sends Basic authentication (user and password); it is fault tolerant, i.e. it does not throw on 4xx/5xx and the error is detected through the `ResponseEntity` and its status (SBR p.226). Apache HTTP Client (version 4.3.2 or higher) is **recommended, not mandatory**; with it on the classpath the template is configured to use it and turns on test-friendly features: **redirects are not followed** (you can assert the response's location header; the book's example uses `assertThat(headers.getHeaders().getLocation()).hasHost("other.example.com")`) and **cookies are ignored** (the template stays stateless) (SBR p.227). It can be created directly with `new TestRestTemplate()` and a full URL (SBR p.227-228). **Injection and host:** with `@SpringBootTest` in `RANDOM_PORT` or `DEFINED_PORT` you can inject (`@Autowired`) an already configured `TestRestTemplate`, and any URL without host and port connects by itself to the embedded server (SBR p.228-229). **Timeouts and tweaks:** extra customizations come from the `RestTemplateBuilder` bean, for example in a nested `@TestConfiguration` that defines `setConnectTimeout` and `setReadTimeout` with `Duration` (the example uses 1 second) (SBR p.228-229). `WebTestClient`: the TIP on SBR p.227 only says it exists since Spring Framework 5.0, serves WebFlux integration tests and end-to-end WebFlux and MVC tests, and has a fluent assertion API, unlike `TestRestTemplate`; **the book does not declare it "recommended" nor a replacement**; it requires spring-webflux on the classpath and, without webflux, Boot offers `TestRestTemplate` (SBR p.165, 227).

## Test slices: details per annotation (SBR p.172-223)
- **[from source]** General rules: each slice restricts the component scan to certain types and loads a minimal set of auto-configurations; to exclude one, most `@…Test` annotations have the `excludeAutoConfiguration` attribute (or `@ImportAutoConfiguration#exclude`); **combining several `@…Test` is not supported**: pick one and include by hand the `@AutoConfigure…` of the others; the `@AutoConfigure…` annotations also work with `@SpringBootTest` (SBR p.172). In all slices, plain `@Component` and `@ConfigurationProperties` beans are **not** scanned and `@EnableConfigurationProperties` brings in the `@ConfigurationProperties` (SBR p.175, 190, 193).
- **[from source]** **`@DataJpaTest`**: by default scans `@Entity` classes and configures Spring Data JPA repositories; **if there is an embedded database on the classpath, it configures one** (SQL queries are logged: `spring.jpa.show-sql` becomes true; the `showSql()` attribute turns it off); plain `@Component`/`@ConfigurationProperties` are not scanned (SBR p.190). Tests are **transactional and roll back** at the end of each test; to turn off transaction management on the test or class: `@Transactional(propagation = Propagation.NOT_SUPPORTED)` (SBR p.190-191). You can inject `TestEntityManager` (a test-specific alternative to `EntityManager`) and `JdbcTemplate`; `@AutoConfigureTestEntityManager` in another test requires it to run in a transaction (e.g. `@Transactional`) (SBR p.191). To test against a real database instead of the embedded one: `@AutoConfigureTestDatabase(replace = Replace.NONE)` (SBR p.193).
- **[inference/extrapolation]** Typical question "my data vanished / it used H2 / my service does not exist in the test": (1) rollback is the slice default; the Reference solves it with `NOT_SUPPORTED` (SBR p.190-191); the Spring Test Rollback and Commit annotations **do not appear** in the Reference (0 occurrences; label [extrapolation]); (2) the embedded database comes from the slice itself and goes away with `Replace.NONE` (SBR p.193); (3) a service bean is a plain component and is not scanned by the slice: [inference] use `@Import` (SBR p.190, 221) or a full-context test (SBR p.156-159). The Reference's Testcontainers: example with Neo4j and `@DynamicPropertySource` (`neo4j::getBoltUrl`, SBR p.649; Kotlin version p.650; the container starts before the tests if Docker is local, p.648), not Postgres (SBR p.647-650).
- **[from source]** `@JdbcTest`: only `DataSource` (no Spring Data JDBC); configures an embedded database and `JdbcTemplate`; transactional with rollback, can be turned off as in JPA; `@AutoConfigureTestDatabase` the same (SBR p.193-194). `@DataJdbcTest`: Spring Data JDBC repositories; only subclasses of `AbstractJdbcConfiguration` are scanned; transactional with rollback, and the transaction is turned off "as in the JDBC example", i.e. `@Transactional(propagation = Propagation.NOT_SUPPORTED)` on the test or class (SBR p.194, JDBC example on p.193-194). **Appendix D, p.830 (diff `@DataJdbcTest` x `@DataJpaTest`):** both import in common Cache, DataSource, DataSourceTransactionManager, JdbcTemplate, **Flyway, Liquibase** (migrations run in both slices), SqlInitialization, Transaction and TestDatabase (`TestDatabaseAutoConfiguration`); only Data JDBC imports `JdbcRepositoriesAutoConfiguration`; only Data JPA imports `JpaRepositoriesAutoConfiguration`, `HibernateJpaAutoConfiguration` and `TestEntityManagerAutoConfiguration` (SBR p.830). `@DataR2dbcTest`: embedded database, `R2dbcEntityTemplate`, R2DBC repositories; **not transactional** (SBR p.194-195). `@JooqTest`: configures `DSLContext`; uses the existing `DataSource` (the jOOQ Java schema depends on the real database) and `@AutoConfigureTestDatabase` swaps it for an embedded one (SBR p.195).
- **[from source]** NoSQL: `@DataMongoTest` (embedded Mongo if available, `MongoTemplate`, `@Document` classes, repositories; `excludeAutoConfiguration = EmbeddedMongoAutoConfiguration.class` turns off the embedded one) (SBR p.196-197); `@DataNeo4jTest` (`@Node` classes; transactional with rollback, can be turned off with `NOT_SUPPORTED`; **test transactions are not supported with reactive access**) (SBR p.197-199); `@DataRedisTest` (`@RedisHash` classes) (SBR p.199); `@DataLdapTest` (embedded LDAP if available, `LdapTemplate`, `@Entry` classes; `EmbeddedLdapAutoConfiguration` excludes the embedded one) (SBR p.200-201); `@DataCassandraTest` (`CassandraTemplate`, `@Table` classes) (SBR p.187); `@DataCouchbaseTest` (`CouchbaseTemplate`/`ReactiveCouchbaseTemplate`, `@Document` classes) (SBR p.188); `@DataElasticsearchTest` (`ElasticsearchRestTemplate`, `@Document` classes) (SBR p.189).
- **[from source]** `@JsonTest`: configures the available JSON mapper (Jackson `ObjectMapper` with `@JsonComponent` and modules, Gson or Jsonb); `@AutoConfigureJsonTesters` adjusts it; AssertJ helpers `JacksonTester`, `GsonTester`, `JsonbTester`, `BasicJsonTester` can be `@Autowired` (`write`, `parse`, `parseObject`; `isEqualToJson`, `hasJsonPathStringValue`) (SBR p.172-173). For a number in a JSON path `isEqualTo` may not work: use AssertJ's `satisfies` (e.g. `isCloseTo`) (SBR p.174-175).
- **[from source]** `@WebMvcTest`: configures the MVC infrastructure and limits beans to `@Controller`, `@ControllerAdvice`, `@JsonComponent`, `Converter`, `GenericConverter`, `Filter`, `HandlerInterceptor`, `WebMvcConfigurer`, `WebMvcRegistrations` and `HandlerMethodArgumentResolver`; it is usually limited to one controller with `@MockBean` for the collaborators; auto-configures `MockMvc` (in other tests: `@AutoConfigureMockMvc`, whose attributes adjust, for example, servlet filters); extra modules come in with `@Import` (SBR p.175-177). With HtmlUnit/Selenium there are `WebClient`/`WebDriver` beans; the `WebDriver` lives in a special `webDriver` scope (discarded after each test; `@Scope("singleton")` turns that off) and replaces a custom scope of the same name (SBR p.177-179). With Spring Security on the classpath, `@WebMvcTest` also scans `WebSecurityConfigurer` beans; instead of turning security off, use Spring Security's test support (SBR p.179).
- **[from source]** `@WebFluxTest`: beans limited to `@Controller`, `@ControllerAdvice`, `@JsonComponent`, `Converter`, `GenericConverter`, `WebFilter`, `WebFluxConfigurer`; auto-configures `WebTestClient` (other tests: `@AutoConfigureWebTestClient`) (SBR p.179-181). It **does not detect** functional-model routes (`RouterFunction`) nor a `SecurityWebFilterChain` `@Bean`: import them with `@Import` or use `@SpringBootTest` (SBR p.182).
- **[from source]** `@GraphQlTest`: requires `spring-graphql-test`; no transport or server; beans limited to `@Controller`, `RuntimeWiringConfigurer`, `JsonComponent`, `Converter`, `GenericConverter`, `DataFetcherExceptionResolver`, `Instrumentation`, `GraphQlSourceBuilderCustomizer`; `GraphQlTester` (`ExecutionGraphQlServiceTester` on the server; `HttpGraphQlTester` with a client); with `@SpringBootTest`, `@AutoConfigureHttpGraphQlTester` (SBR p.182-186).
- **[from source]** `@RestClientTest`: Jackson/Gson/Jsonb, `RestTemplateBuilder` and `MockRestServiceServer`; the beans under test go in `value`/`components` (SBR p.201-202). `@WebServiceClientTest` (mock `MockWebServiceServer`, customizes the `WebServiceTemplateBuilder`) and `@WebServiceServerTest` (`MockWebServiceClient`) (SBR p.214-217). `@AutoConfigureRestDocs` (Spring REST Docs with MockMvc, WebTestClient or REST Assured; default output `target/generated-snippets` on Maven and `build/generated-snippets` on Gradle) (SBR p.203-214).
- **[from source]** Extra auto-configurations in a slice: `@ImportAutoConfiguration` on the test (do not use plain `@Import` for auto-configurations) (book example: `@JdbcTest` + `@ImportAutoConfiguration(IntegrationAutoConfiguration.class)`, a class in the package `org.springframework.boot.autoconfigure.integration`) or the file `META-INF/spring/org.springframework.boot.test.autoconfigure.jdbc.JdbcTest.imports` (one class per line; `#` comments) for all tests of that slice; a *slice annotation* or own `@AutoConfigure…` (*custom slice*) can be customized this way as long as it is meta-annotated with `@ImportAutoConfiguration` (SBR p.218-219).
- **[from source]** User configuration and slices: scanned `@Configuration` classes do **not** enter a slice (e.g. a `WebMvcConfigurer` `@Bean` in a `@Configuration` is left out of `@WebMvcTest`; a `@Component` that implements `WebMvcConfigurer` gets in); do not pollute the `@SpringBootApplication` class with area-specific configuration (e.g. `@EnableBatchProcessing`: move it to a separate `@Configuration`); a custom `@ComponentScan` on the main class nullifies the filters and makes the slice scan everything; the way out is to move the directive or create a `@SpringBootConfiguration` in the test hierarchy (SBR p.219-223). Spock 2.x via `spock-spring` (SBR p.223).

## Creating auto-configuration and starter
- **[from source]** `@AutoConfiguration` classes listed in `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` (one per line; `#` comments); never through component scan; ordering by `before`/`after`, `@AutoConfigureBefore`, `@AutoConfigureAfter` and `@AutoConfigureOrder` (SBR p.230-231).
- **[from source]** Conditions: `@ConditionalOnClass` and `@ConditionalOnMissingClass` (isolate `@Bean` in a nested `@Configuration`), `@ConditionalOnBean` and `@ConditionalOnMissingBean` (use only in auto-config; specific return type), `@ConditionalOnProperty` (`prefix`, `name`, `havingValue`, `matchIfMissing`), `@ConditionalOnResource`, `@ConditionalOnWebApplication`, `@ConditionalOnWarDeployment`, `@ConditionalOnExpression` (SBR p.231-236). **`@ConditionalOnProperty`:** by default, without `havingValue`, it matches any property that exists and is not equal to `false` (an absent property or one with the value `false` does not match); `havingValue` and `matchIfMissing` allow finer checks (SBR p.236). **`@ConditionalOnWarDeployment`/`@ConditionalOnNotWarDeployment`:** include the configuration depending on whether the app is a traditional WAR deployed in a servlet container; the condition **does not match in an application run with an embedded web server** (SBR p.236). **`@ConditionalOnExpression`:** includes the configuration depending on the result of a SpEL expression; the book's NOTE warns that referencing a bean in the expression makes that bean be initialized very early in the context refresh, so it is not eligible for post-processing (such as configuration property binding) and its state may be incomplete (SBR p.236). **Interface x concrete class:** the TIP that precedes the property conditions says to give as much type information as possible in the return of the `@Bean` method; if the concrete bean implements an interface, the return type should be the concrete class, not the interface, because the evaluation of bean conditions only sees the type declared in the method signature (SBR p.236).
- **[from source]** Why to isolate `@ConditionalOnClass` from `@Bean` (SBR p.232-233): on a `@Configuration` class the annotation metadata is read via ASM, so `value` can point to the real class even if it is absent from the classpath; on a `@Bean` method the condition target is usually the return type, and before the condition applies the JVM has already loaded the class and may process references that fail if it does not exist. The book's solution is a static nested `@Configuration` annotated `@Configuration(proxyBeanMethods = false)` + `@ConditionalOnClass(SomeService.class)` that contains the `@Bean` with `@ConditionalOnMissingBean` (SBR p.232-233).
- **[from source]** Own starter: `autoconfigure` module + starter module (can be one); **do not** start names with `spring-boot`; use your own namespace in keys (not `server`, `management`, `spring`); document properties with Javadoc; `spring-boot-configuration-processor`/`spring-boot-autoconfigure-processor` (SBR p.240-245, 813).

## Kotlin
- **[from source]** Kotlin ≥ 1.3.x; `kotlin-stdlib` + `kotlin-reflect`; `kotlin-spring` plugin (final classes); `runApplication`; `@ConstructorBinding` with `data class`; `-Xjsr305={strict|warn|ignore}` (default `warn`); JUnit 5 and MockK/SpringMockK (SBR p.245-248).

## Round 4 additions: tests, custom auto-configuration and Kotlin (page details)
- **[from source]** Tests, basics: if you have JUnit 4 tests, use JUnit 5's vintage engine with the `junit-vintage-engine` dependency (SBR p.155). Boot features (external properties, logging etc.) are only installed in the context by default when it is created via `SpringApplication`; `@SpringBootTest` replaces spring-test's standard `@ContextConfiguration` annotation; with JUnit 4 do not forget `@RunWith(SpringRunner.class)`, with JUnit 5 the equivalent `@ExtendWith(SpringExtension.class)` is not needed (SBR p.156). `@SpringBootTest` with `webEnvironment = WebEnvironment.RANDOM_PORT` also starts the management server on a separate random port if the application uses a different management port (SBR p.157). If you use `@ComponentScan` directly (without `@SpringBootApplication`), register the `TypeExcludeFilter`; an imported `@TestConfiguration` is processed before an inner-class `@TestConfiguration` and before any configuration found by component scan, which only matters if you depend on bean overriding (SBR p.159). For a `@SpyBean` on a proxied bean, `AopTestUtils.getTargetObject(yourProxiedSpy)` removes the Spring proxy (SBR p.172). The `@AutoConfigure…` annotations also work with `@SpringBootTest` when you want only a few test beans, without "slicing" (SBR p.172).
- **[from source]** JSON helpers: outside `@JsonTest`, call the helper's `initFields` in `@Before`; when asserting a number in a JSON path with the AssertJ helpers, `isEqualTo` may not work depending on the type and then `satisfies` is used (the example asserts a float close to 0.15 with a margin of 0.01) (SBR p.174). `@AutoConfigureTestEntityManager` in another class requires a test in a transaction (`@Transactional`) (SBR p.191). `@WebFluxTest` does not detect a security configuration registered as a `SecurityWebFilterChain` `@Bean`: import it with `@Import` or use `@SpringBootTest` (SBR p.182). For end-to-end tests with a real server, the book points to `@SpringBootTest` (SBR p.179, 182). Do not use plain `@Import` for auto-configurations in slices: use `@ImportAutoConfiguration` or a file in `META-INF/spring` (SBR p.219). About `WebTestClient`: the TIP on p.227 merely describes that it works in WebFlux integration tests and in end-to-end WebFlux/MVC tests and has a fluent assertion API, unlike `TestRestTemplate`; it is not a recommendation by the book in its favor (SBR p.227; requirement of spring-webflux on the classpath: SBR p.165).
- **[from source]** Custom auto-configuration, notes (SBR p.231-243): auto-configurations can only be loaded by name in the imports file, live in a specific package and are never a target of component scan; they must not enable component scan to find extra components (SBR p.231). In tests with `ApplicationContextRunner` you do not need to order the auto-configuration declarations: they are invoked in the same order as in the real application (SBR p.237). To document properties: only plain text in the Javadoc of the fields (it is not processed before entering the metadata JSON); Boot's own rules: do not start with "The" or "A", booleans with "Whether" or "Enable", collections with "Comma-separated list", use `java.time.Duration` and describe the default unit if it is not milliseconds (e.g. "If a duration suffix is not specified, seconds will be used"), and do not repeat the default value in the description unless it is computed (SBR p.243). Mark the library's dependencies as `optional` in the autoconfigure module; Boot uses an annotation processor to collect the conditions into `spring-autoconfigure-metadata.properties` (SBR p.243).
- **[from source]** Kotlin (SBR p.245-247): null-safety is checked at compile time; generic types, varargs and array elements do not yet have supported nullability (SPR-15942), and Boot's own API is not yet annotated (SBR p.246); `runApplication<MyApplication>(*args)` is an idiomatic replacement for `SpringApplication.run` (SBR p.246); with at least one reactive dependency, `kotlinx-coroutines-reactor` comes by default when starting a project at start.spring.io (SBR p.247).
