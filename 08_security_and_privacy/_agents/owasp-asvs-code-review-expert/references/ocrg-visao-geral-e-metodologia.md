# OCRG — overview, secure code review methodology (OCRG p.4-43)

Source: **OCRG** = *OWASP Code Review Guide* v2.0 (2017; leaders Larry Conklin and Gary Robinson; 220 PDF pages). **Convention**: every `OCRG p.N` citation is the PDF page; the printed page is N − 1 in the body (the 4th PDF page prints "3"). The cover, table of contents and chapter title pages have no printed number.

## Scope and stance of the book
- [from source] The guide grew out of the OWASP Testing Guide; the project started in 2006 and this edition in 2013 (reboot and funding from the US DHS). Focus on C#/.NET and Java, with C/C++, PHP and others "where possible"; web application flaws are "remarkably consistent" across languages (OCRG p.4).
- [from source] The guide **does not prescribe a process** for code review: it guides how to structure/run the effort and the **mechanics** of reviewing certain vulnerabilities (OCRG p.10). Three audiences: management (review time in the estimate, metrics, when to review), leads who give feedback to peers and the security reviewer (OCRG p.8).
- [from source] Types of code review cited: API/design, maintainability, integration (care with open source libraries and dependencies) and tests (look at the unit tests of the controls) (OCRG p.8).

## Why secure code review and what it is (OCRG p.10-13)
- [from source] Manual review is "probably the most effective technique" for finding security bugs early in the cycle; together with pentest, it improves cost-effectiveness. The central value is **context**: a human understands the relevance of a bug and estimates the real risk (probability of attack x business impact), prioritizing what to fix (OCRG p.10).
- [from source] CWE catalogs about 1000 weakness types; developers rarely learn this at school or at work; the software market is "black box", so the customer cannot tell good code from insecure code (OCRG p.10). Excuses rejected by the book: "we have never been hacked", "we have a firewall", "we trust our employees" (OCRG p.10-11).
- [from source] Secure code review = auditing the code to verify that security and logic controls **exist, work and are invoked in the right places** ("self-defending"). Rule of thumb: after a good review, a pentest should find no additional code vulnerabilities, or very few (OCRG p.11).
- [from source] Every review combines human effort and technology; SAST is great for coverage and a **minimum baseline**, but does not understand dynamic flow or business logic; **all tool output needs human verification** (is it real? exploitable? what is the risk?) and humans fill blind spots (OCRG p.11).
- [from source] Secure review = ordinary review with security "ahead" of the decision: high risk reviewed more deeply, reviewers with context and skill; general code review appears when the organization reaches maturity level 2-3 (CMM) (OCRG p.12).
- [from source] Scale: a hobbyist will not use everything; an organization of thousands of devs will treat security like performance. Book example: 15 extra minutes per week for 5,000 devs = 1,250 hours/week (about 30 full-time devs per year); but finding the bug in test/production costs more (OCRG p.12-13).
- [from source] **"You cannot hack your way to security"**: pentest is black-box and point-in-time, repeated at every release; the effectiveness of an unmaintained pentest decays; privacy, compliance and availability may not be covered by pentest (OCRG p.13; also Foreword, OCRG p.4: attackers have more time than the defender). The four methods (code scanning, automated pentest, manual pentest, review with an expert) are complementary; defense in depth reduces the risk of unknown problems (OCRG p.13-14). Survey charts (AppSec USA 2015) show manual review equal to or better in many cases (OCRG p.14-15; values only in a figure).
- [from source] **Team building**: security core + "satellites" (BSIMM term) in the teams; feedback within the review is 100% relevant "on-the-job" training (OCRG p.13, 24).
- [from source] **360 review**: use the review to plan the pentest and the pentest to direct a new review; white-box pentest establishes the real risk; once a class of flaw is found, look for other instances (OCRG p.15-16).
- [from source] Implicit benefits: historical record, verification of tests done, education of juniors, familiarization with the codebase, warning of integration conflicts, point of contact for secure coding guidelines (OCRG p.16-18).

## Technical aspects and compliance (OCRG p.18-20)
- [from source] Review is not just hunting for patterns: it is understanding the code flow and logic; study existing controls (e.g. a centralized blacklist) and **enumerate their weaknesses**; do **source-to-sink analysis** (sources = all inputs; sink = dangerous point such as dynamic SQL, log writer, response to the client); when a flaw is found, enumerate all instances (sweep started by management) (OCRG p.18).
- [from source] Compliance (PCI, central banks, audit, HIPAA): PCI-DSS 6.3.2 requires review of in-house code before release (by someone other than the author, with knowledge of secure code techniques; per guidelines; fixes before release; results approved by management); 6.5 requires training and development with guidelines; PA-DSS 5.1.4 and 5.2 for payment applications (OCRG p.18-20).

## Methodology (ch. 6, OCRG p.21-39)
### Factors (OCRG p.21-22)
- [from source] Forms: informal walkthrough, formal inspection, tool-assisted review (OCRG p.21). Factors: **risks** (prioritize with a risk-based approach; peer review of all code, but not everything gets secure review), **purpose and context** (payment vs promotional site; what the business wants to protect), **lines of code**, **language** (safe-typed languages such as C#/Java have fewer buffer overflows than C/C++; a language new to the company raises risk), **resources/time/deadline** (OCRG p.21-22).
- [from source] Integrate into the S-SDLC with standards and policies, allocated time (including for fixes) and a standard report with: date, application/modules, developers and reviewer, task/feature, classification and priority of vulnerabilities, links (requirements, design, tests, threat model), checklist used, tests done by the dev, tools used (OCRG p.22-23).

### When to review (OCRG p.23-24)
| Moment | Advantage | Disadvantage | Page |
|---|---|---|---|
| pre-commit (before check-in) | substandard code never gets in; requires links to requirements/design and tests; can reject for lack of docs/tests | slows down check-in | OCRG p.23 |
| post-commit | faster for the dev | lower quality ("already in"), risk of other changes in the same module, rework/regression | OCRG p.23-24 |
| periodic audits / when a repeated pattern is suspected | scanners and string searches speed it up; reviews the whole codebase | not tied to a feature/bugfix | OCRG p.24 |
- [from source] Agile: review should be continuous and aligned with the submitted code; there may be a "security sprint"; for security, agile vs waterfall does not matter (OCRG p.23-25). Who reviews: **all** devs need to understand the exposure points; security should be "assistance, not an obstacle"; the reviewer should act as an advisor, not a police officer (OCRG p.24, 27).

### Risk-based approach (OCRG p.25-26)
- [from source] It does not scale to bring in specialists for every change: **review intensity follows module risk**, measured by a reproducible criterion defined by management (never "everything is high risk"). Risk techniques (Table 1): quantitative, qualitative and **Delphi** (anonymous consultation) (OCRG p.25).
- [from source] Module criteria (Table 2): **ease of exposure** (directly on the Internet? internal use?), **loss value** (password hash module vs HTML border of an internal tool) and **regulatory controls** (OCRG p.26). Example: a level 1 module requires 3 reviewers with a security architect; level 4, one peer; high risks may require test coverage/SAST; only those with access to the sensitive repository review (OCRG p.26).
- [from source] Response to the risk found in review (Table 3): **Reduce** (fix; typical path), **Accept** (only if there is no other way; document risks and mitigations), **Avoid** (do not make the change). In code review risk is **not transferred** (insurance) (OCRG p.26).

### Preparation and discovery (OCRG p.27-30)
- [from source] The reviewer must understand the business purpose and critical impacts, the attack surface, the threat agents and motivations (OCRG p.27). Items: business rules/features and consequences of failure; **context** (the "Holy Grail"); classified sensitive data; roles and access rights (internal vs Internet); application type (web, desktop, service, mobile, hybrid); language; design (MVC, Struts/Spring: where configs are, how the view is rendered); company standards (OCRG p.27-28).
- [from source] Documentation is often outdated and lacks security; start by talking to devs and the architect, seeing the application running and the code structure; with no other means, reconnaissance through the code and document it (OCRG p.28-29). **Table 4 — design questions**: existing controls (known weaknesses in third-party controls? correctly positioned?), architecture (external connections secure? external inputs validated?), configuration files and data stores (sensitive data in config? who accesses?), authentication/access control (all resources? sessions? what works without authentication?), data flow (does user input reference business logic directly? data binding? correct flow on failure?) (OCRG p.29).
- [from source] A context **checklist** filled in by the team as a barometer of what the dev considered; areas: data validation, authentication, session, authorization, cryptography, error handling, logging, security configuration, network architecture (OCRG p.30). The Appendix A checklist is in `references/ocrg-checklist-e-apendices.md`.

### Metrics (OCRG p.40-43)
- [from source] Metrics measure size/complexity and also the performance of the review process (OCRG p.40). Size: **LOC** (executable lines; rough estimate), **function point**, **defect density** (insufficient for security: treats minor and major alike), **risk density** (defects classified by risk per LOC or function point; e.g. "4 high-risk defects per 1000 LOC") (OCRG p.40). Table 10: unmitigated, partially mitigated and fully mitigated threats (OCRG p.40).
- [from source] **Cyclomatic complexity** (McCabe): CC = number of decisions + 1; ranges 0-10 stable, 11-15 medium risk, 16-20 high risk (refactor very complex modules); **Bad Fix Probability**: probability that the fix introduces an error (CC 1-10 = 5%; 20-30 = 20%; > 50 = 40%; near 100 = 60%) (OCRG p.42). It does not prove security risk: it serves to **decide where to start** (OCRG p.42).
- [from source] **Inspection rate** (e.g. 250 LOC/h as a baseline) serves to estimate duration, not quality; **defect detection rate** and **re-inspection defect rate** (OCRG p.43).
