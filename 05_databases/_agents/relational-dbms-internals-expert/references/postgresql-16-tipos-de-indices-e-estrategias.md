# PostgreSQL 16: index types and indexing strategies

> Pages = PDF of the PG16 manual (16.15); printed = N − 38. Chapter 11 (Indexes) = PDF 467-482; index internals chapters (64-72) = PDF 2488-2566. The pages "420-445" and "2450-2515" in v1 were approximate and inaccurate printed numbers.

## 1. Available types [from source]
PostgreSQL offers **B-tree, Hash, GiST, SP-GiST, GIN, BRIN** and the **bloom** extension; `CREATE INDEX` creates a B-tree by default and the others are chosen with `USING` (PG16 p.468). (v1 said "six families" and omitted SP-GiST.) Indexes also have a cost: they must be kept in sync with the table, can prevent HOT tuples (in practice, indexes on columns that are updated; summarizing indexes, i.e. BRIN, do not prevent HOT: PG16 p.2576), and rarely used indexes should be removed (PG16 p.468). By default, index creation allows reads but **blocks writes**; `CREATE INDEX CONCURRENTLY` avoids this, at the cost of two scans and waiting for existing transactions (PG16 p.468, p.1758).

## 2. B-tree [from source]
- Handles equality and range on sortable data; the planner considers the index for `< <= = >= >`, and `BETWEEN`, `IN`, `IS NULL` and `IS NOT NULL` are equivalent to combinations of these operators (PG16 p.468). It also serves `LIKE`/`~` with a constant pattern anchored at the start (`'foo%'`, not `'%bar'`); outside the C locale a special operator class is needed (`text_pattern_ops`, `varchar_pattern_ops`, `bpchar_pattern_ops`), and the index with the default class is still needed for `<`, `>` (PG16 p.468, p.480).
- It is the **only** type that delivers data in order (ORDER BY without a sort); this is not always faster than scanning and sorting, but with `ORDER BY ... LIMIT n` it can avoid scanning the rest (PG16 p.469, p.471).
- It is the only type that can be `UNIQUE`; nulls are distinct by default, and `NULLS NOT DISTINCT` changes that (PG16 p.473). Creating a manual index on a column that is already `PRIMARY KEY`/`UNIQUE` would only duplicate it (PG16 p.473).
- Structure: a multilevel tree in which each level is a doubly linked list; a metapage; leaf and internal pages; "typically more than 99% of the pages are leaves"; splits "cascade upward" (PG16 p.2512). An entry cannot exceed approximately one third of the page (PG16 p.2508). There is bottom-up deletion (versions "churn" from UPDATEs) and deduplication with posting lists (PG16 p.2512-2513).
- Multicolumn: the index can be used with any subset of the columns, but is most efficient with constraints on the **leading** columns: equalities on the leading columns plus an inequality on the first column without equality limit the scanned portion; for `(a,b,c)` with a condition only on `b` or `c`, the whole index would have to be scanned and the planner normally prefers a sequential scan (PG16 p.471). Indexes with more than three columns rarely help, "unless the table usage is extremely stylized" (PG16 p.471). Limit of 32 columns, counting the `INCLUDE` ones (PG16 p.470).
- Directions and nulls: the index can be created with `ASC`/`DESC` and `NULLS FIRST`/`NULLS LAST`; useful in multicolumn when the ORDER BY mixes directions (PG16 p.472).

## 2b. B-tree deduplication (`deduplicate_items`): what it does, when it does not apply, cost and when it is decided [from source] (PG16 p.2513-2514)
- **B-tree deduplication, what it does** (PG16 p.2513): a "duplicate" is a leaf tuple whose key columns match those of another tuple on the same leaf; the (optional) technique periodically merges each group of duplicates into a single **posting list tuple**, in which the key value appears once, followed by a sorted array of TIDs. It reduces index size when each value repeats several times and can reduce latency and index vacuum cost. `NULL` counts as any other value for this. It happens lazily, when an item arrives that does not fit on the leaf and tuple cleanup did not free enough space.
- **Deduplication in CREATE INDEX and REINDEX** (PG16 p.2514): it is **enabled by default**. In these commands the strategy is slightly different: each group of duplicates read from the sorted input is merged into a posting list before entering the pending leaf, packing as many TIDs as possible, with no separate deduplication pass, which suits one-off bulk operations.
- **Cost of deduplication in a write workload without duplicates** (PG16 p.2514): write-heavy workloads on indexes with few or no repeated values pay a **small, fixed penalty**, unless deduplication is turned off; pure reads never have a penalty (reading a posting list is at least as efficient as the ordinary representation). The manual says turning it off does not usually help.
- **Turning deduplication off for a single index (`deduplicate_items = off`)** (PG16 p.2514): the `deduplicate_items` storage parameter turns the technique off **per index**; the manual suggests using it selectively if the overhead is a concern.
- **Deduplication in a unique (`UNIQUE`) index** (PG16 p.2514): unique indexes and constraints can sometimes use it; leaves temporarily "absorb" duplicates of **versions** generated by UPDATE, which complements bottom-up deletion, especially when a long transaction holds a snapshot and blocks garbage collection; this postpones splits until the transaction ends. A heuristic avoids useless passes on a unique index, so leaving it on has little cost.
- **When deduplication safety is decided** (PG16 p.2514): deduplication does not apply in all cases because of implementation restrictions, and safety is determined **when `CREATE INDEX` or `REINDEX` runs**.
- **Types and cases without deduplication (unsafe or restricted)** (PG16 p.2514): `text`, `varchar` and `char` with a **nondeterministic collation** (case and accent differences must be preserved); `numeric` (the display scale must be preserved); `jsonb` (the operator class uses `numeric`); `float4` and `float8` (`-0` and `0` have distinct representations, although equal); **container types** (composites, arrays, ranges), an implementation restriction that may be lifted in a future version; and **indexes with `INCLUDE`**, which never use it, whatever the operator class or collation. `[inference]` from the list: `bigint`/`int` and `text` with a deterministic collation do not fall under these exclusions; `float8`, `numeric`, `jsonb`, array and `INCLUDE` do.

## 3. Hash [from source]
Stores a 32-bit hash code of the value; supports only `=` (PG16 p.469). Details: it is **persistent and fully recoverable after a crash**; single-column indexes only; does not check uniqueness; each tuple stores only the 4-byte hash (all scans are "lossy"); can be much smaller than a B-tree for UUIDs and URLs; suited to SELECT and UPDATE workloads with equality on large tables; overflow pages under uneven distribution; does not shrink without `REINDEX`; bucket expansion happens in the foreground (PG16 p.2565). It has no FSM (PG16 p.2572).

## 4. GiST and SP-GiST [from source]
- **GiST** is a balanced-tree infrastructure in which several strategies are implemented by operator classes; the built-in classes cover geometries (`box_ops`, `circle_ops`...), ranges (`range_ops`, `multirange_ops`) and text (`tsvector_ops`, `tsquery_ops`) (PG16 p.2515-2517). It supports nearest-neighbor searches, for example `ORDER BY location <-> point '(101,456)' LIMIT 10`, depending on the class (PG16 p.469). Multicolumn: the first column is the most important, and the index is ineffective if it has few distinct values (PG16 p.471). It supports index-only scan for some classes (PG16 p.477).
- **SP-GiST** allows unbalanced structures (quadtrees, k-d trees, radix trees) (PG16 p.469).

## 5. GIN [from source]
- **Inverted** index for values with several components (arrays etc.); keeps (key, posting list) pairs; each key is stored once (PG16 p.470, p.2545). Array operators: `<@ @> = &&` (PG16 p.470). In multicolumn, effectiveness is the same regardless of the column used (PG16 p.471). It does **not** support index-only scan (PG16 p.477).
- Internally it is a B-tree over the keys, with a posting list or "posting tree" (PG16 p.2548-2549).
- **Fast update**: insertions go to an unsorted pending list and are moved in bulk to the main structure at VACUUM/autoanalyze, via `gin_clean_pending_list` or when it exceeds `gin_pending_list_limit`; trade-off: searches must scan the pending list, and the update that triggers the cleanup becomes slower; `fastupdate` is a storage parameter, on by default (PG16 p.2549, p.1758). For bulk loads, the manual advises dropping and recreating the GIN index; the build is sensitive to `maintenance_work_mem` (PG16 p.2550).
- **JSONB**: the default GIN index (`jsonb_ops`) supports `@>` and key-existence operators; the `jsonb_path_ops` class supports only `@>`, `@?` and `@@`, tends to be **smaller and more specific**, but does not find isolated keys or structures without values such as `{"a": {}}` (PG16 p.223, p.225). An expression index (e.g. `((jdoc -> 'tags'))`) can be smaller and faster than the general index, and an index on the whole column is more flexible (PG16 p.224).
- Text search: the match operator is `@@` between `tsvector` and `tsquery`, and the manual says text searches can be accelerated by indexes (PG16 p.484-485).
- **Text search, section 12.9: GIN vs GiST** (PG16 p.519-520): an index is not mandatory, but is usually worthwhile if the column is searched frequently. There are two types: GIN (`tsvector` column) and GiST (`tsvector` or `tsquery` column, with the optional `siglen` parameter in bytes). **GIN is the preferred type**: an inverted index with one entry per lexeme and a compressed list of positions; in a multi-word search it finds the first word and uses the index to discard rows without the others. GIN stores only the lexemes, **not the weights**, so a query with weights requires checking the table row (recheck). GiST is **lossy**: each document becomes a fixed-size signature (each word becomes 1 bit by hash, combined by OR), words that fall on the same bit generate false positives and the row must be checked (PostgreSQL does this automatically). GiST can be covering with `INCLUDE` (included columns are left uncompressed). The loss of precision limits the usefulness of GiST; reducing the number of distinct words with dictionaries helps. For the build: increasing `maintenance_work_mem` usually speeds up **GIN**, and the **GiST** build is **not sensitive** to that parameter. Partitioning large collections and using GIN and GiST well allows fast searches with online updates (PG16 p.519-520).
- **`siglen` (GiST signature)**: the default is 124 bytes and the maximum 2024; a larger signature gives a more precise search (fewer heap pages) and a larger index; a smaller signature, a smaller index and more false positives (PG16 p.520).
- **`ts_lexize` and thesaurus dictionary** (PG16 p.519): `ts_lexize` expects **a single token**, not text; with a phrase the thesaurus knows, it returns NULL, because it does not do parsing. To test thesaurus dictionaries the manual says to use `plainto_tsquery` or `to_tsvector`.

## 5b. Text search: ranking with `ts_rank` and `ts_rank_cd` and normalization [from source] (PG16 p.493-494)
- **Two ranking functions** (PG16 p.493): `ts_rank` orders by the **frequency** of the matching lexemes; `ts_rank_cd` computes the **cover density** (it also takes into account the proximity between lexemes) and **requires position information**: "stripped" lexemes are ignored and, if none with position remain, the result is **zero**. Both take lexical, proximity and structural information into account; the manual says relevance is vague and application-specific, that the built-in functions are only examples and that you can write your own functions or combine the result with other factors (for example, modification date).
- **Weights** (PG16 p.493-494): the optional `weights` argument weighs the categories D, C, B, A, **in that order**; without it `{0.1, 0.2, 0.4, 1.0}` apply. Weights serve to treat sections such as title or abstract as more or less important than the body.
- **Normalization** (PG16 p.494): the optional integer argument is a **bit mask** (combine with `|`, for example `2|4`) that decides how document length affects the rank: **0** (default) ignores the length; **1** divides by 1 + log of the length; **2** divides by the length; **4** divides by the mean harmonic distance between extents (**only implemented by `ts_rank_cd`**); **8** divides by the number of unique words; **16** divides by 1 + log of the number of unique words; **32** divides the rank by itself + 1. With more than one bit, the transformations are applied **in the order listed**.
- **Limit**: the functions **do not use global information**, so it is impossible to normalize fairly to 1% or 100%; option 32 (rank/(rank+1)) brings all ranks into the zero-to-one interval, but is **only cosmetic** and **does not change the order** of the results. The manual's example orders by `rank DESC` with `LIMIT 10`.

## 5c. Text search: `tsquery` operators and FOLLOWED BY (phrase search) [from source] (PG16 p.485-486)
- **What a `tsquery` combines** (PG16 p.485): already **normalized** terms (lexemes), joined by AND (`&`), OR (`|`), NOT (`!`) and FOLLOWED BY (`<->`). Matching a literal `tsvector` with `to_tsquery('fat & rat')` fails because "rats" is not normalized to "rat" (PG16 p.485). The forms `text @@ tsquery` and `text @@ text` are equivalent to applying `to_tsvector` to the text (and `plainto_tsquery` to the second text) (PG16 p.485).
- `phraseto_tsquery`, `to_tsquery`, `plainto_tsquery` and `to_tsvector`: functions that convert user text into `tsquery` (or the document into `tsvector`) **normalizing** the words; `phraseto_tsquery` builds a phrase query with `<->` between the words (PG16 p.485-486).
- **`<->` (FOLLOWED BY)** (PG16 p.485-486): matches only if the arguments have **adjacent occurrences in the given order**; in the manual's example, "fatal error" matches `fatal <-> error`, but "error is not fatal" does not.
- **`<N>`** (PG16 p.486): the general form in which N is the **difference between the positions** of the lexemes; `<1>` is equivalent to `<->` and `<2>` allows **exactly one** lexeme between the two. `phraseto_tsquery` uses this to build phrases when there are **stop words**: "the cats ate the rats" becomes the sequence cat, ate, rat with `<->` between the first two and `<2>` between the last two, because the stop word occupies a position.
- **`<0>`** (PG16 p.486): requires two patterns to match **the same word**.
- **Precedence without parentheses** (PG16 p.486): `|` binds the least, then `&`, then `<->`, and `!` binds the most; parentheses control nesting.
- **Subtle semantics of AND/OR/NOT inside FOLLOWED BY** (PG16 p.486): since the exact position matters, `!x` (which normally matches only documents **without x anywhere**) in `!x <-> y` comes to match a `y` **that does not come immediately after x**; an x elsewhere in the document does not prevent the match. Likewise, `x & y` normally only requires both anywhere, but `(x & y) <-> z` requires x and y to match **at the same position**, right before z, and therefore differs from `x <-> z & y <-> z` (which accepts two separate sequences, "x z" and "y z"). The manual notes that this specific query is useless as written (x and y do not match at the same position), but similar forms are useful, for example with prefix patterns.
- `[inference]` To search for an exact phrase in user text, `phraseto_tsquery` is the manual's indicated route for phrases with stop words; the manual does not compare the cost with GIN indexes here (see section 5).

## 6. BRIN [from source]
Stores **summaries per range of adjacent blocks** (*block range*); most effective when values have **good correlation with physical order**; for types with a linear order it stores minimum and maximum per range (PG16 p.470, p.2552). It is "lossy": it answers by bitmap scan returning all tuples of the matching ranges, and the executor rechecks; the index is small, so scanning it costs little compared with a sequential scan (PG16 p.2552). `pages_per_range` has **default 128** (PG16 p.1758); smaller value = larger index and more precise summary (PG16 p.2552). New ranges are not summarized automatically: VACUUM (manual or autovacuum) summarizes; `autosummarize` is off (PG16 p.2552). Operator classes: minmax, inclusion, bloom and minmax-multi (PG16 p.2553). BRIN, like GIN, has the same effectiveness in multicolumn (PG16 p.471).

### 6.1 BRIN: how many entries and when `pages_per_range` matters [from source + derived]
- The manual says the range size is fixed at index creation by the `pages_per_range` storage parameter and that **the number of index entries equals the relation size in pages divided by the chosen value**; the smaller the value, the **larger** the index (more entries), but the summary is more precise and more blocks can be skipped in the scan (PG16 p.2552). The default is 128 (PG16 p.1758). New ranges only get a summary with VACUUM, `autosummarize` or the summarization functions (PG16 p.2552-2553).
- `[derived]` (the default page is 8 kB, PG16 p.2573): a 1 TiB table has 2^40 / 2^13 = 2^27 = **134,217,728 pages**. With the default of 128 pages per range, the index has 2^27 / 2^7 = 2^20 = **1,048,576 entries** (each range covers 128 x 8 kB = 1 MiB of heap). With `pages_per_range = 32` there would be 2^27 / 2^5 = 2^22 = **4,194,304 entries** (4 times more, 256 kB range). With 16 times fewer pages per range, 16 times more entries.
- Size in **bytes** of the index: the manual does not state the size of each entry; any value in MB or GB for the index is `[extrapolation]` (it depends on the operator class: `minmax` stores two values per range, `bloom` a filter, `minmax-multi` several, PG16 p.2553).
- Choosing the value: a **smaller** range when queries ask for few values and the physical correlation is good (skips more), **larger** when the index needs to be tiny; the manual gives no formula for the best value, it is a trade-off to measure with `EXPLAIN (ANALYZE, BUFFERS)` (PG16 p.2552).
- **BRIN only helps if the column has natural correlation with physical position** (PG16 p.2552). `[inference]` a column such as `created_at` in an insert-only table tends to have high correlation; a random key (UUID v4, for example) does not, and BRIN would be of little use.
- Note on Hash: the hash index does not check uniqueness and serves only equality (PG16 p.469, p.2565). `[derived]` for "equality only, no uniqueness" Hash is a candidate, but the manual does not claim it is faster than the B-tree.

### 6.2 BRIN internals with pageinspect (F.25.4) [from source] (PG16 p.2878-2879)
- **BRIN functions of the pageinspect module** (PG16 p.2878-2879; only superusers can use the module, PG16 p.2873): four functions take the page image obtained with `get_raw_page`. The returned columns correspond to the fields of the source code's `BrinMemTuple` and `BrinValues` structures (PG16 p.2879).
- `brin_page_type`: returns the BRIN page type (in the example, page 0 is `meta`) or an error if the page is not BRIN (PG16 p.2878).
- `brin_metapage_info`: shows the metapage (`magic`, `version`, `pagesperrange`, `lastrevmappage`); in the example, `pagesperrange` is 4 and `lastrevmappage` is 2 (PG16 p.2878-2879).
- `brin_revmap_data`: lists the TIDs of a range map page (*range map*) (PG16 p.2879).
- `brin_page_items`: shows the data of a BRIN data page, with `itemoffset`, `blknum`, `attnum`, `allnulls`, `hasnulls`, `placeholder`, `empty` and `value` (PG16 p.2879).
- **How to read the example** (PG16 p.2879): `blknum` is the first heap block of the range; with `pagesperrange` equal to 4, `blknum` 0, 4 and 8 appear, that is, each range covers **4 pages** (0-3, 4-7, 8-11). There is one row per range and per indexed column (`attnum` 1 and 2): for `attnum` 2 the `value` summary is a minimum-maximum interval ({1 .. 88}, {89 .. 176}, {177 .. 264}), typical of the minmax operator class (which stores minimum and maximum, see section 6.1). The `attnum` 1 row shows `allnulls` true and `value` empty.
- **Inconsistency in the manual itself (record, do not fix)**: the `brin_revmap_data` example reads page 2 of the index and returns TIDs that point to index page **6**, `(6,137)` to `(6,141)` (PG16 p.2879); but the `brin_page_items` example calls `get_raw_page('brinidx', 5)`, page **5**, and shows `itemoffset` 137, 138, 139, which are precisely the offsets the map points to in `(6,N)`. `[inference]` the example should read page 6 (offsets 137+ match the TIDs of page 6); the manual text does not explain the difference. In practical answers, say that the example's page number is inconsistent and use reasoning (TID `(6,137)` = page 6, item 137) instead of copying the `5`.
- **Default range**: the default value of `pages_per_range` is 128 (PG16 p.1758); the pageinspect example uses 4, which shows that the index was created with a non-default value. The number of entries follows section 6.1 above.

## 7. Strategies [from source]
- **Expression index**: e.g. `CREATE INDEX ... ON test1 (lower(col1))`; expensive to maintain (computed on every insert and non-HOT update) and cheap to query; useful when read speed matters more than write speed (PG16 p.473-474).
- **Partial index** (*partial index*): contains only rows that satisfy a predicate; uses: avoid common values (values that occupy "more than a few percent" of the table would not use the index anyway), exclude uninteresting values, create conditional uniqueness (PG16 p.474-476). It is only used when the query's WHERE **implies** the predicate, checked at planning time: **parameterized queries do not work** (PG16 p.475-476). Do **not** replace partitioning with many partial indexes; prefer a composite index or partitioning (PG16 p.476-477).
- **Covering / `INCLUDE`**: "payload" columns that are not part of the key; enables index-only scans; only **B-tree, GiST and SP-GiST** support included columns; expressions cannot be included; `UNIQUE` applies only to the key (PG16 p.478). An index-only scan requires (1) an index type that stores or reconstructs the value and (2) a query that references only index columns; in addition, it consults the **visibility map** and only gains performance if a large share of the pages are "all-visible" (PG16 p.477-478). Beware of wide columns: a tuple that is too large makes the insertion fail (PG16 p.478).
- **Combining indexes**: bitmap scan (AND/OR) in memory; loses order (PG16 p.472).
- **Examining usage**: run ANALYZE first, use real data, compare with `enable_seqscan`/`enable_nestloop` turned off, and `EXPLAIN ANALYZE`; adjust cost parameters (PG16 p.481-482). If the plan ignores a useful index because the row estimate is wrong for filters on **several correlated columns**, the manual points to **extended statistics** (`CREATE STATISTICS` + `ANALYZE`, PG16 p.555-557; details in `otimizacao-de-consultas-e-planos-de-execucao.md` §6). When testing `EXPLAIN ANALYZE` of `UPDATE`/`DELETE`, remember it **executes** the command: use `BEGIN; ...; ROLLBACK;` (PG16 p.550-551). To see whether an index is actually used, the `pg_stat_user_indexes` view (same columns as `pg_stat_all_indexes`, filtered to user tables) provides `idx_scan`, `last_idx_scan`, `idx_tup_read` and `idx_tup_fetch` (PG16 p.841, p.870).
- Periodic reindexing may be worthwhile for B-trees in patterns where most keys of each range are deleted; `REINDEX CONCURRENTLY` avoids the exclusive lock (PG16 p.798).
- Declarative partitioning (range, list, hash) is an alternative to the giant index; the benefits "normally only pay off for very large tables" (PG16 p.132-133).

## 7b. `CREATE INDEX CONCURRENTLY` (CIC), INVALID index, partitions and `CREATE INDEX` notes [from source] (PG16 p.1758-1760)
- **Ordinary vs concurrent build**: the ordinary build blocks the table against writes and does **one** scan; readers continue, but inserts, updates and deletes wait for it to finish. With `CONCURRENTLY` PostgreSQL does **two scans** and also waits for all existing transactions that may modify or use the index: it takes more total work and much longer, in exchange for not blocking writes (useful in production), and the extra CPU and I/O load can slow other operations (PG16 p.1758).
- **Steps**: the index enters the catalog as invalid in one transaction, then the two scans occur in two transactions; before each one it waits for transactions that modified the table; after the second it waits for those holding a snapshot older than it (including transactions of concurrent builds on other tables, if the indexes involved are partial or have columns that are not simple references); only then is it marked valid. Even so it may not be usable immediately: in the worst case, only when the transactions prior to the start of the build finish (PG16 p.1759).
- **Failure leaves an INVALID index**: if a problem arises in the scan (deadlock, uniqueness violation in a unique index), the command fails but **leaves behind** an index marked INVALID (*invalid index*). It is **ignored by queries** (it may be incomplete), but **still incurs update cost**; psql shows it as INVALID. Recommended recovery: `DROP INDEX` and retry `CREATE INDEX CONCURRENTLY`; another option is `REINDEX INDEX CONCURRENTLY` (PG16 p.1759).
- **Concurrent unique index (the trap)**: the uniqueness constraint is already enforced against other transactions when the second scan starts, so violations can appear in other queries before the index is available, or even if the build ends up failing; and, if the failure occurs in the second scan, the INVALID index **continues to enforce uniqueness** afterwards (PG16 p.1759).
- Concurrent builds of expression and partial indexes are supported; errors in evaluating those expressions can cause an effect similar to that of a uniqueness violation (PG16 p.1759).
- **Concurrency between builds**: two ordinary builds on the same table can occur together, but only **one** concurrent build per table at a time; in both cases the table does not accept schema changes during the build. An ordinary `CREATE INDEX` can be inside a transaction block; with `CONCURRENTLY`, it **cannot** (PG16 p.1759).
- **Partitioned tables**: a direct concurrent build is not supported; the manual's alternative is to build concurrently on each partition and create the partitioned index last non-concurrently (then it is only a metadata operation), reducing the write-blocking time (PG16 p.1759). `CREATE INDEX` without `ONLY` recurses to all partitions: it reuses (attaches) an equivalent index that already exists or creates a new one; with `ONLY` there is no recursion and the index is born marked invalid, and `ALTER INDEX ... ATTACH PARTITION` marks it valid when all partitions have equivalent indexes; partitions created later with `PARTITION OF` get an index automatically (PG16 p.1760).
- **Command notes**: only B-tree, GiST, GIN and BRIN accept several key columns, independently of `INCLUDE`; at most 32 columns counting those of `INCLUDE` (limit changeable at compile time); **only B-tree supports a unique index** (PG16 p.1759). The `ASC`, `DESC` and `NULLS FIRST/LAST` clauses only exist for methods with ordered scan (today B-tree) (PG16 p.1760). Build speed depends on `maintenance_work_mem`; parallel build only for B-tree; each worker needs at least 32 MB of the budget and another 32 MB is left for the leader; `parallel_workers` set by `ALTER TABLE` ignores the cost model; a new expression index needs `ANALYZE` or autovacuum to have statistics (PG16 p.1760).
- **Storage parameters** (PG16 p.1758): GiST `buffering` (AUTO turns on the buffered build on reaching `effective_cache_size`), GIN `fastupdate` (default ON) and `gin_pending_list_limit` (in kB), BRIN `pages_per_range` (default 128) and `autosummarize` (default off).

## 8. [inference]
- For a huge table in which the date column grows with insertion, the "BRIN + partitioning" combination follows from the manual's two properties (BRIN effective with physical correlation, p.2552; partitions removable without VACUUM, p.132). The manual does not prescribe this combination.
- For JSONB with `@>` queries and no need for key existence, `jsonb_path_ops` is a candidate because it is smaller and more specific (PG16 p.225).

## 9. [extrapolation] and what the sources do NOT say
- **Thresholds such as "table > 10 GB"** and v1's calculation "100 GB B-tree takes 20 GB, BRIN < 10 MB (99.9%)" **do not exist** in the sources; the manual only speaks qualitatively. "BRIN = 128 pages = 1 MB" is arithmetic from the default 8 kB × 128 (PG16 p.1758, p.2573).
- "Leftmost prefix rule" is a common name, not the manual's; the manual describes the efficiency rule above and says the index **can** be used for any subset of columns (PG16 p.471).
- "Old hash without WAL support" ([DATED] in v1) is not in the pages consulted; PG16 only says hash is recoverable after a crash (PG16 p.2565).
- Indexes on PostGIS and `pg_trgm` columns belong to extensions, outside the scope of the sources.
