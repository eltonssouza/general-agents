# OCRG — A2 Authentication and session management (OCRG p.60-70)

Source: OCRG v2.0, ch. 8 (8.1-8.7). Pages = PDF (printed = N − 1). Related in the ASVS (mapping `[inference]`): V2.x, V3.x. **Caution**: some OCRG (2017) password advice contradicts ASVS 4.0.3 (2021); see "Tensions" below and `references/datado-e-tensoes.md`.

## Description (OCRG p.60)
- [from source] Authentication is the gate to protected functionality. The developer does not control how the user stores credentials, but must ensure that **there is no path to execute functions without authentication**. Forms: passwords (most common), client certificates, biometrics, OTP via SMS/device, OAuth/SSO. Stronger authentication may be required for high-risk functions (OCRG p.60). Authentication is as important inside the firewall as outside; separation of duties (OCRG p.60).

## What to review in authentication (OCRG p.60-62)
- [from source] Login **only over TLS** (if the login page is HTTP and only the POST is HTTPS, a MITM can swap the submit URL); usernames **case-insensitive**; failure messages **without leaking information** (do not reveal whether the user exists or how the password failed; a single text "incorrect username or password"); every typed character must go into the password (no truncation) (OCRG p.60, 62).
- [from source] **Do not log invalid passwords**: someone who uses e-mail as a login may have typed a valid password from another site; if the log leaks, the compromise affects other sites (OCRG p.61).
- [from source] Minimum password enforced by the application; below 10 characters is considered weak; encourage passphrases (OCRG p.61).
- [from source] Brute force: temporary lockout after N failures (e.g. 5) or a 10 s delay; caution: it can **leak** the existence of the user, so apply the same logic to invalid names (OCRG p.61).
- [from source] Password recovery is functionality triggered by unauthenticated users: protect against abuse (e-mail/SMS spam to the victim) (OCRG p.61). Store the password with the correct cryptographic technique (storage cheat sheet) (OCRG p.61).
- .NET MVC: `RequireHttpsAttribute` in `RegisterGlobalFilters` and TLS on all pages, not just login; protect session cookies (Sample 8.1) (OCRG p.61-62).
- [from source] **MFA** for high-risk functions (transfers, profile changes) — also mitigates CSRF and session hijacking (factors: something you know, have, are); **SSL client auth** (two-way TLS) in controlled environments, with secure certificate transmission (OCRG p.62).

## Forgot password, CAPTCHA and out-of-band (OCRG p.62-66)
- **Forgot password (8.4)**: "link in the e-mail/SMS" pattern, validation through an existing third-party login, notification of changes, a window (e.g. 48 h) for the user to reaffirm; the shared secret never in clear (not even in a queue), always hashed/encrypted; the organization does not need to see the password, and the password never goes back to the user; a single message for invalid user/password (OCRG p.62-63). Corresponding ASVS: V2.5.x (ASVS p.27).
- **CAPTCHA (8.5)**: access control against automation; review: no multiple guesses after an error; guessing statistics (4 images = 25% per guess; a fixed pool allows building an answer bank); consider an HMAC key for the answer; principles for text CAPTCHA (random length and size, waviness, simple charset, anti-recognition, lines crossing letters, wide lines); **accessibility (ADA)** (OCRG p.63-64). The text states that CAPTCHAs were recognized in courts and cites US/EU cases (OCRG p.63): this is legal information `[DATED]`.
- **Out-of-band (8.6)**: separate channel (SMS, call, e-mail, mail) for sensitive actions (change password/e-mail, transfers, orders); it is two-factor authentication when combined with something you know (OCRG p.64-65). What to review: risk of abuse/flooding; only authenticated users (except forgot password); **rate limit**; **do not accept a user-supplied destination** (use the registered phone/e-mail); in-person registration for high-risk sites; do not send personal/authentication data; short-lived, random PINs; channel option (Zitmo malware on SMS); separate hardware/software that generates the PIN without exposing it to the application (OCRG p.65-66). ASVS: V2.7.x and V2.2.2 (ASVS p.25, 28).

## Session management (8.7) (OCRG p.66-70)
- [from source] A session = a sequence of requests from the same user; the **ID links** credentials, traffic and access controls; implementing it well is hard (OCRG p.66). Disclosure, capture, prediction, brute force or **fixation** of the ID lead to hijacking (hijacking/sidejacking), targeted or generic (OCRG p.66).
- [from source] ID properties: non-descriptive name (replace the framework's default name with a generic one), **length ≥ 128 bits with ≥ 64 bits of entropy**, meaningless content (OCRG p.66-67); it recommends generating cryptographically strong IDs, for example with hash functions such as 256-bit SHA-2 (OCRG p.67). Compare with ASVS V3.2.2 (≥ 64 bits of entropy, ASVS p.32).
- **What to review**: what stays in the cookie; require cookies when there is authentication; cookie flags in the configuration files (.NET `requireSSL`, Java `secure`, PHP `session_set_cookie_params` with secure/httponly; Samples 8.2-8.4) (OCRG p.67). **Expiration**: .NET default of 30 minutes (example of 15); Java `session-timeout`; **PHP has no timeout mechanism** — build your own (OCRG p.67-68). **Logout**: `Session.Abandon()` destroys objects; `Session.Clear()` empties keys but does not change the ID (OCRG p.68).
- **Fidelity note**: the book's Sample 8.5 shows `cookieless="true"` (ID in the URL) in a timeout example (OCRG p.68), while the text says IDs go in cookies and not in URLs (OCRG p.69) and PHP recommends `session.use_trans_sid = 0` (OCRG p.70). Do not copy the example as good practice.
- **Three attacks**: *hijacking* (most common via XSS → HttpOnly cookies; do not let JS depend on the cookie; ID in a cookie, not in the URL (history/Referer); geolocation check and warnings of access from another location/concurrent session) (OCRG p.69); *fixation* (reject an ID that is not in the pool generated by the application, "the application is the sole authority") (OCRG p.69); *elevation* (**roll the ID** when the session is elevated — login, logout, certain authorizations — transferring the data to the new ID; clear higher-level data on downgrade) (OCRG p.69). Defenses per platform: `SessionIDManager` with GUID (Sample 8.7), `invalidate()` + `getSession(true)` (Java; Sample 8.8), `session.use_only_cookies` (PHP; Sample 8.9) (OCRG p.69-70).
- Corresponding ASVS (`[inference]`): V3.2.1 new token on authentication; V3.4.x cookie flags; V3.3.x termination; V3.7.1 (ASVS p.32-35). Terms absent from the OCRG: `SameSite`, `__Host-`, JWT, OAuth (only one mention of OAuth/SSO in OCRG p.60).
