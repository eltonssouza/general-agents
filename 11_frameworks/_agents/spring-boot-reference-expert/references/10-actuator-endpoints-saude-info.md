# 10 — Actuator: endpoints, security, health, probes, info, HTTP/JMX, loggers (ch. 13.1 to 13.5)

Pages = PDF (SBR p.N; printed = N−20). Version 2.7.18 [DATED]. Support script: `scripts/sbr_actuator.py`.

## Enabling and exposing
- **[from source]** Dependency `spring-boot-starter-actuator` (SBR p.440). An endpoint is **available** when enabled **and** exposed; by default all are enabled except `shutdown`; `management.endpoint.<id>.enabled`; `management.endpoints.enabled-by-default=false` makes enabling opt-in; a disabled endpoint is removed from the context (SBR p.440, 442-443).
- **[from source]** List of IDs (2.7.18): `auditevents`, `beans`, `caches`, `conditions`, `configprops`, `env`, `flyway`, `health`, `httptrace`, `info`, `integrationgraph`, `loggers`, `liquibase`, `metrics`, `mappings`, `quartz`, `scheduledtasks`, `sessions`, `shutdown`, `startup`, `threaddump`; web only: `heapdump`, `jolokia`, `logfile`, `prometheus` (SBR p.441-442). Each with requirements (e.g. `httptrace` needs `HttpTraceRepository`; `startup` needs `BufferingApplicationStartup`; `shutdown` only with jar) (SBR p.441).
- **[from source]** Default exposure: JMX = all (except the web-only ones); **web = only `health`**; properties `management.endpoints.{web|jmx}.exposure.{include|exclude}`; **`exclude` beats `include`**; `*` in YAML requires quotes (SBR p.443-445). `EndpointFilter` allows a custom strategy (SBR p.445).
- **[from source]** Default path `/actuator/<id>` (SBR p.440); `management.endpoints.web.base-path` and `path-mapping.<id>` change it (SBR p.470-471); discovery page at `/actuator` (`management.endpoints.web.discovery.enabled=false`) (SBR p.449). With a custom *management context path*, the page moves to the root of that context; with the management context path set to `/`, the book says it is disabled to avoid clashing with other mappings (SBR p.449). The book does NOT say this about the base-path property: in the examples with base-path `/` and `path-mapping` it does not comment on the discovery page (SBR p.470-471). **[inference]** treating management.endpoints.web.base-path=/ as equivalent to the "management context path `/`" (and therefore without a discovery page) is not written on p.449; confirm in the environment (GET `/`) before stating it.

## Security
- **[from source]** By default only `/health` is exposed on the web. If you set `exposure.include`, make sure the endpoints hold no sensitive information or are protected (firewall/Spring Security) (SBR p.445).
- **[from source]** With Spring Security and **no** custom `SecurityFilterChain`/`WebSecurityConfigurerAdapter`, all endpoints except `/health` are protected; **a custom bean makes Boot back off completely**, so you must also cover the rest of the application; `EndpointRequest.toAnyEndpoint()` (SBR p.445-448).
- **[from source]** CSRF on by default: POST/PUT/DELETE endpoints (`shutdown`, `loggers`) give **403** with the default config; turn CSRF off only for services of non-browser clients (SBR p.448). CORS is disabled until you set `management.endpoints.web.cors.allowed-origins` (SBR p.449-450).
- **[from source]** Cache of read responses without parameters: `management.endpoint.<id>.cache.time-to-live` (SBR p.448).

## Custom endpoints
- **[from source]** `@Endpoint` + `@ReadOperation`/`@WriteOperation`/`@DeleteOperation` (GET/POST/DELETE); `@JmxEndpoint`, `@WebEndpoint`, `@EndpointWebExtension`, `@ServletEndpoint`, `@ControllerEndpoint`; only simple types in parameters; compile with `-parameters`; response 200/404 (read without value)/204 (write without value)/400 (invalid parameter) (SBR p.450-454).

## Health
- **[from source]** `management.endpoint.health.show-details` and `show-components` = `never` (default) | `when-authorized` | `always`; `management.endpoint.health.roles` (SBR p.454). `always` requires security to allow `health` for authenticated and unauthenticated users (SBR p.454).
- **[from source]** `HealthIndicator`/`CompositeHealthContributor`; `StatusAggregator` orders the statuses (no known status → `UNKNOWN`); automatic indicators (keys `cassandra`, `couchbase`, `db`, `diskspace`, `elasticsearch`, `hazelcast`, `influxdb`, `jms`, `ldap`, `mail`, `mongo`, `neo4j`, `ping`, `rabbit`, `redis`, `solr`) with `management.health.<key>.enabled`; `management.health.defaults.enabled`; `livenessstate`/`readinessstate` are not enabled by default (SBR p.454-455).
- **[from source]** **Slow health indicator** (response > 10 s; indicators are generally called over HTTP and must respond before connection timeouts) produces a log warning (`management.endpoint.health.logging.slow-indicator-threshold`, default `10s`, Appendix A) (SBR p.457, 771); a custom status requires your own `StatusAggregator` or `management.endpoint.health.status.order` (book example: `fatal,down,out-of-service,unknown,up`) (SBR p.457); the **default severity order** is `[DOWN, OUT_OF_SERVICE, UP, UNKNOWN]`, in the Appendix A table (SBR p.771), not in the body (p.457 only has the custom example); HTTP: `DOWN` and `OUT_OF_SERVICE` = **503**, `UP`/`UNKNOWN` = 200; **a custom mapping disables the defaults** for DOWN/OUT_OF_SERVICE (reconfigure them) (SBR p.457-458).
- **[from source]** Groups: `management.endpoint.health.group.<name>.{include|exclude|show-details|roles|status.order|status.http-mapping.*|additional-path}`; URL `/actuator/health/<name>`; `additional-path` requires the prefix `server:` or `management:` and a single segment (SBR p.460-462). `DataSource`: `management.health.db.ignore-routing-data-sources` (SBR p.462).

## Kubernetes probes
- **[from source]** `/actuator/health/liveness` and `/actuator/health/readiness`; groups enabled automatically **only in a Kubernetes environment**; in any environment: `management.endpoint.health.probes.enabled=true` (SBR p.462-463). `management.endpoint.health.probes.add-additional-paths=true` publishes `/livez` and `/readyz` on the main port (SBR p.463).
- **[from source]** Pod manifest (SBR p.463), with `<actuator-port>` = the port where the endpoints are (the main one or `management.server.port`):
  ```yaml
  livenessProbe:
    httpGet:
      path: "/actuator/health/liveness"
      port: <actuator-port>
    failureThreshold: ...
    periodSeconds: ...
  readinessProbe:
    httpGet:
      path: "/actuator/health/readiness"
      port: <actuator-port>
    failureThreshold: ...
    periodSeconds: ...
  ```
  If the endpoints are in a separate management context, the probe may pass even with the main application broken (not accepting connections): the book suggests `management.endpoint.health.probes.add-additional-paths=true` (`/livez`, `/readyz` on the main port) (SBR p.463). For `preStop`/`terminationGracePeriodSeconds`, see `references/09` (SBR p.528).
- **[from source]** `startupProbe` is generally unnecessary (readiness already fails until startup ends), useful if startup is long (SBR p.463). **Liveness must not check external systems**; Boot does not include external checks in readiness and the decision is the developer's (SBR p.464). The text mentions **circuit breaker** only in passing here (non-essential external systems, where the application could have circuit breakers and fallbacks, and failures handled higher up the stack, perhaps with a circuit breaker in the caller); the Reference does not cover Resilience4j or circuit breaker configuration (SBR p.464). State table at startup/shutdown in SBR p.465.

## Info
- **[from source]** Contributors: `build` (needs `META-INF/build-info.properties`), `env` (`info.*` properties), `git` (`git.properties`), `java`, `os`; `management.info.<id>.enabled`; `env`/`java`/`os` are disabled by default, `build`/`git` enabled; `management.info.defaults.enabled`; `management.info.git.mode=full` (SBR p.466-468).

## HTTP, JMX, loggers
- **[from source]** `management.server.port` (own port), `management.server.ssl.*`, `management.server.address` (only with a different port), `management.server.port=-1` turns HTTP off; so does `exposure.exclude=*` (SBR p.471-474). On Cloud Foundry an extra route is needed for an own port (SBR p.471).
- **[from source]** JMX is **not enabled** by default (`spring.jmx.enabled=true`); domain `org.springframework.boot`; `spring.jmx.unique-names`, `management.endpoints.jmx.domain`; Jolokia requires `jolokia-core` and does not exist in WebFlux (SBR p.474-476).
- **[from source]** Loggers: view/change level at runtime; POST `{"configuredLevel":"DEBUG"}`; `null` resets (SBR p.476-477).

## Round 4 additions: endpoints, security, custom endpoints, health, info, paths and JMX
- **[from source]** Details of the web-only endpoints (SBR p.442): `heapdump` returns an HPROF file on a HotSpot JVM and a PHD file on OpenJ9; `logfile` only exists if `logging.file.name` or `logging.file.path` is set and accepts the HTTP `Range` header to return part of the file; `jolokia` requires `jolokia-core`; `prometheus` requires `micrometer-registry-prometheus`. The same chapter points to separate API documentation with the request/response formats of each endpoint (SBR p.441-442). Exposure examples from the book: `management.endpoints.jmx.exposure.include=health,info` (JMX only with those two) and, on the web, `include=*` with `exclude=env,beans` (SBR p.444). If the app is publicly exposed, the book strongly recommends protecting the endpoints (SBR p.445).
- **[from source]** Endpoint security (SBR p.445-448): with Spring Security on the classpath and no other `WebSecurityConfigurerAdapter`/`SecurityFilterChain`, all endpoints except `/health` are protected by auto-configuration; when you define your own, auto-configuration backs off and the Actuator rules become yours. The book's example builds a `SecurityFilterChain` with `EndpointRequest.toAnyEndpoint()`, requires the role `ENDPOINT_ADMIN` (`hasRole`) and `httpBasic`; for those behind a firewall who want access without authentication, `management.endpoints.web.exposure.include=*` plus a `SecurityFilterChain` with `permitAll()` (SBR p.445-447). Since Boot's security backs off completely in the presence of any `SecurityFilterChain`, a second bean with the rules for the rest of the application is needed (SBR p.448).
- **[from source]** Actuator CORS (SBR p.449-450): only applies with MVC or WebFlux and only turns on when `management.endpoints.web.cors.allowed-origins` is set; example `allowed-origins=https://example.com` with `management.endpoints.web.cors.allowed-methods=GET,POST`; the full list of options is in `CorsEndpointProperties`. The discovery page (`/actuator`) moves to the root of the management context when there is its own path (e.g. `/management`) and is turned off if the path is `/` (SBR p.449-450).
- **[from source]** Custom endpoints, input (SBR p.450-452): `@Endpoint` is exposed over JMX and, in a web app, over HTTP by Jersey, MVC or WebFlux (if Jersey and MVC both exist, MVC wins); `@JmxEndpoint`/`@WebEndpoint` restrict to the technology and `@EndpointWebExtension`/`@EndpointJmxExtension` extend an existing endpoint. Parameters come from query parameters and the JSON body (each root property of the body becomes a parameter; e.g. `name` and `counter`); in JMX they map to the MBean operation parameters. Parameters are **required** by default; to make them optional use the Nullable annotation (`javax.annotation` or `org.springframework.lang`). Since the endpoint is technology-agnostic, only simple types work in the signature (a single parameter of type `CustomData` with `name`/`counter` is not supported). Compile with `-parameters` (Java) or `-java-parameters` (Kotlin); it happens on its own with the Boot Gradle plugin or with Maven + `spring-boot-starter-parent` (SBR p.450-451). Type conversion uses `ApplicationConversionService` and `Converter`/`GenericConverter` beans qualified with `@EndpointConverter` (SBR p.452).
- **[from source]** Custom endpoints, web (SBR p.452-454): the path comes from the endpoint ID and the base path (`/actuator`); parameters with `@Selector` become path variables, and `@Selector(Match=ALL_REMAINING)` on the last parameter captures the rest of the path (type compatible with `String[]`). HTTP method: `@ReadOperation` GET, `@WriteOperation` POST, `@DeleteOperation` DELETE. The `consumes` of a `@WriteOperation` with a body is `application/vnd.spring-boot.actuator.v2+json, application/json`; `produces` is automatic: empty for `void`, `application/octet-stream` for `Resource`, and `application/vnd.spring-boot.actuator.v2+json, application/json` otherwise (can be fixed in the `produces` attribute). Status: read with value 200 and without value 404; write/delete with value 200 and without value 204; a missing or unconvertible parameter gives 400 without calling the method. Operations that return `Resource` support `Range` requests in MVC and WebFlux, **not** in Jersey. An operation can receive `java.security.Principal` (with `@Nullable` to handle anonymous users) or `SecurityContext` (`isUserInRole`). `@ServletEndpoint` (class implementing `Supplier<EndpointServlet>`) and `@ControllerEndpoint`/`@RestControllerEndpoint` integrate more deeply with the web container/framework at the cost of portability; prefer `@Endpoint`/`@WebEndpoint` (SBR p.452-454).
- **[from source]** Health, mechanics (SBR p.454-458): health is assembled from the `HealthContributorRegistry` (by default all `HealthContributor` beans in the context), which also lets you register and remove indicators at runtime; the contributors form a tree (a `CompositeHealthContributor` groups others); the `StatusAggregator` orders the status of each indicator and uses the first in the list (SBR p.454). Roles: if the endpoint has no roles configured, every authenticated user is considered authorized under `when-authorized` (SBR p.454). A custom `HealthIndicator` implements `health()` and returns `Health` (`Health.down().withDetail(...)` or `Health.up()`); the identifier is the bean name without the `HealthIndicator` suffix (a `MyHealthIndicator` shows up as `my`) (SBR p.455-457). New status (e.g. `FATAL`): configure the severity and HTTP codes, for example `management.endpoint.health.status.order=fatal,down,out-of-service,unknown,up` and `management.endpoint.health.status.http-mapping.fatal=503`; for more control, an `HttpCodeStatusMapper` bean (SBR p.457-458).
- **[from source]** Reactive health (SBR p.458-460): `ReactiveHealthContributor` is the non-blocking contract, with `ReactiveHealthContributorRegistry`; plain `HealthContributor` beans that do not use a reactive API run on the elastic scheduler; in a reactive app use the reactive registry and, to register a plain contributor, wrap it with `ReactiveHealthContributor#adapt`; auto-configured reactive indicators: `cassandra`, `couchbase`, `elasticsearch`, `mongo`, `neo4j`, `redis`; when they exist, they replace the plain ones, and any `HealthIndicator` not handled explicitly is wrapped automatically (SBR p.458-460).
- **[from source]** Health groups, details (SBR p.460-462): `management.endpoint.health.group.custom.include=db` creates `/actuator/health/custom`; `exclude=db` includes everything but the database ones. By default the group inherits the `StatusAggregator` and `HttpCodeStatusMapper` of the global health, but can have its own (`status.order`, `status.http-mapping.<status>`) and override `show-details` and `roles` (e.g. `show-details=when-authorized`, `roles=admin`) (SBR p.460-461). Including/excluding part of a composite uses the qualified name, e.g. include `"test/primary"` and exclude `"test/primary/b"` (SBR p.462). `additional-path` (e.g. `management.endpoint.health.group.live.additional-path="server:/healthz"`) publishes the group on the main port; the prefix is mandatory (`server:` or `management:`) and the path has a single segment; it was designed for Kubernetes with a separate management port (SBR p.462). The `DataSource` indicator also covers routing data sources (each target named by the routing key); `management.health.db.ignore-routing-data-sources=true` omits them (SBR p.462).
- **[from source]** Probes, details (SBR p.462-465): `ApplicationAvailability` feeds `LivenessStateHealthIndicator` and `ReadinessStateHealthIndicator` (also in the global health `/actuator/health`); the groups are only turned on automatically on Kubernetes. To check external systems in readiness, include indicators in the group, e.g. `management.endpoint.health.group.readiness.include=readinessState,customCheck`; by default Boot does not add other indicators to these groups (SBR p.462-464). If all instances are unready, a `ClusterIP` or `NodePort` Service does not accept connections (there is no HTTP 503 response, since there is no connection); `LoadBalancer` may or may not accept, and with an explicit ingress it depends on the implementation (503 is likely); the autoscaler may react differently to removal from the balancer (SBR p.464-465). Lifecycle table (SBR p.465): at startup, `Starting` = liveness `BROKEN`, readiness `REFUSING_TRAFFIC`, HTTP not started; `Started` = `CORRECT` and `REFUSING_TRAFFIC` (context refreshed, runners executing, server refuses requests); `Ready` = `CORRECT` and `ACCEPTING_TRAFFIC`. At shutdown: `Running` = `CORRECT`/`ACCEPTING_TRAFFIC`; during graceful shutdown readiness becomes `REFUSING_TRAFFIC` and new requests are rejected while in-flight ones finish; when done, the server is off and the states do not apply.
- **[from source]** Info, details (SBR p.466-468): contributors `build`, `env`, `git`, `java`, `os`; `env` exposes properties whose name starts with `info.` (e.g. `info.app.encoding`, `info.app.java.source`) and can use values expanded at build time (`info.app.encoding=@project.build.sourceEncoding@`, `info.app.java.source=@java.version@`) (SBR p.466-467). With a `GitProperties` bean (auto-configured if there is a `git.properties` at the classpath root), the endpoint exposes by default `git.branch`, `git.commit.id` and `git.commit.time`, if present; to not expose one, exclude it from `git.properties`; `management.info.git.mode=full` shows the complete content and `management.info.git.enabled=false` turns git off in the endpoint (SBR p.467-468). With a `BuildProperties` (file `META-INF/build-info.properties` on the classpath, generated by the plugins) the endpoint publishes build data (SBR p.468). A custom `InfoContributor` uses `withDetail` (SBR p.468-469).
- **[from source]** HTTP, paths (SBR p.469-471): the Actuator works natively with MVC, WebFlux and Jersey (MVC wins if they coexist) and Jackson is a mandatory dependency for the documented JSON (SBR p.470). `management.endpoints.web.base-path` (e.g. `/manage`) is relative to `server.servlet.context-path` (servlet) or `spring.webflux.base-path` (reactive); if `management.server.port` is set, it is relative to `management.server.base-path`. Remapping an endpoint: `management.endpoints.web.base-path=/` with `management.endpoints.web.path-mapping.health=healthcheck` maps `/actuator/health` to `/healthcheck` (SBR p.470).
- **[from source]** SSL and management address (SBR p.471-474): with an own port you can have own SSL via `management.server.ssl.*`; the book shows the main app on HTTPS (`server.port=8443`, `server.ssl.enabled=true`) with `management.server.port=8080` and `management.server.ssl.enabled=false`, or both with SSL and different key stores (`main.jks` and `management.jks`) (SBR p.471-472). `management.server.address` (e.g. `127.0.0.1`, to refuse remote management connections) only applies if the port differs from the main one; `management.server.port=-1` or `management.endpoints.web.exposure.exclude=*` turn off the Actuator HTTP (SBR p.473-474).
- **[from source]** JMX, details (SBR p.474-476): Boot exposes the `MBeanServer` as the `mbeanServer` bean and publishes in it beans with `@ManagedResource`/`@ManagedAttribute`/`@ManagedOperation`; it uses the platform `MBeanServer` if one exists, otherwise the VM's and, as a last resort, creates a new one (see `JmxAutoConfiguration`). Endpoints live in the domain `org.springframework.boot` (e.g. `org.springframework.boot:type=Endpoint,name=Health`); for full control register your own `EndpointObjectNameFactory`. With more than one `ApplicationContext`, use `spring.jmx.unique-names=true` to avoid collisions and `management.endpoints.jmx.domain` (e.g. `com.example.myapp`) to change the domain; `management.endpoints.jmx.exposure.exclude=*` turns off JMX exposure (SBR p.474-475). Jolokia: `org.jolokia:jolokia-core`, then `jolokia` (or `*`) in `management.endpoints.web.exposure.include`, accessible at `/actuator/jolokia`; it is servlet-specific (MVC and Jersey) and does **not** exist in WebFlux; Jolokia parameters use the prefix `management.endpoint.jolokia.config.` (e.g. `debug=true`) (SBR p.475-476).
- **[from source]** Loggers (SBR p.476-477): for each logger the endpoint shows the explicitly configured level and the effective one; the possible values are TRACE, DEBUG, INFO, WARN, ERROR, FATAL, OFF and `null` (no explicit configuration). To change: POST of a partial entity `{"configuredLevel": "DEBUG"}`; sending `null` in `configuredLevel` restores the default configuration (SBR p.477).
- **[from source]** **Autoscaling** (passing mention, round 5): if the application uses Kubernetes autoscaling, it may react differently to instances removed from the balancer, depending on the **autoscaler** configuration (SBR p.464-465). The Reference does **not** cover HPA, Helm or autoscaling values; only that sentence.
