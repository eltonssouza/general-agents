## Lambda applications / SAM / CloudFormation
- [from source] (LAMBDA p.839) Lambda application = combination of functions, event sources and other resources; CloudFormation groups them into a single package; integrates with CodePipeline, CodeBuild, SAM CLI
- [from source] (LAMBDA p.839) Serverless Application Repository: ready-made apps and examples, deployable in a few clicks; you can submit your own
- [from source] (LAMBDA p.839) CloudFormation: template defines resources, manages them as a stack; automatic rollback to the previous configuration if part of the update fails; parameters allow multiple environments from the same template; SAM extends CloudFormation with simplified syntax; AWS CLI has high-level commands (upload packages, update templates); SAM CLI validates templates, tests locally and integrates CI/CD; Git repository via CodeCommit or CodeStar connection to GitHub
- [from source] (LAMBDA p.840) Console Applications lists CloudFormation stacks with Lambda functions (launched via CloudFormation console, SAR, CLI or SAM CLI); overview shows template and resources
- [from source] (LAMBDA p.840) The application's Monitoring tab shows an aggregated CloudWatch dashboard; basic dashboard by default; custom dashboards via the AWS::CloudWatch::Dashboard resource in the template (they replace the default; switch via dropdown)
- [p.841-842] Dashboard template example: metric widget with namespace AWS/Lambda, metric Invocations, dimension FunctionName, stat Sum, expression SUM(METRICS()); definition of any widget of the default dashboard: Monitoring > View in metrics > Source
- [from source] (LAMBDA p.843) Tutorial of an app with continuous delivery in the console: creates Application (Node.js function + build spec + SAM template), Pipeline (CodePipeline), Repository (CodeCommit), Trigger (EventBridge rule watching the main branch), Build project (CodeBuild), Deployment configuration (CloudFormation), S3 artifacts bucket and Roles (pipeline per stage; function with execution role). Application template in the repository; pipeline in a separate template outside version control, with its own stack; one pipeline maps a single branch to one application stack; more pipelines = more environments; you can add test/staging/manual approval stages
- [p.844-845] Steps: Applications > Create application > Author from scratch; name my-app, runtime Node.js 14.x, CodeCommit, repo my-app-repo, Permissions "Create roles and permissions boundary"; Infrastructure stack (repo, build, etc.) then deploys the application stack (function + execution role); invoke helloFromLambdaFunction with Test and event {}
- [p.846-847] Add a resource: clone the repo (git clone), edit template.yml with AWS::Serverless::SimpleTable (PrimaryKey id String, ProvisionedThroughput 1/1), env var DDB_TABLE: !Ref ddbTable and policy DynamoDBCrudPolicy; commit and push trigger the pipeline; follow in the Deployments tab
- [from source] (LAMBDA p.848) Permissions boundary: the sample application applies a boundary to the function's execution role to prevent anyone with write access to the repository from giving the template out-of-scope access; when adding permissions (e.g. DynamoDB) the boundary must be extended (the console detects resources outside the boundary and provides an updated policy; Resources > Edit permissions boundary)
- [p.848-849] Sample code uses DynamoDB and context.logStreamName as the function instance id; handler changed to src/handlers/index.handler; each log stream of the log group corresponds to one instance; a new instance is also created when code or configuration changes
- [p.849-850] Next steps: SAM transform simplifies syntax and automates upload; SAM CLI tests locally in a Docker container that emulates the Lambda environment; AWS Cloud9; IDE toolkits (JetBrains, Eclipse, VS Code, Visual Studio)
- [from source] (LAMBDA p.850) Error types: build (compilation, test, packaging), deployment (CloudFormation fails to update the stack: permissions, account quotas, service, template) and invocation; diagnosis: Applications > app > Deployments > Deployment pipeline > failing action > Details; in ExecuteChangeSet look for the UPDATE_FAILED event (it is below several events because of the rollback); if no change set was created, the error appears in Change sets
- [p.850-851] Common cause: missing permission in some role. The deployment role (CloudFormationRole) matches the user's permissions; the function's execution role is also subject to the application's permissions boundary. To connect a function to a VPC: (1) user permissions on the deployment role; (2) execution role permissions in the boundary; (3) permissions on the execution role in the template; (4) commit/push. Then "Release change" reruns build and deploy
- [from source] (LAMBDA p.851) Cleanup: delete the application stack (my-app), the S3 artifacts bucket, and the infrastructure stack (serverlessrepo-my-app-toolchain); the function's log group is NOT associated with the stacks and must be deleted separately in CloudWatch Logs


## Rolling deployments (CodeDeploy + SAM)
- [from source] (LAMBDA p.852) Rolling deployment: new version deployed automatically with gradually increasing traffic; amount and rate are configurable; implemented with CodeDeploy (allows monitoring and starting rollback) and SAM (YAML template). SAM: configures the function and creates an alias (alias routing is the underlying capability), creates a CodeDeploy application and deployment group (manages deployment and rollback), detects the new version and triggers CodeDeploy
- [p.852-853] SAM example: Transform AWS::Serverless-2016-10-31; AutoPublishAlias: live (creates the live alias and publishes a new version when new code is detected, updating the alias); DeploymentPreference Type: Linear10PercentEvery2Minutes (+10% traffic every 2 minutes); list of predefined configurations in the CodeDeploy documentation

## Orchestration with Step Functions
- [from source] (LAMBDA p.862) Step Functions: orchestration service that connects Lambda functions into serverless workflows called state machines; uses: application workflows (e.g. checkout), long workflows (IT automation, human approval) and short high-volume workflows (streaming ingestion/processing)
- [from source] (LAMBDA p.862) State machines are defined in Amazon States Language (ASL, JSON); they contain states; each state's logic defines the next one, the data and the termination; the state name is any string unique within the state machine's scope
- [from source] (LAMBDA p.862) A state machine with Lambda needs: (1) an IAM role for Lambda/Step Functions with policies (e.g. AWSLambdaRole); (2) one or more Lambda functions; (3) a state machine in ASL
- [p.862-863] Patterns: catch and retry (Catch fields = array of objects with a fallback state; Retry = array of retry policies for runtime errors); branching (Choice = array of rules that decide the next transition based on the function's output); chaining (Task states in series, output of one is input of the next); parallelism (Parallel state: branches in parallel with the same input); dynamic parallelism (Map state: for-each loop, same steps for each element of an input array)
- [from source] (LAMBDA p.863) Besides the application patterns, Step Functions supports service integration patterns, including pausing a workflow for human approval or calling a legacy/third-party system
- [p.863-865] WhichCoat example: Choice with StringEquals on $.Weather (FREEZING/COOL/WARM) leads to Task states that invoke Lambda functions (wear_heavy_coat etc.) via Resource ARN, with End:true; input {"Weather":"FREEZING"}
- [p.865-866] Lambda console: lists the region's state machines with at least one step that invokes Lambda; graph with functions in blue; a function referenced dynamically via JsonPath shows no details (appears as "Dynamic reference" and is gray); Edit opens Edit definition in the Step Functions console; Execute opens New execution
- [from source] (LAMBDA p.867) All work in a state machine is done by Tasks (activity, Lambda function or parameters for APIs of supported AWS service integrations); a Task state invokes Lambda with the state machine input or any JSON
- [p.867-868] Optimized integration: Resource arn:aws:states:::lambda:invoke with Parameters FunctionName (may be an ARN with version :1) and Payload; TimeoutSeconds on the Task ([DATED] example 25); permissions: managed policy AWSLambdaRole or inline policy restricted to the function; FunctionName/Payload map to the Invoke API parameters, and also accept InvocationType and ClientContext (e.g. "InvocationType": "Event" for async without waiting for the result); "Payload.$": "$" uses the execution input; invoke.waitForTaskToken to wait for a callback
- [from source] (LAMBDA p.868) Errors: retry or branch by error type; example retries Lambda 5XX exceptions (ServiceException), throttles (TooManyRequestsException), runtime errors (Lambda.Unknown) and the function-defined error function.MaxDepthError; Catch of function.DoublesRolledError leading to the CaughtException state
- [from source] (LAMBDA p.869) Retry example: ErrorEquals [function.MaxDepthError, Lambda.TooManyRequestsException, Lambda.ServiceException, Lambda.Unknown] with [DATED] MaxAttempts 5; Catch of function.DoublesRolledError -> CaughtException. To catch/retry function errors, create a custom error type whose name must match the errorType of the formatted error response that Lambda returns when an error is thrown
- [p.869-870] SAM: resource AWS::Serverless::StateMachine (inline definition or in a separate file; DefinitionSubstitutions with FunctionArn: !GetAtt function.Arn); example with Retry (IntervalSeconds 1, MaxAttempts 5), a specific Catch and Catch States.ALL -> UncaughtException, Pass states for results, Events Schedule rate(1 minute), Type STANDARD, Policies AWSLambdaRole
- [p.869-870] [NOTE] The text's example lists function.MaxDepthError twice in ErrorEquals (apparent duplicate) and uses InvocationType: Event together with Retry/Catch of function errors (with asynchronous invocation the Task does not receive the function's errors; apparent inconsistency in the example)
