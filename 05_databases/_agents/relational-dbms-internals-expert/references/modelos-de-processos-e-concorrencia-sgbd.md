# Process models, parallelism and concurrency primitives

> Pages = PDF. ARCH: printed = N + 140.

## 1. Vocabulary of the paper [from source]
The paper defines: **OS process** (unit of execution with a private address space), **OS thread**, **lightweight thread package** (scheduled in user space, with faster context switching, but a blocking synchronous I/O stalls all the threads of the process), **DBMS client** and **DBMS worker** (1:1 relation with the client: the worker handles all the SQL requests of a client) (ARCH p.9-11). When the text says "threads" without qualification, it can be any of these cases (ARCH p.11).

## 2. The three basic models (uniprocessor) [from source]
The paper starts from two simplifying assumptions (the OS has good threads; hardware with one CPU) and lists three options: **process per worker**, **thread per worker** and **process pool** (ARCH p.12).

| Model | What the book says | PDF |
|---|---|---|
| Process per worker | Easy to implement; the OS schedules and protects against common bugs such as memory overruns; debuggers and memory checkers work well. Trade-off: the lock table and buffer pool must live in OS shared memory, and this use **reduces part of the isolation advantage**. Scales worse for very many connections because a process has more state than a thread. Used by DB2, PostgreSQL and Oracle. | p.13-14 |
| Thread per worker | One multithreaded process; a dispatcher thread receives connections and each connection gets a thread. Challenges: the OS does not protect threads from each other (overruns, dangling pointers), debugging with race conditions, portability. Scales well for many connections; used by DB2, SQL Server, MySQL, Informix and Sybase. | p.14-15 |
| Process pool | Variant of process per worker: a central process holds the connections and hands each request to a process of the pool (limited and often fixed size; if all are busy, the request waits). Much more economical in memory. | p.15-16 |

### Real practices cited [from source] (2007) [DATED]
- **PostgreSQL** uses process per worker **exclusively**, on all supported OSs (ARCH p.20).
- **Oracle**: default process per worker; process pool optional and recommended for many connected users (ARCH p.20, p.22).
- **IBM DB2**: supports four models; default thread per worker where there is good thread support (ARCH p.20-21).
- **MySQL**: OS thread per worker (ARCH p.21).
- **SQL Server**: the default is **workers multiplexed over a thread pool** (the book says more than 99% of installations run this way); the "Fibers" option (DBMS threads over OS threads) is little used (ARCH p.21-22).
- **Sybase** and **Informix**: DBMS threads over OS processes (ARCH p.21).

## 3. Structures shared among workers [from source]
In any model, the workers share: the **buffer pool**, the **log tail** (in-memory queue of the log, flushed periodically in FIFO order), client communication buffers and the **lock table**. In thread per worker these structures are heap memory; in the other models they live in OS shared memory (ARCH p.16-19). A transaction is only reported as committed after its commit record is flushed to the log; the server holds the resources (locks) until then; flushes can be postponed to group commits ("group commit") (ARCH p.18).

## 4. Admission control [from source]
Above a certain load, throughput **drops** (thrashing), typically from memory pressure in the buffer pool (sorts and hash joins consume a lot of memory) or from lock contention with many deadlocks and restarts (ARCH p.22-23). The paper describes two layers: a connection limit in the dispatcher and, inside the query processor, an execution controller that uses optimizer estimates (disks and I/Os, CPU and, above all, memory footprint) to postpone the query, reduce its resources or release it (ARCH p.23-24).

## 5. Parallel architectures [from source]
Chapter 3 of the paper (ARCH p.25-35) summarizes the standard terminology (Stonebraker) and discusses, for each architecture, the process model and the memory coordination. Everything below is paraphrase; the page numbers are PDF pages.

### 5.1 Shared-memory (ARCH p.25-27)
- All processors access the same RAM and the same disk with similar performance; it is common server hardware (2 to 8 processors), and machines with dozens of processors cost a high premium but are widely used in high-end OLTP (ARCH p.25). The hardware cost is usually small compared with the cost of qualified people to administer the system (footnote, ARCH p.26).
- Multicore processors share caches and bus and, to the programmer, look like shared-memory; the three process models of ch. 2 run well on this hardware, and the OS distributes workers (processes or threads) transparently among the processors (ARCH p.26-27). The real challenge is parallelizing **one** query across CPUs (ARCH p.27).

### 5.2 Shared-nothing (ARCH p.27-29)
- Cluster of independent machines connected by a network; none directly accesses the memory or disk of another; all coordination is left to the DBMS (ARCH p.27).
- Common technique: each node runs the standard process model (accepts SQL, compiles, accesses data), but stores only **a part** of the data; the request is sent to the other nodes and all execute in parallel over their data. Tables are sliced by **horizontal partitioning**: by attribute hash, by range, round-robin or hybrid (hash + range) (ARCH p.28).
- Each machine takes care of access, locks and log of its local disks. The optimizer decides how to repartition tables and intermediate results among the machines; the executors exchange data requests and tuples, without transferring thread state. Coordination is minimal, but good partitioning is indispensable and weighs on the DBA (table layout) and on the optimizer (ARCH p.28).
- There is explicit coordination for transaction termination, balancing and maintenance: control messages for distributed deadlock detection and *two-phase commit*, which can become a bottleneck (ARCH p.28).
- **Partial failure** (ARCH p.28-29): in shared-memory the failure of a processor usually brings down the entire machine; in shared-nothing the fall of a node does not necessarily bring down the others, but it affects the DBMS behavior, because that node stores part of the data. The paper lists **three approaches**:
  1. **bring down all the nodes** if one fails (emulates what happens in shared-memory);
  2. **"Data Skip"** (name given by Informix): queries run on the nodes that are up and "skip" the data of the failed node. It works when availability matters more than completeness, but *best effort* results have no well-defined semantics; since the DBMS is usually the "system of record" of a layered system, the availability x consistency trade-off is usually made in an upper layer (ARCH p.29);
  3. **redundancy**, from full database failover (twice the machines and licenses) to fine-grained schemes such as **chained declustering**, in which copies of the tuples are spread over several nodes. Advantages over naive schemes: (a) it requires fewer machines to guarantee availability; (b) when a node fails, the load is distributed reasonably uniformly: the **remaining n-1 nodes each do n/(n-1) of the original work**, and this linear degradation continues as more nodes fall (ARCH p.29). Most commercial systems are in a middle ground between full failover and chained declustering (ARCH p.29). Section 7.3 of the paper returns to the subject: the chained declustering of the Gamma project coincided in time with the invention of RAID and works better for a DBMS (ARCH p.106).
- `[derived]` with n = 5 nodes and one failure: 5/4 = 1.25, that is, each survivor now does 125% of the original work (+25%); with n = 10: 10/9 ≈ 1.11. `[inference]` for k simultaneous failures the same formula would give n/(n-k) (for example 5/3 ≈ 1.67 with two failures in five nodes); the text says only that the linear degradation continues. The formula n/(n-1) is from the paper; the "200%" of simple mirroring between pairs is the package's calculation, not the book's.
- The book places shared-nothing at the top of the scale, generally for decision support and data warehouses, and observes that a shared-nothing cluster is usually made of nodes that are, each, shared-memory multiprocessors (ARCH p.29).

### 5.3 Shared-disk (ARCH p.30-31)
- All processors access the disks with similar performance, but **not** each other's RAM. Examples: Oracle RAC and DB2 for zSeries SYSPLEX; it became more common with SANs, which make it easy to mount logical disks on several hosts (ARCH p.30).
- Administration advantage: the DBA **does not need to partition tables among machines** to get parallelism; even so, very large databases still usually require partitioning, which reduces the difference (ARCH p.30). Another advantage: the failure of a processing node does not prevent the others from accessing the entire database, unlike shared-memory (failure as a unit) and shared-nothing (loses access to part of the data) (ARCH p.30).
- **Single points of failure that remain**: if the data is damaged by a hardware or software failure before reaching the storage subsystem, **all** nodes see only that corrupted page; with RAID or similar redundancy, the corrupted page is stored redundantly, but remains corrupted in all copies (ARCH p.30-31).
- Since there is no partitioning, the same data can be in RAM and be changed on several machines. There is no natural memory location to coordinate this: each machine has its own memory for locks and buffer pool pages, so a **distributed lock manager** and a **cache coherence protocol** for the distributed buffer pools are needed, complex components that can be a bottleneck under contention; the IBM zSeries SYSPLEX implements the lock manager in a hardware subsystem (ARCH p.31).

### 5.4 NUMA and DBMS threads (ARCH p.31-33)
- **NUMA**: shared-memory programming model over a cluster of systems with independent memories (fast local access, slower remote access); it is a middle ground between shared-nothing and shared-memory. NUMA clusters had no commercial success, but the pattern was adopted in large shared-memory multiprocessors, divided into "pods" of memory and CPUs (ARCH p.31-32). **Definition of pod** (ARCH p.32): the memory of a large shared-memory multiprocessor is divided into sections, each associated with a small subset of the processors; each pair (memory subset + CPUs) is usually called a pod; each processor accesses the local memory of its pod a little faster than that of another pod. This use of the NUMA pattern allowed shared-memory systems to scale to very large numbers of processors; hence **NUMA shared-memory multiprocessors are very common today**, whereas NUMA clusters never had significant market share (ARCH p.32). NUMA clusters have practically disappeared, but the programming model and the optimization techniques remain important because many large shared-memory systems have very non-uniform memory access (ARCH p.32) `[DATED]` (2007).
- The DBMS can ignore the non-uniformity if it is small; when the ratio between near and distant access exceeds the range of 1.5:1 to 2:1, the following applies: (a) allocate memory local to the processor and (b) reschedule, if possible, the worker on the same processor on which it ran before (ARCH p.32).
- **DBMS threads and multiprocessors**: the lightweight thread package inside **one** OS process uses only one processor at a time (the initial architecture of Sybase SQL Server suffered from this and moved to several OS processes in the 90s); with several processes it is necessary to migrate threads among them (Informix did this well starting with version 6.0). Rule of thumb: **one process per physical processor** (ARCH p.32-33).

### 5.5 Practice and discussion (ARCH p.33-35) `[DATED]`
- All the large ones support shared-memory (DB2, Oracle, SQL Server). Shared-nothing: DB2, Informix, Tandem, NCR Teradata, among others; Greenplum offers a version of PostgreSQL with shared-nothing parallelism. Shared-disk: Oracle RAC, RDB and DB2 for zSeries. None of the leaders supported shared-nothing and shared-disk in the same code base, and SQL Server implemented neither (ARCH p.33-34).
- At datacenter scale, administration is only viable if automated; with daily disk failures and weekly server failures, **administrative backup tends to be replaced by redundant online copies** on other servers and disks (sometimes in another datacenter); automated offline backup remains useful for application, administration or user error. Redundancy can be obtained (a) at the storage level (SAN), (b) by replication in the storage engine (Section 7.4, see `componentes-compartilhados-catalogo-memoria-replicacao.md`), (c) by redundant execution of queries and (d) by redundant requests generated by the client (ARCH p.34-35). Middle-tier caches are also common (for example, in-memory databases such as TimesTen) (ARCH p.35).

## 6. Locks vs. latches [from source]
The lock manager keeps a **lock table** (hash by lock name; each lock has a mode and a wait queue) and a **transaction table**; a *deadlock detector* periodically examines the lock table looking for wait cycles and aborts a transaction (ARCH p.83). Latches are lighter and protect internal structures (for example, one latch per buffer pool frame) (ARCH p.83). Differences listed (ARCH p.83-84):
- locks live in the lock table and are found by hash; latches live near the resource and are accessed by direct address;
- locks follow strict 2PL; latches can be acquired and released during the transaction;
- locks can deadlock (resolved by restarting the transaction); **latch deadlock is a bug** of the DBMS;
- a latch is an atomic hardware instruction (or, rarely, kernel mutual exclusion); a latch call takes a few dozen cycles, a lock, hundreds;
- the locks of a transaction are released automatically on exception; latches are not tracked and need manual cleanup.
Latch API: `latch(object, mode)`, `unlatch(object)` and `conditional latch(object, mode)`; modes normally only shared and exclusive (ARCH p.84).

## 7. PostgreSQL [from source]
PG16 confirms "process per user": each client talks to exactly one backend created by the `postmaster`, and the backends coordinate through semaphores and shared memory (PG16 p.2291-2292). `max_connections` has a default typically of 100 (PG16 p.646). PG16 recommends connection pooling as a good performance practice, especially with Serializable isolation (PG16 p.531).

## 7b. PostgreSQL: background processes (background worker processes, chapter 48) [from source] (PG16 p.1529-1531)
- **What they are** (PG16 p.1529): PostgreSQL can be extended to run user code in **separate processes**, which are started, stopped and monitored by `postgres`, so that their life is tied to the server state. They attach to **shared memory**, can **connect to databases internally**, run several transactions in series like an ordinary server process and, linking to libpq, connect to the server as a client. **Manual warning**: there are considerable robustness and security risks, because, written in C, they have unrestricted access to the data; only carefully audited modules should be allowed to run workers.
- **Registration** (PG16 p.1529): at startup, by listing the module in `shared_preload_libraries` and calling `RegisterBackgroundWorker(BackgroundWorker *worker)` from `_PG_init()` (can only be called **inside the postmaster**). With the system already up, `RegisterDynamicBackgroundWorker(worker, &handle)` is used, which must be called from an **ordinary backend or another worker**.
- **Worker limit** (PG16 p.1531): the maximum number of registered background workers is limited by `max_worker_processes`.
- **`BackgroundWorker` structure** (PG16 p.1529-1530): `bgw_name`, `bgw_type`, `bgw_flags`, `bgw_start_time`, `bgw_restart_time` (seconds, or `BGW_NEVER_RESTART`), `bgw_library_name`, `bgw_function_name`, `bgw_main_arg`, `bgw_extra`, `bgw_notify_pid`. Flags: `BGWORKER_SHMEM_ACCESS` (mandatory) and `BGWORKER_BACKEND_DATABASE_CONNECTION` (which **also requires** the former, otherwise startup fails). `bgw_start_time`: `BgWorkerStart_PostmasterStart` (cannot connect to databases), `BgWorkerStart_ConsistentState` (consistent state in hot standby; read-only queries) or `BgWorkerStart_RecoveryFinished` (normal read-write state); the last two are equivalent outside a hot standby; the option only says **when to start**, the worker does not stop if the state changes (p.1530). `bgw_restart_time` is the interval before restarting the process if it crashes (any positive value, or `BGW_NEVER_RESTART`). `bgw_notify_pid` is the PID of a backend that receives `SIGUSR1` from the postmaster when the worker starts or terminates (0 for workers registered at postmaster startup; otherwise `MyProcPid`) (p.1530). On Windows/`EXEC_BACKEND` and in dynamic workers, **it is not safe to pass `Datum` by reference**, only by value; pass an `int32` and use it as an index into an array in shared memory (p.1530).
- **Connecting to a database** (PG16 p.1530-1531): the worker calls `BackgroundWorkerInitializeConnection(dbname, username, flags)` or `...ByOid` (only once; **it cannot switch databases**); this allows transactions and queries through SPI; without a database (NULL/`InvalidOid`) it only accesses shared catalogs; without a user, it runs as the superuser created in `initdb`; `BGWORKER_BYPASS_ALLOWCONN` ignores the restriction of databases that do not allow connections.
- **Signals** (PG16 p.1531): signals start **blocked** when control reaches the worker's main function and it must unblock them (`BackgroundWorkerUnblockSignals`; blocking with `BackgroundWorkerBlockSignals`), so that it can install its own handlers.
- **Restart x unregistration (`bgw_restart_time`, `BGW_NEVER_RESTART`)** (PG16 p.1531): if `bgw_restart_time` is `BGW_NEVER_RESTART`, **or** the worker exits with **exit code 0**, **or** it is terminated by `TerminateBackgroundWorker`, it is **unregistered** automatically by the postmaster on exit. Otherwise it is restarted after the configured interval, or **immediately** if the postmaster reinitializes the cluster because of a backend failure. Whoever needs only to **suspend execution temporarily** should use an **interruptible wait** (`WaitLatch()`), and not exit; when calling it, the **`WL_POSTMASTER_DEATH`** flag must be on and the return code checked to exit quickly if `postgres` itself died.
- **Dynamic worker status** (PG16 p.1531): the registering backend passes the address of a `BackgroundWorkerHandle *` and receives an opaque handle for `GetBackgroundWorkerPid` (returns `BGWH_NOT_YET_STARTED`, `BGWH_STOPPED` or `BGWH_STARTED` + PID) and `TerminateBackgroundWorker` (the postmaster sends `SIGTERM` if it is running and unregisters as soon as it is not). To **wait for startup**: initialize `bgw_notify_pid` with `MyProcPid` and call `WaitForBackgroundWorkerStartup(handle, &pid)`, which blocks until the postmaster tries to start the worker or dies (returns `BGWH_STARTED`, `BGWH_STOPPED` or `BGWH_POSTMASTER_DIED`). To **wait for termination**: `WaitForBackgroundWorkerShutdown(handle)` (returns `BGWH_STOPPED` or `BGWH_POSTMASTER_DIED`).
- **Asynchronous notifications and `LISTEN`** (PG16 p.1531): workers can **send** notifications with `NOTIFY` via SPI or `Async_Notify()` (delivered at commit), but **should not register to receive** with `LISTEN`, since **there is no infrastructure for a worker to consume** these notifications. The module `src/test/modules/worker_spi` has a working example.
- `[inference]` a worker that needs to sleep between work cycles uses `WaitLatch` with timeout and `WL_POSTMASTER_DEATH`; exiting with code 0 to "wait" would unregister it permanently.

## 8. [inference] / [extrapolation]
- `[inference]` If the model is process per worker and each connection consumes a process, many idle connections cost memory (ARCH p.14); a connection pool in front of the DBMS is consistent with the PG16 recommendation (p.531).
- `[extrapolation]` Specific tools (PgBouncer etc.) and numeric thresholds ("more than 500 to 1,000 connections") do **not** appear in the sources; v1 presented them as `[from source]`.
- `[extrapolation]` Modern execution models (task-based, vectorized) are not covered; the book only cites research on "staged" and asynchronous engines (ARCH p.24).
