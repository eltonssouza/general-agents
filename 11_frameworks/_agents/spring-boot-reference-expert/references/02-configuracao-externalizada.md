# 02 — Externalized configuration (ch. 7.2)

Pages = PDF (SBR p.N; printed = N−20). Version 2.7.18 [DATED]. Support script: `scripts/sbr_precedence.py`, `scripts/sbr_propcheck.py`.

## 1. Sources and precedence
- **[from source]** Sources: `.properties` files, YAML, environment variables and command-line arguments; values are injected through `@Value`, through the `Environment` or through `@ConfigurationProperties` (SBR p.87).
- **[from source]** Order of the PropertySources (a later one overrides an earlier one): 1 default properties; 2 `@PropertySource` (too late for `logging.*` and `spring.main.*`); 3 config data (`application.properties`); 4 `random.*`; 5 environment variables; 6 system properties; 7 JNDI `java:comp/env`; 8 ServletContext init params; 9 ServletConfig init params; 10 `SPRING_APPLICATION_JSON`; 11 command-line arguments; 12 `properties` attribute in tests; 13 `@DynamicPropertySource`; 14 `@TestPropertySource`; 15 devtools global settings in `$HOME/.config/spring-boot` (SBR p.87-88).
- **[from source]** Order of the config data files: (1) `application.*` inside the jar, (2) `application-{profile}.*` inside the jar, (3) `application.*` outside the jar, (4) `application-{profile}.*` outside the jar (SBR p.88). In the same location, `.properties` wins over YAML (SBR p.88).
- **[from source]** Arguments starting with `--` (e.g. `--server.port=9000`) become properties and take precedence over files; `setAddCommandLineProperties(false)` turns this off (SBR p.89-90).
- **[from source]** Embedded JSON: `SPRING_APPLICATION_JSON` / `spring.application.json` (variable, system property or argument); `null` values in the JSON do not override lower-order sources (SBR p.90).
- **[from source]** To debug where a value came from, use the `env` and `configprops` endpoints (SBR p.89). To see **which configuration files were loaded**, set the log level of the package `org.springframework.boot.context.config` to `trace` (SBR p.565, section 17.2.3; the level property is `logging.level.<logger>`, SBR p.141). `env`/`configprops` mask (`******`) the values of keys such as `password`, `secret`, `key`, `token` (SBR p.639).

## 2. Where the files live
- **[from source]** Default locations (increasing precedence): classpath root; `/config` on the classpath; current directory; `config/` in the current directory; immediate children of `config/` (SBR p.90-91).
- **[from source]** `spring.config.name` changes the base name; `spring.config.location` **replaces** the default locations; `spring.config.additional-location` **adds** to them; directories must end with `/`; these three are read very early and **must be environment properties** (OS variable, system property or argument) (SBR p.91-92).
- **[from source]** The `optional:` prefix avoids `ConfigDataLocationNotFoundException`; `spring.config.on-not-found=ignore` ignores all of them (SBR p.92). Location groups separated by `;` change the "last-wins" rule for profiles (SBR p.91-94).
- **[from source]** Wildcards (`config/*/`) only for external directories, a single `*`, never in `classpath:` (SBR p.92-93).
- **[from source]** Profile-specific files `application-{profile}`: they win over the non-specific ones; with several profiles, the last one wins (`prod,live`); with no active profile, `default` applies (SBR p.93-94).

## 3. Import, configtree, missing extension
- **[from source]** `spring.config.import` (e.g. `optional:file:./dev.properties`); the imported file counts as a document right below the importer and **takes precedence over it**; each import happens once (SBR p.94-95).
- **[from source]** The position of the `spring.config.import` line inside the document does not matter: with the `import` before or after `my.property`, the result is the same, and the imported file wins over the one that declared it. Several locations under a single `import` key are processed in the written order, and the **last one imported prevails** (SBR p.95). Likewise, in `spring.config.location` the last location wins, at the location-group level (with `,` all the files of one location are processed before those of the next; with `;` the locations stay at the same level) (SBR p.94).
- **[from source]** File without extension: hint in square brackets, `file:/etc/config/myconfig[.yaml]` (SBR p.96). Configuration trees (Kubernetes volumes, Docker secrets): `optional:configtree:/etc/config/`, `/*/` for several children; the file name becomes the key, the content becomes the value (SBR p.96-98).

## 4. Placeholders, multi-document, activation
- **[from source]** `${name}` and `${name:default}`; always use the **canonical form** (lowercase kebab-case) in the placeholder, otherwise relaxed binding does not match all the forms (SBR p.99).
- **[from source]** Multi-document: YAML with `---`; `.properties` with a `#---` or `!---` line (no leading space, exactly three hyphens); not loadable via `@PropertySource`/`@TestPropertySource` (SBR p.99-100). Documents are processed **from top to bottom** and later ones override earlier ones (SBR p.99); the lines immediately before and after the `#---` separator **must not have the same comment prefix** (SBR p.100).
- **[from source]** Activation: `spring.config.activate.on-profile` (expression, e.g. `prod | staging`) and `on-cloud-platform` (e.g. `kubernetes`) (SBR p.100-101). When combined in the same document they apply **together (AND)**: the book's example only activates the second document on Kubernetes **and** with `prod` **or** `staging` (the `|` is the OR inside the profile expression) (SBR p.100-101).

## 5. Encryption, YAML, random values, environment prefix
- **[from source]** **There is no native support for encrypting properties**; there are hooks (`EnvironmentPostProcessor`); for secrets the text cites Spring Cloud Vault (SBR p.101). The book's alternative for secrets mounted as files (Kubernetes, Docker swarm secrets in `/run/secrets/`): `spring.config.import=optional:configtree:/run/secrets/` (SBR p.97-98; it is **not** p.101).
- **[from source]** YAML requires SnakeYAML (already included in `spring-boot-starter`); lists become `my.servers[0]`; YAML is not loadable via `@PropertySource` (SBR p.101-102).
- **[from source]** `RandomValuePropertySource`: `${random.value}`, `${random.int}`, `${random.long}`, `${random.uuid}`, `${random.int(10)}`, `${random.int[1024,65536]}` (SBR p.103).
- **[from source]** Syntax of `random.int*`: `OPEN value (,max) CLOSE`, where OPEN and CLOSE are **any characters** (`(` `)` and `[` `]` are equivalent) and value and max are integers; with `max`, `value` is the minimum and `max` is **exclusive** (largest possible value = max-1); `${random.int(10)}` = less than 10 (SBR p.103).
- **[from source]** Prefix for system environment variables configured on the `SpringApplication` (SBR p.103).
- **[from source]** Section 7.2.7 "Configuring System Environment Properties": the prefix is set directly on the `SpringApplication`; the book's example with prefix `input`: the property `remote.timeout` is also resolved as `input.remote.timeout` in the system environment. Useful when several Spring Boot applications share the same environment (SBR p.103). [inference] the name of the Java method (`setEnvironmentPrefix`) does not appear in the book; label it [extrapolation] if you cite it, and the environment-variable form (`INPUT_REMOTE_TIMEOUT`) follows the relaxed binding rules on p.117, it is not a sentence from the book.

## 6. Relaxed binding and environment variables
- **[from source]** Accepted forms: kebab-case (recommended in properties/YAML), camelCase, underscore; UPPERCASE with `_` for environment variables; the `@ConfigurationProperties` prefix must be in kebab-case (SBR p.115-116).
- **[from source]** Variable name: dots become `_`, hyphens are removed, uppercase (`spring.main.log-startup-info` → `SPRING_MAIN_LOGSTARTUPINFO`); list index between `_` (`my.service[0].other` → `MY_SERVICE_0_OTHER`) (SBR p.117). `scripts/sbr_precedence.py env-name KEY` applies the rule.
- **[from source]** Map keys with special characters use brackets, such as `my.map.[/key1]` (quoted in YAML) (SBR p.116-117).
- **[from source]** Rule for binding a `Map` (SBR p.116-117): without brackets, **characters that are not alphanumeric, `-` or `.` are removed** from the key (`my.map./key3` becomes key `key3`; `[/key1]` and `[/key2]` preserve the slash). In YAML the brackets require quotes. **Scalar values** (enums and `java.lang` types except `Object`): in `Map<String,String>`, `a.b=c` preserves the dot (`{"a.b"="c"}`); in `Map<String,Object>` it becomes `{"a"={"b"="c"}}`, and only `[a.b]=c` preserves `a.b`.

## 7. `@ConfigurationProperties`
- **[from source]** JavaBean binding (getters/setters; initialized maps only need a getter; collections: setter recommended; an initialized nested POJO needs no setter) (SBR p.104-107). Constructor binding (immutable) with `@ConstructorBinding` and `@DefaultValue`, **including `record`**: details in the section "Constructor binding, `record`, nested class and `@DefaultValue`" further below (SBR p.107-110). `java.util.Optional` is not recommended and, without a value, binds `null` (SBR p.110).
- **[from source]** Enable with `@ConfigurationPropertiesScan` or `@EnableConfigurationProperties`; bean name `<prefix>-<fqn>` (prefix = the one from `@ConfigurationProperties`; **without a prefix, the name is just the FQN**; book example: `some.properties-com.example.app.SomeProperties`) (SBR p.112). The book recommends that the class deal only with the `Environment` and **not inject other beans**; for corner cases use setter injection or the `*Aware` interfaces (e.g. `EnvironmentAware`). If you still want to inject beans through the constructor, the class must be a `@Component` **and** use JavaBean binding (SBR p.112). Consequence: constructor binding (`@ConstructorBinding`) does not apply to `@Component`/`@Bean`/`@Import` (SBR p.110), so it does not suit that class that injects beans (answer to C01 of round 7). For third-party `@Bean` (SBR p.113-114).
- **[from source]** **Merging:** (*merging complex types*, merge of list and map) lists are replaced as a whole by the one with higher priority (a profile's list is not added to the base nor merged item by item: book example, base with 1 item + `dev` profile with 1 item = 1 item with `description` null, p.119; base with 2 items + `dev` with 1 item = 1 item, p.120) and, in YAML, a comma-separated list or a YAML list also replaces it entirely (SBR p.119-120); maps merge by key, and for the same key the higher-priority one wins (SBR p.120-121). **Book NOTE:** these merge rules apply to properties from **all sources**, not only files (SBR p.121).
- **[from source]** Conversions: `Duration` (milliseconds by default; ISO-8601; `10s`; units ns, us, ms, s, m, h, d), `Period` (days by default; ISO; `1y3d`; y, m, w, d), `DataSize` (bytes; `10MB`; B, KB, MB, GB, TB) (SBR p.121-127). `scripts/sbr_precedence.py duration VALUE`.
- **[from source]** Validation: `@Validated` + JSR-303; `@Valid` on nested ones (SBR p.129-131). `@ConfigurationProperties` vs `@Value`: relaxed binding yes/limited, metadata yes/no, SpEL no/yes (SBR p.132-133). **SpEL in a properties file (SBR p.133):** Boot does NOT evaluate SpEL expressions when reading `application.properties`/`.yml` and filling the `Environment`; the text stays as is. Only when the value is consumed by `@Value` is it evaluated, if it is a SpEL expression. In `@ConfigurationProperties` (SpEL = no) the expression is not evaluated.
- **[from source]** The **Spring MVC** `ConversionService` is a different one: `Duration`/`Period`/`DataSize` converters and `@DurationUnit` do not apply to it (SBR p.255).

## Round 4 additions: application and configuration how-tos (ch. 17.1 and 17.2)
- **[from source]** Custom `FailureAnalyzer`: turns a startup exception into a readable message (`FailureAnalysis`); Boot already ships analyzers for context exceptions, JSR-303 validations and others. `AbstractFailureAnalyzer` is only called when the exception type is present; if it cannot handle it, return `null` to give another one a turn. Registration is mandatory in `META-INF/spring.factories` (key `org.springframework.boot.diagnostics.FailureAnalyzer`); if you need the `BeanFactory` or the `Environment`, implement `BeanFactoryAware` or `EnvironmentAware` (SBR p.556).
- **[from source]** Auto-configuration diagnostics: the `ConditionEvaluationReport` appears with DEBUG logging or, with Actuator, in the `conditions` endpoint. The book's practical rules for reading the code: look for `*AutoConfiguration` classes and their `@Conditional*` annotations; add `--debug` or `-Ddebug`; look for `@ConfigurationProperties` classes (e.g. `ServerProperties` with prefix `server`) and the `configprops` endpoint; look for uses of `bind` from the `Binder` (relaxed binding, usually with a prefix), `@Value` annotations and `@ConditionalOnExpression` (SpEL expressions with `Environment` placeholders) (SBR p.556-557).
- **[from source]** Customizing the `Environment`/`ApplicationContext` before startup (SBR p.557-559): per application in code (`addListeners` and `addInitializers` of the `SpringApplication`), per application declaratively (properties `context.initializer.classes` or `context.listener.classes`) or for all applications that use a library jar with `META-INF/spring.factories`. For the `Environment`, an `EnvironmentPostProcessor` registered in `META-INF/spring.factories` can load arbitrary files; the book's example reads a YAML from the classpath with `YamlPropertySourceLoader` and adds it with `addLast` (so keys defined in the usual sources take precedence; another implementation may use a different order) (SBR p.557-559). Warning: `@PropertySource` on the `@SpringBootApplication` class looks convenient but is **not recommended**, because the source only enters the `Environment` at context refresh, too late for `logging.*` and `spring.main.*` (SBR p.559).
- **[from source]** Context hierarchy: the fluent builder (class `ApplicationBuilder` in the how-to text) creates parent/child (SBR p.560). Non-web application: keep server dependencies (such as the Servlet API) off the classpath; if you cannot, call `setWebApplicationType(WebApplicationType.NONE)` or set the `applicationContextClass` property; the business logic can be a `CommandLineRunner` registered as a `@Bean` (SBR p.560).
- **[from source]** Build property expansion (SBR p.560-562): Maven with `spring-boot-starter-parent` uses `@..@` placeholders (e.g. `app.encoding=@project.build.sourceEncoding@`, `app.java.version=@java.version@`); only the production configuration is filtered (nothing in `src/test/resources`) (SBR p.560-561). With the `addResources` flag, the `spring-boot:run` goal puts `src/main/resources` directly on the classpath (hot reload) and this **bypasses the filter**; alternative: `exec:java` or adjust the plugin (SBR p.561). Without the starter parent you must enable `<filtering>true</filtering>` on the resources and configure the `maven-resources-plugin` with the `@` delimiter and `useDefaultDelimiters` set to false (otherwise Spring `${...}` placeholders may be expanded by the build) (SBR p.561). In Gradle, `processResources` with `expand(project.properties)` and placeholders such as `app.name=${name}` (SBR p.561-562). The starter parent changes the default filter token of the `maven-resources-plugin` from `${*}` to `@`; if you enable filtering directly on `application.properties`, consider another delimiter (SBR p.565).
- **[from source]** Externalizing the `SpringApplication` (SBR p.562-565): `spring.main.*` properties (e.g. `spring.main.web-application-type=none`, `spring.main.banner-mode=off`) override and replace what was given by the Java API, **except for the primary sources** (those passed to the `SpringApplication` constructor); with `spring.main.sources` (e.g. `MyDatabaseConfig` and `MyJmsConfig`) the final order is the class from the code first and then those from the external file (SBR p.562-565). Changing the location of the files: `spring.config.name` (variable `SPRING_CONFIG_NAME`) and `spring.config.location` (`SPRING_CONFIG_LOCATION`); Boot always loads `application.properties` and, with YAML, also `.yaml` and `.yml` (SBR p.565).
- **[from source]** Short command-line argument: `server.port=${port:8080}` allows `--port=9000`; on PaaS such as Heroku or Cloud Foundry the `PORT` variable is set automatically and Spring binds it through uppercase synonyms (SBR p.565-566). YAML is a superset of JSON; it needs `snakeyaml` (already included in `spring-boot-starter`) and the map is flattened into dot-separated keys (SBR p.566).
- **[from source]** Profiles (how-to): active via `spring.profiles.active` (system property, variable `SPRING_PROFILES_ACTIVE` or `-D` **before** the jar); the value in `application.properties` is replaced by the system property or environment variable, but not by `SpringApplicationBuilder.profiles()`, which is for adding without changing the defaults (SBR p.566-567). Default profile name: `spring.profiles.default` (or `SPRING_PROFILES_DEFAULT`) (SBR p.567). Documents with `spring.config.activate.on-profile` enter the merge if the expression matches `Environment.acceptsProfiles()`; book example: port 9000 by default, 9001 with `development` and 0 with `production`; the documents are merged in the order they appear and later values win (SBR p.567-568). There is no single exhaustive list of supported properties (jars on the classpath contribute); the `configprops` endpoint shows the bindable ones and the definitive list comes from `@ConfigurationProperties`, `@Value` and uses of `Binder` (SBR p.568).

## Round 4 additions: config data, placeholders, conversions and profiles (page details)
- **[from source]** JSON in `SPRING_APPLICATION_JSON`: `null` values enter the property source, but the `PropertySourcesPropertyResolver` treats `null` properties as absent; therefore the JSON **cannot** override values of lower-order sources with `null` (SBR p.90).
- **[from source]** `spring.config.import`: profile-specific variants are also considered on import (importing `my.properties` also brings `my-<profile>.properties`) (SBR p.96). The location API is pluggable: by default it imports Properties, YAML and configuration trees; third-party jars can support Consul, Apache ZooKeeper or Netflix Archaius; for your own location, see `ConfigDataLocationResolver` and `ConfigDataLoader` (SBR p.96).
- **[from source]** Config tree (SBR p.97-98): a file name with dots is also mapped (a file `myapp.username` in `/etc/config` becomes the property `myapp.username`); the values can be bound to `String` and to `byte[]`; a `configtree:` location ending in `/*/` imports all immediate children as config trees; directories loaded by wildcard are sorted alphabetically, and if you need another order list each location as a separate import; for Docker secrets (secret `db.password` mounted in `/run/secrets/`), use `spring.config.import=optional:configtree:/run/secrets/`.
- **[from source]** Placeholders (SBR p.99): always reference the canonical form (lowercase kebab-case): `${demo.item-price}` picks up `demo.item-price` and `demo.itemPrice` from `application.properties` and `DEMO_ITEMPRICE` from the system environment; `${demo.itemPrice}` would **not** pick up `demo.item-price` or `DEMO_ITEMPRICE`; the technique also creates "short" variants of existing properties. The same applies to `@Value("${demo.item-price}")` (SBR p.133).
- **[from source]** YAML (SBR p.102): properties with `[index]` notation can be bound to `List` or `Set` by the `Binder`; YAML is not loadable via `@PropertySource` or `@TestPropertySource`; to load YAML directly there are `YamlPropertiesFactoryBean` (as `Properties`), `YamlMapFactoryBean` (as `Map`) and `YamlPropertySourceLoader`.
- **[from source]** `@ConfigurationProperties` (SBR p.107-125): for JavaBean binding the empty default constructor and getters/setters are usually mandatory (SBR p.107); `java.util.Optional` is not recommended, and if declared without a value it binds `null` and not an empty `Optional` (SBR p.110); metadata for IDE autocompletion comes from `@ConfigurationProperties` (SBR p.113); the prefix must be in kebab-case (e.g. `my.main-project.person`) (SBR p.115) and the properties, when possible, in lowercase kebab-case (`my.person.first-name=Rod`) (SBR p.116). When migrating a `Long` property to `Duration`, set the unit with `@DurationUnit` if it is not milliseconds (SBR p.125); `Period` accepts int (days by default, or `@PeriodUnit`), ISO-8601 or the simple format `1y3d`, and weeks (`w`) are just a shortcut for 7 days (the `Period` does not store weeks) (SBR p.125); `DataSize` uses `@DataSizeUnit` (SBR p.125-127).
- **[from source]** Profiles: `spring.profiles.include`, like `spring.profiles.active`, only applies in **non**-profile-specific documents (not in profile files nor in documents with `spring.config.activate.on-profile`); profile groups (`spring.profiles.group.<name>`) are useful when profiles get too granular (e.g. `proddb` and `prodmq`) and can also add active profiles when a profile is activated (SBR p.136-137). Programmatic: `SpringApplication.setAdditionalProfiles(…)` before running, or the `ConfigurableEnvironment` interface (SBR p.137).
- **[from source]** i18n (SBR p.147): the `MessageSource` auto-configuration only applies if the bundle's default properties file exists (`messages.properties` by default); if there are only language-specific files, you must add the default one; if no file matches the configured basenames, there is **no** auto-configured `MessageSource`; `spring.messages.basename` accepts a comma-separated list (package or resource from the classpath root) and `spring.messages.fallback-to-system-locale=false` turns off the fallback; see `MessageSourceProperties` for the other options.

## Constructor binding, `record`, nested class and `@DefaultValue` (round 5; SBR p.107-110)
- **[from source]** Constructor binding is the immutable form of `@ConfigurationProperties`: the class is annotated with `@ConstructorBinding` and the binder looks for a constructor with the parameters to bind; `final` fields, getters only, no setters (example `my.service` with `enabled`, `remoteAddress` and `security`) (SBR p.107-109).
- **[from source]** **`record` (Java 16 or higher)**: constructor binding works with `record`; unless the `record` has **several constructors**, `@ConstructorBinding` is **not needed**. That is: a `record` with a single constructor binds without the annotation; with several constructors, the annotation goes on the constructor to use (SBR p.109-110). In version 2.7.18 [DATED] the book does not make this conditional on Boot 3: the text describes the `record` rule in this very version (SBR p.109).
- **[from source]** **Nested class** (such as `Security`, inside the properties class): the nested members of a class with constructor binding are also bound through the constructor (SBR p.109).
- **[from source]** **`@DefaultValue`** goes on a constructor parameter or, with Java 16+, on a `record` component; the `ConversionService` converts the value text to the parameter type when the property is missing (e.g. `@DefaultValue("USER") List<String> roles`) (SBR p.108-109).
- **[from source]** **Nested null vs non-null**: if no property is bound to the nested one, the outer class instance carries `null` in it; to have a non-null instance even with no bound properties, use an **empty** `@DefaultValue` on the nested parameter (or `record` component); in Kotlin this requires the parameters without a default (`username`, `password`) to be declared nullable (SBR p.109-110).
- **[from source]** **Enabling and limits**: the class must be enabled by `@EnableConfigurationProperties` or by configuration-properties scanning. Constructor binding **does not apply** to beans created by the regular Spring mechanism: `@Component`, `@Bean` methods and `@Import` (SBR p.110). With more than one constructor, put `@ConstructorBinding` directly on the chosen constructor (SBR p.110).
- **[from source]** `java.util.Optional`: not recommended (designed for return values); if declared and without a value, what gets bound is `null`, not an empty `Optional` (SBR p.110).
- **[inference]** For JavaBean (getters/setters) none of this applies; the decision point is just: single-constructor `record` = no annotation; ordinary immutable class = `@ConstructorBinding` (SBR p.107-110).
