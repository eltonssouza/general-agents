# 00 — Overview, version, installation, upgrade and "Using Spring Boot" (chs. 1-6)

Pages = PDF (SBR p.N; printed = N−20). Labels: **[from source]** checked on the cited page; **[inference]**; **[extrapolation]** (outside the collection); **[DATED]** relative to version 2.7.18 (2023 copy).

## 1. Identity and goals
- **[from source]** Spring Boot creates "stand-alone, production-grade" Spring applications, with an opinionated view of the platform and third-party libraries; most apps need little Spring configuration (SBR p.27).
- **[from source]** Stated goals: fast start, be opinionated but "get out of the way" when requirements diverge, provide common non-functional features (embedded servers, security, metrics, health checks, externalized configuration) and **no code generation and no XML requirement** (SBR p.27).
- **[from source]** Run with `java -jar` or traditional war deployment; there is also the CLI that runs "spring scripts" (SBR p.27).

## 2. Requirements and version [DATED]
- **[from source]** Spring Boot **2.7.18** requires **Java 8**, compatible up to Java 21; Spring Framework **5.3.31+** (SBR p.27).
- **[from source]** Build: Maven 3.5+ (table p.27); Gradle 6.8.x, 6.9.x, 7.x and 8.x (SBR p.27). **Internal inconsistency in the PDF:** the installation text says Maven "3.3 or later" (SBR p.28) and the plugins chapter says Maven 3.2+ for the plugin (SBR p.550). Cite the value with the page.
- **[from source]** Embedded servlet containers: Tomcat 9.0 (Servlet 4.0), Jetty 9.4 (3.1), Jetty 10.0 (4.0), Undertow 2.0 (4.0); it also deploys to any Servlet 3.1/4.0 container (SBR p.27-28).
- **[inference]** The text uses `javax.*` (e.g. `javax.validation`, `javax.servlet`); `jakarta` only appears in Appendix F coordinates. Any question about Spring Boot 3/Jakarta EE = NOT COVERED (boundary: java-backend-frameworks-expert).

## 3. Installation
- **[from source]** "Classic" use: put the `spring-boot-*.jar` files on the classpath or, preferably, use Maven/Gradle with dependency management (SBR p.28). Dependencies use the groupId `org.springframework.boot`; the POM typically inherits from `spring-boot-starter-parent` (SBR p.28).
- **[from source]** CLI: manual installation (zip/tar.gz), SDKMAN! (`sdk install springboot`), Homebrew (`brew tap spring-io/tap`; `brew install spring-boot`), MacPorts, Scoop (SBR p.29-31). Completion commands listed: `grab help jar run test version` (SBR p.31).
- **[from source]** First application: `spring-boot-starter-parent` 2.7.18 in `<parent>`, `spring-boot-starter-web`, a class with `@RestController` + `@SpringBootApplication` and `SpringApplication.run`; run with `mvn spring-boot:run`; generate an executable jar with `spring-boot-maven-plugin` and `mvn package` (the jar is around 18 MB and there is a `.jar.original`) (SBR p.32-39).
- **[from source]** `@SpringBootApplication` combines `@SpringBootConfiguration`, `@EnableAutoConfiguration` and `@ComponentScan` (SBR p.36, 54).

## 4. Upgrade
- **[from source]** Instructions live in the project wiki and in the release notes; when skipping more than one release, read the notes of the intermediate ones (SBR p.40).
- **[from source]** For property changes between releases, add `spring-boot-properties-migrator` (runtime scope): it diagnoses at startup and temporarily migrates properties; properties added late (e.g. `@PropertySource`) are not covered; remove the module after migrating (SBR p.40).
- **[from source]** The documentation is version-specific (SBR p.41).

## 5. Developing with Spring Boot (ch. 6)
- **Dependency management:** each release has a curated list of dependencies (BOM `spring-boot-dependencies`); you do not need to declare versions; you can override them, but the Spring Framework version should not be specified (SBR p.42); the version properties to override are in table F.2 (SBR p.876-881, summary in references/14). **Do not confuse** with the CLI's dependency management (`@DependencyManagementBom`, which is CLI-only; see references/12).
- **Starters:** `spring-boot-starter-*` convention; third-party starters must **not** start with `spring-boot` (e.g. `thirdpartyproject-spring-boot-starter`) (SBR p.45). Tables of application starters, production starters (`spring-boot-starter-actuator`) and technical starters (jetty, log4j2, logging, reactor-netty, tomcat, undertow) in SBR p.45-48.
- **Code structure:** avoid the "default package" (a class with no package declaration): the problem is specific to apps that use `@ComponentScan`, `@ConfigurationPropertiesScan`, `@EntityScan` or `@SpringBootApplication`, because all classes from all jars are read; the book recommends following Java's package naming conventions with a reversed domain (e.g. `com.example.project`) (SBR p.48). Put the main class in a root package above the others: `@SpringBootApplication` implicitly defines the base search package (e.g. where to look for `@Entity` in JPA) and the root package restricts the component scan to your project (SBR p.48-49). Table of technical starters (SBR p.48): `spring-boot-starter-tomcat` = Tomcat as the embedded servlet container, **the default of `spring-boot-starter-web`**; `spring-boot-starter-undertow` = alternative to Tomcat; `spring-boot-starter-reactor-netty` = Reactor Netty as the embedded reactive HTTP server; `spring-boot-starter-logging` = Logback, the default logging starter; `spring-boot-starter-log4j2` = alternative to logging.
- **Configuration:** prefer Java `@Configuration` classes; `@Import` and `@ImportResource` (XML) (SBR p.50).
- **Auto-configuration:** opt-in via `@EnableAutoConfiguration`/`@SpringBootApplication` (add only one); it is non-invasive (your own `DataSource` bean makes the embedded one back away); `--debug` prints the conditions report; exclude with `exclude`/`excludeName` or `spring.autoconfigure.exclude`; only the **name** of the auto-configuration class is public API (SBR p.50-51).
- **DI:** constructor injection recommended; `@Autowired` on the chosen constructor when there is more than one (SBR p.52-53).
- **Running:** IDE, `java -jar`, remote debugging with `-Xdebug -Xrunjdwp...`, `mvn spring-boot:run` (`MAVEN_OPTS`), `gradle bootRun` (`JAVA_OPTS`) (SBR p.57-58).
- **Devtools — packaging (SBR p.59, 68):** repackaged archives **do not contain devtools by default**; to include it (only for the remote devtools feature) use `excludeDevtools` = `false` in the Maven plugin, or include the `developmentOnly` configuration in the task classpath in the Gradle plugin; marking the dependency as `optional` (Maven) or `developmentOnly` (Gradle) prevents it from propagating transitively to modules that use your project (SBR p.59). Forcibly enabling with `-Dspring.devtools.restart.enabled=true` in a production environment is a security risk (SBR p.59).
- **Devtools — details (SBR p.59-70):** classloader problems in multi-module projects: try disabling restart; if that fixes it, customize the restart classloader (SBR p.59). Restart: when the classpath changes (Eclipse: save; IntelliJ: Build Project; plugins: `mvn compile`/`gradle build`; **the plugin fork must stay enabled**); it depends on the shutdown hook (does not work with `setRegisterShutdownHook(false)`) and does not work with AspectJ weaving; JRebel replaces automatic restart; two classloaders (base and restart); conditions delta report on every restart (`spring.devtools.restart.log-condition-evaluation-delta=false` turns it off) (SBR p.61-62). Default exclusions (`/META-INF/maven`, `/META-INF/resources`, `/resources`, `/static`, `/public`, `/templates`) do not restart but trigger live reload; `spring.devtools.restart.additional-exclude` adds to them; `additional-paths` watches folders outside the classpath; `spring.devtools.restart.enabled=false` in properties still initializes the classloader — to turn it off entirely, set the system property before `SpringApplication.run` (SBR p.62-63). `trigger-file` (name only, on the classpath) (SBR p.64-65); `META-INF/spring-devtools.properties` with `restart.exclude.*`/`restart.include.*` (regex over the classpath) to decide which classloader loads what: `include` items go up to the restart classloader and `exclude` items go down to the base one; the value is a regex applied to the classpath (the book's example uses `restart.exclude.companycommonlibs` with a pattern like `/mycorp-common-[\\w\\d-\\.]+\\.jar` and `restart.include.projectcommon` with an analogous pattern for the project's own jar); the keys must be unique and any key starting with `restart.include.` or `restart.exclude.` is considered; all `META-INF/spring-devtools.properties` on the classpath are read, including those packaged in libraries; by default, projects open in the IDE (and the project with `@SpringBootApplication` in `mvn spring-boot:run`/`gradle bootRun`) go in the restart classloader and ordinary jars in the base one (SBR p.65). Limitation: objects deserialized with the standard `ObjectInputStream` do not work well with restart; the book suggests Spring's `ConfigurableObjectInputStream` combined with `Thread.currentThread().getContextClassLoader()`, and warns that several third-party libraries deserialize without considering the context classloader, in which case you need to ask the authors for a fix (SBR p.66). LiveReload: embedded server; `spring.devtools.livereload.enabled=false`; only one at a time; requires restart enabled (SBR p.66). Global configuration in `$HOME/.config/spring-boot` (`spring-boot-devtools.properties|yaml|yml`; `SPRING_DEVTOOLS_HOME` or `spring.devtools.home`; profiles are not supported; **fallback:** if there are no files in `$HOME/.config/spring-boot`, a `.spring-boot-devtools.properties` is looked for at the root of `$HOME`, to share configuration with applications on older Boot versions that do not use the new location; profiles activated in that file also do not affect profile-specific files, and `spring-boot-devtools-<profile>.properties` and `spring.config.activate.on-profile` are not supported (SBR p.67)) and `poll-interval`/`quiet-period` (Appendix A: 1s and 400ms) (SBR p.66-67, 798). Development defaults applied (table): `server.error.include-binding-errors|include-message|include-stacktrace` = `always`, `spring.h2.console.enabled`, `spring.graphql.graphiql.enabled`, `spring.mvc.log-resolved-exception`, template caches and `spring.web.resources.cache.period` = 0; DEBUG logs for the `web` group; `spring.mvc.log-request-details`/`spring.codec.log-request-details` show (potentially sensitive) details (SBR p.59-60). Remote: proxy via `spring.devtools.remote.proxy.host|port`, always use `https://`, `RemoteSpringApplication` as the main class in the IDE, it only updates while the client is running, failures uploading in batches suggest increasing `poll-interval`/`quiet-period` (SBR p.68-70). Turn off the dev defaults with `spring.devtools.add-properties=false` (SBR p.60). **Remote devtools (SBR p.68-69):** opt-in (security risk: only on a trusted network or with SSL; **never in production**); requires including devtools in the archive (`excludeDevtools=false`) and setting the *remote secret* (`spring.devtools.remote.secret`, unique and strong) (SBR p.68); it has two parts: an endpoint on the server and a client running in the IDE; **the server component is enabled automatically when `spring.devtools.remote.secret` is set; the client is launched manually** (main class `org.springframework.boot.devtools.RemoteSpringApplication`, with the **same classpath** as the remote project; **only required argument = the remote URL**) (SBR p.68-69); because the client uses the same classpath, it **reads the application's properties, and that is how `spring.devtools.remote.secret` is read and sent to the server for authentication** (SBR p.69); not supported in Spring WebFlux (SBR p.68). Appendix A (SBR p.798): `remote.secret` has no published default (required to enable remote support), `remote.secret-header-name` = `X-AUTH-TOKEN`, `remote.context-path` p.797, `remote.restart.enabled` true.
- **[from source]** For production the text points to an executable jar and, if you want health/auditing/metrics, `spring-boot-actuator` (SBR p.70).

## Round 4 additions: devtools and "Using Spring Boot" (page details)
- **[from source]** Devtools, restart: depends on the context's shutdown hook (does not work with `setRegisterShutdownHook(false)`); it also needs to customize the `ApplicationContext`'s `ResourceLoader` (if the application already provides one, it is wrapped; directly overriding the context's `getResource` is not supported); there is no restart support with AspectJ weaving (SBR p.61). Trigger file: used to trigger a restart only when you want it (useful if the IDE compiles continuously); set `spring.devtools.restart.trigger-file` to the name (without a path) of the file, which must be somewhere on the classpath (e.g. `.reloadtrigger` in `src/main/resources`); any update to the file triggers the check, but the restart only happens if devtools detects something to do (SBR p.64-65).
- **[from source]** Devtools, global configuration and watcher: the global files live in `$HOME/.config/spring-boot` (`spring-boot-devtools.properties`, `.yaml` or `.yml`); profiles are **not** supported in them (neither `spring-boot-devtools-<profile>.properties` nor `spring.config.activate.on-profile` documents) (SBR p.66-67). The `FileSystemWatcher` works by polling at an interval and then waiting for a quiet period (`spring.devtools.restart.poll-interval` and `quiet-period`), because Boot relies entirely on the IDE to compile and copy the files (SBR p.67). Remote devtools: files are only monitored while the remote client is running; changes made before starting it are not sent to the remote server (SBR p.70). LiveReload requires automatic restart enabled (SBR p.66).
- **[from source]** Running from the IDE: if you run the web application twice by mistake, "Port already in use" appears; Spring Tools users can use the Relaunch button instead of Run to close the existing instance (SBR p.57). The running section covers only jar packaging; for war, see the server and IDE documentation (SBR p.57). If you do not want to use the `spring-boot-antlib` Ant module, the how-to "Build an Executable Archive From Ant without Using spring-boot-antlib" covers the alternative (SBR p.44). `@SpringBootApplication` is not mandatory: you can replace that single annotation with any of the features it enables (for example, without component scan or without configuration properties scan) (SBR p.55-56).
