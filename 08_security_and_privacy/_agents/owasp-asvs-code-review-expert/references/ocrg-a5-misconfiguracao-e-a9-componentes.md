# OCRG — A5 Security misconfiguration (Java/.NET/IIS frameworks) and A9 Vulnerable components (OCRG p.84-117, 148-149)

Source: OCRG v2.0, chs. 11 and 15. Pages = PDF (printed = N − 1). Related in the ASVS (mapping `[inference]`): V14.1.3, V14.2.x, V14.3.x, V10.3.x, V1.14.3. **Content mostly [DATED]** (Struts 1, JEE 5/6, IIS 7, .NET Framework 2-4, Code Access Security, 2010 FxCop): use as a **method** (review the framework configuration together with the code), not as a list of versions.

## Central principle (OCRG p.84)
- [from source] Much transactional functionality is not in the developer's code but in framework parent classes and **configuration files** (XML or annotations); the reviewer needs to know the framework and the language. Without that, auditing only the Java, "you do not see validation being executed" (OCRG p.84). OS and network hardening is **out of scope** of the guide (CIS benchmarks; SANS Critical Control 10 for network devices) (OCRG p.84).

## Java and servers (OCRG p.84-92)
- **Struts** (11.1): `struts-config.xml` (action mappings per request) and `web.xml` (deployment descriptor) are the central points; the **validator** (regex) **is not enabled by default** — it requires a plug-in and `validation.xml`/`validator-rules.xml` (Sample 11.1) (OCRG p.84-85).
- **Declarative JEE** (11.2): `web.xml` and `ejb-jar.xml` define resources, authorized roles, restricted HTTP methods (e.g. GET/POST), `transport-guarantee` `CONFIDENTIAL` (SSL) and authentication (Samples 11.2-11.4); the reviewer checks that the controls are on the **correct roles** and that bean methods have permission or are in an `exclude-list` (OCRG p.85-89). **Annotations** (`@DeclareRoles`, `@DenyAll`, `@PermitAll`, `@RolesAllowed`, `@RunAs`; Sample 11.5): must reflect correct roles and be consistent with `ejb-jar.xml` (OCRG p.89).
- **Servers** (11.4): Tomcat `server.xml` (Table 12: `maxPostSize`, `maxParameterCount`, `SSLEnabled`, `secure`, `ciphers`, `autoDeploy`, `deployXML`, `allowLinking`...; also review the filters); Jetty (form limits `maxFormContentSize`/`maxFormKeys`; obfuscated passwords); JBoss (password masking); WebLogic (`weblogic.xml`, Table 13) (OCRG p.90-92). `[inference]` Obfuscating/masking a password in XML is not the same as protecting a secret (ASVS V2.10.4 requires secrets outside the code/repository, ASVS p.30).
- **Programmatic J2EE** (11.5): `getRemoteUser`, `isUserInRole`, `getUserPrincipal`; check `security-role-ref` in the descriptor (Sample 11.9) (OCRG p.92-94).

## IIS and .NET (OCRG p.94-117)
- [from source] `web.config` (per application) overrides `machine.config`; many security settings are there, not in the code; on IIS 7+, `Web.config` and `ApplicationHost.config`, section `<system.webServer><security>`: authentication, authorization, request filtering and limits, SSL, IP filtering and error handling (Samples 11.10-11.15; Tables 14-15) (OCRG p.94-99). **Request filtering** (`denyUrlSequences` for `..` and `:`, `fileExtensions` with `allowUnlisted="false"`, `requestLimits`, `verbs` with `allowUnlisted="false"`, `hiddenSegments`, `allowDoubleEscaping="false"` against **double encoding** `%252E%252E%252F`) (OCRG p.97-105). There is also programmatic configuration (appcmd, C#) (OCRG p.98-100).
- [from source] **Protecting the web.config**: the `appSettings`, `connectionStrings`, `identity` and `sessionState` sections must be **encrypted** (`aspnet_regiis -pef`); some sections cannot be; machine vs user RSA container (shared hosting) (OCRG p.105-106). **Trust level** (Full…Minimal) and locking with `allowOverride="false"` (OCRG p.106-107).
- [from source] **Strong names**: guarantee a unique name, version lineage and integrity (important in the GAC), but do **not** prevent removing the signature, modifying and re-signing; the reviewer understands how the private key is protected; *delay signing* (OCRG p.107-110). **Round tripping** (Ildasm/Ilasm) and **obfuscation** (Dotfuscator) (OCRG p.111).
- [from source] **ASP.NET**: Forms authentication — Sample 11.32 and recommendations: partition the site, `protection="All"`, short timeouts, SSL (and, without SSL, `slidingExpiration="false"`), **do not use `<credentials>` in production**, configure `machineKey`, unique cookie names/paths (OCRG p.114). Classic ASP: manual authentication in session variables (OCRG p.114). Managed code: fewer buffer overflows; CAS (Table 16); declarative > imperative (Sample 11.33); `IDisposable`; exceptions (avoid try in loops; find who **swallows** them; do not use exceptions just for flow) (OCRG p.114-115).
- [from source] **FxCop** (analyzes binaries, not source): security rules (Tables 17): request validation/event validation/ViewState MAC and encryption, `ViewStateUserKey` (anti-CSRF), `enableCrossAppRedirects` (open redirect), Forms `protection` = All, `requireSSL`, no credentials in forms, `customErrors` with a default page, **debug compilation off**, **trace off**, `httpOnlyCookies`, anonymous access, `ValidateAntiForgeryToken`, role manager cookie, `enableHeaderChecking` (OCRG p.115-117). The linter implements a subset (`CFG-*`).

## A9 — Components with known vulnerabilities (OCRG p.148-149)
- [from source] Components (libraries, frameworks) almost always run with full privilege; flaws in popular components apply to everyone who uses them and are sold in underground markets (OCRG p.148).
- [from source] There is almost **no code to review**, unless the organization reviews the component; what the review can do is support **tracking** of components and versions (spreadsheet/wiki in small companies; 20 products × 5-6 components = over 100 sources of vulnerability; reacting to "a Heartbleed") (OCRG p.148).
- [from source] **Control the ingredients**: limit which libraries may be used (e.g. one version of OpenSSL), to know the risk profile; library integration must go through code review: is the library allowed? (if the dev is unaware one already existed, reject and use the original); is tracking up to date for quick remediation? (OCRG p.148-149).
- [from source] "**Sledgehammer to crack a nut**": a large library for a small use widens the surface (unused code can open a door and talk to the Internet); turn off unused functionality or remove it; **OWASP Dependency Check** provides automation (OCRG p.149).
- ASVS: V14.2.1 (all up to date, dependency checker), V14.2.2 (remove unused), V14.2.4 (trusted repositories), V14.2.5 (**SBOM**; absent from the OCRG), V14.2.6 (sandbox) (ASVS p.62).
