> ESM pattern for streams and queues, parameters, errors, batch item failures, differences per service.
> Source: AWS Lambda Developer Guide (2022 edition; last release entry on 11/28/2022), acronym LAMBDA. Citations `(LAMBDA p.N)` = PDF page (printed = N-22). Lines without an explicit label come from the book; [DATED] = number/limit/runtime/version/CLI that has aged; [extrapolation] = outside the text. Paraphrase; check the current documentation before acting. Note: the text of the references has no accents, because the reading notes it came from had none.

## DynamoDB Streams (p.643-655) - EVENT SOURCE MAPPING PATTERN FOR STREAMS (reference for Kinesis)
- [from source] (LAMBDA p.643) Lambda reads records from the stream in batches and invokes the function SYNCHRONOUSLY with an event containing the records; for non-Lambda targets or to enrich data, the note points to EventBridge Pipes
- [from source] (LAMBDA p.643) Event: Records[] with eventID, eventName (INSERT/MODIFY/REMOVE), eventSourceARN, dynamodb{Keys, NewImage, OldImage, SequenceNumber, SizeBytes, StreamViewType}
- [from source] (LAMBDA p.644) Lambda polls the shards at a base rate of 4 times per second; when there are records it invokes and waits for the result; on success it resumes polling [DATED]
- [from source] (LAMBDA p.644) Batching: by default it invokes as soon as there are records (a single record -> invokes with one). Batching window up to 5 minutes; Lambda keeps reading until the batch is full, the window expires or the payload reaches 6 MB [DATED]
- [from source] (LAMBDA p.644) On function error Lambda retries the batch until success or the data expires; to avoid a stuck shard: reduce the batch size (split), limit retries, discard old records; retain discarded records by sending details to an SQS queue or SNS topic
- [from source] (LAMBDA p.644) Concurrency: up to 10 simultaneous batches per shard (ParallelizationFactor 1 to 10, default 1); ordering guaranteed at the shard level even with parallelism; e.g. factor 2 allows up to 200 concurrent invocations for 100 shards; does not work with Kinesis aggregation; useful when IteratorAge is high [DATED]
- [from source] (LAMBDA p.645) Permissions on the execution role: dynamodb:DescribeStream, GetRecords, GetShardIterator, ListStreams (managed policy AWSLambdaDynamoDBExecutionRole); for a failure destination: sqs:SendMessage or sns:Publish
- [from source] (LAMBDA p.645) You can create several event source mappings to process the same data with several functions, or several streams with one function
- [from source] (LAMBDA p.646) Options: Batch size (up to 10,000; sends the whole batch in one call as long as the total is <= 6 MB synchronous payload), Batch window (seconds), Starting position (Latest = only new; Trim horizon = all records), On-failure destination (SQS or SNS), Retry attempts (does not apply to service/throttle errors where the batch did not reach the function), Maximum age of record, Split batch on error (splits in two; original batch size unchanged), Concurrent batches per shard, Enabled (when re-enabled it resumes from the last processed record) [DATED: limits]
- [from source] (LAMBDA p.646) There is no charge for the GetRecords calls Lambda makes on DynamoDB triggers [DATED: price]
- [from source] (LAMBDA p.647) APIs: Create/List/Get/Update/DeleteEventSourceMapping. CLI: create-event-source-mapping --batch-size 500 --maximum-batching-window-in-seconds 5 --starting-position LATEST; update-event-source-mapping --maximum-retry-attempts 2 --maximum-record-age-in-seconds 3600 --destination-config OnFailure; --parallelization-factor 5. Updates are applied asynchronously (State Updating until complete; use get-event-source-mapping) [DATED: CLI]
- [from source] (LAMBDA p.648) Error handling: the ESM invokes synchronously and retries on error. If Lambda throttles the function or returns an error without invoking, it retries until the records expire/exceed the maximum age. If the function receives and returns an error, it retries until expiry, exceeding the maximum age or reaching the retry quota; batch splitting isolates bad records and works around timeouts and does NOT count toward the retry quota
- [from source] (LAMBDA p.648) With the default configuration, a bad record can block the shard for up to a day; recommendation: configure a reasonable number of retries and maximum age [DATED: 1 day]
- [from source] (LAMBDA p.649) Failed-event destination (Add destination > Source Stream invocation): invocation document with requestContext.condition ("RetryAttemptsExhausted"), responseContext, DDBStreamBatchInfo (shardId, start/endSequenceNumber, batchSize, streamArn). It does not contain the records: you must fetch them from the stream before they expire
- [from source] (LAMBDA p.649) IteratorAge metric (age of the last record in the batch at the end of processing); a growing trend indicates a problem
- [from source] (LAMBDA p.649) Tumbling windows: state kept between invocations, max 1 MB per shard (beyond that the window ends early); at-least-once processing (not exactly once), ordering only the first time; the response MUST contain the state property (TimeWindowEventResponse {state, batchItemFailures}), otherwise it is a failure; at the end of the window isFinalInvokeForWindow=true, final synchronous invocation; if it fails, processing is suspended; for Java use Map<String,String> as the state (p.649-650) [DATED: 1 MB]
- [from source] (LAMBDA p.650) At the end of the window isFinalInvokeForWindow is true; after the final invocation succeeds the checkpoint advances; if it fails, processing is suspended until success
- [from source] (LAMBDA p.652) Config: --tumbling-window-in-seconds (e.g. 120); window boundaries by the approximate timestamp of insertion into the stream; does NOT support resharding (shard ends -> window closes, children start a new window with zeroed state); supports maxRetryAttempts and maxRecordAge. The DynamodbTimeWindowEvent event carries window{start,end}, state, shardId, isFinalInvokeForWindow, isWindowTerminatedEarly (p.651)
- [from source] (LAMBDA p.652) ReportBatchItemFailures: by default there is a checkpoint at the highest sequence number only if the batch is a total success; any other outcome = total failure and retry of the batch. Enable by including ReportBatchItemFailures in the ESM's FunctionResponseTypes list; it reduces retries but does not completely eliminate retries of successful records
- [from source] (LAMBDA p.653) Response syntax: {"batchItemFailures":[{"itemIdentifier":"<id>"}]} (in streams the id is the sequence number); with several items, Lambda uses the LOWEST sequence number as the checkpoint and retries everything from there. Total success: empty or null list, empty or null EventResponse. Total failure: itemIdentifier empty string, null or with a wrong key name
- [from source] (LAMBDA p.653) Bisect: if BisectBatchOnFunctionError is on, the batch is split on failure regardless of ReportBatchItemFailures; with both on and a partial response, the batch is split at the returned sequence number and only the remainder is retried
- [from source] (LAMBDA p.654) Examples (Java StreamsEventResponse/BatchItemFailure; Python): on the first error return immediately the sequence number of the failed item, since in streams the retry restarts from that item onward
- [from source] (LAMBDA p.655) All event source types share Create/UpdateEventSourceMapping, but only some parameters apply to each. Table for DynamoDB Streams [DATED]: BatchSize default 100 max 10,000; BisectBatchOnFunctionError default false; DestinationConfig (SQS/SNS); Enabled true; EventSourceArn, FunctionName and StartingPosition (TRIM_HORIZON or LATEST) required; MaximumBatchingWindowInSeconds default 0; MaximumRecordAgeInSeconds default -1 (infinite) min -1 max 604800; MaximumRetryAttempts default -1 min -1 max 604800 (as printed); ParallelizationFactor default 1 max 10; TumblingWindowInSeconds min 0 max 900
- [from source] (LAMBDA p.647) INCONSISTENCY in the text: the CLI output shows MaximumRecordAgeInSeconds 604800 and MaximumRetryAttempts 10000 as default values, while the table on p.655 indicates default -1 (infinite); the table lists "Maximum: 604800" also for MaximumRetryAttempts (probable copy error)
- [from source] (LAMBDA p.655) The table says EventSourceArn "ARN of the data stream or a stream consumer" (text inherited from the Kinesis table; consumer does not apply to DynamoDB)
- [from source] (LAMBDA p.659) DDB tutorial: create a table with the stream enabled, note the stream ARN, create the ESM (--batch-size 100 --starting-position LATEST). The same stream can have several functions and one function several streams, BUT the functions share the stream's read throughput
- [from source] (LAMBDA p.659) list-event-source-mappings shows LastProcessingResult: "No records processed" (has not started polling or empty stream) and "OK" indicate no problem; otherwise it carries an error message; filter with --function-name
- [from source] (LAMBDA p.662) Java: normal return = batch processed successfully and reading continues; exception = batch not processed and Lambda re-invokes with the SAME batch (without ReportBatchItemFailures)
- [from source] (LAMBDA p.664) SAM: Events of type DynamoDB (Stream: !GetAtt Table.StreamArn, BatchSize, StartingPosition) and Policies AWSLambdaDynamoDBExecutionRole; StreamViewType NEW_IMAGE


## Self-managed Kafka (p.678-) - start
- [from source] (LAMBDA p.678) Kafka is supported as an event source; Lambda polls internally and invokes the function SYNCHRONOUSLY in batches; configurable maximum batch size, default 100 messages [DATED]; supports batching window and batch size; a self-managed cluster includes Kafka not hosted on AWS (e.g. CloudKarafka); event: eventSource "SelfManagedKafka", bootstrapServers, records{"topic-partition":[{topic, partition, offset, timestamp, timestampType, key, value (base64), headers}]}; the note points to EventBridge Pipes
- [from source] (LAMBDA p.679) Authentication: VPC access (if only users in the VPC access the brokers, configure the ESM for VPC access), SASL/SCRAM with TLS (credentials sent encrypted), SASL/PLAIN with TLS (credentials in clear text), SASL credentials stored as a secret in Secrets Manager; mTLS (Lambda is the client)
- [from source] (LAMBDA p.680) mTLS: CLIENT_CERTIFICATE_TLS_AUTH secret with certificate and privateKey fields (PEM; PKCS #8 key; an encrypted key requires privateKeyPassword; only PBES1, not PBES2); certificate = chain starting from the client up to the root; the server cert can be from a public CA (in Lambda's trust store) or private/self-signed (secret with the root CA); Secrets Manager supports secrets up to 65,536 bytes [DATED]


## Self-managed Kafka (cont., p.681-689)
- [from source] (LAMBDA p.682) Required permissions on the execution role: logs:CreateLogGroup/CreateLogStream/PutLogEvents. Optional depending on the case: secretsmanager:GetSecretValue and kms:Decrypt (secret/KMS key) and VPC permissions (ec2:CreateNetworkInterface, DescribeNetworkInterfaces, DescribeVpcs, DeleteNetworkInterface, DescribeSubnets, DescribeSecurityGroups) if only VPC users access the cluster (p.681-682)
- [from source] (LAMBDA p.682) By default Lambda does NOT have permission for the self-managed Kafka actions; they must be defined in a policy attached to the execution role; IAM users also need an identity-based policy to operate the event source APIs
- [from source] (LAMBDA p.683) Authentication/authorization errors appear in the ESM in LastProcessingResult: "Cluster failed to authorize Lambda" (SASL/SCRAM or mTLS: user without Kafka ACLs DescribeConfigs Cluster, Describe/Read Group, Describe/Read Topic; the topic must match the ESM's and the group must equal the ESM UUID; role changes can take several minutes), "SASL authentication failed" (invalid user/password), "Server failed to authenticate Lambda" (no client cert for mTLS, brokers without mTLS, or untrusted cert), "Lambda failed to authenticate server" (private/self-signed CA without root CA, mismatched root CA, or hostname without the broker's SAN), "Provided certificate or private key is invalid" (PEM and PBES1) (p.683-684)
- [from source] (LAMBDA p.684) Network: recommends PrivateLink VPC endpoints for Lambda and STS (and Secrets Manager if there is authentication), or a NAT gateway per public subnet. Security groups at minimum: inbound all traffic on the broker port (default 9092) in the event source SGs; outbound port 443 to everything and the broker port; if using VPC endpoints, the endpoints' SG must allow inbound 443 from the event source SGs [DATED: ports]
- [from source] (LAMBDA p.684) Prerequisites: Kafka cluster version 0.10.0.0 or later [DATED]; execution role with permission on the resources used
- [from source] (LAMBDA p.685) Customizable consumer group ID: lets you migrate existing consumers to Lambda; if there are other active pollers in the same group Kafka distributes messages among all of them (Lambda does not receive everything); if the group already exists Lambda IGNORES StartingPosition and uses the committed offset; if it does not exist it uses StartingPosition; it must be unique among your Kafka event sources and CANNOT be changed later
- [from source] (LAMBDA p.685) Console: type Apache Kafka, Bootstrap servers (host:port per broker), Topic name, Batch size, Batch window, Consumer group ID, Starting position (Latest/Trim horizon), VPC (required if only VPC users access), Authentication (BASIC_AUTH for SASL plaintext, SASL_SCRAM_*, CLIENT_CERTIFICATE_TLS_AUTH) with secret, Encryption (secret with private root CA), Enable trigger. Explicit recommendation: create the trigger disabled for testing (clear Enable trigger)
- [from source] (LAMBDA p.686) CLI: create-event-source-mapping --topics AWSKafkaTopic --source-access-configuration Type=SASL_SCRAM_512_AUTH,URI=<secret arn> --self-managed-event-source '{"Endpoints":{"KAFKA_BOOTSTRAP_SERVERS":[...]}}'; for VPC use source-access-configuration with Type VPC_SUBNET (URI subnet:...) and VPC_SECURITY_GROUP (URI security_group:...) [DATED: CLI]
- [from source] (LAMBDA p.687) Lambda reads from the topics according to StartingPosition and, after success, the offset is committed in the Kafka cluster; with LATEST it starts at the last message of each partition and does NOT read what was produced during the trigger's configuration window; on error in any message of the batch, it retries the whole batch until success or expiry
- [from source] (LAMBDA p.687) LIMIT: despite the functions' maximum timeout of 15 minutes, ESMs for MSK, self-managed Kafka and Amazon MQ (ActiveMQ and RabbitMQ) only support functions with a maximum timeout of 14 minutes (to handle errors and retries) [DATED]
- [from source] (LAMBDA p.687) Kafka auto scaling: starts with ONE consumer for all partitions (each consumer with several processors in parallel); scales up to one consumer per partition (preserves per-partition order); every 1 minute it evaluates the offset lag; adjustment takes up to 3 minutes; if the function is overloaded, it reduces consumers; monitor consumer_lag/consumer_offset and concurrency metrics [DATED]
- [from source] (LAMBDA p.688) A function error makes the Kafka consumer stop processing that partition (other consumers continue if they do not have the same error); cause in StateTransitionReason: ESM_CONFIG_NOT_VALID, EVENT_SOURCE_AUTHN_ERROR, EVENT_SOURCE_AUTHZ_ERROR, FUNCTION_CONFIG_NOT_VALID
- [from source] (LAMBDA p.688) Records above 6 MB may go unprocessed; OffsetLag metric (offset difference between the last written and the last processed by the consumer group); a growing trend indicates a problem with the pollers
- [from source] (LAMBDA p.689) Self-managed Kafka parameter table [DATED]: BatchSize default 100 max 10,000; MaximumBatchingWindowInSeconds default 500 ms; SelfManagedEventSource (required, list of brokers, creation only); SelfManagedKafkaEventSourceConfig (ConsumerGroupId, default unique value, creation only); SourceAccessConfigurations (VPC or credentials; SASL_PLAIN uses BASIC_AUTH); StartingPosition TRIM_HORIZON/LATEST (creation only); Topics (creation only); FilterCriteria (event filtering). There is no BisectBatchOnFunctionError, retry/maximum age or destination in the Kafka table


## Kinesis Data Streams (p.691-712) - same pattern as DynamoDB Streams; only the DIFFERENCES are detailed
- [from source] (LAMBDA p.691) Stream = set of shards; a consumer can be shared throughput (standard iterator) or dedicated (enhanced fan-out). Standard: Lambda polls each shard over HTTP and the ESM shares the read throughput with other consumers of the shard. Enhanced fan-out: dedicated connection per shard, Kinesis PUSHES records over HTTP/2; useful with many applications reading the same data or reprocessing with large records
- [from source] (LAMBDA p.691) Synchronous invocation; each batch contains records from a SINGLE shard/stream; event Records[].kinesis{partitionKey, sequenceNumber, data (base64), approximateArrivalTimestamp}, eventSourceARN, eventName aws:kinesis:record
- [from source] (LAMBDA p.692) Same batching behavior (default invokes when there are records; batching window up to 5 min; 6 MB payload), retry until success/expiry, batch split, SQS/SNS as destination, up to 10 batches per shard and ParallelizationFactor 1-10 with per-shard ordering, does not work with Kinesis aggregation (text identical to DynamoDB)
- [from source] (LAMBDA p.693) Standard iterator: polling per shard at a base rate of once per second (DynamoDB: 4 per second) [DATED]; EFO consumer created with Kinesis RegisterStreamConsumer (aws kinesis register-stream-consumer --consumer-name --stream-arn); for more speed, add shards (each shard processes in order and an error stops the shard; more shards dilute the impact); if the function does not scale enough, request a quota increase or reserve concurrency
- [from source] (LAMBDA p.693) Permissions: kinesis:DescribeStream, DescribeStreamSummary, GetRecords, GetShardIterator, ListShards, ListStreams, SubscribeToShard (managed policy AWSLambdaKinesisExecutionRole); failure destination: sqs:SendMessage / sns:Publish
- [from source] (LAMBDA p.694) Kinesis ESM options = those of DynamoDB, plus Consumer (optional, for EFO) and Starting position with 3 values: Latest, Trim horizon and At timestamp (from a date/time). Several ESMs are possible; when processing several streams, each batch has records from one shard/stream
- [from source] (LAMBDA p.694) Kinesis charges per shard and, with enhanced fan-out, for the data read [DATED: price]
- [from source] (LAMBDA p.695) CLI: create-event-source-mapping --starting-position AT_TIMESTAMP --starting-position-timestamp 1541139109 (Unix time); for a consumer, provide the consumer ARN instead of the stream ARN; update with --maximum-retry-attempts/--maximum-record-age-in-seconds/--destination-config and --parallelization-factor (p.695-696) [DATED: CLI]
- [from source] (LAMBDA p.696) Error handling identical to DynamoDB (retry until expiry/maximum age/retry quota; split does not count toward the quota; throttle/error without invoking retries until expiry). DIFFERENCE: with the default config a bad record can block the shard for up to ONE WEEK (DynamoDB: one day) [DATED]
- [from source] (LAMBDA p.697) The destination's invocation record carries KinesisBatchInfo (shardId, start/endSequenceNumber, approximateArrival*, batchSize, streamArn), condition RetryAttemptsExhausted; it does not carry the records, which must be fetched from the stream before they expire
- [from source] (LAMBDA p.698) IteratorAge metric same as DynamoDB; tumbling windows identical (state max 1 MB per shard, at-least-once, response must have state, isFinalInvokeForWindow, TumblingWindowInSeconds up to 900, no support for resharding, uses maxRetryAttempts/maxRecordAge) with the KinesisTimeWindowEvent event (p.698-699)
- [from source] (LAMBDA p.700) ReportBatchItemFailures identical (FunctionResponseTypes, batchItemFailures/itemIdentifier = the record's sequence number; the lowest sequence number becomes the checkpoint; total success = empty/null list; total failure = empty/null itemIdentifier/wrong key; bisect at the returned sequence number). Java/Python examples for Kinesis use record.kinesis.sequenceNumber (p.701-702)
- [from source] (LAMBDA p.703) Kinesis parameter table [DATED]: BatchSize 100 (max 10,000); BisectBatchOnFunctionError false; DestinationConfig SQS/SNS; Enabled true; EventSourceArn required (stream or consumer); MaximumBatchingWindowInSeconds 0; MaximumRecordAgeInSeconds -1 (infinite, Lambda does not discard) min -1 max 604,800; MaximumRetryAttempts -1 (infinite) min -1 max 10,000; ParallelizationFactor 1 max 10; StartingPosition AT_TIMESTAMP/TRIM_HORIZON/LATEST; StartingPositionTimestamp (only with AT_TIMESTAMP, Unix seconds); TumblingWindowInSeconds 0-900. NOTE: here MaximumRetryAttempts max is 10,000, different from the DynamoDB table (604800, copy error)
- [from source] (LAMBDA p.706) Tutorial: role with AWSLambdaKinesisExecutionRole; create a stream with 1 shard (create-stream --shard-count 1); describe-stream shows RetentionPeriodHours 24 [DATED: default stream retention]; ESM with --batch-size 100 --starting-position LATEST; ESMs can be disabled to pause polling without losing records; test with aws kinesis put-record (data in base64 via the CLI) (p.703-706)
- [from source] (LAMBDA p.707) The example code does NOT support aggregated records: disable aggregation in the KPL or use the Kinesis Record Aggregation library to deaggregate
- [from source] (LAMBDA p.708) Node/Java/C#/Python/Go examples decode the data field from Base64 (Node Buffer.from, Python base64.b64decode); Java: normal return = batch ok, exception = resend of the same batch (p.708)
- [from source] (LAMBDA p.711) SAM: Events of type Kinesis (Stream: !GetAtt stream.Arn, BatchSize, StartingPosition); for an EFO consumer create AWS::Kinesis::StreamConsumer and use ConsumerARN in Stream (HTTP/2 stream consumer)


## Amazon MQ (p.715-722) - ActiveMQ and RabbitMQ
- [from source] (LAMBDA p.715) The ESM reads messages from the broker and invokes SYNCHRONOUSLY. Restrictions: no cross-account processing; authentication only ActiveMQ SimpleAuthenticationPlugin and RabbitMQ PLAIN, credentials must be in Secrets Manager; there is a broker connection quota per protocol; brokers in a private VPC require the function to have VPC access; only queue-type destinations (virtual topic allowed as a queue); topology: ActiveMQ one single-instance or standby broker per ESM, RabbitMQ one single broker or cluster (single requires a failover endpoint); protocols: ActiveMQ OpenWire/JMS (only TextMessage and BytesMessage), RabbitMQ AMQP 0-9-1
- [from source] (LAMBDA p.716) Amazon MQ's default weekly maintenance window: without standby, Lambda processes nothing during it
- [from source] (LAMBDA p.716) Lambda creates a consumer group with an ID equal to the ESM UUID; batching by window/size up to a 6 MB payload; messages become a base64 BLOB in a single JSON; an error in any message retries the whole batch until success or expiry; maximum function timeout 14 min (like Kafka); monitor the ConcurrentExecutions metric
- [from source] (LAMBDA p.717) Events: ActiveMQ {eventSource aws:mq, messages[{messageID, messageType jms/text-message|jms/bytes-message, destination.physicalName, data base64...}]}; RabbitMQ {eventSource aws:rmq, rmqMessagesByQueue{"queue::/vhost":[{basicProperties, redelivered, data}]}}
- [from source] (LAMBDA p.718) Execution role permissions: mq:DescribeBroker, secretsmanager:GetSecretValue, ec2 (CreateNetworkInterface, DeleteNetworkInterface, DescribeNetworkInterfaces, DescribeSecurityGroups, DescribeSubnets, DescribeVpcs), logs:*; kms:Decrypt if a customer managed key
- [from source] (LAMBDA p.719) MQ trigger options: broker, batch size, queue name, source access configuration (virtual host + secret), enable trigger; reconfigure later only through the ESM APIs. Brokers are created with PubliclyAccessible=false; Lambda assumes the BROKER's VPC config (not the function's); requirements: NAT gateway per public subnet OR VPC-Lambda connection with STS and Secrets Manager endpoints (p.719)
- [from source] (LAMBDA p.720) Minimum security group: inbound all traffic on all ports (from the source SG if the broker is not public, or from everyone if public); outbound all traffic; the VPC config is discovered through the Amazon MQ API and is not passed in create-event-source-mapping. CLI: --queues ExampleQueue --source-access-configuration Type=VIRTUAL_HOST,URI="/" Type=BASIC_AUTH,URI=<secret arn> [DATED: CLI]
- [from source] (LAMBDA p.721) Errors: the ESM stops the consumer on an unrecoverable error; see StateTransitionReason (ESM_CONFIG_NOT_VALID, EVENT_SOURCE_AUTHN_ERROR, EVENT_SOURCE_AUTHZ_ERROR, FUNCTION_CONFIG_NOT_VALID); records above 6 MB are discarded/not processed; for redelivery on error use the broker's DLQ
- [from source] (LAMBDA p.722) Lambda does not support a custom redelivery policy: it uses the ActiveMQ default values with maximumRedeliveries = 5 [DATED]
- [from source] (LAMBDA p.722) MQ parameter table [DATED]: BatchSize 100 (max 10,000); Enabled true; FunctionName required; FilterCriteria; MaximumBatchingWindowInSeconds 500 ms; Queues; SourceAccessConfigurations (ActiveMQ BASIC_AUTH; RabbitMQ BASIC_AUTH + VIRTUAL_HOST)


## Amazon MSK (p.723-)
- [from source] (LAMBDA p.723) MSK as an event source works like SQS/Kinesis: internal polling and SYNCHRONOUS invocation in batches (default 100 messages); Lambda reads sequentially per partition and COMMITS the batch offsets after processing; an error in any message retries the batch until success or expiry; max timeout 14 min; the note points to EventBridge Pipes; event eventSource "aws:kafka" with records by "topic-partition"
- [from source] (LAMBDA p.724) Cluster access options: unauthenticated (only if no client accesses over the internet), SASL/SCRAM (with TLS, credentials in a Secrets Manager secret; MSK does not support SASL/PLAIN), IAM role-based, mTLS
- [from source] (LAMBDA p.725) IAM auth: if the cluster has IAM enabled and you do NOT provide a secret, Lambda uses IAM by default; permissions on the execution role: kafka-cluster:Connect, DescribeGroup, AlterGroup, DescribeTopic, ReadData, DescribeClusterDynamicConfiguration, with cluster, topic and group resources (scopeable)
- [from source] (LAMBDA p.725) mTLS on MSK: Lambda is the client; client cert in a secret; the server cert must be from a CA in AWS's trust store; MSK does NOT support self-signed server certs (brokers use public certs from Amazon Trust Services, which Lambda trusts by default)


## MSK (cont., p.726-733) - differences from self-managed Kafka
- [from source] (LAMBDA p.726) mTLS secret CLIENT_CERTIFICATE_TLS_AUTH same as self-managed (PEM, PKCS #8, PBES1 yes / PBES2 no, client->root chain, Secrets Manager up to 65,536 bytes)
- [from source] (LAMBDA p.727) Choice of bootstrap broker: if there is a secret for mTLS or SASL/SCRAM, it uses that method; without a secret it chooses the strongest active method. Priority order: mTLS, SASL/SCRAM, SASL IAM (no secret and IAM active), unauthenticated TLS, Plaintext. If it cannot connect with the most secure type it does NOT try a weaker one; to force a weaker one you must deactivate the stronger ones on the cluster
- [from source] (LAMBDA p.727) Execution role: managed policy AWSLambdaMSKExecutionRole or custom with kafka:DescribeCluster, kafka:DescribeClusterV2, kafka:GetBootstrapBrokers, network ec2:* (CreateNetworkInterface, DescribeNetworkInterfaces, DescribeVpcs, DeleteNetworkInterface, DescribeSubnets, DescribeSecurityGroups), logs:*; kafka:DescribeCluster will be removed in the future: migrate to DescribeClusterV2
- [from source] (LAMBDA p.728) Error messages in LastProcessingResult as in self-managed (Cluster failed to authorize Lambda, SASL authentication failed, Server failed to authenticate Lambda, Provided certificate or private key is invalid; no "Lambda failed to authenticate server" since MSK uses a public CA). For IAM, the role lacks group/topic permissions (list p.703/725)
- [from source] (LAMBDA p.729) The ACL/IAM topic must match the ESM's topic and the group the ESM UUID; changes take minutes; "SASL authentication failed" with IAM = missing kafka-cluster:Connect on the cluster; it can occur INTERMITTENTLY when the number of TCP connections exceeds the MSK quota: Lambda backs off and retries until it connects and the result changes to OK
- [from source] (LAMBDA p.729) MSK network: PrivateLink endpoints for Lambda and STS (the poller needs STS to assume the execution role and the Lambda endpoint to invoke), plus Secrets Manager if there is a secret; alternative NAT gateway per public subnet; SG inbound/outbound: broker ports 9092 plaintext, 9094 TLS, 9096 SASL, 9098 IAM, and outbound 443 [DATED: ports]; the endpoints' SG must allow inbound 443
- [from source] (LAMBDA p.730) When adding MSK as a trigger Lambda assumes the VPC settings of the MSK CLUSTER and not the function's; the VPC is discovered through the MSK API (do not configure in create-event-source-mapping); prerequisite: MSK cluster and Kafka topic; customizable consumer group ID with the same rules as self-managed (ignores StartingPosition if the group exists; unique; immutable)
- [from source] (LAMBDA p.731) MSK console: type MSK, cluster, batch size, batch window, topic, consumer group ID, starting position, authentication (secret); recommendation: create the trigger disabled for testing (clear Enable trigger). CLI: create-event-source-mapping --event-source-arn <cluster> --topics AWSKafkaTopic --starting-position LATEST --function-name
- [from source] (LAMBDA p.732) MSK auto scaling: same as self-managed (1 initial consumer, up to 1 per partition, evaluation every 1 min, adjustment in up to 3 min); difference: if the function is THROTTLED, Lambda reduces consumers; monitor OffsetLag (p.732)

## SQS (p.772-790) - ESM PATTERN FOR QUEUES (polling)
- [from source] (LAMBDA p.772) The ESM supports standard and FIFO queues; Lambda polls and invokes SYNCHRONOUSLY per batch; when the batch is processed successfully, Lambda DELETES the messages from the queue (the note points to EventBridge Pipes for other targets)
- [from source] (LAMBDA p.772) By default Lambda reads up to 10 messages at a time; batch window up to 5 minutes; before invoking, it keeps reading until the window expires, the payload quota is reached or the maximum batch size is reached [DATED]
- [from source] (LAMBDA p.773) With a batch window and a very low-traffic queue, Lambda may wait up to 20 seconds before invoking, even with a window smaller than 20 s [DATED]
- [from source] (LAMBDA p.773) FIFO: records carry extra attributes (SequenceNumber, MessageGroupId, MessageDeduplicationId)
- [from source] (LAMBDA p.773) Visibility semantics: when the batch is read the messages stay hidden for the queue's visibility timeout; success -> deletion; by default, on error ALL messages in the batch become visible again. Therefore the code must be IDEMPOTENT (process the same message several times without side effects). To avoid reprocessing: batch item failures in the response, or call SQS DeleteMessage when finishing each message
- [from source] (LAMBDA p.774) Standard scaling: long polling; when there are messages it reads up to 5 batches and sends them to the function; if there are still more, it increases the reader processes by up to 60 more instances per minute; maximum of 1,000 simultaneous batches per ESM [DATED]
- [from source] (LAMBDA p.774) FIFO scaling: messages sent in the order received; Message Group ID guarantees order within the group; Lambda sends only ONE batch at a time per group; on error, it tries all the retries for the affected messages before receiving others from the same group; concurrency scales up to the number of active groups
- [from source] (LAMBDA p.774) RULE: source queue visibility timeout >= 6 times the function timeout (slack for retry in case of throttle) [DATED]
- [from source] (LAMBDA p.774) DLQ: configure on the SOURCE queue (redrive policy), NOT on the function; the function's DLQ serves the asynchronous invocation queue, not SQS sources. Set the redrive policy's maxReceiveCount to at least 5, since errors and throttling due to maximum concurrency may succeed on new attempts [DATED]
- [from source] (LAMBDA p.774) Execution role permissions: sqs:ReceiveMessage, sqs:DeleteMessage, sqs:GetQueueAttributes (policy AWSLambdaSQSQueueExecutionRole in the tutorial, p.779)
- [from source] (LAMBDA p.775) Options: batch size default 10 (p.778), standard up to 10,000, FIFO max 10; for batch > 10 MaximumBatchingWindowInSeconds >= 1 s is mandatory; payload limit 6 MB and the metadata adds to the payload and can reduce the number of records per batch; batch window only applies to standard
- [from source] (LAMBDA p.775) With batch window > 0, the recommended visibility timeout is 6 x function timeout + MaximumBatchingWindowInSeconds; if (window + function timeout) > the queue's visibility timeout, the effective visibility becomes window + timeout + 30 s [DATED]
- [from source] (LAMBDA p.775) Lambda processes up to 5 batches at the same time (5 workers) and scales up to +60 instances/min up to 1,000 simultaneous (same numbers as p.774); SQS has a perpetual free tier and charges per million requests; the active ESM makes requests to the queue (cost) [DATED: price]
- [from source] (LAMBDA p.776) Recommendations: function timeout sufficient to process the whole batch; if items are slow, smaller batch; a large batch helps fast workloads/ones with overhead, but on error all items come back; with reserved concurrency, a minimum of 5 concurrent executions to reduce throttling and 1,000 to eliminate the chance (maximum of one SQS ESM) [DATED]
- [from source] (LAMBDA p.776) CLI: create-event-source-mapping --batch-size 5 --maximum-batching-window-in-seconds 60 --event-source-arn <queue> [DATED: CLI]
- [from source] (LAMBDA p.776) ReportBatchItemFailures (SQS): by default, on error all messages in the batch (including those already processed) become visible again; including ReportBatchItemFailures in FunctionResponseTypes makes only the ones that failed come back
- [from source] (LAMBDA p.777) SQS syntax: batchItemFailures[{itemIdentifier: <messageId>}] (here the id is the messageId, not the sequence number); SQSBatchResponse class (Java). The function must catch ALL exceptions and report the failures; if it throws an exception, the whole batch is a complete failure. FIFO: stop at the first error and return all failed and unprocessed messages to preserve order
- [from source] (LAMBDA p.778) Total success: empty/null batchItemFailures, empty/null EventResponse. Total failure (SQS): invalid JSON, itemIdentifier empty, null, with a wrong key OR with a nonexistent messageId
- [from source] (LAMBDA p.778) Monitor the SQS metrics NumberOfMessagesDeleted (dropping to 0 indicates an incorrect failure response) and ApproximateAgeOfOldestMessage (a sharp increase likewise)
- [from source] (LAMBDA p.779) SQS parameter table [DATED]: BatchSize default 10 (standard max 10,000, FIFO max 10); Enabled true; EventSourceArn required; FunctionName required; FunctionResponseTypes (ReportBatchItemFailures); MaximumBatchingWindowInSeconds default 0. There is no retry/maxAge/bisect: retry control belongs to SQS (visibility timeout, redrive)
- [from source] (LAMBDA p.778) ERROR in the text: the SQS table describes EventSourceArn as "The ARN of the data stream or a stream consumer" (text inherited from Kinesis)
- [from source] (LAMBDA p.780) Tutorial: a handler that returns normally = message processed and deleted; exception = batch not processed and the function is invoked again with the same batch; role AWSLambdaSQSQueueExecutionRole
- [from source] (LAMBDA p.785) Cross-account SQS tutorial (account A = function, account B = queue): the queue policy in account B grants the execution role from account A (AWS principal) access (in the example "sqs:*" - too broad, a least privilege antipattern); the ESM is created in account A pointing to the queue ARN in account B; the function's execution role has AWSLambdaSQSQueueExecutionRole (p.783,785)
- [from source] (LAMBDA p.790) SAM: Events of type SQS (Queue: !GetAtt MySqsQueue.Arn, BatchSize: 10)


## SYNTHESIS: common event source mapping pattern (stream/queue) and differences (derived from the pages above)
- [from source] (LAMBDA p.588) Who grants what: with polling (SQS, Kinesis, DynamoDB, Kafka/MSK, MQ) the permission is the function's EXECUTION ROLE to read from the source; with push events (S3, SNS, API Gateway, ALB, EventBridge, Lex, IoT) the permission is the function's RESOURCE-BASED POLICY for the service principal (with source-arn/source-account)
- [from source] (LAMBDA p.590) In streams the ESM invokes synchronously; it does not require granting Lambda permission to invoke, only to read
- [from source] (LAMBDA p.644) Maximum batch size 10,000 in DynamoDB, Kinesis, Kafka, MQ and SQS standard (FIFO max 10); default 100 (DDB, Kinesis, Kafka, MSK, MQ) and 10 (SQS); the 6 MB synchronous payload limit applies to all [DATED]
- [from source] (LAMBDA p.644) Batching window: streams and SQS standard up to 5 minutes (MaximumBatchingWindowInSeconds; Kafka and MQ have a default of 500 ms); the batch is sent when full, the window expires or the payload reaches 6 MB [DATED]
- [from source] (LAMBDA p.648) Error handling in streams (DynamoDB/Kinesis): batch retry until success/expiry; controls: MaximumRetryAttempts, MaximumRecordAgeInSeconds, BisectBatchOnFunctionError, DestinationConfig.OnFailure (SQS/SNS, metadata without the records' payload), ReportBatchItemFailures (checkpoint at the lowest failed sequence number), TumblingWindow; shard blocked for up to 1 day (DDB) or 1 week (Kinesis) by default
- [from source] (LAMBDA p.774) Error handling in SQS: there is no retry in the ESM; control belongs to SQS (visibility timeout >= 6x function timeout, maxReceiveCount >= 5, DLQ on the source queue) and ReportBatchItemFailures by messageId; Kafka/MSK/MQ: an error retries the whole batch until success/expiry and the consumer stops; max timeout 14 min; messages > 6 MB are lost
- [from source] (LAMBDA p.774) Scaling: SQS standard 5 initial batches +60/min up to 1,000; FIFO by message groups; Kinesis/DDB per shard (ParallelizationFactor 1-10 per shard); Kafka/MSK 1 initial consumer up to 1 per partition (evaluation every minute, adjustment in up to 3 min)
