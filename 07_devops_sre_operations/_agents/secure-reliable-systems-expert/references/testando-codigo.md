## Ch. 13 — Testing code (BSRS p.307-338)

### Premise (BSRS p.307-308)
- [from source] A reliable system withstands failures and meets documented SLOs, which may include security guarantees; testing and analysis are aids and should be a focus of the implementation; unexpected inputs cause data corruption or unavailability (the "Query of Death" example from the SRE book) and code errors cause buffer overflow and XSS (BSRS p.307). The techniques have distinct cost-benefit profiles; fuzzing helps security and reliability; for systems that cannot be fixed quickly, it is necessary to test well beforehand (BSRS p.307-308).

### Unit testing (BSRS p.308-311)
- [from source] Self-contained units, without external dependencies, tested with inputs chosen by the engineer; xUnit frameworks (JUnit, GoogleTest, go2xunit, Python's unittest) with common setup/teardown and a standardized result format; they run locally and in CI/CD before merging into the mainline (BSRS p.308).
- [from source] Tests should be fast, reliable, and hermetic (they must reproduce the same results in an isolated environment; see Ch.9 of the book); storage quota system example: security tests for negative values, capacity overflow at values near the type's limit, and error messages for malicious or malformed input; parameterized tests reduce boilerplate (BSRS p.308-309).
- [from source] When to write them: right after the code, in the same commit (translating requirements such as "only billing administrators of the group can request quota"); reviewers can check whether the tests would pass even without the new code (replacing a condition with if (false) or if (true) without anything failing indicates insufficient tests: mutation testing, automated at Google, Petrović and Ivanković 2018); TDD writes the tests first; in legacy projects, increase coverage gradually as bugs arise; even with full coverage there is no absence of bugs; regression tests in response to security reviews and fixes, important when the code is hard to reason about and affects security (access control checks with a complex permission model); more time is often spent writing tests than code, which pays off (BSRS p.309-310).
- [from source] Effect on code: design or refactor to intercept calls to external systems (example: opening tickets in a remote issue tracker; abstract into an IssueTrackerService interface with a test implementation that records calls and a production implementation); this reduces flakiness; a flaky test must be fixed, otherwise developers ignore results; mocks, stubs, and fakes are terms used interchangeably but differ: standardize vocabulary; beware of overabstraction (tests that assert call order and "test" the language's control flow); fakes provided by the team that owns the service preserve realism (BSRS p.310-311).
- [from source] Correctness validation: suites that compare implementations (GCC's torture test; Wycheproof test vectors for cryptographic algorithms via the Java Cryptography Architecture, usable in other languages; suites that exercise each RFC rule for parsing media formats, useful for replacing parsers) (BSRS p.311-312).

### Integration testing (BSRS p.312-313)
- [from source] Replaces fakes with real implementations (database, network service); slower and more flaky, exercises more complete paths and gives greater confidence; formats vary with complexity (base class that sets up a database in a known state; dependency orchestration; at Google, teams dedicated to standardized setup infrastructure); in CI (such as Jenkins) they can run together with or separately from the unit tests (BSRS p.312). Apply Ch.5: do not mirror real databases into test environments (sensitive data accessible to whoever runs tests, violating least privilege); use non-sensitive test data, which makes it easier to clean the environment to a known state and reduces flakiness (BSRS p.313). Example: use the issue tracker's QA endpoint instead of creating bugs in production, with supervisory logic that verifies external actions; good logging at logical points to debug integration failures; the types of tests do not replace each other (BSRS p.313).

### Dynamic program analysis (BSRS p.313-316)
- [from source] Dynamic analysis executes the program, including in virtualized or emulated environments, beyond testing: profilers and coverage reports are the best known; Valgrind (a VM that interprets the binary) already presented; focus on compiler instrumentation (BSRS p.313-314). Google Sanitizers (LLVM, now also in GCC): ASan (out-of-bounds accesses etc.), UBSan, TSan, MSan, LSan; proposals to use hardware memory tagging to speed up ASan; ASan uses shadow memory, instructions inserted by the compiler, and its own malloc/free implementations with red zones ("poisoned" regions) before and after the allocated region; freed memory is also poisoned, detecting use-after-free (BSRS p.314-315). Example run with clang -fsanitize=address (BSRS p.315-316).
- [from source] Performance tradeoff: instrumented binaries can be orders of magnitude slower; add pipelines with sanitizers to CI/CD running less frequently (for example, nightly), along with coverage metrics (BSRS p.316).

### Fuzzing (BSRS p.316-326)
- [from source] A fuzz engine generates many candidate inputs passed by a fuzz driver to the fuzz target; popular targets: file parsers, compression, network protocols, audio codecs (BSRS p.316). Benefits: finding memory corruption bugs with security implications, inputs that trigger exceptions in Java and Go causing cascading DoS, testing service resilience; chaos engineering injects failures such as latency and outages (Netflix's Simian Army as an early example, with parts integrated into tools such as Spinnaker); fuzzing to compare implementations (crash on different outputs, as in OpenSSL's BigNum fuzzer); since fuzzing can run indefinitely, not every commit is blocked on it, so it complements other tests and the inputs that found bugs become regression tests (BSRS p.316-317).
- [from source] How they work: dumb fuzzing (random bytes) vs. smart engines integrated into the compiler (coverage-guided); use as many engines as you can integrate and monitor % coverage (if it plateaus, investigate); keyword dictionaries from grammars (HTTP, SQL, JSON) to reach relevant code; engines such as Peach Fuzzer let you define the format and relationships between fields; seed corpus (representative samples; files from existing tests, or corpora published by OSS-Fuzz, The Fuzzing Project, AFL); coverage-guided engines preserve samples that find new paths; afl-gcc and go-fuzz-build for instrumentation; crashes in code with a sanitizer record the input and metadata (stack trace, memory layout) for prioritization (for example, a write violation is more critical than a read) (BSRS p.317-318). Consistent events signal bugs to the engine; a time limit per input categorizes infinite loops and deadlocks as crashes, helping avoid DoS (BSRS p.319).
- [from source] "Known safe" functions: benign bugs can prevent fuzzing (e.g., signed integer overflow in C++ triggering UBSan with no consequence) and hinder reaching deeper code; if it cannot be fixed (unsigned types, clamp), manually annotate the function with no_sanitize after careful review (may produce false negatives) (BSRS p.319). Heartbleed (CVE-2014-0160) can be found quickly with the right driver and sanitizer; Google's fuzzer-test-suite has an example; ASan report with heap-buffer-overflow (BSRS p.319-320). Limits: hand-written assembly is not instrumented; fuzzing without sanitizers reduces detection of invalid states; binary-only libraries: emulators such as QEMU with AFL (slower and with less assistance) (BSRS p.320-321). Modern engines: libFuzzer, AFL, Honggfuzz; a single driver can serve several; periodically transfer interesting samples from each engine to the others' seed corpus (BSRS p.321).
- [from source] Effective drivers: interface LLVMFuzzerTestOneInput(const uint8_t *data, size_t size); avoid nondeterministic behavior, slow operations (console logging, disk I/O; use "fuzzer-friendly" builds or an in-memory filesystem), and intentional crashes; avoid integrity checks (CRC32, digests) that the engine cannot satisfy; preprocessor flag convention such as -DFUZZING_BUILD_MODE_UNSAFE_FOR_PRODUCTION (BSRS p.321-322).
- [from source] Example fuzzer for the Knusperli JPEG decoder (Bazel, .bazelrc with an asan configuration, driver jpeg_decoder_fuzzer.cc): synthetic corpus vs. a corpus with one image of colored bars (>10% coverage improvement); exploring the JpegReadMode parameter by hashing part of the input or splitting the input (FuzzedDataProvider or initial bytes as parameters): a hash can change the configuration drastically with one bit; splitting lets the engine track the relationship between options and behavior; beware of the usability of existing seeds; results with coverage and executions per second; on finding a sanitizer error, reproduce with the saved artifact (BSRS p.322-325).
- [from source] Continuous fuzzing: a daily build pipeline generates fuzzers consumed by a system that runs them, collects crashes, and opens bugs; ClusterFuzz (Google's open source; manages VM pools, web interface, corpus management, crash deduplication by program state, periodic retesting, and automatic issue closing; does not build fuzzers; in early 2020 supports libFuzzer and AFL); OSS-Fuzz (ClusterFuzz distributed on GCP; in five months since Dec/2016 it found more than a thousand bugs and later tens of thousands; finds problems hours after modified code enters the upstream repository; single flow at Google) (BSRS p.325-326). [DATED] Numbers and engine support are from 2020.

### Static program analysis (BSRS p.326-337)
- [from source] Static analysis inspects the source code without executing it; tradeoffs between depth and cost (from textual or AST pattern matching to reasoning about semantics, control flow, and data flow) and between false positives and negatives; fundamental limit: statically verifying any program is undecidable; integration into code review targets only new code with precise warnings; release of safety-critical software (avionics, medical devices) requires more formal analysis (BSRS p.326-327).
- [from source] Automated code inspection tools (linters): syntactic, shallow, scalable (time close to compiling) and extensible; they focused on style and readability due to high acceptance; Error Prone (Java) and Clang-Tidy (C/C++) allow custom checks (early 2018: 162 authors, 733 checks in Error Prone) and suggest fixes; C++ core guidelines with GSL; examples of AST pattern matching: absl-string-find-startsWith, memcpy with sizeof of a pointer (warning); modernize-use-nullptr with --fix; GoVet, Pylint; Error Prone example with CollectionIncompatibleType (BSRS p.327-332).
- [from source] Integration into the development workflow: run fast static analysis as early as possible (the cost of fixing rises after commit or deploy); low barrier in CI/CD; Tricorder (and the open version Shipshape): analyzes ~50,000 changes per day in code review, 146 analyzers across more than 30 languages (early 2018), goal of a perceived false positive rate of at most 10% with "Not useful" feedback to turn off checks and "Please fix"; fixes applicable with one click (BSRS p.332-334). [DATED] 2018 numbers.
- [from source] Reverse engineering and test input generation: decompilers and disassemblers (Ghidra) to understand suspicious binaries; concolic testing (concrete execution with symbolic analysis and a constraint solver) generates inputs that cover other paths; KLEE as a tool (BSRS p.334-335).
- [from source] Abstract interpretation (deep static analysis): static semantic analysis, used in critical software (flight control); example of the interval domain [2, 20] and imprecision (false positive for the value 11); uses a CFG with basic blocks; it is slow, generally runs occasionally (nightly) or differentially in code review; tools: Frama-C, Infer, AbsInt; Google Play's ASI program (interprocedural analysis of each submitted Android app; early 2019: more than a million fixes by more than 300,000 developers) (BSRS p.335-336).
- [from source] Formal methods: specify properties (safety: something bad never happens; liveness: something desired eventually happens); verify for systems or models, or develop correct by construction; high upfront cost (mathematically rigorous specification); standard in hardware design and used in specialized domains (TLS cryptographic protocols analyzed continuously) (BSRS p.337).
- [from source] Conclusion: integrate all methods into engineering workflows and CI/CD; design for testability from the start (BSRS p.338).
