# TLS: handshake, resumption, ALPN, SNI, records and optimization

Sole source: *High Performance Browser Networking* (Grigorik, 2013), chapter 4. Cited pages are the PDF pages (printed = PDF − 18). The book covers SSL 3.0 through TLS 1.2; there is no TLS 1.3 in it. What the book presented as new in 2013 is marked [DATED].

---

## 1. Fundamentals

- SSL was born at Netscape, implemented at the application layer, directly on top of TCP, so that HTTP, email and other protocols worked without changes. When used properly, a third-party observer can only infer the endpoints, the cipher type and the frequency and approximate volume of data (HPBN p.65).
- Versions (HPBN p.66): SSL 2.0 was quickly replaced by SSL 3.0 because of flaws; the IETF standardized it as TLS 1.0 (RFC 2246, January 1999); TLS 1.1 in April 2006; TLS 1.2 in August 2008.
- TLS was designed for reliable transport such as TCP; DTLS (RFC 6347) adapts it to datagrams (HPBN p.66).
- Three services: encryption (obscuring the content), authentication (verifying the identity presented) and integrity (detecting tampering and forgery). In principle one can do without some, but a secure web application uses all three (HPBN p.66, p.67).
- The key to the handshake is public-key cryptography: the peers agree on a shared secret without prior knowledge and over an open channel (HPBN p.67). The server can optionally validate the client, for example with a certificate for each employee (HPBN p.67).
- Each TLS record gets a MAC (a one-way hash function with negotiated keys), which lets the receiver check integrity and authenticity (HPBN p.67).

### Intermediaries and why new protocols use HTTPS
- Proxies and intermediaries on port 80 may forward HTTP extensions badly, or block them; the result is unpredictable deployment. That is why WebSocket, SPDY and similar protocols usually establish an HTTPS tunnel, which hides the data from intermediaries. The cost is losing useful services they provide (authentication, caching, security scanning) (HPBN p.68).
- This is the reason WebSocket guides recommend HTTPS for mobile clients; over time and with intermediaries being updated, the requirement diminishes, unless the session actually needs TLS's guarantees (HPBN p.68).

## 2. Full TLS handshake and cost in RTTs

Before any data flows, it is necessary to agree on the TLS version, choose the ciphersuite and verify certificates; each step spends round trips (HPBN p.68). The book's timeline (New York–London, 28 ms one-way in fiber) (HPBN p.69, p.70):

| Time | Event |
|---|---|
| 0 ms | TCP handshake (1 full RTT) |
| 56 ms | Client sends, in clear text, the TLS version, list of ciphersuites and options |
| 84 ms | Server chooses version and ciphersuite, attaches the certificate and replies; optionally requests the client's certificate |
| ~112 ms (interval omitted in the extracted text; inferred) | Client accepts the certificate, generates a symmetric key, encrypts it with the server's public key and asks to switch to encrypted communication |
| 140 ms | Server decrypts the key, checks the MAC and returns an encrypted "Finished" |
| 168 ms | Client decrypts, checks the MAC; tunnel ready, application data can be sent |

- A new connection requires two round trips for the "full handshake"; the "abbreviated handshake" requires one (HPBN p.70).
- Each TLS connection costs up to two more round trips on top of TCP; without care, this adds up to hundreds to thousands of milliseconds (HPBN p.70).
- Worst case: three round trips before any data (one for TCP, two for TLS). With an RTT of 56 ms: 168 ms for full TCP+TLS; 112 ms with resumed TLS (HPBN p.83). The numbers grow with RTT, and 56 ms is optimistic (HPBN p.83).
- In the book's model, the symmetric key is generated by the client and sent encrypted with the server's public key (HPBN p.69, p.70).

### Public vs. symmetric key
- Public-key cryptography is used only for establishment; afterwards, all communication uses the symmetric key, because asymmetric is much more expensive (HPBN p.70).
- Suggested comparison: `openssl speed rsa` and `openssl speed aes`. The units differ (operations/s vs. bytes/s), but the number of RSA operations with 1,024- or 2,048-bit keys (the sizes recommended at the time) tends to be the bottleneck; run the tests on your own hardware, do not trust outdated benchmarks (HPBN p.71) [DATED].

## 3. Session resumption (TLS Session Resumption)

The cost of the full handshake is high in latency and CPU; TLS allows reusing the secret already negotiated between connections (HPBN p.73). Most browsers wait for the first TLS connection to finish before opening others to the same server, so they can reuse the session (HPBN p.74). Since the page opens several parallel connections to the same host, resumption is an indispensable optimization (HPBN p.74).

### Session Identifiers (session caching)
- Introduced in SSL 2.0 (the book cites RFC 5246): the server generates a 32-byte identifier in the ServerHello of the full negotiation and keeps a cache of IDs and negotiated parameters per peer (HPBN p.73).
- The client stores the ID and sends it in the next ClientHello. If both find the parameters in their caches, the abbreviated handshake occurs; otherwise, a full negotiation generates a new ID (HPBN p.73).
- Gain: eliminates one whole round trip and the cost of public-key cryptography, with no loss of security (HPBN p.74).
- Limitation: the server must keep a per-client session cache. This means memory per connection, cache and eviction policy, and difficulties on sites with many servers, which ideally share a session cache (HPBN p.74, p.75).

### Session Tickets (RFC 5077) [DATED: "relatively new", HPBN p.85]
- Removes the per-client state on the server. If the client indicates support, in the last exchange of the full handshake the server includes a New Session Ticket record with the session data encrypted by a key only the server knows (HPBN p.75).
- The client stores the ticket and sends it in the SessionTicket extension of the next ClientHello (HPBN p.75).
- They are called, respectively, session caching and stateless resumption. The gain is removing the server-side cache; it holds as long as the ticket has not expired (HPBN p.75).
- In load-balanced environments, all servers must be initialized with the same session key, and a mechanism may be needed to rotate it periodically (HPBN p.75).

### Configuration checklist (HPBN p.85)
- Do not assume session support is on; on many servers it is off by default.
- Servers with several processes/workers should use a shared session cache.
- Size the cache according to traffic and set a session timeout.
- On multiple servers: route the same client IP (or the same session ID) to the same server; if that is not possible, use a shared cache.
- Monitor the TLS session cache statistics.
- Enable tickets and identifiers at the same time: tickets for those that support them, IDs as a fallback for old clients (HPBN p.85).

## 4. ALPN (Application-Layer Protocol Negotiation)

### Problem it solves
- Dedicated ports per protocol are slow to get approved, and firewalls and intermediaries generally only let ports 80 and 443 through (HPBN p.71). The protocol must be negotiated over these ports.
- On port 80, HTTP's Upgrade mechanism costs an extra round trip and is unreliable with intermediaries. On 443, the encrypted tunnel hides the data and makes deployment reliable, but the protocol still has to be negotiated (HPBN p.71). Reusing Upgrade inside HTTPS would cost another full round trip (HPBN p.71).

### Procedure (HPBN p.72)
1. The client adds to the ClientHello the ProtocolNameList field, with the application protocols it supports.
2. The server reads the list and returns, in the ServerHello, the ProtocolName field with the chosen protocol. It replies with only one name; if it supports none, it may abort.
3. Once the handshake is done, the tunnel is ready and both ends already agree on the protocol: they can speak immediately.

- ALPN eliminates the extra round trip of Upgrade; the TLS handshake is still necessary. That is, negotiating via ALPN is not faster than Upgrade on an open channel; it only guarantees that negotiating over TLS is not slower (HPBN p.72).

### NPN and ALPN
- NPN (Next Protocol Negotiation) was born from SPDY, at Google, with an equivalent goal. In NPN the server announced the protocols and the client chose; in ALPN the order was inverted: the client lists and the server selects and confirms, aligning with other negotiation standards (HPBN p.72).
- ALPN is the revised version approved by the IETF; NPN is obsolete and clients/servers that depend on it need to migrate (HPBN p.72) [DATED]. ALPN's role in enabling HTTP/2 is discussed in [http2-binary-framing-multiplexing-e-streams.md](http2-binary-framing-multiplexing-e-streams.md); the book refers to HTTP/2's Upgrade flow in "Efficient HTTP 2.0 Upgrade and Discovery" (HPBN p.71, p.242).

## 5. SNI (Server Name Indication)

- A TLS tunnel can be made with any TCP peer, by IP alone. But, without other information, a server with several sites on the same IP, each with its own certificate, cannot choose the right certificate. The book answers that, in this case, it simply does not work (HPBN p.72, p.73).
- The SNI extension lets the client indicate, at the start of the handshake, the hostname it wants; the server reads the name, selects the certificate and continues (HPBN p.73).
- It is TLS's equivalent of HTTP's Host header: both are needed to distinguish domains on the same IP (HPBN p.73).
- Old clients do not support SNI (most IE versions on Windows XP, Android 2.2 and others). To serve them over TLS a dedicated IP per host may be needed (HPBN p.73) [DATED].

## 6. Chain of trust and revocation

### Chain of trust
- Authentication is indispensable: you can encrypt a conversation with an attacker; the effort is worthless if you do not know who you are talking to (HPBN p.75).
- The model is one of transitive trust (Alice, Bob, Charlie example): Alice trusts Bob's signature on Charlie's key (HPBN p.76).
- The web uses the same process. Whom the browser trusts: manually imported certificates; certificate authorities (CAs), third parties trusted by both parties; and the list of CAs that the operating system and browser already ship with (HPBN p.76, p.77).
- The browser defines the root CAs; it is up to the CAs to verify, audit and revoke compromised certificates (HPBN p.77). The trust anchor is the root CA (in the book's example, igvita.com → StartCom intermediate → StartCom root) (HPBN p.78).
- There are hundreds of trusted CAs, which is a common criticism: it increases the attack surface (HPBN p.78).

### Revocation
- Reasons: compromised private key, compromised CA or soft reasons such as certificate replacement; the certificate carries instructions on how to check revocation (HPBN p.79).
- **CRL (RFC 5280)**: the CA periodically publishes a list of revoked serial numbers; the client downloads it and checks. Problems: the list only grows and each client downloads all of it; there is no instant notification, and a cached CRL considers a revoked certificate valid until the cache expires (HPBN p.79, p.80).
- **OCSP (RFC 2560)**: real-time query for just the serial number in question; uses less bandwidth and gives real-time validation. Problems: the CA must withstand the load and be always available; the client blocks navigation waiting for the query; and the CA comes to know which sites the client visits (privacy) (HPBN p.80).
- CRL and OCSP are complementary, and browser behavior varies (they provide their own lists or download from the CA; they diverge when OCSP fails) (HPBN p.80).

## 7. TLS Record Protocol

- All data in TLS is framed into records; the Content Type field distinguishes handshake, alert and data (HPBN p.80).
- Send flow (HPBN p.81): application data is split into blocks of at most 2^14 bytes (16 KB); is optionally compressed; gets a MAC/HMAC; is encrypted; goes to TCP. At the receiver, the flow is reversed.
- Implications (HPBN p.81): the maximum record is 16 KB; each record has a 5-byte header, a MAC (up to 20 bytes in SSLv3, TLS 1.0 and 1.1; up to 32 bytes in TLS 1.2) and padding if the cipher is a block cipher; and the record must be complete to be decrypted and verified.
- Small records have more framing overhead; large records must be delivered and reassembled by TCP before TLS processes them (HPBN p.81).

## 8. Optimizing TLS

If the TCP best practices have already been applied, the application practically does not change; what is investigated is operational: where to deploy servers, record and buffer sizes, certificate size and abbreviated handshake support (HPBN p.81, p.82). See the TCP foundation in [fundamentos-tcp-e-gargalos-de-transporte.md](fundamentos-tcp-e-gargalos-de-transporte.md).

### Computational cost
- Asymmetric cryptography (the handshake) is expensive and used to require dedicated "SSL offloading" hardware; today it runs on the CPU. Google and Facebook serve hundreds of millions of users with TLS in software on commodity hardware (HPBN p.82).
- Gmail numbers from January 2010 (testimony of Adam Langley): TLS takes less than 1% of CPU, less than 10 KB of memory per connection and less than 2% network overhead (HPBN p.82) [DATED].
- Even so, session resumption remains important to save CPU and latency; update the SSL libraries (for example, OpenSSL) and recompile the server against them (HPBN p.83).

### Early termination (terminating TLS close to the user)
- Idea: shorten the distance, since the packet cannot travel faster. A nearby server terminates TCP and TLS, and keeps a pool of long-lived secure connections to the origin, forwarding the requests (HPBN p.83, p.84).
- CDNs offer this; you can also build your own infrastructure (cloud servers in a few data centers, a proxy in each, DNS with geographic load balancing) (HPBN p.84).
- "Uncached origin fetch": even non-cacheable (personalized) content benefits, since the client's handshake is with the nearby node and it uses a pool of warm connections to the origin (HPBN p.84, p.85). Some CDNs use nodes close to both sides, traveling over the CDN's optimized backbone (HPBN p.85).
- Reusing the connection is even more critical under TLS: if you can avoid the handshake, avoid it (HPBN p.83).

### TLS record size
- Each record adds 20 to 40 bytes of overhead (header, MAC, padding). If it fits in one TCP packet, add 20 bytes of IP and 20 of TCP without options: 60 to 100 bytes per record. On a typical 1,500-byte MTU, this gives at least 6% overhead (HPBN p.86).
- A very large record crosses several TCP packets; if one is lost, arrives out of order or is held by congestion control, the fragments stay buffered, adding latency. The book shows a capture of an 11,211-byte record split into 8 TCP segments (HPBN p.86).
- Small records generate overhead, large ones generate latency. Rule for the web: one TLS record per TCP packet, filling the whole MSS (HPBN p.86).
- Calculation (HPBN p.87): 20 bytes of IPv4 (40 for IPv6) + 20 of TCP + 40 of TCP options (timestamps, SACK). With an MTU of 1,500, 1,420 bytes remain for the record on IPv4 and 1,400 on IPv6. Use 1,400 bytes, or less if the MTU is smaller.
- This size is not configured by the application, but on the TLS server (sometimes a compile-time constant) (HPBN p.87).
- Memory per connection: OpenSSL allocates up to 50 KB by default; Google's servers reduced the buffers to about 5 KB (HPBN p.87).

### TLS compression
- Turn it off on the server. Reasons: the CRIME attack (2012) uses TLS compression to recover authentication cookies and hijack sessions; and transport-level compression does not know the content and recompresses already-compressed data (HPBN p.87) [DATED].
- Instead, use Gzip for text and appropriate formats for image, video and audio (HPBN p.88).

### Certificate chain size
- Include all intermediate certificates. If they are missing, many browsers fetch the intermediate on their own, which may require DNS, TCP and HTTP GET, adding hundreds of milliseconds (HPBN p.88).
- Do not include unnecessary certificates. The chain travels on a new TCP connection, still in slow-start; if it exceeds the initial cwnd, it adds a round trip. The book shows a 5,323-byte chain (HPBN p.88), which overflows the initial cwnd of old servers (HPBN p.89).
- Recommendations (HPBN p.89): the ideal chain has exactly two certificates (the site's and the CA's intermediate); minimize the number of intermediate CAs (a criterion for choosing the CA); the root certificate is already in the browser and must not be sent (including it does not make it trusted); a well-managed chain can stay at 2 to 3 KB.
- Raising the initial cwnd also helps (HPBN p.89).

### OCSP stapling
- Revocation checking varies widely across browsers: some use their own CRL update mechanisms; some only do real-time OCSP/CRL for EV certificates; some block the handshake, others do not (HPBN p.89).
- In *stapling*, the server attaches the CA's OCSP response to the chain, allowing the browser to skip the online query; the server caches the signed response and saves the request of many clients (HPBN p.89, p.90).
- Cautions (HPBN p.90): the OCSP response ranges from 400 to 4,000 bytes and can overflow cwnd; only one response can be attached, so the browser may still query for other intermediates.
- Nginx, Apache and IIS support stapling (HPBN p.90).

### HSTS (HTTP Strict Transport Security)
- Policy declared by header; book example: `Strict-Transport-Security: max-age=31536000` (HPBN p.90). Rules enforced by the user agent (HPBN p.90):
  - all requests to the origin go over HTTPS;
  - insecure links and requests are converted to HTTPS on the client, before sending;
  - on a certificate error, the warning is shown and the user cannot bypass it;
  - `max-age` is the rule's lifetime in seconds (31536000 = 365 days);
  - optionally, the UA may "pin" a host's fingerprint in the chain, limiting the authorities that can authenticate it.
- In performance, it eliminates HTTP→HTTPS redirects by moving the conversion to the client (HPBN p.90).
- Support in early 2013: Firefox 4+, Chrome 4+, Opera 12+ and Chrome/Firefox for Android (HPBN p.90) [DATED].

## 9. Performance checklist (HPBN p.91)

- Apply the TCP best practices.
- Update the TLS libraries and rebuild the servers against them.
- Enable and configure session caching and stateless resumption; monitor the hit rate.
- Terminate TLS sessions close to the user.
- Tune the TLS record to fit in one TCP segment.
- Ensure the certificate chain does not overflow the initial cwnd; remove unnecessary certificates and minimize the depth.
- Turn off TLS compression.
- Configure SNI.
- Configure OCSP stapling.
- Send the HSTS header.
- As a developer, do not mix HTTP and HTTPS content on pages (HPBN p.91).

### Testing and verification
- Use a service such as the Qualys SSL Server Test and the `openssl` command-line client (HPBN p.91).
- Book example: `openssl s_client -state -CAfile startssl.ca.crt -connect igvita.com:443`. The root must be provided manually, since s_client does not assume known roots (HPBN p.91, p.93).
- In the sample output: the server sent 2 certificates, totaling 3,571 bytes (close to the initial cwnd of 3 to 4 segments, so be careful not to overflow it); the session issued a session ID for stateful resumption; `Timeout: 300 (sec)`; protocol TLSv1 and cipher RC4-SHA, which are from the example of the time [DATED] (HPBN p.92, p.93).

## After the book [extrapolation]
- **TLS 1.3 (RFC 8446)**: the full handshake now costs 1 TLS RTT, and there is resumption with data in 0-RTT (early data) with pre-shared keys, at the cost of replay risk. This reduces the three worst-case round trips described above, but is not part of the book. TLS compression was removed.
- The RFC numbers for ALPN (7301), SNI (6066, part of the TLS extensions), OCSP stapling (6066) and HSTS (6797) do not appear in the book; HSTS's `includeSubDomains` and `preload` directives are also later than the book's example.
- In HTTP/3, TLS 1.3 is integrated into QUIC, and the transport and cryptographic handshakes happen together.

## What the source does not cover
- TLS 1.3, 0-RTT, early data, QUIC and HTTP/3.
- Ephemeral key exchange (ECDHE/forward secrecy) and modern AEAD suites; the book describes the symmetric key encrypted with the server's public key.
- Certificate Transparency, OCSP Must-Staple, ECH/ESNI (SNI is sent in the clear).
- Details of session ticket key rotation beyond the warning that it must exist (HPBN p.75).
- Current recommendations on versions and ciphers (the book's example uses TLSv1 and RC4-SHA).
- Adoption and performance data after 2013.
