# The Dependency Rule and the concentric circles (The Clean Architecture, 2012)

Source: Robert C. Martin, **"The Clean Architecture"**, post on The Clean Code Blog, August 13, 2012 (acronym `CA12`; 15-page PDF, browser printout). Content on **p.1-7**; p.8-15 are only the blog sidebar (titles/dates). The circular diagram cited by the text ("the diagram at the top of the article") is **not legible in the PDF** (it is an image that was not extracted); the layer names come from the text.

**Convention**: `(CA12 p.N)` = PDF page (no printed numbering). Labels: `[from source]`, `[inference]`, `[extrapolation]`, `[DATED]`.

---

## 1. Starting point: several architectures, one goal

- The text lists earlier architectures: Hexagonal (Ports and Adapters, Alistair Cockburn), Onion (Jeffrey Palermo), "Screaming Architecture" (an earlier post of his), DCI (Coplien and Reenskaug) and BCE (Ivar Jacobson) `[from source] (CA12 p.1-2)`.
- All have the same goal, the **separation of concerns**, achieved by dividing the software into layers, with at least one layer for business rules and another for interfaces `[from source] (CA12 p.2)`.
- The systems they produce are, according to the text: (1) independent of frameworks, (2) testable (rules tested without UI, database, web server etc.), (3) independent of the UI, (4) independent of the database, (5) independent of any external agency `[from source] (CA12 p.2)`.
- The diagram is an attempt to integrate these architectures into a single actionable idea `[from source] (CA12 p.2)`.

## 2. The Dependency Rule

- The concentric circles represent different areas of software; in general, the further in you go, the higher level the software becomes. **Outer circles are mechanisms; inner circles are policies** `[from source] (CA12 p.3)`.
- **The rule**: source code dependencies can only point inward. Nothing in an inner circle can know anything at all about something in an outer circle; in particular, the **name** of something declared in an outer circle must not be mentioned by the code in an inner circle (functions, classes, variables or any other named entity) `[from source] (CA12 p.3)`.
- Data formats used in an outer circle should not be used by an inner one, especially if generated by an external framework `[from source] (CA12 p.3)`.

## 3. The layers described

| Circle (text) | What the text says | Page |
| :--- | :--- | :---: |
| **Entities** | Encapsulate **enterprise-wide** business rules; can be objects with methods or sets of data structures and functions, as long as they are reusable by many applications in the enterprise. If there is no "enterprise", they are the application's business objects. They are the least likely to change when something external changes (page navigation, security). | p.3 |
| **Use Cases** | **Application-specific** business rules; they encapsulate and implement the use cases, orchestrating the flow of data to and from the entities and directing them to use their rules to achieve the goals of the use case. Changes in this layer must not affect the entities, nor should changes in the database, UI or frameworks affect it; changes in the operation of the application affect the use cases. | p.3-4 |
| **Interface Adapters** | Adapters that convert data from the format most convenient for use cases and entities to the one most convenient for an external agency (database, web). Contains the whole MVC architecture of a GUI (Presenters, Views, Controllers). Data is converted here to the form of the persistence framework; all SQL must be confined to this layer; nothing further inward should know about the database. Adapters for external services also live here. | p.4-5 |
| **Frameworks and Drivers** | The outermost layer: frameworks and tools (database, web framework). In general only "glue" code is written for the next circle. This is where the details go: "the Web is a detail, the database is a detail; we keep these things on the outside where they can do little harm". | p.5 |

- **Only four circles?** The text says the circles are **schematic**: you may need more than four; the Dependency Rule always applies. Moving inward, the level of abstraction increases; the outermost circle is low-level concrete detail; the innermost is the most general `[from source] (CA12 p.5)`.
- The text does not contain the word "POJO/POCO", "Gateways" as a named layer, "Ports & Adapters" as a mechanism of this architecture, nor the "Presenters/ViewModels" subdivision with "Input DTOs": these are terms from secondary material `[extrapolation]`. The text says the GUI **models** are probably just data structures passed from controllers to use cases and from these to presenters and views (p.4).

## 4. Crossing boundaries

- Example in the lower right corner of the diagram (not legible in the PDF): controllers and presenters communicate with the use cases; the **flow of control** begins in the controller, passes through the use case and ends up executing in the presenter; but the **source code dependencies** all point inward, toward the use cases `[from source] (CA12 p.5)`.
- The apparent contradiction is resolved with the **Dependency Inversion Principle**: in a language like Java, interfaces and inheritance are arranged so that source code dependencies oppose the flow of control at the right points of the boundary `[from source] (CA12 p.5-6)`.
- Example: the use case needs to call the presenter, but cannot call it directly (it would violate the rule: no name from the outer circle may be mentioned in the inner one). So the use case calls an **interface** (in the diagram, "Use Case Output Port") inside the inner circle, and the presenter, in the outer circle, implements it `[from source] (CA12 p.6)`.
- The same technique applies to all boundaries, taking advantage of dynamic polymorphism `[from source] (CA12 p.6)`.

## 5. What data crosses the boundaries

- Typically, **simple data structures**: basic structs, *Data Transfer Objects* if you prefer, function arguments, a hashmap or a constructed object. What matters is that isolated, simple structures cross the boundary; you must **not** "cheat" by passing Entities or database rows `[from source] (CA12 p.6)`.
- The structures must not have dependencies that violate the Dependency Rule. Example from the text: a database framework returns a convenient format ("RowStructure"); passing it inward would violate the rule, as it would force the inner circle to know about the outer one `[from source] (CA12 p.6)`.
- When crossing a boundary, the data is **always in the form most convenient to the inner circle** `[from source] (CA12 p.7)`.

## 6. Conclusion of the text

Following these simple rules is not hard and saves headaches; separating into layers and respecting the Dependency Rule produces a system that is **intrinsically testable**; when external parts (database, web framework) become obsolete, they can be replaced with minimal effort `[from source] (CA12 p.7)`.

## 7. What the text does NOT say (avoid attributing)

- "Entities have no framework annotations" as a literal rule: it is a consequence of the dependency rule `[inference]` applied to names of outer circles (p.3), but the post does not mention JPA/Hibernate/`@Entity`.
- That entities leak into JSON/REST, *mass assignment*, CQRS, DDD: the post does not cite them `[extrapolation]`.
- "Strict" prohibitions on DTOs: the text accepts several forms of simple data (p.6).
- A rule about assigning to "Frameworks & Drivers" everything that is "infrastructure"; the example lists (Postgres, Express, Kafka) are `[extrapolation]`.
