## 1. Bytecode (GPP p.163-189)
- Intent: give logic the flexibility of data, encoding behavior as instructions of a virtual machine `[from source] (GPP p.163)`.
- Motivation: games have huge codebases, slow recompilations, a need to iterate with designers, to fix things after release and to support mods safely (sandbox) `[from source] (GPP p.163-164)`.
- Contrast with the GoF **Interpreter** pattern: a tree of objects that evaluate themselves; problems: loading many small objects, memory (the example expression takes at least 68 bytes on a 32-bit machine, without padding), data and instruction cache; Ruby used this model for about 15 years until version 1.9 `[from source] (GPP p.164-167)`. Machine code is dense, linear, low-level and fast, but unsafe to hand to users; the compromise is a custom VM with *bytecode* `[from source] (GPP p.167-168)`.
- Pattern: instruction set, sequence of bytes, a VM that executes them one by one with a stack `[from source] (GPP p.169)`. When to use: a lot of behavior to define and the engine's language is low-level, slow to iterate or too trusted; cost: it is the most complex pattern in the book and is slower than native code `[from source] (GPP p.169)`.
- Cautions: scripting systems grow; a *front-end* (tool/compiler) is needed, and the debugger is lost `[from source] (GPP p.169-171)`.
- Example of wizard spells with a stack VM: `LITERAL`, `GET_*`, `SET_*`, `ADD`, step-by-step execution `[from source] (GPP p.171-179)`. The VM is a sandbox: it controls memory (stack) and, without loop instructions, is not Turing complete `[from source] (GPP p.179)`. Graphical authoring tools `[from source] (GPP p.180-182)`.
- Decisions: stack-based vs register-based VM (Lua uses registers, as described for Lua 5.1 `[DATED]`; Nystrom recommends a stack for simplicity) `[from source] (GPP p.182-183)`; instruction kinds (external primitives, internal, flow control through jumps, abstraction with a return stack) `[from source] (GPP p.183-184)`; value representation (single type, tagged variant, untagged union, interface) `[from source] (GPP p.184-187)`; bytecode generation (textual language or graphical tool) `[from source] (GPP p.187-188)`. See also: Lua, UnrealEd's Kismet, Wren `[from source] (GPP p.189)`.

## 2. Type Object (GPP p.191-207)
- Intent: create new "classes" with a single class, each instance representing a type `[from source] (GPP p.191)`.
- Motivation: an RPG with monster breeds (dragon, troll) that the typical OOP answer models as subclasses of `Monster`; designers want hundreds of breeds and to tweak numbers (e.g., troll health from 48 to 52) without recompiling `[from source] (GPP p.191-193)`.
- Solution: two classes, `Monster` and `Breed`; each monster references its breed, which holds the shared data (starting health, attack text); no inheritance; types definable in data `[from source] (GPP p.194-195)`. Useful when the types are not known in advance or you want to change them without recompiling `[from source] (GPP p.195)`.
- Costs: the programmer must manage the type objects (analogy: C++'s *vtable* is a type object) and it is hard to define **behavior** per type (use predefined functions, Interpreter or Bytecode) `[from source] (GPP p.196-197)`.
- Code: `newMonster()` in `Breed` as a factory method ("constructor" that controls allocation, e.g., pool) `[from source] (GPP p.198-200)`; inheritance between breeds through dynamic delegation or through **copy-down** (copies attributes in the constructor) and a JSON example with a `"parent"` field `[from source] (GPP p.200-203)`.
- Decisions: encapsulated or exposed type object; how objects are created; the type can change (e.g., monster becomes zombie); no, single or multiple inheritance (multiple is complex, p.206-207) `[from source] (GPP p.203-207)`. Relative of Flyweight (which is only about saving memory) and of State (the type object delegates "what the object is", State delegates "how it is right now") `[from source] (GPP p.207)`. See also Prototype `[from source] (GPP p.207)`.

## 3. Component (GPP p.209-228)
- Intent: allow a single entity to span several domains without coupling the domains to each other `[from source] (GPP p.209)`.
- Problem: the hero class (`Bjorn`) concentrates input, physics, animation, sound; it becomes a 5,000-line file, with domains tied in a "Gordian knot" (conditions mixing collision, rendering and sound); with threads per domain this is worse `[from source] (GPP p.209-210)`.
- Solution: cut by domain into component classes (`InputComponent`, `PhysicsComponent`, `GraphicsComponent`); the entity becomes a thin container; "pan-domain" state (position, velocity) stays in the entity `[from source] (GPP p.210-211, 219)`. Inheritance for decorations, props and zones leads to the "Deadly Diamond"; with components a single `GameObject` is enough (decoration = graphics without physics; zone = the opposite; prop = both) `[from source] (GPP p.211-213)`.
- Pattern and when to use `[from source] (GPP p.213-214)`. Costs: more complexity, harder communication between components, indirection; on the other hand it can improve the cache and makes Data Locality easier `[from source] (GPP p.214)`.
- Example: interfaces for the components, `PlayerInputComponent` vs `DemoInputComponent` (demo mode) and a generic `GameObject`; "entity-component" systems where the entity is just an ID `[from source] (GPP p.219-223)`.
- Decisions: who creates the components; how they communicate (container state, direct reference, messages, and the author recommends combining them, starting simple) `[from source] (GPP p.223-228)`.
- Cited uses: Unity's GameObject (entirely component-based), Delta3D's `GameActor`, XNA's `GameComponent` `[from source] (GPP p.228)` `[DATED]` (XNA). **Unreal and Godot are not cited** in the chapter as adopters: do not attribute them to the book (label `[extrapolation]`). Comparison with Strategy: components usually have state and identity `[from source] (GPP p.228)`.

## 4. Event Queue (GPP p.230-249)
- Intent: decouple when a message or event is sent from when it is processed `[from source] (GPP p.230)`.
- Manifestations: GUI event loops (the application pulls events from an OS queue) and a central event "bus" between game systems (the tutorial example that listens for "enemy died") `[from source] (GPP p.230-232)`.
- Audio example: a synchronous `playSound()` API has three problems: it **blocks** the caller (loading a file freezes frames), it **does not aggregate** requests (two enemies hurt in the same frame play the same sound twice and add up volume; there is a channel limit) and it runs on the **wrong thread** `[from source] (GPP p.233-235)`.
- Pattern: FIFO queue of notifications/requests; sending is enqueuing and returning; a processor consumes later; it decouples sender and receiver statically and temporally `[from source] (GPP p.235)`. Only use a queue when you need to decouple in **time**; to decouple only who receives, Observer and Command suffice; a queue is a poor choice if the sender needs a response `[from source] (GPP p.235-236)`.
- Cautions: a central queue is a global variable; the world may change until the event is processed (events carry more data); feedback loops (avoid sending events inside a handler) `[from source] (GPP p.236-237)`.
- Code: simple *array*, then **ring buffer** (head/tail; no allocation, cache friendly; fixed capacity or growing array with constant amortized cost) `[from source] (GPP p.237-243)`; **aggregation** when enqueuing (same id: uses the larger volume; O(n) cost unless a hash table is used) `[from source] (GPP p.243-244)`; several threads: protect the operations, `update()` waits on a condition `[from source] (GPP p.244-245)`.
- Decisions: events (already happened, several listeners) vs messages (future request, one listener); who reads (single-cast, broadcast, work queue); who writes; object lifetime (pass ownership, share, the queue owns) `[from source] (GPP p.245-249)`. It is the asynchronous cousin of Observer; related names: message queue, pub/sub; Go's `channel` `[from source] (GPP p.249)`.
- The example with "20 monsters in the same frame" and "dedicated thread that merges with normalized volume" is **not** from the book: it speaks of two enemies and picks the larger volume.

## 5. Service Locator (GPP p.251-265)
- Intent: global access point to a service without coupling the users to the concrete class `[from source] (GPP p.251)`.
- Motivation: services such as audio, log, allocator, random numbers; the phone book analogy `[from source] (GPP p.251-252)`. Pattern: service interface, concrete provider, locator that hides the type and the lookup process `[from source] (GPP p.252)`.
- When to use: "sparingly"; first consider **passing the object**; it is justified for systems such as log or audio that do not belong to each module's public API `[from source] (GPP p.252-253)`. It is a flexible cousin of the Singleton, with the same baggage if misused `[from source] (GPP p.253)`.
- Cautions: the locator defers the binding of the dependency to runtime (harder to read the dependencies); the service may not be found; the service does not know who calls it `[from source] (GPP p.253)`.
- Code: provider registered by external code (the author calls this *dependency injection*) `[from source] (GPP p.254-255)`; **null service** (*Null Object*) to never return `NULL`, also useful to turn off audio in development `[from source] (GPP p.255-257)`; **log decorator** around the service `[from source] (GPP p.257-259)`.
- Decisions: how the service is located (registered externally, compile-time, runtime via configuration/reflection); what to do if it is not found (let the user handle it, `assert`, null service; the most common is `assert`, but on large teams he recommends the null service); scope (global or restricted to a class and descendants) `[from source] (GPP p.259-265)`. Cited: Unity's `GetComponent()` and XNA's `GameServices` `[from source] (GPP p.265)`.
- "Null Object" appears both here and in Command (button with no action) `[from source] (GPP p.24, 256)`.
