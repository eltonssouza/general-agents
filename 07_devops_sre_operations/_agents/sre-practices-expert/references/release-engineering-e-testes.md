## Release engineering (Ch. 8)
- Definition: building and delivering software; reliable releases require reproducible, automated, repeatable builds, not "unique snowflakes". [from source] (SRE p.76)
- Four principles: self-service, high velocity, hermetic builds, enforcement of policies and procedures. [from source] (SRE p.76-77)
- Hermetic: the same build at the same revision gives an identical result on different machines; fixing a bug in an old release = rebuild at the original revision + cherry picks. [from source] (SRE p.77)
- ACL-controlled operations (approve changes, create a release, approve an integration proposal and cherry picks, deploy, change build config); change report archived with the artifacts. [from source] (SRE p.77)
- Google tools: Rapid (releases), Blaze (build; open source as Bazel), MPM (packages), Sisyphus (rollout automation). [from source] (SRE p.77-80) [DATED]
- Branching: everything goes into mainline; the release branch is cut at a revision and never merged back; fixes go into mainline and are cherry-picked, so as not to mistakenly pick up unrelated changes submitted to mainline after the original build (direction mainline → branch). [from source] (SRE p.78)
- Tests: continuous build on mainline; create the release at the revision of the last continuous build that passed; rerun unit tests on the release branch for an audit trail, because with cherry picks the branch may have code that exists nowhere in mainline. [from source] (SRE p.78)
- 4-step release process (branch, build+unit test, system test/canary, log and change report). [from source] (SRE p.79)
- Fit the deploy to the risk profile: hourly build and automatic push in pre-prod; start in one cluster and expand exponentially; sensitive infrastructure over days across regions. [from source] (SRE p.80)
- Four configuration management models: mainline, config and binary in the same MPM package, configuration packages, external store. [from source] (SRE p.80)
- Final questions: how to version, continuous or periodic, frequency, config policy, metrics. Budget for release engineering from the start; devs should not "throw it over the wall". [from source] (SRE p.81)
- The book does NOT mention DORA, blue/green or automated canary analysis under that name. Canary: Ch. 17 gives the rule of thumb of 0.1% of traffic (note 89, p.147) and Ch. 27 describes the canary on **a few machines of a datacenter**, with automatic rollback (p.268); what the book does not give is a fixed percentage of machines (see the section "Post-blind-test corrections (round 3)" below).

## Testing (Ch. 17)
- Central responsibility: quantify confidence; failing tests generally prove the absence of reliability, passing does not prove its presence. [from source] (SRE p.135)
- "Zero MTTR": a system test applied to a subsystem detects what monitoring would detect and blocks the push; more zero-MTTR bugs increase the MTBF seen by users. [from source] (SRE p.135)
- Two categories: traditional (unit, integration, system with smoke/performance/regression) and production (configuration, stress, canary). [from source] (SRE p.136-139)
- Unit = smallest isolated unit; integration with dependency injection/mocks; system end to end with smoke, performance and regression. [from source] (SRE p.137)
- Staged rollouts make production non-hermetic; hence production tests. [from source] (SRE p.137-138)
- Configuration test: one test per versioned config file, comparing production to the file. Stress test: find limits (components fail catastrophically). [from source] (SRE p.138)
- Canary: a subset is updated and incubated ("baking the binary"); not really a test, it is structured acceptance; rule of thumb from a note: start with 0.1% of traffic and increase by orders of magnitude every 24 h. [from source] (SRE p.138-139; note p.147)
- Mathematical model of canary with exponential rollout: on p.139 the exponents were lost in the PDF (the expression appears as CU = RK, without superscripts), so use only the idea (order U of the failure); the formula of note 90 (p.147), however, is readable and checks out: K = 86,400 ÷ ln(0.1 ÷ 0.01) = 37,523 s = 10 h 25 min. [from source] (SRE p.139, 147)
- Create a testing culture: prioritize by importance, smoke tests per release, every bug becomes a test case, continuous build; when the build breaks, stop and fix it. The book notes that stability and agility are often in tension in the SRE world, but here **stability drives agility**: with the build predictably solid and reliable, developers iterate faster; without it, release cadences such as nightly and weekly builds lose value and responding to an emergency release (e.g. a security vulnerability) becomes more complex and difficult. [from source] (SRE p.139-140)
- Barriers against risky software; test DR and repair tools; statistical tests (Lemon, Chaos Monkey, Jepsen) are not repeatable by nature. [from source] (SRE p.140-142)
- Simple tests in seconds; the 42,000 tests calculation: to accept 99% of perfect patches, each test must be right more than 99.9999% of the time. [from source] (SRE p.142-143)
- Release cadence: an annual release gives an MTBF of one year; testing intermediate versions gives confidence; "reliability budget" per team. [from source] (SRE p.143-144)
- Configuration: files changed only on failure vs changed more than once per release; noisy **break-glass** mechanism. [from source] (SRE p.144)
- Config in an interpreted language (interpreted languages, e.g. Python, common because the interpreter can be embedded and there is simple sandboxing against non-malicious errors) is risky: the file's content is, for testing purposes, potentially **hostile** to the interpreter, and there are latent flaws that are hard to handle once and for all. **Loading the config is executing a program**, so there is **no inherent upper bound** on the inefficiency of loading. How to test: pair the integration test with **rigorous deadline checking in all integration test methods**, marking as failed the tests that do not finish in a reasonable time. [from source] (SRE p.145)
- Alternatives: own text syntax requires coverage of all test categories from scratch; **YAML with a heavily tested parser (Python's safe_load)** removes part of the toil and, with good choice of syntax and parser, gives a **hard upper bound** on load time; but schema gaps are left to the implementer, and the simple strategies for that have no time limit and rarely have robust unit tests. **Protocol buffers**: the schema is defined beforehand and checked automatically at load, removing more toil and keeping time bounded. Since any tool can fail from bugs the tests do not catch, the book advises **defense in depth** (another tool or a tested validator should report the misbehavior; report, not always fix). [from source] (SRE p.145)
- Production probes: known bad, known good replayable, known good non-replayable; integrated into the readiness check; combinations of probe and application versions. **What it means for the probe to fail:** the probe in production runs a configuration that was never tested before (the release test uses a frontend with a fake backend; the probe uses the release binary with a balancer in front and a real persistent backend; frontends and backends have independent release cycles). It should never fail; if it fails, the frontend API (coming from the balancer) or the backend API (to the persistent storage) is **not equivalent between production and the release environment** and, unless the reason is already known, **the site is probably broken**. The same production updater that swaps the application swaps the probes gradually, continuously generating the four combinations (old/new probe × old/new application); it detects the combination that generates errors and **rolls back to the last known good state**. With the probe included in the readiness check, the update fails indefinitely, no user traffic reaches the new version and it stays paused until engineers diagnose it and take the updater to a clean rollback. [from source] (SRE p.145-146)
- Fake backend and compatibility between peer versions. [from source] (SRE p.146)
- Testing is one of the most profitable investments for reliability. [from source] (SRE p.146)

## Release and testing in more detail (Ch. 8 and 17) [from source]
**Blaze/Bazel and hermetic build (what the book says and does not say).**
- **Blaze** is Google's build tool (C++, Java, Python, Go, JavaScript): it defines targets (e.g. a JAR) and their dependencies and builds the dependencies automatically; Rapid passes flags such as the build identifier; every binary accepts a flag that shows build date, revision and identifier. **Note 37 (p.81) says Blaze was open-sourced as Bazel**. Hermetic = insensitive to libraries installed on the machine; depends on known versions of compilers and dependencies; the build tools themselves are versioned by the project revision, so a cherry pick from last month does not use this month's compiler. (SRE p.77-78, 81)
- In Ch. 17 the book returns to Bazel as an example of a tool with more precise control of tests: it creates **dependency graphs**; when a file changes it rebuilds only what depends on it; builds are reproducible and **only the tests of the changed code run**, cheaper and faster (p.140; note 93 on p.147). [from source]
- **The book does NOT carry** a Maven to Bazel migration plan, BUILD/WORKSPACE files, `pom.xml`, commands or rules; only the hermetic/reproducible principle, the internal use of Blaze and these two mentions of Bazel.
- Other details of Ch. 8: "Push on Green" (deploy of every build that passes all tests) and hourly builds with version selection by test results (p.77); MPM packages with stage labels (dev, canary, production) that migrate to the new package when the label is reapplied (p.78); Rapid configured by "blueprints" with ACLs by role; serial or parallel workflows; dispatch to Borg tasks (p.78-79); **Sisyphus** for complex rollouts (a rollout is a logical unit of one or more tasks; it can update everything at once or successive clusters over several hours) (p.79-80); release velocity metrics (time until a change reaches production) (p.76); example of configuration in its own package: flag `first_folio` replaced by `bad_quarto` via cherry pick without rebuilding the binary, with label `much_ado` to install both packages together (p.80).

**Canary and tests: additional numbers and concepts (Ch. 17).**
- Rule of thumb of note 89 (p.147): start with **0.1% of traffic** and increase by orders of magnitude every 24 h, varying the geographic location (day 2: 1%, day 3: 10%, day 4: 100%). Note 90 says that, with continuous exponential growth from 1% to 10% in 24 h, the time for traffic to grow by a factor of e is about **10 hours and 25 minutes** [checked: 24 h ÷ ln 10 ≈ 10.4 h]. Canary model in the body text: the cumulative number of variation reports grows as a power of the failure order **U**: U=1 simply broken code, U=2 the request corrupts data that a future request will see, U=3 the corrupted data is also a valid identifier of an earlier request; **most bugs are of order 1** and grow linearly with traffic (on p.139 the exponents were lost in the PDF; use only the idea; the book writes "172%" for the factor and, without recomputing; the fn90 of p.147 is readable: K = 86,400 ÷ ln(0.1/0.01) = 37,523 s, i.e. 10 h 25 min 23 s, and the book says about 10 h 25 min; 10 h 23 min would be a conversion error). High-order bugs must be caught at release, or the operational load grows too fast. (SRE p.139, 147)
- Unit tests cost milliseconds on a laptop; bringing up a full server with dependencies takes minutes to hours; performance test example: a program going from 8 GB to 32 GB of memory or from 10 ms to 50 ms and 100 ms of response without anyone noticing. Configuration tests: one per versioned file, comparing production with the file; they get more complex when there are defaults embedded in the binary, preprocessing (bash for flags) or shared runtime context. (SRE p.137-138)
- When the build breaks, **everyone should drop everything else and fix it**: it is harder to fix later, it slows the team down, it makes nightly/weekly builds lose value and complicates an emergency release (p.140). Barrier defenses for risky software (3 steps: a barrier that makes the replica fail the health check; risky software only accesses unhealthy replicas; a validation tool removes the barrier) (p.141). Automation tools also need testing (e.g. a container balancer that tries to move itself; upgrade and rebalancing tools with a circular dependency) (p.141). Offline DR tools: checkpoint equivalent to a clean stop, loadable, with barrier and clean start (p.141-142).
- Statistical tests (Lemon, Chaos Monkey, Jepsen) are not repeatable; recording the random generator seed and redoing the run as a release test helps measure how hard it will be to prove the failure was fixed (p.142). **The 42,000 tests calculation**: a service with more than **21,000 simple tests** compares the result vector before and after the patch (21,000 + 21,000 = 42,000); if rejecting 1 patch in 10 causes outrage and 1 in 100 goes unnoticed, you want to accept 99% of perfect patches: the 42,000th root of 0.99 requires each test to be right **more than 99.9999%** of the time (p.142-143). [checked: 0.99^(1/42000) ≈ 0.99999976]
- An annual release had an MTBF of one year "no matter how much testing"; testing intermediate versions gives a mappable cause and a shorter feedback cycle; the "reliability budget" can be segmented by functionality or team (SRE has a separate one). A config file that only changes on failure has a cadence slower than the MTBF; one that changes more than once per app release dominates reliability if it does not have better coverage than the app; noisy break-glass (open a bug) that **does not turn off** the tests (associates the push with the pending test and annotates afterwards). (SRE p.143-144)
- Example of `/etc/passwd` read halfway: the tool that maintains home directories must **report** the discrepancy and **not** "remediate" by deleting user data (p.145). Probes: the production updater gradually swaps application **and** probes, generating the four combinations (old/new probe × old/new app); if the probe is part of the readiness check, the update fails forever and **no user traffic goes to the new version** until the team diagnoses it (p.146). Fake backends maintained by the peer's team and monitoring aware of the versions on both sides of the interface (p.146); only the **new** combinations (result of a new release of one of the sides) need to run, and this need not block the release itself, but **rollout automation should, ideally, block the production rollout until the problematic combinations are no longer possible**; the peer team's automation may consider draining (and updating) the replicas that have not yet left the problematic combination (p.146).

## Post-blind-test corrections (round 3): branch, cherry-pick, MPM, canary (p.78, p.268) and notes of Ch. 17 [from source]
- **Why the release branch with cherry-pick exists (p.78).** Code goes to mainline; the branch is cut at a specific revision and is **never merged back**. Fixes go into mainline first and are cherry-picked to the branch. The stated reason: **avoid mistakenly picking up unrelated changes submitted to mainline after the original build**; this way "we know the exact contents of each release". Attention: the direction is *mainline → branch*; it is not "avoid dragging changes from the branch into main" (that reading inverts the book). (SRE p.78)
- **Why rerun the tests on the branch (p.78).** The test targets of the continuous build must match those that **block** the release, and the release must be created at the revision of the last continuous build that passed all tests (less chance of failure in the release build). Even so, at release the unit tests run again **on the branch**, with an audit trail that all passed: if the release has cherry picks, **the branch may contain a version of the code that exists nowhere in mainline**, and you want the guarantee that the tests pass in the context of what is actually released. In addition there is an independent test environment that runs system tests on the packaged artifacts, triggered by hand or by Rapid. (SRE p.78)
- **Packaging in MPM (p.78).** Packages assembled from Blaze rules (artifacts, owners, permissions), with a name (e.g. search/shakespeare/frontend), **versioned with a unique hash** and **signed** to guarantee authenticity; Rapid applies a label with the build ID, which makes the package uniquely referenceable by name + label; phase labels (dev, canary, production) **move automatically** to the new package when reapplied. **The book does not say what the hash algorithm is** (nor the signer's): questions about it are NOT COVERED for the detail.
- **Canary: two distinct scenarios in the book.** (1) **Ch. 17**: rule of thumb (note 89, p.147) of starting with 0.1% of **traffic** and increasing by orders of magnitude every 24 h. (2) **Ch. 27 (p.268)**: almost every Google update is gradual; a new server is installed on **a few machines of a datacenter**, observed for a defined period, then on all machines of that datacenter, observed again, and finally globally; the **first stages of the rollout are called canaries**; the tools that manage installations observe the newly started server and **roll back automatically** if the change does not pass validation. The book therefore does **not** limit the canary to "traffic, not machines": Ch. 17 talks about a fraction of traffic and Ch. 27 about a few machines; what it does not give is a **fixed percentage of machines**. For Android apps the equivalent is releasing the version to a subset of installs and raising the percentage to 100%. See the 6 feature flag requirements in `lancamentos-e-capacity-planning.md`. (SRE p.147, 268)
- **Notes of Ch. 17 (p.147).** Note 86: after the engineer defines tests in a generalized way, the rest of the work is common to all SRE teams and becomes shared infrastructure: a **scheduler** (divides budgeted resources among unrelated projects) and **executors** (sandbox the test binaries so they are not treated as trusted). Note 94: an example in which the synchronous API started returning a *future* and argument errors only appear when the future is evaluated, so many incorrect uses slip through. Note 95: the focus is on SRE tools that need to be scalable; the others should also be tested, with a strategy similar to user-facing applications. Note 98: even repeating the test with the same seed, there is no serialization between task deaths and fake traffic, so there is no guarantee of exercising the observed code path again. Note 102: tools that cross technology verticals and layers of abstraction have a weak association with many software teams and a slightly stronger one with systems teams. (SRE p.147)

### Barriers against risky software and testing automation tools (Ch. 17, p.141) [from source]
- SRE tools have two characteristics: their side effects stay within the already tested main API and they are isolated from user-facing production by an existing validation and release barrier. Software that **bypasses** the normally tested API (example: a database engine that allows temporarily turning off transactions to shorten maintenance windows) can cause havoc if released by mistake against a user-facing replica. The defense design has **3 steps**: (1) use a separate tool to put a **barrier** in the replication configuration, so that the replica fails the health check and is not released to users; (2) configure the risky software to check the barrier at startup and only access unhealthy replicas; (3) use the tool that validates the replica's health (the one from black-box monitoring) to remove the barrier. (SRE p.141)
- **Automation tools** (index selection, balancing across datacenters, shuffling relay logs) have "out-of-band" risk and subtler tests: the operation uses a robust, tested API, but the goal is a side effect that is a discontinuity invisible to another API client; documented invariants (such as a DNS cache retaining results until the TTL) may not hold across the operation. Tools that touch each other's environment (the fleet upgrade one and the container rebalancing one) create a circular dependency, acceptable if the APIs have restart semantics, there is test coverage for them and the checkpoint health is independently ensured. **Disaster recovery tools** can be designed to operate offline: they compute a checkpoint state equivalent to cleanly stopping the service, push it to be loadable by the normal validation tools and use the usual release barriers. (SRE p.141)

## Post-blind-test corrections (round 6): cadence × MTBF, unattended production, four configuration models, note 36 and p.141 [from source]
### More released versions make MTBF worse, but teach (Ch. 17, p.143-144)
- Before, software shipped once a year, with binaries produced over hours or days by a chain of compilation and tests done by people against written instructions; the release effort was dominated by documentation, data migration and retraining. The MTBF of those releases was **one year**, "no matter how much testing there was": so many changes per release that some user-visible defect would be hidden; in practice, the reliability data of the previous release was irrelevant to the next. (SRE p.143)
- Today API/ABI management tools and interpreted languages allow building and running a new version every few minutes. In principle an army of testers could validate each incremental version by the same criterion; the annual version ships with higher quality because the **intermediate versions are also tested**: the team maps the problems found unambiguously to the causes and is confident that the whole problem, and not just the exposed symptom, was fixed; the principle of the short feedback cycle also applies to automated test coverage. (SRE p.143-144)
- **The central sentence of p.144:** if you let users experience more versions of the software during the year, **the MTBF suffers** (gets worse), because there are more opportunities for user-visible breakage; in return you discover areas that would benefit from more test coverage, and each implemented test protects against a future failure. Careful reliability management combines the bounding of uncertainty by test coverage with the bounding of user-visible failures to tune the cadence; this combination maximizes the knowledge gained from operations and users, which in turn drives test coverage and release velocity. That is, the thesis that "more released versions raise the MTBF" contradicts p.144; the gain lies in smaller, testable batches with a mappable cause. (SRE p.144)
- Do not confuse with p.135: there, more "zero MTTR" bugs (caught by a test that blocks the push) raise the MTBF seen by users; it is another mechanism, the block before production. (SRE p.135)
- If an SRE changes a configuration file or the strategy of an automation tool, the work follows the same conceptual model as a user feature; when defining cadence by reliability, it is advisable to segment the "reliability budget" by functionality or, more conveniently, by team: the feature team pursues an uncertainty limit tied to its target cadence, and the SRE team has its own budget and uncertainty, hence its own release rate ceiling. (SRE p.144)

### "Mostly unattended" production (without supervision) and why the SRE's tool needs testing (p.144)
- To remain reliable without scaling the number of SREs linearly with the service, the production environment needs to run **mostly unattended**, and for that it needs to be resilient to minor failures. When a serious event requiring manual SRE intervention happens, the tools used have to be well tested; otherwise the intervention **reduces confidence that historical data holds for the near future**, and this loss of confidence forces waiting for analysis of monitoring data to eliminate the uncertainty. Hence the conclusion of the passage: testing determines how often it is appropriate to use the tool against production. (SRE p.144)
- Do not confuse with p.329 (App. B): there the text says that **non-emergency rollouts should be supervised** (monitored by the stage engineer or, preferably, by monitoring proven to be reliable) and that, faced with unexpected behavior, you revert first and diagnose afterwards. Supervising a rollout (p.329) and letting the environment run unattended day to day (p.144) are complementary ideas. (SRE p.144, 329)
- Configuration files exist because changing configuration is faster than rebuilding the tool, which helps keep MTTR low; from a reliability viewpoint, a file that only changes on failure has a release cadence slower than the MTBF (uncertainty about whether each manual edit is optimal), and a file that changes more than once per app release (for example because it holds release state) dominates the site's reliability if it does not have test coverage and monitoring far better than the app's. (SRE p.144)

### The four configuration management models, with pros and cons (Ch. 8, p.80)
- Context: configuration is an area of close collaboration between release engineers and SREs; it seems a deceptively simple problem, but configuration changes are a potential source of instability, and the approach evolved considerably. **All schemes keep the configuration in the main source code repository and impose a strict code review requirement.** Project owners choose the model case by case. (SRE p.80)
- **1. Mainline.** It was the first method used to configure services on Borg (and in earlier systems): developers and SREs change the files at the head of the main branch; changes are reviewed and then applied to the running system. Advantage: binary release and configuration change are **decoupled**, and it is simple in theory and in procedure. Disadvantage: it tends to generate **skew** (divergence) between the configuration version in the repository and the one running, because jobs need to be updated to pick up the changes. (SRE p.80)
- **2. Config and binary in the same MPM package.** Suitable for projects with few configuration files or whose files (or part of them) change every release cycle. Advantage: it simplifies deploy, since a single package is installed. Disadvantage: it **limits flexibility**, because it ties binary and configuration together. (SRE p.80)
- **3. Separate MPM configuration packages.** It applies the hermetic principle to configuration: since configurations tend to be tightly tied to binary versions, build and packaging are used to take a snapshot of the configuration along with the binary; the build ID lets you reconstruct the configuration at a point in time. With two packages (binary and configuration) each changes independently: if the feature shipped with the flag `first_folio` and later it turns out it should be `bad_quarto`, you cherry pick onto the release branch, rebuild only the configuration package and deploy, **without a new binary build**. The MPM label, such as `much_ado`, indicates which versions of the packages are installed together; since the label is unique in the package namespace, only the most recent package with that label is used. (SRE p.80)
- **4. External store.** For projects whose files need to change frequently or dynamically (with the binary running); they live in Chubby, Bigtable or the source-based file system. (SRE p.80)
- In summary, the book presents four options and says each project decides which works best; the only declared common denominator is main repository plus strict code review. The book points to the skew of the mainline model as a concrete defect and the loss of flexibility of the single package. (SRE p.80)
- The book does not label any of the four models an "anti-pattern" nor say that "configuration without review is an anti-pattern" in general terms: p.80 only says all schemes require strict code review, and the passages on p.76-81 do not use the word anti-pattern. Whoever writes "anti-pattern" is inferring.

### Deploy risk profile and Rapid steps (p.79-80)
- Rapid has workflows that define the release actions; actions run in series or in parallel and a workflow can launch others; work is dispatched to tasks of a Borg job in production, which allows thousands of simultaneous release requests. Typical steps: (1) create the release branch from the requested integration revision number (often obtained from the continuous testing system); (2) Rapid uses Blaze to compile all binaries and run the unit tests, often in parallel, in dedicated environments separate from the workflow's Borg job; (3) the artifacts become available for system testing and canary, and a typical canary brings up a few jobs in production after the system tests; (4) each step is logged and a report of all changes since the last release is generated. Rapid also manages release branches and cherry picks, which can be approved or rejected case by case. (SRE p.79)
- Deploy: Rapid drives simple deploys by updating Borg jobs to the new MPM packages, according to the deploy definitions in blueprint files and specialized task executors; for complicated deploys **Sisyphus** is used (a rollout automation framework built by SRE, with extensible Python classes, control panel and tracking), and Rapid creates a rollout in a long-running Sisyphus job, passing the MPM package build label. (SRE p.79-80)
- Stated objective: fit the deploy process to the service's **risk profile**: in development or pre-production, hourly builds and automatic push when all tests pass; in large user-facing services, start in one cluster and expand exponentially until all are updated; in sensitive infrastructure, extend the rollout over several days, interleaving instances from different geographic regions. (SRE p.80)

- Note 36 is tied to the sentence on p.77 about hermetic builds ("the same product, at the same revision of the source code repository, on different machines, gives identical results"): the text of the note, on p.81, says Google uses a **unified monolithic source code repository** (monolithic unified source code repository), with a reference to [Pot16]. ### Automation tools: invariants that do not hold and why the self-displacement test is not enough (Ch. 17, p.141-142)
- Automation tools (database index selection, balancing across datacenters, shuffling relay logs for fast remastering) have two characteristics: the operation is done against a robust, predictable and well-tested API, and the **purpose of the operation is the side effect**, a discontinuity invisible to another API client. Testing shows the desired behavior of the other layer before and after the change, and it is often possible to test whether the internal state seen by the API is constant throughout the operation (for example, databases chase correct answers even without a suitable index). But some **documented API invariants may not hold across the operation**: a DNS cache that keeps the result until the TTL is the book's example; if a runlevel switch replaces the local nameserver with a caching proxy, both promise to retain complete lookups for many seconds, but it is unlikely that the cache state is passed from one to the other. (SRE p.141)
- The book's question: in what environment do these tools run? The automator that shuffles containers to improve utilization tends to shuffle itself if it also runs in a container; it would be embarrassing if a new version of its internal algorithm generated dirty memory pages so fast that the mirroring network bandwidth prevented completing the live migration. Even if there is an integration test in which the binary deliberately displaces itself, the test probably **does not use a production-sized model of the container fleet** and almost certainly **cannot use the scarce high-latency intercontinental bandwidth** to test these races. (SRE p.141)
- Even more fun: an automation tool may change the environment in which another runs, or the two may change each other's environment at the same time. Example: the fleet upgrade tool consumes the maximum of resources when pushing upgrades, which would tempt the container rebalancer to move it, and the rebalancer in turn needs an upgrade from time to time. This circular dependency is acceptable if the APIs have restart semantics, someone remembered to implement test coverage of that semantics and the checkpoint health is independently guaranteed. (SRE p.141)
- Disaster recovery tools can be designed to operate offline with five constraints: offline, checkpoint, loadable, barrier and clean start. If any of them is broken, it becomes much harder to show confidence that the tool will work at any moment, in the short term. Online repair tools operate outside the main API and are therefore more interesting to test: a hard point is knowing whether normal, eventually consistent behavior interacts badly with the repair; the offline tool usually expects instantaneous consistency, which is easier to test, and a unified instrumented binary may be needed to observe the transactions. (SRE p.142)
