# The tree-walk interpreter (jlox), the AST and the resolution pass

Source: CI chs. 5-8 and 11 (PDF p.59-139 and p.163-186). Convention: PDF page (see `INDEX.md`). The book's code is Java (jlox).

## 1. Context-free grammars and trees (CI ch. 5)
- `[from source]` (CI p.60-62): a context-free grammar "generates" strings; the rules have a head and a body, with *terminals* (symbols the scanner produces) and *nonterminals* (references to other rules); the book uses a variant of BNF (Backus-Naur, CI p.61). Parsing plays the game in reverse (CI p.80).
- `[from source]` (CI p.59): to evaluate an arithmetic node, the subtrees must be evaluated first: it is a *post-order* traversal (CI p.59, p.101).
- `[from source]` (CI p.65-71): the expression nodes (`Binary`, `Grouping`, `Literal`, `Unary` in the first grammar) are classes generated by a small program (TAUP's Rule of Generation, p.47-48, applies: `[inference]`).

## 2. The expression problem and the Visitor pattern (CI p.69-78)
- `[from source]` (CI p.69-70): with one class per node type, the interpreter needs to associate behavior with each type; a chain of `instanceof` is slow and inelegant; putting an `interpret()` method in each class scatters domains (parser, interpreter, name resolution, type checking) across the same classes and violates separation of concerns.
- `[from source]` (CI p.70-71): **expression problem**: imagine a table with types in the rows and operations in the columns. OO languages make it easy to add rows (new types) and hard to add columns (new operations); languages of the ML family invert this (pattern matching); no style makes adding both easy, and "no perfect language" has solved this.
- `[from source]` (CI p.72-73): the **Visitor** is described as "approximating the functional style within an OO language": it allows adding new columns (operations) without touching the types; a visitor interface is defined with one method per type and each class implements `accept()`, which calls the right method of the visitor passing `this`. The book warns that the pattern is not about "visiting" or walking trees (that is a coincidence) and is "the most misunderstood pattern" of the GoF.
- `[from source]` (CI p.74-75): in the expressions, the visitor uses generics (`Visitor<R>` with `R visitBinaryExpr(...)` etc.) so that each operation chooses its return type; `accept` has the form `<R> R accept(Visitor<R> visitor)`.
- `[inference]`: "double dispatch" (v1, CI p.74) and "satisfies the Open/Closed Principle" are **not** terms from the text of CI (empty search); they are reader interpretations of the mechanism described at CI p.72-73.

## 3. Recursive-descent parsing (CI ch. 6)
- `[from source]` (CI p.80-82): ambiguity in the expression grammar; precedence (who evaluates first) and associativity (for the same operator); Lox's table (same as C's) from lowest to highest: equality, comparison, term (`-`, `+`), factor (`/`, `*`), unary (`!`, `-`), all left-associative, except unary (right) (CI p.81-82).
- `[from source]` (CI p.82-83): the grammar is *stratified* by precedence level; a left-recursive rule is correct but not ideal for the chosen technique, so `factor → unary ( ( "/" | "*" ) unary )*` is used.
- `[from source]` (CI p.84): recursive descent is a top-down parser that translates rules into code, fast, robust and capable of sophisticated error handling; the book cites GCC, V8 and Roslyn as users.
- `[from source]` (CI p.91-94): error recovery by *panic mode* and *synchronization* (discard tokens up to a safe point; in jlox, it uses a `ParseError` exception to unwind calls and synchronizes at statement boundaries) avoids cascading errors.

## 4. Evaluating expressions and environments (CI chs. 7-8)
- `[from source]` (CI p.100-101): the `Interpreter` implements the `Visitor`; it evaluates each node after its children (post-order); dynamic typing is checked at run time (CI p.101).
- `[from source]` (CI p.123-139): variables and state live in chained `Environment` objects (each with a map and a pointer to the enclosing environment); in ch. 11 the book calls the environment "the dynamic manifestation of static scopes" (CI p.165).

## 5. The scope bug and the resolution pass (CI ch. 11, p.163-186)
- `[from source]` (CI p.163-164): Lox uses *lexical/static scope*: one can tell which declaration a name refers to just by reading the text; the precise rule is: a used variable refers to the preceding declaration with the same name in the innermost scope that encloses the expression (CI p.164).
- `[from source]` (CI p.164-166): the example (global variable `a`, a block with `showA()` that prints `a`, then `var a = "block"` and a new call to `showA()`) prints `global` and then `block`, although no variable is reassigned. The book explains that closures capture a reference to the current *mutable* `Environment`; the later declaration in the same block shows up for the closure (CI p.166-167). It is not a problem of "dynamic scope" in the formal sense: the book says that "a bit of dynamic scope leaked" into the interpreter (CI p.161).
- `[from source]` (CI p.167-168): two ways out: persistent environments (immutable; the classic form in Scheme interpreters) or resolving statically. The book chooses to resolve: each variable use is resolved once (semantic analysis), which also avoids the cost of re-resolving on every evaluation (CI p.168).
- `[from source]` (CI p.169-170): the *resolver* is a separate pass, after the parser and before execution, that computes how many environment "hops" separate the use from the declaration; it works as a mini-interpreter without side effects and without control flow (both branches of the `if` are visited; loops once).
- `[from source]` (CI p.170-172): the `Resolver` class implements the visitors; it keeps a `Stack<Map<String, Boolean>>` of block scopes (locals only; whatever is not found is assumed global); `declare` and `define` separate declaration from initialization (avoids reading the variable in its own initializer, CI p.172).
- `[from source]` (CI p.176): the function name is defined immediately (allows recursion), and the body is resolved at declaration time (at execution the body is only touched on the call).
- `[from source]` (CI p.179-181): the resolver hands the depth to the interpreter (`locals.put(expr, depth)`, a side map node→distance, CI p.179); on use, `lookUpVariable` consults the map; if there is a distance, `environment.getAt(distance, name)` climbs exactly that number of environments (via `ancestor`); if there is none, the variable is global (CI p.180-181).
- `[from source]` (CI p.182-185): resolution errors: a duplicate variable in a local scope and `return` in top-level code are detected statically; the interpreter does not run if there is a resolution error.
- `[extrapolation]`: v1 said the bug also appears in "`for` loops that share a single iteration variable among closures", attributing it to CI p.187; the text of CI p.163-168 does not treat this. Remove as an attribution.

## 6. What the book does not say
- It does not use "Open/Closed Principle" or "double dispatch" when explaining the Visitor; it does not claim that Visitor "groups an interpreter's logic into a cohesive class" as the central reason (the reason is adding operations without changing types, CI p.72).
