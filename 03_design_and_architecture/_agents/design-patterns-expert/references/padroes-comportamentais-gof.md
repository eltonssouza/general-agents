# Behavioral patterns (RG) and Command, Observer and State according to Nystrom (GPP)

Sources: **RG** (Refactoring.Guru catalog as a 279-page PDF) and **GPP** (Nystrom, 338 pages). Pages = **PDF**. See `INDEX.md`. Labels: `[from source]`, `[inference]`, `[extrapolation]`, `[DATED]`.

RG: behavioral patterns deal with algorithms and the assignment of responsibilities between objects `[from source] (RG p.14)`. In the PDF: Chain of Responsibility p.157-171, Command p.172-186, Iterator p.187-198, Mediator p.199-210, Memento p.211-222, Observer p.223-234, State p.235-247, Strategy p.248-257, Template Method p.258-267, Visitor p.268-279.

## 1. Chain of Responsibility (RG p.157-170)
- Intent: pass the request along a chain of handlers; each decides whether to process it or pass it on `[from source] (RG p.157)`. Aliases CoR, Chain of Command.
- Problem: an order system with sequential checks (authentication, sanitization, filtering of repeated attempts by IP, cache) that turn into messy, duplicated code when reused `[from source] (RG p.158-159)`.
- Solution: each check becomes a handler with one method; handlers are chained, each with a reference to the next; a handler can stop the chain. "More canonical" variant: the handler processes **or** passes on, so only one (or none) handles it; common in GUI events `[from source] (RG p.159-161)`.
- When to use: request types and sequences unknown in advance; execution in a specific order; set/order of handlers mutable at runtime (setters) `[from source] (RG p.167-168)`. Steps `[from source] (RG p.168-169)`.
- Cons: some requests may go unhandled; the client must be prepared (a one-link chain, a request that does not reach the end) `[from source] (RG p.169)`.
- Relations: CoR x Command x Mediator x Observer (ways of connecting senders and receivers); CoR with Composite; CoR x Decorator (similar structures; handlers can stop the flow, decorators cannot) `[from source] (RG p.169-170)`.

## 2. Command (RG p.172-185; GPP p.21-32)
- Intent (RG): turn a request into a standalone object with all the information; allows passing it as an argument, deferring, queuing and supporting undoable operations; aliases Action, Transaction `[from source] (RG p.172)`.
- Problem: toolbar buttons with subclasses per action couple the GUI to the logic and duplicate the operation (copy by button, menu and Ctrl+C) `[from source] (RG p.173-174)`. Solution: the GUI triggers a command with an execution method; sender (*invoker*), command, receiver; the command is pre-configured with the data `[from source] (RG p.174-176, 178)`.
- Undo in RG: history (stack) of commands with a *backup* of the state; two costs cited: private state is hard to save (mitigable with Memento) and RAM consumption; the alternative is for the command to execute the inverse operation, which may be difficult or impossible `[from source] (RG p.179-182, 183)`.
- When to use: parameterize objects with operations; queue/schedule/execute remotely (serializable commands); reversible operations `[from source] (RG p.183)`. Steps `[from source] (RG p.184)`. Pros and cons (one more layer) `[from source] (RG p.184)`.
- Relations: Command x Strategy (Command converts any operation into an object; Strategy describes ways of doing the same thing), Command + Memento for undo, Prototype to keep copies of commands, Visitor as a "powerful version" of Command `[from source] (RG p.185)`.
- **GPP**: Nystrom sums up Command as a "reified method call" and cites the GoF "object-oriented replacement for callbacks" `[from source] (GPP p.21-22)`. Cases: input configuration (remapping buttons with `execute()`, a command that does nothing = Null Object `[from source] (GPP p.22-24)`; commands that receive the actor as an argument and serve the AI, command stream/queue and networking `[from source] (GPP p.25-27)`; undo/redo storing only what changed (`xBefore_`, `yBefore_`) and a list with a "current" pointer, discarding what comes after when a new command is executed `[from source] (GPP p.27-30)`; replay recording the commands per frame instead of the whole state `[from source] (GPP p.30)`. He says Memento did not work well for undo because it stores too much state `[from source] (GPP p.29)`. In languages with closures, functions can play the role `[from source] (GPP p.31-32)`.

## 3. Iterator (RG p.187-198)
- Intent: traverse elements without exposing the representation (list, stack, tree) `[from source] (RG p.187)`. Problem: several traversal algorithms (depth, breadth, random access) blur the collection's responsibility `[from source] (RG p.188-189)`.
- Solution: extract the traversal into an *iterator* object that keeps position and progress; several iterators can traverse the same collection at the same time; all implement the same interface `[from source] (RG p.189-191)`.
- When to use: hide a complex structure; reduce duplication of traversal code; traverse different or unknown structures `[from source] (RG p.196)`. Cons: overkill for simple collections; may be less efficient than traversing specialized collections directly `[from source] (RG p.197)`. Relations: Composite, Factory Method, Memento, Visitor `[from source] (RG p.197-198)`.

## 4. Mediator (RG p.199-209)
- Intent: reduce chaotic dependencies; objects communicate only via the mediator; aliases Intermediary, Controller `[from source] (RG p.199)`.
- Problem: a profile form with interdependent controls ("I have a dog" checkbox reveals a name field; the submit button validates all of them) makes the classes hard to reuse `[from source] (RG p.200)`. Solution: components notify the mediator (the dialog box itself can be the mediator) `[from source] (RG p.201, 203)`.
- When to use: classes hard to change because of coupling; non-reusable components; many subclasses just for reuse in different contexts `[from source] (RG p.206-207)`. Con: the mediator can become a *God Object* `[from source] (RG p.208)`.
- Mediator x Observer: the goal of Mediator is to eliminate mutual dependencies between components; that of Observer, dynamic one-way connections; there is a popular implementation of Mediator based on Observer `[from source] (RG p.209)`. Facade x Mediator `[from source] (RG p.133, 208)`.

## 5. Memento (RG p.211-221)
- Intent: save and restore the previous state without revealing the implementation; alias Snapshot `[from source] (RG p.211)`. Problem: copying state "from outside" requires exposing private fields and couples to the structure `[from source] (RG p.212-213)`.
- Solution: the *originator* creates a snapshot of its own state in an immutable *memento*; the *caretaker* keeps mementos but only sees metadata `[from source] (RG p.213-215)`. Three implementations: nested classes, intermediate interface, stricter encapsulation (memento tied to the originator) `[from source] (RG p.215-217)`.
- When to use: snapshots to restore state, "undo" and also transactions with rollback `[from source] (RG p.219-220)`. Cons: a lot of RAM if mementos are created frequently; caretakers must discard obsolete mementos; dynamic languages (PHP, Python, JavaScript) do not guarantee that the state in the memento remains intact `[from source] (RG p.221)`. Prototype can be a simpler alternative `[from source] (RG p.221)`.

## 6. Observer (RG p.223-233; GPP p.43-59)
- Intent (RG): subscription mechanism to notify several objects; aliases Event-Subscriber, Listener `[from source] (RG p.223)`. The object with the state of interest is the *publisher* (or subject); the interested parties are *subscribers* `[from source] (RG p.224)`.
- Solution: list of subscribers and methods to add/remove; all subscribers follow the same interface, which declares the notification method with context data `[from source] (RG p.225-227)`. The publisher can pass itself as an argument to the subscriber `[from source] (RG p.228, 232)`.
- When to use: a change in one object requires changing others and the set is dynamic/unknown (GUI); observation for a limited time `[from source] (RG p.231)`. Con: subscribers are notified in **random order** `[from source] (RG p.232)`. Mediator x Observer `[from source] (RG p.233)`.
- **GPP**: example of achievements triggered by notifications from the physics engine; the subject keeps a **list** of observers so that they do not interfere with each other `[from source] (GPP p.43-47)`. Difference "observer" (observes the thing) vs "event" (observes an object that represents the event) `[from source] (GPP p.48)`. The three complaints and answers: "it's slow" (notifying is walking the list and calling virtual methods; it is synchronous, so a slow observer blocks the subject; beware of locks and threads), "it allocates too much" (allocates only on registration; version with an intrusive linked list or node pool) `[from source] (GPP p.49-54)`.
- GPP, remaining problems: destroying subject/observer (dangling pointers; the observer must unregister, the subject can send a final notification, or the observer unregisters automatically) `[from source] (GPP p.55-56)`; **lapsed listener problem** in garbage-collected languages: the subject's list retains the observer, which becomes a "zombie" `[from source] (GPP p.56-57)`; difficulty reasoning about the flow, since the coupling is dynamic; use it when there is little communication between nearly independent modules `[from source] (GPP p.57-58)`. Today prefer observers as functions/closures; mention of *data binding* `[from source] (GPP p.58-59)`.
- Careful attribution: **weak references do not appear** in GPP; the remedy given is to unregister with discipline. Citing weak references is `[extrapolation]`.

## 7. State (RG p.235-246; GPP p.92-110)
- Intent (RG): the object changes its behavior when its internal state changes; "looks as if it changed its class"; related to finite-state machines `[from source] (RG p.235-236)`. `Document` example (Draft, Moderation, Published) and the weakness of `if/switch` in every method `[from source] (RG p.236-238)`.
- Solution: one class per state, the context delegates; the transition swaps the state object; states may know each other and initiate transitions (difference from Strategy) `[from source] (RG p.238-240)`. When to use and steps `[from source] (RG p.244-245)`. Con: overkill if there are few states or rare changes `[from source] (RG p.245)`. State can be seen as an extension of Strategy `[from source] (RG p.246)`.
- **GPP**: the platformer heroine with accumulated boolean flags (jumping in the air, ducking, diving) becomes an FSM; first with `enum` and `switch`, then with the state interface/classes `[from source] (GPP p.92-101)`. Static states (no fields; flyweight) vs instantiated (with state data, e.g., `chargeTime_`) `[from source] (GPP p.101-103)`; entry/exit actions `[from source] (GPP p.103-105)`.
- Limits: an FSM is not Turing complete; extensions: **concurrent machines** (one for what she does and another for what she carries: n+m states instead of n x m) `[from source] (GPP p.105-107)`, **hierarchical** (superstate through inheritance or a stack) `[from source] (GPP p.107-108)` and **pushdown automata** (push/pop to return to the previous state, e.g., firing) `[from source] (GPP p.109-110)`. Nystrom notes that game AI today tends toward *behavior trees* and planning `[from source] (GPP p.110)`.

## 8. Strategy (RG p.248-256)
- Intent: family of algorithms, each in a class, interchangeable `[from source] (RG p.248)`. Problem: a navigation app whose main class doubles with each new routing algorithm (car, walking, public transport) `[from source] (RG p.249)`. Solution: extract algorithms into strategies (`buildRoute`); the context does not choose, the client passes the strategy `[from source] (RG p.250)`.
- When to use: variants of an algorithm swappable at runtime; similar classes that differ only in one behavior; isolate business logic from algorithm detail; giant conditional that chooses the variant `[from source] (RG p.254-255)`. Cons: not worth it with few, rarely changed algorithms; the client must know the differences `[from source] (RG p.255)`.
- Modern languages with function types allow anonymous functions in place of strategy classes `[from source] (RG p.256)`. Template Method (inheritance, static) x Strategy (composition, at runtime); Decorator changes the "skin", Strategy the "guts" `[from source] (RG p.256)`.

## 9. Template Method (RG p.258-266)
- Intent: algorithm skeleton in the superclass; subclasses override steps without changing the structure `[from source] (RG p.258)`. Problem: data-mining classes for DOC, CSV and PDF with duplicated code `[from source] (RG p.259)`.
- Solution: steps become methods (abstract or with a default implementation) called by the *template method*, which should not be overridden; **hooks** are optional steps with an empty body `[from source] (RG p.260-261)`. Strategy-game AI example (`turn()` with collect resources, build, attack) `[from source] (RG p.262-265)`.
- When to use: let clients extend only parts of the algorithm; classes with nearly identical algorithms `[from source] (RG p.265)`. Cons: limited by the skeleton; may violate the LSP by suppressing a default step; harder to maintain with many steps `[from source] (RG p.266)`. Factory Method is a specialization of Template Method `[from source] (RG p.266)`.
- The "Hollywood Principle" does **not** appear in the PDF: do not attribute it.

## 10. Visitor (RG p.268-278)
- Intent: separate algorithms from the objects they operate on `[from source] (RG p.268)`. Problem: exporting a geographic graph to XML without being able to alter the node classes in production `[from source] (RG p.269-270)`.
- Solution: the new behavior goes into a *visitor* class with one method per element class; **double dispatch** (`accept` on the element calls the right method on the visitor) resolves the choice without conditionals; method overloading does not solve it because the exact class is not known in advance `[from source] (RG p.270-272)`. Structure `[from source] (RG p.273-274)`.
- When to use: an operation over all elements of a complex structure (tree); clean business logic of auxiliary behaviors; behavior that only makes sense in some classes of the hierarchy `[from source] (RG p.276-277)`. Cons: update all visitors when adding/removing an element class; limited access to private members `[from source] (RG p.278)`. Relations: Command, Composite, Iterator `[from source] (RG p.278)`.

## 11. Note on the Interpreter
The RG PDF does not contain the *Interpreter*. The word "Interpreter" appears in GPP in the Bytecode chapter as a VM concept (see `padroes-comportamentais-e-desacoplamento-em-jogos.md`); do not confuse it with the GoF pattern.
