# PostgreSQL 16: streaming replication, synchronous/quorum replication, hot standby, failover and pg_rewind

> Pages = PDF of the PG16 manual (16.15); printed = N − 38. Ch. 27 (HA, load balancing and replication) continues in `postgresql-16-backup-pitr-e-replicacao-ha.md` (overview p.815-818); what comes after it is here: log shipping standby (PG16 p.818-821), streaming, slots, cascading, **synchronous replication** (p.823-827), **failover** (p.827-828), **hot standby** (p.828-835), parameters (p.672-679, p.662-666) and `pg_rewind` (p.2256-2259). `[derived]` = calculation done in the package; the default values are the manual's.

## 1. Log shipping standby and streaming [from source]
- Planning: primary and standby should be as similar as possible; **tablespace paths are passed unchanged**, so the mount points must exist on both sides before `CREATE TABLESPACE`; the hardware architecture must be the same (32-bit to 64-bit does not work); log shipping between different **major** versions is not possible; different minor versions probably work, but without formal support, and when upgrading the minor version the safest policy is to upgrade **the standbys first** (PG16 p.819).
- A server enters standby mode if the file `standby.signal` exists in the data directory at startup; it continuously applies WAL, which can come from the archive (`restore_command`) or directly from the primary over TCP (streaming). At startup the cycle is: restore everything from the archive; if it runs out, try `pg_wal`; if that runs out and streaming is configured, connect to the primary; if it drops or there is no streaming, go back to the archive. The loop lasts until the server is stopped or promoted (`pg_ctl promote` or `pg_promote()`) (PG16 p.819).
- Preparing the primary: continuous archiving to a location accessible to the standby **even with the primary down**; for streaming, a role with permission and a `pg_hba.conf` line with the database field equal to `replication`; `max_wal_senders` and, if there are slots, `max_replication_slots` high enough; a base backup to create the standby (PG16 p.820). On the standby: restore the base backup, create `standby.signal`, set `restore_command`, keep `recovery_target_timeline = latest` (default) if there are several standbys and, for streaming, `primary_conninfo` (host, user, password); `archive_cleanup_command` with `pg_archivecleanup` cleans the archive, but if the archive is used for backup you must retain what is needed since the last base backup (PG16 p.820).
- **Streaming replication**: the primary sends the WAL records as they are generated, without waiting for the segment to fill. It is **asynchronous by default**, with a delay typically **under one second** if the standby keeps up with the load; with streaming, `archive_timeout` is not needed to reduce the loss window (PG16 p.821). Without a WAL archive, the primary may recycle segments before the standby receives them, and the standby would have to be recreated: avoid this with enough `wal_keep_size` or with a **replication slot**; with an archive accessible to the standby this is not necessary (PG16 p.821). A `walreceiver` process appears on the standby and a `walsender` on the primary (PG16 p.821).
- **Authentication**: the WAL stream allows extracting privileged information, so only trusted users should read it; the standby authenticates as a role with `REPLICATION` (or superuser), and the manual recommends a dedicated account with `REPLICATION` and `LOGIN`; `REPLICATION` gives high permissions but does not allow modifying data on the primary, unlike `SUPERUSER` (PG16 p.821-822). The password can be in `primary_conninfo` or in `~/.pgpass` with `replication` in the database field (PG16 p.822).
- **Lag monitoring** (PG16 p.822): compare `pg_current_wal_lsn` on the primary with `pg_last_wal_receive_lsn` on the standby; the `pg_stat_replication` view lists the WAL senders; a large difference between `pg_current_wal_lsn` and `sent_lsn` suggests high load on the primary; a difference between `sent_lsn` and the LSN received by the standby suggests network delay or an overloaded standby; on the standby, `pg_stat_wal_receiver` and the difference between `pg_last_wal_replay_lsn` and `flushed_lsn` indicate WAL arriving faster than it is replayed.
- **Replication slots** (PG16 p.822-823): guarantee that the primary **does not remove WAL** not yet received by all standbys and does not remove rows that would cause a recovery conflict even with the standby disconnected. They retain only what is necessary (unlike `wal_keep_size` and the archive, which usually retain more), but **can retain so much WAL that they fill `pg_wal`**; `max_slot_wal_keep_size` limits this (default **-1 = unlimited**; if the slot's `restart_lsn` falls behind, the standby may not be able to continue) (PG16 p.822, p.674). `hot_standby_feedback` alone, without a slot, does not protect during disconnected periods (PG16 p.822). Slot names: lowercase letters, numbers and `_`; `pg_create_physical_replication_slot('node_a_slot')` creates it, `primary_slot_name` on the standby uses it, `pg_replication_slots` shows it (PG16 p.822-823).
- **Cascading replication**: a standby can relay WAL to others (reduces connections to the primary and traffic between sites); each standby has only one upstream; cascading is **asynchronous** and the synchronous replication settings **have no effect** on it; hot standby feedback goes up the chain; if the upstream is promoted, the downstream ones continue with `recovery_target_timeline = latest` (PG16 p.823).

## 2. Synchronous replication [from source]
- By default streaming is asynchronous: if the primary fails, committed transactions may not have been replicated, and the loss is proportional to the lag at the instant of failover. Synchronous confirms that the changes were transferred to one or more synchronous standbys ("2-safe"; "group-1-safe" with `remote_write`). Each write commit waits for confirmation that the commit record was written to WAL on disk on the primary and on the standby: **the only possibility of loss is both failing at the same time**; the cost is longer response time, with a **minimum equal to the round-trip time** between primary and standby (PG16 p.824).
- **Who does not wait**: read-only transactions and rollbacks; subtransaction commits (only the top-level commit waits); long workloads such as data loads or index builds do not wait until the final commit; in two-phase commit, **both the prepare and the commit wait** (PG16 p.824). A synchronous standby can be physical, a logical replication subscriber or any consumer that knows how to send the feedback (for example `pg_receivewal`, `pg_recvlogical`) (PG16 p.824).
- **Minimum configuration**: non-empty `synchronous_standby_names` and `synchronous_commit = on` (the default). The standby name is the connection's `application_name` (in `primary_conninfo`; default: `cluster_name` or `walreceiver`); the default of `synchronous_standby_names` is empty, that is, **no synchronous replication** (PG16 p.824, p.675-676). The named standbys must be **connected directly to the primary** (the primary does not know cascading standbys). `synchronous_commit` can be changed per user, database or transaction (`SET LOCAL synchronous_commit TO OFF`), and `local` or `off` exempt a transaction from waiting for replication (PG16 p.824, p.664, p.676).
- **`synchronous_commit` levels with synchronous standbys** (PG16 p.663-664, Table 20.1): `remote_apply` waits for the standby to **apply** the record (visible to queries; much more latency; in simple cases it allows load balancing with causal consistency, PG16 p.825); `on` (default) waits for the **flush to disk** on the standby (not lost unless the primary and all synchronous standbys lose their storage); `remote_write` waits only for the **write to the operating system** of the standby, protects against a PostgreSQL crash on the standby but not against a crash of its OS; `local` waits only for the local flush; `off` does not wait (maximum delay of 3 × `wal_writer_delay`, with no risk of inconsistency: only loss of the last transactions). If `synchronous_standby_names` is empty, only `on` and `off` make a difference (PG16 p.663-664). With `remote_write` the manual also notes that data loss would only occur if the primary and standby crashed and the primary's database became corrupted at the same time; a fast shutdown request makes users stop waiting, and the server only finishes shutting down after sending the WAL to the connected standbys (PG16 p.824-825).
- **Several synchronous standbys** (PG16 p.825, syntax on p.675): `[FIRST] num_sync (s1, s2, ...)` or `ANY num_sync (s1, s2, ...)`. **FIRST** is priority-based: names earlier in the list have priority; if a current synchronous standby disconnects, it is **replaced immediately** by the next of highest priority. Example from the manual: with `FIRST 2 (s1, s2, s3)` and four standbys, **s1 and s2** are synchronous, **s3** is a candidate and takes over when s1 or s2 fails, and **s4 is asynchronous** (outside the list). **ANY** is quorum-based: the commit waits for the WAL on **at least `num_sync` standbys of any** in the list; `ANY 2 (s1, s2, s3)` waits for replies from any two among s1, s2 and s3, and s4 is asynchronous. `FIRST` is optional; the old syntax `s1, s2` is equivalent to `FIRST 1`; `*` matches any name; there is no check for duplicate names; names are compared case-insensitively (PG16 p.675-676). The `sync_state` column of `pg_stat_replication` shows `async`, `potential`, `sync` or `quorum` (PG16 p.856).
- **Performance planning** (PG16 p.825-826): waiting uses no resources, but **the transaction's locks remain held** until confirmation, so careless use increases response times and contention. The durability level can be set for the system, for users, connections or transactions; the manual's example is a workload with 10% important changes (customer data) and 90% less important changes (chat messages): synchronous is used only for the important ones. **Network bandwidth must be greater than the WAL generation rate** (PG16 p.826).
- **High availability planning** (PG16 p.826): with `synchronous_commit` at `on`, `remote_apply` or `remote_write`, commits "may **never complete** if any of the synchronous standbys goes down". The best solution is to keep as many synchronous standbys as requested, naming **several candidates** in `synchronous_standby_names`. In FIRST, those listed later take over; in ANY, all in the list are candidates and, if one fails, the others continue. If it is not possible to keep the requested number, **reduce the number of synchronous standbys (or disable it) and reload the configuration on the primary**. A newly connected standby is in *catchup* and only becomes synchronous on reaching the **streaming** state (visible in `pg_stat_replication`). If the primary restarts with commits waiting, those transactions are **marked as fully committed** at recovery; **there is no way to be sure that all standbys received all the WAL** at the moment of the crash, so some transactions may appear committed on the primary and not on the standby. **The guarantee is only this**: the application does not receive explicit commit confirmation until the WAL is safe on all synchronous standbys. If the primary becomes isolated from the standbys, fail over to the best candidate among the remaining ones. To recreate a standby while transactions are waiting, run `pg_backup_start()` and `pg_backup_stop()` in a session with `synchronous_commit = off`, otherwise those requests wait forever (PG16 p.826-827).
- `[derived]` **bandwidth vs. WAL rate**: 1 MB/s equals 8 Mbit/s. 40 MB/s of WAL requires 320 Mbit/s for the stream alone, not counting overhead; a 200 Mbit/s (25 MB/s) link cannot keep up, and with synchronous commit commits slow to ~25 MB/s of WAL while, in asynchronous mode, the standby falls further and further behind and WAL accumulates on the primary (or in the slots). The actual WAL volume comes from the pg_stat_wal view, column wal_bytes (PG16 p.865).
- `[derived]` **tolerance to failures** (from PG16 p.825-826): `FIRST 2 (s1, s2)` without a third candidate: if s2 fails, **there is no reserve** and commits wait until s2 returns or the configuration changes; `FIRST 2 (s1, s2, s3)` and `ANY 2 (s1, s2, s3)` tolerate **one** failure; `ANY 2 (s1, s2, s3, s4)` tolerates two. s4 outside the list never counts.

## 2b. `pg_receivewal` as a WAL archiver and synchronous standby [from source] (PG16 p.2159-2161)
- **What it is** (PG16 p.2159): receives the WAL of a running cluster through the replication protocol in **real time** and writes it to a local directory, which can be the archive location for PITR. It does not wait for the segment to close (unlike `archive_command` and `archive_library`); therefore **`archive_timeout` is not needed**.
- **Default flush** (PG16 p.2159): unlike a standby's WAL receiver, `pg_receivewal` by default only does **flush when the WAL file is closed**; to flush in real time you need `--synchronous` (which writes to disk right after receiving and sends the status to the server immediately, p.2160-2161). `--no-sync` turns off forced flush and is incompatible with `--synchronous` (p.2160).
- **Risk with `remote_apply`** (PG16 p.2159): since it does not apply the WAL, **it must not be allowed to become a synchronous standby when `synchronous_commit` is `remote_apply`**; it would look like a standby that never catches up with the primary and commits would **block**. The manual's **three ways out** (all on p.2159, not on p.826-827): (1) set `synchronous_standby_names` to a suitable value; (2) give `pg_receivewal` an `application_name` that **does not match** it; (3) change `synchronous_commit` to something **other than `remote_apply`**.
- **With a slot** (PG16 p.2160-2161): `--slot` requires an existing slot and the program reports the flush position to the server; if it is a synchronous standby, the flush report only happens when the file is closed, which makes primary transactions wait a long time and the configuration **not work well**; you must **add `--synchronous`**. `--synchronous` should always be used when the client is a synchronous standby, so the feedback is timely.
- **Connection and privileges** (PG16 p.2159): uses a normal connection with the replication protocol; the user needs `REPLICATION` (or be a superuser), `pg_hba.conf` must allow the replication connection and `max_wal_senders` must leave at least one session free.
- **Starting point in three steps** (PG16 p.2159): (1) scan the output directory, find the **last complete segment** and start at the beginning of the **next**; (2) if that fails and there is a slot, issue `READ_REPLICATION_SLOT` and use the slot's `restart_lsn` (**only with PG server 15 or later**); (3) otherwise, use the flush position reported by `IDENTIFY_SYSTEM`.
- **Reconnection and termination** (PG16 p.2159): on a non-fatal error connecting or on a drop, it **retries reconnecting indefinitely**; `-n`/`--no-loop` exits at once with an error. Without a fatal error, it runs until `SIGINT` or `SIGTERM`.
- **Stop and status** (PG16 p.2160): `-E`/`--endpos` stops on reaching an LSN with exit 0 (the record with the exactly equal LSN is processed). `--status-interval` default **10 s** (zero turns off the periodic packets, but the server may still request one).
- **Compression** (PG16 p.2161): `-Z`/`--compress` accepts `gzip` and `lz4` (suffixes `.gz`/`.lz4`) or `none`.
- `[inference]` when the question is what the manual presents for the **command**, cite **p.2159**, the command's page, and not neighboring pages on synchronous replication; p.826-827 deal with HA planning for synchronous replication in general and do not list these three ways out.

## 3. Failover [from source]
- If the **primary** fails, the standby starts the failover; if the **standby** fails, there is no failover: if it can be restarted, recovery restarts from where it stopped ("restartable recovery"); otherwise, create a new one (PG16 p.827).
- If the old primary comes back after the standby has become primary, a mechanism is needed to tell the old one that it is **no longer the primary**: **STONITH** (Shoot The Other Node In The Head), necessary to prevent two systems from believing themselves primary, which leads to confusion and data loss (PG16 p.827).
- Many failover systems use two nodes connected by *heartbeat*; a third (**witness server**) avoids certain improper failovers, but the extra complexity only pays off with careful configuration and rigorous testing (PG16 p.827).
- **PostgreSQL does not provide the software that identifies the primary's failure and notifies the standby**: there are many tools that integrate with the operating system (for example, IP address migration) (PG16 p.827). After failover there is only one server (*degenerate state*); a standby must be recreated, on the old primary or on a third system, and **`pg_rewind` can speed this up in large clusters** (PG16 p.827). Regularly switching primary and standby allows maintenance and tests failover; written procedures are recommended; to promote use `pg_ctl promote` or `pg_promote()` (PG16 p.827-828). Reporting-only servers (read offload) need not be promoted (PG16 p.828).

## 4. Hot standby [from source]
- **Overview**: with `hot_standby` on (default `on`, only at startup) the standby accepts connections after reaching a consistent state; all are **strictly read-only**, not even temporary tables can be written. It is **eventually consistent** with the primary; the replicated commit becomes visible to new standby snapshots (PG16 p.828, p.676). Transactions in hot standby **never receive an XID** nor write WAL (PG16 p.828).
- **Allowed**: `SELECT`, `COPY TO`, cursors, `SHOW`, `SET`, `RESET`, `BEGIN`, `END`, `ABORT`, savepoints, `LOCK TABLE` only in `ACCESS SHARE`, `ROW SHARE` or `ROW EXCLUSIVE` modes, `PREPARE`, `EXECUTE`, `LOAD`, `UNLISTEN` (PG16 p.828). **Error**: DML (`INSERT/UPDATE/DELETE/MERGE/COPY FROM/TRUNCATE`), DDL, `SELECT ... FOR SHARE/UPDATE`, `LOCK` in a mode above `ROW EXCLUSIVE` (including the short `LOCK`, which requests `ACCESS EXCLUSIVE`), `BEGIN READ WRITE` (and `START TRANSACTION READ WRITE`), the two-phase commit commands (`PREPARE TRANSACTION`, `COMMIT PREPARED`, `ROLLBACK PREPARED`), `nextval()`, `setval()`, `LISTEN`, `NOTIFY` (PG16 p.829). `SHOW in_hot_standby` indicates whether the session is in hot standby; sessions stay connected on promotion (PG16 p.829). **Before PG 14 the `in_hot_standby` parameter did not exist; the manual indicates `SHOW transaction_read_only` as a viable substitute on old servers** (PG16 p.829). During hot standby `transaction_read_only` is **always true and cannot be changed** (PG16 p.829). The function `pg_is_in_recovery()` also reports recovery (Table 9.92, PG16 p.437). In normal read-only mode `LISTEN` and `NOTIFY` are allowed, so the standby is slightly more restrictive than an ordinary read-only session, and the manual says some restrictions may be relaxed in the future (PG16 p.829).
- **Query conflicts** (PG16 p.829-831): `ACCESS EXCLUSIVE` locks on the primary (explicit LOCK and various DDL), `DROP TABLESPACE`, `DROP DATABASE` (conflicts with the **sessions** connected to that database on the standby, not with a query; see the note from p.834 below) and the application of vacuum cleanup records (which conflicts with standby snapshots that still "see" the rows, and with queries accessing the page). On the standby there is no choice: the WAL **has already happened** on the primary, so the conflicting query is **canceled** after a maximum delay (**except `DROP DATABASE`, which waits no delay at all**, PG16 p.834): `max_standby_archive_delay` (WAL read from the archive) and `max_standby_streaming_delay` (WAL via streaming), **default 30 s each (value in PG16 p.677)**, `-1` = wait forever. They measure the time since the WAL was **received**, not the maximum duration of a query; if a query was delayed considerably, the following ones have little slack. For a high-availability standby use short delays (perhaps zero); for long decision-support queries, hours or `-1`, knowing that a long delay makes other standby sessions not see recent changes (PG16 p.830, p.833, p.676-677). The cancellation is usually just a cancel error (the query can be retried), but, when replaying a `DROP DATABASE`, the conflicting session is terminated entirely (not just the query), and a conflict from an idle-in-transaction lock also terminates the session (PG16 p.831; in the `DROP DATABASE` case the disconnection is immediate, regardless of `max_standby_streaming_delay`, PG16 p.834).
- **Most common cause**: "early cleanup": the primary removes row versions that a standby snapshot still sees; index-only scans require the visibility map to "agree" with the snapshot, so even a VACUUM with no rows to clean can cause a conflict. Tables heavily updated on the primary quickly cancel long queries on the standby (PG16 p.831). Remedy: **`hot_standby_feedback`** (default `off`), which prevents vacuum from removing recently dead rows, at the cost of **bloat on the primary** (at worst equal to running the query on the primary); with standbys that connect and disconnect, consider increasing `max_standby_archive_delay` and `max_standby_streaming_delay`. The feedback **does not override** the primary's `old_snapshot_threshold` (PG16 p.831, p.677-678). Count and reason of cancellations: `pg_stat_database_conflicts` (on the standby); `log_recovery_conflict_waits` logs waits longer than `deadlock_timeout` (PG16 p.831).
- **Administration** (PG16 p.831-834): the standby only accepts connections after reaching the consistent state (messages `consistent recovery state reached` / `ready to accept read-only connections`); hot standby cannot be turned on by reading WAL written with `wal_level` below `replica`; the consistent state may be delayed with more than **64 subtransactions** in a write transaction or very long transactions (PG16 p.832, p.835). Parameters that size shared memory must be **greater than or equal on the standby** than on the primary: `max_connections`, `max_prepared_transactions`, `max_locks_per_transaction`, `max_wal_senders`, `max_worker_processes`; to increase them, change the standbys **first**; to decrease them, the primary first; if the standby finds a larger value than its own in the WAL, it logs a warning and **pauses recovery** (PG16 p.832-833). Not accepted on the standby: DDL, `GRANT`, `REVOKE`, `ANALYZE`, `VACUUM`, `CLUSTER`, `REINDEX`, that is, **indexes or statistics cannot be created only on the standby**; `pg_prepared_xacts` is always empty during recovery; advisory locks work only locally and never conflict with replay; trigger-based replication (Slony, Londiste, Bucardo) does not run on the standby; autovacuum does not run during recovery; the checkpointer performs *restartpoints* and `CHECKPOINT` on the standby performs a restartpoint; cumulative statistics count local reads, but replay does not increment the table counters (PG16 p.833-834). The standby still writes to disk (hint bits, temporary sort files), so no part is "truly read-only" (PG16 p.833).
- **`DROP DATABASE` on standby: immediate disconnection; `RENAME` and `DROP ROLE` on the primary, as seen on the standby** (PG16 p.834): `DROP DATABASE` or `ALTER DATABASE ... SET TABLESPACE` on the primary generates a WAL entry that **forcibly disconnects, immediately, all users connected to that database on the standby, whatever the value of `max_standby_streaming_delay`** (so the assumption "`DROP DATABASE` only cancels the query after the configured delay" is **false**). `ALTER DATABASE ... RENAME` does **not** disconnect anyone, which normally goes unnoticed but can confuse a program that depends on the database name. `DROP USER`/`DROP ROLE` of a role with `LOGIN` that is still connected **does not disconnect it**, neither in normal mode nor in recovery: it stays connected, it just **cannot reconnect**; so a `DROP ROLE` on the primary does not drop that user's session on the standby.
- **Limitations** (PG16 p.835): the **Serializable level is not yet available** in hot standby (trying raises an error), which also applies to logical replicas, and so the manual suggests Repeatable Read with explicit locks on the primary (PG16 p.835, p.537); `AccessExclusiveLocks` of prepared transactions require twice as many entries in the lock table (increase `max_locks_per_transaction`, perhaps to double the primary's, if using many prepared transactions) (PG16 p.835).

## 6. `pg_rewind` and `wal_log_hints` [from source]
- **`pg_rewind`** synchronizes a data directory with another copy of the **same cluster** whose timelines have diverged; the typical scenario is bringing an old primary back as a standby of the new primary. Instead of a new base backup or `rsync`, it **neither compares nor copies unchanged blocks**: only the changed blocks of existing relation files are copied; the other files (new relations, configuration, WAL segments) are copied whole; so it is much faster when the database is large and few blocks diverge (PG16 p.2256). It examines the timeline histories to find the divergence point and **expects to find in the target's `pg_wal` the WAL since that point**; if the target kept running a long time after the divergence, copy the WAL from the archive or use **`-c`/`--restore-target-wal`** (uses the target's `restore_command`) (PG16 p.2256-2257). It is not only for failover: a promoted standby that executed transactions can be "rewound" and return to being a standby (PG16 p.2256).
- **Prerequisites**: the target needs **`wal_log_hints` on or data checksums enabled at `initdb`** (neither is default) and **`full_page_writes = on`** (default) (PG16 p.2256). The target must have been **shut down cleanly** (PG16 p.2257); by default, if it was not, `pg_rewind` **starts the target in single-user mode** to complete crash recovery and stops it; **`--no-ensure-shutdown` skips this and fails immediately** if the shutdown was not clean, leaving the user to handle the situation (it is not a safety shortcut) (PG16 p.2258).
- **Source**: `--source-pgdata` (source shut down cleanly) or `--source-server=connstr` (running source; **normal, non-replication** connection, with a superuser role **or** with `EXECUTE` on `pg_ls_dir(text, boolean, boolean)`, `pg_stat_file(text, boolean)` and both forms of `pg_read_binary_file`; the manual gives the example `rewind_user`) (PG16 p.2257-2258). `-R` creates `standby.signal` and appends the connection to `postgresql.auto.conf` (requires `--source-server`); `-n` is *dry-run*; `-N` does not wait for fsync (faster, but an OS crash may corrupt; for tests) (PG16 p.2257). **Note**: `pg_rewind` **copies whole configuration files from the source**; the recovery configuration may need correcting before restarting the target, otherwise it may diverge again; it fails immediately if it finds files it cannot write (for example, shared read-only SSL keys) (PG16 p.2256-2257).
- **Manual warning**: if `pg_rewind` **fails midway**, the target's data directory is probably **not recoverable**; take a **new backup** (PG16 p.2256). After the rewind, the target still needs to replay WAL (creates `backup_label` and sets the minimum consistency in `pg_control`); at startup it enters recovery and replays the source's WAL from the last checkpoint before the divergence; if part of the WAL was no longer on the source, create `recovery.signal` and configure `restore_command` (PG16 p.2256, p.2259). How it works: scans the target's WAL since the last checkpoint before the divergence noting the touched blocks; copies those blocks from the source; copies the other files (omitting directories such as `pg_replslot/`, `pg_dynshmem/`, `pg_notify/`, `pg_serial/`, `pg_snapshots/`, `pg_stat_tmp/`, `pg_subtrans/`, and files such as `backup_label` and `postmaster.pid`) (PG16 p.2258-2259).
- **`wal_log_hints`** (default **off**, startup only): when on, the server writes the **whole page** to WAL on the first modification after a checkpoint, even for non-critical *hint bit* modifications; with data checksums enabled, hint-bit updates are **always** logged to WAL and the parameter is ignored; it also serves to test how much extra WAL checksums would cause (PG16 p.665). `wal_compression` (default **off**; `pglz`, `lz4` or `zstd` if compiled; `on` is a historical spelling of `pglz`) compresses the full-page images in WAL, reducing volume at the cost of CPU on write and replay, without increasing the risk of corruption (PG16 p.665).

## 7. [inference]
- The recommendation "use `ANY` with a number of candidates greater than the number of synchronous standbys required" follows from what the manual says about commits that may never complete and about naming several candidates (PG16 p.826); the manual does not prescribe a topology. 
- A primary with `FIRST 1 (s1)` and a single synchronous standby becomes a single point of waiting: if s1 fails, writes hang (PG16 p.826) until the number is reduced or synchronous replication is disabled.

## 8. [extrapolation] and what the sources do NOT say
- **Automatic failover** (Patroni, repmgr, pg_auto_failover, Kubernetes operators): not in the manual; the text says only that PostgreSQL does not provide the detection software and that tools exist (PG16 p.827). Label any comparison among them `[extrapolation]`.
- The manual gives no RPO/RTO in numbers beyond "typically under one second" of asynchronous lag (PG16 p.821) and the minimum wait time equal to the round-trip (PG16 p.824); it gives no "acceptable" lag thresholds.
- "Guaranteed zero data loss" is **not** a promise of the manual: what is guaranteed is only the client-confirmation rule described in PG16 p.826; loss is only impossible if there is no simultaneous failure of primary and synchronous standbys (p.824).
- Native incremental backup, `pg_combinebackup`, and PostgreSQL 17+ features are not in the sources (PG16 16.15).
