# Canonical Go glossary

Sources covered now: Effective Go (Eff), Little Go Book (Little), Go Spec go1.26 via the distilled notes in regras-da-spec.md (Spec), and Go 1.20 to 1.24 release notes via versoes-e-migracao.md (RN1.20 to RN1.24). Go 1.25 and 1.26 have no release notes here.
How to cite: use the source suffix already present in each entry, in the format (Eff p.N), (Spec p.N), (Little p.N) or (RN1.xx p.N); ranges as p.N–M.
Marks: DATED = old source (Eff 2009; Little on go1.3.3/GOPATH); [inference] = link I made between entries, not stated by the source. No outside knowledge: what the sources only announce appears as "announced, no detail".

## 1. Types and values

- **zero value** — value that every variable declared without an initializer receives (0, `false`, `""`); it also applies to omitted struct fields (Little p.23, p.29). In a composite literal with `field: value`, whatever is omitted is zeroed (Eff p.16). The Spec defines zero recursively: `false`, `0`, `""`, and `nil` for pointer, function, interface, slice, channel and map (Spec p.108); function results also start zeroed (Spec p.95).
- **Declaration forms (`var`, `:=`, `=`)** — `var N T` declares at the zero value; `N := v` declares, assigns and infers the type; `N = v` only assigns to an existing variable (Little p.24). Repeating `:=` for the same variable in the same scope is an error (Little p.23–24).
- **Redeclaration in `:=`** — in a multiple assignment, `:=` is accepted if at least one variable on the left is new; the others just receive the value, without changing type (Eff p.7; Little p.24). Sources agree; Eff adds that the old variable must be in the same scope and the value must be assignable to it.
- **rune** — Go's term for a Unicode code point (Eff p.9).
- **Composite literal** — expression that creates a new instance on each evaluation; positional fields (all present) or named fields (free order) (Eff p.16). Little calls it a struct literal: positional only suits a few fields, and in a multiline literal the trailing comma is mandatory (Little p.29).
- **Array** — fixed-size value; the size is part of the type (`[10]int` ≠ `[20]int`) and assigning copies everything (Eff p.17–18; Little p.41). Little adds that out-of-range access causes a compile-time or run-time error (Little p.41).
- **Functions as a first-class type** — you can declare a function type and use it as a field, parameter or return; Little presents it as an alternative to interfaces for decoupling (Little p.70).
- **Multiple returns** — functions return several values, with a frequent `value, ok` pattern (Little p.25); consecutive parameters of the same type allow a short form (Little p.25).
- **Named result parameters** — named results, initialized to the zero value and returned by a bare `return` (Eff p.12). Difference in emphasis: Little mentions them only as uncommon, without detail (Little p.25).
- **Nature of the language** — compiled, statically typed, C-style syntax, with garbage collection; binary with no additional dependencies (Little p.14–15). Not classic OO: no objects, inheritance, polymorphism by inheritance or overloading; there are structs with methods and composition (Little p.28).

## 2. Pointers, methods and receivers

- **Pointer (`&X`, `*T`)** — `&X` gets the address; `*T` is the type "pointer to T", distinct from `T` (Little p.29–30).
- **Pass by copy** — arguments are always copied; when passing a pointer the address is copied, and it still points to the same data (Little p.30). [inference] Combined with Eff p.17, 19 (slice by value, shared array), this explains why mutation through a slice is visible to the caller.
- **Method and receiver** — function with a receiver, e.g. `func (s *Saiyan) Super()` (Little p.31).
- **Value vs. pointer receiver** — value methods work for values and pointers; pointer methods only for pointers, except when the value is addressable and the compiler inserts `&` (Eff p.29). Little does not discuss the relation to implementing interfaces and its examples alternate value and pointer without comment (Little p.58, p.77–78). The author's personal preference (not a rule): "when in doubt, use a pointer" (Little p.37).
- **new(T)** — allocates zeroed storage and returns `*T`, with no other initialization (Eff p.15). Little: `new(X)` is equivalent to `&X{}`, and he prefers `&X{}` (Little p.32–33). Eff records an update: `new` accepting an expression as an argument, from Go 1.26 (Eff p.15) — a recent touch-up on 2009 text.
- **Factory function (`NewX`)** — replaces constructors, which do not exist; can return a pointer or a value (Little p.32).
- **Embedding / composition** — including a type in a struct (or interface) without a field name to reuse its implementation; it is not subclassing (Eff p.39–40). Fields and methods are directly accessible and the implicit field name is the type's name (Little p.35–36). The outer type's method "overrides" the embedded one, which stays accessible as `s.Person.Introduce()` (Little p.36).
- **No overloading** — hence names like `Load`, `LoadById`, `LoadByName` (Little p.36).

## 3. Slices, maps and strings

- **Slice** — descriptor with a pointer to the underlying array, length and capacity; passed by value, but shares the array (Eff p.17, 19). Little: lightweight structure over a portion of the array; day to day you use slices, not arrays (Little p.42).
- **len / cap** — `len` is the slice's size; `cap` is the underlying array's (Little p.42).
- **make(T, args)** — only for slices, maps and channels; returns an initialized T, not a pointer (Eff p.17). For slices, `make([]T, n)` gives len=cap=n and `make([]T, 0, n)` gives len 0 and cap n; use `make`, not `new`, because the array must be allocated and the slice initialized (Little p.42).
- **append** — returns the resulting slice; if the array is full, it creates a larger one and copies, so the result must be reassigned (Little p.43). DATED: the prediction that capacity "doubles" (10, 20, 40) is a hypothetical assumption of the author, not a specification guarantee; do not use it as a contract (Little p.43).
- **Slicing `[X:Y]`** — from X (inclusive) to Y (exclusive); `[X:]`, `[:Y]` are shortcuts; no negative indexes; also works on strings (Little p.45).
- **A slice is a window, not a copy** — unlike languages where "slice" copies, changing the slice changes the original array (Little p.44–45).
- **copy(destination, source)** — only two arguments, thanks to slices (Little p.45).
- **Map** — dictionary created with `make(map[K]V)` or a literal; initial size optional; `len` counts keys; `delete` returns no value and accepts a nonexistent key (Little p.47).
- **"comma ok" idiom** — `v, ok := m[k]` (or `x.(T)`) distinguishes absence from the zero value; a missing key returns the zero value and `false` (Eff p.21, 32; Little p.47). Spec: also applies to type assertion (`v, ok`: zero value without panic; the single form panics on failure) (Spec p.56) and to channel receive, where `ok` is true only for an actual send (Spec p.70–71).
- **Map iteration** — `range` over a map yields pairs in random order (Little p.48).
- **fmt verbs** — `%v` default; `%+v` with field names; `%#v` Go syntax; `%T` type; `%q` quotes; `%x` hex (accepts strings and byte slices) (Eff p.23). Shallow coverage; Eff refers to the package documentation (Eff p.25).

## 4. Interfaces

- **Interface** — set of methods that specifies behavior; a contract without implementation (Eff p.29, 38; Little p.58).
- **Implicit implementation** — it is enough for the type to have the methods with the right signature; Little associates this with the tendency toward small, focused interfaces (Little p.58).
- **Composed interfaces** — interface formed from others, such as `io.ReadCloser` = `io.Reader` + `io.Closer` (Little p.59). [inference] It is the same embedding mechanism described in Eff p.39–40, applied to interfaces.
- **Empty interface (`interface{}`)** — satisfied by any type, since it has zero methods (Little p.68). DATED: spelling used in both sources (Eff p.11, 25; Little p.68); Eff does not mark it as old, but the general 2009 warning applies.
- **Interface conversion / type switch** — `.(TYPE)` converts; `switch x := v.(type)` gives the variable the corresponding type in each clause (Eff p.11; Little p.68).
- **Blank identifier `_`** — destination that discards the value, like /dev/null (Eff p.36); it does not actually assign, and can be reused with any type (Little p.25). Spec: it only serves as a left-hand operand of an assignment, does not create a binding and cannot be on the left of `op=` (Spec p.30, p.43, p.82); in an import, `_` only initializes the package (Spec p.106–107). A package name also cannot be `_` (Spec p.106).

## 5. Errors

- **error** — built-in interface with the method `Error() string` (Eff p.48; Little p.63).
- **Errors as values** — preferred strategy: return an error, do not throw an exception (Little p.63). Simple creation with `errors.New("msg")` (Little p.63).
- **Sentinel error** — exported package-level error variable (such as `io.EOF`), compared with `==` by the consumer (Little p.64). DATED/limit: Little does not cover wrapping, `errors.Is/As` or errors with fields; Eff does not cover modern errors either. Another source is needed.

## 6. Concurrency

- **Goroutine** — function executing concurrently in the same address space; lightweight, with a small stack that grows, multiplexed onto OS threads (Eff p.42). Little: scheduled by the runtime, M:N model, cost of a few KB, "millions" on modern hardware (author's claim); started with `go f()` or `go func(){...}()` (Little p.73). The process does not wait for goroutines on exit (Little p.73).
- **Concurrency vs. parallelism** — concurrency is structuring the program into independent components; parallelism is running computations simultaneously on several CPUs (Eff p.47). `runtime.NumCPU/GOMAXPROCS` appear in Eff p.46–47 without an old-text mark; be cautious.
- **Channel** — typed conduit between goroutines: `make(chan int)`, send `c <- v`, receive `v := <-c` (Little p.77). Send and receive block; each value reaches a single receiver (Little p.77, 79).
- **Unbuffered vs. buffered channel** — unbuffered (default, size 0) combines communication and synchronization; with a buffer the sender blocks only when full (Eff p.43). Little: the buffer is a queue to absorb spikes, it does not increase processing capacity; `len(c)` shows queued items (Little p.79).
- **select** — chooses among channel operations, with syntax similar to `switch` (Little p.80). `time.After(d)` returns a channel that receives after `d`, useful for a timeout in `select` (Little p.80–81).
- **sync.Mutex / sync.RWMutex** — the Mutex zero value is already unlocked; RWMutex adds `RLock`/`RUnlock` for multiple readers and exclusive writing (Little p.75–76). `sync/atomic` is only mentioned (Little p.74, p.82).
- **Shared loop variable** — DATED: the `Serve` example (goroutine per request) has a shared loop variable bug in versions before Go 1.22; Eff itself warns about it (Eff p.44). Confirmed: since 1.22 each iteration has its own variables (see "Per-iteration loop variable", section 13).
- **Concurrency gaps** — Eff and Little do not cover `close`, `range` over a channel, `sync.WaitGroup`, `context` or cancellation; Little's workers have an infinite loop with no shutdown (Little p.77–78). The Spec defines `close` and receiving on a closed channel (Spec p.99–100, p.70–71) and `range` over a channel (Spec p.89–90), but gives no usage guidance; `sync.WaitGroup`, `context` and `errgroup` appear in none of the four sources. Absence does not mean discouraged.

## 7. Generics

Eff and Little do not cover generics (Eff p.1); everything below comes from the Spec and the release notes.

- **Type parameter** — Go 1.18. Each parameter is a new named type, which serves as a placeholder until instantiation. Non-blank names are unique and all must exist; `[_ any]` is valid (Spec p.36–37). A function literal does not declare type parameters, and methods only use those of the receiver (Spec p.46, p.41–42). Local types in a generic function: accepted since 1.20 (RN1.20 p.5).
- **Constraint** — interface that limits the type arguments. If it is `interface{E}` with E a type element, the `interface{}` can be omitted in the list (`[T ~int]`, `[T int|string]`); outside a parameter list this is illegal (Spec p.37–38). In `type T[P *C] ...` the parser reads an array; resolve it with `interface{*C}` or a trailing comma (Spec p.37).
- **Type set** — set of types that an interface defines. Empty = all non-interface types; with several elements = intersection; method = non-interface types whose method set includes it; `T` = only T; `~T` = types whose underlying type is T; union = union of the sets. Never contains interfaces (Spec p.21–22). `interface{ int; string }` has an empty type set: it compiles, but cannot be instantiated (Spec p.22, p.43); in review, be suspicious [inference].
- **`~T`** — valid when the underlying type of T is T itself and T is not an interface; `~MyInt` and `~error` are illegal (Spec p.22).
- **Union of terms** — non-interface terms have disjoint type sets (`~int | MyInt` is illegal). A union with more than one term cannot contain `comparable` or an interface with methods (Spec p.23).
- **`comparable`** — Go 1.18; set of strictly comparable non-interface types. Interfaces are comparable but not strictly, so they do not implement it (Spec p.38). Go 1.20 change: they came to satisfy it, so `any` works in `[K comparable]`, with a risk of panic on comparison (Spec p.38–39, p.116; RN1.20 p.2).
- **Implementing vs. satisfying** — non-interface T implements I if it is in I's type set; interface T, if its type set is a subset. T satisfies C if it implements C, or if C is `interface{ comparable; E }` with E basic and T is comparable and implements E (Spec p.24, p.38).
- **Instantiation** — two steps: substitute the type args throughout the declaration and check that each satisfies the already-substituted constraint. The instantiated type becomes a non-generic named type; the instantiated function, a non-generic function (Spec p.58). A generic function must be instantiated before being called or used as a value (Spec p.41); for generic types the args are always explicit (Spec p.60).
- **Type argument inference** — solves a system of equations over the parameters without an explicit argument: assignability between parameter and argument, plus each parameter's constraint; typed operands first, then untyped constants, with the default type (Spec p.60–62). A partial list is a prefix; `apply[]` is illegal; `x := sum` requires a list (Spec p.59). Go 1.21 broadened it: generic function as an argument or assigned without instantiation, and interface methods in inference (RN1.21 p.2; Spec p.116). The appendix's unification rules can be ignored when writing code (Spec p.116–117).
- **Generic alias** — type alias with parameters; preview in 1.23 via `GOEXPERIMENT=aliastypeparams`, full support in 1.24; must be instantiated when used (Spec p.34, p.116; RN1.23 p.1; RN1.24 p.1). `noaliastypeparams` disables it; the `aliastypeparams` option goes away in 1.25 (RN1.24 p.1).
- **Operations on type parameters** — require validity for the whole type set (index, range, receive, literal, operators); type assertion and type switch require an interface operand, not a type parameter (Spec p.44, p.53, p.56, p.66, p.85).

## 8. Packages, modules and tooling

- **Export by capitalization** — first letter uppercase = visible outside the package; lowercase = private to the package. Applies to types, functions, fields and, according to Little, constants and globals (Eff p.3; Little p.56, p.60).
- **package vs. import path** — the name in `package` is a single identifier (e.g. `db`); the import path is complete (e.g. `shopping/db`) (Little p.53). Executable: `main` in `package main` (Little p.19).
- **MixedCaps** — convention for multi-word names, without underscores (Eff p.5).
- **doc comment** — comment immediately before a top-level declaration, with no blank line; it is the primary documentation of a package/command (Eff p.3).
- **init** — function with no arguments per file (there can be several); runs after the package's variable initializers and the initialization of imported packages (Eff p.28). Spec: `init` does not create a binding and, in the package block, can only be a function (Spec p.30). See "Package initialization order" in section 12.
- **gofmt / go fmt** — rewrites the code in the standard style; `go fmt` per package, `gofmt` per file (Eff p.2). Little mentions `go fmt ./...` (Little p.66).
- **Automatic semicolon insertion** — the lexer inserts `;` after a newline when the last token can end a statement (Eff p.5). Little says only that you do not write `;` at the end of a line and that parentheses around conditions are not mandatory (Little p.17).
- **GOPATH / workspace** — DATED: model with manual `bin`, `pkg`, `src` folders, `GOPATH` and `PATH`; project packages resolved from `$GOPATH/src` (Little p.10–12, p.53–55). Little does not discuss modules, and Eff warns that it does not cover modules (Eff p.1). Author's preference: `main/` in a subfolder (Little p.54).
- **go get** — DATED: downloads into the workspace without specifying a revision, always from head/master; goop and godep are cited as "young" tools (Little p.57). No native versioning in the book.
- **Other tools cited** — DATED: `godoc -http=:6060` (Little p.22), `go run --work` (Little p.19). There is no `go vet`, `go test`, race detector or `go mod` in Little; Eff does not cover tests.
- **Reference version** — Little shows `go1.3.3` (Little p.11–12); Eff is from 2009 and "not actively updated" (Eff p.1). Treat both as DATED for everything outside the core of the language.

## 9. Constants and conversions

- **iota** — constant enumerator, reusable in implicitly repeated expressions (Eff p.26). Spec: it is the ConstSpec index in the block, starting at 0, untyped; several uses in the same ConstSpec have the same value; outside a block it is 0; a line with a fixed value consumes an index; to type the sequence, declare the type on the first line (Spec p.33–34). Omitting the list in a parenthesized block repeats the previous list and type (Spec p.33).
- **Constants and globals** — Little mentions them only for the visibility rule (Little p.60). Numeric conversions and constant rules do not appear in Eff/Little; refer to the Spec.

## 10. Runtime, defer and panic

- **defer** — schedules a call to run immediately before the function returns; LIFO order; arguments evaluated at the moment of the `defer` (Eff p.13–14).
- **panic / recover** — panic unwinds the goroutine's stack running defers; recover, only useful in a deferred function, stops the unwinding and returns the panic value (Eff p.50). Little compares them to throw/catch and calls them rare (Little p.64). Spec: `panic(nil)` is a run-time panic, with no version stated (Spec p.105); the notes date it to 1.21: it becomes `*runtime.PanicNilError`, `recover` never returns nil during a panic, and `GODEBUG=panicnil=1` reverts it (automatic in a module with `go 1.20` or lower) (RN1.21 p.3). `defer` of a nil function panics at invocation, not at declaration (Spec p.97).
- **Garbage collection (GC)** — adds overhead, but eliminates a class of serious memory-freeing bugs (Little p.18).
- **Idealized examples** — some Eff examples are schematic (toy cube root, RPC, Counter without synchronization, regexp); they illustrate a concept, they are not production code (Eff p.34, 46, 50–51).

## 11. Types, constants and conversions in the Spec

- **Underlying type** — of a predeclared type or type literal it is the type itself; of a defined type, the one in the declaration; of a type parameter, that of its constraint. An alias does not create a type (Spec p.26).
- **Type definition vs. alias** — a definition creates a distinct type and does not inherit methods (`type NewMutex Mutex` has an empty method set; interface methods and methods of composite type elements remain). An alias (Go 1.9) is the same type, with no new methods (Spec p.34–36, p.115).
- **Type identity** — a named type is never identical to another type. The rest is structural: array (element and length), slice, pointer, map, channel (element and direction), function (arity, types, variadicity; parameter names do not count), interface (same type set), instantiated type (same generic and identical args), struct (same fields, names, types, tags and embedded; unexported names from different packages differ) (Spec p.17, p.27).
- **Assignability** — x of type V is assignable to T if: V and T identical; same underlying type, no type parameter, and at least one not named; channels with the same element, V bidirectional and one not named; T is an interface (not a type parameter) implemented by x; x is `nil` and T is a pointer, function, slice, map, channel or interface; x is an untyped constant representable in T (Spec p.28). [inference] `type A int` and `type B int` are not assignable to each other, since both are named.
- **Representability** — constant x is representable in T if it belongs to T's set of values; a float fits if it rounds without overflow. Spec examples: `1e10` fits in `uint64`; `1.1` does not fit in `int`; `1024` does not fit in `byte`; `'a'` does not fit in `string` (Spec p.28–29). For a type parameter, it holds for each type in the type set (Spec p.29).
- **Untyped constant** — literals, `true`, `false`, `iota` and expressions with only untyped operands. When it gets a type by use, it is an error if not representable. Default types: `bool`, `rune`, `int`, `float64`, `complex128`, `string` (Spec p.11–12). Numeric constants are exact, without overflow; hence there are no constants for -0, infinity or NaN (Spec p.11).
- **Static vs. dynamic type** — a variable of interface type has, besides the static type, a dynamic type: the (non-interface) type of the value assigned at run time, except if the value is the predeclared `nil`, which has no type (Spec p.12). [from source] The Spec example: after `x = v`, with `var v *T`, `x` has the value `(*T)(nil)` and dynamic type `*T` (Spec p.12). [from source] Two interfaces are equal if they have identical dynamic types and equal dynamic values, or if both are nil (Spec p.69). [inference] Combining p.12 and p.69, `x` in this case is not equal to `nil` (it has dynamic type `*T`), that is, `x != nil`; hence the "classic trap" of an interface holding a nil pointer. No source describes this trap and Effective Go (2009) does not cover it.
- **Method set** — of a defined type T: methods with receiver `T`; of `*T`: receiver `*T` or `T`; of an interface: intersection of the type set; other types: empty (Spec p.29–30). With embedding, S with embedded `T` has in S and `*S` the promoted ones with receiver `T`, and `*S` also those of `*T`; S with embedded `*T` has both in S and `*S` (Spec p.17). [inference] A struct by value with embedded `T` does not satisfy an interface that requires a method with receiver `*T`.
- **Conversion** — allowed between assignable types or types with the same underlying type (ignoring tags), integer and float, integer/`[]byte`/`[]rune` and string, slice to array pointer (1.17) and slice to array (1.20), with a panic if the slice is shorter (Spec p.72–76; RN1.20 p.1). Integer to integer never signals overflow; float to integer truncates toward zero (Spec p.73).
- **Map and channel (Spec)** — a nil map reads as empty, but writing to it panics; the key requires full `==` (Spec p.24, p.53). A nil channel is never ready; with no buffer a send only completes with a ready receiver; `close` of a closed or nil channel and a send on a closed one panic (Spec p.25, p.99–100).

## 12. Scope, addressing, evaluation and execution

- **Scope and shadowing** — blocks: universe, package, file, each `if`/`for`/`switch`, each `switch`/`select` clause. An inner block can redeclare; the inner entity applies while visible. A local const/var has scope from the end of the Spec to the end of the innermost block (Spec p.30–31). [inference] Hence `x := x` reads the outer `x`, and predeclared identifiers can be shadowed.
- **Addressability** — `&x` requires a variable, pointer indirection, slice index, addressable struct field or addressable array index; or a composite literal. A call result is not addressable (`makeT().Mp()` is invalid); `&*x` with nil x panics (Spec p.52, p.70). Map elements are not in the list, so `&m[k]` is not valid [inference]. The sources do not use the term "place".
- **Evaluation order** — calls, receives and binary logical operators proceed left to right; the order between this and reading variables or indexing is not specified (`[]int{a, f()}` can give `[1,2]` or `[2,2]` if `f` changes `a`) (Spec p.77–78). `&&` and `||` evaluate the right side only if needed (Spec p.70). [inference] In review, be suspicious of an expression that reads a variable and calls something that changes it.
- **Package initialization order** — the order among files depends on how they are presented to the compiler; initialization dependencies take precedence over left-to-right order (Spec p.78, p.109–110). Packages: sorted by import path, repeating the step of taking the first one whose imports have already been initialized (Spec p.111; RN1.21 p.1–2). Anyone who relied on an order not expressed by imports may see behavior change in 1.21; the notes do not cite GODEBUG for this.
- **Run-time errors** — they are panics with a `runtime.Error` value (satisfies `error`): index out of range, integer division by zero, nil pointer, write to a nil map, failed type assertion, short slice-to-array conversion (Spec p.111–112).

## 13. Iteration, range and loop variable

- **Per-iteration loop variable** — Go 1.22: each iteration has its own variables; the next one is created before the post statement, with the previous one's value at that instant; closures, goroutines and `defer` capture the value of their own iteration (Spec p.88; RN1.22 p.1). It depends on the file's language version: a module with an earlier `go` keeps the old behavior (RN1.22 p.3). That `i := i` becomes unnecessary in 1.22+ is a consequence [inference].
- **Range over integer** — Go 1.22: `for i := range 10` iterates from 0 to 9; nothing if n <= 0; integer type or untyped constant (uses the pre-existing variable's type, otherwise `int`) (Spec p.89–91; RN1.22 p.1–2).
- **Range over function (iterator)** — Go 1.23 (preview in 1.22 with `GOEXPERIMENT=rangefunc`). Accepts `func(func() bool)`, `func(func(V) bool)` and `func(func(K, V) bool)`. The range passes a synthesized yield; if the body ends (by `break`, for example), yield returns false and must not be called again; iterators must test the return value and stop (Spec p.89–91; RN1.23 p.1; RN1.22 p.2). The Spec does not state here the consequence of calling yield after false, nor does it cover `defer`/`recover` in an iterator.
- **`iter`, `Seq` and `Seq2`** — the `iter` package is new in 1.23 and the note refers the details to its documentation; the notes do not give the signatures, and the names `iter.Seq`/`iter.Seq2` do not appear in them (RN1.23 p.1, p.4–5). There are iterators in `slices` and `maps` (`All`, `Keys`, `Values`, `Collect`, `Sorted`…); in 1.24, `Lines`, `SplitSeq`, `FieldsSeq` in `strings`/`bytes` and range over function in `text/template` (RN1.23 p.4–5; RN1.24 p.6–7).

## 14. Versions, modules and migration

- **`go` directive** — the `go` line of `go.mod` (or `go.work`) chooses the default behavior for changes that could break programs; raising only the toolchain keeps the previous behavior. Since 1.21 it is a strict minimum (`go 1.21.0` does not compile with Go 1.20) and numbering becomes `1.N.0` (RN1.21 p.1, p.3). It explicitly conditions `panicnil`, loop variable, timers (`go 1.23.0+`) and vet's `printf` (RN1.21 p.3; RN1.22 p.3; RN1.23 p.4; RN1.24 p.3).
- **`toolchain` directive** — Go 1.21; suggests the minimum toolchain, and the go command can download or invoke others; the selection rules are outside the sources (RN1.21 p.3). `GODEBUG=toolchaintrace=1` traces the selection (RN1.24 p.2).
- **GODEBUG** — setting that restores previous behavior for a potentially incompatible change; formalized in 1.21 and tied to the `go` line (RN1.21 p.3). Examples of reversion: `panicnil=1`, `asynctimerchan=1`, `randseednop=0` (RN1.21 p.3; RN1.23 p.4; RN1.24 p.12). For some, the notes do not give the value. Full table: versoes-e-migracao.md, section 5.
- **`godebug` directive and `//go:debug`** — Go 1.23: `godebug` in `go.mod`/`go.work` declares explicit values (RN1.23 p.2). `//go:debug` appears only as a way to set `rsa1024min=0` (RN1.24 p.8); that it acts on the main package is not stated in the sources.
- **`GOEXPERIMENT`** — build key for previews and implementation reversions: `rangefunc` (1.22), `aliastypeparams` (1.23, removed in 1.25), `noswissmap`, `nospinbitmutex` (1.24), `synctest` (1.24), `cgocheck2` (replaces `GODEBUG=cgocheck=2`, 1.21) (RN1.22 p.2; RN1.23 p.1; RN1.24 p.1, p.3–4, p.6; RN1.21 p.13).
- **PGO (profile-guided optimization)** — preview in 1.20 (`-pgo=<file>|auto|off`); general in 1.21, with `-pgo=auto` by default, `default.pgo` in the main directory used automatically and devirtualization of interface calls; gain of 2 to 7% (RN1.20 p.3, p.5; RN1.21 p.4–5). In 1.22 the gain goes from 2 to 14% (RN1.22 p.4).
- **`log/slog`, `slices`, `maps`, `cmp`** — new packages in 1.21 (RN1.21 p.6). For `log/slog` (structured logging with levels), `slices` and `maps` (common operations via generic functions) the notes only announce them, NO API DETAILS. For `cmp`, the note says the package defines the `Ordered` constraint and the generic functions `Less` and `Compare`, useful with ordered types (RN1.21 p.6). About the rest, all that is known, in later versions, is that `cmp.Or` and `slices.Concat` arrive in 1.22, that `slices.Delete/Compact/Replace` now zero the elements between the new and old length and that `slices.Insert` panics with an out-of-range index (RN1.22 p.7, p.12).
- **`math/rand` (global seed)** — Go 1.20: the global generator (top-level functions like `Float64` and `Int`) is now seeded automatically with a random value, and `Seed` is deprecated; anyone who needs a reproducible sequence must allocate their own source with `rand.New(rand.NewSource(seed))` (RN1.20 p.11). `GODEBUG=randautoseed=0` restores the previous global seeding (RN1.20 p.11). In Go 1.24, top-level calls to `Seed` no longer have any effect; `randseednop=0` restores it (RN1.24 p.12).
- **`runtime.AddCleanup` and `weak`** — Go 1.24; AddCleanup allows several cleanups per object, interior pointers and does not leak in cycles, and is preferable to `SetFinalizer`; `weak` is a new package, presented without a detailed API (RN1.24 p.5).
- **`os.Root` / `os.OpenRoot`** — Go 1.24; file operations confined to a directory, including against symlinks that leave it (RN1.24 p.4).
- **`errors.Join` and multiple `%w`** — Go 1.20; error with `Unwrap() []error`; `fmt.Errorf` accepts several `%w` and `errors.Is/As` traverse the list (RN1.20 p.6, p.10). Covers part of the wrapping gap in section 5.

## Gaps

- Notes coverage: Go 1.25 and 1.26 have no release notes; the Spec is go1.26, but the versions appendix only reaches 1.24 (Spec p.115–116). A feature in the body that is newer than 1.24 must be treated as a version not stated. `new(expr)` appears in Spec p.104 without a version; only Eff dates it to Go 1.26 (Eff p.15).
- Only announced in the notes, without API details: `log/slog`, `slices`, `maps` (1.21); for `cmp` only `Ordered`, `Less` and `Compare` are listed (RN1.21 p.6). Also without detail: signatures of `iter`, `unique` and `weak`; toolchain selection (RN1.21 p.6; RN1.23 p.4–5; RN1.24 p.5).
- The Spec in the notes is partial for `go`, `select`, `defer`, `recover`, initialization dependency and sizes/alignment (Spec p.92–98, p.109–114).
- Little has didactic inconsistencies that are not rules: `new(Saiyan)` with lowercase fields versus an uppercase struct (Little p.33); `process` with a value receiver on p.77 and a pointer receiver on p.78 (Little p.77–78).
