# PostgreSQL 16: logical replication (publication/subscription), filters, conflicts, restrictions and security

> Pages = PDF of the PG16 manual (16.15); printed = N − 38. Chapter 31 (PG16 p.905-927); parameters in PG16 p.673, p.679 and p.926-927. The overview (physical x logical) is in `postgresql-16-backup-pitr-e-replicacao-ha.md`; physical replication (streaming, synchronous, hot standby) in `postgresql-16-replicacao-streaming-sincrona-hot-standby-e-failover.md`. This file does not cover the extensive examples on p.907-912, 914-920 and 921-923, only the rules they illustrate.

## 1. Model [from source]
- **Logical** replication replicates data objects and their changes based on the **replica identity** (normally the primary key), in contrast to physical replication, which uses exact block addresses, byte by byte; the two mechanisms coexist. The model is publish/subscribe: one or more subscribers subscribe to one or more publications of a publisher; the subscriber can republish (cascade) (PG16 p.905).
- It starts with a **snapshot** of the data on the publisher copied to the subscriber; afterwards changes flow in real time, applied **in the same commit order**, so transactional consistency is guaranteed **within a subscription** ("transactional replication") (PG16 p.905, p.924). Uses listed by the manual: incremental changes of a database or subset, firing triggers on the subscriber, consolidating several databases into one (analytics), replicating between **different major versions** and between **different platforms** (Linux to Windows), giving access to different groups of users and sharing a subset of the database (PG16 p.905).
- If the subscriber is treated as read-only, a subscription does not generate conflicts; if there are other writes (application or other subscribers) to the same tables, conflicts can occur (PG16 p.905).

## 2. Publication [from source]
- A publication exists **in a single database**, can contain **tables** and "all tables in a schema" (or `ALL TABLES`); objects must be added explicitly, except in `FOR ALL TABLES`. A table can be in several publications. Publishing does not change how the table is accessed (PG16 p.905).
- A publication can limit the operations to any combination of `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE` (parameter `publish`; default: all); this applies **only to DML**, not to the **initial copy** of the data (PG16 p.905, p.925).
- **Replica identity**: to replicate `UPDATE` and `DELETE`, the published table needs a replica identity, by default the **primary key**; another suitable unique index can be used; without a suitable key, `REPLICA IDENTITY FULL` (the entire row becomes the key), which the manual says is **only a last-resort feature** because the lookup on the subscriber can be **very inefficient** if there is no candidate index (B-tree, not partial, with the first index column being a column and not an expression). If the identity on the publisher is not FULL, the subscriber needs an identity with the same columns or fewer. **Adding to a publication a table with no replica identity that replicates UPDATE/DELETE makes subsequent UPDATE/DELETE fail on the publisher**; `INSERT` continues (PG16 p.906).
- `ALTER PUBLICATION ... ADD/DROP TABLE` is transactional: the table starts/stops replicating at the correct snapshot after the commit (PG16 p.906).
- **Row filters** (per-table `WHERE`, in parentheses): the row is only replicated if it satisfies the expression; evaluated **before** publishing; false or NULL does not replicate; evaluated with the role of the replication connection; **do not affect `TRUNCATE`** (PG16 p.912-913). Only simple expressions: no user-defined functions, operators, types or collations, no system columns and no non-immutable built-in functions; if the publication publishes `UPDATE`/`DELETE`, the filter can only use columns of the replica identity (PG16 p.913). In an `UPDATE`, the expression applies to the old and the new row: both true = UPDATE; both false = nothing; only the new one true = becomes **INSERT**; only the old one true = becomes **DELETE** (Table 31.1) (PG16 p.913). Several filters for the same table in different publications of the same subscription are combined with **OR**; they become redundant if one of them has no filter, or is `FOR ALL TABLES` or `FOR TABLES IN SCHEMA` (which do not accept filters) (PG16 p.914). With partitioned tables, `publish_via_partition_root` (default **false**) decides which filter applies (the root's if true, each partition's if false) (PG16 p.913). The initial copy only copies rows that satisfy the filter, but ignores `publish`, so rows that the DML would not replicate may be copied; on subscribers before version 15 the filter does not apply to the copy (PG16 p.913-914).
- **Column lists**: each publication can choose columns per table; the table on the subscriber must have at least the published columns; **without a list**, columns added later are replicated automatically (a list with all columns is **not equivalent** to no list); only simple column references; **do not use for security**: a malicious subscriber can obtain unpublished columns; no combination with `FOR TABLES IN SCHEMA` (PG16 p.920). Generated columns are skipped in logical replication and cannot be in a list (PG16 p.100).

## 2b. Column lists (31.4): partition, replica identity, TRUNCATE, old subscriber and combining publications [from source] (PG16 p.920-921)
- **Column list and replica identity** (PG16 p.921): if the publication publishes `UPDATE` or `DELETE`, the column list **must include the columns of the table's replica identity** (REPLICA IDENTITY); if it publishes **only `INSERT`**, the list may omit them. `[inference]` a list without the primary key in a publication that replicates `UPDATE`/`DELETE` is of no use.
- **Partitioned tables** (PG16 p.921): what decides which list applies is `publish_via_partition_root`: if **true**, the list of the **root partitioned table** applies; if **false** (the default), the list **of each partition** applies.
- **`TRUNCATE`** (PG16 p.921): column lists **have no effect** on `TRUNCATE`.
- **Initial copy and subscriber before 15** (PG16 p.921): in the initial data synchronization, **only the published columns** are copied; but if the subscriber is of a version **before 15**, **all columns** of the table are copied in the initial synchronization, **ignoring** the lists.
- **Warning: combining lists from several publications** (PG16 p.921): there is no support for a subscription with **several publications in which the same table was published with different column lists**. `CREATE SUBSCRIPTION` **forbids** creating such a subscription, but it is possible to reach this situation by **adding or changing lists on the publisher side later**, after the subscription exists. This means that **changing the column list of tables in already-subscribed publications can cause errors on the subscriber**. If a subscription is affected, the **only way out** to resume replication is to adjust one of the lists on the publisher so that all are **equal** and then **recreate the subscription**, or use `ALTER SUBSCRIPTION ... DROP PUBLICATION` to remove one of the problematic publications and add it again.
- **Already on p.920** (summary in section 2): the list is not security (a malicious subscriber obtains unpublished columns), without a list new columns enter automatically, and a list with all columns is not equivalent to no list; the order of columns in the list is not preserved. The example on p.921 (`CREATE PUBLICATION p1 FOR TABLE t1 (id, b, a, d)`) shows that the order of the names does not matter and that psql's `\dRp+` lists the defined lists.

## 2c. Version 16.11 notes: `MERGE` and `INSERT ... ON CONFLICT DO UPDATE` require REPLICA IDENTITY [from source] (PG16 p.2698)
- **MERGE and REPLICA IDENTITY (merge replica identity)** (PG16 p.2698, Release 16.11, which starts on p.2696): the manual records "Add missing replica identity checks in `MERGE` and `INSERT ... ON CONFLICT DO UPDATE`" (credits to Zhijie Hou). If the `MERGE` may require update or delete actions and the target table **publishes updates or deletes**, it must have a **REPLICA IDENTITY defined**; without this requirement, replication could break **silently**. Likewise, `INSERT` with the `UPDATE` option (`ON CONFLICT DO UPDATE`) requires REPLICA IDENTITY if the target table publishes **inserts or updates** (the text says "publishes either inserts or updates").
- `[inference]` in practice, a `MERGE`/upsert that used to pass on a published table without a key may start to **fail** after upgrading to 16.11 or later; the fix is to define the replica identity (section 3c).

## 3. Subscription and slots [from source]
- A subscription defines the connection and the publications; the subscriber can have several subscriptions (take care that the publications do not overlap). Each subscription receives changes through **one replication slot** on the publisher; additional, transient slots are created for the initial synchronization (generated name `pg_%u_sync_%u_%llu`) and removed at the end (PG16 p.906-907). A subscription can be a synchronous standby (default name = subscription name, or `application_name` in the connection) (PG16 p.906).
- **The schema is not replicated**: published tables must exist on the subscriber, only **ordinary tables** can be a target (not views); matched by **qualified** name; there is no replication to a table of a different name; columns match by **name** (the order may differ); types may differ if the textual representation converts (for example `integer` to `bigint`); the target may have extra columns, filled by the default; the binary format is more restrictive (PG16 p.906-907).
- **Slot management**: normally the slot is created and removed together with the subscription. Special cases: slot already existing (`create_slot = false`); host unreachable at creation (`connect = false`, which `pg_dump` uses; create the slot manually afterwards); keeping the slot when dropping the subscription (dissociate with `ALTER SUBSCRIPTION` before the `DROP`); remote host unreachable at `DROP` (same). **If the remote host exists but is unreachable, the slot (and any remaining synchronization slots) must be removed manually, otherwise it will keep reserving WAL and may fill the disk** (PG16 p.907). `pg_dump` only dumps subscriptions if the user is a superuser (otherwise it warns and skips); when dropping and recreating the subscription, the synchronization information is lost and the data must be resynchronized (PG16 p.906).
- **Initial synchronization**: the snapshot of the tables is copied by a special apply process (with its own slot); once the copy is finished, the content becomes visible, the worker enters synchronization mode, applies the changes that happened during the copy in the same order and returns control to the main apply (PG16 p.925). The initial copy is done as `COPY`, firing row-level and statement-level `INSERT` triggers; the normal apply process fires **only row-level triggers**, never statement-level (PG16 p.924-925).

## 3b. `CREATE SUBSCRIPTION`: parameters, defaults and notes [from source] (PG16 p.1811-1814)
- **Form and effect**: `CREATE SUBSCRIPTION name CONNECTION 'conninfo' PUBLICATION pub [, ...] [WITH (parameters)]`. Whoever runs it becomes the owner; the name must be unique in the current database; the privileges of the `pg_create_subscription` role and CREATE on the database are required. Besides writing to the local catalog, the command normally creates a replication slot on the publisher, and a replication worker starts at the commit of the transaction that ran the command, unless the subscription is born disabled (PG16 p.1811).
- **`connect` and `connect = false`** (default true; PG16 p.1811-1812): with false the command does not even connect, and `create_slot`, `enabled` and `copy_data` are forced to false (you cannot request `connect = false` together with any of them true); with no connection no table is subscribed, so you must create the slot by hand, enable the subscription and do the refresh.
- **`create_slot`, `enabled` and `slot_name`** (PG16 p.1812): `create_slot` (default true): if false, the publisher's slot is up to you. `enabled` (default true): whether the subscription is born replicating. `slot_name`: the default is the subscription name; the value `NONE` means no associated slot and **requires** `enabled` and `create_slot` both false (used to create the slot later, manually).
- **`binary`** (default false; PG16 p.1812): asks the publisher for data in binary format instead of text, and the initial table copy uses the same format. It is potentially faster, but less portable across architectures and versions, and **very type-specific**: it does not allow, for example, copying from a `smallint` column to `integer`, which would work in text. Only types that have binary `send`/`receive` functions travel in binary, and the **initial synchronization requires these functions for all types, otherwise it fails**. In cross-version replication, if the publisher has `send` and the subscriber has no `receive` for a type, the transfer fails and `binary` cannot be used. If the publisher is before version 16, the initial synchronization uses text even with `binary = true`.
- **`copy_data`** (default true; PG16 p.1812): copies the data already existing in the publications when replication starts; WHERE clauses of the publications affect what is copied, and there is an interaction with the `origin` parameter (see Notes on p.1814).
- **Behavior after creation** (PG16 p.1813-1814): `streaming` (default off: the transaction is decoded entirely on the publisher and only then sent; `on`: changes go to temporary files and are applied only after the commit; `parallel`: applied directly by a free parallel apply worker, or, with no free worker, in temporary files). The subscription's `synchronous_commit` (default off; it is safe to use off in logical replication because, if the subscriber loses transactions, the data is resent; in synchronous logical replication off can increase COMMIT latency on the publisher, and `local` or stronger can compensate). `two_phase` (default false; when on, prepared transactions are sent at `PREPARE TRANSACTION`; the internal state stays "pending" until the initial synchronization finishes, visible in `subtwophasestate` of `pg_subscription`). `disable_on_error` (default false). `password_required` (default true; ignored if the owner is a superuser; only a superuser can set false). `run_as_owner` (default false: the worker acts as the owner of each table, a much safer setting, see section 31.9). `origin` (default `any`; `none` asks for only changes without origin).
- **Notes** (PG16 p.1814): a boolean parameter without a value means TRUE. With slot creation (the default), the command **does not run inside a transaction block**. Subscribing to the same cluster you are in only works if the slot is not created in the same command (otherwise the command hangs): create the slot beforehand with `pg_create_logical_replication_slot` and the `pgoutput` plugin and use `create_slot = false`. Rows whose WHERE is false or null are not published; with several publications of the same table with different WHERE clauses, the row goes out if any expression is satisfied, and a publication without WHERE (or `FOR ALL TABLES`/`FOR TABLES IN SCHEMA`) publishes everything. A subscriber before version 15 ignores the row filter in the initial synchronization. The initial copy does not consider the `publish` parameter, so rows that the DML would not replicate may come through. Several publications with different column lists for the same table are not supported. Nonexistent publications can be named (to create them later).

## 3c. `ALTER TABLE ... REPLICA IDENTITY`: DEFAULT, USING INDEX, FULL, NOTHING [from source] (PG16 p.1648-1649, p.906)
- **What the option does** (PG16 p.1648): changes the information written to the WAL to identify updated or deleted rows. In general the old value of each column is **only logged if it differs from the new one**; but if the old value is **stored externally (TOAST), it is always logged**, even without a change. **It has no effect unless logical replication is in use** (it does not affect physical streaming).
- **`DEFAULT`** (PG16 p.1648): records the old values of the **primary key** columns, if any; **it is the default for non-system tables** (PG16 p.906 says the same; without a suitable key, UPDATE/DELETE on a published table fail on the publisher).
- **`USING INDEX name`** (PG16 p.1648): records the old values of the columns of the named index, which must be **unique, NOT partial, NOT deferrable and only with columns marked NOT NULL**; hence a partial index (`WHERE ativo`) or one with a nullable column does not qualify. **If the index is dropped, the behavior becomes that of `NOTHING`.**
- **`FULL`** (PG16 p.1648): records the old values of **all** columns of the row; PG16 p.906 treats it as a last resort (the lookup on the subscriber can be very inefficient without a non-partial B-tree index whose first column is a column and not an expression).
- **`NOTHING`** (PG16 p.1649): records nothing about the old row; **it is the default for system tables**.

## 3d. `CREATE PUBLICATION`: what goes in, column lists, partitions and parameters [from source] (PG16 p.1786-1788)
- **Syntax** (PG16 p.1786): `FOR ALL TABLES`, or `FOR TABLE` (with `ONLY`, `*`, column list and `WHERE ( expression )`, parentheses mandatory) and/or `FOR TABLES IN SCHEMA {schema | CURRENT_SCHEMA}`; `WITH (publish, publish_via_partition_root)`. With no clause, the publication starts with an empty set of tables, useful for adding later; creating the publication **does not start replication** (PG16 p.1788). Partitions of a partitioned table are **never added explicitly**: they are always considered part of the publication (PG16 p.1786).
- **What can go in** (PG16 p.1787): **only persistent base tables and partitioned tables**. **Temporary, unlogged and foreign tables, materialized views and ordinary views can NOT** (also applies to `FOR TABLES IN SCHEMA`).
- **Column list x schema** (PG16 p.1787): specifying a column list when the publication also publishes `FOR TABLES IN SCHEMA` is **not supported, in either direction**; a row filter on a table of the published schema becomes redundant (PG16 p.1788). The list and the `WHERE` do not affect `TRUNCATE`; without a list, all columns go, including those added later (PG16 p.1786).
- **Partitions** (PG16 p.1787): when adding a partitioned table, **all existing and future partitions** enter implicitly, **even those in another schema** in a schema publication; operations done **directly on a partition** are also published by the publications of the ancestors.
- **`publish`** (PG16 p.1787): list of `insert, update, delete, truncate`; default = all. **Affects DML only**: the **initial synchronization** (section 31.7.1) copies the existing data **without considering the parameter**.
- **`publish_via_partition_root`** (PG16 p.1787-1788): `false` (**default**) publishes with the identity and schema of the partition where the change occurred; `true` uses the identity and schema of the root and allows replicating to a **non-partitioned** table or to a partitioned one with a different structure. If a subscription combines several publications and any has `true` for the table, the root applies. With `true`, a `TRUNCATE` directly on a partition is not replicated; row filters and column lists come from the root (with `false`, from the partition). The manual does not recommend "always true": it is a choice depending on the destination.
- **Notes** (PG16 p.1788): `FOR ALL TABLES` and `FOR TABLES IN SCHEMA` require **superuser**; adding a table requires owning it; creating requires `CREATE` on the database. The tables of a publication that publishes UPDATE/DELETE need REPLICA IDENTITY, the column list must include it and the `WHERE` only uses columns of the identity (for INSERT, any column). The filter accepts only simple expressions (no user-defined functions, operators, types or collations, non-immutable functions or system columns). `COPY ... FROM` is published as INSERT; `INSERT ... ON CONFLICT` publishes whatever results (INSERT, UPDATE or nothing); `MERGE` publishes INSERT/UPDATE/DELETE per row; **DDL is not published**; `ATTACH` of a table to a tree whose root is published with `true` does not replicate the table's existing content.

## 4. Architecture [from source]
- Architecture similar to physical streaming: the **walsender** starts logical decoding of the WAL and loads the `pgoutput` plugin, which translates the changes to the logical replication protocol and filters according to the publication; the data goes by streaming protocol to the **apply worker**, which maps to local tables and applies in transactional order (PG16 p.924).
- **Update/Delete message of the logical protocol (fields K and O)** (PG16 p.2428): in the Update message, the optional field Byte1('K') marks a TupleData submessage as the **key** and only appears if the UPDATE changed data of some column of the replica identity index; Byte1('O') marks the **old tuple** and only appears if the table has `FULL` replica identity; the message may have 'K' or 'O' or neither, **never both**; 'N' marks the new tuple (PG16 p.2428). In the Delete message, 'K' appears if the table uses an index as replica identity and 'O' if it is `FULL` (PG16 p.2428).
- The apply runs with `session_replication_role = replica`: by default **triggers and rules do not fire on the subscriber**; they can be enabled with `ALTER TABLE ... ENABLE TRIGGER/RULE` (PG16 p.924).

## 5. Conflicts [from source]
- Replication applies data even if it was changed locally on the subscriber. If received data violates a constraint (for example, duplicate key), replication **stops** (conflict); `UPDATE`/`DELETE` of missing data does **not** generate a conflict and is simply ignored. Insufficient permissions on the target tables, or **RLS enabled** on the target tables for the subscription owner, also cause a conflict (regardless of whether the policy rejects or not) (PG16 p.923).
- The error stops replication and **must be resolved manually**; details are in the subscriber's log (including the transaction's finish LSN and the replication origin name, such as `pg_16395`). Resolution: change data or permissions on the subscriber so as not to conflict, **or skip the transaction** with `ALTER SUBSCRIPTION ... SKIP` using the finish LSN, or with `pg_replication_origin_advance()` (with the subscription disabled beforehand: `ALTER SUBSCRIPTION ... DISABLE` or the `disable_on_error` option; use the LSN following the finish one). **Skipping the whole transaction includes changes that did not violate a constraint and can leave the subscriber inconsistent** (PG16 p.923). In `streaming = parallel` mode the finish LSN may not be logged (PG16 p.923).

## 6. Restrictions of logical replication [from source] (PG16 p.923-924)
- **DDL and schema are not replicated**: copy the initial schema with `pg_dump --schema-only`; keep changes synchronized by hand; replication "is robust" to live schema changes, but errors if the received data does not fit the table until the schema is updated; **additive** changes are usually applied **first on the subscriber** to avoid intermittent errors.
- **Sequences are not replicated**: `serial`/identity columns arrive as part of the table, but the sequence on the subscriber shows the initial value; for switchover/failover the sequences must be updated (copy values with `pg_dump` or compute a sufficiently high value from the tables).
- **`TRUNCATE`** is replicated, with care for groups of tables linked by foreign key: the subscriber truncates the same group (including `CASCADE`), except tables outside the subscription; it fails if any table to be truncated on the subscriber has an FK to tables that are not part of the subscription.
- **Large objects are not replicated** (no solution, other than storing the data in normal tables). Only **tables** (including partitioned ones) are replicated; views, materialized views and foreign tables give an error.
- Between partitioned tables, replication **originates by default in the leaf partitions**, so the publisher's partitions must exist on the subscriber as valid targets; `publish_via_partition_root` uses the root's identity and schema.

## 7. Monitoring and security [from source]
- On the publisher, monitor as on a physical primary (view pg_stat_replication, slots); on the subscriber, `pg_stat_subscription` has one row per subscription worker (normally one apply per enabled subscription; extra rows for table synchronization and for parallel apply; a disabled or crashed subscription has **zero rows**) (PG16 p.925). `pg_stat_subscription_stats` shows errors per subscription (PG16 p.839-840).
- **Replication role**: needs `REPLICATION` (or superuser), `LOGIN`, access in `pg_hba.conf` and `SELECT` on the published tables (to copy the initial data); without `SUPERUSER` and without `BYPASSRLS`, the publisher's row-level security policies **are executed**; if the role does not trust all table owners, use `options=-crow_security=off` in the connection (replication stops instead of executing the policy) (PG16 p.925). The output plugin must be in `output_plugin_libraries` (default `pgoutput,test_decoding`; for subscriptions, `pgoutput`) (PG16 p.673, p.925).
- Creating a publication requires `CREATE` on the database; adding tables requires being the **table owner**; `ALL TABLES` or all tables of a schema require **superuser**. **There are no privileges on publications**: any subscription that can connect accesses any publication, so row filters and column lists **do not hide data** securely if another publication of the same database exposes it (PG16 p.925-926). Creating a subscription requires the privileges of the `pg_create_subscription` role plus `CREATE` on the database. The apply runs with the privileges of the subscription owner, but switches to the table owner for each operation (the subscription owner must be able to `SET ROLE`); with `run_as_owner = true` there is no switch, and any owner of a target table can execute code with the privileges of the subscription owner (for example, with a trigger), which is why the manual says to **avoid** this option unless security between users does not matter. On the publisher the privileges are checked once at the start of the connection; on the subscriber, at each applied transaction (PG16 p.926).

## 7b. PG16 release notes, Appendix E.16 "Release 16": logical replication changes [from source] (PG16 p.2753-2754)
Appendix E.16.3.2 lists what **changed in 16 relative to 15** (p.2753-2754; the printed pages are 2715-2716). Useful for answering "is this new in 16?" and for deciding per-subscription parameters.
- **Logical decoding on standbys** (PG16 p.2753): now allowed; the snapshot WAL records needed to create a logical slot cannot be created on a standby, and to avoid delays the new function `pg_log_standby_snapshot()` allows creating them.
- **`debug_logical_replication_streaming`** (PG16 p.2753): new server variable to control how the logical decoding publisher transfers changes and how subscribers apply them (name with "debug": testing/debugging use `[inference]`).
- **Initial copy in binary format** (PG16 p.2753): the initial table synchronization can copy rows in binary format, but **only for subscriptions marked `binary`**.
- **Parallel apply** (PG16 p.2753): the `STREAMING` option of `CREATE SUBSCRIPTION` now accepts `parallel`, to apply large transactions with parallel workers; the number of workers is controlled by the new variable `max_parallel_apply_workers_per_subscription`; the wait events `LogicalParallelApplyMain`, `LogicalParallelApplyStateChange` and `LogicalApplySendData` were added, and the column `leader_pid` in `pg_stat_subscription`.
- **Apply without a primary key** (PG16 p.2753-2754): better performance; in particular, `REPLICA IDENTITY FULL` can now use btree indexes instead of sequentially scanning the table to find the matching rows.
- **`ORIGIN` option of `CREATE SUBSCRIPTION`** (PG16 p.2754): lets the subscriber process **only changes without origin** (that did not come from another replication), which serves to **avoid replication loops** (bidirectional).
- **Apply `SELECT` and DML as the table owner; `run_as_owner` option** (PG16 p.2754): replication now executes as the **table owner**, which improves security and **requires subscription owners to be superusers or to have `SET ROLE` permission on all the roles that own tables of the replicated set**. The previous behavior (everything executed as the subscription owner) can be re-enabled with the subscription's `run_as_owner` option.
- **`wal_retrieve_retry_interval` per subscription** (PG16 p.2754): the parameter now operates **per subscription**; before, the retry time was applied globally. The change also added the wait events `LogicalRepLauncherDSA` and `LogicalRepLauncherHash`.
- **Other utility changes in the same block** (PG16 p.2754): see `postgresql-16-comandos-reindex-drop-tablespace-truncate-e-utilitarios.md`, section "Notas de versão do 16: comandos" (release notes for 16: commands).

Quick start (PG16 p.927): `wal_level = logical`; the other settings have defaults sufficient for a basic setup; adjust `pg_hba.conf`; on the publisher `CREATE PUBLICATION mypub FOR TABLE users, departments;` and on the subscriber `CREATE SUBSCRIPTION` with the connection.

## 9. [inference]
- For a migration with minimal downtime between major versions, the combination "schema via `pg_dump --schema-only` + subscription + sequence resynchronization at cutover" follows directly from PG16 p.905, p.923-924; the manual does not describe a complete migration script.
- Since the subscriber can have a slightly different schema and replication does not carry DDL, a deploy with `ALTER TABLE` requires coordinating the order (subscriber first, if additive) (PG16 p.924).

## 10. [extrapolation] and what the sources do NOT say
- Expected performance (rows/s, acceptable lag size) and comparisons with third-party tools (pglogical, Debezium, DMS): outside the manual.
- **Bidirectional** logical replication with automatic conflict resolution: the manual says conflicts must be resolved manually (PG16 p.923) and that logical replication can form a bidirectional flow only in the sense that "a server can publish and subscribe" (PG16 p.816); multimaster rules are `[extrapolation]`.
