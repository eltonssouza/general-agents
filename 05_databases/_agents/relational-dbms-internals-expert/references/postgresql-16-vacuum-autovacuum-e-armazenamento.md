# PostgreSQL 16: VACUUM, autovacuum, wraparound, physical storage and TOAST

> Pages = PDF of the PG16 manual (16.15); printed = N − 38. Ch. 25 (Routine Maintenance) = PDF 788-800; Ch. 73 (Physical Storage) = PDF 2567-2576. The v1 cited "p.810-835", which in the PDF is backup/restore and high availability/replication.

## 1. Why VACUUM exists [from source]
- The manual lists four reasons: (1) recover or reuse the space of updated/deleted rows; (2) update planner statistics; (3) update the **visibility map**, which speeds up index-only scans; (4) protect against loss of old data through transaction ID or multixact **wraparound** (PG16 p.788).
- UPDATE or DELETE **do not immediately remove** the old version: it must remain visible to other transactions (MVCC); the space is only recoverable when no transaction sees it, and it is VACUUM that does this (PG16 p.789).
- Standard VACUUM removes dead versions from tables and indexes and marks the space as reusable, but **does not return space to the OS**, except for fully free pages at the end of the table (PG16 p.789). `VACUUM FULL` rewrites the table, requires `ACCESS EXCLUSIVE` and extra space, and the manual recommends **avoiding it**; autovacuum **never** issues VACUUM FULL (PG16 p.789-790). To empty a table periodically, the manual suggests `TRUNCATE` (which violates strict MVCC semantics) instead of DELETE + VACUUM (PG16 p.790).
- Statistics: ANALYZE uses statistical sampling of rows; autovacuum does not ANALYZE partitioned tables or foreign tables; for columns heavily used in WHERE with an irregular distribution, the detail can be raised with `ALTER TABLE ... SET STATISTICS` or `default_statistics_target` (PG16 p.790-791).
- **Visibility map**: records per page whether all tuples are visible to all transactions; it lets VACUUM skip pages and serves index-only scans (PG16 p.791, p.2572).

## 1b. The `VACUUM` command: options, defaults and effects [from source] (PG16 p.2063-2067)
- **Syntax**: options in parentheses can come in any order (form available since 9.0); the form without parentheses requires a fixed order and is obsolete. Options listed: `FULL`, `FREEZE`, `VERBOSE`, `ANALYZE`, `DISABLE_PAGE_SKIPPING`, `SKIP_LOCKED`, `INDEX_CLEANUP`, `PROCESS_MAIN`, `PROCESS_TOAST`, `TRUNCATE`, `PARALLEL`, `SKIP_DATABASE_STATS`, `ONLY_DATABASE_STATS`, `BUFFER_USAGE_LIMIT` (PG16 p.2063-2064).
- **Scope and effect**: without a table list, it processes all tables and materialized views of the current database that the user can vacuum; with a list, only those (partitioned table: all leaves). `VACUUM ANALYZE` vacuums and then runs ANALYZE on each table. Plain vacuum reclaims space for reuse **without an exclusive lock** (coexists with reads and writes) and, in most cases, **does not return** space to the operating system; `FULL` rewrites the table into a new file with no spare space, returns it to the OS, is much slower, requires **ACCESS EXCLUSIVE** and needs extra disk space during the operation (PG16 p.2063-2064). It is not recommended as a routine; it is suitable, for example, after deleting or updating most of the rows (PG16 p.2066-2067).
- **Restrictions and who can run it**: `VACUUM` **does not run inside a transaction block**; for tables with a GIN index, in any form it also completes the pending index insertions. You must be the table owner or a superuser; the database owner can vacuum everything except shared catalogs (so a truly whole-database vacuum is a superuser's). `VACUUM` does not exist in the SQL standard (PG16 p.2066-2067).
- **`FREEZE`** is equivalent to running with `vacuum_freeze_min_age` and `vacuum_freeze_table_age` equal to zero and is redundant with `FULL`. **`DISABLE_PAGE_SKIPPING`** turns off all page skipping via the visibility map and is only justified if the map is suspect (corruption from hardware or software). **`SKIP_LOCKED`** does not wait for a conflicting lock (skips the relation), but may still block when opening the indexes (PG16 p.2064).
- **`INDEX_CLEANUP`** (PG16 p.2064-2065): `AUTO` (default) lets vacuum skip index cleanup when there are very few dead tuples; `ON` conservatively removes all dead tuples from the indexes (behavior of old versions); `OFF` always skips index cleanup, even with many dead tuples, which is only justified to finish as fast as possible in the face of imminent wraparound. Without regular index cleanup, indexes accumulate dead tuples and the table accumulates dead line pointers. The option has no effect on a table without indexes and is ignored with `FULL`.
- **`vacuum_failsafe_age` (failsafe against wraparound)** (PG16 p.2064-2065): the manual says this mechanism usually triggers on its own to avoid failure from wraparound and **should be preferred** over `INDEX_CLEANUP OFF`; it is **not affected** by `INDEX_CLEANUP`: when it triggers, it skips index cleanup even with `INDEX_CLEANUP` set to ON.
- **Floor of `vacuum_failsafe_age`**: the effective value is silently adjusted to at least **105% of `autovacuum_freeze_max_age`** (PG16 p.709; details and multixact ages in `postgresql-16-configuracao-memoria-wal-checkpoint-timeouts-e-locks.md` section 6).
- **`PROCESS_MAIN`** and **`PROCESS_TOAST`** (default true; the latter is mandatory with `FULL`); turning one off serves to vacuum only the TOAST table or only the main one (PG16 p.2065).
- **`TRUNCATE`** (PG16 p.2065): tries to cut the empty pages at the end of the table and return that space to the OS; it is the default, unless `vacuum_truncate` is false for the table. Setting it to false avoids the **ACCESS EXCLUSIVE** lock that truncation requires; [inference] with false that space at the end is not returned to the OS. Ignored with `FULL`.
- **`PARALLEL`**: runs the cleanup and index vacuum phases in parallel. The number of workers equals the number of indexes that support parallel vacuum, limited by the value given in `PARALLEL` (if any) and by `max_parallel_maintenance_workers`; an index only participates if it is larger than `min_parallel_index_scan_size`; **each index uses at most one worker**, and **workers are only launched when the table has at least 2 indexes**. The number may be lower than requested, or zero; workers start before each phase and exit at its end. Does not combine with `FULL`. `PARALLEL 0` turns the feature off. With `ANALYZE` in the same call, `PARALLEL` does not affect the ANALYZE (PG16 p.2063, p.2065, p.2067). [derived] for example, with 5 eligible indexes, `PARALLEL 8` and `max_parallel_maintenance_workers = 3`, vacuum uses at most 3 workers; with 1 index, none.
- **Other options**: `SKIP_DATABASE_STATS` skips updating the database's oldest unfrozen XID statistics (useful in a series of vacuums, followed by `ONLY_DATABASE_STATS`, which only updates those statistics and accepts neither a table list nor other options besides `VERBOSE`) (PG16 p.2065). `BUFFER_USAGE_LIMIT` sets the buffer ring of the access strategy (0 turns it off; minimum 128 kB, maximum 16 GB; the default comes from `vacuum_buffer_usage_limit`; does not apply with `FULL`, except together with `ANALYZE`) (PG16 p.2066).
- **Cost and progress**: vacuum can greatly increase I/O; the cost-based vacuum delay can be used and, in parallel vacuum, each worker sleeps in proportion to the work it did. Progress appears in `pg_stat_progress_vacuum` (and in `pg_stat_progress_cluster` for `FULL`) (PG16 p.2067).

## 2. XID wraparound and freezing [from source]
- XIDs are 32 bits; a cluster with more than 4 billion transactions would suffer wraparound and past data would appear to be in the future ("catastrophic data loss"); every table of every database must be VACUUMed **at least every two billion transactions** (PG16 p.791-792).
- Normal XIDs are compared with modulo-2^32 arithmetic: for each XID there are 2 billion "older" and 2 billion "newer" (PG16 p.792). VACUUM **freezes** rows; there is a special XID `FrozenTransactionId`, always older than any normal XID; since 9.4 freezing only sets a bit, preserving the original `xmin` (PG16 p.792).
- `vacuum_freeze_min_age` controls the age from which rows are frozen; an *aggressive vacuum* (`vacuum_freeze_table_age`) also scans pages that are all-visible but not all-frozen (PG16 p.792). `autovacuum_freeze_max_age` (default **200 million**) forces autovacuum on tables with XIDs older than that **even with autovacuum turned off** (PG16 p.792, p.703).
- Warning signs: the system starts issuing warnings when **forty million** transactions remain before wraparound; if ignored, it **refuses to assign new XIDs when fewer than three million remain**, and only read-only transactions can start (PG16 p.794). The manual says to: resolve old prepared transactions, end long transactions, remove old replication slots and run `VACUUM` on the database; **not** to use VACUUM FULL or VACUUM FREEZE in this scenario (PG16 p.794-795). The text says that, contrary to what the HINT message suggests, it is **neither necessary nor desirable to stop the postmaster and use single-user mode** (PG16 p.794-795).
- The **visibility map** keeps **two bits per heap page**: all-visible (nothing to clean; useful for index-only scans) and all-frozen (not even anti-wraparound vacuum needs to revisit); bits are set only by VACUUM and cleared by any modification of the page (PG16 p.2572).
### 2b. Multixacts (multixact IDs), member storage and wraparound [from source] (PG16 p.795-796)
- **Multixact ID: what it is** (PG16 p.795): when more than one transaction locks the same row at the same time, the information on all of them does not fit in the tuple header; it is encoded in a *multixact ID* and only that ID appears in `xmax`. The list of which XIDs make up each multixact is kept separately, in the `pg_multixact` subdirectory. The multixact ID counter is 32 bits and requires aging, storage cleanup and wraparound handling like the XID; **the separate area that stores the member list also uses a 32-bit counter and also needs to be managed**. The function `pg_get_multixact_members()` (Table 9.80) shows the XIDs of a multixact.
- **How VACUUM handles multixacts** (PG16 p.795): when scanning any part of the table, VACUUM replaces every multixact ID older than `vacuum_multixact_freeze_min_age` with another value, which can be zero, a single XID or a newer multixact. `pg_class.relminmxid` stores the oldest multixact still possible in some tuple of the table; if it is older than `vacuum_multixact_freeze_table_age`, VACUUM is forced to be *aggressive* (it only skips pages that are already all-frozen). `mxid_age()` on `relminmxid` gives the age. Aggressive vacuums, whatever the reason, always manage to advance the table's `relminmxid`; when all tables of all databases advance, the on-disk storage of old multixacts can be removed.
- **Multixact member storage: 10 GB and 20 GB thresholds** (PG16 p.795): as a safety device, an aggressive vacuum occurs on every table whose multixact age exceeds `autovacuum_multixact_freeze_max_age` (default 400 million, PG16 p.704). In addition, **if the storage occupied by multixact members exceeds about 10 GB, aggressive vacuums start occurring more frequently on all tables, beginning with those with the oldest multixact**; both kinds of aggressive scan occur **even with autovacuum nominally turned off**. The members area can grow to **about 20 GB** before reaching wraparound.
- **Multixact wraparound: warnings at 40 million and refusal below 3 million (MXIDs)** (PG16 p.795): as in the XID case, if autovacuum does not clean the old MXIDs of a table, the system starts issuing **warnings when the oldest MXIDs come within forty million transactions of the wraparound point**; if the warnings are ignored, the system **refuses to generate new MXIDs when fewer than three million remain** before wraparound.
- **Recovering when MXIDs run out** (PG16 p.796): the same script as for XID applies (section 2), with four differences: (1) in-progress transactions and prepared transactions can be ignored if there is no chance of their appearing in a multixact; (2) unlike XID, **replication slots do not directly hold back multixact cleanup**, so removing obsolete slots normally does not solve the MXID problem; (3) MXID information is not directly visible in views such as `pg_stat_activity`, but looking for old XIDs is still a good way to find the transactions causing the problem; (4) XID exhaustion blocks **all** write transactions, but MXID exhaustion blocks only **a subset**: those involving row locks that need an MXID.
- **XID recovery trap, still on p.795**: do not use `VACUUM FULL` in this scenario, because it needs an XID and therefore fails, except as superuser, when it consumes an XID and **increases** the wraparound risk; also do not use `VACUUM FREEZE`, which does more than the minimum necessary. After normal operation is restored, check that autovacuum is well configured in the target database. Single-user mode (stopping the postmaster) was necessary in old versions; today it should be avoided, because it turns off the wraparound safeguards; the only reason to use it is `TRUNCATE` or `DROP` of unneeded tables so as not to have to VACUUM them, and that is why the three-million-transaction safety margin exists.

## 3. Autovacuum [from source]
> Default values of `vacuum_freeze_*`, `vacuum_failsafe_age`, `vacuum_cost_*` and of the session timeouts: `postgresql-16-configuracao-memoria-wal-checkpoint-timeouts-e-locks.md`; the views `pg_stat_all_tables` and `pg_stat_progress_vacuum` and `pgstattuple`: `postgresql-16-monitoramento-views-pg-stat-e-extensoes-contrib.md`.
- "Optional but highly recommended"; needs `track_counts`; **on by default** (PG16 p.796, p.702). It is a persistent *launcher* that starts *workers* per database every `autovacuum_naptime` (default 1 min), up to `autovacuum_max_workers` (default 3) (PG16 p.796, p.702-703). Workers do not count toward `max_connections` (PG16 p.796).
- **Formula**: `vacuum threshold = vacuum base threshold + vacuum scale factor × number of tuples`, with `pg_class.reltuples` as the number of tuples (PG16 p.796); defaults `autovacuum_vacuum_threshold = 50` and `autovacuum_vacuum_scale_factor = 0.2` (PG16 p.703). There is also a threshold for **inserts** (`autovacuum_vacuum_insert_threshold` 1000 and `..._insert_scale_factor` 0.2) and one for ANALYZE (`autovacuum_analyze_threshold` 50 and `autovacuum_analyze_scale_factor` 0.1) (PG16 p.703, p.796-797). The count of obsolete tuples counts updates and deletes and is "semi-accurate" (PG16 p.797).
- All thresholds can be overridden **per table** with storage parameters (PG16 p.797). I/O cost: `autovacuum_vacuum_cost_delay` default 2 ms; `autovacuum_vacuum_cost_limit` default -1 (uses `vacuum_cost_limit`, default 200) and the limit is divided among the active workers (PG16 p.704, p.658, p.797).
- Autovacuum does not access temporary tables; partitioned tables are not processed directly (the partitions are), so a manual ANALYZE of the parent table is needed (PG16 p.797). Commands that request a lock conflicting with `SHARE UPDATE EXCLUSIVE` interrupt autovacuum, **except** the one running to prevent wraparound; regularly running ANALYZE can prevent autovacuums from finishing (PG16 p.797).
- Turning off the daemon: the manual says that "it is unwise to disable it completely unless the workload is extremely predictable" (PG16 p.789); even with `autovacuum = off` the system launches wraparound-prevention processes (PG16 p.702).
- `VACUUM` generates considerable I/O; there are parameters to reduce the impact (PG16 p.789). On tables with INSERT but no UPDATE/DELETE, reducing `autovacuum_freeze_min_age` may help (PG16 p.797).
- Monitoring: `pg_stat_all_tables` (and `pg_stat_user_tables`) provides `n_live_tup`, `n_dead_tup`, `n_mod_since_analyze`, `last_vacuum`, `last_autovacuum`, `n_tup_hot_upd` etc. (PG16 p.868-869).
- Periodic reindexing (B-trees whose ranges become nearly empty) is recommended for those patterns; bloat in non-B-tree indexes "has not been well researched" and it is advisable to monitor the physical size (PG16 p.798).

## 4. Physical layout [from source]
- Each table and index is a file (filenode); main **fork**, `_fsm` (free space map), `_vm` (visibility map) and `_init` (unlogged tables); files are divided into **1 GB segments** (compile-time default) (PG16 p.2568-2569).
- Fixed-size pages (normally **8 kB**), five parts: `PageHeaderData` (24 bytes), array of item identifiers (`ItemIdData`, 4 bytes each, allocated from the start of free space), free space, the items (allocated from the end) and special space (indexes; empty in tables) (PG16 p.2573). The header has, among other fields, `pd_lsn` (LSN of the page's last WAL record), `pd_checksum`, `pd_lower`, `pd_upper`, `pd_special` (PG16 p.2573-2574). The item pointer (CTID) is page number + identifier index (PG16 p.2574). See also `postgresql-16-mvcc-e-niveis-de-isolamento.md` for the tuple header.
- **Table 73.3, `PageHeaderData` (24 bytes)** (PG16 p.2574): `pd_lsn` (8 bytes; LSN: next byte after the last WAL record of the last change to the page), `pd_checksum` (2), `pd_flags` (2), `pd_lower` (2; start of free space), `pd_upper` (2; end of free space), `pd_special` (2; start of special space), `pd_pagesize_version` (2; page size and layout version) and `pd_prune_xid` (4; oldest unpruned XMAX, or zero). [derived] 8+2+2+2+2+2+2+4 = **24 bytes**. P.2574 says the page size exists only as a cross-check: **there is no support for more than one page size in an installation**; the last field is a hint on whether pruning the page is worthwhile. Details are in `src/include/storage/bufpage.h`.
- **Why the CTID is stable** (PG16 p.2574): each item identifier takes 4 bytes (offset, length and attribute bits); new ones are allocated from the start of unallocated space, and `pd_lower` grows with each new one. Since an identifier is **never moved until it is freed**, its index serves as a long-term reference even when the item is moved within the page to compact space; every item pointer (`ItemPointer`, CTID) is **page number + identifier index**. Items are allocated back to front from the end of free space; tables and sequences use `HeapTupleHeaderData`. The special space (for example, B-tree sibling links) is empty in ordinary tables (`pd_special` equal to the page size). [inference] a row's CTID still changes when UPDATE creates a new version or `VACUUM FULL` rewrites (see `postgresql-16-mvcc-e-niveis-de-isolamento.md`); the stability holds for the identifier within the page, not for the logical row.
- **FSM**: stores the free space per page **with one byte per page**, organized as a tree of FSM pages (each FSM page is a binary tree in an array); does not exist for hash indexes; consulted on inserts (PG16 p.2572).
- **HOT (heap-only tuples)** (PG16 p.2576, section 73.7). MVCC requires a new row version on each UPDATE, which may require new index entries and the later removal of old versions and their entries. The HOT optimization is possible when **both** conditions hold: (1) the UPDATE **modifies no column referenced by the table's indexes, not counting summarizing indexes**; the **only summarizing method in core is BRIN**; (2) there is enough free space on the **same page** as the old row. In that case, (a) **no new index entries are needed** to represent the updated row, **but summarizing indexes (BRIN) may still need updating**; and (b) old versions can be removed **during normal operation, including in SELECTs**, without waiting for periodic vacuum (this is possible because the indexes do not reference the page's item identifiers). Note: the saving of entries holds for indexes that are **not** summarizing; "new entries in all indexes" would be an overstatement. Practical consequence: an UPDATE that only changes a column indexed **exclusively by BRIN** **can be HOT** (BRIN may still be updated); a column with B-tree, hash, GIN or GiST prevents HOT. Reducing the table's `fillfactor` **increases the chance** of there being space on the page; if it is not reduced, HOT **still happens**, because new rows naturally migrate to pages with free space. Monitoring: the `pg_stat_all_tables` view (`n_tup_upd`, `n_tup_hot_upd`) shows HOT and non-HOT UPDATEs (PG16 p.2576, p.868-869). The manual gives no target HOT percentages.
- **Initialization fork** of unlogged tables: used to reset the table after a crash (PG16 p.2573).

## 5. TOAST [from source]
- PG uses a fixed-size page and **does not allow a tuple to span several pages**; large values are compressed and/or broken into several physical rows, transparently (PG16 p.2569). Only types with a variable-size representation (varlena) support TOAST; the logical limit of a value is **1 GB** (PG16 p.2569-2570).
- TOAST handling is only triggered when the row exceeds `TOAST_TUPLE_THRESHOLD` (normally **2 kB**); it compresses and/or moves fields out of line until the row is smaller than `TOAST_TUPLE_TARGET` (also normally 2 kB, adjustable per table with `toast_tuple_target`) or there is no further gain (PG16 p.2570-2571). Out-of-line values live in an associated TOAST table, split into chunks of at most `TOAST_MAX_CHUNK_SIZE` (by default ~2000 bytes, so that four fit in a page), with columns `chunk_id`, `chunk_seq`, `chunk_data`; the on-disk TOAST pointer is **18 bytes** (PG16 p.2570).
- There are **four strategies** per column: `PLAIN`, `EXTENDED` (default for most; tries to compress first, then move out of line), `EXTERNAL` (out of line, without compression; speeds up substring on `text`/`bytea`) and `MAIN` (compression without leaving the row, except as a last resort) (PG16 p.2571). Compression: `pglz` (default) or `lz4` if compiled with support; `default_toast_compression` (PG16 p.706).
- **Per-column `COMPRESSION` option and `default_toast_compression`** (PG16 p.2570, p.706, p.1819, p.1644): the compression method, for both in-line and out-of-line data, can be chosen **per column** with the `COMPRESSION` option in `CREATE TABLE` or `ALTER TABLE ... SET COMPRESSION` (p.2570). The default for columns without an explicit choice is to consult the `default_toast_compression` parameter **at the time the data is inserted** (p.2570); the parameter applies to compressible columns, accepts `pglz` and, if compiled with `--with-lz4`, `lz4`, and the default is `pglz` (p.706). Compression only applies to variable-width types and is only used when the column's storage mode is `main` or `extended`; `COMPRESSION default` explicitly requests the default behavior; on a partitioned table the property has no direct effect (there is no storage of its own), but it is inherited by new partitions (p.1819). `ALTER TABLE ... SET COMPRESSION` defines how values inserted **in the future** will be compressed and **does not rewrite the table**: existing data may remain compressed with another method; if the table is restored with `pg_restore`, all values are rewritten with the configured method; and data inserted from another relation (`INSERT ... SELECT`) may keep the old method, since it is not always detoasted (p.1644). Even for out-of-line data, the varlena header does not say whether compression occurred; the content of the TOAST pointer does (p.2570).
- **1-byte varlena header (short values)** (PG16 p.2570, p.3001): TOAST uses two bits of the varlena length word, which limits the logical value to **1 GB (2^30 - 1 bytes)**. If the highest/lowest-order bit (depending on the architecture) is set, the value has a **header of just 1 byte** instead of the usual 4, and the remaining bits of that byte give the total size (including the size byte). This allows economical storage of values **smaller than 127 bytes**, without preventing the type from growing to 1 GB. Values with a 1-byte header are **not aligned** on any boundary, whereas 4-byte ones are aligned on at least 4 bytes; the lack of padding saves significant space for short values. If all the remaining bits of the 1-byte header are zero, the value is a **pointer to out-of-line data**. P.3001 (Table K.1) confirms: short variable fields use a 4- or 1-byte header and stay inside the tuple; only an 18-byte pointer needs to stay in the row for large ones.
- Advantage: the main table gets smaller, more rows fit in cache and sorts stay in memory; in a manual test, the main table ended up with about 10% of the data (PG16 p.2571). An UPDATE that does not change the out-of-line values pays no TOAST cost (PG16 p.2570).

## 6. [inference]
- Since UPDATE amounts to creating a new version and the space only comes back through VACUUM (p.789), tables with a high UPDATE/DELETE rate accumulate dead versions ("bloat") if autovacuum does not keep up; the manual describes the mechanism, but does not use bloat numbers.
- The recommendation to reduce the autovacuum scale factor on hot tables is consistent with the formula and with the per-table override (p.796-797); the **value** must be measured in your environment.

## 7. [extrapolation] and what the sources do NOT say
- The values `autovacuum_vacuum_scale_factor = 0.05`, `autovacuum_vacuum_cost_limit = 2000`, "tables bloated 10x or 20x" and "hundreds of updates per second" from v1 **do not come from the manual**.
- PG16 does **not** describe a "forced stop" with mandatory recovery in single-user mode; it describes warnings at 40 million, refusal of new XIDs at fewer than 3 million and recovery **without** single-user mode (PG16 p.794-795).
- "FSM as a binary tree that stores the exact number of free bytes": the manual says **one byte per page** (granularity), without "exact" (PG16 p.2572).
- "LinpData grows downward and HeapTuples upward": the manual says only that new identifiers come from the start of free space and new items from the end (PG16 p.2573).
- The phrase "TOAST replaces with a pointer after LZ4" confuses stages; v1 described three progressive steps, but the manual describes four **per-column strategies** (above).
