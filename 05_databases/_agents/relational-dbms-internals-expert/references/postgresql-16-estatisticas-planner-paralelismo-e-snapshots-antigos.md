# PostgreSQL 16: per-column statistics, CREATE STATISTICS, planner parameters, parallel query and `old_snapshot_threshold`

> Pages = PDF of the PG16 manual (16.15); printed = N − 38. Complements `otimizacao-de-consultas-e-planos-de-execucao.md` (EXPLAIN, pg_statistic, extended statistics p.553-557) with what the manual says in: `ALTER TABLE ... SET STATISTICS` and `n_distinct` (PG16 p.1644), `ANALYZE` (PG16 p.1678-1679), `CREATE STATISTICS` (PG16 p.1807-1808), planning (PG16 p.680-686), parallel query (PG16 p.564-568, p.660-661, p.683), `old_snapshot_threshold` (PG16 p.661-662) and the `old_snapshot` module (PG16 p.2872). `[derived]` = calculation done in the package.

## 1. Per-column statistics: target, `SET STATISTICS` and `n_distinct` [from source]
- **The target (`default_statistics_target`)** sets the maximum number of entries in `most_common_vals` and the maximum number of histogram *bins*; **the default is 100**, and it can be adjusted up or down, trading estimate accuracy for `ANALYZE` time and `pg_statistic` space (PG16 p.554, p.685, p.1679). It can be set per column with `ALTER TABLE ... ALTER COLUMN ... SET STATISTICS` (PG16 p.1679).
- **`ALTER TABLE ... SET STATISTICS n`**: accepts **0 to 10000**, or **-1** to revert to the system default (`default_statistics_target`); acquires a **`SHARE UPDATE EXCLUSIVE`** lock (PG16 p.1644). **Target 0 disables collection** of the column's statistics, which can be useful for columns never used in `WHERE`, `GROUP BY` or `ORDER BY` (PG16 p.1679). `ANALYZE` requires only a **read lock** on the table, so it runs in parallel with other activity (PG16 p.1678).
- **The sample**: `ANALYZE` uses a **statistically random sample** of rows (PG16 p.790). **The largest target among the analyzed columns determines how many rows are sampled**, and raising the target proportionally raises the time and space of `ANALYZE` (PG16 p.1679). The sources **give no numeric formula** (for example "300 × target"); any such constant is `[extrapolation]`. The statistics are approximate and change slightly with each `ANALYZE`, even with no change in the data, which rarely changes the plan; to avoid this, increase the amount collected (PG16 p.1678-1679).
- **`n_distinct` and `n_distinct_inherited`** (per-attribute options, `ALTER TABLE ... ALTER COLUMN ... SET (n_distinct = ...)`; the **only** per-attribute options defined) **override the distinct-value estimates of subsequent `ANALYZE` runs**: `n_distinct` affects the statistics of the table itself; `n_distinct_inherited` affects the statistics of the table **plus its inheritance children** and those of **partitioned tables**. **Positive** value: the planner assumes exactly that number of non-null distinct values. Value **between −1 and 0**: the planner estimates the distinct values by multiplying the absolute value by the table's row estimate; **−1 = all distinct; −0.5 = each value appears twice on average**; useful when the table size changes over time. Changing these options acquires `SHARE UPDATE EXCLUSIVE` (PG16 p.1644). `ANALYZE` can be quite wrong in counting distinct values even with the largest possible target, and the manual then recommends determining the value manually and installing it with `SET (n_distinct = ...)` (PG16 p.1679).
- `[derived]` (example): 200 million rows and an average of 4 rows per value ⇒ 200,000,000 / 4 = **50,000,000** distinct values ⇒ `n_distinct = 50000000` (absolute) or `−0.25` (relative: 0.25 × 200,000,000 = 50,000,000, p.1644). On a **partitioned** table, the option is `n_distinct_inherited` (the parent's statistics are those of the hierarchy): `ALTER TABLE eventos ALTER COLUMN usuario_id SET (n_distinct_inherited = -0.25);` and the effect appears **at the next `ANALYZE`** (the option overrides the `ANALYZE` estimate, not the current statistics).
- **`ANALYZE` and inheritance/partitioning** (PG16 p.1679): with inheritance, it collects two sets of statistics (parent only, and parent + children), without analyzing the children individually; **autovacuum considers only inserts/updates on the parent itself**, so if the parent rarely changes, the inheritance statistics go stale without a manual `ANALYZE`. On a **partitioned table**, `ANALYZE` samples rows from **all partitions** and also walks each partition updating its statistics (**each leaf partition only once**, even with subpartitioning); there is no "parent only" statistic, because it is empty. **Autovacuum does not process partitioned tables** nor inheritance parents if only the children are modified: periodic manual `ANALYZE` is needed (PG16 p.1679, p.797). Foreign tables are only analyzed when explicitly selected (and if the wrapper supports it); an **empty** table gets no new statistics (the existing ones are kept); progress appears in `pg_stat_progress_analyze` (PG16 p.1678-1679).
- **Permission**: normally only the owner or a superuser; database owners can analyze all tables of the database except shared catalogs (PG16 p.1678). With no table given, it analyzes all ordinary tables, partitioned tables and materialized views of the database, **not** foreign tables (PG16 p.1678). Common strategy for mostly-read databases: `VACUUM` and `ANALYZE` once a day at a quiet time (not enough with heavy updates); with autovacuum on (default) it takes care of `ANALYZE` (PG16 p.1678).
- **`pg_stats`** is readable by everyone (restricted to the tables the user can read), whereas `pg_statistic` is readable only by a superuser; a column appears in two rows if there is inheritance (`inherited` = t/f) (PG16 p.554).

## 2. `CREATE STATISTICS` (*extended statistics*) [from source]
- Creates a statistics object on **a table, foreign table or materialized view**, in the current database, owned by whoever runs it; **you must own the table**; once created, ownership of the object is independent of the table (PG16 p.1807-1808). Two forms: **univariate** on an expression (benefit similar to an expression index **without the index's maintenance cost**) and **multivariate** on two or more columns and/or expressions; column order does not matter (PG16 p.1807-1808).
- Types: `ndistinct`, `dependencies` (functional dependencies) and `mcv` (most-common-value lists); without the clause, **all** types are included (PG16 p.1807). The object only *defines*; collection is done by `ANALYZE` (PG16 p.555).
- **Single-expression form x multivariate form: the statistics type** (PG16 p.1807-1808): the first form (`CREATE STATISTICS [name] ON (expression) FROM table`) collects **univariate** statistics of a single expression and **does not allow specifying the statistics type** (`ndistinct`, `dependencies`, `mcv`), because those types refer only to multivariate statistics. Hence `CREATE STATISTICS ... (ndistinct) ON (expression) FROM t` is not a valid form. The second form (multivariate) accepts the list of types in parentheses and requires **at least two columns or expressions**, in any order; it also automatically generates univariate statistics for each listed expression. Expression statistics are built automatically when the definition includes complex expressions and not just plain columns. With `IF NOT EXISTS` the name is mandatory; without a name, PostgreSQL chooses one from the table and the columns/expressions.
- **"Extended statistics are currently not used by the planner for selectivity estimates of joins between tables"**; the manual says this limitation will probably be removed in a future version (PG16 p.1808). That is, extended statistics do not apply to joins: the correlation between columns of **different tables** in a JOIN is not corrected by `CREATE STATISTICS`: the object applies to a single table. For tables or partitions, see `ANALYZE`'s handling of inheritance (PG16 p.1808).
- Manual example (PG16 p.1808): `a` and `b` functionally dependent (`i/100`, `i/500` over `generate_series(1,1000000)`); without extended statistics, `WHERE a = 1 AND b = 0` has a drastically underestimated row count; after `CREATE STATISTICS s1 (dependencies) ON a, b FROM t1; ANALYZE t1;` the estimate improves.
- When propagating estimates: ARCH says that **selectivity errors early on propagate multiplicatively up the plan tree** (ARCH p.44-45), which explains why a `rows=1` estimate for a correlated filter can ruin joins and access methods further up (see `otimizacao-de-consultas-e-planos-de-execucao.md`).

## 2b. `EXPLAIN ANALYZE`: measurement artifacts and `reltuples`/`relpages` [from source] (PG16 p.552-553)
- **Measured time x real time** (PG16 p.552): `EXPLAIN ANALYZE` time can diverge from normal execution because no rows are delivered to the client (network transmission and I/O conversion are left out) and because the overhead of the measurement itself can be large, especially where `gettimeofday()` is slow; the `pg_test_timing` tool measures this overhead. The result should not be extrapolated to very different situations (toy table x large table); with a one-page table a sequential scan almost always results, whether or not there is an index.
- **Estimated x actual without estimation error** (PG16 p.552): when a node is stopped early by `LIMIT` (or a similar effect), estimated cost and rows are shown as if the node ran to completion, but the actual is smaller; it is a display discrepancy, not a planner error.
- **Planning time and Execution time** (PG16 p.552): the first does not include parse or rewrite; the second includes executor startup and shutdown and fired triggers, but not parse, rewrite or planning. BEFORE triggers are included in the time of the Insert/Update/Delete node; AFTER triggers are **not**, because they fire after the whole plan, and the total time of each trigger is shown separately. Deferred constraint triggers only run at the end of the transaction and are **not accounted for** by `EXPLAIN ANALYZE`.
- **Merge join** (PG16 p.553): has its own measurement artifacts. It stops reading one input when the other is exhausted and the first's next key is greater than the other's last (no further match is possible), so it **does not read one of the children in full**, with an effect similar to `LIMIT`. In addition, if the outer child has **duplicate keys**, the inner child is **backed up and re-read** for the part that matches that key, and `EXPLAIN ANALYZE` **counts those re-emissions as if they were new rows**: with many duplicates in the outer, the inner child's `actual rows` can be **much larger** than the real number of rows in the inner relation.
- **`BitmapAnd` and `BitmapOr`** (PG16 p.553): always report **zero** actual rows, due to an implementation limitation. `[inference]` The manual cites only these two nodes; the example on p.548 shows a plain `Bitmap Index Scan` with a normal actual count (rows=10), so one should **not** generalize "bitmap nodes show zero".
- **`Subplans Removed: N`** (PG16 p.553): the executor may decide that certain nodes need not run because they would produce no rows, based on parameters unknown at planning time; today this only applies to children of `Append` or `MergeAppend` on a partitioned table. Those nodes vanish from the output and the annotation with the count appears (see also run-time pruning in `postgresql-16-particionamento.md`).
- **`reltuples` and `relpages`** (PG16 p.553): `pg_class` stores, per table and per index, the total number of entries (`reltuples`) and of disk blocks (`relpages`); it is the first piece of the planner's statistics. In the manual's example the table `tenk1` has 10000 rows in 358 pages and each index has 10000 entries in 30 pages. These values are **not updated in real time** and tend to be **slightly out of date**: what updates them are `VACUUM`, `ANALYZE` and some DDL commands such as `CREATE INDEX`. A `VACUUM` or `ANALYZE` that **does not scan the whole table** (the common case) updates `reltuples` **incrementally** from the scanned part, giving an approximate value. In any case the planner **scales** the `pg_class` values to the table's **current physical size**, obtaining a better approximation.

## 3. Planner parameters and their defaults [from source] (PG16 p.680-686)
- The `enable_*` settings (all **on** by default, except `enable_partitionwise_join` and `enable_partitionwise_aggregate`, **off**, because they are expensive in memory and CPU) are a "crude" method of influencing plans: the manual treats them as a **temporary workaround**, and recommends as better paths adjusting the cost constants, running `ANALYZE`, raising `default_statistics_target` and per-column `SET STATISTICS` (PG16 p.680-682). Among them: `enable_seqscan`, `enable_indexscan`, `enable_indexonlyscan`, `enable_bitmapscan`, `enable_hashjoin`, `enable_mergejoin`, `enable_nestloop`, `enable_hashagg`, `enable_sort`, `enable_material`, `enable_memoize`, `enable_partition_pruning`, `enable_parallel_append`, `enable_parallel_hash`, `enable_gathermerge`, `enable_presorted_aggregate` (PG16 p.680-682).
- **`enable_indexscan` and `enable_indexonlyscan`**: the first also covers the index-only scan (PG16 p.680). Turning off `enable_indexscan` disables index scan **and** index-only scan; `enable_indexonlyscan` turns off only the index-only scan, and the manual says `enable_indexscan` **must also be on** for the planner to consider index-only scans. That is, with `enable_indexscan = off` there is no index-only scan, even with `enable_indexonlyscan = on`. `[inference]` To investigate whether the planner would use an index-only scan, keep both on; the manual treats all `enable_*` as a temporary workaround, not a permanent adjustment.
- **Costs**: `seq_page_cost` 1.0; **`random_page_cost` 4.0** (the manual says random access on durable storage normally costs much more than 4x sequential, but the default is lower because most random accesses, such as index reads, are assumed to be cached; if caching is less frequent and network latency is minimal, it can be raised; with media that has a lower relative random cost, lower it); `cpu_tuple_cost` 0.01; `cpu_index_tuple_cost` 0.005; `cpu_operator_cost` 0.0025; **`parallel_setup_cost` 1000**; **`parallel_tuple_cost` 0.1**; `min_parallel_table_scan_size` 8 MB; `min_parallel_index_scan_size` 512 kB (PG16 p.682-683).
- **`effective_cache_size`** (default **4 GB**): the planner's assumption about the size of the disk cache available **to a single query**, summing shared_buffers and the part of the OS cache used by data; it **does not reserve memory** nor change the allocated shared memory; larger values favor index scans, smaller values favor sequential scans (PG16 p.683-684).
- **`jit`** default **on**; `jit_above_cost` 100000; `jit_inline_above_cost` 500000; `jit_optimize_above_cost` 500000 (makes no sense below `jit_above_cost`); -1 disables each one (PG16 p.684, p.686).
- **GEQO** (genetic optimizer): `geqo` on; `geqo_threshold` **12** FROM items (a `FULL OUTER JOIN` counts as one item); `geqo_effort` 5 (1 to 10); `geqo_pool_size` 0 = automatic; `geqo_selection_bias` 2.00; `geqo_seed` 0 (PG16 p.684-685). For simple queries the exhaustive planner is better; with many tables the exhaustive search takes longer than the penalty of a bad plan.
- **`from_collapse_limit` = 8** (subqueries are merged if the resulting FROM list does not exceed this) and **`join_collapse_limit`** (default equal to `from_collapse_limit`): rewrites explicit JOINs (except FULL JOIN) into lists of FROM items; **value 1 prevents any reordering of explicit JOINs** (the written order will be the execution order); smaller values reduce planning time and can worsen the plan; values ≥ `geqo_threshold` can trigger GEQO and generate non-optimal plans (PG16 p.686).
- **`default_statistics_target`** 100 (PG16 p.685); **`constraint_exclusion`** default `partition` (examines the CHECK constraints only of inheritance children and `UNION ALL` subqueries) (PG16 p.685-686); **`cursor_tuple_fraction`** 0.1 (smaller values favor fast-start plans for cursors) (PG16 p.686); **`recursive_worktable_factor`** 10.0 (estimated average size of the work table of a recursive query, as a multiple of the non-recursive initial term; a smaller value such as 1.0 can help in certain recursion cases, p.686-687) (PG16 p.686); **`plan_cache_mode`** `auto` (default), `force_custom_plan` or `force_generic_plan`: custom plans are redone at each execution with the parameter values, generic plans are reusable (they save planning, but can be inefficient if the ideal plan depends on the values); applies to explicit and implicit PREPARE (for example in PL/pgSQL) (PG16 p.686).

## 4. Parallel query [from source]
- **How it works** (PG16 p.564-565): the plan gets a `Gather` or `Gather Merge` node with **a single child**, the part of the plan executed in parallel; only the part below it runs in parallel. Planned workers are limited by `max_parallel_workers_per_gather`; the total of background workers is limited by `max_worker_processes` and `max_parallel_workers`, so a query can run with **fewer workers than planned, or none** (PG16 p.564-565). **Defaults** (another page: PG16 p.660-661, not p.564-565): `max_parallel_workers_per_gather` = **2** (0 disables), `max_worker_processes` = **8** (only at startup; on a standby it must be equal to or greater than on the primary), `max_parallel_workers` = **8** (p.661). The leader also executes the parallel part and reads the rows from the workers; with many generated rows, the leader ends up almost only reading. `Gather Merge` preserves ordering (each process produces ordered output and the leader merges); `Gather` reads in whatever order is convenient, destroying the ordering (PG16 p.564-565). Many queries run **more than 2x** faster and some **4x or more**, especially those that touch a lot of data and return few rows (PG16 p.564).
- **When it is not used** (PG16 p.565-566): `max_parallel_workers_per_gather = 0`; single-user mode; the query **writes data or locks rows** (including inside a CTE; exceptions: the inner `SELECT` of `CREATE TABLE AS`, `SELECT INTO`, `CREATE MATERIALIZED VIEW`, `REFRESH MATERIALIZED VIEW`); the query can be **suspended** (`DECLARE CURSOR` cursor; PL/pgSQL `FOR x IN query` loop); it uses a function marked `PARALLEL UNSAFE` (most system functions are `PARALLEL SAFE`; **user-defined ones are `PARALLEL UNSAFE` by default**); it is inside another query that is already parallel. At run time the leader runs everything alone if no workers are available or if the client sends `Execute` with a nonzero row count (PG16 p.565-566).
- **Parallel scans** (PG16 p.566): parallel seq scan (blocks divided into ranges); parallel bitmap heap scan (one leader does the index scan and builds the bitmap; **the index scan is not parallel**); parallel index scan/index-only scan **only for B-tree**, each process taking one index block at a time.
- **Parallel joins** (PG16 p.566-567): nested loop (inner side always non-parallel; efficient if it is an index scan); merge join (inner side always non-parallel and executed in full by each process, which can be inefficient if there is sorting); hash join without "parallel" (each process builds an identical copy of the hash); `Parallel Hash` splits the construction of a shared hash.
- **Parallel aggregation** (PG16 p.567): in **two stages**: each process does a `Partial Aggregate` (partial result per group it knows), the partials go to the leader via `Gather`/`Gather Merge`, and the leader re-aggregates in the `Finalize Aggregate`. Because the `Finalize Aggregate` runs in the leader, **queries with many groups relative to the number of input rows look less favorable**: in the worst case, the number of groups seen by the `Finalize Aggregate` can equal the number of input rows seen by all the workers, with no benefit at all; the planner takes this into account and **is unlikely to choose** parallel aggregation in that scenario. **Requirements**: each aggregate must be **parallel safe** and have a **combine function** (*combine function*); if the transition state is of type `internal`, it needs **serialization and deserialization** functions. There is **no parallel aggregation** if any aggregate call contains **`DISTINCT` or `ORDER BY`** (for example count(DISTINCT x)), nor for **ordered-set aggregates** (such as `percentile_cont ... WITHIN GROUP`) nor for queries with **`GROUPING SETS`**; and only if **all joins** of the query are part of the parallel portion of the plan (PG16 p.567, p.1713-1714).
- **Parallel append**: `Parallel Append` spreads the processes among the children (partitions, `UNION ALL`) and accepts partial and non-partial children (a non-partial child is scanned by a single process) (PG16 p.567); `enable_parallel_append` turns it off.
- **Tips** (PG16 p.567-568): if an expected query does not go parallel, reduce `parallel_setup_cost` or `parallel_tuple_cost` (even to zero; if it is still not parallel there is another reason); `EXPLAIN (ANALYZE, VERBOSE)` shows per-worker statistics.
- **Parallel safe, parallel restricted and parallel unsafe (parallel safety)** (PG16 p.568): the planner classifies each operation into one of three classes. **Parallel safe** does not conflict with a parallel query; **parallel restricted** does not run in a worker, but can run in the leader (never below `Gather`/`Gather Merge`, can appear in other parts of the plan); **parallel unsafe** runs neither in a worker nor in the leader, and anything unsafe **disables parallelism for the whole query**. Always restricted: scans of a CTE, of a temporary table, of a foreign table (unless the FDW says otherwise), nodes with `InitPlan`, and nodes that reference a correlated `SubPlan`.
- **Marking functions and aggregates** (PG16 p.568): the planner **cannot determine on its own** the class of a user-defined function or aggregate, because that would require predicting everything the function may do; the manual says this is equivalent to the **Halting Problem** (impossible in general) and that, **even for simple functions** where it would be conceivable, the planner **does not try**, as it is expensive and error-prone. Hence the planner **does not read the body** of the function: user-defined functions and aggregates are treated as **PARALLEL UNSAFE** unless marked (`PARALLEL SAFE|RESTRICTED|UNSAFE` in `CREATE FUNCTION`/`ALTER FUNCTION`; the `PARALLEL` option with `SAFE|RESTRICTED|UNSAFE` in `CREATE AGGREGATE`). Those that write to the database, access sequences, alter transaction state (even an `EXCEPTION` block in PL/pgSQL) or make persistent configuration changes must be UNSAFE; RESTRICTED are those that access temporary tables, client connection state, cursors, prepared statements or backend-local state that cannot be synchronized among workers (`setseed` and `random` are restricted for this reason). **Marking wrongly** (safe when it is restricted/unsafe, or restricted when it is unsafe) **can generate errors or wrong results**; poorly marked C functions can have undefined behavior; when in doubt, UNSAFE (PG16 p.568). `CREATE AGGREGATE` with `COMBINEFUNC` (and, if the state is `internal`, `SERIALFUNC` and `DESERIALFUNC`) enables partial/parallel aggregation (PG16 p.1709-1711); `ordered-set` aggregates and calls with `DISTINCT`/`ORDER BY` never use partial aggregation (PG16 p.1713-1714).
- **Resources** (PG16 p.660-661): each worker is a separate process and consumes roughly as much as an additional session; **limits such as `work_mem` apply per worker**: a parallel query with 4 workers can use **up to 5 times** the CPU, memory and I/O of a query without workers. `max_parallel_maintenance_workers` (default **2**) applies to **B-tree** `CREATE INDEX` and `VACUUM` without `FULL`, and `maintenance_work_mem` applies to the whole command (not per worker); `parallel_leader_participation` default **on** (PG16 p.661).

## 5. `old_snapshot_threshold` and the `old_snapshot` module [from source]
- **`old_snapshot_threshold`** (PG16 p.661-662): minimum time a snapshot can be used without risk of a "snapshot too old" error. Dead data older than the limit can be cleaned by vacuum, helping avoid bloat when there are long snapshots; an error is raised if the snapshot is older than the limit and is used to read a page modified after the snapshot. **Without a unit, the value is in minutes; default −1 (disabled, equivalent to an infinite limit); can only be set at server start.** Useful values in production: from a few hours to a few days; small values (0, 1min) exist only for testing; 60d is allowed, but in many workloads extreme bloat or XID wraparound can occur within much shorter periods.
- **Side effects**: with the feature on, **free space at the end of a relation cannot be returned to the OS**; all allocated space remains associated with the relation, for reuse within it, unless explicitly released (for example `VACUUM FULL`) (PG16 p.662).
- **It does not guarantee the error**: if correct results can be generated from a cursor that materialized the result set, **no error is raised** even with the rows cleaned; **tables that cannot be cleaned early** (such as system catalogs) are not affected: it neither reduces bloat on them nor creates an error (PG16 p.662).
- `hot_standby_feedback` **does not override** the primary's limit: a snapshot on the standby that exceeds the limit can be invalidated (PG16 p.677-678).
- **`old_snapshot` module** (PG16 p.2872): only **inspects** the internal state used by the feature, and exposes one function: `pg_old_snapshot_time_mapping(array_offset int4, end_timestamp timestamptz, newest_xmin xid)`, which returns all entries of the server's time → XID mapping; each entry is the newest `xmin` of any snapshot taken in the corresponding minute. **There are no functions to reset or change the limit at run time** (the sources do not include `pg_old_snapshot_reset` or `pg_old_snapshot_set_threshold`).

## 6. [inference]
- For a table with 40 million groups and a sum per group, the manual explains why the Finalize in the leader sees almost as many groups as input rows and the planner tends to refuse parallelism (PG16 p.567); "removing the `DISTINCT` may allow the parallel plan" is a consequence of PG16 p.567, but the planner still decides by cost.
- A fixed `n_distinct` becomes obsolete when the table grows; the relative (negative) value tracks growth (PG16 p.1644) `[inference]` — but only as long as the proportion of distinct values per row remains similar.

## 7. [extrapolation] and what the sources do NOT say
- ANALYZE sample-size formulas (such as "300 × target") are not in the sources consulted.
- `old_snapshot_threshold` was removed in versions after PG16 (external knowledge; the sources cover 16.15).
- The manual does not say how to choose the value of `random_page_cost` for SSD; it only describes the logic (cache x random cost) (PG16 p.682).
