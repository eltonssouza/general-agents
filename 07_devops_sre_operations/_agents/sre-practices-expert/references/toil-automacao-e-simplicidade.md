## Toil (Ch. 5)
- Definition: work tied to running a production service that tends to be manual, repetitive, automatable, tactical, devoid of enduring value, and that scales linearly as the service grows. Not every task has all the attributes. [from source] (SRE p.51)
- It is **not** toil: work one dislikes, administrative overhead (team meetings, setting and grading goals, snippets, HR paperwork) and "grungy" work with long-term value (e.g., cleaning up alert configuration). [from source] (SRE p.51)
- Manual includes running by hand a script that automates the task: it is faster than executing each step, but the human hands-on time spent running the script (not the elapsed time) is still toil. Repetitive: a task done for the 1st time, or even the 2nd, is not toil. [from source] (SRE p.51)
- Overhead (the book's list): hiring, HR paperwork, team/company meetings, bug queue hygiene, snippets, peer reviews and self-assessments, training courses. [from source] (SRE p.53)
- Six criteria: manual, repetitive, automatable, tactical, no enduring value, O(n) with service growth. [from source] (SRE p.51-52)
- Goal: toil below 50% of each SRE's time; at least 50% on engineering. [from source] (SRE p.52)
- Floor calculation: with 1 week of primary and 1 of secondary per cycle, a 6-person rotation gives a floor of 2/6 = 33% of time; with 8 people, 2/8 = 25% (lower bound of potential toil). [from source] (SRE p.52)
- Largest reported sources: interrupts, on-call, releases/pushes. Quarterly survey: average ~33%, with outliers from 0% to 80%. [from source] (SRE p.52) [DATED]
- Activity categories: software engineering, systems engineering, toil, overhead. [from source] (SRE p.52-53)
- Harms of excess toil: career stagnation, low morale, confusion about the role, slowdown, precedent (devs push operations onto SRE), friction, broken promises to those who joined for projects. In small doses it is not bad. [from source] (SRE p.53)
- Beware of "requires human judgment": it can be a design failure (a service that alerts several times a day). [from source] (SRE p.53-54, note 21)
- The book does NOT give an automation ROI formula nor a method for prioritizing which toil to eliminate (the only related reference is note 28 of Ch. 7, which merely points to the xkcd.com/1205 cartoon). [from source] (SRE p.74, note 28)

## Automation (Ch. 7)
- Values: consistency, platform, faster repairs (MTTR), faster action, time savings ("decoupling operator from operation"). [from source] (SRE p.63-64)
- Automation is a "force multiplier", not a panacea; better still is a system that does not need automation (autonomous). [from source] (SRE p.63)
- Hierarchy of classes (example: DB master failover): (1) none, (2) SRE script maintained outside the system, (3) generic automation maintained outside, (4) internal, specific automation, (5) system that needs no automation. [from source] (SRE p.66)
- **"Maximalist" view and its limits (p.65)** [from source]: Google has an ideological inclination to use machines to manage machines (and controls the whole stack, since the code is almost always available), but the book admits reality demands adjustment: **it is not appropriate to automate every component of every system**, not everyone has the ability or willingness to develop automation at a given moment, and some essential systems were born as quick prototypes, not designed to last or to interact with automation. The previous paragraph describes a maximalist position, put into practice with broad success in Google's context; the general choice was to build platforms, or to position itself to build platforms over time, seen as necessary for manageability and scale. (SRE p.65)
- **Rarely executed automation and bit rot (p.66)** [from source]: turnup automation is usually kept separate from the core system and suffers bit rot (it does not change when the system changes); trying to couple the two more tightly fails because of misaligned priorities, since developers rightly resist requiring a test deployment on every change; in addition, automation that is crucial but runs only occasionally, and is therefore hard to test, is especially fragile because of the long feedback cycle. **Classic example of rare automation: cluster failover**, which may happen only every few months, or so rarely that inconsistencies between instances accumulate. (SRE p.66)
- High abstractions are easy to manage but "leak": case of a binary push that assumes atomicity. [from source] (SRE p.65)
- Ads/MySQL on Borg case: manual failover of 30-90 min per instance was incompatible with the error budget (at best 99% uptime; the budget called for <30 s per failover); the "Decider" daemon (2009) did failover in <30 s in 95% of cases; cost: all applications gained much more failure-handling logic (custom JDBC); mundane operational work dropped ~95%, with automated schema changes the total maintenance cost fell nearly 95%, and ~60% of the hardware was freed. Details in the section "Automation cases with numbers and narrative". [from source] (SRE p.66-67)
- Prodtest and idempotent fixes: each test paired with an idempotent fix that can run every 15 minutes; lessons on latency between test and fix producing flaky tests. [from source] (SRE p.68-70)
- Competence / latency / relevance triangle: automation kept away from those who operate loses relevance and competence; bad incentives arise when the owning team is not accountable for the automation. [from source] (SRE p.70-71)
- Admin Servers / Local Admin Daemon: authenticated RPC with ACLs, code review and auditing instead of root SSH. [from source] (SRE p.72) [DATED]
- **Evolution of turnup automation in 5 stages (p.72, the book's own list)** [from source]: 1. manual action triggered by an operator (no automation); 2. system-specific automation, written by the operator; 3. generic automation maintained externally; 4. system-specific automation, maintained internally; 5. autonomous systems that need no human intervention. Do not confuse with the failover list on p.66. (SRE p.72)
- Bigtable initial disk case (implicit safety signal): automation wiped disks of Bigtable machines because it assumed "unused disk = machine with no storage"; replicas prevented loss. [from source] (SRE p.68). Bit rot of turnup automation maintained outside the system: (SRE p.66)
- Diskerase case: the empty set was interpreted as "all machines"; lessons: sanity checks, rate limiting, idempotent workflow. [from source] (SRE p.74; also Ch. 13, p.119-120)
- Recommendation: automating does not require Google scale; the biggest lever is in design; autonomy is hard to retrofit. [from source] (SRE p.74)
- Counter-risk: when automation fails, the operator has lost fluency and a mental model (reference to Air France 447); train with drills (Air France 447 and drills are in notes 33 and 35, printed on p.75). [from source] (SRE p.73-75)

## Simplicity (Ch. 9)
- Perfect stability only in a vacuum; SRE balances agility and stability; exploratory code with an expiry date may sacrifice stability. [from source] (SRE p.82)
- "The virtue of boring": surprises in production are the nemesis of SRE; essential vs accidental complexity (Brooks); SRE should resist the accidental. [from source] (SRE p.82-83)
- Commented-out code and dead code guarded by a permanently disabled flag are bad ideas (the book cites Knight Capital and the SEC order; the loss figure, US$ 440 million in a few hours, is in Ch. 33, p.321-322); every line is a liability; removal routine and bloat detection in tests. [from source] (SRE p.83)
- "Negative lines of code" metric; minimal APIs; modularity and API versioning; avoid "util"/"misc" binaries. [from source] (SRE p.83-84)
- Simple releases: small batches make it easier to attribute cause (analogy with gradient descent). [from source] (SRE p.84)
- Modularity (p.84): release cadence can vary between parts of the system, without requiring a full push for every change; the separation of responsibilities between APIs and binaries matters more as the system grows, in direct analogy with object-oriented design: just as a "grab bag" class with unrelated functions is bad practice, so is putting a "util" or "misc" binary into production; a well-designed distributed system has collaborators with a clear, bounded purpose. Modularity also applies to data formats: one of the central strengths of Google's **protocol buffers** was creating a wire format that is backward and forward compatible. **Note 40 (p.84)**: protocol buffers ("protobufs") are an extensible, language- and platform-neutral mechanism for serializing structured data; the text is the same as note 12 of Ch. 2 (p.35), but note 40 is the one that accompanies Ch. 9. [from source] (SRE p.84)
- Saying "no" to a feature keeps the environment free for real engineering. [from source] (SRE p.84)

## Automation cases with numbers and narrative (Ch. 7) [from source]
**Ads MySQL on Borg and the Decider (SRE p.66-67).**
- Context: the Ads database ran on MySQL; from 2005 to 2008 it was in a "mature and managed" state (the replica swap routine was already automated). In late 2008 the team built a proof of concept of MySQL on Borg, hoping to (1) eliminate machine/replica maintenance, since Borg restarts tasks, and (2) pack several instances onto the same physical machine with containers. (SRE p.66-67)
- The problem: tasks move on Borg **once or twice a week**; tolerable for replicas, **unacceptable for masters**. Master failover took **30 to 90 minutes per instance**; with shared machines, reboots for kernel upgrades and normal failures, there would be several unrelated failovers per week. That, added to the number of shards, meant: manual failover would consume many human hours and give, at best, **99% availability**, below the business requirement; and, to fit in the **error budget**, each failover would have to cause **less than 30 seconds of unavailability**, and "there was no way to optimize a human-dependent procedure to under 30 seconds". The book's conclusion: the only way out was to automate failover. (SRE p.67)
- Arithmetic [derived]: from 30-90 min to < 30 s is a reduction of **60x to 180x** (1,800-5,400 s ÷ 30 s); 99% uptime is equivalent to ~3.65 days of unavailability per year.
- The solution: in **2009** Ads SRE finished the failover daemon **"Decider"**, which performed **planned and unplanned failovers in under 30 seconds 95% of the time**. The team went from optimizing the infrastructure for the absence of failover to **accepting that failure is inevitable and optimizing for fast recovery through automation**. (SRE p.67)
- **Admitted cost**: all applications needed much more failure-handling logic than before; since the MySQL world assumes the instance is the most stable component, software such as **JDBC** had to be customized to tolerate a failure-prone environment. (SRE p.67)
- Benefits: time spent on mundane operational tasks **fell 95%**; a database task going down **stopped paging** a human; later, with **schema change automation**, the total operational maintenance cost of Ads Database fell **nearly 95%**; migrating to MoB (MySQL on Borg) freed resources by scheduling several instances per machine: **about 60% of the hardware freed**. "We automated ourselves out of a job." (SRE p.67)

**Cluster turnup, Prodtest and idempotent fixes (SRE p.67-72).**
- Cluster turnup: steps from preparing the building to assigning resources to services; some services had more than a hundred subsystems and complex dependencies; configuring one subsystem differently from the others is "a customer-impacting outage waiting to happen". A multi-petabyte Bigtable cluster was configured to **not use the first (log) disk on 12-disk machines**; a year later an automation assumed "first disk unused = machine with no storage" and **instantly erased all the Bigtable data** (the real-time replicas were saved): automation must not rely on implicit safety signals. (SRE p.68)
- **Prodtest** extended the Python unit-testing framework to test real services, with chained tests (one failure aborts the following ones), per cluster; it generates a graph of the states; each delay caused by another team's misconfiguration becomes a bug to extend Prodtest. For the first time managers could predict when a cluster would go "live" and understand why each cluster took **six weeks or more from "network-ready" to serving traffic**. Senior management's mission: within three months, five new clusters would be network-ready on the same day and should be turned up in **one week** ("One Week Turnup"). (SRE p.68-70)
- Each test was paired with an **idempotent fix**, which could run every **15 minutes** without risk; if a fix fails several times the automation stops and notifies; it made it possible to go from "network works and machines in the database" to "serving 1% of search and ads traffic" in one to two weeks. In retrospect there were flaws: the latency between test, fix and new test created **flaky tests**, and not every fix was naturally idempotent. (SRE p.70)
- The **competence / latency / relevance** triangle: it started with a competent process (maintained by the owners), high latency and very relevant; when centralized in a turnup team, there were **more than a thousand changes per day** in the affected systems, the automation lost relevance and competence, and bad incentives arose (whoever speeds up turnup is not accountable for the service's technical debt). The way out: a security mandate replaced SSH with **Admin Servers** (authenticated local daemon, with ACLs, RPC and code review; each change is auditable) and then turnup became a service-oriented architecture problem: each owner exposes a turnup/turndown API (contract); the process became competent, accurate and low-latency even as the number of teams and services doubled every year. (SRE p.70-72) [DATED]
- Borg and the "warehouse-scale computer": thousands of machines are born, die and go to repair daily without SRE effort; rescheduling a task onto another machine looks like a process switching CPUs, an intrinsic feature of the system and not something to "automate". If automation takes the place of manual actions and they continue to be presumed, operators lose fluency and mental model (note 33: Air France 447; note 35: drills). (SRE p.72-74)
- **Diskerase** (SRE p.74; also p.119-120): the decommissioning of a rack failed after Diskerase; on restarting from the beginning, the set of machines to wipe was (correctly) empty, but the empty set was a special value meaning "everything": almost all machines in all colos were sent to Diskerase; within minutes the CDN lost its disks and stopped terminating connections; users were served by the company's own datacenters and **only a small latency increase was seen**, thanks to good capacity planning; most of **two days** to reinstall the machines in the affected colo and **weeks** to audit and add sanity checks, **including rate limiting**, and to make the decommissioning workflow **idempotent**. (SRE p.74)
- Value of automation (Ch. 7): consistency ("the value of consistency is in many ways the primary value"), platform (a bug fixed once), faster repairs (lower MTTR; a defect found later costs more), faster action and time savings ("decoupling the operator from the operation"); for Google, services would not survive without automation, as they crossed the threshold of manual operation long ago. (SRE p.63-64)

## Knight Capital and dead code (Ch. 9 and Ch. 33) [from source]
- Ch. 9 (p.83): the proposals "comment out the code", "guard it with a flag" instead of deleting are "terrible"; version control reverts changes easily, and code that never executes, guarded by an always-off flag, is "a time bomb", as **Knight Capital experienced**; the reference is the SEC order "In the Matter of Knight Capital Americas LLC" ([Sec13]).
- Ch. 33 (p.321): automation can cause a lot of damage and financial loss in very little time; **"in 2012 Knight Capital Group experienced a 'software glitch' that led to a loss of US$ 440 million in a few hours"**; note 160 (printed on p.322) points to section "FACTS", B, of the SEC order, about the Power Peg software. In the same paragraph: the 2010 Flash Crash (attributed to a trader trying to manipulate the market by automated means) caused a loss "on the order of trillions of dollars in 30 minutes" in the market, which recovered quickly (note 161). The book's lesson: "speed can be negative if the tasks are poorly configured". (SRE p.321-322)
- **The book gives the figure (US$ 440 million) and says "in a few hours"; it gives no duration in minutes.** Any "45 minutes" does not come from the book [extrapolation].

## Round 4 sweep: notes of Ch. 5 and 7 [from source]
- Note 21 (p.53): beware of "it is not toil because it requires human judgment": one must check whether the nature of the task **really** requires judgment and cannot be solved by better design; the example is a service that alerts SREs several times a day, each alert requiring a complex response with a lot of judgment: it is a poorly designed service. (SRE p.53)
- Notes of Ch. 7 (p.74): note 27 says that the expertise gained when building an automation has value of its own (the engineers understand the automated process deeply and automate new processes faster afterward); note 30 recalls that not every managed system exposes callable APIs, which forces certain tools to use a CLI or "automated clicks on websites"; note 26 warns that those who already know the value of automation can go straight to "The Value for Google SRE", but that the description has useful nuances. (SRE p.74)

### Use cases and limits of automation (Ch. 7, p.65) [from source]
- Automation is "meta-software" (software that acts on software); examples of use: user account creation, cluster turnup and turndown, preparation and decommissioning of installations, version rollouts, runtime configuration changes (including of dependencies). In SRE the focus is usually the **lifecycle of systems** (for example, deploying a service to a new cluster), and not the quality of the data passing through the infrastructure, although gross differences are alerted on (half of a dataset disappearing after a push). Tools such as Puppet, Chef, cfengine and even Perl differ mainly in level of abstraction; the trade-off is classic: high abstractions are easy to manage, but when they "leak" the failure is systemic and can be inconsistent (a supposedly atomic binary push can leave binaries prepared but not shipped, shipped but not restarted, or restarted but not verifiable). The book acknowledges that it is not appropriate to automate everything and that some essential systems were born as prototypes; the preference is to build **platforms**. (SRE p.65)

## Corrections after the blind test (round 6): the DNS example in Prodtest (Ch. 7, p.68-71) [from source]
- **Figure 7-1 (p.69): ProdTest of the DNS service.** Shows how **a failing test aborts the chain of following tests**: Prodtest tests have dependencies on each other, forming a chain, and the failure of one quickly stops those that depend on it. The text introducing it is on p.68. Figure 7-2 (p.71) shows the DNS ProdTest in which **a failed test resulted in running only one fix**. (SRE p.68-71)
- **How Prodtest is used (p.68).** Each team's Prodtest receives the **cluster name** and validates that team's services in that cluster. Later it became possible to generate a **graph of the unit tests and their states**: the engineer quickly sees whether the service is well configured in all clusters and, if not, why; the graph highlights the step that failed and the failing Python test emits a more detailed error message. (SRE p.68)
- **Delay caused by another team: bug to extend Prodtest (p.68).** Whenever a team suffered a delay from another team's unexpected misconfiguration, a **bug was opened to extend that team's Prodtest**, so that a similar problem would be discovered earlier in the future; this is prevention, not the blocking mechanics of the fix. (SRE p.68)
- **From test to fix (p.70).** The unit test already knew which cluster it was examining and which test was failing, so each test was **paired with a fix**. If each fix were idempotent and could assume its dependencies were satisfied, solving the problem would be easy and safe; requiring idempotent fixes meant teams could run the "fix script" **every 15 minutes** without fear of damaging the cluster configuration. (SRE p.70)
- **The DNS example with the Machine Database (p.70).** If the **DNS** team's test was blocked by the configuration of a new cluster done by the **Machine Database** team, as soon as the cluster appeared in the database the DNS tests and fixes began to work. It is a dependency block that resolves itself when the other team finishes; it is not a test that "aborts everything". (SRE p.70)
- **The names in the DNS example (Figure 7-2, p.70).** In the DNS example, if `TestDnsMonitoringConfigExists` fails, `FixDnsMonitoringCreateConfig` is called, which scrapes the configuration from a database and checks a skeleton configuration file into the revision control system; then `TestDnsMonitoringConfigExists` passes on retry and `TestDnsMonitoringConfigPushed` can be tried; if this fails, `FixDnsMonitoringPushConfig` runs. **If a fix fails several times, the automation assumes the fix failed, stops and notifies the user.** (SRE p.70)
- **Result and flaw (p.70).** With these scripts a small group of engineers went from "the network works and the machines are listed in the database" to "serving 1% of search and ads traffic" in one or two weeks, which seemed the pinnacle of automation technology; looking back, the approach had a fundamental flaw: the latency between test, fix and second test created **flaky tests** that sometimes passed and sometimes failed, and not every fix was naturally idempotent, so an unstable test followed by a fix could leave the system in an inconsistent state. (SRE p.70)
- **Before Prodtest (p.68).** The creative, fragile shell scripts did not answer readiness questions: were the service's dependencies available and correctly configured? Were all configurations and packages consistent with other deployments? Could the team confirm that every configuration exception was desired? An example of an effect: a flag that made GFS more responsive to log processing leaked into the default templates and cells with many files could run out of memory under load. (SRE p.68)
- **Why the example matters for teaching (p.68-70).** Project managers began to predict when a cluster would go live and to understand why each cluster took six weeks or more from "network-ready" to serving traffic; that visibility, plus the mission "five clusters network-ready on the same day, turned up in one week", motivated the idempotent fixes. (SRE p.68-70)
