# PostgreSQL 16: data types (ranges and limits) and constraints

> Pages = PDF of the PG16 manual (16.15); printed = N − 38. Constraints = PDF 100-110 (section 5.4); numeric types = PDF 184-190; character types = PDF 191-192; date/time = PDF 195-204; boolean = PDF 205; UUID = PDF 216; JSON/jsonb is in `postgresql-16-json-jsonb-e-gin.md`. This reference gathers the **ranges, sizes and numeric warnings** that users ask about most. `[derived]` = calculation done in the package.

## 1. Numeric types [from source] (PG16 p.184-190)
| Type | Storage | Range | Page |
|---|---|---|---|
| `smallint` | 2 bytes | −32,768 to +32,767 | p.184 |
| `integer` | 4 bytes | −2,147,483,648 to +2,147,483,647 | p.184 |
| `bigint` | 8 bytes | −9,223,372,036,854,775,808 to +9,223,372,036,854,775,807 | p.184 |
| `numeric`/`decimal` | variable | up to **131,072** digits before the decimal point and up to **16,383** after | p.185 |
| `real` | 4 bytes | 6 decimal digits of precision (range ~1E-37 to 1E+37) | p.185, p.188 |
| `double precision` | 8 bytes | 15 decimal digits of precision (range ~1E-307 to 1E+308) | p.185, p.188 |
| `smallserial` / `serial` / `bigserial` | 2 / 4 / 8 bytes | 1 to 32,767 / 1 to 2,147,483,647 / 1 to 9,223,372,036,854,775,807 | p.185 |
| `money` | 8 bytes | −92,233,720,368,547,758.08 to +92,233,720,368,547,758.07 (two decimal places) | p.190 |

- `integer` is the **typical choice** (best balance between range, size and performance); `smallint` only if disk space is critical; `bigint` when the range of `integer` is not enough. Out-of-range values give an **error** (PG16 p.185). `[derived]` a `serial` (4 bytes) is exhausted at 2,147,483,647 identifiers: at 1,000 inserts per second, that is 2,147,483,647 / 1,000 / 86,400 ≈ **24.9 days**; at 10 per second, ≈ 6.8 years. The manual says to use `bigserial` if you expect more than 2^31 identifiers over the life of the table (PG16 p.190).
- **`numeric`**: recommended for monetary values and quantities that require exactness; calculations give **exact** results, but are **much slower** than integers and floating point (PG16 p.185). NUMERIC(p,s) declaration: the maximum declarable precision is **1000**; the scale can range from −1000 to 1000 (the SQL standard requires 0 to the precision); `NUMERIC(3,1)` rounds to 1 decimal place and stores from −99.9 to 99.9 (PG16 p.186).
- **numeric with negative scale (since PG15)**: `NUMERIC(2,-3)` rounds to the thousand and stores from −99000 to 99000; precision remains the maximum number of unrounded digits. The detail of the negative scale is on **p.186** (p.185 only anticipates that the scale can be positive or negative). A scale greater than the precision is also allowed (`NUMERIC(3,5)` stores from −0.00999 to 0.00999) (PG16 p.186).
- **`NUMERIC` without precision** stores values of any size within the implementation limits and **does not coerce the scale**; the SQL standard would ask for scale 0, which the manual calls "kind of useless" (PG16 p.186). The declared precision and scale are **maximums, not fixed allocations**: storage is **2 bytes per group of 4 decimal digits plus 3 to 8 bytes of overhead** (PG16 p.186). It accepts `Infinity`, `-Infinity` and `NaN` (infinity only in unconstrained `numeric`); `NaN` is treated as equal to another `NaN` and greater than all values (to allow sorting and indexes) (PG16 p.187). **Rounding**: `numeric` rounds ties **away from zero**; `real`/`double precision` round ties to the **nearest even** on most machines (manual example: rounding 2.5 as numeric gives 3 and as double precision gives 2) (PG16 p.187).
- **Floating point** (`real`, `double precision`): **inexact** types (IEEE 754); **for exactness (such as money) use `numeric`**; comparing equality between floating-point values may not work as expected; `float(1)`–`float(24)` = `real`, `float(25)`–`float(53)` = `double precision`, `float` without precision = `double precision` (PG16 p.188-189). The default output is the shortest precise decimal representation (up to 17 significant digits for `float8` and 9 for `float4`); `extra_float_digits = 0` restores the old rounding to 6 and 15 digits (PG16 p.188).
- **`extra_float_digits` and `float4`/`float8` output (default format, values 0, negative and greater than 0)** (PG16 p.188): by default the text output is the **shortest precise decimal representation** (the decimal value produced is closer to the stored binary value than to any other representable one); it uses **at most 17 significant digits** in `float8` and **9** in `float4`; it is never exactly halfway between two representable values. It is faster to generate than the historical rounded format. For compatibility with old versions or to reduce precision, `extra_float_digits` selects the **rounded** output: value **0** restores the old default (rounding to **6** digits in `float4` and **15** in `float8`); a **negative** value reduces further (`-2` gives 4 and 13 digits); **any value greater than 0** selects the shortest precise format. Applications that wanted precise values used `extra_float_digits = 3`, and **for maximum compatibility between versions the manual says to keep using 3**. So the idea that "the default is to round to 15 digits" is out of date: it was the old default (value 0), and `extra_float_digits` also serves to **reduce** digits, not only to ask for more.
- **Special floating-point values (`Infinity`, `-Infinity`, `NaN`)** (PG16 p.188-189): `real` and `double precision` have `Infinity`, `-Infinity` and `NaN` (IEEE 754); in SQL constants they must be **quoted** (`UPDATE tabela SET x = '-Infinity'`); on input they are recognized case-insensitively, and infinity may also be written `inf` and `-inf`. By IEEE, `NaN` would not equal anything (not even itself), but PostgreSQL treats `NaN` as **equal** and **greater than all non-NaN values**, to allow sorting and use in tree indexes. Range and precision: `real` about 1E-37 to 1E+37, with at least 6 decimal digits; `double precision` about 1E-307 to 1E+308, with at least 15; values too large or too small give an error, and non-representable values close to zero give an underflow error (PG16 p.188).
- **`serial`** is not a real type: it is equivalent to an `integer NOT NULL DEFAULT nextval('seq')` column with the sequence marked as "owned" by the column (dropped along with it); it **does not automatically create `UNIQUE`/`PRIMARY KEY`**; **there can be gaps** in the sequence, even without deleting rows, because an allocated value is "spent" even if the transaction rolls back (PG16 p.189-190). The SQL-standard alternative is the identity column (`GENERATED ... AS IDENTITY`) (PG16 p.189). Changes to sequences are not rolled back on abort (PG16 p.526).
- **`money`**: the fractional precision comes from `lc_monetary`; the output depends on the locale, which can get in the way of restoring data into a database with a different `lc_monetary`; **floating-point numbers should not be used for money**; division of `money` by an integer truncates toward zero (PG16 p.190).

## 2. Character types [from source] (PG16 p.191-192)
- `character varying(n)`/`varchar(n)` (with limit), `character(n)`/`char(n)` (space-padded), `text` (no limit). The limits `n` are in **characters, not bytes**; `n` must be greater than zero and **cannot exceed 10,485,760**; without a specifier, `varchar` and `text` accept strings of any length; `char` without a specifier is equivalent to `char(1)`. The maximum of a stored value is **about 1 GB** (PG16 p.191-192).
- Trying to store a string longer than `n` gives an **error**, unless the excess is only spaces (then it truncates); an **explicit cast** to `varchar(n)` truncates without error (PG16 p.191).
- **Manual tip**: there is **no performance difference** among `char(n)`, `varchar(n)` and `text`, beyond the extra space of the padded type and a few CPU cycles to check the length; `char(n)` is generally the **slowest**. In most cases use `text` or `varchar`; if there is no real limit, **do not invent an arbitrary limit** (PG16 p.191-192).
- The internal type `name` has 64 bytes (63 usable characters, `NAMEDATALEN`) and serves catalog identifiers; the `"char"` type (with quotes) stores one byte (PG16 p.192).

## 2b. Identifiers: `NAMEDATALEN`, truncation, quoting and case (SQL Syntax) [from source] (PG16 p.72)
- **Length limit** (PG16 p.72): the system uses **at most `NAMEDATALEN`-1 bytes** of an identifier; longer names can be written in commands, but **are truncated**. By default `NAMEDATALEN` is 64, so the maximum length is **63 bytes** (bytes, not characters: multibyte characters consume more than one). If the limit is a problem, it can be raised by changing the `NAMEDATALEN` constant in `src/include/pg_config_manual.h` (that is, by **recompiling** the server). `[inference]` two long names that coincide in the first 63 bytes become the same identifier after truncation (collision); the manual does not do that calculation, it only says they are truncated.
- **Quotes and limit** (PG16 p.72): a delimited identifier (in double quotes) can contain any character except the zero code (to include double quotes, write two); **the length limitation still applies**. In quotes the name becomes **case-sensitive**; without quotes, it is always folded to lowercase (`FOO`, `foo` and `"foo"` are the same; `"Foo"` and `"FOO"` are different from each other and from the three). A quoted identifier is never a keyword (`"select"` is a name; unquoted `select` is a syntax error where a name is expected). Folding to lowercase is incompatible with the SQL standard (which folds to uppercase); for portability, the manual suggests always quoting a name or never quoting it. The `U&"..."` variant writes Unicode characters by code (`\0061` or `\+000061`), with `UESCAPE` to change the escape.

## 2c. PostgreSQL limits (Appendix K, Table K.1) [from source] (PG16 p.3001)
- **Table K.1 (PostgreSQL Limitations)** (PG16 p.3001): these are **hard** limits; practical limits (performance, disk) may appear earlier. Values: database size **unlimited**; number of databases **4,294,950,911**; relations per database **1,431,650,303**; relation size **32 TB** (with the default `BLCKSZ` of 8192 bytes); rows per table limited by the number of tuples that fit in **4,294,967,295 pages**; **columns per table 1,600** (also limited by the tuple fitting in a page); **columns in a result 1,664**; **field size 1 GB**; indexes per table unlimited (restricted by relations per database); **columns per index 32**; **partition keys 32**; **identifier length 63 bytes**; **function arguments 100**; **query parameters 65,535**. Columns per index, partition keys, identifier and function arguments **can be raised by recompiling** PostgreSQL.
- **Columns per table and the 8192-byte page** (PG16 p.3001): the tuple must fit in an 8192-byte heap page; manual example: 1,600 `int` columns (without the tuple header) occupy 6,400 bytes and fit, but 1,600 `bigint` occupy 12,800 and do **not** fit. Large `text`, `varchar` and `char` fields can go to the TOAST table, leaving only an **18-byte pointer** in the tuple; short fields use a 4- or 1-byte header and stay in the tuple. **Dropped columns still count** toward the limit, and the null bitmap also takes space.
- **Out-of-line values (TOAST)** (PG16 p.3001): each table can store **at most 2^32 out-of-line values** (theoretical), because each is identified by a 32-bit OID; the practical limit is much lower, since with the OID space full, finding a free OID becomes expensive and slows `INSERT`/`UPDATE`; in general it only matters for tables with many terabytes, and **partitioning** is a possible workaround. `[inference]` the TOAST limit is per **number of values**, not rows; do not confuse it with the 1 GB per-field limit.

## 3. Date and time [from source] (PG16 p.195-204)
| Type | Size | Range | Resolution |
|---|---|---|---|
| `timestamp [(p)]` (without time zone) | 8 bytes | 4713 BC to 294276 AD | 1 microsecond |
| `timestamp [(p)] with time zone` (`timestamptz`) | 8 bytes | 4713 BC to 294276 AD | 1 microsecond |
| `date` | 4 bytes | 4713 BC to 5874897 AD | 1 day |
| `time [(p)]` | 8 bytes | 00:00:00 to 24:00:00 | 1 microsecond |
| `time [(p)] with time zone` | 12 bytes | 00:00:00+1559 to 24:00:00-1559 | 1 microsecond |
| `interval [fields] [(p)]` | 16 bytes | −178,000,000 to 178,000,000 years | 1 microsecond |
- The precision `p` (fractional digits of the seconds) ranges from **0 to 6**; writing just `timestamp` is equivalent to `timestamp without time zone` (SQL standard) (PG16 p.195-196). The manual says `time with time zone` has "questionable usefulness" and recommends combinations of `date`, `time`, `timestamp` and `timestamptz` (PG16 p.195-196, p.201).
- **Time zones**: all types with a time zone are stored **internally in UTC** and converted to the zone of the `TimeZone` parameter on display; types with only a date or only a time assume the local zone; three ways to specify a zone: full IANA name (e.g. `America/New_York`, which contains daylight-saving rules), abbreviation (shifts by a fixed offset; **cannot be used in `TimeZone`/`log_timezone`**) and POSIX style (PG16 p.201). `DateStyle` (MDY, DMY, YMD) resolves the ambiguous day/month/year order on input (PG16 p.196).

## 3a. `interval`: input, `IntervalStyle`, internal fields (months, days, microseconds) and rounding of fractions [from source] (PG16 p.202-204)
- **Interval input, verbose syntax** (PG16 p.202): `[@] quantity unit [...] [direction]`, with units from `microsecond` to `millennium` (and abbreviations/plurals), `direction` = `ago` or empty; the `@` is optional; the quantities are summed with their sign, and `ago` negates all fields. Days, hours, minutes and seconds can come without a unit (`'1 12:59:10'` = `'1 day 12 hours 59 min 10 sec'`); years and months can come with a hyphen (`'200-10'` = 200 years 10 months); these short forms are the only ones allowed by the SQL standard and the ones used in the output with `IntervalStyle = sql_standard`. ISO 8601 is also accepted: the format with designators (`P1Y2M3DT4H5M6S`, the `M` depends on being before or after the `T`) and the alternative format (`P0001-02-03T04:05:06`) (PG16 p.202-204).
- **`INTERVAL '1'` without a unit and interval fields** (PG16 p.203): when writing a constant with a field specification, the reading of quantities without a unit depends on the fields: `INTERVAL '1' YEAR` is **1 year**, whereas `INTERVAL '1'` (no fields) means **1 second**. Values to the **right** of the least significant allowed field are **silently discarded**: `INTERVAL '1 day 2:03:04' HOUR TO MINUTE` loses the **seconds**, but **not** the day.
- **Interval sign (`IntervalStyle` default x `sql_standard`)** (PG16 p.203): under the SQL standard all fields have the same sign, so a leading sign applies to all. PostgreSQL allows different signs and, traditionally, treats each field of the text as having an independent sign: in `'-1 2:03:04'` the sign applies to the **days** and the hours/minutes/seconds part stays **positive**. With `IntervalStyle = sql_standard`, a leading sign applies to **all** fields (only if no other sign appears). To avoid ambiguity, the manual recommends an explicit sign on each field if any is negative.
- **Internal storage of `interval`: three integer fields (months, days and microseconds)** (PG16 p.203): `months`, `days` and `microseconds`, kept **separate** because the number of days in a month varies and a day can have 23 or 25 hours at a daylight-saving transition. The input string is normalized to this format: weeks become days (7 per week) and are kept separate, while the smaller and larger units are combined. Manual example: `'2 years 15 months 100 weeks 99 hours 123456789 milliseconds'` comes out as `3 years 3 mons 700 days 133:17:36.789`. `[derived]` with the same rule: `'3 years 14 months 10 weeks 30 hours 7200000 milliseconds'` = 36+14 = 50 months = 4 years 2 months; 10 weeks = 70 days; 30 h + 7,200,000 ms (= 2 h) = 32 h, that is, `4 years 2 mons 70 days 32:00:00`.
- **Fractions in interval (`'1.5 weeks'`, `'1.5 years'`, `'1.75 months'`)** (PG16 p.203): since there are only integer fields, fractions are converted to smaller units. Fractions of units **larger than months** become a whole number of months (`'1.5 years'` = `1 year 6 mons`). Fractions of weeks and days become whole days plus microseconds, with **30 days per month and 24 hours per day** (`'1.75 months'` = `1 mon 22 days 12:00:00`). `[derived]` `'1.5 weeks'` = 10.5 days = `10 days 12:00:00`. Only the seconds appear fractional in the output.
- **Interval output and `IntervalStyle`** (PG16 p.204): on output, `months` is divided by 12 into years and months; `days` appears as is; microseconds become hours, minutes, seconds and fraction, so months, minutes and seconds never exceed 0-11, 0-59 and 0-59, but years, days and hours can be large (`justify_days` and `justify_hours` transpose). There are four styles: `sql_standard`, `postgres` (**default**), `postgres_verbose` and `iso_8601`, chosen with `SET intervalstyle`. In `sql_standard`, mixed-sign intervals come out as a year-month literal followed by a day-time one with explicit signs (e.g. `-1-2 +3 -4:05:06`).

## 3b. Appendix B: how the parser reads date/time, two-digit year and daylight saving [from source] (PG16 p.2616-2617)
- **Overview** (PG16 p.2616): date/time input goes through an internal heuristic parser that breaks the string into fields, classifies each one and then interprets, ignores or rejects it; there are internal tables for months, days of the week and time zones.
- **Step 1, classify the token** (PG16 p.2616): with a colon it is a time; with a hyphen, slash or two or more dots it is a date (if a date has already been read, the token becomes a time zone name such as `America/New_York`); digits only is a single field or concatenated ISO 8601 date/time (`19990113`, `141516`); starting with `+` or `-` is a numeric time zone or special field.
- **Step 2, alphabetic token** (PG16 p.2616): first looks for a time zone abbreviation (supplied by the configuration file of section B.4); then an internal table of special words (`today`), days, months and noise words (`at`, `on`); if nothing matches, **error**.
- **Step 3, numeric token** (PG16 p.2616): eight or six digits with no other date read = concatenated date `YYYYMMDD` or `YYMMDD`; three digits with a year already read = day of year; four or six digits with a year already read = time (`HHMM`, `HHMMSS`); three or more digits with no date read = **year** (forces the yy-mm-dd order of the others); otherwise the order follows the `DateStyle` parameter (mm-dd-yy, dd-mm-yy or yy-mm-dd), with an **error** if month or day are out of range.
- **Step 4, BC** (PG16 p.2616): with BC, the year is negated and one is added for internal storage (there is no year zero in the Gregorian calendar).
- **Step 5, two-digit year** (PG16 p.2617): without BC and with the year field having **two digits**, it is adjusted to four: if **less than 70, add 2000**, otherwise add 1900. `[derived]` So 69 becomes 2069 and 70 becomes 1970. Manual tip: years 1 to 99 AD are entered with four digits and leading zeros, such as `0099`.
- **B.2, out-of-range values** (PG16 p.2617): a syntactically valid string with a field out of range gives an error (February 31 is rejected).
- **B.2, daylight-saving transition (DST)** (PG16 p.2617): an apparently valid timestamp can be **nonexistent** (spring forward) or **ambiguous** (fall back). These cases are **not rejected**: the ambiguity is resolved by choosing the UTC offset. With `TimeZone` set to `America/New_York`: `'2018-03-11 02:30'` (spring forward) is read as standard time UTC-5 and displayed as 03:30 UTC-4; `'2018-11-04 01:30'` (fall back, two possible 01:30s) is read as standard time and displayed with -05; writing `'2018-11-04 01:30 EDT'` forces the other interpretation, -04.
- **Exact rule** (PG16 p.2617): an **invalid** timestamp inside a spring-forward gap gets the offset that applied **just before** the transition; an **ambiguous** timestamp in a fall-back gets the offset that applies **just after** the transition. In most zones this amounts to "prefer standard time when in doubt".
- `[inference]` To avoid the ambiguity in applications, store the instant with an explicit offset (or in UTC) instead of depending on the automatic resolution; the appendix only describes the rule, it does not make this recommendation.

## 3c. Appendix B.4-B.5: time zone abbreviations and POSIX time zone specification (`TZ`) [from source] (PG16 p.2620-2622)
- **Abbreviation files (B.4)** (PG16 p.2620): the zone name definitions in the files can be copied from the IANA database, but the files themselves cannot be used directly in `timezone_abbreviations` because of the dot in the name. An error reading the set keeps the old one (at startup, the server does not come up). Abbreviations from the file **override** internal meanings that are not time zones (the Australia file defines `SAT`, which then stops meaning Saturday). Changes to `share/timezonesets/` are up to the user (the normal dump does not include the directory).
- **POSIX form (B.5)** (PG16 p.2620): `STD offset [DST [dstoffset] [,rule]]`, with no spaces in practice. `STD` = abbreviation of standard time; `offset` = offset of standard time relative to UTC; `DST` = abbreviation of daylight saving time (without it and the rest, the zone has a **fixed offset, with no daylight-saving rule**); `dstoffset` is usually omitted and is **one hour less** than the standard offset; the abbreviation can be letters (`EST`) or text between `<>` (`<UTC-05>`). The abbreviations here serve only for **output**; those accepted on input come from B.4. The manual says the POSIX specification is inadequate for the complexity of the real history of time zones, but there are reasons to use it sometimes.
- **Inverted sign** (PG16 p.2620-2621): in `offset` (`hh[:mm[:ss]]`, optional sign) the **positive sign means west of Greenwich**, the **opposite of the ISO-8601 convention** used in the rest of PostgreSQL; `hh` with 1 or 2 digits, `mm` and `ss` with 2.
- **Transition rule** (PG16 p.2621): `dstdate[/dsttime],stddate[/stdtime]` (start of daylight saving time and start of standard time; in the southern hemisphere the first date may fall after the second in the year). Date formats: **`n`** (plain integer) = day of year from 0 to 364 (365 in leap years); **`Jn`** = from 1 to 365, **not counting February 29**, so more useful for fixed dates; **`Mm.n.d`** = month `m` (1-12), `n`-th occurrence of weekday `d` (n from 1 to 4, or 5 = the last of the month) and `d` from 0 (Sunday) to 6; `M3.2.0` = second Sunday of March. Times in the rule have no sign and, if omitted, default to **02:00:00**. The M format does not follow **changes in law**; for past dates the IANA database of named zones is needed.
- **Default rule (fallback)** (PG16 p.2621): if there is a daylight-saving abbreviation and the rule is omitted, **`M3.2.0,M11.1.0`** applies, which corresponds to **US practice in 2020** (second Sunday of March to first Sunday of November, at 2am); this rule **does not give the correct US dates for years before 2007**. Manual example (non-American): `CET-1CEST,M3.5.0,M10.5.0/3` describes Paris (last Sunday of March at 2am CET to last Sunday of October at 3am CEST).
- **`EST5EDT`, `CST6CDT`, `MST7MDT` and `PST8PDT`** (PG16 p.2621-2622): look like POSIX, but are treated as **named zones**, since files with these names exist in the IANA database (historical reasons); in practice they produce the **correct historical US transitions**, even where a plain POSIX specification would not. `[inference]` therefore `EST5EDT` is not a generic rule: it is a zone name with American history; time zones of other countries use other IANA names or a POSIX specification with its own rule (like the Paris example).
- **No validation** (PG16 p.2622): there is no reasonableness check of the abbreviation; `SET TIMEZONE TO FOOBAR0` **works**, leaving the system with a strange abbreviation for UTC.

## 4. Other types [from source]
- `boolean`: 1 byte, three states (true, false and unknown = NULL); accepts true, yes, on and 1 for true and false, no, off and 0 for false (PG16 p.205).
- `uuid`: a **128-bit** quantity, written as 32 hex digits in groups 8-4-4-4-12; offers a better uniqueness guarantee than sequences in **distributed systems**, since sequences are only unique within one database (PG16 p.216); the `uuid-ossp` extension offers generators (PG16 p.2977, pointer).
- `bytea`: `hex` format (default of `bytea_output`) or `escape` (PG16 p.193, p.709).
- Text/JSON/arrays/ranges: see `postgresql-16-json-jsonb-e-gin.md` (JSON); **ranges** are summarized in section 4b (PG16 p.244-248); arrays and composite types (PG16 p.229-243) remain **pointer only**.

## 4b. Range types and multirange [from source] (PG16 p.244-248)
- **What they are** (PG16 p.245): a range represents a span of values of a **subtype** (for example `tsrange` has subtype `timestamp`); the subtype must have a **total order**. Useful for scheduling (room booking) and for expressing overlap clearly. Each range type has a corresponding **multirange**, an ordered list of **non-contiguous, non-empty and non-null** ranges.
- `daterange`, `int4range`, `int8range`, `numrange`, `tsrange`, `tstzrange`: built-in range types (PG16 p.245), with the subtypes date, integer, bigint, numeric, timestamp without time zone and timestamp with time zone, in that alphabetical order of names; the multirange has the analogous name (for example `int4multirange`).
- **Operators cited** (PG16 p.245): containment `@>`, overlap `&&`, intersection `*`, `upper()` and `isempty()`; complete lists in the function and operator tables.
- **Inclusive and exclusive bounds** (PG16 p.246): every non-empty range has a lower and an upper bound; `[` is inclusive lower, `(` exclusive lower, `]` inclusive upper and `)` exclusive upper. `lower_inc` and `upper_inc` test inclusion.
- **Unbounded ranges** (PG16 p.246): omitting a bound means no limit on that side, for example `(,3]`. Declaring an omitted bound inclusive is converted to exclusive: `[,]` becomes `(,)`. An omitted bound is **not** the subtype's `infinity`: it is a special value, "beyond" any +/-infinity of the element. With subtypes that have infinity: `[today,infinity)` **excludes** the value `infinity`, whereas `[today,infinity]`, `[today,)` and `[today,]` include it. `lower_inf` and `upper_inf` test infinite bounds.
- **Input and output** (PG16 p.246-247): four patterns, combining parenthesis or bracket on each side (lower bound, comma, upper bound), and the word `empty` (empty range). Each bound may come in double quotes, and this is **necessary** if the value contains **parentheses, brackets, commas, quotes or backslashes** (space is not on this list). To write a bound that is an **empty string**, use `""`, because writing nothing means an infinite bound. Whitespace before and after the range is allowed, but whitespace between the delimiters is part of the bound's value (it may or may not matter depending on the subtype). The rules resemble those of composite type literals.
- **Manual examples** (PG16 p.247): `[3,7)` includes 3 and does not include 7; `(3,7)` includes neither; `[4,4]` has only the point 4; `[4,4)` has no points and is normalized to `empty`. A multirange is written between braces, with ranges separated by commas (`{[3,7), [8,9)}`), with no need for quotes around the set.
- **Constructors** (PG16 p.247-248): a function with the **same name as the type**; with **two arguments** it forms the default range (inclusive lower, exclusive upper, `[)`); the **third argument** is a string `()`, `(]`, `[)` or `[]`; `NULL` in one of the bounds makes the range unbounded on that side. The multirange has an analogous constructor that takes zero or more ranges.
- **Discrete ranges** (PG16 p.248): subtypes with a defined "step" (integer, date) allow converting between inclusive and exclusive representation; `[4,8]` and `(3,9)` are the same set for integers, but **not** for `numeric`. `timestamp` is treated as **continuous**. A discrete type must have a **canonicalization function**; without it, ranges written differently are treated as **unequal** even though they represent the same set. `int4range`, `int8range` and `daterange` use the canonical form `[)`; user-defined types may use another convention.
- **New types** (PG16 p.248): `CREATE TYPE ... AS RANGE` with `subtype` (and `subtype_diff` when useful), for example for `float8`.
- `[inference]` For a room booking without overlap, the `[)` form prevents the end of one booking from colliding with the start of the next; the exclusion constraint with ranges (PG16 p.109) is the mechanism cited to prevent overlap.

## 5. Constraints [from source] (PG16 p.100-110)
- **Any violation gives an error, even if the value comes from the `DEFAULT`** (PG16 p.100).
- **`CHECK`** (PG16 p.100-103): the constraint is satisfied if the expression is **true or NULL**; since most expressions give NULL with a NULL operand, **CHECK does not prevent NULL** (use `NOT NULL`). It can be column-level or table-level; the name can be given with `CONSTRAINT name`. **PostgreSQL does not support CHECK that references data from other rows or tables** (it may seem to work in simple tests, but does not guarantee the database never reaches a state where the condition is false, and dump/restore may fail); use `UNIQUE`, `EXCLUDE` or `FOREIGN KEY` for cross-row/table constraints, or a trigger for a one-time check at insert. The system **assumes that CHECK conditions are immutable**: if a function used in the CHECK changes behavior, PostgreSQL **does not notice** rows that now violate; the manual recommends dropping the constraint, fixing the function and recreating the constraint, which revalidates it.
- **`NOT NULL`** (PG16 p.103): always written as a column constraint; functionally equivalent to `CHECK (col IS NOT NULL)`, but **more efficient** (the downside: you cannot give it an explicit name); "in most designs, most columns should be NOT NULL".
- **`UNIQUE`** (PG16 p.104-105): automatically creates a **unique B-tree index**; by default **two NULLs are not considered equal**, so it is possible to store duplicates with NULL in a constrained column; `NULLS NOT DISTINCT` changes this (default `NULLS DISTINCT`); the default handling is implementation-defined under the SQL standard, so beware of portability. Constraints that cover only **some rows** are not `UNIQUE`: use a **partial unique index** (PG16 p.104).
- **`PRIMARY KEY`** (PG16 p.105): unique **and** not null; a table has at most one; creates an index. On **partitioned** tables the key must include the partition key (see `postgresql-16-particionamento.md`).
- **`FOREIGN KEY`** (PG16 p.106-109; `ON DELETE` actions on p.108-109): the referenced column must be a PK, `UNIQUE` or a column of a non-partial unique index. **`ON DELETE`**: `NO ACTION` (default; allows deferring the check until the end of the transaction), `RESTRICT` (prevents deletion of the referenced row, **without** deferral), `CASCADE` (deletes the referencing rows), `SET NULL`, `SET DEFAULT` (if the default violates the FK, the operation fails); there is a column list for `SET NULL`/`SET DEFAULT` in `ON DELETE` and an analogous `ON UPDATE` (no column list in `ON UPDATE`). The manual advises: if the tables represent independent objects, `RESTRICT` or `NO ACTION`; if one depends on the other (items of an order), `CASCADE` may be appropriate. `MATCH FULL` prevents a referencing row from escaping the FK by having some null column. **PostgreSQL does not automatically create an index on the referencing columns**; since a `DELETE` on the referenced table or `UPDATE` of a referenced column requires scanning the referencing table, **it is often good to index the referencing columns** (PG16 p.109).
- **Exclusion constraint** (`EXCLUDE USING gist (c WITH &&)`) (PG16 p.109): if two rows are compared on the columns/expressions with the indicated operators, at least one comparison must return false or null; automatically creates an index of the specified type.
- **Generated columns** (PG16 p.99-100): cannot have `DEFAULT` or identity, cannot be part of the partition key; keep their own privileges (it is possible to read the generated column without reading the base ones); are computed **after** `BEFORE` triggers; are not replicated in logical replication and do not enter publication column lists.
- **System columns** (PG16 p.109-110): `ctid` identifies the physical location of the row version and **changes if the row is updated or moved (for example, by `VACUUM FULL`)**, so it is not a long-term identifier; `xmin`/`xmax` are the insertion and deletion XIDs (see `postgresql-16-mvcc-e-niveis-de-isolamento.md`). Each UPDATE creates a new version of the same logical row.

## 6. [inference]
- The recommendation "use `bigint` for keys of tables that may grow a lot" follows from the limits of `integer` (2^31−1) and the manual's advice for `bigserial` (PG16 p.190); the manual gives no growth estimates.
- "`CHECK` with a subquery does not work" is the short form of PG16 p.102: the manual says PostgreSQL **does not support** it and that the guarantee does not hold; a `UNIQUE`/`EXCLUDE`/FK or trigger is the alternative path.
