# OCRG — A4 IDOR, A7 function-level authorization, A8 CSRF and A10 redirects/forwards (OCRG p.79-82, 135-146, 151-154)

Source: OCRG v2.0, chs. 10, 13, 14 and 16. Pages = PDF (printed = N − 1). Related in the ASVS (`[inference]` mapping): V4.1.x, V4.2.1, V4.2.2, V1.4.x, V5.1.2, V5.1.5, V13.2.3, V13.1.4.

## A4 — Insecure direct object reference (IDOR) (OCRG p.79-82)
- [from source] The user may be authorized in the application but not for **a specific object** (record, file, URL); if the application does not check the user against that object, there is IDOR. The root of the problem is manipulation of data previously generated by the server (OCRG p.79).
- [from source] Examples: a parameterized query that uses the request's `acct` parameter **without checking the owner** (Sample 10.1) (OCRG p.79); the **Yahoo!** case (analyst Ibrahim Raafat): changing `fid`/`cid` in POSTs allowed deleting other users' comments/posts — more than 1.5 million records (OCRG p.79-80). Attackers also deduce method/URL names (`View` → `Update`/`Modify`/`admin`) from patterns (OCRG p.80).
- [from source] **Data binding** (JSP/Struts/Spring): request parameters automatically bound to variables of the business object; unexposed variables (price, max limit, role) with a static or computed value can be overwritten if the attacker sends extra parameters. Design recommendations: binding objects only with variables that depend on input; accept only desired inputs and reject/leave unbound the rest; **initialize unexposed variables after binding** (OCRG p.80-81).
- [from source] Reviewer criterion: map **all places where user input directly references objects** (database row, file, page) and understand whether changing that input retrieves unauthorized objects; require **server-side authorization checks and validation** (OCRG p.81). **.NET MVC over-posting / mass assignment** (Sample 10.2 hidden `isAdmin` in the view): use a model without values the user must not edit, `Bind` with an allow list of attributes, or `UpdateModel` excluding attributes (OCRG p.81-82).
- ASVS: V4.2.1 (IDOR), V4.1.2, V5.1.2 (mass assignment) (ASVS p.36, 38). The linter flags `UpdateModel` (`BIND-UPDATEMODEL`; OCRG p.82).

## A7 — Missing function-level access control (OCRG p.135-139)
- [from source] Applications often check rights before **showing** the function in the UI, but must repeat the check **on the server** on every access; without it, forged requests reach the function (OCRG p.135). Authorization is as important as authentication: access to functions and to **all data** must be authorized (does the data belong to the authenticated user?) (OCRG p.135).
- [from source] **Classic MVC mistake**: putting the check in the **view**; the action (add user, change password) is executed before the view is denied (Figure 11; same flaw in ASP.NET with POSTBACKs without a check) (OCRG p.135-136). Test actions forgotten in the configuration (`TestAction`, Sample 13.1) enlarge the surface (OCRG p.136-137). Data binding with `price` (OCRG p.137).
- [from source] **What to review** (OCRG p.137-139): put all validations before any logic; global filters in MVC 3+ (`RegisterGlobalFilters` with `AuthorizeAttribute`) to **deny by default** and `[AllowAnonymous]` only on public pages (Samples 13.2-13.3); **every input and every function authorized**; **efficient and centralized** checks; authorization failure → HTTP **403**; with RBAC, a users x roles report for **periodic audit** (e.g. an admin who changed department) and easy role removal, with audit logs; high-risk roles with multiple levels (**maker/checker**); keep **few roles** (many increase permission conflicts); no authorization on the client (thick client or JavaScript); never base authorization on untrusted data (client header or hidden field); **complete mediation** (check at every step — e.g. four purchase pages); default deny; decide where to store authorization data (DB or session); remove test/redundant configurations; binding objects only with input-dependent variables (OCRG p.138-139).
- [from source] Two authorization designs: **RBAC** (users→roles→permissions; reduces human error and allows rechecking) and **ACLs** (OCRG p.135).
- ASVS: V4.1.1, V1.4.1, V1.4.4, V1.4.5, V4.1.3, V4.1.5, V13.1.4 (ASVS p.18, 36, 58) `[inference]`.

## A8 — CSRF (OCRG p.141-146)
- [from source] CSRF makes a logged-in victim's browser send a forged request with the session cookie; it holds even with HTTPS; it is different from XSS; it only works if the victim is logged in and the action can be executed by a well-formed request (OCRG p.141-142). Targets: high-value accounts, community sites, "ease of use" such as one-click purchase (OCRG p.141). Samy worm (MySpace, 2005) (OCRG p.141, 146).
- [from source] **What to review**: check whether there is a **unique identifier per request** (token) tied to the user; the **session ID is not enough** because it is sent automatically (OCRG p.142). **Measures that do NOT work** (Table 21 and text): secret cookie, accepting **POST only** (a hidden form on the attacker's site makes a POST), **multi-step transactions** (predictable) and **URL rewriting** (exposes the credential in the URL) (OCRG p.142-143). For actions such as password/transfer/purchase, the application must **require a password or an OOB factor** (OCRG p.143).
- [from source] **Prevention**: unique ID per link/form generated with secure randomness (e.g. `SecureRandom`), validated on the server; if absent, terminate the session and show an error (OCRG p.143). **Synchronizer Token Pattern**: a per-session "challenge" token inserted into forms/links of sensitive operations (hidden `CSRFToken` field, Sample 14.2); token per session or **per request** (increases security but hurts the Back button); failure → abort, reset the token and **log as a possible attack** (OCRG p.143-144). Avoid the token in the GET URL (leaks in history, logs, network equipment and Referer); ideally the token only in POST and state-changing actions only respond to POST (OCRG p.144-145).
- [from source] Other defenses: **ViewState** with `ViewStateUserKey = Session.SessionID` (limitation: only on postbacks; Sample 14.3) (OCRG p.145); **Double Submit Cookies** (random value in cookie and parameter; the server need not store it) (OCRG p.145); **checking Referer** (weakest defense: HTTPS→HTTP omits it; `site.com.attacker.com`; XSS bypasses it; absence must be treated as an attack on state change) and **checking Origin** (present on HTTPS; check consistency) (OCRG p.146); **challenge-response** (CAPTCHA, reauthentication, one-time token) for high risk (OCRG p.146).
- [from source] **Any XSS defeats** token, double-submit, referer and origin (the script reads the page and gets the token); XSS does **not** defeat challenge-response — ensure there is no XSS (OCRG p.146).
- ASVS: V4.2.2 and V13.2.3 (ASVS p.36, 59); `SameSite` (V3.4.3, ASVS p.33) does **not** appear in the OCRG.

## A10 — Unvalidated redirects and forwards (OCRG p.151-154)
- [from source] Redirect: the browser is sent to another URL; a redirect URL parameter on the site's own page can lead to a phishing site (OCRG p.151). **Forward**: the server fetches the page (Struts `forward`, .NET `Server.Transfer`); it is limited to the site itself, but **bypasses access control** if authorization is only on the forwarding page (e.g. `FWD=purchase` → `admin.do`) (OCRG p.151-152).
- [from source] **What to review**: if any part of the redirect/forward URL comes from user input, use a **whitelist** or **relative** paths; vulnerable examples in Java (`sendRedirect(request.getParameter("url"))`, Sample 16.1), PHP (`header("Location: ".$_GET[...])`, Sample 16.2) and C# (`Response.Redirect(url)`, Sample 16.3); the diversion can occur without an explicit redirect function (Table 22: `302 Location`, `<meta refresh>`, `window.location`, `Refresh` header) (OCRG p.152-153).
- [from source] Countermeasures: check Referer (does not apply to a URL on the site itself), whitelist of URLs/options, deny the user setting the scheme/host, encode/encrypt the value; forwards: whitelist and **authentication on the destination page too** (OCRG p.153). **J2EE** note: `sendRedirect()` and `forward()` **do not stop** servlet/JSP execution (exception: `<jsp:forward>`): use `return` right after (OCRG p.153). ASVS: V5.1.5 (ASVS p.38). The linter: `REDIRECT-*`.
