## Code Review Do's and Don'ts (OCRG p.193)
- [from source] Besides the technical side, consider the **human side**: if the review becomes a source of conflict, effectiveness at finding bugs drops and developers work around the process; being a good reviewer takes social skill and practice (OCRG p.193).
- [from source] Discussion points: it is **not necessary to find a defect** in every review (otherwise your comments lose credibility); **do not rush**, but with appropriate urgency; know what is being reviewed (security, functionality, maintainability, style) and whether there are style guides/tools; have a defined way to **resolve conflicts** between dev and reviewer; have defined artifacts as the result of the review; know the process when the code changes during the review; and the reviewer should have **domain knowledge** (compliance, business rules, risks), since there is evidence this makes the review more effective (OCRG p.193).

## Agile, CI and TDD (OCRG p.194-196)
- [from source] Integrating security into the agile SDLC is hard: it requires constant involvement of the security team or **well-trained coders in each team** (OCRG p.195). **CI** (check-in several times a day + automatic build/verification): advantage = detecting build problems early; disadvantage for the reviewer = the code compiles but may have vulnerabilities; the review may be only a "minimum standard", not a secure review with risk assessment; and **design** flaws can be deployed quickly (OCRG p.196). **TDD**: write the test, then the minimum to pass, then refactor (OCRG p.196).
- [from source] **Red flags** for the reviewer in agile: no user story addresses vulnerabilities by risk; user stories do not describe sources and sinks; no risk analysis of the application was done (OCRG p.196). The SAST flow with rules tuned by AppSec and sign-off (figure) is on OCRG p.195.
- Mapping `[inference]`: ASVS V1.1.3 (user stories with security constraints), V1.1.2 (threat modeling every sprint), V1.1.7 (checklist available) (ASVS p.17-18).

## Appendix A — Code Review Checklist (OCRG p.197-200)
- [from source] CATEGORY / DESCRIPTION / PASS / FAIL table with **78 rows** (24 + 21 + 23 + 10 per PDF page), extracted by PDF geometry (`scripts/ocrg_checklist.json`) and visually checked against the images of pages 197-199. Categories: General, Authorization, Cryptography, Business Logic and Design, Session Management, Input Validation, Logging and Auditing, User Management and Authentication, Data Management and Web Services.
- **Fidelity**: the book's checklist **repeats** rows (e.g. binding variables "with default value" and "initialized before binding" appear twice; "Classes that contain secrets only accessible through protected APIs" twice; the row about containers twice) and has wording errors ("Does are there any special kind of request skipped from validation?", category "Imput Validation"). The package preserves the rows as they are and flags the repetition.
- Rows that ASVS 4.0.3 **contradicts** (`[DATED]`): "Is Password Complexity Check enforced on the password?" (A.22; OCRG p.197) and "Does application support password expiration?" (A.44; OCRG p.198) — see ASVS V2.1.9 and V2.1.10 (ASVS p.24). Also "Authentication cookies are encrypted"/"Session cookies are encrypted" (A.57, A.65; OCRG p.199) is imprecise wording: the modern requirement is `Secure`/`HttpOnly`/`SameSite` flags, not "encrypted cookie" (ASVS V3.4.1-V3.4.3, ASVS p.33) `[inference]`.
- Use: `python -I scripts/asvs_checklist.py ocrg [--category Session] [--format md|json|csv]`.
- Examples of useful rows (paraphrase): is there background/unexposed business logic? are the authentication/authorization checks in the right place and **before** processing input? is execution stopped after an invalid request? does the configuration apply to all files/users? does the design use the **framework's native controls** (e.g. `<%: %>`)? **reduced privileges whenever possible**? does the program **fail gracefully**? do logs record personal data/passwords? is there a process to **read the audit logs**? keys not in the code? arrays have bounds checked? is all input validated on the server and all output correctly encoded? are entry points and trust boundaries in the risk analysis report? web services: unnecessary protocols (GET/POST), dynamic WSDL generation disabled? (OCRG p.197-200).
