# OCRG — race conditions and buffer overruns (OCRG p.182-188)

Source: OCRG v2.0, chs. 23 and 24. Pages = PDF (printed = N − 1). Related in the ASVS (`[inference]` mapping): V1.11.2, V1.11.3, V11.1.6 (race/TOCTOU; ASVS p.20, 54) and V5.4.1-V5.4.3, V14.1.2 (memory; ASVS p.40, 61).

## Race conditions (ch. 23) (OCRG p.182-183)
- [from source] Race conditions result from **unexpected ordering of events**, taking the state machine to an undefined state and to **contention** of several threads over the same resource, causing integrity problems; without synchronization the code is in an uncertain state and security cannot be guaranteed (OCRG p.182). Book example: two threads do `X = X + 10` with X = 5; the expected result is 25, but the result is 15 because both read the old value (OCRG p.182).
- [from source] **What to look for**: C# — `Thread`, `System.Threading`, `ThreadPool`, `System.Threading.Interlocked`; Java — `java.lang.Thread`, `start()`, `stop()`, `destroy()`, `init()`, `synchronized`, `wait()`, `notify()`, `notifyAll()`; classic ASP only with COM (OCRG p.182-183).
- [from source] **Statics**: static methods and variables (one per class) are a problem when there is state shared between threads; in Struts/Apache, **do not store information from a request in static members**; per-request instances need not be thread-safe, **static state must be**: references to static variables must be under lock; releasing the lock outside `finally` causes problems; static methods that change static state (OCRG p.183).
- Crawling: `Thread`, `Dispose` (without synchronization, several threads calling `Dispose` cause release problems), global static variables with security data (OCRG p.209). The linter has `THREAD-STATIC-STATE` (`[inference]`) and `THREADING-CRAWL` (info).
- `[inference]` For high-value flows (authentication, session, access control), ASVS V1.11.2 asks that they **not share unsynchronized state** and V1.11.3 (L3) that they be thread-safe and resistant to TOCTOU (ASVS p.20); V11.1.6 asks for no TOCTOU in sensitive operations (ASVS p.54). The OCRG does not use the term TOCTOU.

## Buffer overruns (ch. 24) (OCRG p.184-188)
- [from source] Applies to C, C++ and Objective-C (direct memory access through pointers; data and control mixed on the stack). **Java, C#, Python and Ruby are not vulnerable** to buffer overflow because they check bounds and give no direct memory access, **except** in native code called by them (JNI, C# `unsafe`) (OCRG p.184). Arrays start at 0: the last element of 100 is index 99; "off by one" errors are common (OCRG p.184).
- [from source] **C functions**: `strcpy`, `strcat`, `sprintf`, `vsprintf` and `gets` do not check bounds; the `scanf` family can also overflow; use `strncpy`/`strncat`/`snprintf` with the buffer size, `fgets` instead of `gets`, and Microsoft's `_s` versions; always check bounds before writing (OCRG p.185). Sample 24.1 (vulnerable: `strcpy` of 12 bytes into a 10-byte buffer) and Sample 24.2 (uses `strncpy`).
  - **Fidelity caveat** `[inference from the book's own text, OCRG p.184-185]`: Sample 24.2 assigns `smallBuffer[10] = 0` to an array of size 10; as the book itself explains, the last valid index is size − 1, so that line writes **one byte outside the array**. Do not use the example as a model.
- [from source] **C++11**: `std::string`, smart pointers and dynamic STL containers reduce the chance of overflow (still possible via raw pointers or `reinterpret_cast`); **stack canaries** in modern compilers (including iOS); manual review must be complemented by **memory verification tools** (OCRG p.186).
- [from source] **Format function overruns** (Table 23: `%x`, `%d`, `%u`, `%n`, `%s`): input data used as the **format string** makes `printf` walk the stack; `%n` **writes** the number of bytes so far; look for `printf`, `fprintf`, `sprintf`, `snprintf`, `syslog`, `setproctitle` (OCRG p.186-187). Always use a constant format. The linter: `C-FORMAT-STRING` (heuristic: first argument is a variable).
- [from source] **Integer overflows**: a 16-bit `short` ranges from −32,768 to 32,767 (Table 24); adding 1 to 32,767 becomes −32,768; subtracting below the minimum gives underflow; the same with `0x7fffffff + 1`; compilers do not detect it; occurs in comparisons/arithmetic with signed and unsigned integers; Sample 24.3. **Sample 24.4**: the upper-bound check does not catch a very negative `v2` if only the maximum is checked (OCRG p.187-188).
- ASVS: V5.4.1-V5.4.3 and V14.1.2 (compilation flags that enable protections and break the build on insecure operations; ASVS p.40, 61). The OCRG says to look for the functions by crawling (OCRG p.217) and the linter has `C-UNSAFE-STR`, `C-SCANF`.
- Boundary: **memory exploitation** and pentest/WSTG techniques are not covered here; this agent reviews code and requirements.
