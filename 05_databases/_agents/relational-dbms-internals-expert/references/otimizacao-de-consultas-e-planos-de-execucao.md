# Query optimization and execution plans

> Pages = PDF. ARCH: printed = N + 140. PG16: printed = N − 38. REDBK = only the chapter introductions (see `INDEX.md`).

## 1. Query pipeline [from source]
A relational query processor takes a declarative SQL statement, validates it, optimizes it into a procedural dataflow plan and (subject to admission control) executes it; the client "pulls" the tuples (ARCH p.36). The parser checks the syntax, resolves names (four-part names `server.database.schema.table`), converts to the internal format and checks authorization, part of which may be deferred to execution (ARCH p.37-38). The **rewriter** simplifies and normalizes without accessing data: view expansion, constant arithmetic, logical predicate rewriting (including transitivity and satisfiability), semantic optimization (elimination of a redundant join with a foreign key) and *flattening* of subqueries (ARCH p.39-42).

## 2. The cost-based optimizer (Selinger's System R optimizer) [from source]
- **Selinger / System R**: the Red Book summarizes the work as decomposition into three subproblems: **cost estimation**, **relational equivalences that define a search space** and **cost-based search**; cost is measured in I/O and CPU, using precomputed catalog statistics and cardinality heuristics (predicate selectivity); the search is by **dynamic programming**, building "left-deep" trees and taking "interesting orders" into account; even so it is exponential and **does not guarantee the optimal plan** (REDBK p.16). Stonebraker calls the cost-based dynamic programming approach the "gold standard" (REDBK p.14).
- In ARCH, each SELECT-FROM-WHERE block is optimized as in Selinger's paper and then the blocks are stitched together; GROUP BY, ORDER BY, HAVING and DISTINCT operators are added on top (ARCH p.42). Every large DBMS compiles the query into an interpretable structure (ARCH p.42-43).
- Extensions that real systems make to Selinger's model (ARCH p.44-46):
  - **Plan space**: System R only considered "left-deep" plans and postponed Cartesian products; current systems also consider "bushy" trees and early Cartesian products (p.44).
  - **Selectivity**: Selinger used simple table and index cardinalities; today distributions are summarized with **histograms** and other statistics, sometimes by sampling; the paper notes that selectivity errors early on propagate **multiplicatively** up the plan tree (p.44-45).
  - **Search**: Microsoft and Tandem use Cascades-style *top-down* search; both approaches have time and memory exponential in the number of tables (p.45). For queries with too many tables, heuristics are used; the paper describes the MySQL optimizer (at the time) as entirely heuristic (p.45).
  - **Parallelism**: two phases (single-node plan, then scheduling) is what many do (p.45-46).
  - **Auto-tuning** with "what-if" analyses (p.46).
- The Red Book adds that cost estimates can be very wrong, the search uses heuristics because the problem is NP-hard, and discusses top-down (Volcano/Cascades), adaptive (eddies) and progressive optimizers (REDBK p.33-35).
- **Why no optimizer produces an "optimal" plan (Red Book ch. 7, Hellerstein's introduction)**: the chapter gives **two reasons**: (1) all optimizers use **estimation** techniques to guess the real cost of plans, and the errors in those estimates can "blow up" to the point that, in some circumstances, they are as bad as random guesses; (2) they use **heuristics** to limit the explored plan space, because the problem is **NP-hard** (REDBK p.33). Even so, relational optimization has "proven successful" for the common cases, vendors invested years to make optimizers reliable, users learned to live with limits on the number of joins, and declarative SQL remains a much better choice than imperative code in most uses; the best open-source optimizers are limited compared with those of mature commercial DBMSs, and some only work for simple queries (REDBK p.33).
- **Two-table joins vs. multiway algorithms (Red Book ch. 7)**: the text highlights that the traditional use of **2-table** join operators (one pair at a time) has been shown **theoretically inferior** to new multiway join algorithms in certain cases (REDBK p.33). This is only an observation from the introduction; the chapter does not present the algorithm (the package does not summarize it).
- **Volcano/Cascades (the two reference optimizer architectures, Red Book ch. 7)**: the chapter presents **two reference architectures**: (a) Selinger's **System R** optimizer (chapter 3 of the book; "textbook material", implemented in many commercial systems) and (b) the architecture that Goetz Graefe and collaborators refined over a series of projects: **Exodus, Volcano and Cascades**, less covered in textbooks than System R, but widely used, **notably in Microsoft SQL Server** (and, according to the text, supposedly in other commercial systems) (REDBK p.33). The authors chose the **Volcano** paper (Graefe and McKenna, ICDE 1993) as the most accessible representative, and recommend the **Cascades** paper as the most recent and "standard" reference of the approach, which addresses detail deficiencies of Volcano (REDBK p.33). Graefe's architecture is notable, first, for having been **designed to be extensible**: Graefe's optimizers serve to compile SQL into a plan of dataflow iterators, but "can be parameterized for other..." (the sentence continues on p.34, outside this summary) (REDBK p.33). `[inference]` This is optimizer architecture (plan generation), **not** the PostgreSQL execution model: PG16 (p.2293-2294) describes the planner without citing Volcano/Cascades.
- **Orca (Greenplum) and Apache Calcite: Cascades-style open-source optimizers**: the Red Book states that two Cascades-style open-source optimizers have recently emerged: Greenplum's **Orca**, which became part of open-source Greenplum, and **Apache Calcite**, an optimizer that can be used with **several query executors and languages**, including LINQ (REDBK p.33). `[DATED]` (2015): the text predates later evolutions of these projects; the package carries nothing more about them.

## 3. Prepared statements and plan cache [from source]
SQL allows "preparing" a query: passing it through the parser, rewriter and optimizer, storing the plan and reusing it. For queries with program variables, the optimizer assumes "typical" values in the selectivity estimate; if those values are not representative, terrible plans can result (ARCH p.47). Since many programs build SQL dynamically, DBMSs store plans in a **plan cache** (ARCH p.47). A dropped index invalidates plans that used it; vendors differ on when to reoptimize (IBM prioritizes predictability; Microsoft recompiles more aggressively, for example when a table's cardinality changes a lot) (ARCH p.47-48).

## 4. Executor and iterators [from source]
Modern executors use the **iterator model**: each operator is a subclass of an iterator with `init()`, `get_next()` and `close()`; any iterator can be the input of any other; data and control flow together (a tuple returns to the parent when control returns), so a single thread executes the whole graph (ARCH p.48-49). The paper cites Graefe for details and for the *exchange iterators* of parallelism (ARCH p.49-50). Typical operators: filescan, indexscan, sort, nested-loops join, merge-join, hash-join, duplicate-elimination, grouped-aggregation (ARCH p.49). Updates require care with the "Halloween problem" (section 4.1 below).
- **Volcano in ARCH (where it appears)**: ARCH does **not** call the iterator model "Volcano": the term only occurs in the **reference list**, in the title of Graefe's paper "Encapsulation of parallelism in the Volcano query processing system" (SIGMOD 1990), which the text on p.49-50 cites as [23] for the *exchange iterators* (ARCH p.114; ARCH p.49-50). Whoever wants Volcano as an optimizer generator should go to the Red Book (REDBK p.33).

- **No queues or rate matching between iterators (ARCH p.49, section 4.4.1)**: Because of the coupling of dataflow and control flow, **queues and rate matching between iterators are not needed** (ARCH p.49): `get_next()` is an ordinary procedure call and the tuple returns to the caller through the call stack (coupling of dataflow and control flow, ARCH p.49, section 4.4.1). The text contrasts this with dataflow architectures in other environments: networks, for example, depend on queueing and feedback protocols between concurrent producers and consumers (ARCH p.49). Since the single-thread architecture is also efficient in single-system execution (not a cluster), and there is always one active iterator, resource utilization is maximized (ARCH p.49-50). The paper recommends the PostgreSQL open source as an example of a "moderately sophisticated" implementation of the iterators of the standard algorithms (ARCH p.49); it **does not say** that PostgreSQL uses one thread per operator, queues or rate matching.

### 4.1 Updates (INSERT/UPDATE/DELETE) and the Halloween problem [from source]
- INSERT, DELETE and UPDATE plans are usually simple straight lines: an access method as the source and a modification operator at the end of the pipeline (ARCH p.51). The care appears when the plan **reads and writes the same table** (ARCH p.52).
- The "Halloween problem" got that name because the System R group discovered it on October 31 (ARCH p.52). Paper example: give a 10% raise to those earning less than 20 thousand. The naive plan connects an `IndexScan` on `Emp.salary` directly to an `Update`; the pipeline has good I/O locality because it changes the tuple right after fetching it from the B+-tree (ARCH p.52-53).
- The defect: after being updated, the tuple may "move to the right" in the tree, and the index scan **rediscovers** it, applying the raise several times until the salary exceeds 20 thousand. This violates SQL semantics: **a command cannot "see" its own updates** (ARCH p.53).
- Solutions described (ARCH p.53): (1) the optimizer chooses plans that **avoid indexes on the updated column**, which may be inefficient; (2) a batch "read then write" scheme: materialization operators and Record-ID (RID) lookup between the index scan and the `Update` (`Materialize` and `Fetch-by-RID` in Figure 4.3, ARCH p.52). The materialization operator writes the RIDs to be modified into a **temporary file**, then scans it and fetches each tuple by RID to feed the modification operator. If the optimizer chose an index, usually few tuples change, so the temporary tends to fit in the buffer pool and the apparent inefficiency is acceptable. Pipelined update schemes also exist, but require "somewhat exotic" multiversion support in the storage engine (ARCH p.53).
- **Do not confuse it with the phantom**: a footnote in the paper says that, despite the similar names, Halloween has **nothing to do** with the phantom problem (ARCH p.52). `[inference]` Halloween is a plan defect of **one** transaction reading its own writes; the phantom (ARCH p.85-86, p.94-95) involves inserts by **another** transaction within a predicate already read. Both involve "new rows appearing", but through different mechanisms.
- PostgreSQL: the manual consulted does not describe a specific technique against Halloween; there is only the tuple header with the `t_cid` field, which identifies the command within the transaction (PG16 p.2575). `[inference]` this field is compatible with the idea of a command not seeing its own changes, but the link is not stated by the manual on that page; treat it as a clue, not as an official explanation.

### 4.2 Rewriter and data access details [from source]
- **Partition elimination by unsatisfiable predicate**: logical rewrites can short-circuit execution (an impossible predicate becomes FALSE and the query returns empty without touching the database); this same mechanism is the basis of parallel SQL Server's "partition elimination": if the partition's range predicate is unsatisfiable together with the query predicate, the query does not need to run on that volume (ARCH p.40). See the PG16 analogue in `postgresql-16-particionamento.md`.
- **Transitive predicates**: from `R.x < 10 AND R.x = S.y` one can induce `S.y < 10`, which helps the optimizer filter early and use indexes (ARCH p.40).
- **Redundant join elimination**: with a non-null foreign key between `Emp.deptno` and `Dept`, a query that joins the two but only uses columns of `Emp` can lose the join; this appears naturally through views (ARCH p.40-41).
- **Subquery flattening**: most optimizers work on isolated SELECT-FROM-WHERE blocks; flattening subqueries exposes more opportunities to the optimizer, but is delicate in SQL because of duplicates, NULLs and correlation (ARCH p.41-42). Correlated subqueries become nested-loop-style comparisons between blocks, which serializes execution; flattening them is especially important in parallel architectures (ARCH p.42).
- **Access method and SARG**: the contract of an access method is that of an iterator; `init()` receives a search argument (SARG, "column operator constant"), and passing the SARG into the access method avoids, per rejected tuple, function calls and pin/unpin or copy/delete pairs (ARCH p.54). Details in `data-warehouse-colunar-bitmap-e-extensibilidade.md`.

## 5. Join algorithms in PostgreSQL [from source]
PG16 defines three strategies (PG16 p.2294):
- **Nested loop**: the right relation is scanned once for each row of the left; easy to implement, can be slow, and is a good strategy if the right can use an index scan with values from the current row.
- **Merge join**: each relation is sorted by the join attributes and the two are scanned in parallel; the sorting can come from a sort step or from an index on the key.
- **Hash join**: the right relation is read and loaded into a hash table by the join attributes; then the left is scanned and each value is used to locate matches.
EXPLAIN examples from the manual: nested loop with a `Materialize` node over the inner relation (PG16 p.546), hash join with a `Hash` node that builds the table and another node that probes (PG16 p.546-547), merge join with `Sort` for the input that is not ordered (PG16 p.547). If the query uses fewer than `geqo_threshold` relations, the join order search is nearly exhaustive; above that GEQO, the genetic optimizer, comes in (PG16 p.2293-2294, p.2483-2486).

## 6. Cost and statistics in PostgreSQL [from source]
- A node's total cost is the per-row cost of each node multiplied by the selectivity estimate; costs can be adjusted by runtime parameters (PG16 p.482). Defaults: `seq_page_cost` 1.0; `random_page_cost` 4.0 (PG16 p.682); `cpu_tuple_cost` 0.01; `cpu_index_tuple_cost` 0.005; `cpu_operator_cost` 0.0025 (PG16 p.683).
- Selectivity estimates come from `pg_statistic` (seen through `pg_stats`), updated by ANALYZE and always approximate; it stores `most_common_vals` and `histogram_bounds` lists; the default limit is 100 entries (`default_statistics_target`) (PG16 p.554, p.685). ANALYZE uses random row sampling (PG16 p.790).
- Sort operations (ORDER BY, DISTINCT, merge join) and hash operations (hash join, hash aggregation) use `work_mem` (default 4 MB); the hash memory limit is `work_mem` × `hash_mem_multiplier` (default 2.0) (PG16 p.654-655).
- The `enable_*` flags serve to investigate plans (PG16 p.482, p.547); `EXPLAIN ANALYZE` runs the query and compares estimated and actual rows (PG16 p.547).
- **How to read the `EXPLAIN ANALYZE` output** (PG16 p.548-551):
  - The `actual time` values are in real milliseconds; estimated costs are in **arbitrary units**, so they are not expected to coincide. What usually matters more is whether the row estimate is reasonably close to reality (PG16 p.548).
  - In nodes executed more than once, `loops` is the total number of executions and `actual time` and `rows` are **per-execution averages**; for the total time spent in the node, **multiply by the value of `loops`** (in the manual's example, the inner index scan adds up to 0.220 ms) (PG16 p.548).
  - `Sort` nodes show the method and the memory or disk used; `Hash` shows buckets, batches and peak memory (PG16 p.548-549).
  - `Rows Removed by Filter` shows rows rejected by the filter (useful especially in join nodes); it only appears if at least one row, or candidate join pair, was rejected (PG16 p.549). `Rows Removed by Index Recheck` appears in "lossy" indexes (PG16 p.550).
  - `EXPLAIN (ANALYZE, BUFFERS)` adds buffer statistics to locate the most I/O-intensive parts (PG16 p.550; **the BUFFERS option is described on p.550, not on p.548**, which covers `loops`, `actual time` and costs in arbitrary units).
- **`EXPLAIN ANALYZE` really executes the query**: side effects occur normally, and only the result is discarded. To analyze `INSERT`/`UPDATE`/`DELETE`/`MERGE` without altering the tables, the manual says to undo afterwards, with `BEGIN; EXPLAIN ANALYZE ...; ROLLBACK;` (PG16 p.550-551). The top node (Update, Delete etc.) does the writing work; the planner does not add the cost of that work to the estimates (PG16 p.551). `[inference]` besides the rows, the real execution also generates WAL and acquires row/table locks while the transaction is open; the manual does not detail this on those pages.
- **Extended statistics** (*extended statistics*; PG16 p.555-557; `CREATE STATISTICS` is not used in join estimates between tables, PG16 p.1808; see `postgresql-16-estatisticas-planner-paralelismo-e-snapshots-antigos.md`): it is common to see bad plans because columns used together are **correlated**; the planner normally assumes the conditions are **independent**, and per-column statistics do not capture correlation between columns (PG16 p.555). `CREATE STATISTICS` creates a statistics object (just a catalog entry); whoever collects the data is `ANALYZE` (manual or autoanalyze), and the result sits in `pg_statistic_ext_data`; a larger statistics target increases the sample and tends to give more accurate extended statistics (PG16 p.555). Types: `dependencies` (functional dependencies; without them the planner underestimates the result when there are conditions on the dependent and independent columns; they only apply to equality with a constant and `IN` with constants, PG16 p.555-556), `ndistinct` (multicolumn distinct counts, for `GROUP BY a, b`, PG16 p.556-557) and `mcv` (multicolumn most-common-value lists, PG16 p.557). The manual advises creating them only for groups of columns that are really correlated or used, to avoid wasting `ANALYZE` (PG16 p.555-557). Manual example: `CREATE STATISTICS stts (dependencies) ON city, zip FROM zipcodes; ANALYZE zipcodes;` (PG16 p.555).
- Under Serializable, a sequential scan requires a predicate lock at relation level (PG16 p.531).
- A partial index is only used if the optimizer can prove that the query's WHERE implies the index predicate, and this happens at planning time, so **parameterized clauses do not work with a partial index** (PG16 p.475-476).

## 7. [inference]
- The estimation error that propagates multiplicatively (ARCH p.45) is the technical reason behind PG16's recommendation to run ANALYZE before evaluating indexes (PG16 p.482).
- Prepared statements cause the plan to be chosen before knowing the real value (ARCH p.47); combined with the partial index rule (PG16 p.476), this explains why plan choice can change between literal and parameterized SQL.

- An estimate far below the actual (e.g. `rows=5` estimated against tens of thousands actual) with filters on several columns is, according to the manual, a typical symptom of correlated columns treated as independent (PG16 p.555); the diagnosis for the concrete case, however, remains `[inference]` until checking `pg_stats`, `ANALYZE` and real data.

## 8. [extrapolation] and what the sources do NOT say
- The formula "Cost = pages × I/O cost + tuples × CPU cost + operator cost" and the complexities $O(|R|\log|S|)$ etc. were presented in v1 as `[from source]`; they are **not** in the sources. What PG16 gives is the list of parameters and the qualitative description of the three joins.
- "Grace Hash Join", "selectivity errors are the number one cause of disastrous plans" and the description of the model as "Volcano" in ARCH do not appear in the sources: ARCH uses "iterator" (ARCH p.49-50) and **only cites Graefe** for the iterator details and for the *exchange iterators* (ARCH p.49-50); the word "Volcano" appears in ARCH **only in the reference list**, in the title of Graefe's paper on encapsulation of parallelism (ARCH p.114, ref. [23]), never as the name of the execution model; "Volcano" in the Red Book refers to an **optimizer generator** (REDBK p.33).
- The ARCH paper does not describe hash join and merge join algorithms in detail; use PG16 (p.2294, p.546-547) for the mechanics.
