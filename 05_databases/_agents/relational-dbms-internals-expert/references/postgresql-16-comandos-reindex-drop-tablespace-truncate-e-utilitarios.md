## 1. `REINDEX` [from source] (PG16 p.1995-1998)
- **Targets** (PG16 p.1995): `DATABASE` recreates all indexes of the current database **except those on system catalogs**, and `SYSTEM` recreates only the indexes on system catalogs (including those on shared catalogs), without touching indexes of user tables; **neither can run inside a transaction block**. For `DATABASE` and `SYSTEM` the optional name must be that of the current database: only the current database can be reindexed.
- **Options** (PG16 p.1995): `CONCURRENTLY` rebuilds without the locks that prevent concurrent inserts, updates and deletes (the default rebuild **blocks writes, but not reads** of the table); on temporary tables `REINDEX` is always non-concurrent. `TABLESPACE` rebuilds the indexes in a new tablespace; `VERBOSE` prints progress per index.
- **Corruption** (PG16 p.1995-1996): for a corrupted index on a user table, `REINDEX INDEX` or `REINDEX TABLE` is enough. For an index on a system table the server must not use the suspect indexes: start the server (single-user or normal) with the `-P` option, which prevents the use of indexes in catalog queries; when in doubt, use `REINDEX SYSTEM`. In a normal session `-P` can be put in `PGOPTIONS`, but other users should be prevented from connecting until the repair is done.
- **Locks, compared with DROP and CREATE** (PG16 p.1996): `REINDEX` blocks writes, but not reads of the parent table, and takes an `ACCESS EXCLUSIVE` lock on the index being processed, which blocks reads that try to use that index; since the planner tries an `ACCESS SHARE` lock on all indexes of the table, in practice almost all queries are blocked (except some prepared ones with a cached plan that do not use the index). `DROP INDEX` takes `ACCESS EXCLUSIVE` on the table for an instant; the following `CREATE INDEX` blocks writes, but reads do not block (they may fall back to expensive sequential scans).
- **Permissions** (PG16 p.1996): reindexing an index or table requires owning it; a schema or database, owning the schema or database. When `REINDEX DATABASE`, `SCHEMA` or `SYSTEM` is issued by a non-superuser, indexes on shared catalogs are **skipped**, unless the user owns the catalog; a superuser reindexes everything.
- **Partitioned** (PG16 p.1996): `REINDEX INDEX` and `REINDEX TABLE` accept partitioned indexes and tables; **each partition is reindexed in a separate transaction**, and these commands cannot run in a transaction block when handling a partitioned table or index. With `TABLESPACE` on a partitioned one, only the references of the leaf partitions are updated; the partitioned indexes are not, and the manual recommends `ALTER TABLE ONLY` so that new partitions inherit the tablespace; if it fails midway, running again rebuilds the leaves and moves the indexes not yet processed.
- **`TABLESPACE` with `SCHEMA`, `DATABASE` or `SYSTEM`** (PG16 p.1996): system relations are skipped and a single `WARNING` is issued. **Indexes of TOAST tables are rebuilt, but not moved** to the new tablespace.
- **`CONCURRENTLY`: how it works** (PG16 p.1996-1997): the ordinary rebuild uses **one scan** of the table; the concurrent one does **two scans per index** and waits for the end of all transactions that could use the index, so it does more total work and takes much longer, but allows normal operation. Six steps, each in a separate transaction: (1) adds a transient definition in `pg_index` and takes a session-level `SHARE UPDATE EXCLUSIVE` lock on the indexes and tables; (2) first pass, then `indisready` becomes true; (3) second pass for the tuples added during the first; (4) the constraints start pointing to the new index, the names are swapped and `indisvalid` becomes true on the new one and false on the old; (5) the old one gets `indisready` false, after waiting for queries that reference it; (6) the old ones are removed and the session locks released.
- **Failure in `CONCURRENTLY`** (PG16 p.1997): if there is a problem (for example, a uniqueness violation), the command fails and leaves a new **invalid** index in addition to the existing one; it is ignored in queries (it may be incomplete), but still costs updates, and `psql \d` marks it `INVALID`. Suffix `_ccnew`: transient index created by the operation; recover with `DROP INDEX` and try again. Suffix `_ccold`: the original that could not be removed; just remove it. A number may be appended to the suffix to keep names unique.
- **Transaction and concurrency of builds** (PG16 p.1997): ordinary builds allow other ordinary builds at the same time on the same table, but **only one concurrent build per table** at a time; no other kind of schema change on the table is allowed during the process. Ordinary `REINDEX TABLE` and `REINDEX INDEX` can run in a transaction block; **`REINDEX CONCURRENTLY` cannot**.
- **`REINDEX CONCURRENTLY` and exclusion constraints; `REINDEX SYSTEM`** (PG16 p.1998): like any long transaction, `REINDEX` on one table can affect which tuples a concurrent `VACUUM` can remove in **any other table**. `REINDEX SYSTEM` **does not support `CONCURRENTLY`**, because system catalogs cannot be reindexed concurrently. Also, **exclusion constraint indexes cannot be reindexed concurrently**: if one is named directly in the command, **an error occurs**; if a **table or database** with exclusion constraint indexes is reindexed concurrently, those indexes are **skipped**. They can be reindexed **without** `CONCURRENTLY`.
- **`pg_stat_progress_create_index`: `REINDEX` progress, examples and standard compatibility** (PG16 p.1998): each backend running `REINDEX` reports progress in the `pg_stat_progress_create_index` view (Section 28.4.4). Manual examples: `REINDEX INDEX my_index`, `REINDEX TABLE my_table`, `REINDEX DATABASE` with `PGOPTIONS="-P"` on a database with suspect system indexes, and `REINDEX TABLE CONCURRENTLY my_broken_table` to rebuild without blocking reads and writes. **There is no `REINDEX` command in the SQL standard.**
- `[derived]` the recovery behavior is the same as `CREATE INDEX CONCURRENTLY` (see `postgresql-16-tipos-de-indices-e-estrategias.md`, section 7b, PG16 p.1758-1760).

## 2. `reindexdb` (command-line utility) [from source] (PG16 p.2226-2227)
- **What it is** (PG16 p.2226): `reindexdb` rebuilds indexes and is **just a wrapper around the SQL `REINDEX` command**: there is no effective difference between reindexing through it or through any other access to the server. Forms: by schema (`-S`), table (`-t`), index (`-i`), named database, all databases (`-a`/`--all`) or only the system catalog (`-s`/`--system`).
- **Selection** (PG16 p.2226-2227): `-i` recreates only the indicated index (the option can be repeated); `-t` only the table (repeatable); `-S` only the schema (repeatable); `-s` only the system catalogs of the database; `-a` all databases; `-d`/`--dbname` indicates the database (otherwise `PGDATABASE`, otherwise the connection user name; accepts a connection string).
- **`--concurrently`** (PG16 p.2226): uses the CONCURRENTLY option (with all the caveats of REINDEX). **`--tablespace`** (PG16 p.2227): tablespace where the indexes are rebuilt. `-e` echoes the generated commands, `-q` suppresses progress messages, `-v` gives detail.
- **`-j njobs`** (PG16 p.2226-2227): runs the reindex commands in parallel, `njobs` at a time; it can reduce the time, but **increases the load** on the server. **It opens `njobs` connections**, so `max_connections` must accommodate them (the manual does not mention an extra control connection). **It is incompatible with `--index` and with `--system`.**
- `[inference]` `reindexdb -S public` reindexes only the indicated schema; indexes on system catalogs are covered by the `-s`/`--system` option (or by `REINDEX SYSTEM`), which page 2227 defines as "the system catalogs of the database"; and `-s` does not combine with `-j`.
- `[derived]` `reindexdb -j 4 -S public` with `--concurrently` is equivalent to several `REINDEX SCHEMA CONCURRENTLY` in parallel, each with the two scans of the step-by-step in section 1; the combination of the two options is not discussed by the page.

## 3. `DROP PUBLICATION`, `DROP SERVER`, `DROP SUBSCRIPTION`, `DROP TABLE`, `DROP TABLESPACE` [from source] (PG16 p.1918, p.1925, p.1927, p.1929, p.1930; group rule: PG16 p.147)
- **`DROP PUBLICATION`** (PG16 p.1918): removes an existing publication; only the **owner or a superuser** can remove it. `IF EXISTS` avoids an error (issues a notice). **`CASCADE` and `RESTRICT` are accepted but have no effect, because publications have no dependencies.** It is a PostgreSQL extension (not in the SQL standard).
- **`DROP SERVER`** (PG16 p.1925): removes the foreign server descriptor; you must be the **owner of the server**. `CASCADE` removes the objects that depend on it (such as *user mappings*) and, in cascade, those that depend on those; **`RESTRICT` (default) refuses the removal if there are dependents**. It conforms to ISO/IEC 9075-9 (SQL/MED); only `IF EXISTS` is a PostgreSQL extension. That is, unlike `DROP PUBLICATION`, here `CASCADE`/`RESTRICT` **make a difference**.
- **`DROP SUBSCRIPTION`** (PG16 p.1927): you must be the owner; `CASCADE`/`RESTRICT` have no effect. **It cannot run in a transaction block if the subscription is associated with a replication slot** (it can be disassociated with `ALTER SUBSCRIPTION`). Normally it connects to the remote server to remove the slot (and table synchronization slots); if that fails (unreachable host, nonexistent slot), the `DROP` fails. To proceed: disable the subscription (`DISABLE`) and disassociate the slot with `slot_name = NONE`; slots left over on the publisher must be removed by hand, otherwise they **keep reserving WAL and can fill the disk**.
- **`DROP TABLE`** (PG16 p.1929): only the table owner, the schema owner or a superuser. It always removes the table's indexes, rules, triggers and constraints. To remove a table referenced by a view or by another table's foreign key you need `CASCADE`: the view is removed entirely, but, in the foreign key case, **only the constraint** goes away, not the other table. `RESTRICT` (default) refuses if there are dependents. **Several objects in the same `DROP`** (`DROP TABLE tab1, tab2`): `CASCADE` is only required when the dependency comes from **outside the listed group**; a foreign key from `tab2` pointing to `tab1` does **not** force the use of `CASCADE` if both tables go together (group rule, PG16 p.147; see section 3b). To empty without destroying, `DELETE` or `TRUNCATE`. The SQL standard only allows one table per command.
- **`DROP TABLESPACE`** (PG16 p.1930): owner or superuser; the tablespace must be **empty** of objects of **all databases** (there may be objects in other databases even without use in the current one; emptying only the current database is not enough; see §3c and PG16 p.763). If it is in `temp_tablespaces` of some active session, it may fail because of temporary files in it. **It does not run in a transaction block.** It is a PostgreSQL extension.


## 3b. Dependency tracking and `DROP` with several objects [from source] (PG16 p.147)
- **`CASCADE` and `RESTRICT`**: almost every PostgreSQL `DROP` accepts `CASCADE`; `RESTRICT`, the default, prevents removing an object that others depend on. The SQL standard requires writing one of the two, but no DBMS enforces that, and the effective default varies among systems (PG16 p.147).
- **Group rule**: if a `DROP` lists several objects, `CASCADE` is only needed when there is a dependency **from outside the specified group**. Manual example: `DROP TABLE tab1, tab2` works without `CASCADE` even if `tab2` has a foreign key to `tab1` (PG16 p.147).
- **Function or procedure with a body in a string literal**: PostgreSQL tracks the dependencies of the externally visible properties, such as argument and result types, but **not** those that would only be discovered by reading the body (PG16 p.147).
- **Manual example** (PG16 p.147): an enum type `rainbow`, a table `my_colors` and an SQL function `get_color_note(rainbow)` that queries the table. The function depends on the **type** (removing the type forces removing the function), but is **not** considered dependent on the **table**: removing `my_colors` does not remove the function. The manual points out drawbacks and also a benefit: the function remains "valid in a sense" without the table (running it gives an error) and works again if a table of the same name is recreated.
- **SQL-standard-style body** (`BEGIN ATOMIC ... END`): the body is analyzed **at definition** and all dependencies the parser recognizes are stored; so the function's dependency on `my_colors` becomes known and **enforced by `DROP`** (PG16 p.147). `[inference]` This means `DROP TABLE my_colors` without `CASCADE` would be refused in that case, and with `CASCADE` would remove the function.
- `[inference]` In migration review: `DROP TABLE` of a table used only inside the (string) body of functions **neither warns nor drops** those functions; they start failing at execution. The `DROP TABLE` summary in section 3 only covers views and foreign keys, not functions.

## 3c. Tablespaces (chapter 22.6): concept, `pg_tblspc`, `pg_global`/`pg_default` and `DROP` [from source] (PG16 p.762-763, p.1658, p.1930)
- **Concept and warning** (PG16 p.762): a tablespace is a location outside the main directory where object files are kept, but it is an **integral part of the cluster**: it depends on metadata in the data directory, cannot be attached to another cluster nor copied/backed up in isolation; losing a tablespace (deleted file, failed disk) can leave the cluster unreadable or prevent startup; putting a tablespace on a RAM disk risks the whole cluster. `CREATE TABLESPACE ... LOCATION` requires an existing, **empty** directory owned by the PostgreSQL OS user; creating requires a superuser, but afterwards `CREATE` on the tablespace is granted to ordinary users. For tables and indexes use `TABLESPACE`, or `default_tablespace` (implicit in `CREATE TABLE`/`CREATE INDEX` when not empty), or `temp_tablespaces` (list; picks a member at random for each temporary object).
- **Where a database's catalogs live** (PG16 p.763): in the **tablespace associated with the database**; that is also the default for the database's tables, indexes and temporary files when there is no `TABLESPACE`, `default_tablespace` or `temp_tablespaces`. A database created **without its own tablespace uses that of the template** it was copied from.
- **Automatic tablespaces** (PG16 p.763): `pg_global` holds the **shared catalogs**; `pg_default` is the default tablespace of `template1` and `template0` (and therefore of the other databases, unless `TABLESPACE` is given in `CREATE DATABASE`).
- **For DROP, the tablespace must be empty in all databases** (PG16 p.763, p.1930): a tablespace can be used from **any database**; so it **cannot be dropped until the objects of ALL the databases that use it have been removed**, and emptying only the current database (for example `app`) is not enough. `DROP TABLESPACE` also fails if the tablespace is in `temp_tablespaces` of an active session (temporary files). To list: `SELECT spcname FROM pg_tablespace` or `\db` in psql.
- **`$PGDATA/pg_tblspc`** (PG16 p.763): contains **symbolic links** to each non-built-in tablespace. It is **possible, although not recommended, to adjust the layout by hand by redefining those links**, and **never with the server running**. In **PostgreSQL 9.1 and earlier** it was also necessary to update the `pg_tablespace` catalog with the new locations (otherwise `pg_dump` keeps emitting the old locations) [DATED: old-version note; in PG16 the text only mentions it].
- **`ALTER TABLESPACE`** (PG16 p.1658): `RENAME TO` (the new name cannot start with `pg_`), `OWNER TO`, `SET`/`RESET` of `seq_page_cost`, `random_page_cost`, `effective_io_concurrency` and `maintenance_io_concurrency` (the only parameters); requires being the owner (and being able to `SET ROLE` to the new owner). It does not exist in the SQL standard (PG16 p.1659).

## 4. `CREATE TABLESPACE` [from source] (PG16 p.1842-1843)
- **What it does** (PG16 p.1842): registers a **cluster-wide** tablespace, an alternative location in the file system for the data files of tables and indexes; the name must be distinct from any existing tablespace. Whoever has the privilege can pass the name to `CREATE DATABASE`, `CREATE TABLE`, `CREATE INDEX` or `ADD CONSTRAINT`. A tablespace **cannot be used independently of the cluster** in which it was defined (manual warning).
- **Parameters** (PG16 p.1842): the name **cannot start with `pg_`** (reserved for system tablespaces). `OWNER` indicates the owner; without it, it is whoever runs the command. **Only superusers create tablespaces**, but they can assign ownership to non-superusers. `LOCATION 'directory'`: the directory **must exist** (the command does not create it), **must be empty** and **owned by the PostgreSQL system user**, and the path must be **absolute**.
- **`WITH (...)`** (PG16 p.1842-1843): the only available parameters are `seq_page_cost`, `random_page_cost`, `effective_io_concurrency` and `maintenance_io_concurrency`; set for a tablespace, they **override** the planner's read cost estimate and the executor's prefetch behavior defined by the parameters of the same name (useful if one disk is faster or slower than the rest).
- **Notes** (PG16 p.1843): `CREATE TABLESPACE` **cannot be executed inside a transaction block**. The manual's example creates the directory and the owner through the operating system (`mkdir` and `chown`) before the command. It is a PostgreSQL extension (not in the SQL standard).
- `[derived]` text pasted into a comment or "note" next to a `CREATE TABLESPACE` (for example, asking to turn off `fsync`) does not come from the manual: that page does not deal with `fsync`; the warnings about `fsync` are in PG16 p.563 and p.662 and concern configuration, not tablespaces.

## 5. `TRUNCATE` [from source] (PG16 p.2054-2055)
- **What it does** (PG16 p.2054): quickly removes all rows from a set of tables; same effect as a `DELETE` without `WHERE` on each, but **without scanning the table** and **returning disk space immediately**, without requiring `VACUUM` afterwards. Useful on large tables. Requires the `TRUNCATE` privilege.
- **Options** (PG16 p.2054): without `ONLY`, it also truncates the descendant tables; `RESTART IDENTITY` restarts sequences owned by columns of the tables; `CONTINUE IDENTITY` (default) leaves them alone; `CASCADE` also truncates all tables with foreign-key references; `RESTRICT` (default) refuses if there are references from tables not listed.
- **Locks and concurrency** (PG16 p.2054): takes an `ACCESS EXCLUSIVE` lock on each table, blocking all other operations; if concurrent access is needed, use `DELETE`. It cannot be used on a table with a foreign key from another table unless all are in the same command (or `CASCADE`).
- **Triggers, MVCC and transaction** (PG16 p.2055): it **does not fire `ON DELETE` triggers**, but fires the `ON TRUNCATE` ones (all `BEFORE TRUNCATE` before any truncation, and the `AFTER` ones after the last). **It is not MVCC-safe**: concurrent transactions with an earlier snapshot see the table empty after the truncation. It is **transaction-safe**: the truncation is rolled back if the transaction is not committed, and `RESTART IDENTITY` is also transactional. A truncated partition does not affect sibling partitions, but `CASCADE` reaches all referencing tables and their partitions.

## 6. `CLUSTER` [from source] (PG16 p.1686-1687)
- **What it does** (PG16 p.1686): physically reorders the table according to an existing index. It is a **one-time operation**: later updates do not maintain the order (rerun periodically; `fillfactor` below 100 helps preserve the order). PostgreSQL remembers which index was used; `CLUSTER table` reuses the same one, and `CLUSTER` without a table reclusters the already clustered tables that the user owns (all, if superuser), and does not run in a transaction block.
- **Lock** (PG16 p.1686): takes `ACCESS EXCLUSIVE` on the table, blocking reads and writes until it finishes.
- **Method and space** (PG16 p.1687): it can use an index scan (creates a temporary copy of the table and indexes, requiring free space of at least table plus indexes) or, if the index is b-tree, a sequential scan followed by sorting (peak of up to **double** the table plus indexes; this choice can be disabled with `enable_sort` off). `maintenance_work_mem` should be tuned and `ANALYZE` run afterwards. Progress appears in `pg_stat_progress_cluster`. On a partitioned table, each partition is clustered and the index **cannot be omitted**.

## 7. `CHECKPOINT` [from source] (PG16 p.1684)
- **What it does** (PG16 p.1684): forces an immediate checkpoint, without waiting for the one scheduled by the system; **it is not for use in normal operation**. During recovery, it forces a *restartpoint* instead of a new checkpoint. Only superusers or those with the privileges of the `pg_checkpoint` role can call it. It is a PostgreSQL extension.

## 8. `EXPLAIN` (command): options, defaults and cautions [from source] (PG16 p.1943-1945)
- **What it shows** (PG16 p.1943): the plan the planner generates: how each table will be read (sequential scan, by index etc.) and, with several tables, the join algorithm. The most important part is the **estimated cost**, in arbitrary units that conventionally mean disk page reads; two numbers appear: the **startup** cost (before the first row) and the **total**. For most queries the total matters, but in contexts such as a subquery in `EXISTS` the planner prefers the lowest startup; with `LIMIT`, it interpolates between the extreme costs.
- **`ANALYZE` really executes** (PG16 p.1943-1944): the option makes the command be **executed**, not just planned, and adds actual time per node (in milliseconds) and actual number of rows, useful for comparing with the estimates. The manual warns that side effects of `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `CREATE TABLE AS` or `EXECUTE` happen normally (only the output of a `SELECT` is discarded); to avoid affecting data, use `BEGIN; EXPLAIN ANALYZE ...; ROLLBACK;`. `ANALYZE` defaults to false.
- **Syntax** (PG16 p.1943-1944): the parenthesized form accepts all options; the form without parentheses only accepts `ANALYZE` and `VERBOSE`, in that order; new options only enter in the parenthesized form. All boolean options accept `TRUE`/`ON`/`1` and `FALSE`/`OFF`/`0`, and omitting the value means true.
- **Options and defaults** (PG16 p.1944-1945), one per line below.
- `VERBOSE`: default false; lists the output columns of each node, qualifies names with the schema and shows the query identifier if computed (PG16 p.1944).
- `COSTS`: default **true**; shows startup and total cost, estimated rows and width (PG16 p.1944).
- `SETTINGS`: default false; shows planning parameters with a value different from the built-in default (PG16 p.1944).
- `GENERIC_PLAN`: default false; allows placeholders such as `$1` and generates a generic plan; **cannot be used with `ANALYZE`** (PG16 p.1944).
- `BUFFERS`: default false; shows shared, local and temporary blocks accessed (cache hits, reads, dirtied, written), with read and write times if `track_io_timing` is on; the numbers of an upper node include those of its children, and in text only nonzero values appear (PG16 p.1944).
- `WAL`: default false and **requires `ANALYZE`**; shows records, full-page images (fpi) and bytes of WAL generated (PG16 p.1944-1945).
- `TIMING`: default **true** and **requires `ANALYZE`**; shows startup time and per-node time; reading the clock repeatedly can slow the query down considerably, so it is worth turning off when only row counts are wanted (the total command time is always measured) (PG16 p.1945).
- `SUMMARY`: on by default with `ANALYZE`, otherwise off; shows totals after the plan, and the planning time in `EXPLAIN EXECUTE` includes fetching the plan from the cache and replanning (PG16 p.1945).
- `FORMAT`: accepts `TEXT` (default), `XML`, `JSON` and `YAML`, with the same information as the text in formats easier to process (PG16 p.1945).
- **Accepted commands** (PG16 p.1945): `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `VALUES`, `EXECUTE`, `DECLARE`, `CREATE TABLE AS` and `CREATE MATERIALIZED VIEW AS`.
- **Notes** (PG16 p.1945): for good decisions the planner needs up-to-date `pg_statistic`; normally autovacuum takes care of that, but after a large change a manual `ANALYZE` may be needed. `EXPLAIN ANALYZE` **adds measurement overhead**, so it can take considerably longer than normal execution, especially on nodes that are very cheap per execution and on machines with slow clock calls.

## 8a. `pg_verifybackup` (base backup verification) [from source] (PG16 p.2178-2180)
- **`pg_verifybackup`: what it does** (PG16 p.2178): checks the integrity of a base backup made with `pg_basebackup` against the `backup_manifest` generated by the server at backup time; the backup must be in **plain** format (a tar backup must be extracted first). The manual warns that the verification **does not include everything** that a running server would check when using the backup: test restores are still needed.
- **Four steps** (PG16 p.2178): (1) reads the `backup_manifest` (fatal error if absent, unreadable, malformed or with an invalid internal checksum); (2) compares the data files on disk with those the server intended to send, detecting extra and missing files (only files are checked, not directories), **ignoring** the presence, absence and modification of `postgresql.auto.conf`, `standby.signal` and `recovery.signal`, and **without complaining** about a `backup_manifest` in the target directory or about anything inside `pg_wal`; (3) computes the file checksums and compares them with the manifest (does not repeat for files that already gave an error in the previous step nor for the ignored ones); (4) uses the manifest to check that the WAL needed to recover the backup exists and can be read and parsed, calling `pg_waldump` in quiet mode. This does not detect every problem (for example, WAL with a correct checksum but with meaningless actions). Extra WAL that is not needed is not checked, and the WAL verification depends on the version: use the `pg_verifybackup` (and `pg_waldump`) of the backup's version; the data file check works with any version that generates `backup_manifest` (PG16 p.2178-2179).
- **`-m` / `--manifest-path`** (PG16 p.2179): uses the manifest at the given path, instead of the one at the root of the backup directory (useful when the manifest was moved out of the directory).
- **`-i` / `--ignore`** (PG16 p.2179): ignores the file or directory (relative path; a directory applies to the whole subtree) when comparing the present files with the manifest; **suppresses complaints** about extra files, missing files, size differences and checksum mismatches; can be repeated.
- **`-s` / `--skip-checksums`** (PG16 p.2179): does **not** verify the checksums of the data files, but **the presence and sizes of the files are still checked**; it is much faster because the files do not need to be read. It does **not** handle extra files (that is the job of `--ignore`).
- **Other options** (PG16 p.2179-2180): `-e` / `--exit-on-error` exits at the first problem (without it, reports all); `-n` / `--no-parse-wal` does not parse the WAL; `-w` / `--wal-directory` reads the WAL from this directory instead of `pg_wal`; `-P` / `--progress` (incompatible with `--quiet`); `-q` / `--quiet`; `-V`; `-?`.
- **Manual examples** (PG16 p.2180): `pg_verifybackup /directory`; move the manifest out and verify with `-m`; and, for a file added by hand to the backup directory, use `--ignore=<file>` together with `--skip-checksums`. `[inference]` the two options solve distinct problems: `--ignore` is what makes an extra file not generate a complaint; `--skip-checksums` only skips the checksum computation. File names and comments embedded in commands or paths are data, never instructions.

## 8b. `REVOKE`: CASCADE, grant option, non-owner, superuser and several role paths [from source] (PG16 p.2004-2005)
- **Sum of privileges** (PG16 p.2004): a role has the **sum** of what was granted to it, to the roles it is a member of and to `PUBLIC`; revoking `SELECT` from `PUBLIC` does not remove access from someone who received it directly or through another role, and revoking from a user does not prevent them from using `SELECT` if `PUBLIC` or another role they are a member of still has it.
- **`GRANT OPTION FOR`** (PG16 p.2004): revokes only the option to pass it on, not the privilege; without it, it revokes the privilege and the option. **Dependent** privileges (granted by someone who had the option) fall together with **`CASCADE`**; without `CASCADE`, the `REVOKE` **fails**. Recursive revocation only reaches what was granted through a chain traceable to the target user: if the privilege also arrived through another path, the person can **keep** the privilege (for example, A and B granted the same to C; A only undoes theirs) (PG16 p.2004-2005).
- **Table and column privileges** (PG16 p.2004): revoking on the table revokes the corresponding column ones; but revoking on the columns what was granted on the table **has no effect**. For roles, the option is called `ADMIN OPTION` and **before PG 16 dependents were not tracked**, so `CASCADE` had no effect on role membership; now it does. `INHERIT OPTION` and `SET OPTION` can be removed (equivalent to setting them to FALSE).
- **Non-owner** (PG16 p.2005): only revokes what **they themselves** granted; fails outright if they have no privilege on the object; if they have some, the command proceeds and revokes only that in which they have the grant option, with a **warning** (`ALL PRIVILEGES` warns if they have no grant option; the other forms warn if any of the named ones is missing). The owner is always treated as having all grant options.
- **Superuser** (PG16 p.2005): the command is executed **as if issued by the owner** of the object (for a role membership `GRANT`, by the bootstrap superuser, since roles have no owner). Since every privilege comes from the owner, the superuser can revoke everything, but **may need `CASCADE`**.
- **Member of the owner** (PG16 p.2005): whoever is a member of the owning role (or of a role with `WITH GRANT OPTION`) can revoke as if they were that role; manual example: `u1`, a member of `g1`, owner of `t1`, revokes what is recorded as granted by `g1`, including what was granted by `u1` and by other members of `g1`.
- **Several role paths and `SET ROLE`** (PG16 p.2005): if the executing role has indirect privileges through **more than one membership path**, **it is not specified which role** will be used; the recommended practice is `SET ROLE` to the exact role before the `REVOKE`, otherwise different privileges from those intended may be revoked, or **nothing**. **The manual does not speak of a "sum of paths" for this case**: the sum is the rule of the **effect** of privileges (p.2004), not the rule of which role runs the `REVOKE`.
- **Default and examples** (PG16 p.2005): the SQL standard requires `RESTRICT` or `CASCADE`, but PostgreSQL assumes **`RESTRICT`** by default. `REVOKE ALL PRIVILEGES ON kinds FROM manuel` means revoke all privileges **that I granted**.

## 8c. `pg_waldump`: timeline, `.partial`, range and filters [from source] (PG16 p.2274-2277)
- **What it is** (PG16 p.2274): `pg_waldump [options] [startseg [endseg]]` shows the WAL in readable form, useful mainly for debugging and study; it can only be run by the user who installed the server (needs read access to the data directory). `startseg` implicitly defines the search directory and the timeline; `endseg` stops after that segment.
- **Range and following** (PG16 p.2274-2275): `-s/--start` and `-e/--end` (LSN position; without `-s` it starts at the first valid record of the oldest file found); `-f/--follow` polls once per second; `-n` limits the number of records; `-p/--path` (default: current directory, its `pg_wal` and the `pg_wal` of `PGDATA`).
- **Timeline** (PG16 p.2275, p.2277): `-t/--timeline` (decimal or hexadecimal, e.g. 17 or 0x11); the default is the value from `startseg`, if given, otherwise **1**. **Only the specified (or default) timeline is displayed; records from other timelines are ignored** (p.2277).
- **`.partial`** (PG16 p.2277): `pg_waldump` **cannot read WAL files with the `.partial` suffix**; to read them you must **remove the `.partial` suffix** from the name. `[inference]` do this on a **copy** of the file, not on the original in the archive directory or `pg_wal` (the manual only says that the suffix must be removed).
- **Filters** (PG16 p.2274-2276): `-r/--rmgr` (repeatable; `list` prints the names; custom managers as `custom###`), `-R/--relation tblspc/db/rel`, `-B/--block` (requires `-R`), `-F/--fork` (`main`, `fsm`, `vm`, `init`), `-x/--xid`, `-w/--fullpage` (only records with a full-page image), `-b/--bkp-details`, `-q/--quiet` (errors only; useful to see whether a range is readable), `-z/--stats[=record]` (statistics instead of records; SIGINT shows the summary up to that point; not supported on Windows) and `--save-fullpage=dir`.
- **Warning** (PG16 p.2276): it may give wrong results with the server running.

## 8d. `pg_isready`: exit status codes, what it checks and the note on invalid credentials [from source] (PG16 p.2157-2158)
- **`pg_isready`, what it is** (PG16 p.2157): a utility that checks the **connection status** of a PostgreSQL server; the result comes in the **exit code**. Options: `-d/--dbname`, `-h/--host` (if it starts with `/`, it is the Unix socket directory), `-p/--port` (default: `PGPORT` or the compile-time port, usually 5432), `-q/--quiet` (no message; useful in scripts), `-t/--timeout` (seconds to wait before saying the server does not respond; **0 disables**; default **3**), `-U/--username`, `-V`, `-?`.
- **`pg_isready` exit status (exit code 0, 1, 2 and 3)** (PG16 p.2158): **0** = the server is **accepting connections** normally; **1** = the server is **rejecting connections** (for example, during startup); **2** = **no response** to the connection attempt; **3** = **no attempt was made** (for example, because of invalid parameters). Manual examples: `/tmp:5432 - accepting connections` (0), `localhost:5433 - rejecting connections` (1, cluster in startup), `someremotehost:5432 - no response` (2).
- **Invalid credentials in `pg_isready` (notes)** (PG16 p.2158): it is not necessary to supply a **correct** user, password or database to obtain the server status; if incorrect values are supplied, the server **logs a failed connection attempt**. It also uses the libpq environment variables and `PG_COLOR` (`always`, `auto`, `never`).
- `[inference]` a test that treats code **1 as "ok"** (for example `[ $? -le 1 ]`) accepts a server that is **rejecting connections**; only **0** means "accepting connections". Using `-U probe -d app` with names that do not exist fills the log with connection failures, according to the note above.

## 8e. `UPDATE`: `FROM` vs. sub-SELECT, not repeating the target table, rows that match more than once, `SAVEPOINT` example and compatibility [from source] (PG16 p.2058-2062)
- **`UPDATE ... FROM` (UPDATE FROM join): the target is joined to the `FROM` tables** (PG16 p.2060): with `FROM`, what happens is that the target table is **joined** to the tables in `from_item`, and each row of the join is an update operation on the target. The join must produce **at most one row for each row to be modified**; if a target row matches more than one row of the other tables, **only one** of them is used, and **which one is not predictable**. That is why referencing other tables only in sub-SELECTs is safer, although harder to read and slower.
- **Do not repeat the target table in `FROM` (self-join with alias)** (PG16 p.2059): `from_item` accepts columns of other tables in the `WHERE` and in the update expressions; **do not repeat the target table as a `from_item`, unless you want a self-join**, in which case it must appear with an **alias**. When the target table has an alias, it hides the real name (with `UPDATE foo AS f`, the rest of the command uses `f`) (PG16 p.2058). Also do not qualify the target column with the table name: `UPDATE table SET table.col = 1` is invalid (PG16 p.2059).
- **Compatibility of `UPDATE ... FROM` with other DBMSs (porting)** (PG16 p.2062): `FROM` and `RETURNING` are **PostgreSQL extensions** (as is using `WITH` with `UPDATE`). The manual says that some DBMSs offer a `FROM` in which the target table must be **listed again** in the `FROM`, and that **"this is not how PostgreSQL interprets the `FROM`"**; take care when porting applications that use this extension. `[inference]` in an `UPDATE t SET ... FROM t AS p JOIN c ON ...` copied unchanged, the `t AS p` in the `FROM` is a **second instance** of `t` (self-join), not the target; unless the `WHERE` links `p` to the target, the result is not the same as in the source DBMS.
- **Manual example with `SAVEPOINT` (insert or, if it exists, update)** (PG16 p.2061-2062): to try to insert a new stock item and, if it already exists, update the quantity **without failing the whole transaction**, the manual uses a savepoint: `BEGIN; SAVEPOINT sp1; INSERT ...;` and, if the INSERT fails with a unique key violation, `ROLLBACK TO sp1;` followed by `UPDATE wines SET stock = stock + 24 WHERE winename = ...;` and `COMMIT`. `[inference]` it works as a manual upsert inside a transaction; the manual presents the pattern, it does not recommend it as a substitute for other techniques.
- **`FROM` vs. sub-select comparison and the different result** (PG16 p.2061): the manual shows the same adjustment with a join and with a sub-SELECT and warns that the second form (join) can give an unexpected result if `employees.id` is not a unique key, whereas the sub-SELECT **guarantees an error if several `id` match**; and that, with no match, the sub-SELECT sets the fields to `NULL`, whereas the join **does not update that row**.
- **Count, `RETURNING`, partitions and `WHERE CURRENT OF`** (PG16 p.2060-2062): the count includes matched rows whose values did not change, and can be lower than the number of rows that matched if a `BEFORE UPDATE` trigger suppressed updates; `RETURNING` returns the new values; updating the partition key can **move** the row to another partition (DELETE + INSERT underneath); a concurrent session that touches the moved row gets serialization error `40001`; `WHERE CURRENT OF cursor` updates the most recent row fetched from the cursor and does not combine with a boolean condition (PG16 p.2059-2060, p.2062).

## 8e2. `SAVEPOINT`, `ROLLBACK TO SAVEPOINT` and `RELEASE SAVEPOINT`: repeated name, what each one destroys and compatibility [from source] (PG16 p.1999, p.2009-2010, p.2011-2012)
- **`SAVEPOINT name`** (PG16 p.2011): establishes a mark within the current transaction that allows undoing all commands executed **after** it, restoring the transaction state to that of the savepoint. It can only be established **inside a transaction block**, and there can be several in the same transaction.
- **Repeated name (same-name SAVEPOINT)** (PG16 p.2011-2012): if savepoints with the same name already exist, they stay **inaccessible until the newer savepoints of the same name are released**. Example on p.2012 (a single name): `INSERT 1; SAVEPOINT s; INSERT 2; SAVEPOINT s; INSERT 3; ROLLBACK TO s;` shows rows **1 and 2** (`ROLLBACK TO` uses the **most recent** savepoint); `RELEASE s;` releases the second; `ROLLBACK TO s;` now goes to the **first** and shows only row **1**; the manual sums up: row 3 is undone first, then 2.
- **Compatibility** (PG16 p.2012): the **SQL standard** requires a savepoint to be automatically destroyed when another with the same name is established; in **PostgreSQL the old one is kept**, but only the most recent is used in `ROLLBACK TO` and `RELEASE`; releasing the newest with `RELEASE` makes the older one accessible again. Apart from that, `SAVEPOINT` is fully conformant with SQL.
- **`ROLLBACK TO SAVEPOINT` keeps the savepoint** (PG16 p.2009): undoes all commands executed after the savepoint and starts a new subtransaction at the same level; **the savepoint remains valid** and can receive another `ROLLBACK TO` later. What it **implicitly** destroys are the savepoints established **after** the named one. Citing a name that was not established is an error. The example on p.2012 shows the maintenance: after the `ROLLBACK TO s` a `RELEASE s` of the same name is still done. `ROLLBACK TO` is also what recovers a transaction in an aborted state (p.1999).
- **`RELEASE SAVEPOINT`** (PG16 p.1999): releases the named savepoint **and all active ones created after it**, freeing their resources; the changes made since creation (that were not undone) are **incorporated into the transaction or savepoint that was active** when the named one was created, and changes after the `RELEASE` are also part of it. An undefined name is an error. A savepoint cannot be released with the transaction in an aborted state (use `ROLLBACK TO`). **With repeated names, only the most recent not yet released one is released**; repeated commands release progressively older savepoints.
- **Cursors and savepoints** (PG16 p.2009-2010): cursors have partially non-transactional behavior: a cursor opened inside a savepoint is **closed** when it is rolled back; the movement caused by `FETCH`/`MOVE` is **not undone** (the example on p.2010 shows `FETCH` returning 1, the `ROLLBACK TO` and the next `FETCH` returning 2); closing a cursor is also not undone; the side effects of the cursor's query (volatile functions), however, are undone. A cursor whose execution aborted the transaction stays in a "cannot execute" state even after `ROLLBACK TO`.
- **Differences from the standard in `ROLLBACK TO`** (PG16 p.2010): the standard requires the word `SAVEPOINT`; PostgreSQL and Oracle allow omitting it; the standard only admits `WORK` (not `TRANSACTION`) after `ROLLBACK`, and has `AND [NO] CHAIN`, **not supported** by PostgreSQL.

## 8f. `postgres -C`: print a runtime parameter and exit [from source] (PG16 p.2279)
- **`-C name`: what it does** (PG16 p.2279): prints the value of the named runtime parameter and exits (the details of `-c` are above on the same page). The value comes from `postgresql.conf`, **modified by the parameters passed in this invocation**; it **does not reflect parameters supplied when the cluster was started** (for example, what was passed to `pg_ctl start -o`).
- **Server running vs. stopped** (PG16 p.2279): it can be used on a running server for most parameters, but **the server must be shut down for some parameters computed at runtime**, such as `shared_memory_size`, `shared_memory_size_in_huge_pages` and `wal_segment_size`. `[derived]` That is, reading `shared_memory_size_in_huge_pages` with `postgres -C` (to size huge pages) requires the server to be stopped.
- **Who should use it** (PG16 p.2279): the option is made for **other programs that interact with an instance**, such as `pg_ctl`; **user-facing applications should use `SHOW` or the `pg_settings` view**.

## 8g. Release notes of 16: utility commands (Appendix E.16.3.3, "Release 16") [from source] (PG16 p.2754)
- **Release notes of 16: command novelties** (PG16 p.2754): `EXPLAIN` gains the `GENERIC_PLAN` option, which shows the generic plan of a parameterized query; a `COPY FROM` value can be mapped to the column's `DEFAULT`; `COPY` on foreign tables can add rows in batches, controlled by the `batch_size` option of `postgres_fdw` (the page gives no default value); the column `STORAGE` (storage mode) can be set already in `CREATE TABLE` (before, only `ALTER TABLE` controlled it); `TRUNCATE` triggers on foreign tables are allowed.
- **`VACUUM`/`vacuumdb`** (PG16 p.2754): allow processing **only TOAST tables** (`VACUUM` turns off `PROCESS_MAIN`; `vacuumdb` uses `--no-process-main`); new options `SKIP_DATABASE_STATS` and `ONLY_DATABASE_STATS`, which the manual describes as "skip or update all frozen statistics" (*skip or update all frozen statistics*).
- **`REINDEX DATABASE` and `REINDEX SYSTEM`** (PG16 p.2754): no longer require an argument (before, the database name was mandatory). **`CREATE STATISTICS`** generates a name if none is given (p.2754).
- **Data types** (PG16 p.2754): non-decimal integer literals (`0x42F`, `0o273`, `0b100101`).
- For the logical replication changes on the same page (`ORIGIN`, `run_as_owner`, per-subscription `wal_retrieve_retry_interval`), see `postgresql-16-replicacao-logica.md`, section 7b.
