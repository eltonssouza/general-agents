## Container images
- **[from source]** Copying the fat jar "as is" into the image works, but running the jar without unpacking has overhead and having everything (code + dependencies) in a single layer is suboptimal; split it to take advantage of layer caching (SBR p.436).
- **[from source]** Unpack: `jar -xf myapp.jar` and `java org.springframework.boot.loader.JarLauncher`; with the natural `main` (`-cp BOOT-INF/classes:BOOT-INF/lib/*`) startup improves more, but the `JarLauncher` guarantees a predictable classpath order via `classpath.idx` (SBR p.436).
- **[from source]** Layers: `layers.idx` with `dependencies`, `spring-boot-loader`, `snapshot-dependencies`, `application` (SBR p.436-437). `java -Djarmode=layertools -jar my-app.jar` (`list`, `extract`, `help`); the layertools mode **does not work** on a fully executable jar with a launch script (disable the script) (SBR p.437-438). There is a sample multi-stage Dockerfile using `extract` (SBR p.438). Format and location of `layers.idx`/`classpath.idx` (`BOOT-INF/`, not YAML) and the book's jar vs war conflict: `references/12`, section "Executable jar format (Appendix E)" (SBR p.437, 839-840).
- **[from source]** Cloud Native Buildpacks: direct support in the Maven and Gradle plugins; the Paketo buildpack respects `layers.idx`; buildpacks may change file metadata (modification date), so nothing may depend on that at runtime; `spring.web.resources.cache.use-last-modified` can be turned off (SBR p.438-439).

- **[from source]** Dockerfile and layertools details: the natural `main` can be used with `-cp BOOT-INF/classes:BOOT-INF/lib/*` (faster), but the `JarLauncher` preserves the classpath order (SBR p.436); the `layertools` `extract` creates directories (`dependencies/`, `spring-boot-loader/`, `snapshot-dependencies/`, `application/`) that the final stage copies in order; the book's example uses the base image `eclipse-temurin:11-jre` (a 2023 example, not a requirement); without the jarmode the layers could be assembled with `unzip`/`mv`, but the jarmode simplifies it (SBR p.438).
- **[from source]** What the Reference does **not** include about images: the goal/command of the plugin that generates the image with buildpacks (0 occurrences of build-image and of bootBuildImage); it only says that Maven and Gradle support buildpacks directly and refers to each plugin's documentation (SBR p.439, 550); no Docker Compose step, push to a registry or native image. For these questions: **POINTER ONLY** at p.439 (buildpacks) and NOT COVERED for the rest; the JavaCodeGeeks guide (Spring Boot 3) talks about `bootBuildImage` and belongs to the *java-backend-frameworks-expert*.
- **[from source]** Buildpacks and platforms: Heroku and Cloud Foundry use the "buildpack" approach that wraps the deployed code (JDK + `java`, embedded server or application server) and the ideal is for the executable jar to contain everything (SBR p.524); the Cloud Foundry Java buildpack supports jar and war (SBR p.524).

## Cloud
- **[from source]** Cloud Foundry: `cf push`; metadata and services arrive as `VCAP_*` variables and are flattened into `vcap.*` properties (SBR p.524-527). Heroku: `Procfile` with `web: java -Dserver.port=$PORT -jar ...` (SBR p.528). OpenShift, AWS (Elastic Beanstalk: Tomcat platform = war; Java SE = jar with `server.port=5000`), CloudCaptain/Boxfuse, Azure, Google Cloud (App Engine Standard requires WAR; Flex uses `app.yaml`) (SBR p.529-533). **[DATED]** the CLI/platform examples reflect 2023 and parts are old (e.g. JDK 8 in the logs).
- **[from source]** Kubernetes: detection looks at `*_SERVICE_HOST`/`*_SERVICE_PORT` (override: `spring.main.cloud-platform`); on shutdown there is a window in which traffic still reaches the pod: use `preStop` with `sleep`, then SIGTERM and graceful shutdown; if you increase `spring.lifecycle.timeout-per-shutdown-phase`, increase `terminationGracePeriodSeconds` (default 30 s) (SBR p.527-528). Excerpt from the book (SBR p.528), in the Pod:
  ```yaml
  spec:
    containers:
    - name: "example-container"
      image: "example-image"
      lifecycle:
        preStop:
          exec:
            command: ["sh", "-c", "sleep 10"]
  ```
  Once the hook completes, SIGTERM is sent and graceful shutdown begins, letting in-flight requests finish; if the container keeps running after the grace period it receives SIGKILL (SBR p.528). Liveness/readiness probes: manifest in `references/10` §Probes (SBR p.463).

## OS services
- **[from source]** **systemd:** `.service` file with `ExecStart` of `java -jar`, `SuccessExitStatus=143`; `systemctl enable` (SBR p.533-534). **init.d:** "fully executable" jar (`<executable>true</executable>` in Maven; `launchScript()` in Gradle); warning: `jar -xf` may fail silently on these jars and zip64 jars cannot be executable (SBR p.534-535).
- **[from source]** Default script: runs as the jar's owner, PID in `/var/run/<app>/<app>.pid`, log in `/var/log/<app>.log`; variables `MODE`, `RUN_AS_USER`, `PID_FOLDER`, `LOG_FOLDER`, `CONF_FOLDER`, `JAVA_HOME`, `JAVA_OPTS`, `STOP_WAIT_TIME` (60 s)...; `<app>.conf` file next to the jar (SBR p.535-540).
- **[from source]** **init.d security:** never run as root (`RUN_AS_USER` non-root; jar not owned by root); `nologin` shell; `chmod 500` on the jar; `chattr +i`; `.conf` with `chmod 400` and owned by root (SBR p.536-537). Windows: `winsw` (SBR p.540).

## War and traditional deployment
- **[from source]** For war: subclass of `SpringBootServletInitializer` with `configure`, `packaging war` (Maven) or the `war` plugin (Gradle), `spring-boot-starter-tomcat` as `provided` (Gradle: `providedRuntime`, not `compileOnly`); WebFlux does not support war (SBR p.659-661). Converting an existing app: servlets/filters become beans (SBR p.661-663). WebLogic: the initializer must implement `WebApplicationInitializer` directly and `weblogic.xml` with `prefer-application-packages` for `org.slf4j` (SBR p.666-667).
- **[from source]** Executable and war at the same time: share the `customizerBuilder` between `configure` and `main` (SBR p.663-664).

## Round 4 additions: cloud and OS-service deployment, page details
- **[from source]** Cloud Foundry (SBR p.524-527): the Cloud Foundry Java buildpack supports executable jar and war; `cf push <name> -p <jar>` requires a prior login in `cf` and takes into account a `manifest.yml` present in the directory (SBR p.524-525). Metadata and service credentials arrive as environment variables (`VCAP_SERVICES` etc.), because it is a polyglot platform; Boot extracts and flattens this data into properties with the `vcap` prefix in the `Environment` (e.g. `vcap.application.instance_id`); the Javadoc of `CloudFoundryVcapEnvironmentPostProcessor` has the details and the Java CFEnv project is better suited to configure a `DataSource` (SBR p.526-527). The example logs (JDK 1.8.0_121, Java Buildpack v3.12) are old [DATED] (SBR p.525).
- **[from source]** Kubernetes (SBR p.527-528): shutdown involves several subsystems in parallel (shutdown hooks, removal from the service registry and from the load balancer), so there is a window in which traffic still reaches the pod that has already begun shutting down; configure a `sleep` in a `preStop` handler long enough for new traffic to stop arriving (the duration varies per deployment; the example uses `sleep 10`). Once the hook completes, `SIGTERM` starts graceful shutdown; the default `terminationGracePeriodSeconds` is 30 s and, after the deadline, the container receives `SIGKILL`; when increasing `spring.lifecycle.timeout-per-shutdown-phase`, also increase `terminationGracePeriodSeconds` in the Pod YAML (SBR p.528).
- **[from source]** Heroku (SBR p.528-529): the `Procfile` is `web: java -Dserver.port=$PORT -jar target/demo-0.0.1-SNAPSHOT.jar`; Heroku assigns the port through the `PORT` variable and the `-D` becomes a property of the `Environment`; the usual flow is `git push heroku main` (log examples from 2014 with Maven 3.3.1 and JDK 1.8 are old [DATED]). OpenShift: the text only lists links (S2I builder, architecture guide, Wildfly) (SBR p.529-530).
- **[from source]** AWS Elastic Beanstalk (SBR p.530-531): "Tomcat" platform for projects that produce a war, with no special configuration; "Java SE" platform for a jar with an embedded container: the environment runs an nginx on port 80 as a proxy to the application on port 5000, so set `server.port=5000`. Tips: upload the binaries instead of the source code (`deploy: artifact: target/demo-0.0.1-SNAPSHOT.jar` in `.elasticbeanstalk/config.yml`) and, to avoid the cost of the load balancer (the environment default), use the "Single instance" type (`eb create -s`). CloudCaptain/Boxfuse: turns the jar/war into a minimal VM image; activates the Spring profile `boxfuse` by default and uses `application-boxfuse.properties` if it exists (SBR p.530-532). Azure: the text refers to a guide (Azure Spring Cloud or App Service) (SBR p.532).
- **[from source]** Google Cloud (SBR p.532-533): App Engine **Standard requires WAR packaging**; App Engine **Flex** requires an `app.yaml` (normally in `src/main/appengine`) describing resources (runtime `java`, `env: flex`, `jdk: openjdk8`, `manual_scaling`, `health_check`); deploying with the `appengine-maven-plugin` uses the project ID in the configuration and `mvn appengine:deploy` (the build fails if authentication is needed first).
- **[from source]** systemd (SBR p.533-534): the user, the PID file and the console log are managed by systemd itself and configured in the fields of the `.service` file (there is no `RUN_AS_USER`/`PID_FOLDER` of the embedded script); the example uses `ExecStop=/bin/kill -15 $MAINPID` and `SuccessExitStatus=143`; `ExecStart` does not declare a script action, so the `run` command is used by default; `systemctl enable myapp.service` turns on start at boot.
- **[from source]** init.d and fully executable jar, the *fully executable jar* / *executable jar* (SBR p.534-540): the script embedded at the start of the file makes some utilities not accept the format (`jar -xf` may fail silently); a fully executable jar is recommended only if you will run it directly, and not with `java -jar` or in a servlet container; a jar in zip64 format cannot be fully executable (it becomes corrupted), although a standard jar containing nested zip64 jars can (SBR p.534-535). The default script is tested on CentOS and Ubuntu and other platforms (OS X, FreeBSD) require their own script; installation by symbolic link: `sudo ln -s /var/myapp/myapp.jar /etc/init.d/myapp`, then `service myapp start`; on failure, see `/var/log/<appname>.log`; for automatic start, e.g. `update-rc.d myapp defaults <priority>` on Debian (SBR p.535-536).
- **[from source]** Customizing the script (SBR p.537-540): when writing the jar use `embeddedLaunchScriptProperties` (Maven) or `properties` of the `launchScript` (Gradle) with keys such as `mode` (default `auto`), `initInfoProvides`, `initInfoRequiredStart`, `initInfoDefaultStart` (2 3 4 5), `initInfoDefaultStop` (0 1 6), `initInfoChkconfig` (2345 99 01), `confFolder` (jar folder), `inlinedConfScript`, `logFolder`, `logFilename`, `pidFolder`, `pidFilename`, `useStartStopDaemon` (true) and `stopWaitTime` (60); to write your own entirely, `embeddedLaunchScript` (SBR p.537-538). At runtime, via environment variables or a `.conf` file (same name as the jar, with `.conf`, next to it; `CONF_FOLDER` changes the location): `MODE` (`auto` tries to detect whether it is an init script by being a symbolic link in `init.d`; `service` enables stop|start|status|restart; `run` executes in the foreground), `RUN_AS_USER`, `USE_START_STOP_DAEMON`, `PID_FOLDER` (`/var/run`), `LOG_FOLDER` (`/var/log`), `CONF_FOLDER`, `LOG_FILENAME`, `APP_NAME`, `RUN_ARGS`, `JAVA_HOME`, `JAVA_OPTS`, `JARFILE`, `DEBUG` (turns on `-x` in the shell) and `STOP_WAIT_TIME` (60 s); `JARFILE` and `APP_NAME` are not configured through the `.conf`; `PID_FOLDER`, `LOG_FOLDER` and `LOG_FILENAME` only apply to init.d (SBR p.538-540). Example `myapp.conf`: `JAVA_OPTS=-Xmx1024M` and `LOG_FOLDER=/custom/log/folder` (SBR p.540). Windows service: `winsw` with an example maintained separately (SBR p.540).
