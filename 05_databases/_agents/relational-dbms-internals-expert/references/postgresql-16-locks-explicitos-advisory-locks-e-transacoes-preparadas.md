# PostgreSQL 16: table and row locks, `LOCK`, deadlocks, advisory locks and prepared transactions (two-phase commit)

> Pages = PDF of the PG16 manual (16.15); printed = N − 38. Section 13.3 (Explicit Locking) = PDF 531-537; **13.4.2 (explicit locks for consistency), 13.5 (serialization failures) and 13.6 (caveats) = PDF 538-539**; `LOCK` = PDF 1972-1974; `SELECT ... FOR UPDATE` (locking clause) = PDF 2030; `PREPARE TRANSACTION` = PDF 1989-1990; `COMMIT PREPARED` = PDF 1695; `ROLLBACK PREPARED` = PDF 2008; transaction identifiers and GID = PDF 2577. The overview of MVCC and isolation is in `postgresql-16-mvcc-e-niveis-de-isolamento.md` (section 7 points here). `[derived]` = calculation made in the package.

## 1. Table locks [from source] (PG16 p.531-534)
- They exist for concurrency control when MVCC does not give the desired behavior; most commands automatically acquire the appropriate lock (for example `TRUNCATE` takes `ACCESS EXCLUSIVE`). The `pg_locks` view lists the pending locks (PG16 p.531).
- **All modes are table-level locks, even those with "ROW" in the name** (the names are historical); the only difference between the modes is the set of modes they conflict with (Table 13.2). Two transactions cannot hold conflicting modes on the same table, but **a transaction never conflicts with itself**. Some modes are self-conflicting (an `ACCESS EXCLUSIVE` can be held by only one transaction), others are not (`ACCESS SHARE`) (PG16 p.531-532).
- Modes and who acquires them (PG16 p.532-533):
  - `ACCESS SHARE`: `SELECT` and any query that only reads; conflicts only with `ACCESS EXCLUSIVE`.
  - `ROW SHARE`: `SELECT ... FOR UPDATE/NO KEY UPDATE/SHARE/KEY SHARE`; conflicts with `EXCLUSIVE` and `ACCESS EXCLUSIVE`.
  - `ROW EXCLUSIVE`: `UPDATE`, `DELETE`, `INSERT`, `MERGE`; conflicts with `SHARE`, `SHARE ROW EXCLUSIVE`, `EXCLUSIVE`, `ACCESS EXCLUSIVE`.
  - `SHARE UPDATE EXCLUSIVE`: `VACUUM` (without `FULL`), `ANALYZE`, `CREATE INDEX CONCURRENTLY`, `CREATE STATISTICS`, `COMMENT ON`, `REINDEX CONCURRENTLY` and certain forms of `ALTER INDEX`/`ALTER TABLE`; protects against concurrent schema changes and VACUUM runs; it is self-conflicting.
  - `SHARE`: `CREATE INDEX` (without `CONCURRENTLY`); protects against concurrent data changes (conflicts with `ROW EXCLUSIVE`).
  - `SHARE ROW EXCLUSIVE`: `CREATE TRIGGER` and some forms of `ALTER TABLE`; self-exclusive.
  - `EXCLUSIVE`: `REFRESH MATERIALIZED VIEW CONCURRENTLY`; only allows concurrent `ACCESS SHARE` (read-only continues).
  - `ACCESS EXCLUSIVE`: `DROP TABLE`, `TRUNCATE`, `REINDEX`, `CLUSTER`, `VACUUM FULL`, `REFRESH MATERIALIZED VIEW` (without `CONCURRENTLY`) and many forms of `ALTER TABLE`/`ALTER INDEX`; **it is the default mode of `LOCK TABLE`** without an explicit mode; guarantees total exclusivity. **Only an `ACCESS EXCLUSIVE` blocks a plain `SELECT`** (without FOR UPDATE/SHARE).
- A lock normally lasts **until the end of the transaction**; if acquired after a `SAVEPOINT`, it is released if there is a `ROLLBACK TO` that savepoint; the same holds for a PL/pgSQL `EXCEPTION` block (PG16 p.533).
- `[inference]` since `ACCESS EXCLUSIVE` conflicts with everything, a DDL that requests it waits in the queue behind a long transaction that only read the table and, while it waits, new queries on the table queue up behind it; the manual describes the conflicts (Table 13.2, p.533-534), but **does not explicitly describe the queueing effect**.

## 2. `LOCK TABLE` [from source] (PG16 p.1972-1973)
- `LOCK [TABLE] [ONLY] name [*] [, ...] [IN mode MODE] [NOWAIT]`; **without a mode, uses `ACCESS EXCLUSIVE`**; waits for conflicting locks, or with `NOWAIT` aborts with an error if it cannot obtain it immediately; **there is no `UNLOCK TABLE`**: the lock holds until the end of the transaction; outside a transaction block it is an error (useless). On a view, it recursively locks the relations in the definition. Listed tables are locked **one by one, in the written order**. Without `ONLY`, it includes the descendant tables (PG16 p.1972-1973).
- Manual usage: in Read Committed, `LOCK TABLE ... IN SHARE MODE` before querying guarantees there are no pending writes and none can start; in Repeatable Read/Serializable, the `LOCK` must come **before any SELECT or DML**, because the view freezes at the first command; if the transaction is going to modify the table, use `SHARE ROW EXCLUSIVE` (and not `SHARE`) to avoid deadlock between two transactions that took `SHARE` and want `ROW EXCLUSIVE` (PG16 p.1972). To avoid deadlocks: obtain locks on the same objects in the same order and, when there are several modes for an object, **the most restrictive first** (PG16 p.1972).
- Permissions: with `UPDATE`, `DELETE` or `TRUNCATE` on the table, any mode; with `INSERT`, up to `ROW EXCLUSIVE`; with `SELECT`, `ACCESS SHARE` (PG16 p.1973).

## 3. Row locks [from source] (PG16 p.534-535, p.2030)
- Four modes: **`FOR UPDATE`** (prevents others from locking, modifying or deleting **while the lock lasts; it is not a guarantee for after the owner's commit/rollback, see the caveat in section 3a (PG16 p.538)**; also acquired by `DELETE` and by `UPDATE` that changes columns with a unique index usable in a foreign key), **`FOR NO KEY UPDATE`** (weaker: does not block `FOR KEY SHARE`; acquired by `UPDATE` that does not acquire `FOR UPDATE`), **`FOR SHARE`** (shared lock: blocks UPDATE/DELETE/FOR UPDATE/FOR NO KEY UPDATE, but not another SHARE or KEY SHARE) and **`FOR KEY SHARE`** (the weakest: blocks `DELETE` and `UPDATE` that change a key, but not the others). Conflicts in Table 13.3 (PG16 p.534-535).
- Row locks **do not affect reading** (they only block writers and lockers of the same row). In `REPEATABLE READ`/`SERIALIZABLE`, an error occurs if the row to be locked was changed since the transaction started (PG16 p.534).
- **There is no limit on locked rows**, because PostgreSQL does not keep that information in memory, **but locking a row can cause a disk write** (`SELECT FOR UPDATE` modifies the rows to mark them) (PG16 p.535). Page locks (shared/exclusive) protect buffer pages and are released right after the row is read/written (PG16 p.535).
- `SELECT ... FOR ... [OF table] [NOWAIT | SKIP LOCKED]`: **`NOWAIT`** raises an error instead of waiting; **`SKIP LOCKED`** skips rows already locked: it gives an **inconsistent view**, is not suited for general work, but serves to reduce contention among several consumers of a **queue table**; both apply only to the **row** lock, and the `ROW SHARE` table lock is taken normally (to avoid waiting for it, do `LOCK ... NOWAIT` first) (PG16 p.2030). `WITH TIES` does not accept `SKIP LOCKED` (PG16 p.2029).

## 3a. FOR UPDATE is not enough as a guarantee that "nobody changes the row": 13.4.2, 13.5, 13.6 and 13.7 [from source] (PG16 p.538-540)
- **`SELECT FOR UPDATE`, `SELECT FOR SHARE` and `LOCK TABLE`: when to use** (PG16 p.538): with non-serializable writes, to guarantee the current validity of a row and protect it from concurrent updates you need `SELECT FOR UPDATE`, `SELECT FOR SHARE` or an appropriate `LOCK TABLE`; the first two lock only the rows returned, `LOCK TABLE` locks the whole table. The manual highlights this for those porting applications from other DBMSs.
- **`SELECT FOR UPDATE`: exact caveat** (PG16 p.538): `SELECT FOR UPDATE` **does not guarantee** that a concurrent transaction will not update or delete the selected row. To have that guarantee in PostgreSQL you must **actually update the row (UPDATE), even if no value changes**. `FOR UPDATE` only **temporarily blocks** other transactions that try to obtain the same lock or run an `UPDATE`/`DELETE` that would affect the row; when the lock-owning transaction commits or rolls back, the transaction that was blocked **proceeds with the conflicting operation**, unless a real UPDATE of the row was done while the lock was active. `[inference]` short answer: `FOR UPDATE` suffices for mutual exclusion **during** the owning transaction, but does **not** prevent change/removal by whoever was waiting after the lock ends; for that, do the real UPDATE.
- **Global validations under non-serializable MVCC** (PG16 p.538): two successive `SELECT sum(...)` queries in Read Committed are **not reliable**, because the second tends to include transactions that the first did not count. Both sums in a single Repeatable Read transaction give an exact picture only of the effects committed **before the start** of the transaction (and the result may already be stale when delivered); if the RR transaction itself had already made changes, the check becomes even more debatable. Whoever needs an "indisputable picture of the present" can lock all the tables involved; a `SHARE` lock (or stronger) guarantees there are no uncommitted changes in the table other than those of the current transaction.
- **Explicit locks in Repeatable Read** (PG16 p.538): to rely on an explicit lock against concurrent changes, use Read Committed or, in RR, **obtain the locks before querying**. A lock obtained in RR guarantees that no transaction modifying the table is still running, but the snapshot may predate already committed changes if it was taken before the lock. The RR snapshot is frozen at the **first** `SELECT`, `INSERT`, `UPDATE`, `DELETE` or `MERGE` of the transaction, so it is possible to lock before that.
- **13.5, serialization failures** (PG16 p.538-539): Repeatable Read and Serializable can raise errors that avoid anomalies; the application must be ready to **retry** the transaction; the SQLSTATE is always `40001` (`serialization_failure`). It may also be worth retrying `40P01` (`deadlock_detected`) and, in some cases, `23505` (`unique_violation`) and `23P01` (`exclusion_violation`): for example, when the application chooses the new primary key by looking at the current keys and another instance chooses the same; it is effectively a serialization failure, but the server does not detect it as such because it does not "see" the link between the read and the inserted value (and there are corner cases in which it returns a uniqueness error even though it has information to know it is a serialization failure).
- **How to retry** (PG16 p.539): it is recommended to retry `40001` unconditionally; the other codes require more care, since they may indicate a persistent rather than transient error. Retry the **complete transaction**, including the logic that decides which SQL to issue and which values to use; that is why PostgreSQL **does not offer automatic retry** (it could not guarantee correctness). Retrying does not guarantee success: it may need several attempts, many under high contention; with a conflicting prepared transaction, there may be no progress until it commits or rolls back.
- **13.6 TRUNCATE on hot standby (Serializable, catalogs, hash)**: (a) Serializable does **not** exist on the standby: the strictest is Repeatable Read, which may see a transient state inconsistent with any serial execution on the primary; (b) a `TRUNCATE` committed on the primary is **not MVCC-safe**: a Repeatable Read transaction with an earlier snapshot that has not yet touched the table will see it empty; whoever already touched it holds `ACCESS SHARE` and blocks the DDL; (c) internal catalog access ignores the transaction's isolation, so a new object may become visible, but not its rows or explicit catalog queries; (d) a hash index has a bucket lock and **can** deadlock, unlike B-tree/GiST/SP-GiST (PG16 p.539, details in items 13.6 and 13.7 below).
- **13.6 TRUNCATE and rewriting ALTER TABLE are not MVCC-safe**: `TRUNCATE` and the forms of `ALTER TABLE` that rewrite the table are **not MVCC-safe**: after the commit, whoever has an earlier snapshot that did not touch the table before the DDL sees it empty (whoever touched it before holds at least `ACCESS SHARE`, which blocks the DDL until it finishes). It does not cause apparent inconsistency between successive queries on the same table, but can cause visible inconsistency between the table and the other tables of the database (PG16 p.539). `[inference]` in a Repeatable Read report, a `TRUNCATE` committed on the primary (and replicated to the standby) can indeed appear as an empty table if the report had not yet touched it; "never causes inconsistency" is false.
- **13.6 Serializable is not supported on hot standby**: the strictest level supported on the standby is Repeatable Read, which there can see a transient state inconsistent with any serial execution on the primary; doing all permanent writes in Serializable on the primary guarantees that the standbys reach a consistent state (PG16 p.539).
- **13.6 internal catalog access and concurrent `CREATE TABLE`**: internal catalog access does not use the transaction isolation level: **new objects (for example, a table created by a concurrent transaction) become visible to Repeatable Read and Serializable transactions, although the rows they contain do not**; queries that examine the catalogs explicitly (a direct `SELECT` on the catalog tables) **do not see** the rows of concurrently created objects at those levels (PG16 p.539). `[inference]` therefore "a concurrent `CREATE TABLE` does not appear at all" is false: the table may be seen through the internal path, but not by explicit catalog queries, and its content is not visible.
- **13.7 locks and indexes (hash vs. B-tree, deadlock)**: non-blocking read/write access to table data does not exist for every index method (PG16 p.539). **B-tree, GiST and SP-GiST**: shared/exclusive **page-level, short-term** locks, released right after each index row is read or inserted; they give the **highest concurrency and no deadlock conditions**. **Hash indexes**: shared/exclusive **bucket-level** locks, released only after the whole bucket is processed; better concurrency than whole-index locking, but **deadlock is possible**, since the locks last longer than one index operation; so hash and B-tree do NOT have the same guarantee of no deadlock (PG16 p.539). **GIN** (p.540): short-term page locks, but inserting a value indexed by GIN usually generates several key insertions per row, so it can be a lot of work for a single value. Today **B-tree** has the best performance for concurrent applications and, since it has more features than hash, is the recommended one for scalar data; for non-scalar data use GiST, SP-GiST or GIN (PG16 p.540).
- **13.7, locks and indexes** (PG16 p.539-540): non-blocking read/write access to table data does not exist for every index method. **B-tree, GiST and SP-GiST**: shared/exclusive **page-level, short-term** locks, released right after each index row is read or inserted; they give the **highest concurrency and no deadlock conditions**. **Hash indexes**: shared/exclusive **bucket-level** locks, released only after the whole bucket is processed; better concurrency than whole-index locking, but **deadlock is possible**, since the locks last longer than one index operation (hash vs. deadlock: B-tree and hash do NOT have the same guarantee). **GIN** (p.540): short-term page locks, but inserting a value indexed by GIN usually generates several key insertions per row, so it can be a lot of work for a single value. Today **B-tree** has the best performance for concurrent applications and, since it has more features than hash, is the recommended one for scalar data; for non-scalar data use GiST, SP-GiST or GIN (PG16 p.540).

## 4. Deadlocks [from source] (PG16 p.535-536)
- Using explicit locks increases the chance of deadlock, but **deadlocks also occur through row locks without explicit locks** (for example, two transactions updating the same two accounts in reverse order). PostgreSQL detects it and **aborts one of the transactions**; which one is unpredictable and must not be assumed (PG16 p.535).
- The best defense: **acquire locks in a consistent order** and make the first lock on an object **the most restrictive mode needed**; if not feasible, handle it with **retry** of the transactions aborted by deadlock. Without a detected deadlock, a transaction waits **indefinitely** for conflicting locks, so it is a bad idea to keep transactions open for a long time (e.g. waiting for user input) (PG16 p.536). The check only occurs after `deadlock_timeout` (default 1 s) (PG16 p.715).
- `[inference]` combining `lock_timeout` (default 0, PG16 p.708) with retry bounds the wait, but **a lock timeout is not the same as a deadlock** (one is a long wait, the other is a wait cycle).

## 5. Advisory locks [from source] (PG16 p.536-537)
- Locks with **application-defined meaning**; the system does not enforce their use: it is up to the application to use them correctly. Useful for strategies that fit MVCC poorly, such as emulating **pessimistic locking** of "flat file" systems; the manual says that, compared with a flag in a table, advisory locks are **faster, avoid table bloat and are cleaned up automatically at the end of the session** (PG16 p.536).
- **Two forms**: **session**-level (held until explicit release or end of the session; **they do not respect transactional semantics**: a lock obtained in a transaction that rolls back is still held, and the unlock holds even if the transaction fails later; the same process can acquire it several times, requiring one unlock for each) and **transaction**-level (released automatically at the end of the transaction; **there is no explicit unlock**; more convenient for short-lived use). The two levels for the same identifier block each other; if the session already has the lock, its new requests **always succeed**, even with other sessions waiting (PG16 p.536). They appear in `pg_locks`.
- **Shared memory**: advisory locks and ordinary locks use the same shared memory pool (sized by `max_locks_per_transaction` and `max_connections`); exhausting it prevents the server from granting **any** locks; this imposes a ceiling on advisory locks, typically **tens to hundreds of thousands** depending on the configuration (PG16 p.536).
- **`LIMIT` trap**: `SELECT pg_advisory_lock(id) FROM foo WHERE id > 12345 LIMIT 100;` is **dangerous**, because `LIMIT` is not guaranteed to be applied before the lock function is executed; unexpected locks can remain "hanging" (visible in `pg_locks`) until the end of the session. The safe form is a subquery with the `LIMIT` and, outside, `pg_advisory_lock(q.id)` (PG16 p.536-537).
- **In recovery/hot standby**: advisory locks work normally (including deadlock detection), are **never recorded in the WAL** and hold only on the server where they were obtained; it is not possible to obtain one on the primary and have it replicated to the standby (PG16 p.833-834).

## 6. Business rule consistency in the application [from source] (PG16 p.537)
- Enforcing integrity rules with Read Committed is very hard (the view changes at every command, and even one command may leave the snapshot in case of a write conflict). With Repeatable Read, there is the subtle problem of **read/write conflicts**; Serializable transactions are Repeatable Read with non-blocking monitoring of dangerous patterns, and one of those involved is rolled back to break the cycle (PG16 p.537).
- If Serializable is used on **all writes and reads that need a consistent view**, no other effort is needed for consistency; the manual recommends frameworks that **retry** transactions with serialization failure, and considering `default_transaction_isolation = serializable` and checking the level in triggers to prevent another level from being used and bypassing integrity (PG16 p.537). **Warning**: this protection **does not extend to hot standby or logical replicas**; for those, use Repeatable Read and explicit locks on the primary (PG16 p.537, p.835).
- Performance tips for Serializable (PG16 p.531): declare transactions `READ ONLY` when possible; control the number of connections (pool); do not put more in a transaction than necessary; do not leave "idle in transaction" connections (`idle_in_transaction_session_timeout`); eliminate `SELECT FOR UPDATE/SHARE` and explicit locks that have become unnecessary; page predicate locks are promoted to relation level when memory runs short (increase `max_pred_locks_per_transaction`, `max_pred_locks_per_relation` and/or `max_pred_locks_per_page`); **a seq scan always requires a relation-level predicate lock**, increasing serialization failures (it can help to favor index scans by lowering `random_page_cost` or raising `cpu_tuple_cost`).

## 7. Prepared transactions (two-phase commit) [from source]
- **`PREPARE TRANSACTION 'gid'`** (PG16 p.1989-1990): prepares the current transaction for two-phase commit. After it, the transaction is **no longer associated with the session** and its state is **fully written to disk**, with "very high probability" of being committable even after a crash; for the session, it is similar to a `ROLLBACK` (there is no active transaction and the effects stay invisible until the commit); if it fails for any reason, it becomes `ROLLBACK`. The identifier (GID) is a string literal of **fewer than 200 bytes**, unique among prepared transactions (PG16 p.1989; GID "up to 200 bytes" on p.2577). It must be used **inside a transaction block**. It cannot prepare a transaction that touched **temporary tables**, created **WITH HOLD cursors** or executed `LISTEN`, `UNLISTEN` or `NOTIFY`; `SET` without `LOCAL` persists even afterwards (PG16 p.1989). The manual says it is **not for use in applications or interactive sessions**: it serves **external transaction managers** (for example X/Open XA) for atomic global transactions across databases; if you are not writing a manager, you probably should not use it (PG16 p.1989, p.1990, p.1695).
- **`COMMIT PREPARED 'gid'`** (PG16 p.1695) and **`ROLLBACK PREPARED 'gid'`** (PG16 p.2008): only the **same user** who ran the transaction or a **superuser**; it **need not be the same session**; they **cannot be executed inside a transaction block**; the action is immediate. Prepared transactions appear in the **`pg_prepared_xacts`** view; the GID-to-xid mapping too (PG16 p.1695, p.2577). In hot standby these commands raise an error and `pg_prepared_xacts` is empty during recovery (PG16 p.829, p.833).
- **Manual warning** (PG16 p.1990): leaving transactions in the prepared state for a long time is **imprudent**: they **prevent VACUUM from reclaiming space** and, in extreme cases, can lead the database to **shut down to avoid XID wraparound**; they **keep holding the locks**. The intended use is to commit/roll back as soon as the external manager verifies that the other databases are also prepared. **If you do not have an external manager that tracks the prepared transactions, keep the feature disabled with `max_prepared_transactions = 0`** (the default), preventing them from being created and forgotten (PG16 p.654, p.1990). In wraparound, the manual says to resolve old prepared transactions (PG16 p.794-795).
- **Synchronous replication**: in two-phase commit, both the prepare and the commit wait for confirmation from the synchronous standbys (PG16 p.824).
- `[inference]` `COMMIT PREPARED` or `ROLLBACK PREPARED` is a **business decision** that depends on the state of the distributed transaction coordinator: committing blindly can diverge from the other participants. Running each command outside a transaction block, one by one, with the transaction's owner or a superuser, and checking afterwards that `pg_prepared_xacts` has emptied, is what follows from PG16 p.1695 and p.2008; **it is not possible to "commit all atomically"** (each command acts on one GID) `[inference]`.

## 8. Transaction identifiers [from source] (PG16 p.2577)
- Each transaction has a `VirtualTransactionId` (backend ID + local number, e.g. `4/12532`); the real XID (`xid`, 32 bits, wraps around every 4 billion; there is a 64-bit `xid8` with epoch) is only assigned when the transaction **writes for the first time**; read-only transactions have only a vxid. `pg_locks` shows `virtualxid` and `transactionid`; row locks are recorded in the rows themselves (inspectable with the `pgrowlocks` extension) and may require multixact IDs (PG16 p.2577).

## 8a. The `pg_locks` view: object types and columns [from source] (PG16 p.2357-2359)
- **`pg_locks`, granularity** (PG16 p.2357): one row per **lockable object, requested lock mode and relevant process**; the same object can appear several times, and an object without locks does not appear. Lockable object types: whole relations, pages, tuples, transaction IDs (virtual and permanent), general database objects (class + OID), the right to **extend a relation**, the right to update `pg_database.datfrozenxid` and **advisory** locks on numbers with user-defined meaning.
- **`locktype`** (PG16 p.2357): 12 values: `relation`, `extend`, `frozenid`, `page`, `tuple`, `transactionid`, `virtualxid`, `spectoken`, `object`, `userlock`, `advisory` and `applytransaction` (see also Table 28.11).
- **`database`, `relation`, `page` and `tuple`** (PG16 p.2357): `database` = OID of the database, zero if the target is a shared object, **NULL** if the target is a transaction ID; `relation` = NULL if the target is neither a relation nor part of one; `page` = NULL if the target is not a relation page or tuple; `tuple` = NULL if the target is not a tuple.
- **`virtualxid` and `transactionid`** (PG16 p.2357): NULL if the target is not, respectively, a virtual or permanent transaction ID.
- **`classid`, `objid` and `objsubid`** (PG16 p.2358): identify a general database object (catalog, OID and column number); NULL if the target is not a general object (`objsubid` zero for another general object).
- **`pid`, `virtualtransaction`, `mode`, `granted`, `fastpath` and `waitstart`** (PG16 p.2358): `virtualtransaction` = virtual ID of the holder or waiter; `pid` = **NULL if the lock belongs to a prepared transaction**; `granted` true = held, false = waiting (which implies that another process holds or awaits a conflicting mode); `fastpath` true = taken via the fast path, false = via the main lock table; `waitstart` = start of the wait, NULL if held (may be NULL for moments even with `granted` false).
- **View behavior** (PG16 p.2358): a process waits for at most one lock at a time; every transaction holds an exclusive lock on its virtual ID and, if it received a permanent ID (generally only when changing the database state), also on the permanent one until it ends; to wait for another transaction to finish, it requests a **shared** lock on its ID, granted only when it ends. Although tuples are lockable, **row locks are on disk, not in memory, and normally do not appear in the view**; whoever waits for a row lock usually appears waiting for the **permanent transaction ID** of its holder.
- **Advisory lock key and speculative insertion** (PG16 p.2358): a speculative insertion lock has a transaction ID + token (shown in `objid`); the `bigint` key of an advisory lock appears with the high half in `classid`, the low half in `objid` and `objsubid` = 1 (reassemblable with `(classid::bigint << 32) | objid::bigint`); two-integer key: first key in `classid`, second in `objid` and `objsubid` = 2 (PG16 p.2359); the meaning of the keys is up to the user and advisory locks are local to each database, so the `database` column is significant (PG16 p.2359).
- **`applytransaction`** (PG16 p.2359): locks used in the parallel mode of logical replication to apply a transaction; the remote transaction's ID appears in `transactionid`; `objsubid` = 0 for the lock that synchronizes the change set and 1 for the lock that waits for the end of the transaction (guarantees commit order).
- `[derived]` practical effect: a row with `granted = false` and `locktype = transactionid` indicates a wait for the end of another transaction (including because of a row lock).

## 9. [extrapolation] and what the sources do NOT say
- The manual provides no script for "diagnosing blocking in production" beyond pg_locks and pg_stat_activity; diagnostic queries (joining the two views via the pg_blocking_pids function) are common practice, but here they are `[extrapolation]`. The wait_event_type column with value Lock appears in PG16 p.844.
- No number for a "safe limit" of locks per transaction beyond the default of 64 for `max_locks_per_transaction` (PG16 p.715).
