# ASVS V6 Stored cryptography, V7 Errors and logging, V8 Data protection (ASVS p.42-49)

Source: ASVS 4.0.3. `L1/L2/L3` = required at each level; `-` = not required. **Privacy/LGPD**: V8.3 touches on privacy, but privacy engineering and legal compliance belong to the `privacy-lgpd-engineering-expert` agent; here only the ASVS technical requirement.

## V6 — Stored cryptography (ASVS p.42-43)
- [from source] Objectives: cryptographic modules fail securely and errors are handled; adequate RNG; key access managed securely (ASVS p.42).
- [from source] V6.2 and V6.4 are not easily pentestable and L1 is missing from most items, but **developers should consider the entire sections mandatory** (ASVS p.42-43). Algorithms that are secure today may stop being so: it must be possible to swap algorithms (ASVS p.42).

| Section | Requirements (paraphrase) | Levels | Page |
|---|---|---|---|
| V6.1 classification | private data/PII, health and regulated financial data encrypted at rest (V6.1.1-V6.1.3); always perform a privacy impact assessment to classify (section text) | L2/L3 | ASVS p.42 |
| V6.2 algorithms | V6.2.1 cryptographic modules fail securely, no padding oracle (**L1**); V6.2.2 approved algorithms/modes/libraries, not home-grown crypto; V6.2.3 IV/cipher/modes configured securely; V6.2.4 algorithms, key sizes and rounds **reconfigurable/replaceable at any time**; V6.2.5 **no** ECB, PKCS#1 v1.5, small block ciphers (3DES, Blowfish) and weak hashes (MD5, SHA-1), except for backward compatibility; V6.2.6 nonces/IVs never repeated with the same key | L1 only V6.2.1; V6.2.2-6: L2/L3 | ASVS p.42-43 |
| V6.2 (L3) | V6.2.7 encrypted data authenticated (signature, authenticated mode, HMAC); V6.2.8 cryptographic operations in constant time | L3 only | ASVS p.43 |
| V6.3 randomness | V6.3.1 unguessable values (numbers, file names, GUIDs, strings) generated by the **approved CSPRNG**; V6.3.2 GUID v4 with CSPRNG; V6.3.3 (L3) adequate entropy under load or graceful degradation | L2/L3; V6.3.3 L3 only | ASVS p.43 |
| V6.4 secret management | V6.4.1 secret management solution (key vault) to create/store/control/destroy; V6.4.2 key material not exposed to the application (isolated module/vault) | L2/L3 | ASVS p.43 |
- [from source] Section V6.3 explains that a true PRNG is very hard: entropy sources are exhausted if overused and poor sources generate predictable keys (ASVS p.43).
- References (ASVS p.43): Testing Guide (weak cryptography), Cryptographic Storage Cheat Sheet, FIPS 140-2.
- The book does **not** mention Argon2/scrypt; PBKDF2/bcrypt only in V2.4 (see `references/asvs-v2-autenticacao.md`).

## V7 — Error handling and logging (ASVS p.44-46)
- [from source] The goal is not to generate many logs, but **high-quality logs**, with more signal than noise; high-quality logs often contain sensitive data and must be protected under local laws: do not collect/log sensitive data unnecessarily, protect according to classification and **do not keep forever** (absolute lifetime as short as possible) (ASVS p.44). Applications must fail securely and errors must not reveal unnecessary information (ASVS p.44).
- [from source] V7.1 and V7.2 cover OWASP Top 10 2017:A10, are **not pentestable**: developers must comply with everything as if it were L1; testers validate through interview, screenshots or attestation (ASVS p.44-45).

| Section | Requirements | Levels | Page |
|---|---|---|---|
| V7.1 content | V7.1.1 **do not log credentials or payment data; session tokens only in irreversible hashed form**; V7.1.2 do not log other sensitive data under local laws/policy (both L1); V7.1.3 record relevant events (authentication OK/failure, access control failures, deserialization and input validation failures); V7.1.4 each event with information to reconstruct the timeline | V7.1.1-2 L1/L2/L3; V7.1.3-4 L2/L3 | ASVS p.44 |
| V7.2 processing | V7.2.1 all authentication decisions logged (without tokens/passwords); V7.2.2 all access control decisions loggable and failures logged | L2/L3 | ASVS p.45 |
| V7.3 protection | V7.3.1 logging components encode data against **log injection**; V7.3.3 security logs protected against unauthorized access/modification; V7.3.4 clocks synchronized (and consider UTC) | L2/L3 | ASVS p.45 |
| V7.4 errors | V7.4.1 **generic** message on unexpected/sensitive error, possibly with a unique ID for support (**L1**); V7.4.2 exception handling (or equivalent) across the whole codebase; V7.4.3 "last resort" handler that catches unhandled exceptions | V7.4.1 L1/L2/L3; V7.4.2-3 L2/L3 | ASVS p.46 |
- [from source] Note: log encoding (V7.3.1) is hard to test dynamically; architects, developers and reviewers should treat it as L1 (ASVS p.45). Logs that can be altered/removed are useless in investigations and prosecutions; disclosure exposes internal details (ASVS p.45). V7.3.2 was removed (ASVS p.45).
- [from source] Note: languages such as Swift and Go (and many functional ones) have no exceptions or last-resort handlers; use an equivalent pattern/framework to handle exceptional events (ASVS p.46).
- References (ASVS p.46): Testing Guide (error handling), error messages section of the Authentication Cheat Sheet.
- Review (`[inference]`): `ocrg_lint.py` flags ERR-*, LOG-PASSWORD; OCRG: `references/ocrg-logging-erros-alertas-e-defesa-ativa.md`.

## V8 — Data protection (ASVS p.47-49)
- [from source] Three elements: confidentiality, integrity and availability (CIA); the standard assumes protection on a trusted system (hardened server) and that **user devices are compromised**: whatever is stored on them must be encrypted and hard to obtain/alter (ASVS p.47).

| Section | Requirements | Levels | Page |
|---|---|---|---|
| V8.1 general | V8.1.1 sensitive data not cached in load balancers/application caches; V8.1.2 temporary copies protected or purged; V8.1.3 minimize request parameters (hidden fields, cookies, headers); V8.1.4 detect/alert on abnormal request volume (per IP, user, hour/day); V8.1.5 regular backups with restore testing; V8.1.6 backups stored securely | L2/L3; V8.1.5-6 L3 only | ASVS p.47 |
| V8.2 client | V8.2.1 sufficient anti-cache headers; V8.2.2 browser storage (localStorage, sessionStorage, IndexedDB, cookies) without sensitive data; V8.2.3 authenticated data removed from client storage after the session ends | L1/L2/L3 | ASVS p.47 |
| V8.3 private data | V8.3.1 sensitive data in the HTTP body/headers, **never in the query string**; V8.3.2 user can remove/export their data; V8.3.3 clear language about collection/use and **opt-in**; V8.3.4 sensitive data identified and policy defined (L1/L2/L3); V8.3.5 access to sensitive data audited (without logging the data); V8.3.6 sensitive data in memory overwritten as soon as possible; V8.3.7 data to be encrypted uses algorithms that provide confidentiality **and** integrity; V8.3.8 retention: old data deleted by classification | V8.3.1-4 L1/L2/L3; V8.3.5-8 L2/L3 | ASVS p.48 |
- [from source] V8.3 protects against unauthorized creation/reading/updating/removal, especially in volume; compliance implies compliance with V4 (V4.2.1, on ASVS p.36). Privacy laws (APP-11, GDPR) affect the implementation and the book says to consult local laws and a specialist; core criterion: detect, deter or, preferably, block abnormal mass actions; "abnormal" depends on the threat model and business risk (ASVS p.48).
- References (ASVS p.49): Security Headers, Secure Headers Project, OWASP Privacy Risks, User Privacy Protection Cheat Sheet, GDPR, Internet Privacy Engineering Network.
