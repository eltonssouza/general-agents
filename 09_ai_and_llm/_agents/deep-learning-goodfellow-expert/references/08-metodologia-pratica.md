## 1. Design process (DLB p.436-437)
1. Determine the **goals**: error metric and target value, guided by the problem.
2. Establish an **end-to-end** *pipeline* as early as possible, with an estimate of the metrics.
3. **Instrument** to find bottlenecks: diagnose whether it is overfitting, underfitting or a data/software defect.
4. Make **incremental changes** (collect data, tune hyperparameters, change algorithm) based on specific findings.
- `[from source]` (DLB p.436) In practice, you do much better by correctly applying a common algorithm than by carelessly applying an obscure one.
- `[from source]` (DLB p.437) Running example: transcribing Street View address numbers to add buildings to Google Maps.

## 2. Metrics (DLB p.437-439)
- `[from source]` The **Bayes error** is the minimum achievable error even with infinite data (incomplete features, stochasticity, finite data); it is generally impossible to reach zero (p.437). The metric differs from the training cost function (p.438).
- `[from source]` **Asymmetric** costs (in spam, blocking a legitimate message is worse than letting spam through) call for total cost instead of error rate (p.438). For rare events (a disease in 1 million), a classifier that always answers "absent" has 99.9999% accuracy: use **precision** (fraction of detections that are correct) and **recall** (fraction of true events detected); "nobody has it" gives perfect precision and zero recall, "everybody has it" gives perfect recall and precision equal to the prevalence (p.438).
- `[from source]` PR curve sweeping the threshold; **F = 2pr/(p + r)** (eq. 11.1) or the area under the PR curve (p.439). The system may **refuse to decide** (a human takes over): **coverage** metric (fraction of examples on which it answers); coverage is traded for accuracy; Street View goal: human-level accuracy (98%) with **95% coverage** (p.439). Define the metric beforehand and focus on it (p.439). `scripts/dlb_calc.py metrics`.

## 3. Baseline models (DLB p.440-441)
- `[from source]` If a few linear weights solve the problem, start with a simple statistical model (logistic regression); for "AI-complete" problems (object recognition, speech, translation), start with an appropriate deep learning model (p.440).
- `[from source]` **Fixed-size vector** inputs: fully connected feedforward network; input with **topology** (image): CNN; **sequence**: LSTM or GRU; piecewise linear units (ReLU, Leaky ReLU, PReLU, maxout) (p.440).
- `[from source]` Reasonable optimizer: SGD with momentum and a decaying learning rate (linearly to a minimum, exponentially, or dividing by a factor of 2 to 10 when validation plateaus) or Adam (p.440). *Batch normalization* can be left out of the first baseline, but should come in quickly if optimization is problematic, especially in CNNs and in networks with sigmoidal nonlinearities (p.440).
- `[from source]` Unless training has tens of millions of examples, include mild regularization from the start; **early stopping** should be used almost universally; dropout is excellent and compatible with many models; batch normalization sometimes makes dropout unnecessary (p.440).
- `[from source]` If the task resembles another well-studied one, copy the model and algorithm that already work (or the trained model; for example, features from a CNN trained on ImageNet, Girshick 2015) (p.441). Unsupervised learning: helps a lot in NLP (word embeddings); in vision only in semi-supervised settings with few labels; include it in the first baseline only if the domain demands it (p.441). `[DATED]` The book admits that "better default algorithms" appear quickly (p.440).

## 4. Collect more data? (DLB p.441-442)
- `[from source]` For newcomers, it is tempting to try many algorithms; it is often **better to collect more data** than to improve the algorithm (p.441).
- `[from source]` Flow: (a) if **training** performance is poor, the algorithm is not using the data it already has: **do not collect more data**; enlarge the model (layers, units), improve the algorithm (tune the learning rate); if large, well-optimized models fail, the problem may be **data quality** (noise, wrong inputs): start over with cleaner data or more *features* (p.441). (b) If training is acceptable, measure **test**: if acceptable, nothing to do; if much worse than training, collecting data is one of the most effective solutions, weighing cost and feasibility (internet companies: almost always; medicine: may be infeasible); alternatives: shrink the model or improve regularization (weight decay, dropout); if the gap persists after tuning regularization, collect more data (p.442).
- `[from source]` How much to collect: error versus training set size curves (like Fig. 5.4) and extrapolation; adding a small fraction of the examples does not noticeably change the error; experiment on a **logarithmic scale** (doubling the number of examples between experiments). With no way to collect more data, improving the algorithm becomes research, "not advice for applied practitioners" (p.442).

## 5. Hyperparameters (DLB p.442-451)
- `[from source]` Goal of manual tuning: **match the effective capacity** to the complexity of the task, which depends on three factors: representational capacity, the algorithm's ability to minimize the cost, and degree of regularization (p.443). Generalization error is a U-shaped curve versus many hyperparameters (p.443); some only decrease capacity (minimum weight decay = 0, p.444).
- `[from source]` **The learning rate is perhaps the most important hyperparameter: if you can tune only one, tune the learning rate** (p.444). Training error has a U-shaped curve versus the learning rate (Fig. 11.1, p.445): in the idealized quadratic case, the error **increases** if ε ≥ 2× the optimum (LeCun 1998a); ε too low makes training slower and can stall it at high error (poorly understood effect).
- `[from source]` If training error > target: increase capacity (if there is no regularization and optimization is working: more layers/units) (p.444). If test error > target: the test error is the training error + the gap; reduce the gap with dropout or weight decay without increasing the training error faster than the gap shrinks; "the best performance often comes from a large, well-regularized model" (p.445). Brute force (increasing capacity and data) practically guarantees success if resources allow (p.445-447).
- `[from source]` **Table 11.1** (p.446): capacity increases when: number of hidden units ↑; learning rate well tuned; convolution kernel width ↑ (narrower output without padding); implicit zero padding ↑; weight decay coefficient ↓; dropout rate ↓. `dlb_diagnose.py --hyper`.
- `[from source]` Networks usually benefit from tuning some 40 or more hyperparameters (p.447). **Grid search** (up to 3 hyperparameters; values on a logarithmic scale, for example ε ∈ {0.1, 0.01, 10⁻³, 10⁻⁴, 10⁻⁵} and units ∈ {50, 100, 200, 500, 1000, 2000}; repeat/refine the grid; cost O(nᵐ)) (p.447-449). **Random search** (Bergstra and Bengio 2012): marginal distributions per hyperparameter, log-uniform for scales (log_lr ∼ u(−1,−5), lr = 10^log_lr, eq. 11.2-11.3), without discretizing; it is exponentially more efficient than the grid when few hyperparameters matter and does not waste runs (p.448-450). `dlb_calc.py search`.
- `[from source]` **Model-based** hyperparameter optimization (Spearmint, TPE, SMAC; Bayesian regression, exploration × exploitation): the book **does not recommend unequivocally**; sometimes it matches experts, sometimes it fails catastrophically; it requires full runs (p.450-451). `[DATED]`

## 6. Debugging (DLB p.451-455)
- `[from source]` ML is hard to debug because (1) the expected behavior is not known a priori and (2) the adaptive parts compensate for defects in others (example: a bias update that does not use the gradient) (p.451-452).
- `[from source]` Tests: **(a) visualize the model in action** (look at detections, listen to samples); evaluation bugs are the most devastating (p.452). **(b) visualize the worst errors / most confident errors**: in Street View, tight crops omitted digits (p.452-453). **(c) reason with training and test error**: low training + high test → training works; it is algorithmic overfitting or an error in the test measurement (saving/reloading the model, different data preparation); both high → software defect or underfitting, requires the following tests (p.453). **(d) fit a tiny dataset** (one example): if it cannot fit one example (classifier, autoencoder, generative model), there is a software defect; extend to a few examples (p.453). **(e) compare backprop derivatives with numerical derivatives**: f′(x) ≈ (f(x+ε) − f(x))/ε (11.6) and the **centered** difference (f(x+½ε) − f(x−½ε))/ε (11.7); ε large enough not to be rounded away; for g: ℝᵐ → ℝⁿ use f(x) = uᵀg(vx) with random u, v (repeat with more than one pair); the **complex step** f(x + iε) = f(x) + iεf′(x) + O(ε²) allows ε = 10⁻¹⁵⁰ (Squire and Trapp 1998) (p.454). **(f) monitor histograms** of activations and gradients (saturation, ReLUs always off); the per-minibatch update should be ≈ **1%** of the parameter magnitude (not 50%, nor 0.001%) (Bottou 2015) (p.455). **(g) test the guarantees** of the algorithm (the objective does not increase after a step; zero gradient at convergence), with tolerance (p.455). `dlb_calc.py autodiff|grad-mlp` demonstrate (e).

## 7. Street View example (DLB p.455-457)
`[from source]` Metric adjusted to the business (98% accuracy; **coverage** was sacrificed), CNN baseline with ReLU and n independent softmaxes; refinement with principled log-likelihood to reject examples with p(y|x) < t; coverage still < 90%, with training and test errors almost equal (tens of millions of examples): visualizing confident errors revealed tight crops; systematically widening the crop added **ten percentage points** of coverage; the last points came from hyperparameters (larger model under a cost constraint). Result: hundreds of millions of addresses transcribed (p.457).
