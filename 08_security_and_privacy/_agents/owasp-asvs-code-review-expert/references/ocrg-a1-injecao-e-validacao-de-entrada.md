# OCRG — A1 Injection, JSON, CSP/headers and input validation (OCRG p.45-58)

Source: OCRG v2.0, ch. 7 (7.1-7.6). Pages = PDF (printed = N − 1). Related in the ASVS (mapping `[inference]`): V5.3.4, V5.3.5, V5.1.3, V5.1.4, V1.5.3, V1.5.4, V5.3.6, V5.5.4, V14.4.x.

## Injection in general (OCRG p.45)
- [from source] Injection lets a malicious user add content/commands to change the application's behavior; it is common, easy to test and to exploit, and very present in legacy applications. The most common type is SQL injection; "SQL, LDAP, XPath, OS commands and XML parsers" belong to the same family (OCRG p.45).
- [from source] Consequences: leakage of sensitive information, integrity problems (changing/inserting/deleting data), privilege escalation and access to the back-end network (OCRG p.45). The SQL parser does not distinguish **code** from **data** when the command is built by concatenation (OCRG p.45).
- [from source] The book lists "the five best ways, all used together" (defense in depth): HtmlEncode of the input; static analysis; **parameterized SQL queries**; stored procedures (which can build dynamic SQL and mix code and data again); training (OCRG p.45-46). `[inference]` The list mixes controls of different natures (HTML encoding does not prevent SQL injection; ASVS V5.3.4 requires parameterization); treat parameterization as the main control.

## SQL injection — what to review (OCRG p.46-51)
- **Blind SQL injection**: the application does not show the result, but the attacker infers it from error responses or from response **time** (OCRG p.46). Generic messages make it harder (see `references/ocrg-logging-erros-alertas-e-defesa-ativa.md`).
- **Parameterized query** (prepared statement): the query string does not depend on client input; values enter through typed setters (`setString`, `setInt`...), which verify that there is no SQL syntax in the value (Sample 7.1, OCRG p.46).
- **"Safe" concatenation?** It is possible to use concatenation safely (using only the *existence* of the input to build the clause), but it raises the risk of error: a book example where, with no filter supplied, the query loses the WHERE and returns the **whole table** — not injection, but a leak even with a parameterized query (OCRG p.46-47). Advice: avoid building the query string, especially the WHERE clause (OCRG p.47).
- **Flexible queries**: prefer `if`/`else` that picks a complete, parameterized query for each combination of filters (Sample 7.4), for maintainability (OCRG p.47-48).
- **PHP**: `addslashes()` and `mysql_real_escape_string()` only protect if the value is wrapped in quotes in the query; a numeric id without quotes remains vulnerable (Sample 7.6) (OCRG p.48-49). `[DATED]` The `mysql_*` extension is legacy; the book mentions PDO in the references (OCRG p.52).
- **Java**: concatenating the request parameter into the SQL string (Sample 7.7) allows access to all records (OCRG p.49). **.NET**: concatenating into `SqlDataAdapter` or calling an SP while concatenating input (Samples 7.8-7.9); using **`SqlParameterCollection`** treats the input as a literal, with type and length checking (out-of-range values throw an exception — which must be handled) (Sample 7.10) (OCRG p.50-51). The book notes that old .NET Framework versions (1.0 and 2.0) may be more vulnerable than later ones (OCRG p.50).
- **ORM/HQL**: "it is a very common misconception" to think Hibernate/ORMs are SQLi-proof: *native SQL* is vulnerable to SQL injection and HQL to HQL/ORM injection; **LINQ is not SQL**, but `ExecuteQuery`/`ExecuteCommand` via LINQ lose the protection; NHibernate with dynamic queries is also vulnerable; the reviewer makes sure of **parameterized HQL** or the **Criteria API** (OCRG p.51-53).
- **"What to review" checklist** (OCRG p.51): validate type, length, format and range; test string contents accepting only expected values and rejecting binaries, escape sequences and comment characters; validate XML against the schema on input; **never build SQL directly from input**; use SPs to validate or the platform's SQL API (parameterized queries); multiple layers of validation; never concatenate unvalidated input ("concatenation is the main entry point"); review all code that calls `EXECUTE`/`EXEC` and SQL calls that reach external resources or the command line.
- Book references in this section: SQLi prevention and parameterization cheat sheets, CWE 77/89/564 (OCRG p.51-52).

## JSON and ORM (7.3-7.4) (OCRG p.52-53)
- [from source] The main concern with JSON is JSON text dynamically embedded in JavaScript; the reviewer makes sure **`eval` is not used** (use `JSON.parse`); `eval` of JSON text is a "red flag" for the reviewer (OCRG p.52). Do not try to reject bad patterns by regex (error-prone and hard to test): allow only alphanumeric keywords on an allow list and validated numbers; **do not let JSON data build dynamic HTML** — use safe DOM APIs such as `innerText` or `CreateTextNode` (OCRG p.52).

## CSP and security headers (7.5) (OCRG p.53-55)
- [from source] **CSP** (W3C specification) tells the browser where/what types of resources it may load from; it helps detect and mitigate XSS and data injection; directives per resource type, via header or meta tag. Risks: **misconfigured policy** and **overly permissive policy**. The reviewer understands which policies the design required and how they are tested (OCRG p.53). `[DATED]` The names `X-Content-Security-Policy` (Firefox < 23, IE 10) and `X-WebKit-CSP` (Chrome < 25) are historical (OCRG p.53).
- [from source] Table 11 — headers: **Strict-Transport-Security** (example `max-age=16070400; includeSubDomains`), **X-Frame-Options** (anti click-jacking: deny, sameorigin, allow-from), **X-Content-Type-Options: nosniff**, **Content-Security-Policy** (and `-Report-Only` for tuning) and **X-XSS-Protection** (re-enables the browser's XSS filter) (OCRG p.54). In many architectures these headers can be set in the web server configuration, without changing the code — a quick and cheap partial mitigation, an additional layer for new apps (OCRG p.54). `[DATED]` The `X-XSS-Protection` header and the filter it controlled are no longer recommended; prefer CSP (check the current source; ASVS V14.4.3 requires CSP, ASVS p.63).

## Input validation (7.6) (OCRG p.55-58)
- [from source] Validation is "one of the most effective technical controls": it mitigates XSS, several injections and some buffer overflows; it is more than checking form fields. Golden rule: all external input — including between systems — is validated; the rules come from business requirements (OCRG p.55).
- [from source] Hierarchy: **exact match** (only expected values) > **known good / allow list** (only defined characters/ranges; more flexible and slightly weaker) > **known bad / blacklist** (not future-proof; requires maintenance) > **encode bad** (very weak) (OCRG p.55). Complex regexes are error-prone in corner cases, hard for QA to test and for the reviewer to review (OCRG p.55).
- [from source] **Business validation**: limit transaction ranges/values and reject nonsensical input; review rounding and floating point that cause integer overflow (OCRG p.55). **Canonicalization**: several equivalent forms (UTF-8, UTF-16...; a "." can be 2E or C0 AE); naive filters are bypassed; compare the canonical path (Samples 7.11 vs 7.12: `getAbsolutePath` x `getCanonicalPath`) (OCRG p.55-56).
- [from source] .NET **Request Validation** is a good start, but too generic: **never use it as protection against XSS**; validate URIs with `Uri.IsWellFormedUriString` and check the http/https scheme; encode output with `<%: %>`, Razor `@` or `Server.HtmlEncode` (OCRG p.56-57).
- [from source] **Managed vs unmanaged code**: do not declare a native method public; declare it private and expose a public *wrapper* that validates the input (including `offset+len` overflow) and copies mutable inputs (Sample 7.13) (OCRG p.57).
- [from source] **Validation checklist** (OCRG p.57-58): mechanism present; every modifiable input (headers, fields, hidden, dropdowns) validated; length check; well-formed and only known characters; **server-side validation**; centralized vs decentralized; no backdoors in the validation model; "Golden Rule: all external input is examined and validated".

## Limits
- The OCRG does not treat NoSQL as its own surface (it only mentions terms), nor SSRF, deserialization, template injection or HTTP parameter pollution (terms absent). For SQLi use the OCRG as a guide to **what to look at** and the ASVS (V5.3.x) as the **verifiable requirement**.
