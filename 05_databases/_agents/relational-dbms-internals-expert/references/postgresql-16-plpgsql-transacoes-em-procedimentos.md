# PostgreSQL 16: transaction control in PL/pgSQL procedures (`COMMIT` and `ROLLBACK` inside `CALL` and `DO`)

> Pages = PDF of the PG16 manual (16.15); printed = N − 38. Section 43.8 (Transaction Management) = PDF 1389-1390. Summary in English (the manual is in English). There is no summary of the rest of ch. 43 (PL/pgSQL) in this file; see the pointer map in `INDEX.md`.

## 1. Transaction management in PL/pgSQL: COMMIT and ROLLBACK in procedures and DO blocks [from source] (PG16 p.1389-1390)
- **When it is possible**: in procedures called by `CALL` and in anonymous blocks (`DO`), the transaction can be ended by `COMMIT` or `ROLLBACK` from inside the PL/pgSQL code (PG16 p.1389).
- **Automatic new transaction**: after `COMMIT` or `ROLLBACK` a new transaction starts by itself; for that reason there is **no** separate `START TRANSACTION` command in PL/pgSQL. `BEGIN` and `END` have a different meaning in that language (they delimit a block, not a transaction) (PG16 p.1389).
- **Manual example** (PG16 p.1389): a procedure with a `FOR` loop from 0 to 9 that does an `INSERT` on each iteration and issues `COMMIT` when the counter is even and `ROLLBACK` when it is odd; called with `CALL`, only the rows for the even numbers remain [derived from the example].
- **Characteristics of the new transaction**: it starts with the default characteristics (for example the isolation level). To keep the same characteristics as the previous one, for example in loops that commit on each iteration, use `COMMIT AND CHAIN` or `ROLLBACK AND CHAIN` (PG16 p.1389).
- **Call stack rule**: transaction control is only possible in a **top-level** `CALL` or `DO`, or in **nested** `CALL`/`DO` **with no other command in between**. The manual gives the example: `CALL proc1()` calling `CALL proc2()` calling `CALL proc3()` allows control in the last two; but `CALL proc1()` calling `SELECT func2()` which calls `CALL proc3()` does **not** allow it, because of the intermediate `SELECT` (PG16 p.1389).
- **Cursor loops** (PG16 p.1389-1390): normally cursors close at commit, but the cursor created by a `FOR r IN SELECT ...` loop becomes a **holdable cursor** at the first `COMMIT` or `ROLLBACK`; this means the cursor is **evaluated in full** at that moment, not row by row. The cursor is still removed automatically at the end of the loop, so the effect is "almost invisible" to the user.
- **Prohibitions** (PG16 p.1390): (a) transaction commands are **not allowed** in a cursor loop driven by a command that is **not read-only**, for example `UPDATE ... RETURNING`; (b) a transaction **cannot be ended inside a block with an exception handler** (`EXCEPTION`).
- `[inference]` An ordinary function (`CREATE FUNCTION`) called by `SELECT` cannot issue `COMMIT`: it follows from the stack rule, since the `SELECT` is an intermediate command. The text on p.1389 only gives `SELECT func2()` in the middle of the stack as an example.
- `[inference]` For the typical case "process a large batch and commit every N rows", the design is a **procedure** with a loop and periodic `COMMIT`, invoked by a direct `CALL` (no function in between), without an `EXCEPTION` handler in the same block, and with the loop over a read-only `SELECT` (not over `UPDATE ... RETURNING`).

## 2. [extrapolation] and what the pages do NOT say
- Pages 1389-1390 do not discuss the performance of commits in a loop, the effect on locks already acquired, or the exact error message of each violation; **do not state** these details without reading the manual (for example the pages for `CALL` and `DO`, pointer only).
- `[extrapolation]` Using partial commits loses the atomicity of the work as a whole: what has already been committed does not come back with a later `ROLLBACK`. It is a general consequence of transactions, not a sentence from p.1389-1390.
