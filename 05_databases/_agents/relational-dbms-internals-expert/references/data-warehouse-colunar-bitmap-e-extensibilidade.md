# Access methods, data warehouses (bitmap, columnar) and extensibility

> Pages = PDF. ARCH: printed = N + 140. REDBK = chapter introductions only. This file covers sections 4.5 to 4.9 of ARCH (p.53-69) and the introduction to chapter 4 of the Red Book (REDBK p.21-22). Everything is paraphrased; calculations are labeled.

## 1. Access methods, SARG and RID [from source]
- An **access method** is the routine that manages the on-disk structures: unordered files ("heaps") and indexes. All the large commercial systems implement heaps and B+-trees; Oracle and PostgreSQL offer hash indexes for equality; some are starting to offer multidimensional indexes such as R-trees; PostgreSQL has the extensible GiST infrastructure, used for R-trees and RD-trees; IBM UDB 8 introduced MDC (multidimensional clustering) indexes; data warehouse systems often have bitmap variants (ARCH p.53-54).
- **API**: an access method is an iterator (see `otimizacao-de-consultas-e-planos-de-execucao.md`); `init()` receives a **SARG** (search argument of the form column operator constant); a null SARG asks for a full scan; get_next() returns NULL when there are no more tuples satisfying the SARG (ARCH p.54).
- **Why pass the SARG into the access method**: (1) indexes such as B+-trees only work well with a SARG; (2) CPU performance, including for heap scans: if the caller tests the predicate, each returned tuple requires either pinning the page in the buffer pool or copying it, and then unpinning or deleting the copy if the tuple does not qualify, plus a call/return pair per tuple; by testing the SARG one page at a time inside the access method, get_next() returns only for tuples that qualify. The paper sees this as a case of the principle of "amortizing work across items", here for CPU rather than for disk (ARCH p.54-55).
- **RID (row ID)**: many DBMSs point to rows by physical disk addresses, which is fast but makes moving a row expensive, because all secondary indexes must be updated. Rows move when an UPDATE increases their size and there is no room on the page, and when a B+-tree splits (if the B+-tree is the primary storage). DB2 uses a forwarding pointer (costs a second I/O, but does not update the secondary index) and does not support B+-tree as primary storage. SQL Server and Oracle support B+-tree as primary storage and use, in secondary indexes, the **primary key** (with system bits to ensure uniqueness if there is no unique key) instead of the physical RID: they lose a little speed in access through the secondary index, but avoid the row-movement problem. Oracle also keeps a physical pointer alongside the primary key (fast if the row has not moved) and avoids moving heap rows by letting them occupy more than one page (ARCH p.55) `[DATED]`.
- Unlike the other iterators, access methods interact deeply with concurrency and recovery (ARCH p.55; see `controle-de-concorrencia-2pl-e-mvcc.md`).

## 2. Data warehouses: what changes compared with OLTP [from source]
- Data warehouses are large historical databases for decision support, loaded periodically; the paper says some estimate they account for 1/3 of DBMS activity, and that conventional optimizers and executors **do not work well** in this scenario, requiring extensions (ARCH p.56). For reasons of response time and schema, the warehouse sits on separate hardware from the OLTP system, fed by ETL (extract, transform, load) flows (ARCH p.56-57).
- **Bitmap indexes** (ARCH p.57-58): B+-trees are optimized for fast insertion, deletion and update; a warehouse does an initial load and then stays static for months or years, and many columns have few values. For a **two-valued** attribute (the example is customer sex), a bitmap uses **one bit per record**, whereas a B+-tree stores (value, record pointer) pairs and "typically consumes 40 bits per record" (ARCH p.57). Bitmaps also help with conjunctive filters (for example sex = "F" **and** state = "California"): the answer comes from the **intersection** of bitmaps (ARCH p.57-58). The drawback is that they are **expensive to update**, so they only pay off in a warehouse environment; Oracle offers them as a complement to B+-trees, DB2 in a more limited version, and Sybase IQ uses them heavily (ARCH p.58) `[DATED]`.
  - `[derived]` for 500 million rows and a boolean attribute: 500e6 x 1 bit = 500e6 / 8 bytes ≈ 62.5 MB of bitmap, against 500e6 x 40 bits = 20e9 bits = 2.5 GB in the B+-tree of the paper's example; ratio 40:1. The "40 bits" is the paper's number for that example, not a general property of B+-trees.
  - PostgreSQL does **not** have a persistent bitmap index: in the manual, "bitmap" appears as a scan type (bitmap index scan, which combines indexes in memory), and the listed index types are B-tree, Hash, GiST, SP-GiST, GIN and BRIN (PG16 p.468; BRIN answers by bitmap scan, PG16 p.2552). `[inference]` therefore there is no direct equivalent of the paper's recommendation for low-cardinality columns; the alternatives in PG16 are a partial index, B-tree or BRIN, depending on the case.
- **Fast load** (ARCH p.58-59): warehouses are usually loaded at night with the day's data; a *bulk loader* is used that injects records into storage without going through the SQL layer and takes advantage of B+-tree bulk-loading methods; "in round numbers" it is an order of magnitude faster than SQL INSERTs (ARCH p.58). With real-time warehouses, conflicts arise between the write locks of loads and the read locks of queries, which can "freeze" the warehouse; the way out is to avoid update-in-place and keep timestamped versions, allowing queries "as of" a recent instant, without read locks (multiversion isolation, like Oracle's Snapshot Isolation) (ARCH p.58-59).
- **Materialized views** (ARCH p.59-60): real tables that correspond to a logical view over the base tables; three aspects: choosing which to materialize (part of auto-tuning), keeping them up to date, and using them in ad-hoc queries. There are refresh techniques ranging from updating on every UPDATE to the base tables to dropping and recreating periodically, with a trade-off between run-time overhead and consistency.
- **OLAP and cubes** (ARCH p.60): predictable queries can be served by materialized views of aggregates; data cubes are one class of these views (ROLAP; systems that internally use OLAP storage schemes are sometimes called HOLAP); they give high performance for a limited and predictable class of queries, but do little for ad-hoc queries.
- **Star and snowflake schema** (ARCH p.60-61): a central fact table with foreign keys to dimensions (customers, products, stores, time); hierarchical dimensions form a *snowflake*; essentially all queries filter dimensions, join to the fact table, group and aggregate; vendors created special paths in the optimizers for this class (ARCH p.61).
- **Conclusion of the paper** (ARCH p.61-62): besides B+-trees, bitmaps; instead of a generic optimizer, attention to aggregate queries over a snowflake; materialized views instead of ordinary views; fast load instead of fast transactional updates. Vendors cited: Teradata and Netezza (proprietary shared-nothing hardware), Greenplum (parallelization of PostgreSQL) and others (ARCH p.61-62) `[DATED]`.

## 3. Columnar storage [from source]
- **In ARCH (p.62)**: some authors (the text itself says this includes one of the authors) claim that column stores have a "huge advantage" in data warehousing over stores whose unit is the row. Storing each column separately is especially efficient for wide tables with accesses to few columns; on-disk compression is simple and effective because the column data has the same type; the challenge is keeping row positions consistent across the stored columns (or using extra mechanisms to bring columns together), which is a major problem for OLTP but not for append-mostly databases such as warehouses or log repositories. Vendors cited: Sybase, Vertica, Sand, Vhayu, KX (ARCH p.62) `[DATED]`. In 5.5 the paper records renewed interest in column storage also for sparse data (ARCH p.77).
- **In the Red Book (REDBK p.21)**, Stonebraker opens chapter 4 by declaring the death of "one size fits all" and giving the quantitative reasoning for the warehouse case: the fact table is "fat" (a hundred or more attributes) and the typical query aggregates and reads "half a dozen" of the 100 attributes; a column store moves **a factor of 16 less data** from disk to memory than a row store (6 columns versus 100). Other arguments: (a) a column block has a single attribute, so compression works better than with 100; (b) row stores have a header per record (in SQL Server, according to the text, 16 bytes), column stores do not; (c) the row executor's *inner loop* is paid per record examined, whereas the columnar executor pays it **once per column**. In the author's opinion, "in most real-world environments" column stores are **50 to 100 times faster** than row stores (REDBK p.21) `[DATED]` (a 2015 opinion, from a columnar advocate). He cites Sybase IQ and MonetDB as early column stores, C-Store/Vertica in the 2000s, and says the warehouse market moved from row store to column store (REDBK p.21).
- `[derived]` the "factor of 16" is 100/6 ≈ 16.7 (equivalent to reading about 6% of the data, that is, 94% less), valid **only** for the example (wide facts, queries that touch 6 of 100 columns). It does not extend to OLTP, which reads and writes whole rows per transaction (`[inference]`: ARCH itself says that keeping rows aligned across columns is a major problem for OLTP, p.62). The "50-100x" range is an opinion claim with no benchmark on the page: do not present it as a measurement; and never apply it to OLTP.
- Red Book, same introduction (REDBK p.22, which continues the reasoning started at the end of p.21): the price of main memory fell; **"today you can buy 1 terabyte for maybe US$ 25,000"** and a **high-performance computing cluster with a few terabytes for maybe US$ 100 thousand** `[DATED]` (2015 prices, not current). The "key idea" is that OLTP databases "simply are not that big": **1 TB is a very large OLTP database and a candidate for main-memory deployment**; the text cites the *looking glass* paper to say that you do not want to run a disk-based row store when the data fits in memory, because the overhead is "too high". The OLTP market would be turning into a market of main-memory DBMSs, and traditional disk-based row stores "are not competitive"; new solutions for concurrency control, crash recovery and multithreading are needed.
  - **Concurrency**: "my best current guess is that nobody will use traditional two-phase locking"; timestamp-ordering or multiversion techniques will prevail; the third paper of the section discusses Hekaton, which implements a state-of-the-art MVCC scheme.
  - **Crash recovery**: the proposed solution is replication and online failover (pioneered by Tandem, two decades earlier). The traditional wisdom is to write a log, move it over the network and redo it at the backup site (**active-passive**), which was shown in [6] to be **a factor of 3 worse** than an **active-active** scheme, in which transactions simply run on each replica. In active-active you must ensure that transactions run **in the same order on each replica** and, "unfortunately, MVCC does not do that"; hence the interest in **deterministic concurrency control schemes**, which would be "much faster" than MVCC in an end-to-end system.
  - **NoSQL** (REDBK p.22): about 100 DBMSs with two traits: (1) an "out of the box" experience that is easy for the programmer, whereas RDBMSs are "heavyweight" and require a schema up front; (2) support for semistructured data, where records with different attributes would give very wide and sparse tuples in a traditional row store. It is a call to commercial vendors to make use easier and to support semistructured types such as JSON; the author expects the NoSQL market to merge with SQL over time. The fourth change is the Hadoop/HDFS/Spark environment (Ch. 6).
  - All of this is **2015 opinion** `[DATED]`; the caveat "MVCC does not guarantee the same order" is a statement about active-active replication by transaction execution, **not** a description of PostgreSQL's MVCC nor a general criticism.

## 4. Extensibility [from source]
- **Abstract data types (ADT)** (ARCH p.62-63): the type system and the parser are driven by the catalog, which lists the types and the "methods" (code) that manipulate them; the DBMS does not interpret the type, it only invokes its methods; this requires a runtime for user code that executes it without risk of crashing the server or corrupting data. The optimizer must consider user-defined "expensive" predicates (sometimes deferring selections until after joins), and it is useful to index ADTs: B+-trees extended to **expression indexes** (the "functional indexes") and an extensible index scheme for predicates that are not a linear order (the original Postgres interface and GiST) (ARCH p.63). PostgreSQL ships with support for C, Perl, Python and Tcl, accepting new languages at run time (ARCH p.63) `[DATED]`.
- **Structured types and XML** (ARCH p.64-65): three approaches (ARCH p.64): (1) a **dedicated ("custom") system**, which historically was **overshadowed** by the approaches that accommodate structured types inside a traditional relational DBMS, a trend followed in the XML case as well; (2) treating the complex type as an ADT (XPath search becomes opaque to the optimizer); or normalizing the structure into relations ("shredding", with a storage cost and joins to reconstruct). Vendors offer ADT and shredding and let the designer choose; with shredding it is common to offer the option of **discarding ordering information** between XML elements at the same level (ARCH p.64-65). **Footnote 3** (ARCH p.64): XML is sometimes called **"semi-structured"** data because it imposes no restrictions on the structure of documents, but, unlike free text, it **encourages structure**, including non-relational complexities such as ordering and nested collections; the complications of storing and querying XML come from **dealing with structure**, not from dealing with unstructured text inside the document; many XML query processing techniques have roots in the ODMG object model and the OQL language. `[inference]` "semi-structured" here is a convenience label of the book, not a third model. Arrays and nested tables, common in Oracle installations, have similar trade-offs (ARCH p.65). `[inference]` it is the same dilemma that reappears between `json`/`jsonb` columns and relational modeling (see `postgresql-16-json-jsonb-e-gin.md`).
- **Text search** (ARCH p.65-66): modeling text as an "inverted file" relation (word, document, position) with a B+-tree on the word; text engines optimize by denormalizing to (word, list of occurrences) and compressing the "postings list" with delta; a naive implementation inside the DBMS would be about an order of magnitude slower. The text index is usually updated asynchronously; PostgreSQL is described as unusual in offering a text index with transactional update; external indexes require separate backup and restore. The semantic challenge is reconciling relational results (complete, unordered sets) with ranked search (ordered, generally incomplete) (ARCH p.65-66) `[DATED]`.
- **Other extensions** (ARCH p.66-67): rule-based extensible optimizers (DB2, Tandem, Microsoft) and the ability to "wrap" remote sources as tables, which requires generalizing the matching of SARGs to predicates and an executor tolerant of slow or bursty sources.

## 5. Standard practice and discussion [from source]
- The coarse architecture of essentially all relational query engines resembles that of the System R prototype; the larger differences are in the optimizer's search strategy (top-down x bottom-up) and in the executor's flow-control model (iterators and exchange x asynchronous producer/consumer schemes), mainly in shared-nothing and shared-disk (ARCH p.67). PostgreSQL has a reasonably sophisticated query processor, with a traditional cost-based optimizer, many execution algorithms and extensibility; MySQL's is much simpler, based on nested-loop joins over indexes, focused on key/foreign-key joins, outer join rewriting and queries that ask for only the first rows (ARCH p.67-68) `[DATED]`.
- Discussion (ARCH p.68-69): approximate processing by sampling had slow adoption (Oracle and DB2 sample a single table, with no robust estimate for several tables); vendors preferred to enrich OLAP, which gives 100% correct answers; data mining (clustering, classification, regression, association rules) has integration challenges; data-parallelism frameworks such as Map-Reduce, Dryad and Hadoop resemble shared-nothing relational executors with custom operators and handle node failure, common at large scale (ARCH p.69).

## 6. [extrapolation] and what the sources do NOT say
- The number of pages, rows or bytes for choosing between bitmap and B+-tree: only the two-valued example (1 bit x 40 bits) is in the paper (ARCH p.57).
- Whether the PostgreSQL of the current manual uses "bitmap index" as a persistent index: it does not (PG16 p.468 lists the types); the term "bitmap" in the manual refers to the scan.
- Benchmarks that prove the Red Book's "50-100x": the page only asserts it (REDBK p.21).
