# PostgreSQL 16: MVCC, isolation, snapshots and tuple header

> Pages = PDF of the PG16 manual (16.15). Printed = N − 38 (e.g.: Ch. 13 starts at printed 487 = PDF 525). v1 used numbers such as "p.461" for MVCC; in the PDF that page belongs to the type conversion chapter.

## 1. Multiversion model [from source]
PostgreSQL maintains consistency with a multiversion model (MVCC): **each SQL command sees a snapshot** of the data as it was some time ago, regardless of the current state; this avoids seeing inconsistent data from concurrent transactions. In MVCC, read locks **do not conflict** with write locks: "reading never blocks writing and writing never blocks reading", a guarantee kept even at the strictest level, thanks to SSI (PG16 p.525). There are also explicit table and row locks for those who want to manage conflicts, and advisory locks (PG16 p.525). The manual states that proper use of MVCC generally gives better performance than locks (PG16 p.525).

## 2. Phenomena and levels [from source]
- Phenomena: dirty read, nonrepeatable read, phantom read, serialization anomaly (PG16 p.525-526).
- **Table 13.1** (PG16 p.526): Read Uncommitted (dirty read "allowed, but not in PG"); Read Committed; Repeatable Read (phantom "allowed, but not in PG"); Serializable (no phenomenon). Internally there are **only three** distinct levels: Read Uncommitted **behaves as** Read Committed (PG16 p.526). PG's Repeatable Read **does not allow phantom reads**, which is acceptable because the standard defines only the minimum (PG16 p.526).
- Changes to sequences (and to the `serial` counter) are visible to all transactions and are **not** rolled back on abort (PG16 p.526).

## 3. Read Committed (default) [from source]
It is the default level. A SELECT sees only data committed **before the query started**; two consecutive SELECTs in the same transaction can see different data (PG16 p.526). UPDATE/DELETE/SELECT FOR UPDATE look for rows like SELECT, but, if the row has already been changed by a concurrent transaction, they **wait**: if the first rolls back, the second proceeds; if it commits, the second reevaluates the WHERE clause over the new version (PG16 p.526-527). Consequence: a command can see an inconsistent snapshot (sees effects of concurrent commands on the rows it tries to update, but not on the others); the `website.hits` example shows a DELETE that affects nothing (PG16 p.527-528). The manual says that this mode is "adequate for many applications", but not for commands with complex search conditions (PG16 p.527-528). `INSERT ... ON CONFLICT` and `MERGE` have their own rules in Read Committed (PG16 p.527).

## 4. Repeatable Read [from source]
Sees only data committed **before the transaction started**: the snapshot is that of the start of the first command that is not a transaction control command (PG16 p.528). Prevents all the phenomena of Table 13.1, except serialization anomalies (PG16 p.528). If it tries to modify or lock a row that another transaction changed and committed after the start, it receives `ERROR: could not serialize access due to concurrent update`; the application must **abort and repeat the whole transaction** (PG16 p.528). Only write transactions need retry; read-only transactions never have a serialization conflict (PG16 p.528). Even so, the stable view may not be consistent with any serial execution (example of the control record and the detail record), and "enforcing business rules in this mode probably won't work correctly without explicit locks" (PG16 p.528-529). **Rule for the application**: in Repeatable Read (and in Serializable) the application must be prepared to **repeat the whole transaction** after a serialization failure; on the retry, the transaction sees the already committed change as part of its initial view (PG16 p.528-529). Implemented with **Snapshot Isolation**; up to 9.0, asking for Serializable gave this same behavior (PG16 p.529).

## 5. Serializable (SSI) [from source]
Works like Repeatable Read, plus **monitoring** of conditions that would make the set of transactions incompatible with any serial order; this monitoring adds no blocking beyond Repeatable Read, but has a cost, and detection triggers a serialization failure (PG16 p.529). Manual example: two transactions sum `class` 1 and `class` 2 and insert the result into the other class; under Repeatable Read both commit, under Serializable one is rolled back with `ERROR: could not serialize access due to read/write dependencies among transactions` (PG16 p.529-530). It uses **predicate locks** that **do not block** (do not take part in deadlock), visible in `pg_locks` with mode `SIReadLock`; they can be promoted from tuple to page to save memory; READ ONLY transactions can release them early, and `SERIALIZABLE READ ONLY DEFERRABLE` waits for a safe snapshot (PG16 p.530). Serialization failures return SQLSTATE `40001`, and the environment needs generic handling for them (PG16 p.530). Performance tips: declare READ ONLY, control the number of connections with a pool, short transactions, avoid "idle in transaction", adjust `max_pred_locks_per_*`; sequential scan always requires a relation-level predicate lock (PG16 p.531). The manual describes the technique as **Serializable Snapshot Isolation** (PG16 p.531).

## 6. Tuple header and snapshots [from source]
- Table 73.4 (`HeapTupleHeaderData`): `t_xmin` (insertion XID, 4 bytes), `t_xmax` (deletion XID, 4 bytes), `t_cid`, `t_xvac`, `t_ctid` (current TID **of this or of a newer version** of the row, 6 bytes), `t_infomask2`, `t_infomask`, `t_hoff`; the fixed header takes 23 bytes on most machines (PG16 p.2575).
- The item pointer (`ItemPointer`, CTID) is page number + index of the item identifier (PG16 p.2574).
- XIDs are 32 bits and wrap around every 4 billion transactions; there is the 64-bit `xid8` type with epoch (PG16 p.429, p.2577). Non-virtual XIDs are assigned when the transaction first writes (PG16 p.2577).
- The `pg_snapshot` type has the textual representation `xmin:xmax:xip_list` (example `10:20:10,14,15`): `xmin` is the lowest XID still active (everything below is committed and visible or rolled back); `xmax` is "one past the highest completed XID" (everything `>= xmax` had not yet completed, hence invisible); `xip_list` are the in-progress transactions (PG16 p.429).
- Old row versions are **not removed** immediately by UPDATE/DELETE; it is VACUUM that reclaims the space (PG16 p.789). See `postgresql-16-vacuum-autovacuum-e-armazenamento.md`.
- HOT (heap-only tuples) reduces the cost of updates when no indexed column (except by summarizing indexes, i.e. BRIN) changes and the page has space (PG16 p.2576); details in `postgresql-16-vacuum-autovacuum-e-armazenamento.md` section 4.

## 7. Explicit locks [from source]
> Detail (eight table modes and who takes them, four row modes, `LOCK`, `SKIP LOCKED`, deadlocks, advisory locks, prepared transactions): `postgresql-16-locks-explicitos-advisory-locks-e-transacoes-preparadas.md`.
Table lock modes (ACCESS SHARE ... ACCESS EXCLUSIVE; all are table locks, even with "ROW" in the name) and conflict matrix (PG16 p.531-533); row locks (PG16 p.535); **caveat (PG16 p.538, 13.4.2): `SELECT FOR UPDATE` blocks only while the lock lasts; it does not prevent whoever was waiting from changing or deleting the row after the owner's commit/rollback, unless the transaction made a real UPDATE of the row; in Repeatable Read, obtain the locks before the first query (the snapshot freezes at the first SELECT/INSERT/UPDATE/DELETE/MERGE); `SHARE` or stronger guarantees there are no uncommitted changes in the table; retry 40001, 40P01 and, with care, 23505/23P01 (PG16 p.538-539)**; `CREATE INDEX` without CONCURRENTLY takes `SHARE` and blocks writes; `VACUUM` and `CREATE INDEX CONCURRENTLY` take `SHARE UPDATE EXCLUSIVE` (PG16 p.532).

## 7b. Transaction ID and snapshot functions; deprecated `txid_*`; commit timestamp [from source] (PG16 p.428-430)
- **Current functions** (Table 9.80, PG16 p.428-429): `pg_current_xact_id()` (returns `xid8`; assigns an ID if the transaction does not have one yet; in a subtransaction returns the top-level ID), `pg_current_xact_id_if_assigned()` (NULL if there is no ID; better for a possibly read-only transaction), `pg_xact_status(xid8)` (`in progress`, `committed`, `aborted` or NULL when the information has already been discarded; a prepared transaction appears as `in progress`), `pg_current_snapshot()`, `pg_snapshot_xip`, `pg_snapshot_xmin`, `pg_snapshot_xmax`, `pg_visible_in_snapshot(xid8, snapshot)` (does not give the right answer for a subtransaction ID), `pg_get_multixact_members`, `age` and `mxid_age`. The internal `xid` is 32 bits and wraps around every 4 billion transactions; the functions on `xid8` (64 bits) do not wrap around during the life of the installation (PG16 p.429). `pg_snapshot` text: `xmin:xmax:xip_list`, for example `10:20:10,14,15` (PG16 p.429).
- **`txid_*` are the old, deprecated versions** (Table 9.82, PG16 p.430): before PG 13 there was no `xid8` type; the functions used `bigint` and the snapshot type `txid_snapshot`. They remain supported for compatibility, but **may be removed** in a future version. Replacements, function by function:

| Deprecated function (PG16 p.430) | Current replacement |
|---|---|
| `txid_current()` -> bigint | `pg_current_xact_id()` |
| `txid_current_if_assigned()` | `pg_current_xact_id_if_assigned()` |
| `txid_current_snapshot()` -> txid_snapshot | `pg_current_snapshot()` |
| `txid_snapshot_xip()`, `txid_snapshot_xmax()`, `txid_snapshot_xmin()` | `pg_snapshot_xip()`, `pg_snapshot_xmax()`, `pg_snapshot_xmin()` |
| `txid_visible_in_snapshot(bigint, txid_snapshot)` | `pg_visible_in_snapshot(xid8, pg_snapshot)` |
| `txid_status(bigint)` | `pg_xact_status(xid8)` |

- **`pg_xact_commit_timestamp`, `pg_xact_commit_timestamp_origin`, `pg_last_committed_xact` (commit timestamp)**: `pg_xact_commit_timestamp(xid)` returns the commit instant; `pg_xact_commit_timestamp_origin(xid)` also returns the `roident`, the replication origin; `pg_last_committed_xact()` returns xid, timestamp and origin of the last committed transaction (Table 9.83, PG16 p.430). **They only bring useful data with `track_commit_timestamp` enabled and only for transactions committed after it was enabled**; the information is **routinely removed by vacuum** (PG16 p.430). The default of `track_commit_timestamp` is off (PG16 p.674).
- Not present in p.428-430: `track_commit_timestamp_retention`, `pg_xact_commit_timestamp_batch()` nor any period in days; do not invent a name or value, say it is not there.

## 8. [inference]
- In PG's Repeatable Read the second updater **waits** for the first; if the latter commits, the second is aborted (p.528). In ARCH terms, this looks more like "the first to write waits/wins" (ARCH p.87) than like the "first to commit wins" that ARCH attributes to classic Snapshot Isolation; v1 called PG's behavior "First-Committer-Wins" as if it were from the manual. The manual **does not use** that expression.

## 9. [extrapolation] and what the sources do NOT say
- "MVCC without a rollback segment, unlike MySQL/InnoDB or Oracle": PG16 does not make this comparison; the ARCH describes that Oracle reconstructs old versions with undo records (ARCH p.87). The comparison with InnoDB is external knowledge.
- The terms **write skew** and **dangerous structure** do not appear in PG16 or in ARCH/REDBK (checked by search); they are vocabulary of the SSI literature.
- "`xmax = 0` if the tuple is alive" is not in the pages consulted; use only "deletion XID" (PG16 p.2575).
- The number of "three practical levels" is correct (PG16 p.526), but "Read Uncommitted possible in 2PL DBMSs" comes from ARCH p.85 (ANSI levels by locking), not from PG.
