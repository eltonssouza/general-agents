## Ch. 10 — Mitigating denial-of-service attacks (BSRS p.253-265)

### Framing (BSRS p.253-254)
- [from source] DoS is where security and reliability intersect: caused by an adversary or by circumstances (a backhoe cutting fiber, a malformed request taking down a server); it generally shows up as a usage surge; some mitigations can be applied to existing systems, but minimizing effects requires careful design (BSRS p.253). In economic terms: the attacker tries to make demand exceed supply (capacity); the organization decides between spending more to absorb it or suffering downtime; any service can be a target; DoS extortion is relatively indiscriminate, and many extortionists only perform a small "demonstration attack" without the ability to scale (BSRS p.253-254).

### Attack and defense strategies (BSRS p.254-256)
- [from source] Attacker: uses limited resources efficiently; a service has dependencies (DNS, network, frontends, backends) and an attack on any stage takes it down; novices send a flood; sophisticated attackers generate costly requests (e.g., abusing search); DDoS via botnet (compromised machines) or amplification attack (BSRS p.254).
- [from source] Amplification: requests with a forged source sent to thousands of open servers generate a response reflected against the victim; providers should prevent source IP spoofing but enforcement is uneven; protocols such as DNS, NTP, and memcache; the traffic comes from a known source port, hence the defense with network ACLs that limit UDP of abusable protocols (BSRS p.255).
- [from source] Defender: overprovisioning the entire stack absorbs attacks but is expensive; cloud autoscaling can help; prioritize by greatest impact and avoid recency bias; use a threat model approach focused on the weakest link in the dependency chain, comparing threats by the number of machines the attacker would need to control to cause visible disruption (BSRS p.255-256). Terminology: DDoS = attacks effective only because they are distributed (botnet or amplification); DoS = attacks that could come from a single host; DoS can be defended at the application layer, DDoS often with infrastructure filtering (BSRS p.256).

### Designing for defense (BSRS p.256-258)
- [from source] An ideal attack concentrates all its power on a single constrained resource (bandwidth, application server CPU/memory, a backend such as a database); protect each in the most efficient way; attack traffic becomes more focused and more expensive to mitigate the deeper it gets; layers of defense, each protecting the one behind it, are essential (BSRS p.256).
- [from source] Defensible architecture: shared infrastructure (peering, network and application load balancers) is the natural place for shared defenses: edge routers limit high-bandwidth attacks, network load balancers limit packet floods, application load balancers limit specific attacks; inner layers only need capacity for attacks that get through the outer ones; eliminate attack traffic as early as possible (ACLs at the edge; caching proxies near the edge) (BSRS p.256). Stateful firewalls should normally not be the first line of defense for systems that receive inbound connections (state exhaustion attack); use router ACLs to restrict to the necessary ports without state in the data path (BSRS p.257). Economies of scale in shared defenses (example: Project Shield; commercial mitigation services use similar bundling) (BSRS p.257). A large DDoS can overload a datacenter like a magnifying glass concentrating the sun; use network and application load balancing to spread traffic to the nearest datacenter with capacity; anycast announces the same IP from multiple locations, dispersing the attack (BSRS p.257-258).
- [from source] Defensible services: the best is to degrade gracefully under overload; simple changes: caching proxies (Cache-Control), avoiding unnecessary requests (icon spriting; e.g., replacing four rounded-corner images with a single circle saved 10 million requests/day; fewer real requests also reduce false positives when identifying bots), minimizing outbound bandwidth (resizing images; limiting or deprioritizing unavoidable large responses) (BSRS p.258).

### Mitigating attacks (BSRS p.259-262)
- [from source] Monitoring and alerting: resolution time is dominated by MTTD and MTTR; monitor request rate in addition to CPU and memory; actionable alerts: if the attack does not harm the user, it is often better to absorb it; it is recommended to alert only when demand exceeds capacity and the automatic DoS defenses have been triggered (the same for synflood with syncookies and for link saturation) (BSRS p.259).
- [from source] Graceful degradation: network ACLs to limit suspicious traffic, an immediate "switch"; do not always block, to maintain visibility and limit the risk to legitimate traffic with the same signature; a smart adversary simulates legitimate traffic, so use QoS to prioritize critical traffic (batch at a lower QoS frees bandwidth) (BSRS p.259). Degraded modes (Blogger read-only without comments; Web Search with reduced features; DNS servers that answer what they can and do not fall over under any load) (BSRS p.260); more in Ch.8.
- [from source] DoS mitigation system: automated defenses (limiting the most active IPs, JavaScript challenge or CAPTCHA) mitigate quickly and consistently and buy the team time; two components: detection (traffic visibility with statistical sampling at all endpoints and central aggregation, together with load balancers that know the capacity) and response (e.g., set of IPs to block); false positives and negatives are inevitable (NAT shares an IP); CAPTCHA lets real users bypass blocks at the application layer (BSRS p.260). Stateless CAPTCHA implementation: exemption cookie with a pseudonymous identifier, type of challenge solved, timestamp, IP that solved it (avoids sharing the exemption across a botnet), and a signature against forgery (BSRS p.260-261).
- [from source] The mitigation system must be resilient to attack and avoid dependencies on production infrastructure that can be affected (includes the response team's tools and communication: Google has backup communication methods and playbook storage); tension between responding in seconds and deploying changes slowly: canary all changes (including automatic responses) on a subset, sometimes for only 1 second; failure of the central controller: neither fail closed (would block everything) nor fail open (would let the attack through): fail static (the policy does not change), and the DoS engine does not need as much availability as the frontend, reducing cost (BSRS p.261).

### Strategic response (BSRS p.261-262)
- [from source] Being purely reactive and filtering the current traffic may not be optimal; the adversary has infinite chances to probe defenses; a strategic response avoids informing the adversary's analysis; example: attack with User-Agent "I AM BOT NET": blocking by the string would teach the attacker to use a plausible User-Agent; instead, enumerate the IPs and intercept all their requests with CAPTCHA for a period, making A/B testing harder for the adversary and blocking the botnet even if the User-Agent changes (BSRS p.261-262).
- [from source] Understand capabilities and objectives: small amplification suggests a single server with spoofing; repeated HTTP DDoS suggests a botnet; sometimes the "attack" is unsustainable scraping (solution: make the site less easy to scrape); you are not alone: mitigation providers, upstream filtering by network providers, and the community of operators (BSRS p.262).

### Self-inflicted attacks (BSRS p.262-264)
- [from source] User behavior synchronized by external events (night earthquake on 10/14/2019, Figure 10-2) (BSRS p.262-263). "Bot or Not?" case (2009): bursts of German-language searches with the same prefix, originating in Germany, normal distribution of browsers; it was a TV game show; the solution was a design change (suggestion to complete words while typing) (BSRS p.263).
- [from source] Client retries: clients should avoid retry loops; use exponential backoff (doubling the wait after each failure) with jitter (random duration) to avoid synchronization; Google uses this in most clients; when you do not control the client (authoritative DNS servers), legitimate resolvers can generate about 30x normal usage; the best option is to respond as much as possible while keeping the server healthy with upstream throttling, since each successful response frees a client from the loop (BSRS p.264).

### Conclusion (BSRS p.264-265)
- [from source] Every online service should prepare for DoS; absorbing is rarely the cheapest option; consider blocking a problematic hosting provider (with some real users) or suffering a brief outage and explaining it to users; the "attack" may be unintentional (BSRS p.264). To get support from other teams: focus on economics and simplification; capacity planning can concentrate on real demand; a WAF filters known malicious requests and lets security focus on new threats and block exploitation of application vulnerabilities until the patch (BSRS p.265).
