## XSS (ch. 9) (OCRG p.72-77)
- [from source] XSS lets an attacker inject malicious content into pages seen by other users and can bypass controls such as the same-origin policy. Three types: **reflected**, **stored** and **DOM-based**; the delivery means differ, the consequences are the same (OCRG p.72).
- [from source] It is hard to find and remove; the best practice is an **intense review** looking for all the places where input from an HTTP request can reach HTML output (OCRG p.72). The reviewer checks: untrusted data is **not** transmitted in the same HTTP responses as HTML/JavaScript without handling; on leaving the server it must be **correctly encoded** ("do not assume data from the server is safe"); on entering the DOM, use `Node.textContent`, `document.createTextNode` or `Element.setAttribute` (2nd parameter only) (OCRG p.72). Tags such as `<img src…>`, `<iframe…>` can also carry script (OCRG p.72).
- [from source] Scanners (e.g. OWASP ZAP) help but do not find everything; neither does manual review; use defense in depth according to risk (OCRG p.72).
- **Libraries and frameworks**: HtmlEncode/validation are **not enough** when the data goes into JavaScript, tag attributes, XML or URL; use an anti-XSS library (Microsoft Anti-XSS, OWASP Java Encoder, ESAPI) (OCRG p.73-75). JS frameworks: check CVEs and whether it is on the latest stable version (OCRG p.73).
- **.NET**: check that `validateRequest` was not turned off (`<pages validateRequest="false" />`, `ValidationRequest="false"`, or `requestValidationMode="2.0"` in 4.0); if turned off, understand why and the risks; in MVC, `HtmlEncode` (OCRG p.73). The linter flags this (`CFG-VALIDATE-REQUEST-OFF`).
- **Context-based encoding** (OCRG p.74-77):
  - *HTML attribute*: escape all characters with ASCII < 256 except alphanumerics, in the format `&#xHH;`; unquoted attributes can be broken out of by many characters; the book lists "safer" attributes (OCRG p.74).
  - *HTML body*: mapping of `& < > " '` to entities; `Encode.forHtmlAttribute`, `ESAPI.encoder().encodeForHTML` (OCRG p.75).
  - *JavaScript parameters*: data inside a JS function/string requires specific handling (OWASP HTML/JSON Sanitizer, `encodeForJavaScript`); **some functions never use untrusted data safely, even with escaping**: `eval()` and `setInterval` with a string (the book shows this case; `setTimeout` with a string is analogous `[inference]`); jQuery `.html` must become `.text` (Samples 9.1-9.2) (OCRG p.75-77).
  - *Nested contexts*: avoid them (e.g. an `onclick` attribute calling a JS function); if unavoidable, apply encoding **in layers in the right order**: JavaScript first, then HTML attribute (OCRG p.77).
- Link to CSP and headers: `references/ocrg-a1-injecao-e-validacao-de-entrada.md` (OCRG p.53-55); ASVS V14.4.3 (ASVS p.63).

## HTML5 (ch. 17) (OCRG p.155-158)
- [from source] Two layers of control: one independent of the browser, another additional (users do not always have an up-to-date browser) (OCRG p.155).
- **Web Messaging / postMessage** (OCRG p.155): give the **expected origin** in the 2nd argument (not `'*'`); the receiver **checks the sender's `origin`** and **validates `data`**; never interpret a message as code (`eval`) nor insert it via `innerHTML` (use `textContent`); check the origin by exact FQDN — `indexOf(".owasp.org")` is "very insecure" (matches `www.owasp.org.attacker.com`); third-party content with scripts: avoid (Caja/sandboxed frames). An XSS in the sender allows messages of any format.
- **CORS** (OCRG p.156): `Access-Control-Allow-Origin: *` should not appear on URLs with sensitive content; use the header only on URLs that need it; prefer a **whitelist** of domains (do not echo `Origin` without checking); CORS does not prevent CSRF; pre-flight may not occur, so "ordinary" GET/POST must have access control; discard HTTP with an HTTPS origin; do not trust `Origin` alone (spoofable outside the browser). Compare ASVS V14.5.2-V14.5.3 (ASVS p.63).
- **WebSockets** (OCRG p.156-157): only versions > hybi-00 (rfc6455 recommended); **`wss://`** instead of `ws://`; the protocol does not handle authentication/authorization; treat messages as **data** (`JSON.parse`, never `eval`); validate input because the client can be forged outside the browser; check `Origin` in the handshake; XSS can hijack the browser's WebSocket; TCP tunnels increase exposure under XSS. Note: the book's Sample 17.1 uses `ws://` as an example (OCRG p.157).
- **Server-Sent Events** (OCRG p.158): validate the `EventSource` URL; treat `event.data` as data; check `event.origin` with a whitelist.

## Same Origin Policy (ch. 18) (OCRG p.159-160)
- [from source] SOP = scheme + host + port; IE has non-standard exceptions (trust zones; ignores the port) `[DATED]` (OCRG p.159). The reviewer: validate path/query/fragment coming from the user; **user-controlled scheme and authority** are a major injection/phishing risk → only the necessary prefixes, **allow list**; authority only alphanumeric, "-" and "."; watch out for **IDN homographs**; do not assume the browser escapes; limit the authority of content by **MIME type** (serving user content as `image/png` is less risky than `text/html`); privileges must apply to the whole origin, not per document (OCRG p.160).

## Client-side JavaScript (ch. 25) (OCRG p.189-191)
- [from source] DOM XSS is hard to detect: **obfuscated/minified** JS (review before), huge frameworks (jQuery, Knockout, Angular, Backbone, JSF) that can only be analyzed with the framework code — many companies simply accept this risk (OCRG p.189). Recommendation: **hybrid analysis** (static with *taint analysis*, black-box for reflected/stored and manual source-to-sink validation) and testing with JS turned off (OCRG p.189-190).
- [from source] Examples: Sample 25.1 (`document.URL` → `document.write`) and 25.2 (`document.location`); controllable sources: `document.url`, `document.location`, `document.referrer`, `window.location`; sinks: `document.write`, `window.location.href` (client-side open redirect), `innerHTML` (stored DOM XSS) (OCRG p.190-191). Why avoid `eval()`/`new Function()`: it runs with the caller's privileges, the code sees the scope, and it is not suitable for JSON (OCRG p.191). Three points: logic on the server; check sources/sinks; check and update insecure JS libraries (OCRG p.191).
