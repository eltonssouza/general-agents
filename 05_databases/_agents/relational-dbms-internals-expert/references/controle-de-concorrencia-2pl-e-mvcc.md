# Concurrency control: strict 2PL, MVCC, OCC and isolation levels

> Pages = PDF. ARCH: printed = N + 140. REDBK = chapter introductions. PostgreSQL-specific behavior is in `postgresql-16-mvcc-e-niveis-de-isolamento.md`.

## 1. ACID and serializability [from source]
ARCH warns that "ACID" is a mnemonic by Haerder and Reuter whose terms were not formally defined; even so, it organizes the discussion around them: atomicity (all or nothing), consistency (an application-specific guarantee, generally via SQL constraints), isolation (a transaction does not see another's in-progress updates) and durability (ARCH p.79-80). Isolation and atomicity result from locking (preventing visibility of transient states) and logging (guaranteeing the correctness of what becomes visible); durability, from logging and recovery (ARCH p.80). **Consistency is managed by run-time checks in the query executor**: if a transaction's actions violate an SQL integrity constraint, the transaction is **aborted** and an error code is returned (ARCH p.80). Therefore "the log guarantees consistency (the C in ACID)" is false according to ARCH: the log serves atomicity, durability and the correctness of visible data; consistency comes from the constraints checked by the executor. **Serializability** is the notion of correctness: an interleaved execution of committed transactions is equivalent to some serial execution; "isolation" is the same idea from the point of view of a single transaction (ARCH p.80).

## 2. Three control techniques [from source]
1. **Strict 2PL**: the transaction requests a shared lock before reading and an exclusive lock before writing; **all locks are held until the end of the transaction** and released atomically; a transaction that cannot get the lock waits in a queue (ARCH p.80-81). Most commercial RDBMSs implement full serializability via 2PL (ARCH p.81).
2. **MVCC**: transactions hold no locks, but have a consistent view of the database at a point in the past; in commercial implementations this stable value is the one at the start of the transaction or at the start of the SQL statement (ARCH p.81). To keep writes from waiting on readers, the write proceeds after the prior version of the row is saved or guaranteed to be recoverable (ARCH p.81). It is often offered **without** full serializability (ARCH p.81).
3. **OCC (optimistic)**: several transactions read and update without blocking; each keeps a history of reads and writes and, before committing, checks for conflicts; if there are any, one is rolled back. It converts lock waits into rollbacks; it does well when conflicts are rare and poorly when they are frequent (ARCH p.81-82).

The Red Book adds that **there is no universally best concurrency mechanism**: the best strategy depends on the workload, the subject of the study by Agrawal, Carey and Livny (REDBK p.17-18).

## 3. Lock manager, deadlock and latches [from source]
- Locks are names registered in a **lock table** with modes and a compatibility matrix; Gray's hierarchical locking lets a table lock coexist with row locks (ARCH p.82-83). Basic calls: `lock`, `remove transaction` and, since the SQL standard allows lower isolation, also per-item `unlock`, plus `lock upgrade` and `conditional lock` (ARCH p.82).
- **Deadlock**: a periodic detector looks for wait cycles (waits-for) and aborts one of the transactions, chosen by heuristics studied in the literature; in shared-nothing/shared-disk systems, distributed detection or timeouts are needed (ARCH p.83).
- **Latch vs lock**: see `modelos-de-processos-e-concorrencia-sgbd.md` section 6 (ARCH p.83-84).
- **WAL presupposes strict 2PL**: on rollback, the recovery code must change pages/tuples that the transaction already changed and, for that, it needs the locks; under non-strict 2PL, a transaction that released locks before aborting may not be able to reacquire them (ARCH p.96).

## 3b. Concurrency in B+-tree indexes: latches, latch coupling (crabbing) and right-link [from source] (ARCH p.92-97)
- **Why not 2PL on index pages**: the pages of a B+-tree go through the buffer pool like data pages, and using two-phase locks on them would force **every transaction that touches the index to lock the root of the tree until commit**, "a recipe for limited concurrency" (ARCH p.92). Schemes based on **latches** were developed that avoid transactional locks on index pages. The key idea: **modifications to the physical structure of the tree (such as splitting pages) can be done non-transactionally**, as long as concurrent transactions keep finding the correct data in the leaves (ARCH p.92).
- **Three families** (ARCH p.92-93):
  1. **Conservative**: several transactions access the same pages only if it is guaranteed that they do not conflict; for example, a reader traversing a full internal page while an insertion below may need to split it. They sacrifice too much concurrency compared with the following ones (ARCH p.92).
  2. **Latch coupling ("crabbing")**: the tree traversal latches each node **before** visiting it and only **releases** a node's latch when the **next node to visit has already been latched successfully**. The name comes from the crab's movement: "hold" a node, "grab" the child, release the parent and repeat. It is used in some commercial systems; IBM's **ARIES-IM** version is well described in the literature and includes details and corner cases (sometimes it must **restart traversals after splits** and even put very short-lived latches on the whole tree) (ARCH p.92). Package note: the text does not describe the variant "release the parent when the child is safe"; the book's rule is to release the parent **after latching the child**.
  3. **Right-link**: a **link from each node to its right neighbor** is added to the B+-tree. On descent there is **no latch coupling**: each node is latched, read and unlatched. The intuition: if the transaction follows a pointer to a node *n* and discovers that *n* was split in the meantime, it detects this and **"moves right"** through the links to find the correct location. Some systems also have backward links (reverse traversal) (ARCH p.93).
- **Only valid for B+-trees**: Kornacker et al. discuss the differences and point out that **latch coupling only applies to B+-trees** and does not work for index trees over more complex data (for example, geographic data) that have no single linear order. **PostgreSQL's Generalized Search Tree (GiST) is based on the extensible right-link scheme of Kornacker et al.** (ARCH p.93).
- **Logging of physical structures** (ARCH p.93): structural index changes do not need to be undone when the associated transaction aborts (if a page was split by an insertion whose transaction aborts, there is no rush to undo the split). This creates the challenge of labeling some log records as **redo-only**; ARIES offers **nested top actions**, which let recovery "skip" the records of physical-structure modifications without special code (see `wal-recuperacao-e-algoritmo-aries.md`).
- **Interdependencies** (ARCH p.96-97): access methods complicate concurrency and recovery; most leading DBMSs only implement **heap files and B+-trees** as transactionally protected access methods, and **PostgreSQL's GiST implementation is a "notable exception"** (ARCH p.96). The latching, locking and logging logic is specific to each access method, "not generic". The right-link scheme for B+-trees **assumes that tree pages never "re-merge" after a split**, and this assumption requires the recovery scheme to use a mechanism such as **nested top actions** so as not to undo splits generated by aborted transactions; the dependency holds in both directions (the concurrency protocol may depend on the recovery logic and vice versa) (ARCH p.97). Optimistic and multiversion concurrency schemes generally **ignore access methods** or mention them only superficially, which makes it hard to combine mechanisms (ARCH p.96-97).
- `[inference]` short answer to "why isn't the split undone on rollback?": the book says the split need not have any effect on the tuples seen by other transactions (ARCH p.93); the explanation that other transactions may already have used the new structure is the natural reading, not a sentence from the book.

## 4. ANSI standard isolation levels [from source]
- The standard defines four levels: **READ UNCOMMITTED** (reads any version, no read locks), **READ COMMITTED** (reads committed data; repeated reads may see different versions; read lock released right after access), **REPEATABLE READ** (reads a single committed version; read lock held until the end) and **SERIALIZABLE** (ARCH p.85). Writes always have write locks held until the end at all levels (footnote, ARCH p.85).
- REPEATABLE READ seems to give full serializability, but does not because of the **phantom problem**: 2PL at tuple granularity does not prevent new inserts that satisfy the predicate; a table lock prevents it, but is restrictive (ARCH p.85-86). Phantom protection with an index uses **next-key locking** (an insert requires an exclusive lock on the next key; readers request a shared lock on the next key), which can **lock too much** (example: a scan from 1 to 10 with keys 1, 5 and 100 locks up to 100) (ARCH p.94-95).
- Berenson et al. show that neither Gray's work nor the ANSI standard defines the levels in a truly declarative way, since both assume locking (ARCH p.86); the Red Book says the same: the standard is ambiguous and does not cover Snapshot Isolation (REDBK p.29).
- Additional vendor levels: **CURSOR STABILITY** (against the "lost update" of READ COMMITTED; holds a lock on the last item read by the cursor) (ARCH p.86); **SNAPSHOT ISOLATION** (operates on the version at the start of the transaction; start and end timestamps; commits only if no overlapping transaction wrote the same data; **"first committer wins"** applies) (ARCH p.87); Oracle's **READ CONSISTENCY** (each statement sees values committed at the start of the statement; keeps only the most recent version and reconstructs old versions by applying undo records; writers hold long locks, so **the first writer wins** and the second waits) (ARCH p.87).
- Weak isolation is the default in practice: SQL Server uses READ COMMITTED as the default; this leaves the ACID "I" without a guarantee, and the application must reason about subtleties (ARCH p.88). In a survey cited in the Red Book, only 3 of 18 SQL/NewSQL databases offered serializability by default and 8 did not offer it at all; Oracle's "serializable" is Snapshot Isolation (REDBK p.28). The Red Book gives the example of two concurrent withdrawals from an account under READ COMMITTED and the Flexcoin incident (REDBK p.29).
- Gray's Degree 3 = serializable strict 2PL; Degree 2 today would be Repeatable Read and Degree 1, Read Committed, according to the Red Book (REDBK p.17).

## 5. Who uses what (2007) [DATED]
Production: ACID, WAL and 2PL, **except PostgreSQL**, which uses MVCC for everything; Oracle pioneered MVCC side by side with locking (Snapshot Isolation and Read Consistency, the latter being the default in Oracle) (ARCH p.97-98). MySQL: MyISAM with table locks and InnoDB with row locks, neither with System R's hierarchical locking (ARCH p.98).

## 5b. Weak isolation, ORMs, NoSQL and Dynamo in the Red Book [from source] (REDBK p.29-30)
- Example: with weak isolation that allows concurrent writes to the same item (Read Committed), two users can **withdraw more money than is in the account** (each reads the balance, computes the new total and writes); "this is not a hypothetical scenario": the Flexcoin case, in which an attacker systematically exploited the behavior with non-transactional read-modify-write cycles (a vulnerability under Read Committed and, with a more sophisticated access pattern, under Snapshot Isolation) (REDBK p.29).
- Few developers know they are running under non-serializable isolation; **many open-source applications on top of ORMs assume serializable isolation**, which leads to integrity violations on common engines. Those who do know use application techniques, such as acquiring locks explicitly (`SELECT FOR UPDATE`) and **introducing false conflicts** (writing to a dummy key under Snapshot Isolation), which the text calls **"highly error-prone"** and which negates many of the benefits of the transaction concept (REDBK p.29). Weak isolation specifications are "often incomplete, ambiguous and even imprecise" (REDBK p.29).
- The most convincing argument for weak isolation "working" in practice: few applications have a high degree of concurrency; without concurrency, most weak-isolation implementations give serializable results. At Facebook, only 0.0004% of the results from the eventually consistent store were "stale" (REDBK p.29).
- **NoSQL and isolation** (REDBK p.30): with Internet-scale services and cloud computing, weak isolation became more prevalent; distribution aggravates the cost of serializability and, with partial failures, transactions can block indefinitely. NoSQL stores often pursue **higher availability with weaker models** and an explicit focus on fault tolerance. The text notes the irony: **"while NoSQL stores are often associated with the use of non-serializable guarantees, classic RDBMSs also do not provide serializability by default"** (REDBK p.30).
- **Dynamo** (Amazon, SOSP 2007; REDBK p.30): created for high availability and low latency in the shopping cart; it combines quorum replication, anti-entropy with Merkle trees, consistent hashing and *version vectors*. The system is **entirely non-transactional, offers no atomic operations** (for example compare-and-swap) and **relies on the programmer to reconcile divergent updates**; any node can update any item (with hinted handoff). It adopts **optimistic replication**: it accepts writes first and reconciles divergent versions later, with a merge function; presenting divergent versions is friendlier than discarding concurrent updates as Read Committed does, but programmers have to reason about merge functions. Some clones (such as Apache Cassandra) do not offer merge operators and choose the "winning" write by numeric timestamp; others (Basho Riak) use libraries of mergeable types (CRDTs). Dynamo **does not promise read recency**: only that, if writes stop, all replicas end up with the same set of writes (**eventual consistency**), a "remarkably weak" guarantee; there are also "session guarantees" (reading your own writes) (REDBK p.30).
- CAP: the Red Book includes Brewer's 12-year retrospective on the CAP theorem, describing the trade-off between coordination (availability) and strong guarantees such as serializability (REDBK p.30). The text also states that cases such as maintaining indexes and views, constraints and distributed aggregation often **do not require coordination** for "correct" behavior (REDBK p.30).

## 6. Red Book opinions [DATED]
Stonebraker predicts that "nobody will use traditional 2PL" in in-memory OLTP, preferring timestamp ordering or multiversion (REDBK p.22). On failure recovery, the text says the proposed solution is online replication and failover (pioneered by Tandem), and that conventional wisdom (write the log, ship it over the network and redo at the backup site, an **active-passive** architecture) was shown in [6] to be **a factor of 3 inferior** to an **active-active** scheme, in which transactions simply run on each replica. **In an active-active scheme it is necessary to guarantee that transactions run in the same order on each replica, and "unfortunately MVCC does not do this"**, which generated interest in **deterministic concurrency control**, "probably much faster" than MVCC in an end-to-end system (REDBK p.22). Treat this as a 2015 opinion, not as a fact about current DBMSs.

## 6b. Red Book, chs. 2 and 3: System R, Postgres, Gamma, atomic commit and consensus [from source] (REDBK p.14-15, p.18-19) [DATED]
- **System R** (REDBK p.14): an IBM Research project started around 1972 under Frank King; it adopted SQL early and was split into a "lower half" and an "upper half", which did not stay fully in sync (the lower half implemented *links*, like IMS, and the upper half never got the optimizer working for them). In Stonebraker's opinion, System R's greatest **legacy** is the **transaction manager**, the work of Jim Gray, whose design persists in commercial systems; second comes the cost-based **optimizer** with dynamic programming. Criticisms by the same author: nobody cleaned up SQL (the upper half was coupled to VSAM to form DB2) and the subroutine-call interface, today ODBC, is heavyweight (REDBK p.14).
- **Postgres** (REDBK p.14-15): a project started in 1984. The legacy the author highlights is the system of **abstract data types (ADT)**: user-defined types and functions entered most relational DBMSs through the Postgres model. He also credits the importance of Postgres to a robust open-source line, maintained since the mid-1990s by volunteers; the project continued at Berkeley until 1992, when Illustra appeared, and left a generation of implementers (REDBK p.15).
- **Time travel and no-overwrite storage** (REDBK p.14): the Postgres project experimented with *time travel*, which the text says **did not work very well**; the author thinks no-overwrite storage (*no-overwrite storage*) will still have its day, when faster storage changes the economics of data management [DATED].
- **Gamma** (REDBK p.15): built at Wisconsin between 1984 and 1990; in the author's opinion, it popularized the *shared-nothing* approach of tables partitioned across several nodes (Teradata had parallel ideas) and the class of *hash join* algorithms; according to him, practically every data warehouse uses a Gamma-style architecture and shared-disk or shared memory have almost disappeared, and this should continue as long as network latency and bandwidth do not approach those of disk.
- **Atomic commit (AC) and 2PC** (REDBK p.18): AC (*atomic commitment*) guarantees that a transaction executed on several servers (replicas, partitions or both) commits or aborts on all of them. The classic algorithm, from the mid-1970s, is Two-Phase Commit (2PC; not to be confused with 2PL). The interactions between 2PC, local storage and the local transaction manager are complex. Failure example: if the coordinator and a participant crash after the votes, the others do not know whether the crashed one voted YES or NO and cannot safely proceed. **Any AC implementation can block** over an unreliable network; combined with serializable concurrency control, blocking can bring throughput to a halt. Hence there are AC algorithms with relaxed assumptions (synchronous network; failure detectors) (REDBK p.18-19).
- **Presumed Abort and Presumed Commit** (REDBK p.18): variants of 2PC that the chapter's paper presents to improve performance. *Presumed Abort* avoids forcing the abort decision to disk and acknowledging aborts, saving disk and network; *Presumed Commit* makes an analogous saving when most transactions commit.
- **Consensus vs AC** (REDBK p.19): in consensus, **any proposal** can be chosen as long as all processes end up agreeing; in AC, **any participant can vote NO**, and then everyone aborts. This makes consensus an "easier" problem than AC, but **every consensus implementation can also block** in certain scenarios. In modern distributed databases, consensus is usually the basis of **replication** (replicas apply the updates in the same order: *state-machine replication*) and AC is used for transactions that cross **partitions**. Paxos (Lamport) is one of the first consensus implementations; Viewstamped Replication, Raft, ZAB and Multi-Paxos may be more useful in practice because they implement the **distributed log** abstraction instead of a "consensus object". The text notes that the database and distributed computing communities were separate and that this distance narrowed in the cloud era.
- **Paxos Commit** (REDBK p.19): Gray and Lamport collaborated in 2006 on this algorithm, which combines AC and Lamport's Paxos; the text cites it as an example of the convergence between the database and distributed computing communities.

## 7. [inference]
For the package rule "keep transactions short and free of external I/O": ARCH says strict 2PL holds locks until the end (p.80-81) and the server holds resources until the commit is flushed (p.18); from this it is **inferred** that waiting on an external call inside the transaction prolongs the locks. The book gives neither this advice nor the "tens of seconds" numbers.

## 8. [extrapolation] and what the sources do NOT say
- "Growing phase/shrinking phase" and "cascading aborts" (why strict 2PL is preferred) **do not appear** in ARCH or the Red Book; they are general transaction theory. Label them `[extrapolation]` if used.
- **Write skew** is not named in ARCH, REDBK or PG16; PG16 shows a concrete example of a serialization anomaly (PG16 p.529-530). Do not cite a page for the word.
- Victim selection criteria (age, number of locks, rollback cost): ARCH only says "heuristics from the literature" (p.83).
- The principle "readers never block writers..." **is not in ARCH**; it is in the PostgreSQL manual (PG16 p.525).
