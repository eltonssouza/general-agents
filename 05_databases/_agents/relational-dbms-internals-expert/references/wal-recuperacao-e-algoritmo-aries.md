# WAL, checkpoints and recovery (ARIES)

> Pages = PDF. ARCH: printed = N + 140. PG16: printed = N − 38. **Coverage warning**: ARCH does not describe the ARIES phases in detail; it refers to the original paper (ARCH p.88). The summary of the three phases is in the Red Book (REDBK p.18).

## 1. The three WAL rules [from source]
ARCH says that the standard theme of recovery is **Write-Ahead Logging** and that the protocol has **three** simple rules (ARCH p.88-89):
1. Every page modification must generate a log record, and that record must be flushed to the log device **before** the data page is flushed.
2. Log records must be flushed **in order** (record r can only be flushed after all earlier ones).
3. On a commit request, the commit record must be flushed to the log **before** the commit returns successfully.
The book notes that many people only remember the first, but all three are necessary; rule 1 guarantees atomicity (undo), and rules 2 and 3 together guarantee durability (redo) (ARCH p.89). The ordering requirement between log and data also explains why OS buffering gets in the way (ARCH p.72-73).

## 2. Buffer policies: DIRECT, STEAL/NOT-FORCE [from source]
Most commercial systems run in "DIRECT, STEAL/NOT-FORCE" (Haerder and Reuter): data is updated in place; unpinned frames may be "stolen" (written) even with uncommitted data; pages do **not** need to be forced to disk before commit (ARCH p.89). This gives freedom to the buffer manager, but obliges the log to undo stolen pages of aborted transactions and to redo unforced pages of committed transactions (ARCH p.89-90). The Red Book calls ARIES the canonical algorithm for "No Force, Steal" recovery (REDBK p.18).

## 3. Physical, logical and "physiological" logging; checkpoints [from source]
- Logical logging is smaller, but undo/redo becomes complicated and can degrade recovery; in practice a "physiological" mixture is used. In ARIES, **physical** logging supports REDO and **logical** logging supports UNDO, part of the rule of "repeating history" up to the crash state and then rolling back the transactions (ARCH p.90).
- Instead of starting from the first log record, recovery starts at the **recovery LSN**: the oldest of (a) the record of the oldest change on a dirty page in the pool and (b) the start of the oldest transaction; it is computed periodically at **checkpoints** (ARCH p.90-91).
- A naive checkpoint would force all dirty pages (seconds of delay with a large pool); ARIES uses a **"fuzzy" checkpoint**, whose records are tiny and which does not write pages synchronously (ARCH p.91).
- Rollback also writes log; log space may run out during rollback; this is avoided by reserving space (ARCH p.91).
- Structural index changes can be **redo-only** (they need not be undone on abort); ARIES offers "nested top actions" so recovery can "skip" these records (ARCH p.93). The same idea applies to extending heap files (extent map) (ARCH p.94).

## 4. The three phases of ARIES [from source]
According to the Red Book (REDBK p.18): (1) **analysis**: scans the log forward to find out which transactions were in progress at the crash; (2) **redo**: scans the log again and redoes the effects; (3) **undo**: walks the log backward undoing the effect of uncommitted transactions. The key idea is **"repeating history"**; the undo phase can use the same logic as abort in normal operation (REDBK p.18). The ARIES paper is by Mohan et al. (REDBK p.16) and the algorithm is "from IBM" (REDBK p.18). The Red Book warns that the original paper is complicated because it discusses alternatives and index details (nested top actions, logical undo) (REDBK p.18).

## 5. PostgreSQL [from source]
- **Concept**: changes to the data files are only written after the WAL records describing them have been flushed; data pages do not need to be flushed at every commit; after a crash the missing changes are redone (REDO, "roll-forward") (PG16 p.898). Only the WAL needs fsync to confirm the transaction; it is sequential; one fsync can serve many simultaneous commits (PG16 p.898).
- Journaling file systems are not necessary for the reliability of the data files and the WAL (PG16 p.898).
- Each page has in its header the **`pd_lsn`** field (8 bytes): the LSN of the last WAL record for the last change to the page (PG16 p.2574).
- **Partially written pages**: PG writes full-page images to the WAL (`full_page_writes`) before modifying the page (PG16 p.897); each WAL record is protected by CRC-32C; **page checksums are not enabled by default** (PG16 p.897-898).
- (Default values of `max_wal_size`, `min_wal_size`, `checkpoint_timeout`, `wal_buffers`, `wal_compression`, `wal_log_hints` and other WAL parameters: `postgresql-16-configuracao-memoria-wal-checkpoint-timeouts-e-locks.md`.)
- **Checkpoints**: write all dirty pages and a special record to the WAL; recovery starts from the last checkpoint (the "redo record"); automatic every `checkpoint_timeout` (default 5 min) or when `max_wal_size` (default 1 GB) is about to be exceeded; `checkpoint_completion_target` default 0.9 spreads the writing (PG16 p.900-901). The first modification of a page after each checkpoint writes the full page to the WAL, so more frequent checkpoints increase the WAL volume (PG16 p.900).
- **Asynchronous commit** (`synchronous_commit` off): the server responds before the WAL goes to disk; risk of **losing the last transactions**, not of corruption; the risk window is at most 3× `wal_writer_delay` (PG16 p.899). Different from `fsync = off`, which turns off the synchronization logic and can cause **arbitrary corruption** after an OS crash (PG16 p.900).
- **`commit_delay`, per-transaction mode and immediate shutdown in asynchronous commit**: `commit_delay` looks like asynchronous commit, but it is a **synchronous** flush-grouping mechanism and is **ignored** during an asynchronous commit (PG16 p.900). The commit mode is chosen **per transaction** (the value of `synchronous_commit` at the start of the commit applies), so synchronous and asynchronous transactions coexist; certain utility commands, such as `DROP TABLE`, and the two-phase commit commands, such as `PREPARE TRANSACTION`, are **always synchronous** whatever the setting (PG16 p.899). A shutdown in **immediate** mode is equivalent to a crash and loses asynchronous commits not yet flushed (PG16 p.899). With no WAL written since the previous checkpoint, the new checkpoint is **skipped** even after `checkpoint_timeout` has passed (PG16 p.900).
- **WAL on disk: `pg_wal`, LSN, 16 MB segments and 8 kB page**: the insertion position is an **LSN**, a byte offset that grows monotonically (type `pg_lsn`, comparable to measure the volume between two positions); the files live in `pg_wal`, in **16 MB segments** (changeable with initdb's `--wal-segsize` option), divided into 8 kB pages (changeable only **at compile time**, with configure's `--with-wal-blocksize` option); segments receive increasing numbers and **the numbering does not wrap around** (PG16 p.903). It is advantageous to put the WAL on another disk: **with the server stopped**, move the `pg_wal` directory and create a symbolic link in the old place (PG16 p.903). The WAL guarantee can be subverted by disks that report a write as completed when they have only put it in cache; a power failure like that can cause unrecoverable corruption (PG16 p.903).
- For sites that do not require the durability guarantee (the manual's words; "disposable load" would be `[inference]`), the manual lists "non-durable" settings: directory on a RAM disk, `fsync` off, `synchronous_commit` off, `full_page_writes` off, larger `max_wal_size` and `checkpoint_timeout`, and **UNLOGGED tables** (not crash-safe) (PG16 p.563). `[inference]` this shows that `fsync = off` is a conscious choice to give up durability, not "the anti-pattern" in itself; the manual does not call it an anti-pattern, it only describes the risk (p.900).

## 6. [extrapolation] and what the sources do NOT say
- **Dirty Page Table, Transaction Table, `recLSN`, `UndoNextLSN` and CLRs (Compensation Log Records)**, the `pageLSN > flushedLSN` check before eviction, and redo idempotence by LSN comparison are descriptions from v1 that are **not** in ARCH or the Red Book. They are standard knowledge about ARIES (the Mohan et al. paper), useful, but label them `[extrapolation]`.
- "64-bit" LSN: PG16 says `pd_lsn` occupies 8 bytes (PG16 p.2574); ARCH does not mention the size.
- "ARIES invalidated by fsync off" and "maintenance in single-user mode" are v1 sentences with no backing.
- The "IBM Almaden Research" origin of ARIES is not in the sources (only "IBM", REDBK p.16, p.18).
