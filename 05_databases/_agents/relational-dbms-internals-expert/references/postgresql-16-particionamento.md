# PostgreSQL 16: table partitioning (declarative, inheritance and pruning)

> Pages = PDF; PG16 printed = N − 38. Main source: PG16 section 5.11 (p.132-145). The SQL commands cited are from the manual; numeric examples from the package are `[derived]` or `[extrapolation]` and say so.

## 1. What it is for and when it is worthwhile [from source]
- Partitioning is splitting what is logically one large table into smaller physical pieces. Benefits (PG16 p.132): (1) query performance can improve greatly when the heavily accessed rows are in one or a few partitions, since partitioning "replaces" the upper levels of the indexes and helps the hot part fit in memory; (2) when the query or update accesses a large part of a single partition, a sequential scan of it can beat an index lookup; (3) bulk loads and removals become adding or removing partitions, and `DROP TABLE` or `DETACH PARTITION` avoid the VACUUM cost of a mass DELETE; (4) rarely used data can go to cheaper media.
- In general it is only worthwhile when the table would be very large; a rule of thumb from the manual is that the table size exceeds the server's physical memory (PG16 p.132).
- Supported forms (PG16 p.132-133): **range** (non-overlapping ranges; inclusive lower bound and exclusive upper bound, so the value 10 belongs to the partition that starts at 10), **list** (listed values) and **hash** (modulus and remainder). Other forms require inheritance or `UNION ALL` views, with flexibility but without some of the performance gains of declarative partitioning (PG16 p.133).

## 2. Declarative partitioning [from source]
- **Partition key (*partition key*): what it is** (PG16 p.133): it is the column, set of columns or expressions listed by `PARTITION BY` (by range, list or hash); the server routes each row by the key. In hash partitioning, the row goes to the partition whose remainder of dividing the key's hash value by the modulus matches the declared one. **Updating the key** of a row moves it to another partition if it no longer satisfies the bounds of the original. To create a `PRIMARY KEY` or `UNIQUE` on the partitioned table, the key cannot have expressions or function calls and the constraint columns must include all the key columns (PG16 p.137, section 4). It is not the *partition key* of a distributed NoSQL database (Cassandra, Dynamo), which the package does not cover.
- The partitioned table is "virtual": it has no storage of its own; rows go to partitions, which are ordinary tables, routed by the key value; updating the partition key moves the row to another partition if it no longer satisfies the bounds of the original. Partitions can be sub-partitioned, have their own indexes, constraints and defaults, and be foreign tables (with care: ensuring the content respects the rule is the user's responsibility) (PG16 p.133).
- An ordinary table cannot be converted into a partitioned one or vice versa, but an existing table can be attached (`ATTACH PARTITION`) as a partition or removed (`DETACH PARTITION`), which simplifies maintenance (PG16 p.133).
- Steps of the `measurement` example (PG16 p.134-135): `CREATE TABLE ... PARTITION BY RANGE (logdate)`; create partitions with `FOR VALUES FROM (...) TO (...)` (overlapping bounds raise an error, and adjacent partitions can share the bound value, since the upper one is exclusive); create the index on the key and on other columns **on the partitioned table**, which creates the corresponding index on each existing and future partition (the index on the key is "not strictly necessary", but usually helps); make sure `enable_partition_pruning` is not turned off (PG16 p.134-135).
- Inserting into the parent a row that fits no existing partition causes an **error**; the appropriate partition must be created (PG16 p.135). There is also the `DEFAULT` partition (PG16 p.136), which receives whatever does not match the others `[inference]` from how the manual treats it when attaching new partitions.
- The manual suggests a script that generates the monthly DDL (PG16 p.135).

## 3. Maintenance: DROP, DETACH, ATTACH and locks [from source]
- Removing old data: `DROP TABLE partition` deletes millions of records quickly, but requires an `ACCESS EXCLUSIVE` lock on the parent table. A frequent alternative: `ALTER TABLE ... DETACH PARTITION`, which keeps the data as an independent table (allowing backup with COPY or pg_dump, aggregation or reporting before discarding). The normal form requires `ACCESS EXCLUSIVE` on the parent; with `CONCURRENTLY` it requires only `SHARE UPDATE EXCLUSIVE` on the parent, with restrictions described in the statement's manual page (PG16 p.135).
- Adding a partition: creating the table **outside** the structure and attaching it later allows loading, checking and transforming the data before it becomes visible; `ATTACH PARTITION` requires only `SHARE UPDATE EXCLUSIVE` on the partitioned table, whereas `CREATE TABLE ... PARTITION OF` requires `ACCESS EXCLUSIVE` (PG16 p.136). `CREATE TABLE ... LIKE ... INCLUDING DEFAULTS INCLUDING CONSTRAINTS` avoids repeating the definition (PG16 p.136).
- **Before `ATTACH`, create a `CHECK` equal to the expected partition's constraint**: this way the system skips the scan that validates the implicit constraint; without the `CHECK`, the table is scanned **with `ACCESS EXCLUSIVE` on the partition**. After `ATTACH`, it is advisable to remove the redundant `CHECK`. If the partitioned table has a `DEFAULT` partition, it is also worth creating a `CHECK` that excludes the new partition's constraint, otherwise the `DEFAULT` is scanned (with `ACCESS EXCLUSIVE` on it) to verify that it contains no rows that belong to the new partition; this applies recursively to sub-partitions (PG16 p.136).
- **Indexes on partitions**: creating an index on the partitioned table applies to the whole hierarchy, but `CONCURRENTLY` **cannot** be used on it. To avoid long locks: `CREATE INDEX ... ON ONLY table` (the index is left invalid and does not propagate), create the partitions' indexes with `CONCURRENTLY` and attach them with `ALTER INDEX ... ATTACH PARTITION`; when all are attached, the parent index becomes valid. The technique applies to `UNIQUE` and `PRIMARY KEY` constraints (PG16 p.136-137).

## 4. Limitations [from source] (PG16 p.137-138)
- **Primary/unique key**: partition keys cannot include expressions or function calls, and the constraint columns must **include all the partition key columns**, because each index only guarantees uniqueness within its own partition; it is the partition structure that guarantees there are no duplicates across them. `[derived]` with `PARTITION BY RANGE (ts)`, a `PRIMARY KEY (id)` is rejected; `PRIMARY KEY (id, ts)` works, and this does **not** guarantee `id` is unique by itself.
- There is no exclusion constraint spanning the whole partitioned table (only per leaf partition); `BEFORE ROW` INSERT triggers cannot change the destination partition; temporary and permanent relations cannot be mixed in the same tree (PG16 p.137).
- Partitions cannot have columns absent from the parent; `ATTACH PARTITION` requires identical columns; the parent's `CHECK` and `NOT NULL` are always inherited; `ONLY` on constraints only works without partitions (except `UNIQUE`/`PRIMARY KEY`); `TRUNCATE ONLY` on a partitioned table always errors (PG16 p.137-138).

## 5. Partition pruning [from source]
- Definition: the planner examines each partition's definition and **proves** that it could not contain rows that satisfy the `WHERE`; if it can, it excludes (prunes) the partition from the plan; compare with `EXPLAIN` and `enable_partition_pruning` on/off (PG16 p.142-143).
- Pruning is driven by the key's implicit bounds, **not by the existence of indexes**; creating an index on the key depends on whether the query reads much or little of the partition (PG16 p.143).
- **Pruning also at execution (run-time pruning)** (PG16 p.143-144): useful for values unknown at planning time (`PREPARE` parameters, a subquery value, a parameter on the inner side of a nested loop). When: (a) at **plan initialization**, for parameters already known at that stage; partitions pruned there do not appear in `EXPLAIN`, the number removed appears as `Subplans Removed`, and **pruned partitions are still locked at the start of execution**; (b) **during plan execution**, for values only known at run time; pruning is redone when the parameter changes, and `EXPLAIN ANALYZE` shows different `loops` per subplan and `(never executed)` for those always pruned (PG16 p.143-144).
- **Constraint exclusion** (PG16 p.144): a similar technique, but based on `CHECK` (pruning uses partition bounds), at planning time only, slower; default `partition`. It only works with constants (or external parameters); a comparison with a non-immutable function such as `CURRENT_TIMESTAMP` cannot be optimized. Keep constraints simple (comparisons of the column with constants using B-tree-indexable operators); many children increase planning time: with inheritance it works well up to perhaps a hundred children, not thousands (PG16 p.144).
- **Rule for counting touched partitions** (package correction after round 2's blind test): a query touches **all partitions whose range can contain rows that pass the `WHERE`**; what decides is the **shape of the predicate**.
  - `[derived]` with monthly partitions from January to December and a `WHERE ts >= X AND ts < Y` with **both bounds** constant and a 7-day window, at most **2** partitions are touched (a 7-day window crosses at most one month boundary).
  - With only a **lower bound** (`WHERE ts >= now() - interval '7 days'`, no `ts <= ...`) the predicate excludes nothing **above** X: the window's partitions **and all existing future partitions** are touched (for example pre-created months), plus the `DEFAULT` partition if there is one. `[inference]` from the definition of pruning as proof that the partition cannot contain rows that satisfy the `WHERE` (PG16 p.142-143): without an upper bound the planner cannot prove this for ranges above X.
  - For `now()`, which is stable and not constant, the manual does not say explicitly at which phase pruning occurs; run-time pruning with values only known at execution is described in PG16 p.143-144, and treating `now()` as that case is `[inference]`, to be confirmed with `EXPLAIN` (the `Subplans Removed` and `never executed` nodes). For a `CURRENT_TIMESTAMP` in inheritance with constraint exclusion, the manual says it **cannot** be optimized (PG16 p.144).
  - Practical lesson: for the window to stay at 2 partitions, also write the upper bound (`AND ts < now()` or a constant).

## 6. Inheritance as partitioning (legacy) [from source]
It allows features that declarative lacks (children with extra columns, multiple inheritance, free splitting criterion), with more work: children with mutually exclusive `CHECK`s (the manual warns that `BETWEEN 100 AND 200` and `BETWEEN 200 AND 300` is an error due to overlap and recommends `>=` and `<`), an index on each child and INSERT redirection by trigger (which returns `NULL` so as not to also insert into the root) or by rules (which have more overhead per query, but pay it once per query and not per row; `COPY` ignores rules) (PG16 p.138-141). Caveats: manual `VACUUM` and `ANALYZE` must run on each child (an `ANALYZE measurement` processes only the root), `ON CONFLICT` does not work as expected, and an UPDATE that changes the key fails because of the `CHECK`s (PG16 p.142).

## 7. Best practices [from source] (PG16 p.144-145)
- Choose the partition column by the one that appears most in the `WHERE` (pruning needs compatible clauses), also considering `PRIMARY KEY`/`UNIQUE` requirements and data removal (design so that what will be removed together falls in a single partition).
- The number of partitions is decisive: too few leave large indexes and poor locality; too many increase planning time and memory in planning and execution, because the metadata of each touched partition is loaded into the memory of **each session**. The planner handles hierarchies of up to a few thousand partitions well if typical queries prune almost all of them. In a data warehouse more partitions can be used than in OLTP. Redoing the partitioning of a lot of data is "painfully slow"; simulate the load; **do not assume that more or fewer partitions is better**.
- Manual example: with one partition per customer and a few large customers today, future growth to many small customers can make `LIST` unworkable; `HASH` with a reasonable number of partitions would be more robust (PG16 p.145).
- Sub-partitioning or multicolumn range easily lead to too many partitions (PG16 p.145).

## 8. What the manual does NOT say / [extrapolation]
- A "right" number of partitions, or a size in GB per partition: the manual only gives a rule of magnitude (table larger than memory; "a few thousand" partitions with good pruning).
- Statistics: see `procedimentos.md` P9; `[extrapolation]` autovacuum does not ANALYZE the parent table (already recorded in `casos-e-antipadroes.md` item 9, PG16 p.790-791); the inheritance manual says `ANALYZE measurement` processes only the root (PG16 p.142).
- The duration of each lock in a real environment: the manual indicates the lock mode, not the time.
