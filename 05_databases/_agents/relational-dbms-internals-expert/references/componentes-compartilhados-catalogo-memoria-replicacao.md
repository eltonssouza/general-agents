# Shared components: catalog, memory, disks, replication and utilities

> Pages = PDF. ARCH: printed = N + 140. PG16: printed = N − 38. Covers Section 7 of ARCH (p.100-110) and the conclusion (p.111). Replication in PostgreSQL 16 (WAL shipping, logical, HA) is in `postgresql-16-backup-pitr-e-replicacao-ha.md`.

## 1. Catalog (the catalog manager) [from source]
- The catalog stores the names of entities (users, schemas, tables, columns, indexes etc.) and their relationships and is itself stored as **database tables**, in the same format as the data. This makes the system more compact and allows metadata to be queried with the same language; the article says that ignoring this lesson in early implementations is usually a cause of regret (ARCH p.100).
- For efficiency the catalog is treated specially: the highest-traffic parts are materialized in memory in "denormalized" structures (networks of objects), used by the parser and the optimizer; catalog data is also cached in plans; catalog tables get transactional tricks to reduce hot spots. A cited ERP had more than 60,000 tables, with 4 to 8 columns each, typically with two or three indexes per table (ARCH p.101).

## 2. Memory allocator [from source]
- Besides the buffer pool, the DBMS uses a lot of memory: Selinger-style optimization accumulates state in the dynamic programming; hash joins and sorts allocate memory at execution time (ARCH p.101).
- Commercial systems use a **context-based allocator** ("memory contexts"): a context keeps a list of contiguous regions of virtual memory; the API creates a context (with a name or type, which tells the allocator the allocation pattern: the optimizer grows in small increments, hash joins allocate in a few large batches), allocates in a context, frees a piece (uncommon), **deletes the whole context** or **resets** it ("reset") (ARCH p.101-102).
- Advantages: a low-level, programmer-controlled alternative to the garbage collector (the optimizer allocates in the query context and, when choosing the plan, copies the plan to the executor context and deletes the optimizer context in one go, without walking structures) and spatial and temporal control of deallocation; also a performance gain, since it avoids many expensive `free()` calls and dispenses with the compaction logic of `malloc()`. The article recommends looking at the open-source code of PostgreSQL, which has a sophisticated allocator (ARCH p.102-103).
- **Memory for operators** (ARCH p.103-104): vendors diverge. Some (the example is DB2 for zSeries) let the DBA fix the RAM for sorts and hash joins and guarantee that RAM to each query, with admission control honoring the guarantee: stability, but the DBA statically decides how to balance buffer pool and operators. Others (the example is SQL Server) automate the distribution, taking operator memory from the buffer pool itself and using the OS allocator only for contiguous requests larger than a pool page. It is the same philosophical split as plan recompilation (see `otimizacao-de-consultas-e-planos-de-execucao.md` section 3) `[DATED]`.
- In PostgreSQL, the practical equivalent of per-operator limits is in the `work_mem` and `hash_mem_multiplier` parameters (PG16 p.654-655; see the same optimization reference).

## 4. Replication services [from source] (ARCH p.106-108)
- **Reasons**: keep a *warm standby*, slightly behind, in a different physical location to continue after a fire or catastrophe; or offer a pragmatic kind of distributed database for geographically dispersed companies (partitioning by region with updates on the local primary and queries that mix fresh local data with slightly delayed replicated data) (ARCH p.106-107).
- **Three typical schemes** (ignoring hardware replication), of which only the third has the performance and scale of high-end environments, at the cost of being the hardest to implement (ARCH p.107):
  1. **Physical replication**: duplicate the whole database every period; does not scale (bandwidth to send and cost to reinstall), it is hard to guarantee a transactionally consistent snapshot; used only as a low-level customer solution, and most vendors do not support it with software.
  2. **Trigger-based replication**: triggers on the tables write a "difference" record to a special replication table, which is sent and "re-executed" at the destination; solves the problems of the physical approach, but with a performance penalty that is unacceptable for some workloads.
  3. **Log-based replication**: the preferred solution when feasible. A *log sniffer* intercepts the log writes and delivers them to the remote system. Two broad techniques (ARCH p.107-108): (1) read the log and **build SQL commands** to re-execute at the destination; (2) read log records and **send them** to a destination in "perpetual recovery", which reapplies them as they arrive. SQL Server, DB2 and Oracle implement both; SQL Server calls the first Log Shipping and the second Database Mirroring.
- Advantages of the log (ARCH p.108): low overhead invisible to the running system; incremental updates, scaling with the size of the database and the update rate; reuses DBMS mechanisms; and yields **transactionally consistent** replicas through the log's own logic. Log replication between different vendors is much harder, because it requires understanding the other's log format (ARCH p.108).
- `[inference]` this two-flavor scheme corresponds, in PostgreSQL, to WAL shipping by file or streaming (reapplication of the log at the destination, physical) and to logical replication (interpretation of the log into data changes); the correspondence is mine, the article is from 2007 and does not name PG (see PG16 p.816, p.924).

## 5. Administration, monitoring and utilities [from source] (ARCH p.108-110)
Utilities are rarely evaluated in benchmarks, but they determine manageability, and the technical challenge is running them **online**, with queries and transactions in progress (the overnight "reorganization window" no longer exists in 24x7 operations) (ARCH p.108).
- **Optimizer statistics**: scan tables to build statistics; histograms are hard to build in a single pass without exhausting memory; the article cites the work of Flajolet and Martin on counting distinct values (ARCH p.108-109).
- **Physical reorganization and index building**: space becomes fragmented by insertion and deletion patterns; reclustering or repartitioning in the background is hard to do without holding locks for a long time and while maintaining physical consistency (ARCH p.109).
- **Backup/export**: all DBMSs do a physical dump; since it takes long, locks cannot be used naively; most do a **"fuzzy"** dump and complement it with log logic to guarantee transactional consistency (ARCH p.109).
- **Bulk load**: an optimized utility, backed by custom code in the storage manager, for example bulk loading of B+-trees, much faster than repeated inserts (ARCH p.109).
- **Monitoring, tuning and resource governors**: performance counters via SQL "virtual tables"; history in some systems; alerts when a query exceeds limits on time, memory or locks (possibly aborting the query); tools such as IBM's Predictive Resource Governor try to prevent heavy queries from running (ARCH p.109-110).
- `[inference]` these topics have equivalents in the PostgreSQL manual (ANALYZE, CREATE INDEX CONCURRENTLY, `pg_basebackup`, COPY, `pg_stat_*` views), but the article does not name them; for the PG pages, see the PG16 references.

## 6. Conclusion of the article (ARCH p.111)
Modern commercial systems are founded on academic research and industrial experience; writing a complete, high-performance relational DBMS is an enormous investment, but many lessons transfer to other data-services domains (ARCH p.111).

## 6b. PostgreSQL: the `pg_collation` catalog [from source] (PG16 p.2309)
- `pg_collation` describes the available collations, which are mappings from an SQL name to operating-system locale categories. Columns: `collname`, `collnamespace`, `collowner`, `collprovider`, `collisdeterministic`, `collencoding` (encoding in which it is valid, or -1 if it works for any), `collcollate`, `collctype`, `colliculocale`, `collicurules` and `collversion` (PG16 p.2309).
- **`collprovider` and `collversion`** (PG16 p.2309): `collprovider` is `d` (database default), `c` (libc) or `i` (icu). The `collversion` is recorded when the collation is created and checked on use, to detect definition changes that could corrupt data.
- The catalog's **unique key** is (`collname`, `collencoding`, `collnamespace`), not just name and schema. PostgreSQL ignores collations whose `collencoding` is neither that of the current database nor -1, and it is forbidden to create an entry with the same name as one with `collencoding = -1`. Therefore **the qualified name (schema.name) is enough to identify a collation**, although it is not unique by the catalog's definition. The catalog is defined this way because `initdb` fills it, at cluster creation, with the locales available on the system for all possible encodings (PG16 p.2309).
