# SQL injection prevention and parameterization

## 1. What the book says [from source]
- **Albert Gonzalez (opening case of the chapter)**: the chapter opens with the case of Albert Gonzalez, convicted in March 2010 of the largest identity theft in history, with about 130 million credit and debit card numbers from large retail chains and processors. He beat his own previous record, 45.6 million cards in 2006, obtained by exploiting vulnerable wireless networks (the "almost triple" calculation is [derived]: 130 / 45.6 ≈ 2.85). The larger attack, according to the cited indictment, used **SQL Injection** to gain privileged access and upload files to the victims' servers, where "sniffer" programs that captured the card data were installed. The passage **does not state the total financial loss in dollars**. The chapter states that the flaw is one of the most common on the internet, partly because developers do not understand the nature of the vulnerability, and defines dynamic SQL as SQL assembled as a string with application variables (ANTI-INJ p.5).
- **Objective**: writing dynamic SQL queries (assembled as a string with application variables) is natural and useful; the hard part is making the software secure (ANTI-INJ p.5-6).
- **Antipattern "Execute Unverified Input As Code"**: injection occurs when interpolated content changes the **syntax** of the query in unintended ways; classic example: the value `1234; DELETE FROM Bugs` terminates the command and executes another (ANTI-INJ p.6). An "honest accident" is the name `O'Hare` breaking the string (ANTI-INJ p.6-7); the greater risk is the attacker manipulating the command, such as `userid=123 OR TRUE` in an UPDATE that now changes all accounts (ANTI-INJ p.7-8).
- **Key principle**: injection works by **altering the SQL syntax before it is parsed**; if you insert dynamic parts before the parse, there is risk (ANTI-INJ p.8).
- **"Quest for a cure"**: no single technique is proof against all forms of injection, "so you need to use all of them, in different cases" (ANTI-INJ p.8).
  - **Escaping values** (doubling quotes, backslash, PDO's `quote()`): reduces the risk of unpaired quotes, but does not work well for **non-string** content: `'123 OR TRUE'` becomes a literal and, besides, comparing a numeric column with a string does not work in all databases; there are also "obscure corners" in which strings of non-ASCII character sets pass through an escape function leaving quotes unescaped (**footnote 4** on p.9 refers to a MySQL bug by the URL `http://bugs.mysql.com/8378`; the book **does not state the version or character set** involved, so do not invent them). In standard SQL you must use `CAST()` on purpose to convert a string to a number; some databases do the conversion implicitly, others do not (ANTI-INJ p.8-9).
  - **Query parameters**: "very often cited as a panacea"; they are "a **very strong** defense", but **not universal** because the parameter value is always interpreted as **a single literal value**: they do not accept a **list of values** (`IN (?)` with `"1234,3456,5678"`), **table identifier**, **column identifier** (`ORDER BY ?` becomes a constant) nor **SQL keyword** (`DESC`) (ANTI-INJ p.9-11).
  - **Stored procedures**: contain fixed SQL parsed at definition time, but can use dynamic SQL insecurely; using dynamic SQL inside a procedure is "no more or less safe" than in the application (ANTI-INJ p.11).
  - **Data access frameworks**: saying they protect is false for any framework that allows writing SQL as a string; the book's analogy is that a framework prevents injection "the way a toothbrush prevents cavities": you have to use it consistently (ANTI-INJ p.11-12).
- **Box "What Was My Complete Query?"**: parameters are **not** a way of "quoting" automatically; the server parses the SQL when preparing the query and after that **nothing can change the syntax**; the values are supplied at execution, one per placeholder, and the DBMS keeps query and values separate, which is good for security; therefore the retrieved prepared query does not contain the values; to debug, log the statement with placeholders at prepare and the values at execute (ANTI-INJ p.12). `[inference]` (package deduction, not in the book): a log that shows the SQL already with the values embedded was assembled by the application code or by the logging layer, not by the server.
- **How to recognize it**: practically every application assembles SQL dynamically; **if any part** of a statement is assembled by concatenation or interpolation, it is potentially exposed; "assume you have some vulnerabilities" in any SQL application, unless you have just done a specific code review (ANTI-INJ p.12).
- **Legitimate uses**: there are no legitimate reasons to have this vulnerability; it is the developer's responsibility to write defensive code (ANTI-INJ p.12-13).
- **"Rule #31: Check the Back Seat"**: injection can be **indirect**; data inserted safely through parameters can be used later to assemble dynamic SQL (example of the surname read from the database and concatenated into a `MATCH ... AGAINST` search) (ANTI-INJ p.14).

## 2. Context of DBMSs in the other sources [from source]
- A **prepared statement** goes through parser, rewriter and optimizer and has its plan stored; for queries with variables, the optimizer assumes "typical" values when estimating selectivity (ARCH p.47). This is a performance effect, not a security one, but it explains why plans may differ between literal and parameterized SQL.
- **PostgreSQL, libpq**: `PQexecParams` allows passing values **separately** from the command text (referenced as `$1`, `$2`...), "avoiding the tedious and error-prone quoting and escaping"; unlike `PQexec`, it accepts **at most one SQL command** in the string, which "has some usefulness as an extra defense against injection" (PG16 p.971-972). The manual warns that it is neither necessary nor correct to escape a value passed as a parameter (PG16 p.984).
- For identifiers received from an untrusted source, PG16 offers `PQescapeIdentifier` (PG16 p.984-985) and, in PL/pgSQL, `quote_ident` and `format(... %I ...)`; the parameter symbols `$n` **are valid only for data values**, never for table or column names, and only in optimizable commands (SELECT, INSERT, UPDATE, DELETE, MERGE) (PG16 p.1364-1365). In `EXECUTE ... USING`, the manual says it is "much less prone to SQL injection, since there is no need for quoting or escaping" (PG16 p.1364).
- PG16 also warns, for `PQescapeLiteral`, that escaping is "especially important" with untrusted strings (PG16 p.984).

## 4. [inference]
- If the only way to assemble the query is concatenation (dynamic list, column name), the book shows that parameters do not solve it (p.10-11) and PG16 shows identifier quoters (p.984-985, p.1364); combining them, the approach most faithful to the sources is: values by parameter, identifiers by driver/DBMS quoting, and a closed set of permitted names as an additional defense `[extrapolation]`.
- The book says "no single technique is enough" (p.8); therefore v1 was wrong to call prepared statements "the only definitive first-line defense" and "immutable against injections".
