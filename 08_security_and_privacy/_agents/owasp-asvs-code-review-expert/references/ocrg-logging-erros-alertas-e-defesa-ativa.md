# OCRG — logging, error handling, security alerts and active defense (OCRG p.161-181)

Source: OCRG v2.0, chs. 19-22 (technical reference). Pages = PDF (printed = N − 1). Related in the ASVS (mapping `[inference]`): V7.x (ASVS p.44-46), V1.7.x (ASVS p.20), V11.1.7-V11.1.8 (ASVS p.54), V8.1.4 (ASVS p.47), V4.1.5 (fail securely; ASVS p.36).

## Reviewing logging code (ch. 19) (OCRG p.161-163)
- [from source] The application log has the richest context (identity, roles, target, action, result) that infrastructure devices lack; it is usually **forgotten** and rarely described in the requirements/design; the level of monitoring, alerting and reporting must be defined in requirements and design, **proportional to risk**, consistent across the application and the portfolio, using industry standards (OCRG p.161). Volume must be controlled (CPU, network, disk cost; the reader needs to find the relevant message) (OCRG p.161).
- [from source] Log types: state/process, security and business (billing) (OCRG p.161). Sending to remote systems (SIEM/SEM) directly or by periodic secure copy; if the log has legal value, consider **source verification, integrity and non-repudiation**; log data, temporary debug and copies **must not be destroyed before the retention period nor kept beyond it** (OCRG p.161). Logs on clients (desktop/mobile): how do they reach the server? (OCRG p.161).
- [from source] **What to review** (OCRG p.162-163): log files on a separate partition, with strict permissions; logs **not** in a web-accessible location (if so, with restricted access and plain-text MIME); in a database, a **dedicated write-only account** with restricted permissions; **what to log**: input and output validation failures, authentication successes and failures, authorization failures, session failures (e.g. change of the cookie value), connection times; **what each message contains**: date/time in a common format (nodes synchronized by NTP), user, attempted action, client information (IP, port, user-agent), external classifications (SCAP, CAPEC), and **sanitization against log injection** (CR, LF and delimiters) — and apply the SQL injection rules if writing to a DB; make sure logging is enabled in security tests, fuzz, pentest and performance; that the log **cannot exhaust resources** (DoS by filling the disk); protection against tampering in transit and against access/modification/removal afterwards; copy to **read-only media** as soon as possible.
- [from source] **What NOT to log** (OCRG p.163): session IDs (consider a hash), sensitive personal data/PII, **authentication passwords (right or wrong)**, DB connection strings, **keys**, and data of a higher classification than the logging system is permitted. References: NIST SP 800-92, PCI DSS v2.0 req. 10, Common Event Expression (OCRG p.163).
- ASVS: V7.1.1 (no credentials; token only as hash), V7.1.3 (events), V7.3.1 (log injection), V7.3.3 (protection), V7.3.4 (time); remember that V7.1/V7.2 are "treat as L1" in review (ASVS p.44-45). The linter: `LOG-PASSWORD`.

## Error handling (ch. 20) (OCRG p.164-175)
- [from source] Two reasons: (1) **application state** — the initial failure can lead to an insecure state; **fail securely**: errors must not leave the application insecure; release resources, end sessions if necessary, stop calculations/business logic; (2) **information leakage** — messages help build attack vectors (OCRG p.164). A **generic** error page for most cases makes it harder to identify attack signatures (e.g. blind SQLi, timing analysis) (OCRG p.164). The company's code guideline must have an error handling section; a centralized strategy reduces uncaught errors "bubbling" up to the front end; leakage (hosting name, employee names) facilitates social engineering (OCRG p.164).
- [from source] Reminders (OCRG p.164-165): **not every error is an exception** (handle the `default` of a `switch`, the `else` of an `if`, all function exits; RAII; in Java/C#, `Error` ≠ `Exception`); **catching is not handling**; **do not catch more than you know how to handle** — `catch(Exception)` in Java/C# and `catch(...)` in C++ should be avoided because the type (server down, quota, out of memory) requires different handling; **log** the occurrence to tell an attack from a bug (OCRG p.165-166). Manual review does not cover all exception paths; with a debug build, automated tools can force exceptions and the reviewer makes sure the relevant errors are tested (OCRG p.165).
- [from source] **Error wiring** per platform (OCRG p.165-166, 169-171): Struts (`<exception` in `struts-config.xml`), JSP/`web.xml` (`<error-page>` per exception or per 404/500 → `GenericError.jsp`; Samples 20.1-20.3), IIS (`Application_Error()`, `customErrors`), Apache (`ErrorDocument`, handlers returning codes). A localized friendly message **never** comes from the exception class (stack trace, line number, class/method names); no file paths or names of people/internal contacts (OCRG p.166).
- [from source] **Failing securely** (OCRG p.166-167): failures from business rules, environment, upstream/downstream systems or hardware; release resources (memory, pools, handles); invalidate the session when the nonsensical condition suggests **malicious activity** (e.g. a logged-in user requesting an account that is not theirs → kill the session and redirect to login), remembering that the session object must be examined on **every** HTTP request.
- [from source] **By language** (OCRG p.167-170): Java — `printStackTrace()`/`getStackTrace()` leak; **never** `printStackTrace(out)` to the JSP; `setErr()`/`setOut()` to redirect to a file; `Error` is only logged and rethrown. .NET — `Exception` (`StackTrace`, `Source`, `Message`, `HelpLink`); order: `Page_Error` → `Application_Error` (global.asax) → `customErrors` (web.config); `customErrors mode` `On`/`Off`/`RemoteOnly` (default `RemoteOnly`). Classic ASP — no try/catch; `err` object, `On Error Resume Next`/`GoTo 0`; prone to design errors and leakage. C++ — any type can be thrown; derive from `std::exception`.
- [from source] **Bad examples**: `Page_Error` that writes `Request.Url` and `GetLastError().ToString()` to the response (XSS + leakage; Sample 20.6); `Application_Error` that logs an **unvalidated** `Request.Path` (OCRG p.169-170, Sample 20.7). The linter: `ERR-RESPONSE-WRITE-LASTERROR`, `CFG-CUSTOMERRORS-OFF`.
- [from source] **Good practices** (OCRG p.171-175): `try` with a **specific** type `catch` (Samples 20.12-20.14); **catch order**: specific before generic (Samples 20.15-20.16: `non_even_argument` is never handled if `std::invalid_argument` comes first); **`finally`** releases resources (avoids connection pool exhaustion); **RAII** / C# `using` / Java 7 `try-with-resources`; Classic ASP: cleanup function after `On Error Resume Next`; Struts `ActionErrors` with severities (Samples 20.17-20.18).
- ASVS: V7.4.1 (generic message with ID), V7.4.2 (exceptions across the codebase), V7.4.3 (last-resort handler), V4.1.5 (fail securely) (ASVS p.36, 46).

## Security alerts (ch. 21) (OCRG p.176-178)
- [from source] Many companies design only to keep the attacker out and not for the case where **they are already inside**; the application must know what is "normal" to know what is an alert, without logging everything; it can use **risk scoring** with logging modes (only critical in normal use; more items when risk rises) (OCRG p.176).
- [from source] **Month dropdown** example: an authenticated user sending a value outside the 12 possible ones is a sign (bug, stolen credentials, trojan, MITM or plugin); the reaction must be **proportional** (reduce functionality, require extra authentication/OOB, warn the user) and **stated in a legal document**; a single isolated error does not justify an alarm (OCRG p.176-177). User risk (IP, time, previous failures) combined with global risk (e.g. 3% x 23% of "risky" logins) (OCRG p.177). **Honey accounts**: accounts never handed to users; their use indicates a DB leak (OCRG p.178).
- [from source] **What to review** (OCRG p.178): does the application know it is under attack or ignore invalid inputs? does it dynamically change the log level (without restarting)? do requirements/design define what an alert is, peer-reviewed and tested? honey accounts? risk scoring? SIEM triggers with **automated tests** so they are not broken by changes? login failure counting and reaction? operating modes by score and return to normal? how are administrators alerted and is that tested? ASVS: V11.1.7-V11.1.8, V8.1.4 (ASVS p.47, 54).

## Active defense (ch. 22) (OCRG p.179-181)
- [from source] Application-level detection has full context, sees input already decrypted and canonicalized and produces **few false positives** if the detection points are well chosen. Requirements: detect suspicious events, use the knowledge **centrally**, choose a predefined response, execute it (OCRG p.179). Per-account lockout or isolated upload limits are **not** active defense in this sense, unless tied to a central "sensor network" (OCRG p.179). Hard to detect in dynamic testing (invisible responses): **code review is the best method** (OCRG p.179).
- [from source] Review: the **absence** of active defense must be noted as a **weakness**; there is no need to measure effectiveness, only whether the capability exists; it **does not protect** an application with known vulnerabilities (OCRG p.179). How to find it: dedicated module (OWASP **AppSensor**), **CAPEC** tags (e.g. CAPEC-212), identifiers in config, error/security logging mechanisms, validation error handling code with `Record event for attack detection`; the *event store* is analyzed in real time with criteria/thresholds in configuration; common responses: warning, logout, block, admin notification — full list from the book (OCRG p.180-181): increased logging, notification to admin/another system, proxy, status/time change, disable function, logout, lockout, collecting user data, terminating a process.
