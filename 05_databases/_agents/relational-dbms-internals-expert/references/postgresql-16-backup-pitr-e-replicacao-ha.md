## 1. Three backup approaches [from source]
The manual lists three fundamentally different approaches: **SQL dump**, **file system level backup** and **continuous archiving** (PG16 p.800).

### 1.1 SQL dump (`pg_dump`, `pg_dumpall`)
- `pg_dump` is an ordinary client: it needs read access to everything that will be copied (for the whole database, usually superuser). The dump is **internally consistent** (a snapshot of the moment `pg_dump` started) and does not block other operations, except those that request an exclusive lock, such as most forms of ALTER TABLE (PG16 p.800).
- Advantages: the output can usually be reloaded into **newer** versions of the server, and it is the only method that works for moving to a different machine architecture; file backup and continuous archiving, on the other hand, are extremely specific to the server version (PG16 p.800).
- Restore: text dumps are read by `psql` (`psql -X dbname < dumpfile`); non-text formats use `pg_restore`; the target database is not created by the command and must be created from `template0`; the users that own objects must exist beforehand; by default `psql` continues after an SQL error (use `ON_ERROR_STOP` or `--single-transaction`/`-1` to restore all or nothing); after restoring, run `ANALYZE` (PG16 p.801).
- **`ON_ERROR_STOP`, exit status 3, `-1` and the `pg_dump | psql` pipe when restoring a text dump** (PG16 p.801): the general command is `psql -X dbname < dumpfile` (`-X`/`--no-psqlrc` ensures the default `psql` settings; the `dbname` database is **not** created by the command: create it beforehand from `template0`, for example `createdb -T template0 dbname`). By default the script continues after an SQL error; with the `ON_ERROR_STOP` variable on (`psql -X --set ON_ERROR_STOP=on dbname < dumpfile`) `psql` **stops and exits with exit status 3** if an SQL error occurs. Even so, the database is left **partially restored**; the alternative is to restore everything in a single transaction with `-1` or `--single-transaction` (all or nothing; a small error can undo a restore that ran for many hours, which the manual says may be preferable to cleaning up a complex database by hand). Since `pg_dump` and `psql` read and write to **pipes**, a database can be copied directly from one server to another: `pg_dump -h host1 dbname | psql -X -h host2 dbname`. `pg_dump` dumps are relative to `template0`: languages and procedures added via `template1` are also included in the dump; therefore, with a customized `template1`, the empty target database must be created from `template0`. Afterwards, run `ANALYZE` on each database (Sections 25.1.3 and 25.1.6) and see Section 14.4 for efficient loading.
- `pg_dump` dumps **one** database and does not include roles or tablespaces (they belong to the cluster); `pg_dumpall` does the whole cluster, including roles and tablespaces, but the snapshots of the databases are **not synchronized** with each other; `--globals-only` copies only the cluster-wide data (PG16 p.801-802). Large databases: compression (`gzip`), `split`, custom format (`-Fc`, selective restore) and parallel dump (`-j`, directory format) (PG16 p.802-803).
- **`pg_restore -j`, `pg_dump -j` and `-Fc` (custom vs. directory format)** (PG16 p.803): the custom-format dump is compressed if PostgreSQL was built with zlib, and allows **selectively restoring tables**; it **is not a script for `psql`**: it needs `pg_restore` (for example `pg_restore -d dbname filename`). The parallel dump of `pg_dump` (`-j num`) dumps several tables at the same time and **is supported only in the "directory" format** (`pg_dump -j num -F d -f out.dir dbname`). **`pg_restore -j` restores in parallel any file in custom or directory format, whether or not it was created with `pg_dump -j`** (that is, parallel restore does **not** require the dump to have been parallel). For very large databases, the manual says it may be necessary to combine `split` with one of the other two approaches (custom or parallel).

### 1.1a `pg_dumpall`: what it does, privileges and the options that change the result [from source] (PG16 p.2150-2156)
- **What it is** (PG16 p.2150): writes the whole cluster to a single SQL script, calling `pg_dump` for each database, and also dumps the **global objects** (roles, tablespaces and grants of configuration parameters), which `pg_dump` does not save. For a complete dump you normally need to connect as **superuser**, and restoring also requires superuser (to create roles and databases). The output goes to stdout (use `-f` or redirection). It connects once per database, so it asks for a password for each one; the manual recommends `~/.pgpass`. Warning: restoring executes arbitrary code chosen by the superusers of the source; if they are not trusted, inspect the SQL.
- **Scope** (PG16 p.2150-2151): `-g/--globals-only` (roles and tablespaces, no databases), `-r/--roles-only`, `-t/--tablespaces-only`, `-a` data only, `-s` schema only, `-c/--clean` (emits DROP of databases, roles and tablespaces before recreating), `-O` no owners, `-x` no privileges, `-S` superuser for `--disable-triggers`.
- **Options on p.2152** (PG16 p.2152): `--exclude-database=pattern` (pattern in the style of psql's `\d`; repeatable), `--load-via-partition-root` (COPY/INSERT target the root of the hierarchy, useful if rows may land in other partitions at the destination, for example due to a collation difference), `--lock-wait-timeout`, `--disable-triggers` (only for data-only dumps; the emitted commands require superuser), `--inserts`/`--column-inserts` (very slow restore; for loading into non-PostgreSQL databases), `--if-exists` (only valid with `--clean`).
- **`--no-role-passwords`** (PG16 p.2153): does not dump the roles' passwords; when restored, they have a **null** password and password authentication **always fails** until one is set; since the values are not needed, the program reads the `pg_roles` view instead of `pg_authid` (helps when access to `pg_authid` is restricted by security policy).
- **`--no-sync`** (PG16 p.2153): does not wait for the files to be safely written to disk; it is faster, but an operating system crash afterwards may leave the dump corrupted; useful in testing, it should **not** be used when dumping a production installation.
- **`--on-conflict-do-nothing`** (PG16 p.2153): adds `ON CONFLICT DO NOTHING` to INSERT commands; **only valid with `--inserts` or `--column-inserts`** (otherwise the option is not valid).
- **Other `--no-*` options, quoting and INSERT** (PG16 p.2153-2154): `--no-comments`, `--no-publications`, `--no-subscriptions`, `--no-security-labels`, `--no-table-access-method`, `--no-tablespaces`, `--no-toast-compression` and `--no-unlogged-table-data` (omits only the data of unlogged tables; the definitions remain); `--quote-all-identifiers` (recommended between different major versions); `--restrict-key` and `--rows-per-insert` (detailed in the two items below) and `--use-set-session-authorization` (SQL-standard `SET SESSION AUTHORIZATION` commands instead of `ALTER OWNER`; more standard-compliant, but may not restore well, depending on the history of the objects, PG16 p.2154).
- **`--restrict-key=key` (restrict-key; key of psql's `\restrict`)** (PG16 p.2154; same in `pg_dump`, p.2144, and `pg_restore`, p.2173): uses the given string as the key of psql's `\restrict` in the dump output; without the option, the program **generates a random key** when it needs one; the key may contain only **alphanumeric characters**. The manual says the option is intended **mainly for testing and for scenarios that require repeatable output (for example, comparing dump files)**; that is, comparing dumps is an intended use, and a fixed key is what makes the output reproducible. But it is **not recommended for general use**: a malicious server that knows the key in advance can inject arbitrary code that will be executed on the machine running `psql` with the dump output. In `pg_dump` it is only valid for **plain text** dumps (`--format` plain or omitted); in `pg_restore` it is only valid for SQL script output (with `--file`). `[inference]` to compare two dumps, fix the same key in both only in a test environment and do **not** reuse the fixed key in dumps that will be restored in production.
- **`--rows-per-insert=nrows` (rows-per-insert)** (PG16 p.2154; same in `pg_dump`, p.2144): dumps the data as `INSERT` commands (instead of `COPY`) and controls the **maximum number of rows per `INSERT`**; the value must be a number **greater than zero**. An error during restore loses **only the rows of the problematic `INSERT`**, and not the entire contents of the table. `--on-conflict-do-nothing` only works together with `--inserts` or `--column-inserts` in `pg_dumpall` (PG16 p.2153), whereas `pg_dump` also accepts `--rows-per-insert` in that combination (PG16 p.2144).
- **`pg_dumpall -d connstr` (`--dbname`)** (PG16 p.2154): is a connection string whose parameters **override** conflicting command-line options; the database name in the string is **ignored**, because the program connects to several databases; use `-l` for the initial connection database.
- **Connection: `-l`, `-w`/`-W` and `--role`** (PG16 p.2154-2155): `-l dbname` sets the initial connection database, where it finds the globals and discovers the databases (default `postgres`, otherwise `template1`); `-w` never asks for a password, `-W` forces it; `--role` does `SET ROLE` after connecting.
- **Notes and restore** (PG16 p.2155-2156): `--clean` authorizes the script to drop and recreate `postgres` and `template1` (preserves the source's locale/encoding); the "role already exists" error for the bootstrap superuser is harmless; the tablespace directories must exist before the restore; run `ANALYZE` afterwards; when restoring, the manual recommends `psql -X -f db.out -d postgres` (and, with `--clean`, connecting to `postgres` first, since the script tries to drop the other databases).

### 1.1b `pg_dump` and `pg_restore`: formats, `--create`, behavior on errors and warning about superusers [from source] (PG16 p.2135-2136, p.2169-2170)
- **What `pg_dump` does and what it does not include (pg_dump vs. roles)** (PG16 p.2135): makes a consistent backup of **a single database** even while in use, without blocking readers or writers. For the whole cluster or for **global objects** such as **roles and tablespaces**, use `pg_dumpall`; therefore a `pg_dump` does not recreate the roles. There are script formats (SQL text, for `psql`) and archive formats (for `pg_restore`, which allows restoring selectively and reordering items). The **custom (`-Fc`) and directory (`-Fd`)** formats are the most flexible: they allow selecting and reordering items, support parallel restore and are compressed by default. **Only the directory format supports parallel dump**, so `pg_dump -Fc -j 8` does not work `[inference]`: use `-Fd -j 8`. The manual says to examine the output (stderr) for warnings.
- **Warning about untrusted superusers when restoring a dump** (PG16 p.2135): restoring a dump makes the target **execute arbitrary code chosen by the superusers of the source**, and partial dumps or restores do not limit this. If the source superusers are not trusted, the SQL commands of the dump must be **inspected before** restoring; non-text dumps can be inspected with `pg_restore`'s `--file` option. The client running dump and restore does not need to trust the source or target superusers.
- **`pg_dump --create` (-C): what the output gains** (PG16 p.2136): in the script, it begins with the command to **create the database** and reconnect to it (so the database you connect to before running the script does not matter); with `--clean` as well, the script drops and recreates the database. It also includes the **database comment**, the database-specific settings (`ALTER DATABASE ... SET ...` and `ALTER ROLE ... IN DATABASE ... SET ...` that mention it) and the **access privileges of the database itself**, unless `--no-acl` is used. **It is ignored when emitting a non-text archive**; in archive formats, give the option to `pg_restore`. `--clean` also only applies to text scripts and, for archives, goes to `pg_restore`.
- **`pg_restore --create` (-C): the `-d` database is used only for DROP and CREATE** (PG16 p.2169): creates the database before restoring (with `--clean`, drops and recreates it before connecting). It also restores the comment, the `ALTER DATABASE ... SET` / `ALTER ROLE ... IN DATABASE ... SET` settings and the database privileges (unless `--no-acl`; to avoid that part use `--no-acl`). Note: the database given in `-d` is used **only** to issue the initial `DROP DATABASE` and `CREATE DATABASE`, and **all data is restored into the database with the name that appears in the archive**. `[inference]` therefore `pg_restore --clean --create -d vendas_homolog vendas.dump` restores the data into `vendas`, not into `vendas_homolog`.
- **`pg_restore` on errors (`--exit-on-error`, -e)** (PG16 p.2169): the default is to **continue** after an error when sending SQL commands and to show the **error count at the end**; `-e` / `--exit-on-error` makes it exit on the first error. With `--clean`, objects that do not exist at the target generate ignorable errors, unless `--if-exists` is used.
- **Archive format in `pg_restore` (-F)** (PG16 p.2169): **it is not necessary to specify the format**, `pg_restore` determines it by itself; if given, `c` (custom), `d` (directory) or `t` (tar) is valid.
- **`pg_restore -j` (jobs)** (PG16 p.2170): runs the most time-consuming steps (data load, creation of indexes and constraints) in parallel with up to N sessions; ignored when emitting a script instead of connecting to a server. Accepts only the **custom and directory** formats; the input must be a **regular file or directory** (not a pipe or standard input) and does not combine with `--single-transaction`. A good starting point: the number of cores of the server.

### 1.2 File backup
Direct copy of the files (for example `tar`): requires the server to be **shut down** to obtain a usable copy and only works for the whole cluster, because the files are useless without the commit state in `pg_xact` (PG16 p.803). Alternative: a consistent snapshot of the volume, which works with the server running, but the restore will be like a crash recovery (WAL replay; include the WAL files and, if desired, run CHECKPOINT beforehand); with data and WAL on different disks there may be no simultaneous snapshots (PG16 p.804). Another option: `rsync` twice, the second with the server stopped and `--checksum` (PG16 p.804). A file backup is usually larger than a dump (indexes are included) but can be faster (PG16 p.804).

## 2. Continuous archiving and PITR [from source]
- PostgreSQL keeps the WAL in `pg_wal/`; continuous archiving combines a file backup that is **not necessarily consistent** with a backup of the WAL files, since replaying the log corrects internal inconsistencies (as in crash recovery). Benefits: no file system snapshot needed; "continuous backup" simply by continuing to archive WAL (valuable for large databases); replay can stop at any point, which gives **point-in-time recovery (PITR)**: restoring the state at any instant since the base backup; by feeding another machine with the same base backup you get a *warm standby* (PG16 p.804-805).
- `pg_dump` and `pg_dumpall` do **not** produce file-level backups and are not suitable for continuous archiving (dumps are logical and have no information to replay WAL). The method only restores the whole cluster (not a subset) and requires a lot of storage; but it is the preferred one where reliability is critical (PG16 p.805). You need a **continuous** sequence of archived WAL from at least the start of the base backup; test archiving **before** the first base backup (PG16 p.805).

### 2.1 Setting up WAL archiving
- The WAL is divided into segment files, normally **16 MB** each (the size can be changed at `initdb`); without archiving, the system recycles the few old segments (PG16 p.805).
- To enable: `wal_level` at `replica` or higher, `archive_mode` at `on` and an `archive_command` (shell command) or an `archive_library`; `%p` is the file path and `%f` only the name. The command must return zero status **if and only if** it succeeds; with a non-zero status PostgreSQL tries again (PG16 p.805-806). The command must **refuse to overwrite** an already archived file (the manual's example tests for existence before copying) and treat re-sending an identical file as success (PG16 p.806). Run it as the same user as the server and protect the archived content (it contains everything in the database) (PG16 p.806).
- If archiving fails repeatedly or the storage fills up, `pg_wal/` accumulates segments; if the file system of `pg_wal/` fills up, PostgreSQL does a PANIC shutdown (no committed transaction is lost, but the database stays down until space is freed) (PG16 p.806-807). Monitor archiving (PG16 p.807).
- The archived WAL does **not restore** configuration files (`postgresql.conf`, `pg_hba.conf`, `pg_ident.conf`), since they are edited by hand and not through SQL operations; keep them where the ordinary file backup picks them up (PG16 p.807).
- **`archive_timeout`**: the command is only invoked on **complete** segments, so, with little WAL traffic, there can be a long delay between the commit and the safe record in the archive. `archive_timeout` forces the segment switch at least at that interval; files archived early have the **same size** as full ones, so a very short value "bloats" the archive storage; values of about **one minute** are generally reasonable. `pg_switch_wal` forces the switch manually (PG16 p.807).
- With `wal_level = minimal` some commands avoid writing WAL, and the WAL would not have enough data for archive recovery; therefore `wal_level` only changes at server start, whereas `archive_command` changes with a reload. To stop archiving temporarily (via shell) you can set `archive_command` to an empty string: the WAL accumulates in `pg_wal/` (PG16 p.807).
- `[derived]` (package example, based on 16 MB and `archive_timeout = 60 s`): in the worst case, with a forced switch every minute even without traffic, it is 86,400 s / 60 s = **1,440 files/day** (only if there is database activity in every minute: the manual says the forced switch occurs if there was activity, including a checkpoint, and that checkpoints are skipped without activity, PG16 p.668), each 16 MB, or 1,440 x 16 MB = 23,040 MB ≈ **22.5 GiB/day** (23,040 / 1,024). If the server has enough traffic to complete segments before the timeout, the real number is lower; with `archive_timeout = 5 s` the calculation would be 12 times larger. The 16 MB size is the manual's default, but may have been changed at `initdb`.

### 2.2 Base backup
- The easiest way is `pg_basebackup`, which generates ordinary files or tar; the duration does not matter, but if `full_page_writes` is off there may be a performance drop because it is forced on during the backup (PG16 p.807). All WAL segments generated during and after the backup must be kept; the process creates a **backup history file** (`.backup`) in the WAL archive, named after the first segment needed; numerically earlier segments are no longer needed (PG16 p.807-808). The history file is **just a small text file** (it holds the label given to `pg_basebackup` and the start and end times and WAL segments of the backup); with a name such as `0000000100001234000055CD.007C9330.backup`, the **second part of the name** (exact position within the segment) **can normally be ignored**, and what matters for deletion is the segment part (PG16 p.808). Even so, the manual advises keeping several backup sets (PG16 p.808). For `pg_receivewal` as an archiving alternative, see `postgresql-16-replicacao-streaming-sincrona-hot-standby-e-failover.md` section 2b (PG16 p.2159). The interval between base backups depends on the storage one accepts to spend on archived WAL and on the tolerated recovery time, since all segments need to be replayed (PG16 p.808).
- Low-level API: `pg_backup_start` and `pg_backup_stop` in the same connection, `backup_label` and `tablespace_map` must be written without modification (PG16 p.808-809). Omit `pg_wal/` from the file backup, as well as `pg_replslot/` and some temporary directories (PG16 p.809-810).

### 2.2a `pg_basebackup`: whole cluster, privileges, `max_wal_senders` and backup from a standby [from source] (PG16 p.2099)
- **What it does** (PG16 p.2099): takes a base backup of a running cluster **without affecting other clients**; serves both for PITR and as the starting point of a log shipping or streaming standby. Makes an **exact copy of the files** of the cluster and puts the server into and out of backup mode automatically. The backup is **always of the whole cluster**; you cannot copy individual databases or objects (for selective backup, use another tool, such as `pg_dump`).
- **Connection and `max_wal_senders`** (PG16 p.2099): uses an ordinary connection with the **replication protocol**; the user needs the `REPLICATION` permission (or be superuser) and `pg_hba.conf` must allow the replication connection. `max_wal_senders` must allow **at least one walsender for the backup plus one for WAL streaming (if used)**. `[derived]` with `-X none` there is no WAL streaming, so the minimum is **1**; with WAL streaming during the backup, the minimum is 2.
- **Several backups at the same time** (PG16 p.2099): it is possible to run several simultaneous `pg_basebackup`s, but in general it is better, for performance, to take **just one** and copy the result. While it runs, the `pg_stat_progress_basebackup` view shows progress (Section 28.4.6).
- **Backup from a standby** (PG16 p.2099): `pg_basebackup` accepts as source a primary **or a standby**. The standby must accept replication connections (`max_wal_senders` and `hot_standby`, plus `pg_hba.conf`), and `full_page_writes` must be enabled **on the primary**. Limitations: (1) the **backup history file is not created** in the copied cluster; (2) `pg_basebackup` **cannot force the standby to switch WAL file** at the end of the backup: with `-X none` and little writing on the primary, it may wait a long time for the last needed WAL to be switched and archived, and it may then be useful to run `pg_switch_wal` **on the primary**; (3) if the standby is **promoted** to primary during the backup, the backup **fails**; (4) all WAL records needed for the backup must contain enough full-page writes, which requires `full_page_writes` on at the primary.
- **What is not there** (PG16 p.2099): this page has no `--switch-wal-on-standby` option or `backup_standby_timeout` parameter; the text extracted from manual 16.15 does not contain these names on any page. Whoever cites them is talking about another version or another product `[extrapolation]`.

### 2.3 Recovering from a continuous archive (PG16 p.810-811)
Steps from the manual: (1) stop the server; (2) copy the data directory and tablespaces to a temporary place if there is space (or at least `pg_wal` with unarchived segments); (3) remove the current files from the data directory; (4) restore the files from the base backup with the correct owner and permissions; (5) **remove the files in `pg_wal/`** that came from the backup (probably obsolete); (6) copy the saved unarchived segments into `pg_wal/`; (7) set the recovery configuration in `postgresql.conf` and create the **`recovery.signal`** file (and, if desired, restrict access in `pg_hba.conf`); (8) start the server, which enters recovery and removes `recovery.signal` when finished; (9) check the data before releasing users (PG16 p.810-811).
- Mandatory: **`restore_command`** (how to obtain archived segments, with `%f` and `%p`); it must return a non-zero status when the requested file does not exist (that is not an error) (PG16 p.811). Requests for `.history` files are normal; segments missing from the archive are looked for in `pg_wal/`, but what is in the archive takes precedence (PG16 p.811).
- **Recovery target**: by date/time, named restore point or transaction ID (in practice, only date/time and named point are usable). **The target must be later than the end of the base backup** (the end of `pg_backup_stop`); you cannot recover to an instant at which the backup was in progress: use the earlier base backup (PG16 p.811-812). If recovery encounters corrupted WAL, it stops there; you can repeat with a target earlier than the corruption point; if it fails for an external reason, it restarts almost from where it stopped (PG16 p.812).
- **Timelines**: when an archive recovery ends, a **new timeline** is created to distinguish the WAL generated afterwards; the timeline ID is part of the segment name, so it does not overwrite WAL from earlier histories; timeline history files (small) record the branching and must be kept; the default is to recover to the latest timeline, controlled by `recovery_target_timeline` (PG16 p.812).
- `[derived]` example: a logical dump (pg_dump) at 02:00 and a crash at 14:32 implies losing up to 12h32 of data (≈ 12.5 h) if there is only the dump; with continuous archiving and an `archive_timeout` of 1 min, the expected loss drops to the interval between the last archived segment and the failure (on the order of 1 minute, `[inference]` from the description of `archive_timeout`, PG16 p.807).

### 2.4 Tips and caveats
Standalone hot backups (without PITR) with `pg_basebackup -X` (PG16 p.813); compression of archived WAL with `gzip` in `archive_command` and `gunzip` in `restore_command` (PG16 p.813); scripts for `archive_command` (PG16 p.813). The manual lists limitations of continuous archiving (for example, `CREATE DATABASE` during the base backup) (PG16 p.813).

### 2.5 Recovery parameters: prefetch, `standby.signal` vs. `recovery.signal`, `restore_command` (PG16 p.669-670)
- **`recovery_prefetch`** (PG16 p.669): enum with values `off`, `on` and `try` (default **`try`**); tries to *prefetch* blocks referenced in the WAL that are not yet in the buffer pool during recovery; `try` only enables if the operating system offers `posix_fadvise` (used to implement prefetch; some systems have the function but it does nothing); it can reduce I/O waits in certain workloads. `maintenance_io_concurrency` also limits the prefetch activity.
- **`wal_decode_buffer_size`** (PG16 p.669): limit on how far ahead the server may look in the WAL for blocks to prefetch; no unit = bytes; default **512 kB**; can only be set at server start.
- **`standby.signal` and `recovery.signal`** (PG16 p.669): "recovery" covers using the server as a standby or doing a targeted recovery. Creating **`standby.signal`** in the data directory starts the server as a **standby** (keeps trying to obtain WAL, via `primary_conninfo` and/or `restore_command`, and **does not end** recovery at the end of the archived WAL); creating **`recovery.signal`** starts a **targeted recovery** (ends when all archived WAL has been replayed or when the `recovery_target` is reached). **If both files exist, standby mode takes precedence.** Standby is typical for high availability and/or read scaling; targeted recovery, for recovering from data loss. The parameters in section 20.5.6 (recovery target) are used in targeted recovery and, in a standby, are "typically not useful".
- **`restore_command`** (PG16 p.669-670): local shell command to fetch an archived WAL segment; it is **mandatory in archive recovery**, but **optional in streaming replication**. Substitutions: **`%f`** = name of the file to fetch; **`%p`** = destination path of the copy on the server (relative to the data directory); **`%r`** = name of the file with the last valid restart point (the oldest that must be kept for the restore to be restartable; used to truncate the archive; generally only in *warm standby* configurations); **`%%`** = a literal `%`. The command must return **zero status only on success**, and **non-zero status** when asked for a file that is not in the archive (this is expected); if the command dies from a signal (except SIGTERM) or a shell error (such as command not found), **recovery aborts** and the server does not come up. Only in `postgresql.conf` or on the command line.
- **`archive_cleanup_command`** (PG16 p.670): optional, executed at each *restartpoint*; cleans up old WAL the standby no longer needs, with `%r`; `pg_archivecleanup` is often used for a single standby, but with **several standbys** reading the same directory you must ensure that no file is deleted before all of them have finished. A non-zero status generates only a warning (death by signal/shell error is fatal).
- **`recovery_end_command`** (PG16 p.670): optional, executed **once** at the end of recovery, also with `%r`; a non-zero status generates a warning and the database comes up anyway; death by signal/shell error prevents startup.

### 2.6 WAL functions (file name, LSN) and recovery information functions (PG16 p.436-437)
- **`pg_walfile_name` and `pg_walfile_name_offset`** (PG16 p.436): convert an LSN into the name of the WAL file that contains it (the second also returns the byte offset within the file); if the LSN is **exactly on the boundary** of a file, both return the **previous file** (the manual says this is generally what is wanted for archiving, since the previous one is the last that needs to be archived).
- **`pg_split_walfile_name`** (PG16 p.436-437): extracts the **sequence (segment) number and the timeline ID** from the name of a WAL file. The manual shows how to compute an LSN with it: LSN = `0/0` + segment number x `wal_segment_size` + offset; the example, with the file `000000010000000100C000AB` and offset 256, results in `C001/AB000100` (PG16 p.437). `[derived]` the general rule: LSN = (segment x segment size) + offset, written as two hexadecimal numbers separated by a slash.
- **`pg_wal_lsn_diff`** (PG16 p.436): difference in bytes (lsn1 - lsn2) between two LSNs; useful with `pg_stat_replication` to measure replication lag.
- **`pg_current_wal_lsn`, `pg_current_wal_insert_lsn`, `pg_current_wal_flush_lsn`** (PG16 p.436): write, insert (the "logical" end of the WAL) and flush (last point known to be in durable storage) position; they are read-only and do not require superuser; the write one is normally the one that matters for archiving.
- **`pg_is_in_recovery`** (PG16 p.437): true while recovery is in progress; the functions in Table 9.92 can run during recovery and in normal operation.
- **`pg_last_wal_receive_lsn`** (PG16 p.437): last WAL **received and synced to disk** by streaming; grows monotonically during streaming and stays static after recovery; returns **NULL if streaming is disabled or has not started yet**.
- **`pg_last_wal_replay_lsn`** (PG16 p.437): last WAL **replayed** in recovery; returns **NULL if the server was started normally, without recovery**.
- **`pg_last_xact_replay_timestamp`** (PG16 p.437): time of the commit or abort of the last replayed transaction (the moment the record was generated **on the primary**); returns **NULL if no transaction was replayed during recovery or if the server started normally, without recovery**.
- **`pg_get_wal_resource_managers`** (PG16 p.437): lists the loaded WAL resource managers and whether each is built-in (`rm_builtin`) or from an extension.

## 3. High availability, load balancing and replication [from source]
- (For synchronous replication with `synchronous_standby_names`, `FIRST`/`ANY`, the rule that commits "may never complete" if a synchronous standby goes down, STONITH, `pg_rewind` and the network bandwidth x WAL rate calculation, see `postgresql-16-replicacao-streaming-sincrona-hot-standby-e-failover.md`.)
- **Central problem**: read-only servers combine easily, but read-write servers are hard, because a write on any one must be propagated to all; it is the synchronization problem, with no single solution (PG16 p.815). Vocabulary: primary/master and standby (secondary); *warm standby* does not accept connections until promoted; *hot standby* accepts read-only queries. **Synchronous**: the transaction is only confirmed when all servers have committed it (lossless failover and consistent reads); **asynchronous**: there is a delay, possibly losing transactions on failover and reading slightly stale data. A synchronous solution over a slow network can cut performance by more than half (PG16 p.815).
- Solutions compared (PG16 p.815-818):
  - **Shared-disk failover**: only one copy of the database on a disk array shared between servers; fast, lossless failover; limitation: if the array fails or is corrupted, primary and standby are both inoperative, and the standby must never access the disk while the primary is running (PG16 p.815).
  - **File system/block replication** (for example DRBD): mirrors the file system, with writes in the same order (PG16 p.816).
  - **WAL shipping** (file-based or streaming): keeps warm/hot standbys reading the WAL stream; synchronous or asynchronous, only for the **whole server** (PG16 p.816).
  - **Logical replication**: stream of logical modifications built from the WAL, **per table**; a server can publish and subscribe, allowing bidirectional flow (PG16 p.816).
  - **Trigger-based replication** (Slony, Londiste), **SQL middleware** (pgpool-II; functions such as `random()` and sequences may diverge between servers), **asynchronous multimaster** (conflict resolution by users or rules) and **synchronous multimaster**: each server accepts writes, best for mostly-read workloads; PostgreSQL **does not offer** this type, although two-phase commit (`PREPARE TRANSACTION`, `COMMIT PREPARED`) can implement it in the application or middleware (PG16 p.816-817).
  - **Outside the categories** (PG16 p.818): (a) **data partitioning**: the tables are divided into sets and **each set can be modified by only one server** (manual's example: data for London and Paris, one server in each office); if the data needs to be combined, the application queries both servers, or primary/standby replication is used to keep on each one a read-only copy of the other's data; (b) **parallel execution of a query on several servers**: the manual says that many of the solutions above let several servers handle **several queries**, but **none lets a single query use several servers to finish faster**; this separate solution divides the data among servers, each executes its part and returns it to a central server that combines the result, and it can be implemented with the **PL/Proxy** toolset. **Commercial solutions**: the manual notes that, because it is open source and easy to extend, PostgreSQL has been used by companies to create closed-source commercial solutions with their own failover, replication and load balancing capabilities, and says they are **not discussed** there (PG16 p.818); thus, the package has nothing about specific commercial products. Table 27.1 summarizes the capabilities of each solution (PG16 p.817-818).
- **Log shipping** (PG16 p.818): the primary operates in continuous archiving and each standby in continuous recovery reading the WAL; no changes to the tables; low impact; 16 MB WAL can be sent over any distance; **it is asynchronous**: the records follow after the commit, so there is a data loss window if the primary fails catastrophically (PG16 p.818).
- **Limitations of logical replication** (PG16 p.924): the schema and DDL are **not replicated**, keep the schema synchronized manually (copy the initial schema with `pg_dump --schema-only`); **sequence data is not replicated** (serial/identity columns arrive as part of the table, but the sequence at the subscriber keeps the initial value; for failover it must be updated); `TRUNCATE` is replicated with caveats; large objects are not replicated; only tables (including partitioned ones) are replicated, not views, materialized views or foreign tables; with partitioned tables, replication by default comes from the leaf partitions. The architecture is that of streaming (walsender and apply worker); the apply process runs with `session_replication_role` set to `replica`, so by default **triggers and rules do not fire on the subscriber** (PG16 p.924).
