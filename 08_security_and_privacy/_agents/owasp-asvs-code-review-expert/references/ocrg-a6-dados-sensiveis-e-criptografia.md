## Cryptographic controls — overview (OCRG p.119)
- [from source] Sensitive data (cards, tax IDs, credentials) deserves extra protection: encryption at rest and in transit and care in the exchange with the browser (OCRG p.119). Cryptography provides **confidentiality** (cipher), **integrity** (hash/digest) and **non-repudiation** (signature); the code must use standard algorithms with strong keys (OCRG p.119).
- [from source] Common flaws: non-standard algorithm or home-grown implementation, insecure standard algorithm (e.g. DES) and weak keys (OCRG p.119). Decide: sensitive data identified; encrypt **in transit** (TLS/HTTPS, FTPS) and/or **at rest** (cards in DB, password hashes, MACs). The developer does not write AES, they **use the library correctly** (OCRG p.119).
- Table 18 (OCRG p.120): definitions of hash, entropy, encoding (does not hide data), salt, encryption, symmetric cryptography, public-key cryptography and certificate.

## Protection in transit — what to review (12.3) (OCRG p.120-122)
- [from source] SSL vs TLS: the guide uses "TLS"; the benefit is protecting data from disclosure and modification between clients and server, and between server and back end (OCRG p.120). Even with certificates and configuration getting cheaper, use TLS across the whole site; client certificates rarely replace user/password (OCRG p.121). **Validated implementations**: FIPS 140-2 list; use a validated TLS module/service configured in approved mode (OCRG p.121). `[DATED]` ASVS 4.0.3 no longer points to FIPS 140-2 and asks for a current TLS configuration validated by a tool (ASVS p.51).
- [from source] TLS checklist (OCRG p.121-122): TLS on **login** and on **authenticated** pages (login without TLS allows swapping the form action; authenticated pages without TLS expose the session ID); **internal** TLS ("employees only" is not enough); prefer **HTTPS only** for all pages; `secure` and `http-only` flags on authentication cookies; **no sensitive data in the URL** (history and logs); **avoid caching** sensitive data; **HSTS** for high-risk interfaces; keys **≥ 2048 bits** and **SHA-256+** `[DATED]`; certificates with a specific FQDN (no wildcard or RFC 1918 addresses; use SANs); **provide the whole certificate chain**.
- ASVS: V9.1.1-V9.1.3, V9.2.2, V14.4.5 (ASVS p.50-51, 63). The OCRG has neither TLS 1.2/1.3 nor OCSP (absent from the text).

## Protection at rest — what to review (12.4) (OCRG p.122-127)
- [from source] Do not create your own libraries/algorithms; use established libraries (Table 19: C# `System.Security.Cryptography`; C/C++ Win32 CryptoAPI/DPAPI; Linux OpenSSL/NSS/boringssl; ASP via COM wrapper; Java JCE/BouncyCastle/Spring Security) (OCRG p.122-123). Corporate strategy: standard algorithms to use, **minimum key sizes** and **which types of data must be encrypted** (OCRG p.123).
- [from source] For the reviewer: strong algorithm and implementation (FIPS 140); right type (hash vs symmetric cipher; public key if there is no way to transfer the symmetric key); **key protection is the most important aspect** (who gets in/sees the keys and how they are used); audit against company/regulatory specifications; test under multithreaded load and check that each datum was correctly encrypted/decrypted; .NET: DPAPI, no proprietary algorithms, `RNGCryptoServiceProvider` for PRNG, key ≥ 128 bits; Java: JCE, `SecureRandom`, key ≥ 128 bits; ASP: via COM (OCRG p.123-124).
- [from source] **Bad practice**: DES and SHA-0 are insecure; Sample 12.1 uses `DES/CBC/PKCS5Padding`; SHA-1 and MD5 should also be avoided in new applications. **Good practices**: strong entropy with `SecureRandom` (Sample 12.2/12.3) and AES with `KeyGenerator` (Sample 12.3 with a 128-bit key) (OCRG p.124-127). `[inference]` The book's AES example uses `Cipher.getInstance("AES")` without explicit mode/padding, which leaves the mode to the provider's choice; do not copy it as a model — ASVS V6.2.3/V6.2.5 ask for secure configuration and forbid ECB (ASVS p.42).

## Hash, salt (12.5) (OCRG p.128-131)
- [from source] Hash for digital signatures, MACs, authentication and **storing passwords** instead of cleartext. **Never accept a programmer-created hash algorithm in code review**; use functions of the language/framework/trusted libraries (OCRG p.128). Cryptography export regulation and legal advice (OCRG p.128) `[DATED]`.
- [from source] "Nothing is secure forever": LanMan is broken; MD5 has collision attacks (which do not affect password hashes); the reviewer knows the weaknesses of obsolete functions and current practices (OCRG p.128).
- [from source] **Salt**: common mistakes — no salt, short salt, the same salt for several hashes (OCRG p.129). The book's demonstration: without salt, a rainbow table breaks everything; with a single fixed salt, another table is computed; with a **random salt per record** the table is per user (100,000 users × 10 days = 2,738 years in the example); the salt **is not a secret** (it can be stored/sent with the hash) (OCRG p.129). Good practices: salt generated by a cryptographic function, **one per hash**, minimum **128 bits**, recommended **256 bits** (OCRG p.130). Sample 12.4 (`RNGCryptoServiceProvider`).
- [from source] MD5 and SHA-1 should not be used in any application (cited opinion); FIPS approves SHA-1/224/256/384/512/512-224/512-256 for federal use; **raise a "red flag" if MD5 or SHA-1 are used and do a risk assessment** (OCRG p.130). Sample 12.5: configurable hash function (algorithm read from configuration: SHA-256/SHA-512) (OCRG p.130-131).
- **Important gap**: the OCRG does **not** mention bcrypt, scrypt, Argon2 or PBKDF2 (verified); to store passwords use ASVS V2.4.1-V2.4.5 (PBKDF2/bcrypt cited; ASVS p.26-27) and mark scrypt/Argon2 as [extrapolation].

## Reducing the attack surface (12.6) (OCRG p.131-133)
- [from source] Attack surface = entry/exit points, roles and rights, data sensitivity; the code structure (authentication, crypto) is also part of it; **RSQ** (Relative Attack Surface Quotient, M. Howard) measures changes over time (OCRG p.131-132). In review, the goal is to ensure the change **does not unnecessarily increase** the surface; the surface can be mapped by scanning (ZAP, Arachni, Skipfish, w3af) and high-risk areas identified; **backups** are part of the surface (OCRG p.132).
- [from source] Review questions (OCRG p.132-133): does the change open doors/entries? does it use HTTP where there was only HTTPS? does the function become available to unauthenticated users? can it be used for denial of service (write a file, send an SMS, heavy computation in a loop)? are **searches** controlled (injection)? is important data separated from trivial data (partition/DB)? **uploads**: authenticated, rate limit, maximum size per upload/aggregate, allowed types (MIME/suffix), antivirus? admins with actions **logged in a way they cannot delete or deny**, with alarms for improper access? compatible with existing countermeasures or a new, non-centralized security module? unnecessary user levels? is the **PII strictly necessary**? simple configuration with an alert for surface expansion? is there an alternative that reduces the surface (e.g. static help instead of a DB search)? is there information stored on the client that should be on the server?
- ASVS: V1.1.4 (document boundaries and flows), V1.14.1 (segregation), V8.1.3 (minimize parameters), V8.3.x (personal data), V12.1.x (upload) (ASVS p.17, 21, 47-48, 56) `[inference]`.
