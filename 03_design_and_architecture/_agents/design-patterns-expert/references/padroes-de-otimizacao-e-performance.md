# Optimization patterns (GPP): Data Locality, Dirty Flag, Object Pool and Spatial Partition

Source: **GPP** = *Game Programming Patterns* (Nystrom), a 338-page PDF web capture. Pages = **PDF**. See `INDEX.md`. The "Optimization Patterns" section opens on p.266 `[from source] (GPP p.266)`. Labels: `[from source]`, `[inference]`, `[extrapolation]`, `[DATED]`. The author's general rule: optimize when there is a performance problem and profile before changing the data structure `[from source] (GPP p.273, 282)`.

## 1. Data Locality (GPP p.267-289)
- Intent: speed up memory access by organizing data to take advantage of the CPU cache `[from source] (GPP p.267)`.
- Motivation: CPU speed grew far more than RAM speed; fetching a byte from RAM can take "hundreds of cycles"; the warehouse and pallet analogy (the CPU brings a contiguous block into the cache) `[from source] (GPP p.267-270)`. There are several cache levels (L1, L2, L3), each larger and slower; the cache line is "usually about 64 to 128 bytes"; *cache hit* and *cache miss*; the miss causes a *stall* `[from source] (GPP p.270-271)`.
- Cited measurement: two programs that did the same computation, one with many misses, the slow one ~**fifty times** slower than the other, with caveats that it depends on the machine `[from source] (GPP p.271)`. Data organized in contiguous memory in the order of use; if several threads touch nearby data, different cache lines are better `[from source] (GPP p.272)`.
- Pattern and when to use: only with a performance problem **caused by cache misses** (use a profiler, for example Cachegrind) `[from source] (GPP p.273)`. Cost: sacrifice abstraction (pointers, interfaces, virtual methods cause "pointer chasing") `[from source] (GPP p.274)`.
- Techniques in the example: (1) **contiguous arrays** of components instead of pointers to entities and components (the AI, physics and render loop over flat arrays; he measured about 50x faster than the pointer version); (2) **packed data** (active particles at the front of the array with `numActive_` and swaps, to dispense with the `isActive` test and branch prediction) `[from source] (GPP p.274-282)`; (3) **hot/cold splitting**: fields used every frame on one side, rare data (e.g., loot) in another structure `[from source] (GPP p.282-284)`.
- Decisions: polymorphism (avoid; type object; separate arrays per type; collection of pointers) and how entities are defined (pointers to components, IDs, entity as an ID) `[from source] (GPP p.284-289)`. The author credits the name "data-oriented design" to Noel Llopis and cites Richard Fabian's book `[from source] (GPP p.272, 285)`.
- Terms **not** used by GPP: "SoA vs AoS" and "ECS" as acronyms; use them as `[extrapolation]`. "Wastes 90% of the time" and "10 to 50 times" are **not** from the book (he cites about 50x in his test).

## 2. Dirty Flag (GPP p.291-305)
- Intent: avoid unnecessary work by deferring it until the result is needed `[from source] (GPP p.291)`.
- Motivation: scene graph with local transforms and **world transforms**; the ship, the crow's nest, the pirate and the parrot; recomputing the world matrices the moment each local transform changes causes many discarded computations (four moved objects generate ten world-transform computations) `[from source] (GPP p.291-294)`. Solution: a *flag* per object, set when the local one changes; when the world one is needed, recompute and clear `[from source] (GPP p.294-295)`.
- Pattern: primary data changes, costly derived data is computed from it, the flag marks the desynchronization `[from source] (GPP p.296)`. Applies to **computation** and **synchronization** (disk/network); requirements: the primary changes more often than the derived is used, and it is hard to update incrementally (if a simple running total will do, it is better) `[from source] (GPP p.296-297)`.
- Cautions: deferring too long causes a visible pause; if something fails the work may never happen (example: "unsaved" indicator in editors; autosave); you must set the flag on **every** change (cache invalidation; encapsulate the modifications); it consumes memory to keep the derived data `[from source] (GPP p.297-299)`.
- Code: `GraphNode` with `dirty_` and `world_`; when rendering, a `dirty` parameter is passed from the parent to the children, **instead of recursively marking the children** in `setTransform` `[from source] (GPP p.299-303)`. Nystrom warns that the `if` can cost due to a mispredicted branch (`[from source] (GPP p.302)`).
- Decisions: when to clear the flag (when the result is needed, at checkpoints, in the background) and the granularity (fine or coarse) `[from source] (GPP p.303-305)`. See also: web frameworks such as Angular, and physics (the "is moving" state of bodies at rest) `[from source] (GPP p.305)`.
- Careful attribution: the phrase "the flag propagates to the children" is **the opposite** of what the GPP code does.

## 3. Object Pool (GPP p.307-321)
- Intent: improve performance and memory use by reusing objects from a fixed pool instead of allocating and freeing individually `[from source] (GPP p.307)`.
- Motivation: particle system on a console/mobile device; **memory fragmentation** (14 free bytes in two blocks of 7 do not satisfy a 12-byte object); *soak tests* required by console manufacturers `[from source] (GPP p.307-308)`. The pool allocates a large block at the start and does not give it back during the game `[from source] (GPP p.308-309)`.
- Pattern and when to use: frequent creation/destruction of objects, objects of similar size, slow or fragmenting allocation, or expensive resources (connection) `[from source] (GPP p.309)`.
- Cautions: the pool may waste memory; there is only a fixed number of active objects (options when exhausted: prevent by tuning the size, do not create the object, kill an existing object, grow the pool); fixed size per slot; reused objects are not cleaned automatically; unused objects stay in memory (relevant with a garbage collector: clear references) `[from source] (GPP p.309-312)`.
- Code: `Particle` with `inUse()`, linear search O(n); **free list** reusing the memory of dead objects (union with a `next` pointer), O(1) creation `[from source] (GPP p.312-317)`. Decisions: objects coupled or not to the pool; who initializes; failure to create `[from source] (GPP p.317-320)`. Difference from Flyweight: here the reuse is over time, not simultaneous sharing `[from source] (GPP p.320)`. Data Locality (contiguous arrays) is an ally `[from source] (GPP p.321)`.
- Careful attribution: "GC pauses of 100 to 300 ms", "500 projectiles" and "zero GC impact" are **not** from GPP; the chapter treats the garbage collector only as a caveat (p.309, 312).

## 4. Spatial Partition (GPP p.322-338)
- Intent: efficiently locate objects by storing them in a structure organized by position `[from source] (GPP p.322)`.
- Motivation: strategy game; comparing all pairs is O(n²); the author shows that, in 1D, sorting by position and using binary search takes it from O(n²) to O(n log n) (and perhaps O(n) with *pigeonhole sort*) `[from source] (GPP p.322-324)`.
- Pattern, when to use (many queries by position that cause a bottleneck) and costs (reorganize when objects move; extra memory) `[from source] (GPP p.324-325)`.
- Example: **fixed grid** with doubly linked lists per cell; `Grid::move` when crossing a cell; also compare neighboring cells when there is a range (looking at only half the neighbors avoids counting the pair twice) `[from source] (GPP p.325-333)`.
- Decisions (hierarchical or flat; depends or not on the set of objects; objects only in the partition or also in another collection); quadtree and octree in detail `[from source] (GPP p.333-337)`. List of common structures: grid, quadtree, BSP, k-d tree, bounding volume hierarchy; grid as a persistent *bucket sort*, BSPs/k-d trees/BVHs as binary search trees, quadtrees/octrees as tries `[from source] (GPP p.337-338)`.
- Careful attribution: GPP does **not** state that partitioning reduces "from O(n²) to O(n)" in general, nor "ignores 99% of entities"; the gain depends on the structure and the distribution (he shows that units clustered in a corner regress to O(n²), p.334).
