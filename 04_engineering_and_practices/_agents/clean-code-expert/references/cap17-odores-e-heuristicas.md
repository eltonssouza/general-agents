# Cap. 17 — Odores e Heurísticas (Smells and Heuristics; catalog C/E/F/G/J/N/T)

Source: CL ch. 17, PDF p.280-309 (opening on p.280; C1 starts on p.281). Machine-readable catalog: `smells.json`.

## How the chapter is organized
- It starts from Martin Fowler's "code smells" (the book *Refatoração*, Refactoring) and adds the author's own heuristics, noted down while refactoring programs. (CL p.280-281)
- The list is meant to be read in sequence and also used as a reference; each heuristic has a cross reference in Appendix C. (CL p.281)
- 66 codes in 7 families: Comments C1-C5, Environment E1-E2, Functions F1-F4, General G1-G36, Java J1-J3, Names N1-N7, Tests T1-T9. Count checked against the text and Appendix C. (CL p.281-309, p.395-396)
- Conclusion: the list is not complete and does not claim to be; it expresses a value system, and clean code is not reached by following rules. (CL p.309)

## Comments (C)
- C1 Inappropriate information: change history, author, date and ticket number belong in version control or in the tracker, not in the comment. (CL p.281)
- C2 Obsolete comment: an old comment drifts from the code and gives wrong information; update it or delete it right away. (CL p.281)
- C3 Redundant comments: do not describe what the code already says (e.g. `i++` with the comment "increments i", Javadoc that repeats the signature). (CL p.281)
- C4 Poorly written comment: if it is worth writing, write it well: choose words carefully, correct grammar, no stating the obvious, brief. (CL p.282)
- C5 Commented-out code: commented-out code rots and no one deletes it; delete it, version control keeps it. The author calls it "uma abominação" (an abomination). (CL p.282)

## Environment (E)
- E1 Build requires more than one step: get the system with one command and build it with another, with no arcane scripts and no hunting for JARs and XMLs. (CL p.282)
- E2 Tests require more than one step: all the unit tests with one command or one button in the IDE; it must be fast, easy and obvious. (CL p.282)

## Functions (F)
- F1 Too many arguments: zero is best, then one, two and three; more than three is questionable and should be avoided. Refers to the section "Parâmetros de Funções" (Function Arguments) of Ch. 3 (CL p.48). (CL p.283)
- F2 Output arguments: they are unexpected; if you must change state, change the state of the object the function is called on. Refers to Ch. 3 (CL p.52). (CL p.283)
- F3 Flag arguments: a boolean declares that the function does more than one thing; eliminate it. Refers to Ch. 3 (CL p.49). (CL p.283)
- F4 Dead function: discard methods that are never called. (CL p.283)

## General (G)
- G1 Multiple languages in one source file: the ideal is one only; in practice, minimize the number and extent of the extra languages. (CL p.283)
- G2 Obvious behavior is unimplemented: the principle of least surprise; e.g. converting a day name accepting abbreviations and ignoring case. (CL p.283-284)
- G3 Incorrect behavior at the boundaries: do not trust intuition; handle every boundary condition and write a test for each. (CL p.284)
- G4 Overridden safeties: turning off compiler warnings, controlling `serialVersionUID` by hand or disabling failing tests is risky (Chernobyl analogy). (CL p.284)
- G5 Duplication: "uma das regras mais importantes neste livro" (one of the most important rules in this book) (CL p.284). DRY (Hunt and Thomas), "once and only once" (Beck; in the edition "uma vez, e apenas uma"), Ron Jeffries' second rule. Identical blocks -> methods; repeated switch/if -> polymorphism; similar algorithms -> TEMPLATE METHOD or STRATEGY. Most design patterns serve to eliminate duplication. (CL p.284-285)
- G6 Code at the wrong level of abstraction: high level at the base, details in the derived classes; the separation must be complete also across files, modules and components. A badly placed abstraction is not fixed by lying (e.g. returning zero). (CL p.285-286)
- G7 Base classes depending on their derivatives: the base must not know its derivatives, so they can be deployed in separate jars. Exception: a fixed number of derivatives (finite state machines). (CL p.286)
- G8 Too much information: small interfaces; fewer methods, fewer variables, few protected members; hide data, utilities, constants and temporaries. (CL p.286)
- G9 Dead code: impossible if, catch that never happens, utility never called, unreachable case. Delete it. (CL p.286-287)
- G10 Vertical separation: local variables right above their first use; private functions right below their first use. (CL p.287)
- G11 Inconsistency: do similar things the same way (same variable name for the same type; parallel names for parallel methods). (CL p.287)
- G12 Clutter: empty constructor, unused variables, uncalled functions, comments with no information. Remove them. (CL p.287)
- G13 Artificial coupling: do not couple for convenience (generic enum inside a specific class, general static function in a specific class). (CL p.287-288)
- G14 Feature Envy: a method that manipulates data of another object via getters/setters wants to live there. Sometimes it is a necessary evil, such as formatting a report without coupling the model to the format. (CL p.288-289)
- G15 Selector arguments: a boolean, enum or integer that chooses behavior joins several functions into one; prefer separate functions. (CL p.289-290)
- G16 Obscured intent: chained expressions, Hungarian notation and magic numbers hide the intent. (CL p.290)
- G17 Misplaced responsibility: put the code where the reader expects it; use function names to decide; if it moves for performance, the name must reflect that. (CL p.290)
- G18 Inappropriate static: static only when all the data comes from the arguments and there is no chance of polymorphism; when in doubt, not static. (CL p.290-291)
- G19 Use explanatory variables: intermediate values with explanatory names (Kent Beck); more explanatory variables is usually better. (CL p.291)
- G20 Function names should say what they do: if you must read the implementation to know, change the name or reorganize. (CL p.291-292)
- G21 Understand the algorithm: passing the tests is not enough; refactor until it is obvious that it works. (CL p.292)
- G22 Make logical dependencies physical: the dependent should explicitly ask for what it needs, not assume. The text cites G17 in the same example. (CL p.292-293)
- G23 Prefer polymorphism to if/else or switch/case: consider polymorphism before the switch; the "ONE SWITCH" rule (UM SWITCH): at most one per type of selection, creating polymorphic objects. Reconciles with Ch. 6. (CL p.294)
- G24 Follow standard conventions: a team standard based on industry norms; the code is the example, no document; what matters is that everyone agrees. (CL p.294)
- G25 Replace magic numbers with named constants: 86,400 -> SECONDS_PER_DAY; 55 lines -> LINES_PER_PAGE. Exceptions: self-explanatory formulas and very well-known numbers (5280, 8 hours); pi must come from `Math.PI`. It applies to any token with no obvious meaning, including test strings. (CL p.294-295)
- G26 Be precise: check for null, do not use floating point for money (use integers or a Money class), handle concurrency and queries with more than one result, declare List instead of ArrayList. (CL p.295)
- G27 Structure over convention: a base class with abstract methods forces implementation; a switch with well-named enums does not. (CL p.296)
- G28 Encapsulate conditionals: extract a function that explains the condition (`shouldBeDeleted(timer)`). (CL p.296)
- G29 Avoid negative conditionals: prefer the affirmative form (`shouldCompact()` instead of `!shouldNotCompact()`). (CL p.296)
- G30 Functions should do one thing: split functions with several sections; refers to "Faça Apenas uma Coisa" (Do One Thing) (CL p.44). (CL p.296-297)
- G31 Hidden temporal couplings: expose the order by making each function return what the next one receives ("bucket brigade"); the extra syntactic complexity reveals the real temporal complexity. (CL p.297-298)
- G32 Don't be arbitrary: the structure must have a visible reason; a public class nested without need is arbitrary. (CL p.298)
- G33 Encapsulate boundary conditions: no scattered +1/-1; a repeated `level + 1` becomes `nextLevel`. (CL p.298-299)
- G34 Functions should descend only one level of [abstraction]: statements at the same level, one below the function name; the author says it is perhaps the hardest heuristic. Separating levels is one of the most important and difficult tasks of refactoring. (CL p.299-300)
- G35 Keep configurable data at high levels: configuration constants and defaults at the top, passed down as arguments. (CL p.300-301)
- G36 Avoid transitive navigation: Law of Demeter / "código tímido" (shy code); avoid `a.getB().getC().doSomething()`; immediate collaborators should offer the service. Ch. 6 covers the Law of Demeter (CL p.102-103). (CL p.301)

## Java (J)
- J1 Avoid long import lists by using wildcards: with two or more classes from a package, import `package.*`; specific imports are hard dependencies; name conflicts are rare. (CL p.301-302)
- J2 Don't inherit constants: do not implement an interface just to use its constants; use static import. (CL p.302-303)
- J3 Constants versus enums: use enum instead of `public static final int`; enums can have methods and fields. (CL p.303-304)

## Names (N)
- N1 Choose descriptive names: re-evaluate names as the software evolves; according to the author, names are 90% responsible for readability (checked on the image). (CL p.304-305)
- N2 Choose names at the appropriate level of abstraction: `Modem.dial(phoneNumber)` -> `connect(connectionLocator)`. (CL p.306)
- N3 Use standard nomenclature where possible: pattern name in the class (AutoHangupModemDecorator), `toString`, project language (Eric Evans). (CL p.306-307)
- N4 Unambiguous names: `doRename` -> `renamePageAndOptionallyAllReferences`; a long name pays off. (CL p.307)
- N5 Use long names for long scopes: `i`/`j` in a scope of about five lines is fine; a larger scope calls for a longer, more precise name. (CL p.307)
- N6 Avoid encodings: no `m_`, `f`, `siv_` prefixes; no Hungarian notation. (CL p.307-308)
- N7 Names should describe side-effects: `getOos` that creates the object -> `createOrReturnOos`. (CL p.308)

## Tests (T)
- T1 Insufficient tests: test everything that could possibly break; "looks good" is not a criterion. (CL p.308)
- T2 Use a coverage tool!: it shows modules, classes and functions that are under-tested, and ifs/catches not exercised. (CL p.308)
- T3 Don't skip trivial tests: documentation value outweighs the cost. (CL p.308)
- T4 An ignored test is a question about an ambiguity: a doubt about a requirement becomes a commented-out test or one with `@Ignore`. (CL p.308-309)
- T5 Test boundary conditions: we tend to get the edges wrong, not the middle. (CL p.309)
- T6 Exhaustively test near bugs: bugs congregate. (CL p.309)
- T7 Patterns of failure are revealing: complete and ordered test cases expose patterns; refers to the SerialDate example. (CL p.309)
- T8 Test coverage patterns can be revealing. (CL p.309)
- T9 Tests should be fast: a slow test is not run and is dropped under pressure. (CL p.309)

## What the chapter does NOT say / common confusions
- It does not use the English expression "code smell"; it uses "odores". The book does not define G37+, N8+, T10+ nor names such as "Long Method", "God Class", "Shotgun Surgery" (checked across the whole book). Use G30, G8, G5 etc. as approximate equivalents [inference].
- It does not forbid switch: it limits it to one per type of selection (G23). (CL p.294)
- It does not require a constant for every number: it accepts self-explanatory formulas and very well-known numbers (G25). (CL p.295)
- It does not condemn all Feature Envy (G14) nor every base class that knows its derivatives (G7). (CL p.286, p.289)
- It does not always require a long name: `i` in a short loop is better than `rollCount` (N5). (CL p.307)
- The codes (G5 etc.) are cited in brackets in Chs. 14-16; the chapter does not state the count "66" explicitly, it comes from the enumeration [inference].
