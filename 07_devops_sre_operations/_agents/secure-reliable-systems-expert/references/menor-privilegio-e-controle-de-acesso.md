## Ch. 5 — Design for least privilege (BSRS p.97-124)

### Premise (BSRS p.97-98)
- [from source] Least privilege: the minimum access needed for the task, for humans and systems; it is most effective when applied early, in the design of new features; unnecessary privilege widens the surface for errors, bugs, and compromise and is costly to contain later (BSRS p.97).
- [from source] You cannot count on human perfection: assume any possible bad action can happen and design to minimize or eliminate the impact; thought exercise: what bad things would you do, would you be detected, how would you hide it, and what is the worst possible unintentional mistake (manual emergency commands one typo away from making the outage worse) (BSRS p.98). "Hope is not a strategy" (SRE maxim) (BSRS p.98).

### Concepts and terminology (BSRS p.98-99)
- [from source] Least privilege applies to humans, automated tasks, and machines, at all layers of authentication and authorization; it rejects implicit authority for tools and seeks to avoid ambient authority (e.g., the power to log in as root) (BSRS p.98).
- [from source] Zero trust networking: network location does not grant privilege (a jack in the meeting room gives no more access than the internet); access is granted by a combination of user and device credentials; Google implemented it at large scale via BeyondCorp (BSRS p.98-99). [DATED] The concept has consolidated as "zero trust architecture" (NIST SP 800-207, 2020, and commercial products); the book presents Google's model.
- [from source] Zero Touch: automation to remove direct human access to production roles (ZTP, ZTN); humans access production indirectly through tools and automation; requires extensive automation, secure APIs, and resilient multi-party approval systems (BSRS p.99).

### Classifying access by risk (BSRS p.99-100)
- [from source] Not all data and actions are equal: classify by impact, security risk, and/or criticality (public data, company data, user data, cryptographic secrets; administrative APIs that delete data vs read APIs); classifications clear, consistent, and known to everyone; can be ad hoc with 2-3 types or a central programmatic inventory (BSRS p.99).
- [from source] Dimensions of control: who should have access, how strict the control, what type of access (read/write), which infrastructure controls (BSRS p.100). Table 5-1: public / sensitive / highly sensitive (no standing access) x read, write, and infrastructure risk (infrastructure = administrative ability to bypass controls, such as reducing logging, changing encryption, direct SSH, restarting a service) (BSRS p.100).
- [from source] Intersection: from the reliability viewpoint you start with infrastructure controls (shutting down jobs, changing ACLs); from the security viewpoint, reading sensitive data can be just as damaging, since broad read permissions lead to mass leakage (BSRS p.100).

### Good practices: small functional APIs (BSRS p.101-103)
- [from source] Avoid open interactive interfaces; design around small, functional APIs ("each API endpoint do one thing well"), which allows granting only the permission for the specific function; API = the sum of all ways to query or modify internal state (BSRS p.101). Prefer CRUD operations on an ID over an API that accepts a programming language (BSRS p.102).
- [from source] Administrative APIs (setup/teardown; maintenance and emergency) are as important as or more important than user-facing ones and are attractive attack surfaces (BSRS p.102).
- [from source] POSIX via an interactive OpenSSH session exposes the entire POSIX API, hard to restrict and audit; auditing an interactive session (bash history, script(1)) "only keeps honest people honest", since an attacker bypasses it (e.g., running commands from inside vim); capturing syscalls via kernel audit is stronger, but difficult; the remedy is to decompose the administrative API into smaller pieces (BSRS p.102-103). You can use the OpenSSH protocol and AAA without exposing all of POSIX (e.g., git-shell) (BSRS p.103).

### Breakglass and auditing (BSRS p.103-106)
- [from source] Breakglass: emergency access that completely bypasses the authorization system; useful for unforeseen circumstances (BSRS p.103-104).
- [from source] Auditing serves to detect incorrect use of authorization (malicious operator, compromised credential, rogue software); it depends on the granularity of the access decision (what, where) and the clarity of the metadata (who, when, why) (BSRS p.104).
- [from source] Small functional APIs give the greatest advantage for auditing; good logs record granular actions (for example, the cryptographic hash of the config sent or the command executed); an interactive session on a large API or direct access to credentials makes a granular trail impossible; a culture of auditing is the antidote to broad APIs and frequent breakglass use; without a culture, audits become rubber stamps and breakglass becomes routine (BSRS p.104-105).
- [from source] Choice of auditor: needs context (knows the action and the why) and the right objectivity; balance between context and objectivity; two types at Google: (1) good practices, distributed by team (e.g., reviewing the week's breakglass in the meeting; positive social pressure; breakglass use signals the lack of a safe normal API) and (2) identification of security breaches, centralized (an advanced attacker compromises one team and jumps to another; only the cross view connects the dots; little-publicized tripwires; coordinate with Legal and HR) (BSRS p.105-106).
- [from source] Structured justification: associating audit events with structured references (bug, ticket, customer case) enables programmatic checks (e.g., support only sees data of the customer who opened the case); free text does not allow automation (BSRS p.106).

### Testing and least privilege (BSRS p.107-109)
- [from source] Two dimensions: testing least privilege (profiles such as analyst, support, SRE have enough and nothing beyond) and testing with least privilege (test infra with only the necessary access) (BSRS p.107).
- [from source] To test least privilege: describe what each profile needs (minimum access, type, permanent or temporary), describe scenarios (read, bulk read, write, delete, bulk delete, administer) with expected outcome and compare; ideally before code or ACL changes; if coverage is incomplete, monitor and alert on accesses (BSRS p.107).
- [from source] Testing with least privilege: a separate environment with its own credentials; without test infrastructure, analysts end up with read/write on real production data; ask whether they need write, whether anonymized data, test accounts, or a test environment can be used; test accounts in production confuse auditing and ACLs; start small (separate environments and credentials, limited access types, limited data exposure, short-lived cloud tests); if there is no suitable framework, people will test in production (BSRS p.107-109).

### Diagnosing access denials and graceful failure (BSRS p.109-110)
- [from source] Three outcomes for a denied access: correct denial; correct denial but with an advanced control (MPA) for temporary access; the client thinks they were wrongly denied (BSRS p.109).
- [from source] Caller with no or very limited privilege: blind denial (just 403 or equivalent) so as not to leak information about the policy; with minimal privileges: provide a token associated with the denial to trigger an advanced control or support; with more privilege: token plus remediation information for self-service; exposing too much allows reconstructing the policy; early in zero trust use tokens and have all clients contact support (BSRS p.109-110).
- [from source] Breakglass for large-scale authorization failures: highly restricted (generally SRE), available only from specific locations (panic rooms with additional physical controls), uses closely monitored, tested regularly (BSRS p.110).

### Worked example: configuration distribution (BSRS p.110-114)
- [from source] Good practices: config in version control, code review, automated distribution first to canaries, canary health check and then gradually across the fleet; this requires giving update access to the automation (BSRS p.110-111).
- [from source] Table 5-2 compares API surface, complexity, scale, auditability, and ability to express least privilege for four alternatives (BSRS p.111): (1) POSIX via OpenSSH: simple and common, but the automation can stop the server, run another binary, read data; bugs cause a coordinated outage; a compromised credential equals compromising all servers (BSRS p.111). (2) Software update API (e.g., .deb package via apt-get in cron): reuses binary distribution infrastructure (canary, health check, signing, provenance); there may be conflicting needs (e.g., an IP deny list that must converge quickly) that require two mechanisms (BSRS p.112). (3) OpenSSH ForceCommand: a script receives the config on STDIN, validates it, and restarts; minimal API over a robust protocol; logging the file or its hash captures the entire action; scales poorly to many actions; better to go straight to gRPC or Thrift instead of creating your own RPC (BSRS p.112-113). (4) Custom HTTP receiver: sidecar (flexible, more code and one more daemon, with AAA such as gRPC with SSL or SPIFFE) or in-process (more flexible, similar to Google, requires code in the binary) (BSRS p.113).
- [from source] Tradeoffs: a smaller API does not prevent pushing arbitrary config by a compromised role, but the mechanism does not allow the compromise implicitly; sign the config independently of the automation that pushes it, segmenting trust; add a bearer token from a central rate limiter, independent of the automation and per host, to protect against bugs in the automation; the independent rate limiter is reusable (binary rollout, reboot) (BSRS p.113-114).

### Policy framework for authentication and authorization (BSRS p.114-117)
- [from source] Authentication = verifying identity; authorization = evaluating whether the request from an authenticated party should be allowed; reuse existing strong cryptographic mechanisms (simple: URL parameter; preshared; complex schemes such as TLS 1.3 and OAuth); the result is a "role" (BSRS p.114-115).
- [from source] Attributes for the authorization decision: action, arguments, origin, role metadata (geography, jurisdiction, ML risk assessment), and server context (request rate, capacity) (BSRS p.115).
- [from source] ACL is the classic form; MFA and MPA require more complex code; separate the authorization decision from business logic with frameworks such as AWS or GCP IAM; Google uses an internal variant of the GCP framework; code does simple checks against an external policy; changing controls becomes a configuration change (BSRS p.115-116). [DATED] IAM services and their names have changed; check current documentation.
- [from source] Shared authorization library: MFA or MPA for all endpoints with one change; apply to a percentage of actions with a config change; require MPA for potentially unsafe actions, similar to code review, helps against insiders and enables a rapid response without broad unilateral access; standardization eases team mobility (BSRS p.116).
- [from source] Pitfalls: a too-simplistic policy language scatters decisions across the code; too general is hard to reason about; use iterative design; consider how the policy is distributed (probably the most security-sensitive configuration, updatable independently of the binary); developers need help from security and SRE for policy decisions (BSRS p.116-117).

### Advanced controls (BSRS p.117-122)
- [from source] Beyond yes/no, a "maybe" with additional checking relieves pressure; use in isolation or combined according to data sensitivity, action risk, and business processes (BSRS p.117).
- [from source] MPA: prevents mistakes, discourages bad actors (discipline for employees, risk of detection for outsiders), raises the cost of the attack (compromising another person or creating a change that passes review), serves auditing if reviews are recorded tamper-evidently, brings comfort to customers (BSRS p.117). Broad MPA (joining a group) can serve as breakglass; prefer granular authorization against small APIs, since the approver knows exactly what they are authorizing (BSRS p.118).
- [from source] MPA pitfalls: approvers need sufficient context (who does what; watch out for phone screens); social pressure (manager, senior); mitigate with after-the-fact escalation and independent auditing of a percentage of approvals; ensure that technology and social dynamics allow saying no (BSRS p.118).
- [from source] Three-factor authorization (3FA): the weakness of MPA in a large organization is that all the "multiple" use the same centrally managed workstations; two separate workstations are expensive and hard to maintain; alternative: approval on a hardened mobile platform for very risky operations; requirements: at least two platforms, ability to approve on two, harden at least one; the 3FA service receives the RPC, presents it on the mobile device, and returns a cryptographically signed approval; users tolerate restrictions on mobile (BSRS p.118-119). MPA protects against a unilateral insider and compromise of one workstation; 3FA protects against broad workstation compromise but not against insiders on its own; combining the originator's 3FA with a simple web MPA from a second party gives strong defense with little overhead (BSRS p.119-120). 3FA is not 2FA/MFA: it strengthens the authorization of a specific request, not the user's authentication (BSRS p.120).
- [from source] Business justifications: tie access to a structured justification (bug, incident, ticket, case, assigned account); anti-pattern in immature organizations: support with access to all customer records; better to block by default and release with verifiable need, evolving along a gradient (open ticket, then specific customer, specific data, with deadline and customer approval) (BSRS p.120). Generic justifications ("Team foo needed access") should trigger an alarm in auditing; if finding an approver is hard, engineers create dangerous behaviors (BSRS p.121).
- [from source] Temporary access: by schedule (on-call, expiring groups) or on demand; combines with MPA and justification; creates a logical audit point and data to reduce requests; reduces ambient authority (sudo and "Run as Administrator" instead of root) (BSRS p.121).
- [from source] Proxies (bastion): when there are no fine-grained controls on the backend, use a restricted, heavily monitored proxy; emergency rollback example: peer approval of each command, access only to the relevant machines, workstation without internet, more detailed logging (BSRS p.121-122).

### Tradeoffs and tensions (BSRS p.122-123)
- [from source] Security complexity increases; have tools to define, manage, analyze, distribute, and debug policies and know how to answer "does this user access this data?" and "who accesses this data?" (BSRS p.122).
- [from source] Collaboration and culture: broad access to source code brings risk but also learning and transparency (makes it harder for inadequate code to go unnoticed); include source code in data classification (BSRS p.122).
- [from source] Quality of the data feeding decisions (roles, groups, customer attributes, ML training, API sensitivity): bad data leads to wrong decisions (BSRS p.123). Productivity: the best posture is the one the user does not notice; make it easy to navigate the new steps and understand denials (BSRS p.123). Complexity for developers: training, documentation, quick access to security engineers; third-party software may require a layer that enforces the policy (BSRS p.123).

### Conclusion: key components (BSRS p.123-124)
- [from source] Knowledge of the functionality to classify by risk; fine-grained partitioning of the system and of access (small APIs are necessary); an authentication system; an authorization system with a well-defined policy; advanced controls (temporary, multi-factor, multi-party); minimum operational requirements: audit all access and generate signals for detection and historical forensics, reason about/define/test/debug the policy with end-user support, and breakglass; plus an organizational commitment and a dedicated security function (BSRS p.123-124).
