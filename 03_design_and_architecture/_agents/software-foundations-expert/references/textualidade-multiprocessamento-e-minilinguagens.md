# Textuality, multiprogramming and minilanguages

Source: TAUP chs. 5, 7 and 8 (PDF pages; printed page = PDF − 2; see `INDEX.md`). The book is from 2003; whatever depends on the era is marked `[DATED]`.

## 1. Textuality (TAUP ch. 5, PDF p.132-160)
- `[from source]` (TAUP p.132): the chapter deals with two linked problems, file formats for persistent data and application protocols between cooperating programs; both involve *serializing* in-memory structures (marshaling/unmarshaling), because memory addresses lose meaning outside memory and native formats create interoperability problems (*big/little endian* byte order, 32 vs 64 bits).
- `[from source]` (TAUP p.133): the design themes are interoperability, transparency, extensibility and storage/transaction economy; interoperability and transparency call for clean representations rather than implementation convenience or maximum performance; extensibility also favors textual protocols.
- `[from source]` (TAUP p.134): when you feel the urge to design a complex binary format or protocol, it is "wise to lie down until the urge passes"; if the worry is performance, compressing the textual stream usually gives a cleaner and maybe faster design. Text "tends to make the system future-proof": numeric ranges are not imposed by the format (example: IPv4 with 32-bit addresses, TAUP p.134).
- `[from source]` (TAUP p.134-135): the only good justification for binary is manipulating data sets large enough to worry about bit density or the time/instruction budget for interpreting the data (examples: large images and multimedia; the X protocol). The book adds that much of these cases is "premature-optimization fever" and that compact binary formats tend to be poorly extensible.
- `[from source]` (TAUP p.135-138): case studies: the Unix password file (one record per line, colon-separated fields; the gain of ~8% from a binary does not pay off; it allows editing with any editor and using `grep`, TAUP p.136), `.newsrc` (TAUP p.137-138) and PNG (a format in self-describing *chunks* that dispenses with a version number, TAUP p.139).
- `[from source]` (TAUP p.139-146): file metaformats: DSV (delimited text), RFC 822, cookie-jar, record-jar, XML and INI; recommendation to use an existing metaformat instead of an idiosyncratic format (TAUP p.139). Good practices include a version number or self-describing *chunks* and care with floating-point rounding in binary↔text conversion (TAUP p.149).
- `[from source]` (TAUP p.150-160): design of application protocols (SMTP, POP3, IMAP; HTTP as a universal protocol; BEEP; XML-RPC/SOAP) is in this range (table of contents, PDF p.7).
- `[extrapolation]`: JSON and YAML are **not** cited in TAUP (empty text search). v1 used them as examples of "key-value pairs" attributed to the book; they may be used as modern examples, labeled.

## 2. Multiprogramming: cooperating processes vs threads (TAUP ch. 7, PDF p.190-216)
- `[from source]` (TAUP p.190): "multiprogramming" (a term the author revives to avoid confusion with multiprocessors) is the modularization technique characteristic of Unix: dividing large programs into cooperating processes; Unix encourages it by (1) making it cheap to create processes, (2) offering means of communication (shellouts, I/O redirection, pipes, message passing, sockets) and (3) encouraging simple, transparent textual data formats.
- `[from source]` (TAUP p.191): in systems where starting processes is expensive (example VAX VMS), one is forced to build monoliths; the trend in Unix was to reduce the cost of `fork(2)`. The cost of partitioning is having to design the protocols between processes well ("bugs accumulate at the interfaces", p.191).
- `[from source]` (TAUP p.192): using concurrency for performance before having a clean architecture is premature optimization; **threads** (processes that share the same address space) are "a performance hack" which, according to the book, increases overall complexity and should be avoided except under great need; partitioning into processes also helps security (separating the part that needs `setuid` from the part that does not, TAUP p.192).
- `[from source]` (TAUP p.193-194): the simplest form of cooperation is delegating to a specialist program (*shelling out*), for example calling the editor named in `EDITOR`; the scale runs from simple techniques to more complex ones and the author recommends proving with prototypes and benchmarks that the simpler techniques are not enough before using the more complex ones (TAUP p.193).
- `[from source]` (TAUP p.194): Doug McIlroy's invention of the *pipe* influenced the design of Unix and the socket abstraction; programs written as *filters* read from standard input and write to standard output (descriptors 0 and 1).
- `[from source]` (TAUP p.213-215): about threads: Unix has no native tradition of threads; from the point of view of controlling complexity, they are a poor substitute for lightweight processes with their own address spaces; managing contention and critical regions in the shared space is hard and a source of bugs; there is no automatic encapsulation; they can cost as much in locking as the context switching they were meant to avoid; thread standards are weak (in 2003) and programs with threads are not portable.
- `[from source]` (TAUP p.216): the book's conclusion: using threads within processes should be a "last resort, not a first"; prefer limited shared memory with semaphores, asynchronous I/O with SIGIO, or `poll(2)`/`select(2)`.
- `[inference]`: the "fault isolation advantage" (a *segfault* in one process does not take down the others) is a consequence of the separate address space, but the book does **not** state it as an argument on p.193 (v1 attributed it there). `copy-on-write` also does not appear in the TAUP text; it is `[extrapolation]`.
- `[DATED]`: comments on the state of thread standards and on "famously efficient" Linux at creating processes (TAUP p.191, p.215) are from 2003.

## 3. Minilanguages (TAUP ch. 8, PDF p.217-250)
- `[from source]` (TAUP p.217): Unix has a long tradition of domain-specific "little languages" (troff, eqn, tbl, pic, grap; awk, sed, dc, bc; make, yacc, lex); the traditional term is *minilanguage*, kept to remind us to keep these designs small and simple. The book cites studies according to which the defect density per line is independent of the language, so that more expressive languages imply fewer bugs (TAUP p.217).
- `[from source]` (TAUP p.218): three paths to a minilanguage: two good ones (realizing at the start that a compact notation raises the level of the specification; realizing that a specification format is becoming a language) and a dangerous one (arriving at it by extending, feature by feature; notorious example: `sendmail.cf`; also TECO → Emacs Lisp).
- `[from source]` (TAUP p.219-221): **taxonomy of languages** (figure 8.1): data files (from simple, like `/etc/passwd` and `.newsrc`, to serialized, like PNG/SNG), declarative languages (m4, makefile, yacc/lex, XSLT), imperative domain languages (typesetting; `bc`/`dc`, explicitly Turing-complete) and general-purpose interpreters (Emacs Lisp, JavaScript, then shell, Tcl, Perl, Python, Java). The v1 taxonomy ("declarative formats / interpreted languages / compiled languages and document processors") is **not** the book's.
- `[from source]` (TAUP p.244-246): when designing: when the domain primitives are simple and stereotyped and users' combinations are fluid; keep it as simple as possible (prefer a structured data file to a minilanguage that modifies external data); embedded features can be abused (JavaScript, Word macros); avoid "accidentally Turing-complete" languages; consider extending/embedding an existing scripting language (more suitable for imperative than for declarative ones, p.246).
- `[from source]` (TAUP p.47-48): the Rule of Generation (programs that write programs, with *parser/lexer generators* as the classic example) and, at TAUP p.44, the Rule of Representation (data in place of logic) are the rules to which minilanguages connect; chapter 9 (PDF p.251) deals with data-driven programming and code generation.
- `[DATED]`: `JavaScript` in the chapter is described as a language embedded in 2003 browsers (TAUP p.243).

## 4. What the book does not say
- It does not define "dynamic scope". It does not cite JSON/YAML. It does not claim that the text stream is "the" universal interface in all cases: it acknowledges exceptions (justified binaries, TAUP p.134-135).
