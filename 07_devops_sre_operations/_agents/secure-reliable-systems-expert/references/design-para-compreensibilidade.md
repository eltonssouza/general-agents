## Ch. 6 — Design for understandability (BSRS p.125-155)

### Definition and why it matters (BSRS p.125-126)
- [from source] Understandability: the degree to which a person with relevant technical background can reason accurately and confidently about the system's operational behavior and invariants, including security and availability (BSRS p.125-126). It can vary by property (understanding high load is easier than understanding malicious inputs) (BSRS p.125).
- [from source] Benefits: reduces the chance of vulnerabilities or resilience failures when changing the system; eases incident response (assessing damage, containing, remediating the root cause); increases confidence in security claims, expressed as invariants ("for all possible behaviors"), which tests alone rarely demonstrate; abstract reasoning is required (BSRS p.126).

### Invariants (BSRS p.127-129)
- [from source] System invariant: a property that is always true, no matter how the environment behaves or misbehaves (malicious users, hardware failures); the system is fully responsible for guaranteeing it (BSRS p.127).
- [from source] Examples of desired properties: only authenticated and authorized users access the data store; operations on sensitive data are audited; values from outside the trust boundary are validated or encoded before injection-prone APIs; backend queries scale proportionally to frontend queries; the frontend degrades gracefully if the backend does not respond; an overloaded component returns an overload error instead of crashing; the system only receives and sends RPCs to designated systems (BSRS p.127).
- [from source] If the property is not an invariant there is a weakness: a handler without an access check is a vulnerability; a frontend with fast retries and no backoff creates a self-inflicted denial-of-service attack (BSRS p.127-128).
- [from source] Analyzing invariants: tradeoff between potential damage and effort; tests and code reading give little confidence (classes such as SQL injection, XSS and buffer overflow remain on top lists; "absence of evidence is not evidence of absence"); at the other extreme, formal proofs (e.g., a verified microkernel in ~20 person-years) are rarely feasible for large-scale application software (BSRS p.128). The book's practical middle ground: explicitly design for understandability, allowing informal but well-grounded arguments (BSRS p.129).

### Mental models (BSRS p.129-130)
- [from source] Engineers build mental models that omit irrelevant details, but models based on typical operation fail in extreme conditions (attack, overload, component failure), which is where security and reliability are analyzed; example: memory thrashing (BSRS p.129).
- [from source] Design so that the mental model remains predictive: new components must be consistent with the models of existing subsystems; example: run production servers without disk swap, so that an allocation failure is a fast error attributable to memory pressure (BSRS p.129-130).

### Complexity x understandability (BSRS p.130-133)
- [from source] The main enemy is unmanaged complexity; some complexity is inherent (Google: tens of thousands of engineers and over a billion lines of code; Gmail as an example of a complex feature set); features are not cut for security, but complexity is compartmentalized and contained to allow high-fidelity reasoning about relevant properties (BSRS p.130-131).
- [from source] Break into smaller components and reason about each in isolation, deriving properties of the whole; this depends on the structure, interfaces and trust relationships between components (BSRS p.131-132).
- [from source] Centralized responsibility: horizontal requirements (auditing, metrics, authentication, authorization) implemented in every component are hard to verify; move them to a central component (library or framework, e.g., an RPC framework enforces authentication, authorization and logging via central policy); for cascading failures use time-outs, deadlines, retries with safeguards, and automatic deadline and cancellation propagation in the framework; benefits: the reviewer looks in one place and there is a lower chance of a wrong ad hoc implementation; the upfront cost is amortized across applications (BSRS p.132-133).

### System architecture (BSRS p.133-135)
- [from source] Layers and components allow reasoning in blocks; tightly coupled components are as hard as a monolith; pay as much attention to boundaries and interfaces as to components (BSRS p.133).
- [from source] The temptation to trust callers of internal APIs; if security depends on preconditions guaranteed by callers, all call sites must be understood; the fewer assumptions about callers, the better; if they are unavoidable, make them explicit in the interface or restrict which principals can interact (BSRS p.133-134).

### Understandable interface specifications (BSRS p.134-136)
- [from source] Prefer narrow, typed interfaces (gRPC, Thrift, OpenAPI) over free-form JSON; they enable tooling, cross-references, conformance checks and safe evolution (protocol buffers have compatibility guidelines; OpenAPI has versioning); without an explicit specification, independently updated client and server may interpret the payload differently and break; it hinders automated auditing that correlates authorization policies (example cited: Istio Authorization Policy) with the exposed surface (BSRS p.134-135).
- [from source] Common object model (like Kubernetes'): base invariants, standard ways of scoping, annotating, referencing and grouping, consistent operations, custom types that can be reasoned about with the same model (BSRS p.135).
- [from source] Idempotency: an operation that gives the same result if applied several times; important because operations may arrive out of order or the response may be lost; if idempotent the client can retry until it succeeds; a simpler mental model for developers and responders; operations can be made idempotent by including a unique identifier (UUID) in mutating RPCs (BSRS p.135-136).

### Understandable identities, authentication and access control (BSRS p.136-141)
- [from source] Every system must identify who has access to which resources; identity = set of attributes or identifiers of an entity; credentials assert the identity (password, X.509 certificate, OAuth2 token); large systems need to identify all active entities (humans, software components, hardware), not only humans (BSRS p.136).
- [from source] IP is not suitable as an identifier in microservices (unstable, spoofable, shared hosts, reusable ports) (BSRS p.137).
- [from source] Identifiers with properties that benefit security and reliability: understandable (e.g., widget-store-frontend-prod instead of 24245223; errors and malicious intent become more visible), robust against spoofing (certificate with key in hardware such as a TPM in a TLS session vs password or bearer token over a cleartext channel) and non-reusable (an ex-admin's email reassigned to a new hire inherits privileges) (BSRS p.137-138).
- [from source] Meaningful identifiers serve auditing (who accesses what) and reliability (planning and enforcing use of shared resources); a single organizational identity system avoids competing systems; identity can be outsourced via OpenID Connect, trading simplicity for dependence on trusted providers (BSRS p.138).
- [from source] Google's identity model: administrators (humans who change state), machines (physical), workloads (scheduled by Borg, normally with an identity different from the machine's) and customers (BSRS p.138-139). A global directory integrated with SSO, a machine inventory, a group that releases the software image tied to whoever logs in as root; orchestration ensures the requester can schedule the workload with that identity and enforces machine restrictions; workloads must not have root on the machine (BSRS p.139-140). Customers have their own subsystem and OpenID Connect to authenticate to endpoints outside Google (BSRS p.140).
- [from source] Authentication and transport security are complex: engineers must understand abstractions and APIs; ALTS provides automatic service-to-service authentication and transport security without configuration, with the application running as a meaningful identity (administrator, machine or workload) and an API to obtain information about the authenticated peer (Istio cited as similar); without a systematic approach the auditor would have to read all the code (BSRS p.140-141).
- [from source] Access control via declarative frameworks reinforces common knowledge, handles interactions with multiple identities (Ingress, Frontend, Backend chain plus authenticated customer) and enables tools that assess exposure of services and data (impossible with ad hoc logic) (BSRS p.141).

### Security boundaries and TCB (BSRS p.141-147)
- [from source] TCB (trusted computing base): the set of components (hardware, software, humans) whose correct operation suffices to enforce the security policy; it must uphold the policy even if what is outside behaves arbitrarily or maliciously; the interface between the TCB and the rest is the security boundary; treat everything that crosses it with suspicion, including message order (BSRS p.141-142). The TCB depends on the policy (kernel and privileged daemons for OS separation between users; the application code, for the application's document sharing policy) (BSRS p.142).
- [from source] Keep the TCB small, excluding components that do not participate in the policy; unnecessary components in the TCB add risk (BSRS p.143).
- [from source] Widget store example: a monolithic application with a single database puts the entire application, the database server and the kernel in the TCB for the property "only the user themselves accesses their addresses"; risks: SQL injection in catalog search or RCE in the web server (CVE-2010-1870 cited) (BSRS p.143-144). Splitting into microservices (web frontend, catalog backend, purchasing backend, each with its own database), the TCB shrinks to the purchasing backend and its database; the catalog attacker does not reach payment data; microservices treat every request as not necessarily trusted and use workload identity and ALTS (BSRS p.144-145).
- [from source] The TCB depends on the threat model and the interface: if the purchasing backend hands over any address on request from the frontend, the frontend enters the TCB; alternative: require an end-user context ticket (EUC), a short-lived internal ticket issued by a central authentication service in exchange for an external credential, so that a compromised frontend only reaches users active at the moment of the attack (BSRS p.145-146). Under the web security model, an origin (host, protocol, port) is a trust domain (same-origin policy): XSS in the catalog reaches checkout if they share an origin; solution: frontends on distinct origins (widgets.example.com and checkout.example.com) (BSRS p.146-147).
- [from source] TCBs and understandability: a TCB must be isolated, with a clean interface and correctness that can be reasoned about in isolation; if correctness depends on assumptions outside the component's control, it is by definition not a TCB; a TCB is usually its own failure domain (Ch.8) (BSRS p.147).

### Software design (BSRS p.147-155)
- [from source] Application frameworks (full-stack, "batteries included") bundle canonical subframeworks with reasonable defaults and a guarantee that they work together; example of danger: a service with RPC and authentication but no authorization policy, open to any authenticated client; the framework must guarantee a valid authorization policy and a default that denies whoever was not explicitly allowed; functionality a framework should cover: request dispatch and deadline propagation, input sanitization, authentication/authorization/auditing of data access, logging, health, quotas, balancing, binary and config deploys, testing, dashboards and alerts, capacity planning, planned outages (BSRS p.148-149).
- [from source] Complex data flows: strings carry implicit assumptions (well-formed URL, https scheme); instead of a string use types whose contract asserts the property (e.g., a Url type created by Url.parse that validates or fails); reduces the amount of code to understand; but type encapsulation in common languages is not a security boundary (reflection and casts) and only holds against non-malicious errors; the rest is guaranteed by repository controls, code review, hardening (BSRS p.149-150).
- [from source] Injection: use types such as SafeSql and SafeHtml for values proven safe in a sink; constructors and builders guarantee the contract (runtime validation and correct-by-construction design, templates with context-sensitive escaping); sinks accept these types (and, if they accept strings, must validate or encode); with that one can argue that the entire application is free of SQL injection or XSS by understanding only the types and the sink APIs; Ch.12 details this (BSRS p.150-152).
- [from source] API usability: secure-by-construction APIs have a double benefit (understandability and culture); the developer gains by not being responsible for security invariants; example: HTML template with contextual autoescaping (BSRS p.152-153).
- [from source] Tink: Google's cryptographic library; crypto is prone to subtle errors (e.g., a decryption oracle from combining cipher and authentication incorrectly); principles: secure by default (the API does not allow nonce reuse in GCM), usability, readability and auditability, extensibility, agility (key rotation and scheme deprecation), interoperability; integrates with KMS (Cloud KMS, AWS KMS, Android Keystore) and does not accept raw key material; limit: does not prevent higher-level design errors (e.g., protecting with a hash data from a small set such as a card number or CPF/SSN instead of authenticated encryption) (BSRS p.153-154). Developers and reviewers must understand what the library or framework does and does not guarantee (BSRS p.155).
- [from source] Conclusion: "reliability" here means upholding all critical guarantees (availability, durability, security invariants); strategies: narrow, consistent, typed interfaces; consistent authentication, authorization and accounting; clear identities for active entities; frameworks and types that encapsulate invariants; SREs need to know the security invariants and, in extreme cases, may have to take a service down during a security incident, sacrificing availability (BSRS p.155).
